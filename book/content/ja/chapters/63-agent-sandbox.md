# 63 Agent Sandbox: コーディングエージェントを AWS の隔離環境で動かす

コーディングエージェントは、モデルが自分で選んだコマンドを実行します。手元のノート PC で動かせば、そのコマンドは、持ち主の AWS の認証情報、SSH の鍵、ほかのリポジトリと同じ場所で動きます。この章は、エージェントを動かす場所を AWS の中に作ります。仕事 1 つにつき環境を 1 つ作って終わったら捨て、その中から届くものを、モデルと、頼まれたリポジトリと、パッケージレジストリだけにします。

題材は Claude Code です。Claude Code について書くことは、公開されているドキュメントに書かれていることに限りました。ドキュメントで確かめられなかったことは、確かめていないと書きます。そして、この章ではエージェントを一度も起動しておらず、モデルも一度も呼んでいません。手元で動かして確かめたのは、起動するかどうかの判断、許可リストの評価、IAM ポリシーの評価、スタックの中身です。

**スタックを置いておくだけなら、料金は 1 か月におよそ USD 0.09 です**（東京、定価。内訳は[料金](/ja/chapters/63-agent-sandbox/wrap.md)にあります）。タスクは仕事があるときだけ動き、30 分のタスク 1 つの Fargate の料金は USD 0.03 ほどで、モデルの料金のほうがずっと大きくなります。時間課金になるのは、タスクが外へ出るための経路です。NAT Gateway、インターフェースエンドポイント、Network Firewall のどれを置くかで、1 か月に USD 20 から USD 292 かかります。経路は [11章](/ja/chapters/11-network.md)のスタックと、この章のコンテキストのフラグで決めます。

前提は [11章](/ja/chapters/11-network.md)の VPC、[21章](/ja/chapters/21-security.md)の IAM とシークレット、[41章](/ja/chapters/41-fargate.md)の単発のタスク、[36章](/ja/chapters/36-bedrock.md)の推論プロファイルと IAM、[19章](/ja/chapters/19-observability.md)のログです。コードは `examples/63-agent-sandbox/` にあります。

## 何から守るのか

<!-- section: 63.threats -->

エージェントが間違ったことをする理由を、Claude Code のドキュメントは 2 つ挙げています。処理した内容に埋め込まれた指示に従ってしまうこと（プロンプトインジェクション）と、モデルの誤りです。ドキュメントは例として、リポジトリの README に書かれた変わった指示を、Claude Code が自分の行動に取り込んでしまう場合を挙げています。モデルはこれに耐えるよう作られていると書いたうえで、それでも防御を重ねることを勧めています。

この章は、エージェントがいつか間違ったコマンドを実行するものとして設計します。そのとき何が起きるかを、種類に分けて考えます。

- **プロンプトインジェクション。** 指示は、クローンしたリポジトリのファイル、取得した Web ページ、インストールしたパッケージの説明文から入ってきます。入口をすべて塞ぐことはできないので、従ってしまったあとに届く範囲を狭くします
- **持ち出し。** エージェントが読めるものは、外へ送れます。読めるのは、リポジトリのコード、環境変数、タスクが持つ認証情報です。送り先を絞るのが出口の許可リストで、読めるものを減らすのが権限の設計です
- **壊すコマンド。** ファイルを消す、ブランチを書き換える、AWS のリソースを消す、といったコマンドです。ファイルはタスクと一緒に捨てるので構いません。ブランチは GitHub の側のルールで守り、AWS は IAM で守ります
- **止まらない料金。** エージェントは、放っておくと動き続けます。モデルの料金と、タスクの時間の料金の両方に、外から止める上限を置きます
- **サプライチェーン。** `npm install` は、他人が書いたコードを実行します。エージェントを使わなくても起きることですが、エージェントはパッケージを自分で選んで入れます。これも、実行されたあとに届く範囲の問題として扱います

どれも、同じ答えに行き着きます。エージェントの中身を信用するのではなく、エージェントが動く場所から届く範囲を、外側の仕組みで決めておくことです。Claude Code 自身にも権限の仕組みとサンドボックスがあり、この章でも使います。ただし、それはエージェントと同じプロセスが守る内側の壁です。外側の壁を、AWS の側に作ります。

この章の不変条件は 1 つです。**エージェントが中から何をしても、本番のデータとデプロイ用のロールには届かない。** スタックのテストと、この章で書く小さなポリシーの評価器が、これを固定します。

## 全体像

<!-- section: 63.architecture -->

```figure
caption: 仕事 1 つにつきタスクを 1 つ起動する。タスクから届くのは、モデルと、リポジトリ 1 つと、パッケージレジストリだけ
node person: 依頼する人 | lambda:InvokeFunction
node launcher: ランチャー | Lambda
node secret: GitHub App の鍵 | Secrets Manager
node task: エージェントのタスク | Fargate, 1 vCPU, 4 GB
node model: Bedrock | 推論プロファイル 1 つ
node git: GitHub | リポジトリ 1 つ
node logs: CloudWatch Logs | 実行ロールが書く
node reaper: リーパー | Lambda, 1 分ごと
edge person -> launcher: 依頼
edge launcher -> secret: 鍵を読む
edge launcher -> task: RunTask
edge task -> model: InvokeModel
edge task -> git: clone, push, pull request
edge task --> logs: 標準出力
edge reaper -x task: StopTask
group sandbox: 本番ではないアカウント = launcher, secret, task, logs, reaper
mark task
```

登場するものを、順に説明します。

**ランチャー**は Lambda の関数です。依頼を受け取り、許可されたリポジトリか、上限の内側かを確かめ、通ったときだけ、そのリポジトリ 1 つに限った 1 時間で切れるトークンを GitHub に作らせ、タスクを 1 つ起動します。

**タスク**は Fargate の単発のタスクです。決まったイメージから起動し、リポジトリをクローンし、Claude Code を 1 回実行し、変更があれば作業用のブランチをプッシュしてプルリクエストを開き、終了します。ファイルシステムは読み取り専用で、書き込める場所は、タスクと一緒に消えるボリュームだけです。

**タスクロール**は、エージェントが持つ AWS の権限です。固定した推論プロファイル 1 つでモデルを呼べます。ほかには何もできません。自分のログを書く権限も持たせていません。ログは、コンテナの外にいる実行ロールが書きます。

**リーパー**は、1 分ごとに動く Lambda の関数です。期限を過ぎたタスクと、1 日の予算を使い切ったあとのタスクを、外から止めます。

上限は 1 か所にまとめてあります。

<<< @/examples/63-agent-sandbox/src/config.ts{limits}

どの数字も、タスクが暴走する経路の 1 つに対応しています。`maxMinutes` が 50 なのは、GitHub のトークンが作ってから 1 時間で切れるからです。タスクは、クローンに使ったトークンで最後にプッシュします。50 分で止めれば、起動とプッシュに 10 分残ります。

スタックは、コンテキストでイメージのタグを渡さなければ、ECR のリポジトリだけを作ります。タグを渡すと残りができますが、既定の構成に時間課金のリソースはありません。

## 実行環境に Fargate のタスクを選ぶ理由

<!-- section: 63.isolation -->

仕事 1 つにつき環境を 1 つ作るやり方は、いくつかあります。Claude Code のドキュメントは、隔離の技術を強さの順に並べています。コンテナは設定しだいで、gVisor と仮想マシンは正しく設定すれば強い、という整理です。コンテナは Linux の名前空間で分けるだけで、ホストとカーネルを共有します。カーネルに脆弱性があれば、コンテナの外に出られる可能性があります。仮想マシンは自分のカーネルを持ちます。

AWS で選べるのは、次の 3 つです。

**EC2 のインスタンスの上のコンテナ。** 1 つのインスタンスで仕事をいくつも動かすと、仕事どうしがカーネルを共有します。前の仕事が残したものを、次の仕事が拾う余地も残ります。この章の目的には合いません。

**仕事ごとの EC2 のインスタンス。** インスタンスは仮想マシンなので、仕事ごとにカーネルが分かれます。[23章](/ja/chapters/23-ec2.md)の道具で作れます。代わりに、AMI を自分で更新し、起動を待ち、インスタンスプロファイルの認証情報がインスタンスメタデータから取れることを前提に設計し、終わったインスタンスを確実に消す仕組みを持つことになります。

**Fargate のタスク。** ECS のドキュメントは、Fargate はワークロードごとに隔離された仮想の環境を用意し、タスクはネットワークインターフェース、エフェメラルストレージ、CPU、メモリをほかのタスクと共有しないと書いています。[41章](/ja/chapters/41-fargate.md)で引いた別のページには、カーネルも共有しないとあります。利用者も AWS の運用者も、タスクを動かしているホストには接続できません。

この章は Fargate のタスクを選びます。仕事ごとの境界が、ホストを持たずに手に入るからです。終わったタスクの後片付けも要りません。料金は秒単位で、仕事が無いあいだは何もかかりません。

Fargate を選ぶと、できなくなることもあります。

- 特権コンテナは使えず、追加できる Linux の capability は `SYS_PTRACE` だけです。Claude Code の参考用の dev container は、コンテナの中のファイアウォールで出口を絞りますが、ドキュメントによればそれには `NET_ADMIN` と `NET_RAW` が要ります。Fargate ではこの方法が取れないので、出口はタスクの外で絞ります
- コンテナの中でコンテナは動かせません。テストに Docker が要るリポジトリの仕事は、この環境ではできません
- 起動のたびにイメージ全体を取得します（41章）。起動には数十秒かかるはずですが、計っていません

タスクという境界が守らないものも、はっきりさせておきます。境界の内側では、エージェントは、タスクロールの認証情報、リポジトリのトークン、タスクから届くネットワークを、すべて使えます。ECS のドキュメントのとおり、タスクロールの認証情報は、コンテナの中から決まったアドレスに問い合わせれば取れます。隔離が守るのは、ほかの仕事とホストです。エージェントに持たせたものは守りません。したがって、この章の設計の大半は、持たせるものを減らす作業です。

Firecracker のような microVM については、Claude Code のドキュメントが仮想マシンの選択肢として名前を挙げています。AgentCore Runtime のドキュメントは、セッションごとに専用の microVM を割り当てると書いています。Fargate については、この章で読んだページは「隔離された仮想の環境」と書くだけで、技術の名前を挙げていません。Fargate の下で何が動いているかは [67章](/ja/chapters/67-firecracker.md)が扱います。

## 自分で作らないほうがよい場合

<!-- section: 63.when -->

この章の構成は、自分のアカウントの中で、自分で決めた権限とネットワークでエージェントを動かしたい場合のものです。部品がいくつもあり、どれも自分で持ち続けることになります。次のどれかに当てはまるなら、そちらが先です。

**Claude Code のクラウドのセッション。** Claude Code には、Anthropic が管理する仮想マシンでセッションを動かす機能があります。ドキュメントによれば、セッションごとに隔離された仮想マシンで動き、ネットワークは既定の許可リストに絞られ、GitHub のトークンはサンドボックスの外のプロキシが持ちます。トークンをエージェントに渡さないという点は、この章の構成より強い設計です。Claude のサブスクリプションが必要で、モデルは Bedrock 経由ではありません。同じセッションを自分のインフラで動かす self-hosted environments もあります。2026-10-13 時点で Team と Enterprise のプランの公開ベータで、隔離、出口の制御、Git の認証情報は、動かす側の責任だと書かれています。その責任の中身が、この章で扱うことです。

**AgentCore Runtime。** [50章](/ja/chapters/50-agentcore.md)の AgentCore Runtime は、セッションごとに専用の microVM を割り当て、セッションが終わると microVM を終了してメモリを消去すると書いています。呼び出しに応答するエージェントを、サービスとして載せるための実行環境です。クローンして変更してプルリクエストを出す、という 1 回きりの仕事には、タスクのほうが素直に合います。エージェントを自分のアプリの機能として提供するなら、50章を読んでください。

**Cloudflare と Vercel のサンドボックス。** どちらにも、エージェントが書いたコードを動かすための環境があります。Cloudflare のドキュメントは、Sandbox のコンテナは自分のカーネルとネットワークを持つ microVM で、Worker から起動し、インターネットに出られるかどうかを Worker が決めると書いています（2026-10-13 時点。Workers Paid プランで使え、スケジューリングの方式は公開ベータ）。Vercel Sandbox は、隔離された Linux の microVM でエージェントが生成したコードを動かすと書いています。アプリがすでにそこにあり、エージェントが VPC の中のものや IAM に触る必要がないなら、移る理由はありません。

**GitHub Actions。** プルリクエストへの反応としてエージェントを動かすだけなら、GitHub がホストするランナーで足ります。ランナーを自分の AWS で持つ話は [62章](/ja/chapters/62-ci-runners.md)にあります。ランナーも「渡されたものを何でも実行する場所」なので、設計の要点はこの章と重なります。

AWS で自分で作る理由になるのは、モデルの呼び出しを自分の AWS アカウントの Bedrock に閉じたいこと、出口を自分のネットワークの決まりで絞りたいこと、記録を自分の CloudTrail と CloudWatch Logs に残したいこと、のどれかです。

実装は[しくみと実装](/ja/chapters/63-agent-sandbox/build.md)と[実装のつづき](/ja/chapters/63-agent-sandbox/more.md)に、料金と注意点は[費用、注意点、片付け](/ja/chapters/63-agent-sandbox/wrap.md)にあります。
