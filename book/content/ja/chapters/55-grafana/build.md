# 55 Grafana: しくみと実装

[前のページ](/ja/chapters/55-grafana.md)で、サインインの条件と料金、Grafana を足す理由を見ました。このページでは、ダッシュボードの定義を 1 つにするところから、ワークスペースへ届けるところまでを実装します。

## 定義を 1 つにする

<!-- section: 55.definition -->

守りたいことは 1 つです。**2 つのダッシュボードは、同じメトリクスを、同じ統計と同じ周期で読む。** これがこの章の不変条件（invariant）です。

19章のダッシュボードは、19章の `Monitoring` コンストラクトが CDK の API で組み立てていて、この章からは変えません。そこで、ダッシュボードに何が載っているかを、CDK にも Grafana にも寄らない形で書き直します。

<<< @/examples/55-grafana/src/signals.ts{types}

`Resource` は、API、関数、テーブルの 3 つです。この 3 つの名前はデプロイするまで決まらないので、定義では名前の代わりに「どのリソースか」を書いておきます。`Signal` は、その線が利用者の何を表すかの分類で、流量（traffic）、エラー（errors）、遅さ（latency）、飽和（saturation）の 4 つです。飽和は、スロットリングや同時実行数のように、上限にどれだけ近いかを表します。19章のダッシュボードをこの 4 つで読み直すと、上の段には利用者が感じる流量とエラーと遅さだけがあり、飽和は下の段に並んでいます。

<<< @/examples/55-grafana/src/signals.ts{rows}

DynamoDB の `ThrottledRequests` と `SystemErrors` は、操作ごとにしか出ないメトリクスです。19章はこれを 5 つの操作の合計として 1 本の線にしているので、定義にも `sum` の形を用意しました。

この定義が 19章のダッシュボードと本当に同じかどうかは、書いた人の注意ではなく、テストで確かめます。まず、定義から CloudWatch のダッシュボードのボディを組み立てる関数を書きます。

<<< @/examples/55-grafana/src/cloudwatch.ts{body}

テストは、19章のスタックをその場で synth して、テンプレートに入っているダッシュボードのボディを取り出し、この関数の出力と丸ごと比べます。ウィジェットの数、位置、タイトル、メトリクス、統計、周期、ラベルのどれか 1 つでも違えば落ちます。19章のダッシュボードに線を足した人は、この章のテストが落ちるので、定義も直すことになります。

デプロイした後にも、同じ検査を使います。

<<< @/examples/55-grafana/src/cloudwatch.ts{read}

`readCloudWatchBody` は、デプロイ済みのボディから、リージョンと 3 つのリソースの名前を読み取ります。19章のスタックは関数やテーブルの名前を出力していないので、名前の出どころを、名前が実際に使われている場所にしました。`agreeingDashboard` は、読み取った名前を定義に当てはめてボディを組み立て直し、元のボディと等しいときだけ名前を返します。コンソールで誰かが線を足したダッシュボードは、ここで断られます。

## Grafana のダッシュボードを生成する

<!-- section: 55.dashboard -->

Grafana のダッシュボードは、1 つの JSON です。パネルが並び、パネルごとにデータソースへのクエリ（Grafana のことばで target）が入っています。CloudWatch のクエリは、次の形です。

<<< @/examples/55-grafana/src/grafana.ts{target}

項目の名前と意味は、Grafana のリポジトリにある CloudWatch データソースの型定義（v13.0.9 のタグ）から取りました。Managed Grafana は、バージョン 13 のワークスペースが 13 系のどのリリースで動いているかを公開していないので、13.0 系のタグを 1 つ選んで読んでいます。

`matchExact` は、指定したディメンションだけを持つメトリクスに限る設定です。外すと Grafana は検索の式を組み立て、条件に合うメトリクスを 100 個まで描きます。別の API の線が紛れ込まないように、常に `true` にします。

<<< @/examples/55-grafana/src/grafana.ts{dashboard}

合計の線は、CloudWatch の metric math をそのまま使います。部品のクエリに `id` を付けて隠し（`hide`）、式のクエリが `getitem + putitem + ...` と ID で足し合わせます。CloudWatch のダッシュボードと同じ式です。

決めたことが 3 つあります。

`uid` は固定です。Grafana は `uid` でダッシュボードを見分けるので、何度反映しても同じダッシュボードが置き換わります。

`editable` は `false` です。正本はリポジトリの定義なので、ワークスペースの画面からは直させません。画面で直したい変更は、定義を直して反映し直します。

`schemaVersion` は 41 です。これは Grafana 12.0 が書く値で、13.0.9 は 42 を書きます。公式ドキュメントは、API から入れた古い形のダッシュボードが、読み込まれるときに新しい形へ自動で移されると説明しています。

19章のダッシュボードと揃えていないものも 1 つあります。19章は Lambda の同時実行数を右の軸に描いていますが、Grafana の側では軸を分けていません。読むメトリクスは同じで、見た目だけが違います。

## ワークスペースとロール

<!-- section: 55.workspace -->

CloudFormation が Managed Grafana のために持っているリソースは、ワークスペースの 1 種類だけです。利用者の割り当て、サービスアカウント、データソース、ダッシュボード、アラートのルールは、どれも CloudFormation のリソースではありません。スタックで作るのはワークスペースとロールまでで、中身は次の節の HTTP API で入れます。

<<< @/examples/55-grafana/infra/bin/app.ts{context}

`authentication` に既定値はありません。渡さなければワークスペースは作られず、スタックにはロールだけが入ります。サインインの方法を選ぶことが、そのまま課金を始める合図になるようにしました。

<<< @/examples/55-grafana/infra/lib/grafana-stack.ts{role}

ワークスペースに渡すロールです。信頼ポリシーは、Grafana のサービスのうち、このアカウントのこのリージョンのワークスペースだけに引き受けを許します。条件を付けないと、Grafana のサービスであれば誰のワークスペースのためでも引き受けられる形になります。

<<< @/examples/55-grafana/infra/lib/grafana-stack.ts{actions}

権限は 2 つのアクションだけです。ワークスペースの権限の持たせ方には、サービスに任せる方法（service managed）と、自分でロールを渡す方法（customer managed）があります。任せると、CloudWatch には AWS 管理ポリシーの `AmazonGrafanaCloudWatchAccess` が付き、ログの読み取りやアラームの参照、EC2 のタグの読み取りまで入ります。この章のパネルが使うのはメトリクスの取得だけなので、自分で渡すほうを選びました。どちらのアクションもメトリクスの ARN を指定できないので、リソースは `*` です。ログを見るパネルを足すときは、そのロググループを読む権限をここに足します。

この 2 つで足りるかどうかは、実際のワークスペースでは確かめていません。

<<< @/examples/55-grafana/infra/lib/grafana-stack.ts{workspace}

残りの設定を順に見ます。

ネットワークについて。ワークスペースは、既定ではどのアドレスからも届きます。サインインは必要ですが、サインインの画面までは誰でも来られます。`-c prefixListIds=pl-...` でマネージドプレフィックスリストを渡すと、そこに載っているアドレスからだけ届くようになり、それ以外には 403 が返ります。プレフィックスリストに書いたプライベートアドレスの範囲は無視されるので、VPC の中から開くにはワークスペース用のインターフェースエンドポイントを作って許可します。この章では作っていません。

プラグインについて。`pluginAdminEnabled` を `true` にすると、ワークスペースの管理者がカタログからプラグインを入れられます。プラグインはデータのすぐ隣で動くコードで、ドキュメントも、コミュニティのプラグインを入れる判断と責任は利用者の側にあると書いています。この章のダッシュボードは最初から入っているものだけで描けるので、`false` にしました。

バージョンについて。選べるのは 9、10、12、13 です。`grafanaVersion` を省くと、作るときにサービスが最新を選びます。上げることはできますが、下げることはできません。更新は取り消せず、最長 10 分ほどのあいだワークスペースは読み取り専用になります。プラグインは一緒には更新されません。`-c grafanaVersion=...` に渡す文字列の正しい形は、この章では確かめていません。

## ダッシュボードを届ける

<!-- section: 55.provision -->

Grafana の HTTP API を呼ぶには、サービスアカウント（service account）のトークンが要ります。サービスアカウントは、人の代わりにプログラムが使う利用者で、管理者、編集者、閲覧者のどれかの役割を持ちます。料金の上でも利用者 1 人として数えられます。

トークンには期限があり、最長で 30 日です。公式ドキュメントは、数時間かそれ以下を勧めています。この章は、もっと短くします。

<<< @/examples/55-grafana/src/provision.ts{token}

トークンは、反映のたびに 15 分の期限で発行し、使い終わったら消します。**どこにも保存しません。** 発行するのは `aws grafana create-workspace-service-account-token` で、これは IAM の権限で呼ぶ AWS の API です。つまり、Grafana に書き込めるかどうかは、結局 AWS の認証情報で決まります。CI から反映するなら、[20章](/ja/chapters/20-shipping.md)の OIDC のロールにこの API を許し、パイプラインの中で発行して消します。長く持つシークレットは、どこにもできません。

どうしてもトークンを置いておく必要があるなら、置き場所は [21章](/ja/chapters/21-security.md)の Secrets Manager です。その場合も 30 日で切れるので、入れ替える仕組みが要ります。期限の切れたトークンは、消すまでワークスペースあたり 100 個の上限に数えられます。

<<< @/examples/55-grafana/src/provision.ts{call}

トークンを載せて送る先は、ワークスペースのエンドポイントだけです。エンドポイントはスタックの出力から取り、ホスト名以外の形（パス、ポート、ユーザー情報つき）は受け付けません。リダイレクトにも従いません。従うと、`Authorization` ヘッダーがリダイレクト先に渡るからです。失敗したときのメッセージには、Grafana が返した文言だけを入れ、送ったリクエストは入れません。

<<< @/examples/55-grafana/src/provision.ts{datasource}

データソースは、無ければ作ります。`authType: "default"` は AWS SDK の既定の認証で、Managed Grafana のドキュメントによると、ワークスペースに渡したロールの権限が使われます。アクセスキーは Grafana に渡しません。データソースを足せるのは管理者だけなので、このサービスアカウントの役割は管理者です。権限が大きいぶん、トークンの寿命を短くしてあります。

<<< @/examples/55-grafana/src/provision.ts{save}

ダッシュボードは `overwrite: true` で送ります。同じ `uid` のダッシュボードがワークスペースにあれば、誰が直したものでも置き換わります。正本を 1 つにする以上、これは意図した動作です。

`vp run grafana:push` は、ここまでの部品を順に呼びます。19章のダッシュボードのボディを CloudWatch から読み、定義と一致しなければそこで止まります。一致すれば、トークンを発行し、データソースを確かめ、ダッシュボードを送り、成功しても失敗してもトークンを消します。

バージョン 13 には、ダッシュボードを Git のリポジトリと双方向に同期する Git Sync もあります。ワークスペースの画面での編集をプルリクエストにできる機能ですが、この章では試していません。

## アラートはどちらが持つか

<!-- section: 55.alerts -->

Grafana にもアラートがあります。ルールがデータソースにクエリを送り、条件を満たした状態が続くと通知を出す仕組みで、バージョン 12 以降のワークスペースでは常に有効です。ルール、通知先、通知のポリシーは、ダッシュボードと同じようにコードから入れられます。HTTP API（`POST /api/v1/provisioning/alert-rules` など）か Terraform を使い、API から入れたルールは、既定ではワークスペースの画面から編集できません。

ただし、この章ではルールを作っていません。人を呼び出すのは、19章の 2 つのアラームのままにします。理由は 3 つあります。

1 つ目は、同じ条件を 2 か所に書けないことです。19章のアラームは、直近 5 分のうち 3 分が閾値を超えたら鳴ります。Grafana のルールにあるのは pending period で、条件を満たした状態が途切れずに続いた時間を数えます。3 分と書いても、「5 分のうち 3 分」にはなりません。データが無いときの扱いも、CloudWatch の `notBreaching` と Grafana の `NoData` の状態では仕組みが違います。両方に似たルールを置くと、片方だけが鳴る夜が来ます。

2 つ目は、5xx の割合の式です。19章は metric math で `errors / requests` を計算しています。Managed Grafana のドキュメントには、ほかのクエリを参照する式のクエリからはアラートのルールを作れないとあります。Grafana の側で式を組み直すことになり、これも 2 つ目の定義です。

3 つ目は、評価する場所です。CloudWatch のアラームは、ワークスペースの有無に関係なく評価されます。Grafana のルールは、ワークスペースが評価します。ワークスペースを消せばルールも消え、ワークスペースが CloudWatch を読めなくなれば、ルールは `NoData` か `Error` になります。

Grafana のアラートが向いているのは、条件が CloudWatch のメトリクスだけでは書けないときです。Prometheus のメトリクスや Athena の集計を条件にしたい、複数のデータソースをまたいで 1 つのルールにしたい、という場合がそれに当たります。そのときも、1 つの症状を呼び出すルールは 1 か所だけにします。ルールのインスタンスは、ワークスペースあたり 100 個までです。

通知を SNS に出すなら、ワークスペースのロールに `sns:Publish` が要ります。権限をサービスに任せた場合に作られるポリシーは、名前が `grafana` で始まるトピックにだけ publish を許します。19章のトピックへ出したいなら、この章のロールにそのトピックの ARN を足します。

## 手元で確かめる

<!-- section: 55.local -->

AWS のアカウントも、Grafana も要りません。

```bash
vp test run examples/55-grafana
vp run grafana:render
vp run grafana:render --cloudwatch
vp run grafana:infra:synth
```

`grafana:render` は、生成したダッシュボードの JSON を表示します。リソースの名前は `API_ID` のような仮の値です。`--cloudwatch` を付けると、同じ定義から組み立てた CloudWatch のボディを表示します。`grafana:infra:synth` は、ロールだけのテンプレートを `cdk.out` に書きます。`-c authentication=AWS_SSO` を付ければ、ワークスペース入りのテンプレートになります。synth は AWS に問い合わせません。

テストが確かめているのは、次のことです。

- 定義が、19章のテンプレートのダッシュボードと完全に一致する
- 統計を変えた、線を足した、別のテーブルが混ざったダッシュボードを、`agreeingDashboard` が断る
- 生成したダッシュボードが、19章と同じメトリクスだけを読む
- スキーマが、知らない項目、重なったパネル、存在しないクエリを指す式を断る
- トークンが `Authorization` ヘッダーにだけ入り、ホスト名でないエンドポイントには何も送られない
- 既定のスタックにワークスペースが無く、ロールの権限が 2 つのアクションだけである

手元で再現していないのは、Grafana そのものです。生成した JSON を本物の Grafana が受け取って線を描くかどうか、HTTP API の応答が偽物と同じ形かどうかは、ワークスペースを作らないと分かりません。API の呼び出しのテストは、ドキュメントの例に合わせて自分で書いた偽の `fetch` に対するものです。
