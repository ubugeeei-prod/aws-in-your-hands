# 33 Production Readiness: しくみと実装

[概要のページ](/ja/chapters/33-production-readiness.md)で、点検の項目を 3 通りの確かめ方に分けました。このページでは、そのうちの 1 つ目、合成したテンプレートを読む検査を作ります。最後に、19章のスタックに本番向けの設定を当てて、検査を通る形にします。

同じ目的の道具は、すでにあります。cdk-nag は、CDK のアプリや CloudFormation のテンプレートを、ルールの組（AWS Solutions、HIPAA Security、NIST 800-53 など）で検査します。CloudFormation Guard は、専用の言語で書いたポリシーで JSON や YAML を検証します。デプロイした後の状態については、AWS Config の管理ルールの一覧に `dynamodb-pitr-enabled` や `cw-loggroup-retention-period-check` といった名前が並んでいます。どれも説明を読んだだけで、この本では動かしていません。

この本のリポジトリの中にも、検査が 2 つあります。`vp check` には awscdk-lint の recommended のルールが入っていて、変数から作ったコンストラクトの ID のような、CDK のコードの書き間違いを見つけます。[21章](/ja/chapters/21-security/build.md)の `sec:iam:lint` は、テンプレートの中の IAM のワイルドカードを見つけます。

それでも小さな検査を自分で書くのは、テンプレートを読む検査に何が見えて何が見えないかを、手を動かして知るためです。ルールは 10 個で、どれもこの本の前の章が決めたことを確かめるものです。実際のプロジェクトでは、既製の道具から始めて、足りないルールだけを書くほうが早いでしょう。

## テンプレートを読む

`vp run <name>:infra:synth` は、CDK のコードを CloudFormation のテンプレートにして、`cdk.out` に `<スタック名>.template.json` という名前で書き出します。検査の入力は、このファイルです。

テンプレートは外から来る値なので、形を確かめてから読みます。

<<< @/examples/33-production-readiness/src/template.ts{template}

`Resources` を必須にしてあるのは、空のオブジェクトを渡された検査が「指摘なし」と答えては困るからです。何も読まなかった検査は、通ったことになりません。同じ考え方は、このあと何度か出てきます。

オブジェクトの検査には、21章の `jsonObject` と `jsonEntries` を使っています。Valibot の `v.object` は配列も受け取り、`v.record` は `constructor` のような名前のキーを黙って落とします。論理 ID を 1 つでも読み落とす検査では困るので、21章が書いた厳しいほうをそのまま import しました。

ルールが読むのは、プロパティの値と、リソース同士のつながりです。つながりは、組み込み関数の `Ref`、`Fn::GetAtt`、`Fn::Sub` を辿って集めます。

<<< @/examples/33-production-readiness/src/template.ts{references}

値のほうには、注意が 1 つあります。テンプレートの値は、リテラルとは限りません。`RetentionInDays` に `{ "Ref": "RetentionDays" }` と書いてあれば、実際の日数が決まるのはデプロイのときで、テンプレートを読んでもわかりません。

<<< @/examples/33-production-readiness/src/template.ts{setting}

### スタックと一緒に消えるデータ

<<< @/examples/33-production-readiness/src/rules/data.ts{stateful-delete}

この本のスタックは、どれも `RemovalPolicy.DESTROY` でした。練習が終わったら何も残さないためです。本番では逆で、スタックを消す操作が、データを消す操作を兼ねていては困ります。

見るのは 2 つの属性です。`DeletionPolicy` は、スタックを消したとき、またはテンプレートからリソースを外したときに、実物をどうするかを決めます。CloudFormation のドキュメントによると、書かなければ消されます。例外は `AWS::RDS::DBCluster` と、クラスターに属さない `AWS::RDS::DBInstance` で、この 2 つは書かなくてもスナップショットが取られます。

もう 1 つの `UpdateReplacePolicy` は見落としやすい属性です。プロパティの中には、変えるとリソースが作り直されるものがあります。CloudFormation は新しいリソースを先に作り、そのあと既定では古いほうを消します。テーブルの名前を 1 文字変えただけのデプロイが、古いテーブルを中身ごと消すわけです。`DeletionPolicy` を `Retain` にしていても、この削除は止まりません。そのため、片方だけが `Retain` のリソースも指摘にしています。

対象の種類は、中身をリポジトリから作り直せないものに限りました。テーブル、バケット、データベース、ボリューム、ユーザープール、シークレット、鍵、ロググループです。キューや関数は入れていません。ECR のリポジトリも、イメージはソースから作り直せるので外してあります。この線引きは、この本の判断です。

2 つの属性の意味は CloudFormation のドキュメントで読んだもので、実際にスタックを消して確かめてはいません。この本がふだん使う cdkd も、固定した版のコードの中で 2 つの属性を読んでいますが、こちらも動かして確かめてはいません。

### 公開されたバケット

<<< @/examples/33-production-readiness/src/rules/data.ts{bucket-public}

バケットについては、テンプレートが公開を止めているかを見ます。`PublicAccessBlockConfiguration` の 4 つの設定がすべて `true` と書いてあれば通ります。書いていないバケットが公開されているとは限りません。S3 のドキュメントによると、新しいバケットは既定では公開されませんし、アカウント全体の設定もあります。それでも指摘にするのは、テンプレートからは止めていると言えないからです。

バケットポリシーは、`Principal` が `*` の `Allow` で、`Condition` のないステートメントを指摘します。`Condition` があるステートメントは通します。条件が「この VPC エンドポイントから」なのか、実質的に誰でも通る条件なのかを、この検査は評価しません。条件付きで全員に開いているポリシーは、人が読む必要があります。

このルールには、書いている途中で見つけた誤りがありました。最初の実装は、ステートメントの形を Valibot の `v.looseObject` で確かめていました。`v.looseObject` は配列をオブジェクトとして受け取り、キーが `0`、`1` のオブジェクトに変えてしまいます。CDK はステートメントを必ず配列で書くので、配列の中のステートメントは 1 つも検査されず、テストは通っていました。テストが使っていたのが、配列に入れていない 1 つだけのステートメントだったからです。見つけたのは、条件の判定をわざと壊してもテストが落ちなかったときです。いまは 21章の `jsonObject` で確かめていて、テストは両方の形を通します。

### 過去に戻せないテーブル

<<< @/examples/33-production-readiness/src/rules/data.ts{table-pitr}

[22章](/ja/chapters/22-recovery.md)が有効にした point-in-time recovery です。グローバルテーブル（`AWS::DynamoDB::GlobalTable`）では、設定がレプリカごとにあるので、すべてのレプリカを見ます。ある Region では有効で別の Region では無効、という状態を作れるからです。グローバルテーブルそのものは [28章](/ja/chapters/28-multi-region.md)の範囲です。

このルールが通っても、戻せるとは限りません。確かめているのは設定が書いてあることだけで、復元を試したかどうかは、テンプレートには現れません。

## 関数を見ているアラーム

<!-- section: 33.watching -->

「アラームのない関数」を見つけるルールは、素直に書くと役に立ちません。[19章](/ja/chapters/19-observability.md)のアラームは、関数ではなく API に付いているからです。19章は、原因（関数のエラー）ではなく症状（利用者に返った 5xx の割合と遅さ）にアラームを付けました。関数の `Errors` にアラームがないことを指摘すると、19章の判断を誤りと呼ぶことになります。

そこで、関数の代わりに見ていてよい場所を、テンプレートのつながりから求めます。

<<< @/examples/33-production-readiness/src/rules/watching.ts{watch-points}

関数そのもの、関数を統合先にしている HTTP API、関数に仕事を渡しているキューと、そのキューのデッドレターキューです。[20章](/ja/chapters/20-shipping.md)のスタックのように、API がエイリアスを呼んでいる場合は、エイリアスから関数まで辿ります。

<<< @/examples/33-production-readiness/src/rules/watching.ts{function-alarm}

テンプレートの中のどのアラームも、これらの場所を 1 つも見ていなければ、指摘になります。

辿る経路は、この 3 つだけです。スケジュール、SNS のトピック、ステートマシン、バケットの通知から呼ばれる関数は、呼び出し元にアラームがあっても指摘になります。[08章](/ja/chapters/08-async.md)の掃除の関数のように時計で動く関数は、失敗しても気づく利用者がいないので、関数そのものにアラームが要る、という判断です。イベントバスやトピックから呼ばれる関数（[25章](/ja/chapters/25-events.md)の範囲です）についても、同じ扱いになります。

アラームがあっても、誰にも届かなければ意味がありません。

<<< @/examples/33-production-readiness/src/rules/watching.ts{alarm-recipient}

指摘になるのは 3 つの場合です。`AlarmActions` がない。`ActionsEnabled` が `false`。通知先のトピックがテンプレートの中にあり、そのトピックを誰も購読していない。19章のスタックは、メールアドレスを渡さずにデプロイすると 3 つ目の状態になります。19章が「アラームが鳴っても何も届きません」と書いていた状態を、デプロイの前に見つけるルールです。

通知先が ARN の文字列や、ほかのスタックからの import のときは、何も言いません。その先に人がいるかどうかは、このテンプレートからは見えないからです。購読があっても、確認メールのリンクを押していなければ届きませんが、それもテンプレートには現れません。

## 本番向けの設定を当てる

<!-- section: 33.twins -->

検査が通るスタックを 1 つ用意します。新しいアプリは作りません。19章のスタックのクラスを、そのまま 2 回使います。

<<< @/examples/33-production-readiness/infra/bin/app.ts{twins}

`AihReadyPractice` は、19章が書いたとおりのスタックです。`AihReadyProduction` は同じクラスに、本番向けの設定を当てたものです。どちらも読むために合成するスタックで、デプロイのタスクは用意していません。通知先の既定値が `oncall@example.com` になっているのも、そのためです。`example.com` は予約されたドメインで、どこにも届きません。

設定を当てる部分は、CDK の Aspect で書きました。

<<< @/examples/33-production-readiness/infra/lib/production-settings.ts{aspect}

Aspect は、スタックの中のコンストラクトを 1 つずつ訪ねる仕組みです。テーブルを見つけたら PITR と削除保護を有効にして `Retain` にし、ロググループを見つけたら保持期間を 90 日にして `Retain` にします。`applyRemovalPolicy` は、`DeletionPolicy` と `UpdateReplacePolicy` の両方を書きます。

19章のファイルを書き換えずに済ませるために Aspect を使いましたが、利点はほかにもあります。Aspect は合成のときに動くので、あとからスタックに足したテーブルにも同じ設定がかかります。テストで、Aspect を付けたあとにテーブルを足して、それにも PITR が付くことを確かめています。「新しいテーブルを作った人が設定を忘れる」という、いちばんありがちな抜けを塞げます。

とはいえ、自分のスタックなら、設定はテーブルを作る場所に直接書くほうが読みやすくなります。Aspect が向いているのは、組織のすべてのスタックに同じ決まりをかけたいときです。

90 日という保持期間は、この章が選んだ値で、推奨値ではありません。決め方は 19章の[料金のページ](/ja/chapters/19-observability/wrap.md)にあります。どこまで遡って調べたいかと、どこまで残してよいかで決めます。

Aspect が変えるのは既存のリソースの設定だけで、リソースは 1 つも足しません。2 つのスタックのリソースの種類を比べると、違いは通知先の購読（`AWS::SNS::Subscription`）の 1 つだけです。これもテストで固定しています。

次のページで、2 つのスタックと、本のすべてのスタックに検査を当てます。
