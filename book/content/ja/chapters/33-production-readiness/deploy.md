# 33 Production Readiness: デプロイ

この章にデプロイするスタックはありません。このページに書くのは、ほかの章のスタックを本番のアカウントにデプロイする前に確かめることです。[概要のページ](/ja/chapters/33-production-readiness.md)の 8 つの分野を順に見ていきます。

項目ごとに、無いと何が起きるか、どう確かめるか、どの章が作業をしているかを書きます。テンプレートの検査で見られる部分は[前のページ](/ja/chapters/33-production-readiness/local.md)までで扱ったので、ここではアカウントを読むタスクと、人への問いが中心になります。出てくるタスクは、どれもこの章では実行していません。25章以降の章は、それぞれの章が扱う範囲だけをもとに挙げています。

同じ一覧は `vp run ready:review` でも読めます。

## アカウントと環境

<!-- section: 33.accounts -->

最初に確かめるのは、どのアカウントが本番で、そこで誰が何をできるかです。ここが曖昧なままだと、ほかの分野の対策は、強い権限を持つ 1 人の操作ミスで全部消えます。Well-Architected のセキュリティの柱は、これを SEC01-BP01（アカウントでワークロードを分ける）として挙げ、アカウントの境界を、セキュリティ、請求、アクセスを分ける強い境界だと説明しています。

### 本番だけのアカウント

この本のスタックは、すべて 1 つのアカウントに入れてきました。[20章](/ja/chapters/20-shipping.md)は環境ごとにスタックを分けましたが、同じアカウントに置くかぎり、分かれているのは名前だけです。練習用のスタックを消すコマンドの宛先を 1 文字間違えると、本番のテーブルに届きます。権限の広すぎるロールも、同じアカウントのすべてのデータに届きます。

確かめ方は、本番のアカウントの ID を言えるかどうかです。この本のタスクは、AWS に触る前に宛先のアカウントを表示し、`.env` の `AIH_AWS_ACCOUNT_ID` と違えば止まります。

```bash
vp run account:whoami
```

アカウントを増やして Organizations でまとめる話は、[21章の「組織になったら」](/ja/chapters/21-security/more.md)にあります。AWS は、複数のアカウントでの構成についてのホワイトペーパーも公開しています。この本では、冒頭を読んだだけで、勧められている構成を試してはいません。

### root ユーザー

root ユーザーのパスワードが漏れると、アカウントも、請求も、その中のバックアップも相手のものになります。MFA を付け、アクセスキーを作らず、ふだんの作業には使いません。[01章](/ja/chapters/01-account.md)で済ませた設定ですが、アカウントを増やすと、アカウントの数だけ root ユーザーも増えます。

```bash
vp run sec:posture
```

21章のこのタスクは、root ユーザーに MFA がないとき、アクセスキーがあるときに失敗します。タスクが答えられないのは、MFA の機器がどこにあって、ほかに誰が使えるかです。

### 消せない記録

管理者のロールを奪った人が最初にするのは、自分の操作の記録を消すことです。CloudTrail の証跡を止める操作を、本番のアカウントの中からはできないようにしておきます。道具は Organizations の SCP で、21章にポリシーの JSON とテストがあります。21章が書いているとおり、実際の組織に付けて確かめてはいません。テンプレートにもタスクにも現れない項目なので、確かめ方は「このアカウントに、どの SCP が効いているか」を答えられるかどうかです。

## identity と最小権限

<!-- section: 33.identity -->

セキュリティの柱の SEC03-BP02（最小権限を与える）にあたる分野です。

### 動いているコードの権限

インターネットからのリクエストを処理する関数のロールに `*` があると、その関数の穴 1 つが、`*` の届く範囲すべての穴になります。テンプレートの検査の `iam-wildcard` が見るのは、ここです。中身は [21章](/ja/chapters/21-security/build.md)の lint で、`*` を残すアクションには理由を書きます。

人の権限は、テンプレートには出てきません。デプロイを CI のロールに移した（20章）あとで、まだ管理者の権限を持っている人が誰で、何のために要るのかを答えられるようにします。SEC03-BP02 は、開発者が本番に入るのは作業のあいだだけに限り、終わったら取り消す形を、目指す状態として書いています。

### 期限のない鍵

アクセスキーは期限のない秘密です。ノートパソコンのバックアップや CI のログに残ったキーは、誰かが気づくまで使えます。この本は、人には 01章の `aws login` を、CI には 20章の OIDC を使い、アクセスキーを 1 つも作っていません。確かめるのは、IAM ユーザーにアクセスキーが残っていないか、残っているなら何が使っているかです。この本には、それを一覧にするタスクはありません。

### 呼び出し元

[06章](/ja/chapters/06-auth.md)は、API のすべてのルートで呼び出し元を確かめ、自分のノートにしか届かないことをテストで固定しました。ここが崩れると、ID を 1 つ推測するだけで他人のノートが読めます。これはアプリのコードの性質で、テンプレートからはほとんど見えません。検査が見るのは、関数 URL の `AuthType` だけです。

あとから足した機能は、同じ不変条件を別の経路で破ることがあります。検索は、その典型です。検索が他人のノートを返さないことは [27章](/ja/chapters/27-search.md)の範囲です。人への問いは、「認証なしで開いているルートはどれで、何を返すか」です。

## データ

<!-- section: 33.data -->

信頼性の柱に、REL09-BP04（定期的に復元して、バックアップと手順を確かめる）があります。そのページが挙げる失敗の例は、「バックアップがあると思い込む」ことと、「復元はしたが、中のデータを読んで確かめていない」ことです。

### 復元を一度は試す

PITR を有効にしただけでは、戻せるかどうかはわかりません。戻し方を知っている人がいるか、戻すのに何分かかるか、戻したテーブルにアプリを向け直せるかは、やってみるまでわかりません。初めての復元が本番の障害の最中になると、手順書を読みながら作業することになります。

[22章](/ja/chapters/22-recovery.md)が、訓練の手順とタスクと記録用のファイルを用意しています。

```bash
vp run recovery:status
vp run recovery:drill new first
```

テンプレートの検査の `table-pitr` が見るのは、設定の有無だけです。22章にも書いてあるとおり、この本の著者は AWS に対する復元を 1 回も実行していません。つまり、この項目はこの本のアプリについても、まだ満たされていません。

### スタックと一緒に消えない

`stateful-delete` のルールが見る項目です。スタックを消す操作、あるいはリソースを作り直す更新が、データを消します。22章のスタックは `-c protect=on` で `RETAIN` と削除保護が付き、この章の Aspect は同じ設定をスタック全体にかけます。

`Retain` には代償があります。CloudFormation のドキュメントによると、残されたリソースは、スタックを消したあとも存在し続け、料金もかかり続けます。消すときは、手で消すことになります。人への問いは、「データを持つスタックはどれで、それを消せるのは誰か」です。

### 公開されていない

`bucket-public` のルールが見る項目です。この本のバケットは、[03章](/ja/chapters/03-spa.md)から一貫して公開を止めていて、読む経路は CloudFront か署名付き URL（[07章](/ja/chapters/07-uploads.md)）だけです。テンプレートから見えないのは、アカウント全体の公開ブロックの設定です。

### 保持と削除

データをどれだけ残すかは、残しすぎても問題になります。利用者がアカウントを消したあと、その人のデータがどこに、いつまで残るかを書き出します。この本のアプリでは、少なくとも次の場所があります。

- テーブルのアイテム。消しても、PITR が有効なら最大 35 日は復元できる（22章）
- バケットのオブジェクト。バージョニングが有効なら、消したあとも古いバージョンが残る。22章のスタックは 30 日で消す
- ログ。保持期間のあいだ残る。何をログに書かないかは [19章](/ja/chapters/19-observability/more.md)が決めている
- 分析用に流したイベントの写し（[26章](/ja/chapters/26-analytics.md)の範囲）と、検索用の索引（[27章](/ja/chapters/27-search.md)の範囲）

テンプレートの検査が見るのは、ロググループの保持期間が書いてあるかどうかだけです。その日数が約束と合っているかは、人が決めます。

### データのある Region

[28章](/ja/chapters/28-multi-region.md)のように複製を足すと、データの置き場所が増えます。[36章](/ja/chapters/36-bedrock.md)が扱う、Region をまたぐ推論の設定も同じで、リクエストが処理される Region が増えます。利用規約や契約で「データは日本に置く」と約束しているなら、写しを持つ Region と、処理する Region を挙げられるようにします。

### 鍵の持ち主

保存時に暗号化されている、という事実は、誰が読めるかについて何も言いません。どの鍵で暗号化され、その鍵を誰が使えるかが問題です。自分で管理して無効にできる鍵が要るデータがあるかどうかは、21章の「鍵の持ち主」の節で判断します。

## 障害

<!-- section: 33.failure -->

### 気づくこと、届くこと

アラームがなければ、止まっていることを最初に知らせてくれるのは利用者です。アラームがあっても、通知先に誰もいなければ同じです。テンプレートの検査の `function-alarm` と `alarm-recipient` が、この 2 つを見ます。

[19章](/ja/chapters/19-observability.md)が、症状に付けるアラームと通知先を作りました。デプロイしたあとの状態は、次のタスクで読みます。

```bash
vp run obs:alarms
```

タスクにもわからないのは、通知が実際に届くかどうかです。メールの購読は、確認のリンクを押すまで保留のままです。人への問いは、「最後の試験通知を、誰が、どの端末で受け取ったか」です。

### 失敗し続ける仕事

何度渡しても処理できないメッセージは、置き場所を決めておかないと、期限まで再試行されたあと、何も残さずに消えます。[08章](/ja/chapters/08-async.md)のキューにはデッドレターキューがあり、`queue-dlq` のルールが見ます。イベントバスのターゲットごとの再試行とデッドレターキューは [25章](/ja/chapters/25-events.md)の範囲です。

デッドレターキューは、作っただけでは何も解決しません。そこに溜まったものを誰が見て、どうするかが決まっていて、初めて役に立ちます。

### RTO と RPO

RTO は、止まってから戻るまでに許せる時間です。RPO は、失ってよいデータの時間の幅です。信頼性の柱の REL13-BP01 は、ワークロードごとにこの 2 つを決めることを求め、失敗の例として、根拠のない数字と、0 のような非現実的な数字を挙げています。

数字が決まっていないと、障害の最中に、2 時間の停止が許されるのかどうかを誰も判断できません。22章の訓練が、決めた数字に足りるかどうかを測る手段です。Region ごと止まった場合の数字は [28章](/ja/chapters/28-multi-region.md)の範囲です。

### 最初に当たる上限

どのサービスにも、アカウントごとの上限があります。利用者が増えたとき、あるいは再試行が重なったときに、誰も調べていなかった線でサービスが止まります。REL01-BP01（クォータと制約を把握する）にあたる項目です。

上限の調べ方と、断られたときの再試行の作法は [32章](/ja/chapters/32-limits.md)の範囲、関数の同時実行数とタイムアウトは [29章](/ja/chapters/29-lambda-tuning.md)の範囲です。[35章](/ja/chapters/35-lambda-managed-instances.md)のように関数を自分の EC2 の容量で動かす場合は、容量の上限が自分の決めた値になります。人への問いは、「いちばん近い上限はどれで、引き上げにどれだけかかるか」です。

### 対応手順

深夜に呼ばれた人が、アラームの意味を調べるところから始めることになります。運用上の優秀性の柱の OPS10-BP02 は、すべてのアラートに決まった対応の手順があることを求めています。対応手順（runbook）は、OPS07-BP03 の言い方では、決まった結果を得るための手順を書いた文書です。

19章は、アラームの説明に、最初に開くダッシュボードとクエリを書くことを勧めていました。クエリの本文は、AWS に触らずに表示できます。

```bash
vp run obs:query:print --name errors
```

手順書が使えるかどうかは、書いた本人以外が一度その手順で作業してみるまで、わかりません。

## 変更

<!-- section: 33.change -->

### パイプラインだけが本番を変える

手元から本番にデプロイできる状態では、動いているものがどのコミットにも対応しなくなります。障害のときに、何が変わったかを誰も言えません。[20章](/ja/chapters/20-shipping.md)が、レビューを通ったコミットを、CI のロールで、CloudFormation を通してデプロイする経路を作りました。

この本のふだんのデプロイに使っている cdkd は、公式ドキュメントが開発とテストの用途向けとしている道具です。本番の経路を AWS CDK CLI と CloudFormation にする理由は、[02章](/ja/chapters/02-toolchain.md)と 20章にあります。

```bash
vp run ship:cfn:diff
```

### 戻せるもの、戻せないもの

ロールバックで戻るのはコードと設定で、新しいコードが書いたデータは残ります。古いコードが読めない形のデータが残ると、戻したあとのほうが壊れます。運用上の優秀性の柱の OPS06-BP01 は、変更がうまくいかなかった場合の計画を、変更の前に持つことを求めています。

20章の[デプロイのページ](/ja/chapters/20-shipping/deploy.md)に、スキーマを「古いコードが動く順」に変える手順があります。コンテナで新旧の版が同時に動く時間は [12章](/ja/chapters/12-containers.md)、SQL のスキーマは [13章](/ja/chapters/13-sql.md)、DynamoDB のキーを止めずに移す方法は [30章](/ja/chapters/30-data-modeling.md)の範囲です。人への問いは、「1 つ前の版は、今日のデータで動くか」です。

### 少しずつ出す

全員に同時に出すと、不具合も全員に同時に届きます。OPS06-BP03 は、安全なデプロイの方法として、feature flag、canary、トラフィックの分割、blue/green を挙げています。

20章は、エラー率のアラームにつないで止める仕組みがないまま段階的に切り替えても、気づくのが遅くなるだけだと書いて、実装を見送りました。その続きが [31章](/ja/chapters/31-progressive-delivery.md)です。確かめるのは、切り替えを止めるアラームがどれで、それが実際に切り替えを止めたことがあるかです。

### 手作業の変更

深夜にコンソールで直した設定は、次のデプロイで元に戻ります。ドリフト検出を定期的に動かし、結果を人が読む場所に流します。

```bash
vp run ship:cfn:drift
```

20章が注意しているとおり、定期実行は止まることがあります。失敗の通知だけに頼らず、最後の報告を誰が読んだかを確かめます。

## 費用

<!-- section: 33.cost -->

コスト最適化の柱の COST01-BP03（予算と予測を立てる）は、月、日、時間の単位で変わる費用に合わせて、予算の立て方を変えることを求めています。

### 予算の通知

[01章](/ja/chapters/01-account.md)で作った予算は、通知であって上限ではありません。更新は 1 日に最大 3 回で、通知が届いたときには、もう超えていることがあります。それでも無いよりはずっとよく、無ければ、使いすぎに気づくのは翌月の請求書です。

確かめるのは、通知が誰に届き、届いたときにその人が何をするかです。環境や機能ごとの予算は、[32章](/ja/chapters/32-limits.md)のタグの話とつながります。

### 何もしていない月の料金

時間で課金されるリソースは、リクエストが 0 でも料金がかかります。この本では、NAT Gateway とインターフェースエンドポイント（[11章](/ja/chapters/11-network.md)）、ALB とコンテナ（[12章](/ja/chapters/12-containers.md)）、RDS や Aurora を選んだ場合のデータベース（[13章](/ja/chapters/13-sql.md)）、`-c store=valkey` を付けたときの ElastiCache（[14章](/ja/chapters/14-kv-cache.md)）、EC2 のインスタンス（[23章](/ja/chapters/23-ec2.md)）がそうでした。あとから足した章にも同じ性質のものがあります。検索の基盤（[27章](/ja/chapters/27-search.md)）、EKS のコントロールプレーン（[34章](/ja/chapters/34-eks.md)）、関数のための EC2 の容量（[35章](/ja/chapters/35-lambda-managed-instances.md)）、provisioned concurrency（[29章](/ja/chapters/29-lambda-tuning.md)）です。

各章の料金の節に、「使っていないとき」の金額があります。本番の構成を決めたら、その構成で誰も使わない 1 か月の金額を足し合わせておきます。本番向けの設定そのものが足す料金は、[最後のページ](/ja/chapters/33-production-readiness/wrap.md)で計算します。

### 内訳

請求が 2 倍になったとき、どの部分が増えたのかを言えるようにします。タグを付け、請求用に有効にし、タグごとに集計する手順は 32章の範囲です。

### 1 人が使える上限

ループに入ったスクリプト 1 つ、長いプロンプトを送り続ける利用者 1 人が、その月の請求を決めてしまうことがあります。この本は、公開する入口にはその章の中で歯止めを付けてきました。API のスロットリング（[04章](/ja/chapters/04-http-api.md)）、利用者ごとのレート制限（[14章](/ja/chapters/14-kv-cache.md)）、入力の上限と予約済み同時実行数（[17章](/ja/chapters/17-ai.md)）です。利用者ごとのトークンの予算は [36章](/ja/chapters/36-bedrock.md)、クエリが読む量の上限は [26章](/ja/chapters/26-analytics.md)の範囲です。

テンプレートの検査の `api-throttle` は、HTTP API のステージに上限が書いてあるかを見ます。値が適切かどうかは見ていません。人への問いは、「1 人の利用者が 1 日に使わせられる金額は、最大でいくらか」です。

## 悪用とセキュリティ

<!-- section: 33.abuse -->

### 入口の歯止め

公開している入口のすべてに、何かの歯止めがあることを確かめます。同じくらい大事なのは、歯止めを迂回できないことです。CloudFront の前に WAF を置いても、その後ろの関数 URL を直接呼べれば、WAF は通りません。[09章](/ja/chapters/09-ssr.md)と 21章は、関数 URL を `AWS_IAM` にして、CloudFront だけが呼べるようにしました。`function-url-auth` のルールが、これを見ます。

WAF を付けられる入口と付けられない入口の違いは、[21章の実装のつづき](/ja/chapters/21-security/more.md)にあります。HTTP API には web ACL を直接付けられないので、そこではスロットリングとアプリのレート制限が歯止めになります。API Gateway のスロットリングと usage plan は 32章の範囲です。モデルに渡す入力と返す出力に対する歯止めは、36章の範囲です。

### シークレット

シークレットを環境変数やリポジトリに置かないことは、21章で済ませました。残るのは、入れ替えを試したことがあるかどうかです。漏れた鍵は、入れ替えるまで有効です。入れ替えの手順を一度も実行していなければ、漏れた日に初めて実行することになります。

```bash
vp run sec:secret:versions
vp run sec:secret:rotate
```

2 つ目のタスクは、シークレットの新しいバージョンを書き込みます。AWS を変更します。

### 記録と検出

「誰が、いつ、これをしたか」という問いは、たいてい記録が消えたあとに出てきます。CloudTrail のイベント履歴は 90 日で、それより前は証跡を作っていなければ残りません。GuardDuty のような検出は、有効にしただけでは誰も見ません。

```bash
vp run sec:posture
vp run sec:trail:iam
```

21章のこの 2 つは読むだけのタスクで、何が有効かと、最近 IAM を変えたのが誰かを表示します。人への問いは、「検出結果はどこに届き、最後の 1 件を誰が見たか」です。

## 運用

<!-- section: 33.operations -->

ここから先は、テンプレートにもタスクにも現れません。運用上の優秀性の柱の OPS07-BP02 が、公開前の点検として挙げているものの中心は、この分野です。

### 当番

サービスが動いていると約束した時間のすべてに、連絡の付く人が決まっていることを確かめます。19章のアラームはメールに届きますが、メールは月曜の朝まで読まれません。通知をチャットや当番の仕組みにつなぐこと、当番が休みのときに誰が代わるかを決めておくことは、この本の外の作業です。

1 人で運用しているなら、正直な答えは「夜は誰も見ていない」かもしれません。それでかまわない場合もあります。大事なのは、その答えを RTO と並べて見ることです。RTO が 1 時間で、夜は誰も見ていないなら、どちらかが嘘になっています。

### 障害の記録

障害のたびに、何が起きたか、いつ気づいたか、何をしたか、何を変えるかを書き残します。書かなければ、同じ障害が戻ってきたときに、調査を最初からやり直します。運用上の優秀性の柱では、OPS11-BP02（障害の後に分析する）にあたります。

22章の訓練の記録（`examples/22-recovery/drill/TEMPLATE.md`）は、時刻を順に埋めていく形になっていて、そのまま障害の記録のひな形に使えます。

記録は、この点検の一覧を育てる材料でもあります。OPS07-BP02 は、自分たちの障害の振り返りが、自分たちの ORR を変えていくべきだと書いています。障害が 1 つ起きたら、`src/review.ts` に項目を 1 つ足すかどうかを考えます。

### 訓練

障害をわざと起こして、手順と権限とアラームが実際に働くかを確かめます。Well-Architected は game day と呼び、信頼性の柱の REL12-BP05 で、本番で対応するのと同じ人たちで定期的に行うことを勧めています。

22章の訓練は、その 1 つの形です。データを消し、戻し、かかった時間を記録します。Region の障害を想定した訓練は [28章](/ja/chapters/28-multi-region.md)の範囲です。訓練で見つかるのは、たいてい手順書の誤りではなく、手順書に書かれていなかった前提です。必要な権限を当番が持っていなかった、通知が届く先が退職した人のアドレスだった、といったことです。

### サポートの終わる日

ランタイム、データベースのエンジン、クラスターには、サポートの終わる日があります。持ち主が決まっていないと、自分で選んでいない日に更新を迫られます。クラスターのバージョンとサポートの期間は [34章](/ja/chapters/34-eks.md)の範囲です。Lambda のランタイムについては、この本のスタックはすべて `nodejs24.x` を使っています。その終了日は、この章では調べていません。
