# 26 Analytics: しくみと実装

[前のページ](/ja/chapters/26-analytics.md)で、記録が Firehose を通って S3 に入り、Athena が読む全体の形を見ました。このページでは、記録の形、アプリからの送り方、フォルダーの分け方、テーブルの定義、クエリの順に実装します。

## 記録の形

<!-- section: 26.record -->

最初に決めるのは、1 件の記録に何を入れるかです。バケットに入った記録は 90 日残り、あとから書き直せません。ログより慎重に決めます。

<<< @/examples/26-analytics/src/record.ts{schema}

項目の名前は、すべて小文字とアンダースコアにしました。テーブルの列の名前と JSON のキーを同じ綴りにしておくためです。JSON を読む SerDe には、キーを小文字に直して列と対応させる設定を持つものもありますが、最初から同じにしておけば、その対応に頼らずに済みます。

`route` は `/notes/:id` のようなパターンで、実際のパスではありません。パスにはノートの ID が入るので、そのまま記録すると値の種類が際限なく増えます。登録されていないパスは、何が書かれているかわからないので、まとめて `other` にします。ノートのタイトルと本文、クエリ文字列、ヘッダーは、どれも記録しません。スキーマを `strictObject` にしてあるので、ここに無い項目を足すとテストが落ちます。

`action` は、そのリクエストがノートに何をしたかです。読み取りと失敗では `null` になります。決めているのはステータスコードです。

<<< @/examples/26-analytics/src/describe.ts{action}

`at` は時刻ですが、Athena の列の型は文字列にしました。Hive の JSON SerDe で文字列を timestamp 型として読むには、書式を SerDe のプロパティに書く必要があるからです。文字列のままでも困りません。`toISOString()` の書き方はミリ秒まで桁がそろっているので、文字列として比べた順序が時刻の順序になります。スキーマでは、ミリ秒のない書き方や、オフセットの付いた書き方を断っています。

`event_id` は、記録 1 件ごとの UUID です。同じ記録が 2 回入ったときに、1 回と数えるために使います。なぜ 2 回入るのかは、次の節で扱います。

### 同じ記録が 2 回入る場合

`PutRecord` の API リファレンスには、Put の操作をやり直すとデータが重複しうる、と書かれています。重複が起きるのは、Firehose が記録を受け取ったのに、その応答が呼び出し側に届かなかったときです。SDK は失敗と見なして送り直すので、Firehose には同じ行が 2 つ入ります。

この状況を、本物の SDK を使って再現するテストがあります。ネットワークの部分だけを差し替えて、1 回目は受け取ったうえで接続が切れたことにし、2 回目は成功させます。結果として、同じ行が 2 回届きます。2 つの行は `event_id` が同じなので、クエリは `count(DISTINCT event_id)` で 1 件と数えられます。

Firehose から S3 への配送については、ドキュメントの書き方が違います。Firehose の配送は「少なくとも 1 回」で重複がありうるものの、S3 を宛先とする場合はその対象から除く、と書かれています。この章で備えているのは、送る側のやり直しによる重複です。

ストリームの定義は次のとおりです。

<<< @/examples/26-analytics/infra/lib/analytics-stack.ts{stream}

`bufferingHints` は、どこまでためてから書くかの目安です。60 秒たつか 5 MB たまるか、先に来たほうでオブジェクトが 1 つできます。間隔を短くすると記録が早くクエリに現れますが、オブジェクトの数が増えます。オブジェクトの数は、S3 への書き込みの料金と、Athena が読むときのリクエストの数になって返ってきます。

### 日付の境目

式が使う時刻について、ドキュメントは「書こうとしているオブジェクトに入っている、いちばん古いレコードの、おおよその到着時刻」と説明しています。タイムゾーンは既定で UTC です。ここから 2 つのことが言えます。

まず、フォルダーの日付は UTC の日付です。日本時間の午前 9 時より前の記録は、前の日のフォルダーに入ります。

次に、フォルダーの日付は、記録の `at` の日付と一致するとは限りません。23 時 59 分 50 秒に届いたレコードと、0 時 0 分 5 秒に届いたレコードが同じオブジェクトに入ると、そのオブジェクトは前の日のフォルダーに置かれます。2 件目は、起きた日の前日のフォルダーに入ることになります。

手元では、この動きだけを写した模型で確かめます。

<<< @/examples/26-analytics/src/lake.ts{delivery}

模型が再現するのは、どのレコードが同じオブジェクトに入るかと、そのオブジェクトがどの日付のフォルダーに置かれるかです。大きさによる区切り、再試行、届けられないデータを Firehose が 24 時間保持することは、再現していません。式の評価も、この章が使う 2 つだけです。

Firehose がバケットに書くためのロールは、自分が書くフォルダーだけに絞ってあります。

<<< @/examples/26-analytics/infra/lib/analytics-stack.ts{delivery-role}

操作の一覧は、Firehose のドキュメントが S3 を宛先にするときに挙げているものです。ドキュメントの例はバケット全体を対象にしていますが、ここではオブジェクトへの操作を、記録のフォルダーと失敗したレコードのフォルダーに限りました。クエリの結果のフォルダーには書けません。この絞り方で Firehose が動くかどうかは、実際の AWS では確かめていません。

## テーブルの定義と partition projection

<!-- section: 26.catalog -->

Athena が読むテーブルは、Glue Data Catalog に定義します。

<<< @/examples/26-analytics/infra/lib/analytics-stack.ts{catalog}

`EXTERNAL_TABLE` は、データを持たないテーブルです。テーブルを消しても、バケットのファイルは消えません。反対に、バケットのファイルを消せば、テーブルは空になります。

`dt` は列の一覧には無く、`partitionKeys` にだけあります。ファイルの中に `dt` の項目は無く、値はフォルダーの名前から来るからです。

ファイルの読み方は、形式ごとに決まった組み合わせがあります。

<<< @/examples/26-analytics/infra/lib/analytics-stack.ts{storage}

JSON を読む SerDe には Hive のものを選びました。もう 1 つの OpenX JSON SerDe は、Athena のドキュメントに、結果の件数や値が実行ごとに変わりうるという注意があり、回避策として Hive JSON SerDe が挙げられています。

パーティションの規則は、テーブルのプロパティに書きます。

<<< @/examples/26-analytics/src/partition.ts{layout}

`projection.dt.range` の `NOW` は、クエリを実行した時点を指します。ドキュメントによると、日付型の値は UTC で作られます。Firehose のプレフィックスも UTC なので、時計は同じです。`storage.location.template` の `${dt}` には、計算した日付が入ります。

Firehose に渡すプレフィックスと、Athena に渡すテンプレートは、同じフォルダーを指していなければなりません。片方だけを変えると、エラーにはならず、クエリの結果が 0 件になります。テストでは、プレフィックスを評価した結果と、テンプレートに日付を入れた結果が一致することを、JSON と Parquet の両方で確かめています。

partition projection には、知っておくべき性質があります。データの無い日付も、パーティションとして計算されます。その日のフォルダーが無くてもエラーにはならず、0 件が返ります。範囲の外の日付を指定したクエリも、エラーにならずに 0 件を返します。この章の範囲は `2026-10-01` から始めているので、それより前の日付を指定すると、データがあっても何も返りません。また、この規則を使うのは Athena だけです。同じテーブルを別のサービスから読むと、登録されたパーティションだけが見えます。

```text
SELECT substr(at, 1, 10) AS day, action, count(DISTINCT event_id) AS events
FROM "aih_analytics"."requests"
WHERE dt BETWEEN '2026-10-11' AND '2026-10-14'
  AND at >= '2026-10-12T00:00:00.000Z'
  AND at < '2026-10-14T00:00:00.000Z'
  AND action IS NOT NULL
GROUP BY substr(at, 1, 10), action
ORDER BY day, action
```

## JSON と Parquet

<!-- section: 26.columnar -->

ここまでのファイルは、gzip で圧縮した JSON の行です。Athena がこのファイルから 1 つの列を読むには、ファイル全体を読んで展開するしかありません。

Parquet は列指向フォーマット（columnar format）で、ファイルの中で列ごとにデータがまとまっています。クエリが 3 つの列しか使わなければ、その 3 列のぶんだけを読めます。Firehose には、JSON で受け取ったレコードを Parquet に変換して書く機能があります。スタックは、デプロイのときに `-c format=parquet` を渡すと、変換するストリームと Parquet のテーブルになります。

<<< @/examples/26-analytics/infra/bin/app.ts{context}

変換のとき、Firehose は列の一覧を Glue のテーブルから読みます。Athena が読むテーブルと同じものです。変換できなかったレコードは、`errors/format-conversion-failed/` に置かれます。

形式を変えると、フォルダーも `requests_parquet/` に変わります。2 つの形式のファイルが 1 つのテーブルの下に混ざると読めなくなるからです。それまでの JSON のファイルは `requests_json/` に残り、新しいテーブルからは見えません。

読む量がどれだけ変わるかを、手元で測りました。同じ 5,000 件のサンプルを、gzip の JSON と Parquet の両方で書き、Parquet のファイルのフッターから列ごとのバイト数を読みます。

<<< @/examples/26-analytics/src/columnar.ts{measure}

```bash
vp run analytics:sizes
```

| クエリ | 読む列 | gzip の JSON | Parquet |
| --- | --- | --- | --- |
| `actions` | `event_id`、`at`、`action` | 293,422 | 209,801 |
| `routes` | `event_id`、`at`、`method`、`route`、`duration_ms` | 293,422 | 219,198 |
| `errors` | `event_id`、`at`、`route`、`status` | 293,422 | 210,979 |
| `status` | `at`、`status` | 293,422 | 31,922 |

単位はバイトです。JSON はどのクエリでもファイル全体で、Parquet は読む列の合計です。

この結果には、Parquet にすれば小さくなるという期待に反する点が 2 つあります。

1 つ目は、ファイル全体の大きさです。Parquet のファイルは 422,796 バイトで、gzip の JSON の 293,422 バイトより大きくなりました。このレコードは、バイト数の大半を `event_id` と `request_id` の 2 つの UUID が占めています。乱数の文字列は、列にまとめても縮みません。

2 つ目は、重複を取り除く代金です。`event_id` を読むクエリは、Parquet でもファイルの半分ほどを読みます。`event_id` を読まない `status` は、gzip の JSON の 11% で済みます。列指向の効果が出るのは、大きな列を読まずに済むクエリです。

この数字は、手元の JavaScript のライブラリが書いた Parquet のファイルのものです。Firehose は自分の実装で書くので、大きさは違うはずです。Athena が実際に読んだと報告するバイト数も、確かめていません。変わらないのは、どの列が大きいかという傾向だけだと考えています。

月 100 万リクエスト程度では、この差は料金に現れません。Athena は 1 回のクエリにつき最低 10 MB ぶんを課金するので、どちらの形式でも最低額になります。Parquet への変換を考えるのは、1 回のクエリが読む量が 10 MB を大きく超えてからです。

## 読みすぎと置きっぱなしを防ぐ

<!-- section: 26.guard -->

Athena の料金は読んだ量で決まるので、条件を書き忘れたクエリ 1 回が、そのまま請求になります。ワークグループ（workgroup）に上限を付けておくと、それを超えたクエリは Athena が取り消します。

<<< @/examples/26-analytics/infra/lib/analytics-stack.ts{bounds}

<<< @/examples/26-analytics/infra/lib/analytics-stack.ts{workgroup}

上限は 1 GiB にしました。1 TB あたり 5.00 なので、1 回のクエリは 0.005 ほどで止まります。指定できる下限は 10 MB です。

この上限について、知っておくことが 3 つあります。取り消されたクエリにも、それまでに読んだぶんの料金がかかります。上限はクエリ 1 回ごとのもので、月の合計は止めません。合計に対して設定できるのは通知で、ドキュメントには、しきい値に達してもクエリは自動では取り消されないと書かれています。そして、上限が効くのはこのワークグループを使ったクエリだけです。同じ人が別のワークグループを使えば、上限はかかりません。本番では、使えるワークグループを IAM で限ります。

`enforceWorkGroupConfiguration` は、結果の保存先などをクライアントの側から上書きさせない設定です。

バケットの側では、置いたままのものが増え続けないようにします。

<<< @/examples/26-analytics/infra/lib/analytics-stack.ts{bucket}

<<< @/examples/26-analytics/infra/lib/analytics-stack.ts{retention}

Athena は、クエリを実行するたびに結果のファイルをバケットに書き、自分では消しません。結果のフォルダーは 7 日で消えるようにしました。記録は 90 日、変換に失敗したレコードは 14 日です。どれも練習用の値です。

記録の保持期間は、07章のライフサイクルルールと同じ考え方で決めます。ただし、ここでは消えることが partition projection と噛み合っています。90 日より前のフォルダーは空になりますが、Athena はエラーにせず 0 件を返します。
