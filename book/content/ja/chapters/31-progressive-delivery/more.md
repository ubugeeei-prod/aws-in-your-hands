# 31 Progressive Delivery: 実装のつづき

[前のページ](/ja/chapters/31-progressive-delivery/build.md)で、コードを段階的に切り替える側を作りました。このページでは、フィーチャーフラグを作ってアプリに組み込み、2 つのバージョンが同じデータを読むときの条件をテストにします。最後に、12章のコンテナのサービスで同じことをするときの選択肢を見ます。

## フラグの定義

<!-- section: 31.flag-document -->

フラグの値は、リポジトリの中の 1 つのファイルに書きます。

<<< @/examples/31-progressive-delivery/flags/flags.json

AppConfig の設定プロファイルには種類があり、`AWS.AppConfig.FeatureFlags` を選ぶと、この形の JSON を受け付けます。`flags` がフラグの定義、`values` が現在の値です。フラグは属性を持てて、属性には型と範囲を付けられます。`noteStats` の `rolloutPercent` は、0 から 100 の数値と決めてあります。AppConfig のドキュメントによると、この種類のプロファイルは、保存するときに AppConfig が JSON Schema と照らして検査します（確認日 2026-10-13）。

フラグは 2 つあります。`readOnly` は運用のためのスイッチで、入れている間は書き込みを断ります。`noteStats` は、新しく足す `GET /stats` というルートを誰に見せるかを決めます。

同じ形を、Valibot のスキーマとしても持っています。

<<< @/examples/31-progressive-delivery/src/flags/document.ts{document}

AppConfig が検査するのに、手元でも検査する理由は 2 つあります。AWS に送る前に、エディターと CI で気づけること。そして、AppConfig の知らない決まりを足せることです。

<<< @/examples/31-progressive-delivery/src/flags/document.ts{check}

足した決まりのうち大事なのは、ファイルとコードが、存在するフラグについて一致していることです。コードが読むフラグがファイルに無ければ失敗し、ファイルにあるフラグをコードが読んでいなくても失敗します。後者は害が無さそうに見えますが、どこにもつながっていないスイッチは、障害の最中に誰かが切り替えて、何も起きずに時間を失う原因になります。使い終わったフラグを消す作業も、このテストが促します。

Valibot の `v.record` は、配列を渡しても通し、`constructor` などの 3 つの名前の鍵を黙って落とします。フラグが 1 つ消えたまま検査を通ると困るので、スキーマの前段でどちらも断っています。

アプリが受け取るのは、このファイルそのものではありません。

<<< @/examples/31-progressive-delivery/src/flags/document.ts{retrieved}

AppConfig のドキュメントによると、アプリに渡るのは、フラグの名前から値への対応だけで、定義は取り除かれます。切ってあるフラグは `enabled: false` だけになり、属性も付きません（確認日 2026-10-12）。この変換を手元でも再現しておくと、手元のサーバーとテストが、AWS で受け取るのと同じ形を読めます。

```bash
vp run flags:check
```

```text
flags/flags.json is valid. An application would receive:
{
  "readOnly": {
    "enabled": false
  },
  "noteStats": {
    "enabled": false
  }
}
```

## フラグを読む

<!-- section: 31.flag-read -->

アプリの側は、受け取った JSON を、自分が読むフラグのスキーマで検査します。

<<< @/examples/31-progressive-delivery/src/flags/evaluate.ts{flags}

すべてのフラグに既定値があり、知らないフラグは無視します。設定とコードは別々にデプロイされるので、片方だけが新しい時間が必ずあるからです。新しいコードが、まだそのフラグを持たない古い設定を読むこともあれば、ロールバックで戻った古いコードが、知らないフラグの入った新しい設定を読むこともあります。どちらの場合も、動き続けなければなりません。

フラグではないものは、断ります。空の配列や文字列を「すべて既定値」として受け入れると、壊れた応答が、正常な設定として通ってしまいます。

`noteStats` を誰に見せるかは、割合で決めます。

<<< @/examples/31-progressive-delivery/src/flags/evaluate.ts{bucket}

フラグの名前と利用者の ID をつなげてハッシュを取り、0 から 9999 の番号にします。その番号が割合より小さければ、対象です。同じ利用者はいつも同じ番号になるので、リクエストのたびに機能が出たり消えたりしません。割合を 10% から 25% に上げたとき、10% のときに対象だった人は必ず対象のままです。ハッシュにフラグの名前を入れてあるので、どのフラグでも同じ人たちが最初の 10% になることもありません。テストは、1 万人ぶんの ID でこの 3 つを確かめています。

<<< @/examples/31-progressive-delivery/src/flags/evaluate.ts{decisions}

エイリアスの重みとは、決まり方が違います。重みはリクエストごとのくじで、同じ人が続けて 2 回呼べば、別々のバージョンに当たることがあります。フラグの割合は人ごとに決まり、何度呼んでも同じです。コードの切り替えで確かめたいのは「落ちないか」で、利用者には違いが見えない前提です。フラグが切り替えるのは利用者に見える機能なので、人ごとに固定します。

AppConfig にも、利用者ごとに設定を固定して配る機能があります。エージェントに `Entity-Id` というヘッダーを付けて問い合わせると、配っている途中でも、同じ ID には同じ版を返すというものです。ドキュメントは、これにはエージェントの 2.0.136060 以降が要ると書いています。一方、Lambda 用の拡張機能の一覧で最も新しい版は 2.0.22365 でした（どちらも確認日 2026-10-13）。Lambda の拡張機能でこの機能が使えるかどうかは確認できなかったので、この章では使わず、割合の計算を自分のコードに置いています。

## AppConfig に届かないとき

<!-- section: 31.flag-fallback -->

フラグを外のサービスから読むようにすると、アプリが動くための条件が 1 つ増えます。AppConfig に届かないときに何が起きるかを、先に決めておきます。

<<< @/examples/31-progressive-delivery/src/flags/reader.ts{reader}

フラグを読む関数は、必ず答えを返します。読めたら、その値を使って覚えておきます。読めなければ、最後に読めた値を使います。一度も読めていなければ、コードに書いた既定値を使います。どこから来た値かは、レスポンスの `x-flags-origin` ヘッダーに `live`、`last-known`、`defaults` のどれかで出します。ログには、この状態が変わったときに 1 行だけ書きます。届かない間ずっとリクエストごとに警告を書くと、障害の上にログの洪水が重なるからです。

Lambda では、AppConfig を直接は呼びません。AWS は、AppConfig Agent の Lambda 拡張機能をレイヤーとして関数に足すことを勧めています。

<<< @/examples/31-progressive-delivery/src/flags/reader.ts{extension}

拡張機能は、関数と同じ実行環境の中で動く別のプロセスです。ドキュメントによると、`localhost:2772` で HTTP を受け付け、設定を自分のキャッシュに持ち、関数が呼ばれたときに前回の確認から決まった時間（既定で 45 秒）が過ぎていれば、AppConfig に新しい版が無いかを確かめます。AppConfig が決まった時間（既定で 3,000 ミリ秒）内に答えなければ、その回の確認を飛ばして、キャッシュにある値を返します（確認日 2026-10-12）。キャッシュは実行環境ごとにあります。

つまり、守りは 2 段あります。拡張機能がキャッシュで持ちこたえ、それでも答えが得られなければ、アプリの側が最後に読めた値か既定値を使います。関数から拡張機能への問い合わせには 500 ミリ秒の期限を付けました。フラグを待ってリクエストを失敗させるより、古い値で答えるほうを選んでいます。

ドキュメントから分からなかったこともあります。一度もデプロイしていない設定を問い合わせたときと、コールドスタートの直後に AppConfig に届かないときに、拡張機能が何を返すかです。アプリの側は、200 以外の応答、期限切れ、読めない JSON をすべて同じ失敗として扱うので、どの形で返ってきても既定値で動きます。

### 既定値の選び方

2 つのフラグの既定値は、どちらも「切」です。`noteStats` は、誰も公開していない機能は公開しない、という意味なので迷いません。

`readOnly` には、考えることがあります。既定値が「切」ということは、フラグが読めないとき、書き込みを受け付けるということです。誰かが `readOnly` を入れた後で AppConfig に届かなくなった場合、すでに動いている実行環境は、最後に読めた値を使うので書き込みを断り続けます。ところが、その間にコールドスタートした実行環境は、一度も読めていないので既定値を使い、書き込みを受け付けます。同じ時刻に、断る実行環境と受け付ける実行環境が混じります。

テストは、この 2 つの動きをそのまま固定しています。止めることが絶対に必要なスイッチ、たとえばデータの移行中に書き込みを止めるスイッチは、既定値を「入」にするか、フラグではない仕組みで止めてください。この章の API なら、書き込みのルートを API Gateway から外してデプロイする方法があります。フラグは、読めなかったときにどちらへ倒れてもよいものに使います。

## フラグをアプリに組み込む

<!-- section: 31.flag-app -->

04章のアプリは変えません。外側に 1 枚かぶせて、フラグが関わるリクエストだけをそこで処理し、残りは 04章のアプリにそのまま渡します。

<<< @/examples/31-progressive-delivery/src/app.ts{app}

順に見ていきます。フラグは、リクエストごとに 1 回読みます。途中で値が変わっても、1 つのリクエストの中では同じ値を使います。

`readOnly` が入っていれば、書き込みのメソッドに 503 を返します。04章のエラーと同じ形の JSON で、同じ CORS のヘッダーを付けます。ヘッダーが無いと、ブラウザーはページにエラーの中身を見せません。

`GET /stats` は、`noteStats` がその利用者に対して入っているときだけ答えます。切ってあるときは 04章のアプリに渡るので、04章の 404 がそのまま返ります。このルートのコードは、フラグを入れるまで、存在しないのと同じに見えます。新しいコードを先に全員へ届けておき、機能はあとから出す、というのはこのことです。

利用者の ID は、`x-client-id` ヘッダーから取っています。04章のアプリには認証が無いので、06章のサインインした利用者の ID の代わりに置いた仮のものです。ブラウザーからは送れません（プリフライトが許すヘッダーは `content-type` だけです）。`curl` と、あとで使う `rollout:probe` から送るためにあります。ID の無いリクエストは、割合が 100% になるまで対象になりません。

どのレスポンスにも、答えたバージョンの番号を `x-app-version` で付けます。値は、Lambda が実行環境に設定する `AWS_LAMBDA_FUNCTION_VERSION` です。切り替えの間、どちらのバージョンが何件答えたかを、呼ぶ側から数えられます。`x-flags-origin` と合わせて、練習のために付けているヘッダーなので、本番では外すか、内部の呼び出しに限ってください。

`FAULT_PERCENT` は、決めた割合のリクエストにわざと 500 を返す設定です。壊れたバージョンをデプロイして、ロールバックが働くのを見るために使います。

組み立ては 1 か所です。

<<< @/examples/31-progressive-delivery/src/compose.ts{compose}

環境変数は、04章のものに加えて、この章のぶんを別のスキーマで読みます。フラグの読み先が指定されていなければ、起動の時点で止まります。何も設定されていない関数が、黙って既定値だけで動き続けるのを避けるためです。

## フラグをデプロイする仕組み

<!-- section: 31.flag-deploy -->

スタックが作るのは、フラグの入れ物までです。

<<< @/examples/31-progressive-delivery/infra/lib/progressive-stack.ts{flags}

AppConfig のアプリケーション、設定プロファイル、デプロイ戦略の 3 つです。フラグの中身は、スタックには入れません。フラグを変えるたびにスタックをデプロイするのでは、コードとふるまいを分けた意味が無くなるからです。中身を保存して配るのは、`flags:deploy` の仕事です。

デプロイ戦略は、配る速さです。ここでは、5 分かけて 20% ずつ配り、そのあと 5 分アラームを見る、と決めました。AppConfig には既定の戦略もあり、AWS が本番向けに勧めている `AppConfig.Linear20PercentEvery6Minutes` は、30 分かけて配り、30 分見ます。練習で何度も試すには長いので、短いものを作っています。

ここで配られる単位は、利用者ではなく、設定を取りに来る側です。Lambda では、実行環境ごとの拡張機能がそれに当たります。配っている途中は、新しい設定を受け取った実行環境と、まだの実行環境が混じります。同じ利用者のリクエストが両方に当たれば、フラグが入ったり切れたりして見えます。`noteStats` の `rolloutPercent` が人ごとに固定しているのは、ある 1 つの設定の中での話です。新しい設定が全部の実行環境に行き渡るまでの数分間は、設定そのものが 2 種類あります。

関数には、拡張機能のレイヤーと、読み先を足します。

<<< @/examples/31-progressive-delivery/infra/lib/progressive-stack.ts{extension}

<<< @/examples/31-progressive-delivery/infra/lib/progressive-stack.ts{function}

レイヤーの ARN は、AppConfig のユーザーガイドにある版の表から取りました（確認日 2026-10-12）。最新の ARN を返す SSM の公開パラメーターもありますが、デプロイのたびに中身が変わりうるので、この本のほかの依存と同じく、版を固定しています。`AWS_APPCONFIG_EXTENSION_PREFETCH_LIST` を設定しておくと、拡張機能は起動したときに、関数の初期化を待たずに設定を取りに行きます。

環境と権限は、アラームができた後に作ります。

<<< @/examples/31-progressive-delivery/infra/lib/progressive-stack.ts{environment}

AppConfig の環境に、前のページの 2 つのアラームをモニターとして付けています。フラグを配っている間と、そのあとの bake time の間にアラームが鳴ると、AppConfig が前の設定に戻します。コードの切り替えを止めるのと同じアラームが、フラグも止めます。

AppConfig がアラームを読むためのロールには、2 つのアラームに対する `cloudwatch:DescribeAlarms` だけを持たせました。AppConfig のドキュメントの例は、リソースを `*` にしています。複合アラームを読むには `*` が要る、というのがその理由です。この章のアラームは複合アラームではなく、AWS の service reference でも `DescribeAlarms` はアラーム単位で絞れることになっていますが、絞った権限で自動のロールバックが働くかどうかは、実環境で確かめていません。

関数が読めるのは、このアプリケーションの、この環境の、この設定 1 つだけです。

保存して配る処理は、API を 2 回呼びます。

<<< @/examples/31-progressive-delivery/src/flags/appconfig.ts{deploy}

1 回目で、ファイルの内容を新しい版として保存します。この時点では、誰にも届きません。2 回目で、その版を、決めた戦略で環境に配り始めます。`flags:deploy` は、最初にファイルを手元のスキーマと決まりで検査し、通らなければ AWS を呼びません。

止めるほうは、いまの状態によって意味が変わります。

<<< @/examples/31-progressive-delivery/src/flags/appconfig.ts{stop}

SDK の型定義にある説明によると、`StopDeployment` は、`AllowRevert` を付けなければ状態が `DEPLOYING` のデプロイにしか使えません。付ければ、進行中のデプロイは `ROLLED_BACK` になり、完了したデプロイは `REVERTED` になって前の版に戻ります。完了から 72 時間を過ぎると戻せません。このスクリプトは常に `AllowRevert` を付け、止めるのか戻すのかを先に表示してから実行します。

## 両方のバージョンが読めるデータ

<!-- section: 31.shared-data -->

エイリアスを戻すと、コードは戻ります。新しいバージョンが 10% の間に書いたデータは、戻りません。

12章の[ローリングアップデートの節](/ja/chapters/12-containers/more.md)で、新旧のタスクが同じレコードを読むときの不変条件を、テストにしました。重み付きエイリアスでも条件は同じで、厳しくなる点が 1 つあります。12章の更新は前へ進むだけでしたが、この章の切り替えは、途中で引き返すことがあります。引き返した後の古いバージョンは、新しいバージョンが書いたレコードを読むことになります。

12章のレコードの形式と、共有の入れ物を、そのまま使います。

<<< @/examples/31-progressive-delivery/test/versions.test.ts{shared-data}

テストは、2 つのバージョンを 50% ずつで動かして両方に書かせ、そのあと重みを 0 に戻して、古いバージョンに一覧を読ませます。乱数は種を固定してあるので、毎回同じ順で振り分けられます。

3 つの場合を見ています。互いのレコードを読める組み合わせでは、切り替えの間も、戻した後も、すべて成功します。新しいバージョンが、古いレコードに無いフィールドを必須にしていると、新しいバージョンに当たったリクエストだけが 500 になります。これはアラームが捕まえる失敗で、戻せば直ります。

3 つ目が、戻しても直らない場合です。古いバージョンが、知らないフィールドを拒否する作りだと、新しいバージョンが書いたレコードを読めません。エイリアスを戻した後、すべてのリクエストが古いバージョンに届き、そのすべてが失敗します。ロールバックは成功していて、サービスは壊れたままです。

データの形を変えるときは、12章と同じく、変更を分けて出します。まず、新しい形を読めるが、書くのは古い形のまま、というコードを全員に出します。次に、新しい形を書くコードを出します。この 2 回目だけが、段階的に切り替える意味のある変更です。引き返す先のバージョンが、新しい形をもう読めるからです。

## ECS のサービスを段階的に切り替える

<!-- section: 31.ecs -->

12章のサービスは、ローリングアップデートで更新していました。新しいタスクを足し、ヘルスチェックに通ったら古いタスクを減らします。うまく起動しないときは、circuit breaker が前のデプロイに戻します。

circuit breaker が数えているのは、起動できなかったタスクと、ヘルスチェックに落ちて置き換えられたタスクです。ECS のドキュメントによると、しきい値は既定で、望むタスク数の 50% を、3 以上 200 以下に丸めた数です（確認日 2026-10-13）。起動して `/health` には 200 を返すが、本物のリクエストの一部で 500 を返す、というバージョンは、circuit breaker には見えません。

ECS には、そこを埋める仕組みが 2 つあります。どちらも ECS 自身の機能で、CodeDeploy は要りません。

1 つは、デプロイにアラームを結び付ける設定です。名前を指定したアラームが `ALARM` になると、ECS はそのデプロイを失敗とし、設定によっては前のデプロイに戻します。ローリングアップデートのまま使えます。

もう 1 つは、デプロイの方式そのものを変えることです。ECS の API リファレンスによると、方式は `ROLLING`、`BLUE_GREEN`、`LINEAR`、`CANARY` の 4 つです（確認日 2026-10-13）。`BLUE_GREEN` は、新しいタスクの組を古い組の横に用意して、トラフィックを一度に切り替えます。`CANARY` は、まず決めた割合だけを新しい組に送り、決めた時間のあとで残りを送ります。`LINEAR` は、同じ割合ずつ、同じ間隔で送ります。blue/green と canary のドキュメントは、切り替えた後もしばらく古い組を動かしたままにすると説明しています。その時間が bake time で、戻すときは、まだ動いている古い組にトラフィックを戻すだけです。

ローリングアップデートのサービスと比べて、増えるものが 3 つあります。ターゲットグループが 2 つ要ります。ECS は、片方に古いタスクを、もう片方に新しいタスクを登録し、ロードバランサーのリスナーのルールの重みを書き換えてトラフィックを移します。そのために、どのルールを書き換えてよいかを ECS に教え、ECS がロードバランサーを操作するためのロールを渡します。そして、切り替えの間と bake time の間は、新旧のタスクが両方動きます。タスク数は一時的に最大で 2 倍になり、そのぶんの Fargate の料金がかかります。

`canaryPercent` は 0.1 から 100 までの 0.1 刻みで既定は 5、canary の時間は 0 から 1,440 分で既定は 10 分です。

前のページのスクリプトと違う点も 1 つ書いておきます。ECS のドキュメントによると、デプロイを始めた時点でアラームがすでに `ALARM` だった場合、ECS はそのデプロイの間、アラームを見ません。壊れたデプロイを直すための次のデプロイを通すためです。この章のスクリプトは、同じ状況では始めること自体を断ります。どちらが正しいということではなく、止まっているものを直すデプロイと、動いているものを変えるデプロイとで、欲しい動きが違います。

このスタックは、テストの中でテンプレートを合成して読んでいるだけで、デプロイするアプリには入っていません。ロードバランサーと 2 つのタスクは、置いてあるだけで時間単位の料金がかかるからです。12章のサービスを、作り直さずにこの方式へ更新できるかどうか、固定した版の cdkd が新しいプロパティを ECS に送るかどうかは、確かめていません。circuit breaker については、API リファレンスに「ローリングアップデートの方式のサービスでだけ使える」とあります。`CANARY` などの方式で併用できるかどうかも、未確認です。
