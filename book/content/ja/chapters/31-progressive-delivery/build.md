# 31 Progressive Delivery: しくみと実装

[前のページ](/ja/chapters/31-progressive-delivery.md)で、コードの切り替えとフラグを別々に動かす構成を決めました。このページでは、コードの側を作ります。エイリアスの置き方、切り替えの計画、アラームからの判断、実行の順に進めます。フラグは[次のページ](/ja/chapters/31-progressive-delivery/more.md)で扱います。

## バージョンとエイリアス

<!-- section: 31.alias -->

20章で、Lambda のバージョンとエイリアスを使いました。バージョンは、ある時点のコードと設定を固定した番号付きの写しで、エイリアスはバージョンに付ける名前です。API Gateway がエイリアスを呼ぶようにしておけば、エイリアスが指す先を変えるだけで、リクエストの届く先が変わります。

エイリアスは、2 つのバージョンを同時に指すこともできます。Lambda のドキュメントによると、指せるのは 2 つまでで、条件は次のとおりです（確認日 2026-10-12）。

- どちらも発行済みのバージョンであること。`$LATEST` は指せない
- 実行ロールが同じであること
- デッドレターキューの設定が同じか、どちらにも無いこと

振り分けは、リクエストごとに確率で決まります。ドキュメントは、リクエストが少ないと、設定した割合と実際の割合が大きくずれることがあると書いています。

20章のスタックは、CDK の `currentVersion` を使っていました。関数が変わるたびに新しいバージョンのリソースができ、エイリアスがそれを指すので、デプロイが終わった時点で全部のリクエストが切り替わります。この章では、デプロイでエイリアスが動かないようにします。

<<< @/examples/31-progressive-delivery/infra/lib/progressive-stack.ts{alias}

バージョンのリソースは 1 つだけで、プロパティは関数の名前しか持ちません。コードを変えてデプロイしても、テンプレートの上ではこのリソースに変更が無いので、新しいバージョンは発行されず、エイリアスも元のままです。変わるのは `$LATEST` だけで、`$LATEST` は誰からも呼ばれていません。スタックのテストは、バージョンのリソースが 1 つであることと、エイリアスに重みが書かれていないことを固定しています。

この置き方には、受け入れることが 2 つあります。

1 つは、エイリアスの中身がテンプレートから離れていくことです。作った直後はバージョン 1 を指していますが、最初の切り替えが終われば 2 を指します。テンプレートには 1 と書いたままです。CodeDeploy を使う構成でも同じことが起きていて、エイリアスの持ち主は、作った後はデプロイの道具ではなくなります。02章のドリフトの検査がこの差をどう報告するかは、実行していないので分かりません。

もう 1 つは、エイリアスの後ろに隠れるのは、コードと関数の設定だけだという点です。環境変数、メモリ、タイムアウト、レイヤーはバージョンに固定されるので、段階的に切り替わります。IAM のポリシー、API Gateway のルート、アラームはバージョンに含まれないので、デプロイした時点で全部のリクエストに効きます。権限を減らす変更を、コードの変更と同じデプロイに入れると、古いバージョンが先に権限を失います。

## 切り替えの計画

<!-- section: 31.plan -->

どの割合を、どれだけの時間かけて移すかは、AWS を呼ぶ前に決まる計算です。計画を表す型と、それを作る関数は次のとおりです。

<<< @/examples/31-progressive-delivery/src/shift/plan.ts{plan}

計画の名前は、CodeDeploy が Lambda 用に用意している設定の名前と同じ書き方にしました。CodeDeploy のドキュメントには、`CodeDeployDefault.LambdaCanary10Percent5Minutes` のような既定の設定が 9 つ載っています（確認日 2026-10-12）。canary は、最初に 10% を移し、決めた時間のあとで残りを一度に移します。linear は、決めた間隔ごとに 10% ずつ移します。この関数は接頭辞を除いた名前を読むので、あとで CodeDeploy に移すときに、同じ名前がそのまま使えます。9 つの名前がドキュメントの説明どおりの段になることは、テストで確かめています。

最後の段は必ず 100% で、その段を見張る時間が bake time です。全部のリクエストが新しいバージョンに届いた後も、しばらくはアラームを見続け、鳴ったら戻します。

計画は、手元で表示できます。

```bash
vp run rollout:plan
```

```text
Canary10Percent5Minutes
  at     0 s:  10% on the new version, watched for 300 s
  at   300 s: 100% on the new version, watched for 300 s
  done after 600 s at the earliest
  at 10%, 20 requests all miss the new version with probability 0.122;
  it takes 44 requests to bring that below 0.01
```

割合をエイリアスの設定に直すところも、関数にしてあります。

<<< @/examples/31-progressive-delivery/src/shift/plan.ts{weights}

100% より手前では、エイリアスは元のバージョンを指したままで、新しいバージョンは重みとして足されているだけです。戻すときは重みを消す 1 回の書き込みで済み、元のバージョンの番号を覚えておく必要もありません。

### 少ない割合で見えるもの

出力の最後の 2 行は、前のページで触れた「リクエストが少ないと意味が無い」ことの計算です。

<<< @/examples/31-progressive-delivery/src/shift/plan.ts{sample}

振り分けがリクエストごとに独立だとすると、10% の重みで 20 件のリクエストが来たとき、新しいバージョンに 1 件も届かない確率は 0.9 の 20 乗で、約 12% です。その確率を 1% 未満にするには 44 件が要ります。1 分に 2 件の API なら、5 分の canary の間に来るのは 10 件で、3 回に 1 回は新しいバージョンに 1 件も届かないまま 100% に進むことになります。

これは Lambda の振り分けを独立な試行とみなした計算で、実際の分布を測ったものではありません。ただ、段の時間を決めるときの下限にはなります。割合と時間は、その間に新しいバージョンへ届くリクエストの数から逆算してください。

## アラームから決める

<!-- section: 31.decide -->

進むか戻すかは、アラームの状態で決めます。スタックは、そのためのアラームを 2 つ作ります。

<<< @/examples/31-progressive-delivery/infra/lib/progressive-stack.ts{alarms}

2 つあるのは、見ているものが違うからです。Lambda の `Errors` は、関数が例外で終わった回数とタイムアウトした回数を数えます。04章のアプリは、途中で起きたエラーを捕まえて、自分で 500 のレスポンスを組み立てます。Lambda から見れば正常に終わった実行なので、`Errors` には数えられません。利用者に届いた 500 を数えているのは、API Gateway の `5xx` です。

しきい値は、1 分に 1 件です。人を呼ぶためのアラームとしては敏感すぎますが、この 2 つは人を呼びません。切り替えを止めるかどうかを決めるだけなので、迷ったら戻す側に倒してあります。データが無い 1 分は、鳴らない扱いにしています（`NOT_BREACHING`）。リクエストが来ていないことと、壊れていることを区別するためです。

1 回の観測から次の行動を決める関数が、判断の中心です。

<<< @/examples/31-progressive-delivery/src/shift/decide.ts{types}

<<< @/examples/31-progressive-delivery/src/shift/decide.ts{decide}

決まりは 3 つです。

アラームが 1 つでも `ALARM` なら、段の途中でも、bake time の途中でも、すぐに戻します。

すべてのアラームが `OK` と答えたときだけ、時間の経過を見て次の段へ進みます。`INSUFFICIENT_DATA` が混じっているときと、アラームを読む呼び出しそのものが失敗したときは、進みません。読めなかったことを「鳴っていない」と同じに扱うと、CloudWatch の調子が悪い間は、見張りが無いまま 100% まで進んでしまいます。

読めない状態が決めた秒数を超えて続いたら、戻します。10% のまま、いつまでも待ち続けるわけにはいかないからです。

始める前にも、同じアラームを見ます。

<<< @/examples/31-progressive-delivery/src/shift/decide.ts{start}

すでに鳴っているアラームの下では、切り替えを始めません。新しいバージョンのせいで鳴ったのか、前から鳴っていたのか、区別がつかないからです。

この関数は時刻も AWS も知りません。時刻は引数で受け取り、アラームの状態も引数で受け取ります。テストは、299 秒では待ち、300 秒で進むこと、読めない状態が 180 秒続いたら戻すことを、時計を動かさずに確かめています。

エイリアスを書くときは、読んだときの `RevisionId` を一緒に送ります。Lambda の API リファレンスによると、`RevisionId` を付けた `UpdateAlias` は、エイリアスが読んだ後に変わっていたら失敗します（確認日 2026-10-12）。05章の条件付き書き込みと同じ使い方で、誰かがコンソールから手で直したエイリアスを、スクリプトが古い判断で上書きしないようにしています。

アラームのほうは、名前を指定して読み、返ってこなかった名前があれば失敗にします。消されたアラームは、鳴っていないアラームと同じに見えるからです。

新しいバージョンは、切り替えを始めるときに発行します。

<<< @/examples/31-progressive-delivery/src/shift/aws.ts{publish}

`PublishVersion` は、前のバージョンからコードも設定も変わっていなければ、新しいバージョンを作りません。同じコードで `rollout:start` をやり直しても、バージョンが増え続けることはありません。

### 書き込みが失敗したとき

ネットワークの向こうへの書き込みは、成功したのに応答だけが届かないことがあります。

<<< @/examples/31-progressive-delivery/src/shift/run.ts{put}

失敗したら、まずエイリアスを読み直します。目的の状態になっていれば、書き込みは届いていたので先へ進みます。なっていなくて、`RevisionId` も変わっていなければ、書き込みは届いていないので送り直します。エイリアスの設定は「新しいバージョンに 10%」という絶対値なので、2 回送っても結果は同じです。`RevisionId` が変わっていたら、他の誰かが書いたということなので、そこで手を止めます。

### 全体の流れ

<<< @/examples/31-progressive-delivery/src/shift/run.ts{run}

結果は 4 種類あります。

<<< @/examples/31-progressive-delivery/src/shift/run.ts{outcome}

`refused` と `abandoned` を分けているのは、エイリアスに触ったかどうかが違うからです。`refused` は始める前に断ったので、何も変わっていません。`abandoned` は、途中で他の誰かがエイリアスを変えたので、それ以上は触らずに終わった状態です。戻そうとしたときに他の誰かの変更を見つけた場合も、上書きはしません。相手は、このスクリプトが知らないことを知っているかもしれないからです。どちらの場合も、タスクは 0 以外で終わります。ロールバックで終わったときも同じです。ロールバックは設計どおりに働いた結果ですが、リリースとしては失敗です。

この処理が守る不変条件は、次の 1 文です。

> 切り替えの間、エイリアスが指すのは元のバージョンと新しいバージョンだけで、アラームが `ALARM` になったのを見たら、すべてのリクエストを元のバージョンに戻して終わる。戻せなかったときは、そう報告する。

テストは、エイリアスとアラームと時計を偽物に差し替えて、この条件を壊そうとします。canary の途中でアラームが鳴る場合、100% にした後の bake time で鳴る場合、アラームが読めなくなる場合、ロールバックの書き込みが 1 回失敗する場合、書き込みの応答が失われる場合、途中で他の誰かがエイリアスを変える場合を、決まった順序で再現しています。

### スクリプトが途中で止まったら

CodeDeploy と違い、このスクリプトは手元の端末か CI のジョブで動きます。10% の段で端末を閉じれば、エイリアスは 10% のまま残り、アラームを見ている者はいなくなります。AWS の側には、続きを引き受ける仕組みがありません。

そのため、もう一度実行すれば続きから始められるようにしてあります。エイリアスが新しいバージョンにいくらかの重みを与えていれば、その割合に対応する段から再開し、その段の見張りを最初からやり直します。再開した時点でアラームが鳴っていれば、戻します。エイリアスが別のバージョンに重みを与えていた場合は、他の切り替えの途中なので、何もせずに断ります。

再開できることは、止まらないことの代わりにはなりません。10 分を超える計画を使うなら、実行する場所を、途中で消えないものにしてください。

## CodeDeploy に任せる場合

<!-- section: 31.codedeploy -->

本番のスタックを CloudFormation でデプロイしているなら、同じことを CodeDeploy に任せられます。CDK で書くと、次の数行です。

<<< @/examples/31-progressive-delivery/infra/lib/codedeploy-sketch.ts{codedeploy}

この関数は、デプロイするアプリには入っていません。テストの中でテンプレートを合成して、エイリアスに `UpdatePolicy` の `CodeDeployLambdaAliasUpdate` が付くことと、デプロイグループが `CodeDeployDefault.LambdaCanary10Percent5Minutes` を指すことを確かめているだけです。CloudFormation のテンプレートリファレンスによると、この属性があると、エイリアスのバージョンが変わるときに CloudFormation が CodeDeploy のデプロイを実行します（確認日 2026-10-13）。先に書いたとおり、固定した版の cdkd にはこの属性を読む処理がありません。cdkd でこのテンプレートをデプロイしたときに何が起きるかは、試していません。

CodeDeploy に任せると、この章のスクリプトに無いものが手に入ります。切り替えは AWS の側で進むので、端末を閉じても止まりません。`UpdatePolicy` には、トラフィックを移す前と後に実行する Lambda 関数をフックとして指定できます。
