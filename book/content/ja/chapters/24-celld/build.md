# 24 Self-hosting: しくみと実装

[前のページ](/ja/chapters/24-celld.md)で、celld の fleet を AWS のどこに置くかを図で見ました。このページでは、ネットワーク、状態の置き場所、ノードの中身の順に、その構成の理由と実装を見ていきます。料金の内訳は[最後のページ](/ja/chapters/24-celld/wrap.md)にあります。

## ピアの通信に TLS は無い

<!-- section: 24.network -->

この本の構成案には、もともと「ピアの通信は private なネットワークと TLS で守る」と書いてありました。調べてみると、TLS のほうは成り立ちません。celld にはリスナーが 2 つあり、公式文書によれば、どちらも TLS を終端しないからです。

- **public のリスナー**（`--listen`）は、デプロイした Worker に届きます。TLS とユーザーの認証は、手前のプロキシかアプリケーションが受け持ちます
- **internal のリスナー**（`--internal-listen`）は、ピアどうしの通信と、運用者向けの API に使います。ピアの通信は平文の HTTP です。fleet で共有する HMAC が接続の確立と制御のリクエストに署名しますが、暗号化はしません。さらに、運用者向けの API の多くには認証がなく、ノードを止める `POST /shutdown` も、状態を見る `/state` も認証なしで呼べます

internal のリスナーに届く人は、全員が管理者として扱われることになります。そのため公式は、信頼できる private なネットワークか、WireGuard や Tailscale のような暗号化されたオーバーレイの上に置くよう指示しています。

この章では、private なネットワークのほうをセキュリティグループで作ります。

<<< @/examples/24-celld/infra/lib/celld-stack.ts{network}

インバウンドのルールは 1 行だけで、internal のポートに、同じセキュリティグループのメンバーからだけ届くようにしています。相手を VPC の CIDR ではなくグループで指定しているので、同じ VPC にある別のインスタンスからは届きません。public のリスナーにはルールがありません。public のリスナーは loopback（`127.0.0.1`）で待たせているので、ノードの外からはもともと届きません。この構成には外からの入口（ingress）がなく、Worker へのリクエストはノードの上から送ります。

VPC の中だから暗号化されている、とは言い切れません。EC2 のドキュメントによると、インスタンス間の通信を自動で暗号化するのは一部のインスタンスタイプだけで、その一覧に M7g や C7g はあっても、この章が使う T4g はありません。AZ をまたぐ通信は物理層で暗号化される、とも書かれています。それで足りるかどうかは、流すデータによって決まります。足りないなら、一覧にあるインスタンスタイプを使うか、celld の勧めるオーバーレイを足してください。この章では、どちらも作っていません。

## 状態はバケットにあるが、ディスクも捨てられない

<!-- section: 24.state -->

長く残す状態がバケットにあるなら、ノードは使い捨てで、インスタンスもボリュームもいつ消してもよいように思えます。

実際には、そうできるのは条件が揃ったときだけです。celld の既定の動作である `fleet` では、cell を担当するノードが書き込みを 1 台か 2 台の別のノード（フォロワー）に送り、フォロワーがディスクに書いた時点で応答を返します。バケットへのアップロードはその後です。公式文書は、フォロワーのディスクが、バケットにまだ無い応答済みの書き込みを持っていることがある、とはっきり書いています。

このことから、ディスクを捨ててよい場合と、捨ててはいけない場合が決まります。

- ノードを 1 台ずつ正しい手順で止めるなら、そのノードのディスクは捨てられます。止まる前に、cell の引き渡しとアップロードを済ませるからです
- 全部のノードのディスクを同時に捨てると、応答済みの書き込みを失うことがあります
- ノードが突然止まったとき、残りのノードは、そのノードがアップロードしていなかった分をフォロワーのディスクから集めます。フォロワーまで消えていたら、集められません

そこで、バケットと、ノードごとのデータボリュームの両方を、残す設定にしました。

<<< @/examples/24-celld/infra/lib/celld-stack.ts{buckets}

ボリュームは 23章と同じく、インスタンスとは別のリソースです。インスタンスを作り直しても、ボリュームは付け替えられるだけで中身は残ります（ノードの定義は `celld-stack.ts` の `nodes` の region にあります）。`stateOnDestroy` の既定は `retain` なので、スタックを destroy しても、バケット 2 つとデータボリュームは残ります。残ったボリュームには料金がかかり続けるので、消し方を[片付け](/ja/chapters/24-celld/wrap.md)に書きました。練習だけなら、`-c stateOnDestroy=delete` を指定すると、スタックと一緒に消える設定になります。

本番で `delete` にする理由は、おそらくありません。

バケットのバージョニングは有効にしていません。celld は自分でオブジェクトを消しますし、古い世代を掃除する仕組み（epoch GC）も持っています。そこにバージョニングを重ねたときの動作はどこにも書かれていなかったので、足しませんでした。

次は、ノードに与える権限です。

<<< @/examples/24-celld/infra/lib/celld-stack.ts{role}

公式は「バケットの認証情報を持つ者が fleet を支配する」と書いています。デプロイしたアプリケーションも、cell の状態も、持ち主の記録も、ピアの認証に使うシークレットも、すべてバケットの中にあるからです。そこで、ノードの権限は 1 つのバケットの 1 つのプレフィックスに絞り、バックアップ用のバケットにはノードから一切触れないようにしました。

celld が S3 のどのアクションを必要とするかの一覧は、公式文書にありません。Azure 向けには「read、write、list、delete」と書かれているので、それを S3 のアクションに読み替え、ソースがマルチパートアップロードを使っているのを見て `s3:AbortMultipartUpload` を足しました。足りなければ、ノードのログに AccessDenied が出るはずです。

## ノードの中身

<!-- section: 24.node -->

マシンの用意は 23章と同じ流れです。ユーザーデータは、アカウントとディレクトリと systemd のユニットを置き、データボリュームをマウントするところまでを受け持ちます。celld 本体は入れません。

ユニットは、celld がスーパーバイザーに求めていることをそのまま書いたものです。

<<< @/examples/24-celld/deploy/celld.service

23章のユニットと違うところが 3 つあります。

1 つ目は `Restart=always` と `StartLimitIntervalSec=0` です。celld のノードは、バケットのリース（生存の記録）を更新できなくなると自分から止まり、`SELF-FENCE:` で始まる行をログに出して、終了コード 3 で終わります。こうなったノードは、再起動でしか戻りません。そこで公式は、スーパーバイザーが回数の上限なしで再起動することと、次の起動までリースの寿命 1 つ分（既定で 10 秒）以上待つことを求めています。23章では 5 回落ちたら諦める設定にしましたが、ここでは逆に、何度でも起こします。

2 つ目の `RestartSec=15` は、その「リースの寿命 1 つ分以上」にあたります。

3 つ目は `TimeoutStopSec=60` です。celld は SIGTERM を受けると、担当している cell をほかのノードに引き渡してから終わります。引き渡しにかける時間の上限は既定で 40 秒です。systemd がそれより先に SIGKILL を送ると、引き渡しが途中で切れます。

`RestartSec` と `TimeoutStopSec` は、celld の要求を満たさない値にすると、ユニットを生成する時点でエラーになるようにしてあります。

プライベートサブネットのノードはインターネットに出られないので、アーカイブは S3 から取ります。`celld:fetch` で取得して確かめたアーカイブを、`celld:artifacts` でバケットに置いておきます。ダイジェストはバケットから読まず、リポジトリに固定した値を引数で渡します。こうしておけば、バケットの中身を書き換えられる人がいても、照合に使うダイジェストまでは書き換えられません。

celld の設定は、フラグではなく環境変数で渡しています。どれも公式文書にある名前です。なかでも大事なのは `CELLD_WATCH` です。指定しないと celld は一時ディレクトリを作業場所にするので、フォロワーとして預かった書き込みが、再起動で消える場所に置かれてしまいます。ここではデータボリュームの上を指定しています。

`CELLD_ADVERTISE` は、ほかのノードから見た自分のアドレスです。インスタンスの private IP を IMDSv2 で読んで書き込みます。

`CELLD_NODE`（ノードのセッション ID）は設定していません。固定してよい値かどうかが文書から読み取れなかったので、起動ごとに生成する既定のままにしました。

このスクリプトは、サービスを起動も再起動もしません。ノードをいつ止めて起こすかは、[デプロイ](/ja/chapters/24-celld/deploy.md)のページで順番を決めて扱うからです。
