# 56 Nova: デプロイ

[手元で動かした](/ja/chapters/56-nova/local.md) API を Lambda にのせます。スタックの定義を、モデル、バケット、権限、関数の順に見てから、デプロイの手順を書きます。このページのデプロイ以降の手順は、この章を書いている時点では実行していません。

## スタック

<!-- section: 56.stack -->

スタックは、説明に使う経路を `-c describeModel=...` で受け取り、最初のページの一覧と照らします。

<<< @/examples/56-nova/infra/lib/nova-stack.ts{model}

一覧にない ID や、画像を読めないモデルの ID を渡すと、synth が止まります。終了したモデルの ID なら、終了した日付を表示します。17章が、確かめていない ID を synth で止めたのと同じ理由です。経路が決まらないと、IAM に書く ARN が決まりません。

バケットは 1 つです。

<<< @/examples/56-nova/infra/lib/nova-stack.ts{bucket}

公開の設定は 07章のバケットと同じで、オブジェクトを公開する方法を残していません。ライフサイクルルールは `c/` にだけかけています。claim は、作ったリクエストが自分で消します。関数が途中で止まって残ったものは、リースが切れた時点で無視されるようになり、1 日たつと S3 が消します。説明文には期限を付けていません。

このスタックは、練習用に自分のバケットを持っています。ノートのアプリに組み込むときは、07章のバケットをそのまま使い、関数のロールに次の権限を足す形になります。

<<< @/examples/56-nova/infra/lib/nova-stack.ts{role}

S3 の権限は、接頭辞ごとに分けています。アップロードの `u/` は読むだけです。関数は画像を書き換えません。この読み取りの権限は、Bedrock が画像を取りに行くときにも使われます。書き込めるのは、説明文の `g/` と claim の `c/` だけです。`If-Match` 付きの書き込みには、`s3:PutObject` に加えて `s3:GetObject` が要る、と S3 のドキュメントにあります。

Bedrock の権限は、一覧の関数が返した ARN をそのまま書いています。既定の `jp.amazon.nova-2-lite-v1:0` なら、profile が 1 つと、東京と大阪のモデルが 2 つです。モデルのステートメントには、17章と同じく、その profile を通した呼び出しに限る条件を付けています。In-Region の経路を選んだときは、profile がないので、東京のモデル 1 つだけを書きます。アクションは `bedrock:InvokeModel` です。`Converse` はこのアクションで認可されます。ストリーミングはしないので、17章の `bedrock:InvokeModelWithResponseStream` は付けていません。

関数と URL は、17章とほぼ同じです。

<<< @/examples/56-nova/infra/lib/nova-stack.ts{function}

タイムアウトは 40 秒で、モデルを待つ上限の 30 秒より長く、リースの 60 秒より短くしてあります。function URL の認証は `AWS_IAM` で、レスポンスストリーミングは使いません。

関数の入口は、04章のアダプターです。

<<< @/examples/56-nova/src/lambda.ts{handler}

function URL が関数に渡すイベントは、API Gateway の HTTP API と同じ形なので、04章の `handleApiGateway` がそのまま使えます。持ち主は、そのイベントから取り出します。

スタックのテストは、次のことを固定しています。ロールに許されたアクションの一覧。`u/` には読み取りしかないこと。Bedrock の対象が、経路の種類ごとに決まった ARN だけであること。バケットが公開されないこと。URL が署名を求めること。終了したモデルで synth が止まること。そして、使っているリソースの種類です。種類は 7 つで、固定した版の cdkd（0.296.28）は、そのすべてに専用の実装を持っています。

テンプレートを作るところまでは、手元で確かめられます。

```bash
vp run nova:infra:synth
```

## デプロイして呼ぶ

<!-- section: 56.deploy -->

ここからは AWS を変更します。手順は 02章と同じです。

```bash
vp run nova:infra:diff
vp run nova:infra:deploy
```

デプロイしたら、まず一覧をアカウントと照らします。

```bash
vp run nova:models
```

このタスクが比べている部分は、次のとおりです。

<<< @/examples/56-nova/scripts/models.ts{compare}

一覧にある経路がアカウントの側に見つからなければ、タスクは失敗で終わります。モデルが終了したか、ドキュメントの読み違いです。どちらの場合も、`src/catalog.ts` を直すところから始めます。

次に、デプロイした URL を通して 1 枚を説明させます。

```bash
vp run nova:smoke
```

このタスクは課金されます。モデルを 1 回呼び、画像 1 枚と数十トークン分の料金がかかります。行うことは、順に次のとおりです。

- 署名のないリクエストを送り、403 で断られることを確かめる
- 署名したリクエストで `/me` を呼び、自分の接頭辞を受け取る
- その接頭辞の下に、あなたの認証情報で画像を 1 枚アップロードする。`--image` でファイルを渡さなければ、1 × 1 ピクセルの PNG を使う
- PUT で説明文を作らせ、202 が返ったら GET で聞き直す
- もう一度 PUT を送り、`reused` が `true` で、`createdAt` が変わっていないことを確かめる
- 説明文とアップロードを消す

リクエストの署名は、17章と同じ方法です。

<<< @/examples/56-nova/scripts/sign.ts{sign}

ドリフトの検査は 02章と同じです。

```bash
vp run nova:infra:drift
```
