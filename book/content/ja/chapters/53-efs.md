# 53 EFS: いくつもの実行環境から同時にマウントするファイルシステム

EFS は、いくつもの実行環境が同時にマウントして、同じファイルを読み書きできるファイルシステムです。Lambda の関数が 10 個同時に動いていても、Fargate のタスクが 2 つの AZ に分かれていても、全員が同じディレクトリを見ます。この章で考えるのは、その先です。全員が同じファイルに書けるとき、ファイルの中身を壊さないためにアプリケーションが何をするか、を扱います。

題材は [23章](/ja/chapters/23-ec2.md)のノートです。23章では、1 台のインスタンスの 1 つのプロセスが、EBS のボリュームの上の 1 つのファイルにノートを書きました。そのコードは「書き手は 1 つ」という前提で正しく動きます。この章では同じノートを EFS に置き、[04章](/ja/chapters/04-http-api.md)の API を Lambda で動かして、書き手を何人にでも増やします。前提が崩れると何が起きるかをテストで見てから、書き手が何人いても成り立つ書き方に直します。

この章のスタックには、時間単位で課金されるリソースがありません。ファイルシステムは置いた量に対して課金され、空のままなら 1 か月で USD 0.000002 ほど、つまり請求書の上では 0.00 です。ただし、同じ 1 GB を置くと S3 の 14 倍あまりの料金になります。内訳はこのページの「料金」にあります。

前提は [11章](/ja/chapters/11-network.md)の VPC です。11章のスタックを既定の構成でデプロイしてあれば足ります。コードは `examples/53-efs/` にあります。

## S3、EBS、EFS の選び方

<!-- section: 53.choice -->

この本では、データを置く場所として S3（[07章](/ja/chapters/07-uploads.md)）と EBS（23章）を使ってきました。EFS を足すと 3 つになります。名前は似ていますが、この 3 つはアプリケーションへの見え方が違います。

S3 はファイルシステムではありません。キーを指定してオブジェクトを丸ごと置き、丸ごと取り出す HTTP の API です。ファイルの途中だけを書き換える操作も、ディレクトリを rename する操作もありません。そのかわり、1 つのキーへの書き込みは丸ごと入れ替わり、読む側が半端な内容を受け取ることはないと、ドキュメントが約束しています。

EBS のボリュームは、ディスクです。ファイルシステムは自分でその上に作ります（23章では XFS でした）。ext4 や XFS は、1 台のマシンのカーネルがディスクを独占している前提で作られているので、ボリュームを使えるのは実質 1 台です。複数のインスタンスにつなぐ Multi-Attach は io1 と io2 にだけあり、ドキュメントは、ふつうのファイルシステムではなくクラスター用のファイルシステムを使うよう書いています。

EFS は、AWS が運用する NFS のサーバーです。ファイルシステムそのものが AWS の側にあり、クライアントはネットワーク越しに `open` や `rename` を頼みます。だから何台からでも同時にマウントでき、容量も前もって決めません。

| | S3 | EBS | EFS |
| --- | --- | --- | --- |
| アプリケーションからの見え方 | HTTP の API | ディスク（ファイルシステムは自分で作る） | マウントしたディレクトリ |
| 同時に使える実行環境 | 何台でも | 実質 1 台、同じ AZ | 何台でも、同じリージョンの複数の AZ から |
| 一部だけの書き換え、rename | できない | できる | できる |
| 1 GB・1 か月（東京、Standard） | USD 0.025 | USD 0.096（gp3） | USD 0.36 |

選ぶときの問いは 1 つで、**そのデータを使うコードが、ファイルのパスを必要とするか**です。

自分で書くコードなら、たいていパスは要りません。ノートのような小さなレコードは DynamoDB（[05章](/ja/chapters/05-dynamodb.md)）に、添付ファイルのような大きなかたまりは S3 に置けば、同時に書いたときの約束がはっきりしていて、料金も安く済みます。この章がノートをファイルに置くのは、ファイルの上で起きることを見るためで、ノートの置き場所として EFS を勧めているわけではありません。

EFS が合うのは、パスを要求するコードを、複数の実行環境で動かしたいときです。たとえば次のような場合です。

- 既存のソフトウェアが、設定やデータをディレクトリに読み書きする。CMS、ビルドのキャッシュ、機械学習のモデルを読むライブラリなどです
- Lambda の `/tmp` や Fargate のエフェメラルストレージには収まらない、あるいは実行環境をまたいで残したいファイルがある
- 複数のタスクが、同じファイルの集まりを読む

1 台で足り、そのマシンの上だけで使うなら、EBS のほうが速くて安くなります。

2026-10-13 時点では、もう 1 つ選択肢があります。Lambda のドキュメントは、関数にマウントできるファイルシステムとして EFS と Amazon S3 Files の 2 つを挙げています。S3 Files は、S3 のバケットをファイルシステムとして見せるサービスで、ドキュメントによると EFS を使って作られていて、ファイルへの変更をバケットと双方向に同期します。この章では概要のページを読んだだけで、料金も、東京リージョンで使えるかも確かめていません。データの正本を S3 に置いたままパスで読み書きしたい場合は、先にそちらのドキュメントを読んでください。

## 料金

<!-- section: 53.cost -->

金額は USD、東京リージョン、従量課金の定価、税別です。単価は 2026-10-13 に AWS Price List から読みました。計算の中身は[料金の計算](/ja/reference/pricing.md)にあります。

EFS の課金は、置いた量と、読み書きした量の 2 本立てです。

| 対象 | 単価 |
| --- | --- |
| Standard の保存（Regional） | 1 GB・1 か月 0.36 |
| Standard の保存（One Zone） | 1 GB・1 か月 0.192 |
| Infrequent Access の保存 | 1 GB・1 か月 0.0272（Elastic スループットでは 0.02） |
| Archive の保存 | 1 GB・1 か月 0.01 |
| Elastic スループットの読み取り | 1 GB 0.04 |
| Elastic スループットの書き込み | 1 GB 0.07 |
| Infrequent Access のデータの読み書き | 1 GB 0.012 |
| Provisioned スループット | 1 MiBps・1 か月 7.20 |

**マウントしていないときにかかるのは、保存の料金だけです。** マウントターゲットとアクセスポイントには、Price List に SKU がありません。料金ページにも、最低料金や初期費用はないと書いてあります。Elastic スループットは読み書きしたバイト数にだけ課金されるので、誰も読み書きしなければ 0 です。空のファイルシステムは、ルートディレクトリ 1 つの 6 KiB として計量されるので、1 か月で USD 0.000002 ほどになります。

置いたままで料金が増えるのは、次の設定をしたときです。この章のスタックは、どちらも既定では使いません。

- Provisioned スループット。確保した量に対して、使わなくても毎月かかります。10 MiBps なら月 72 で、ここから保存量に応じて含まれる分が引かれます
- 自動バックアップ。AWS Backup の保存料金がかかり、スタックを消したあとも復旧ポイントが残ります（[費用、注意点、片付け](/ja/chapters/53-efs/wrap.md)）

使ったときの例も計算しておきます。ノート 100 件を置き、書き込みが月 1,000 回、一覧が月 10,000 回ある場合です。

| 対象 | 数量 | 定価 |
| --- | --- | --- |
| Standard の保存 | 0.000595 GB | 0.0002 |
| Elastic スループットの書き込み | 0.0305 GB | 0.0021 |
| Elastic スループットの読み取り | 30.5 GB | 1.2207 |
| Lambda のリクエスト | 11,000 回 | 0.0022 |
| Lambda の実行時間 | 275 GB 秒 | 0.0037 |
| HTTP API のリクエスト | 11,000 回 | 0.0142 |
| 小計 | | **1.24** |

保存しているのは 600 KiB あまりなのに、読み取りが 30 GB になっています。理由は 2 つあります。1 つは、Elastic スループットの計量の単位です。ドキュメントには、データの操作は最初の 32 KiB のあと 1 KiB 刻みで計量するとあります。この章では、数百バイトのノートを 1 件読んでも 32 KiB として数えられる、と読んで計算しました。もう 1 つは、この章の実装が一覧のたびに 100 件のファイルをすべて読むことです。小さなレコードを一覧する用途では、ファイルを並べるより、インデックスを持つデータベースのほうが向いています。

この表には、メタデータの操作（ディレクトリの一覧、ファイルの作成、rename など）の料金が入っていません。回数を数えていないからで、0 という意味ではありません。関数の実行時間（1 回 0.1 秒）も仮定で、計測していません。Lambda の毎月の無料枠を差し引くと、Lambda の 2 行は 0 になりますが、小計は 1.24 のままです。EFS には、新しいアカウント向けに 12 か月間 5 GB の無料利用枠の記述がありますが、読者のアカウントに当てはまるかを確かめられないので、差し引いていません。

node client: Client
node api: API Gateway | HTTP API
node fn1: Lambda 実行環境 | Private1, /mnt/notes

edge client -> api: HTTPS
edge api -> fn1
edge api -> fn2
edge fn1 -> mt1: NFS over TLS
edge fn2 -> mt2: NFS over TLS

edge mt2 -> ap
edge ap -> fs

API Gateway は、リクエストを Lambda の実行環境のどれかに渡します。同時に届いたリクエストは別々の実行環境で処理され、実行環境は 11章の 2 つのプライベートサブネットのどちらかにつながっています。どの実行環境も、起動するときにアクセスポイントを `/mnt/notes` にマウントします。図の「NFS over TLS」は、Lambda のマウントが TLS で暗号化されるという AWS の発表にもとづいています（[しくみと実装](/ja/chapters/53-efs/build.md)で扱います）。

04章の関数は、ノートを実行環境ごとのメモリに持っていました。だから、ある実行環境で作ったノートは、別の実行環境からは見えませんでした。この章では、どの実行環境で作ったノートも、次のリクエストがどの実行環境に届いても読めます。そのかわり、2 つの実行環境が同じ瞬間に同じディレクトリへ書くことがあります。

## EFS を使わない場合

次のどれかに当てはまるなら、EFS は要りません。

- データを使うのが自分のコードだけで、キーと値で足りる。DynamoDB か S3 を使います
- 書き手が 1 つのプロセスだけで、1 台のマシンで足りる。23章のとおり EBS を使います
- 実行のあいだだけ要る作業用のファイルである。Lambda の `/tmp` や Fargate のエフェメラルストレージで足ります
- レイテンシーが効く処理で、ファイルを何度も開く。EFS の読み書きは、1 回ごとにネットワークを通ります。ドキュメントの値は、読み取りがおよそ 1 ミリ秒、書き込みがおよそ 2.7 ミリ秒で、最良の条件での値だと注記されています。S3 や手元のディスクと数値で比べられる記述は、読んだドキュメントの中にはありませんでした
