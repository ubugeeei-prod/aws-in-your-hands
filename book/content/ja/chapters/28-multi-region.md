# 28 Multi-Region: global tables、S3 replication、Route 53

[22章](/ja/chapters/22-recovery.md)は、消してしまったデータを戻しました。この章では、リージョンが応答しなくなっても、アプリが答え続けるようにします。

ここまでの章は、すべてを東京リージョン（`ap-northeast-1`）に置いてきました。DynamoDB は、アベイラビリティゾーンが 1 つ丸ごと止まっても動き続けるように作られたサービスです。それでも、リージョン全体が使えなくなる障害には、ここまでの構成は備えていません。この章では、同じアプリを大阪リージョン（`ap-northeast-3`）にも置き、テーブルと画像を 2 つのリージョンのあいだで複製し、Route 53 に行き先を切り替えさせます。

2 つ目のリージョンを足す作業そのものは、設定を数行書けば済みます。難しいのは、足したあとに、これまでの章が守ってきた約束のどれが守られなくなるかを知ることです。[05章](/ja/chapters/05-dynamodb.md)は、同じノートを 2 人が同時に編集したら片方に `409` を返すと約束しました。グローバルテーブルの既定の設定では、2 人が別々のリージョンに書いたとき、この約束は破られます。章の中心は、その壊れ方をテストで再現し、どこまでを受け入れるかを決めることです。

先に断っておくと、著者はこの章のスタックを AWS にデプロイしていませんし、リージョンの障害もフェイルオーバーも、一度も起こしていません。手元で確かめたのは、2 つのリージョンをメモリの上に置いたモデルと、スタックのテンプレートです。モデルは、DynamoDB と S3 と Route 53 のドキュメントが書いている規則を写したもので、実物の代わりにはなりません。

前提は 05章、[07章](/ja/chapters/07-uploads.md)、22章です。コードは `examples/28-multi-region/` にあります。

スタックは 2 つあり、同じクラスから作ります。東京のスタック（`AihMultiRegion`）が、グローバルテーブルと、東京のバケット、関数、API を持ちます。大阪のスタック（`AihMultiRegionStandby`）は、大阪のバケット、関数、API を持ちます。テーブルのレプリカは大阪にもできますが、定義は東京のスタックにしかありません。理由は[デプロイのページ](/ja/chapters/28-multi-region/deploy.md)に書きます。

アプリは 05章のノート API をそのまま使っています。関数のコードは 2 つのリージョンで同じで、それぞれが自分のリージョンのレプリカだけを読み書きします。DynamoDB には、リージョンをまたぐエンドポイントがありません。どのリージョンのレプリカと話すかは、関数がどのリージョンで動いているかで決まります。

Route 53 の部分は、ドメインを指定したときだけ作ります。ホストゾーンとドメインが必要で、ヘルスチェックには月額の料金がかかるからです。指定しなければ、2 つの API にそれぞれの URL で直接アクセスできます。

## active-passive と active-active

<!-- section: 28.modes -->

2 つのリージョンの使い方は、大きく 2 つに分かれます。

- **active-passive。** ふだんは東京だけがリクエストに答え、大阪は待機します。東京が異常になったら、大阪に切り替えます
- **active-active。** 両方がいつも答えます。利用者は近いほうにつながります

Route 53 の用語では、フェイルオーバールーティングを使う構成が active-passive、それ以外のルーティングポリシーにヘルスチェックを組み合わせた構成が active-active です。この章のスタックは、既定でフェイルオーバールーティングを使い、`-c routing=latency` を付けるとレイテンシールーティングに変わります。

紛らわしいのは、DynamoDB のグローバルテーブルが、テーブルとしては常に active-active であることです。どのレプリカも、いつでも読み書きを受け付けます。「いまは東京だけが書く」という決まりは DynamoDB の中にはなく、リクエストをどこへ送るかで、アプリの側が作ります。ドキュメントも、active-passive として扱うなら、書き込みの行き先を DynamoDB の外で管理するように書いています。

この章が選ぶのは、**active-passive で、切り替えは自動、大阪は待機中も書き込みを受け付ける**構成です。理由は次のとおりです。

05章の version の検査は、2 つの書き込みが同じレプリカに届いて初めて働きます。書き込みを東京だけに送っていれば、検査は今までどおり効きます。active-active にすると、近いリージョンに書けるぶん速くなりますが、同じノートへの編集が 2 つのリージョンに分かれたとたんに、片方が黙って消えます。ノートのアプリで、それは受け入れにくい壊れ方です。

切り替えを自動にしたのは、目標の復旧時間が 5 分だからです。人が気づいて、判断して、操作するには短すぎます。その代わり、切り替えの前後の短い時間には、古い行き先を覚えているクライアントが東京に書き、新しいクライアントが大阪に書くことがあります。そのあいだは、active-active と同じ壊れ方をします。この章は、その時間の長さを見積もり、起きることをテストに書いたうえで、受け入れます。

受け入れたくない場合のために、大阪を読み取り専用で待たせる設定（`-c standbyWrites=refuse`）も用意しました。書き込みの衝突は起きなくなりますが、切り替えのときに人がデプロイし直す必要があり、5 分の目標は守れなくなります。

もう 1 つの道は、整合性モードを変えることです。グローバルテーブルには、書き込みがほかのリージョンに届いてから成功を返すモード（MRSC）があり、これなら 2 つのリージョンに分かれた編集でも、片方に衝突が返ります。3 つのリージョンが必要で、書き込みは遅くなり、トランザクションと TTL が使えなくなります。固定した版の cdkd がこのモードの指定を扱わないこともあって、この章のスタックは使っていません。動きは、[次のページ](/ja/chapters/28-multi-region/build.md)のモデルで比べます。

## 1 つのリージョンに残るもの

<!-- section: 28.single-region -->

テーブルとバケットを複製しても、アプリ全体が 2 つのリージョンで動くわけではありません。これまでの章が作ったもののうち、東京にしかないものを挙げます。

- **サインイン。** [06章](/ja/chapters/06-auth.md)の Cognito のユーザープールは、1 つのリージョンに作られ、利用者の情報をそのリージョンにだけ保存します。東京のユーザープールに届かなければ、新しいサインインはできません。この章の API は 05章のものなので、サインインを通していません。06章の JWT オーソライザーを大阪に置いたとき、東京に届かないあいだも手持ちのアクセストークンの検証が続くかどうかは、確かめていません
- **シークレット。** [21章](/ja/chapters/21-security.md)のシークレットは、東京の Secrets Manager にあります。Secrets Manager にはほかのリージョンへ複製する機能がありますが、21章は使っていないので、大阪にはありません
- **デプロイの仕組み。** [20章](/ja/chapters/20-shipping.md)のパイプラインも、cdkd が state を置くバケットも、東京を前提にしています。東京が使えないあいだに大阪のスタックを変える必要が出ても、いつもの手順が動くとは限りません
- **キューとメール。** [08章](/ja/chapters/08-async.md)のキューとワーカー、[15章](/ja/chapters/15-email.md)の送信の設定は、東京のスタックが東京に作ったものです。大阪には同じものがありません
- **アラームとダッシュボード。** [19章](/ja/chapters/19-observability.md)のアラームとダッシュボードは、東京のメトリクスを見るように作りました。大阪の関数のログとメトリクスは大阪に出るので、そのままでは誰も見ていません

つまり、この章の構成で大阪に切り替わったあとに動くのは、すでにサインインしている利用者の、ノートの読み書きまでです。実際のフェイルオーバーで困るのは、たいていデータベースではなく、この一覧にあるものです。本番で 2 つ目のリージョンを持つなら、一覧の 1 つずつについて、複製するのか、大阪にも作るのか、止まることを受け入れるのかを決めます。

切り替えの操作にも同じ注意がいります。Route 53 のドキュメントは、障害のときの切り替えを、ヘルスチェックのようにデータプレーンだけで動く仕組みに任せるよう勧めています。コンソールや API でレコードを書き換える操作はコントロールプレーンで、障害の最中に使えるとは限らないからです。この章の既定の構成が、切り替えをヘルスチェックに任せているのは、そのためでもあります。

## 2 つ目のリージョンを持たないほうがよい場合

ここまで読んで、割に合わないと感じたなら、その感覚はたぶん正しいです。2 つ目のリージョンは、料金よりも、考えることを増やします。書き込みの衝突、複製の遅れ、片方にしかないリソース、2 倍になるデプロイと監視です。

DynamoDB の単一リージョンのテーブルは 99.99% の可用性を、グローバルテーブルは 99.999% を SLA に掲げています。この差が要るかどうかを、先に考えてください。データを失わないことが目的なら、22章のバックアップで足ります。リージョンの障害のあいだ数時間止まってもよいなら、バックアップを別のリージョンに置いておき、障害のときに作り直す方法もあります。この章の構成が要るのは、止まってよい時間が分の単位のときです。
