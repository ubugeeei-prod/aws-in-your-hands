# 52 ECR: tag と digest、lifecycle、scan、複製、pull through cache

イメージのタグは名前で、ダイジェストは中身です。名前はあとから別の中身を指せますが、中身から計算したダイジェストは変わりません。この章で扱う設定は、どれもこの違いから出てきます。デプロイが指すのは名前か中身か、消してよいイメージをどう決めるか、検査した結果はどのイメージのものか、という話です。

[12章](/ja/chapters/12-containers.md)では、リポジトリを 1 つ作り、イメージを 1 つ手でプッシュしました。タグは immutable にし、新しいほうから 10 個を残す規則を付けたところで終わっています。この章はその続きで、CI が毎日イメージを積んでいくようになったときに決めることを順に見ていきます。前提は 12章のほかに、GitHub Actions から OIDC で AWS に入る [20章](/ja/chapters/20-shipping.md)と、Inspector を紹介した [21章](/ja/chapters/21-security.md)です。コードは `examples/52-ecr/` にあります。

料金を先に書くと、この章のスタックは、イメージが 1 つも無ければ USD 0 です。ECR の料金は保存している量に対してかかり、東京リージョンでは 1 GB あたり月 USD 0.10 です。時間課金のリソースはありません。

Nix の shell には Docker のデーモンが無いので、この章ではイメージを 1 つもビルドしておらず、プッシュもしていません。手元で動かしたのは、判断を担う関数のテストと、スタックの synth です。ECR のふるまいについて書いたことは、ドキュメントから読んだものです。

## 全体像

<!-- section: 52.overview -->

```figure
caption: CI は 1 つのブランチからだけロールを引き受け、1 つのリポジトリにプッシュする。タスク定義はダイジェストでイメージを指す
node ci: GitHub Actions | main ブランチ
node role: プッシュ用のロール | OIDC, 1 時間
node public: Amazon ECR Public
node cache: pull through cache | ecr-public/*
node repo: ECR のリポジトリ | immutable, scan on push, lifecycle
node task: ECS のタスク定義 | image: repository@sha256:...
edge ci -> role: AssumeRoleWithWebIdentity
edge role -> repo: PutImage
edge public --> cache: 最初の取得で写しを作る
edge cache -> ci: ベースイメージ
edge repo -> task: ダイジェストで取得
group aws: AWS account = role, cache, repo, task
mark repo
```

スタックに入っているのは、リポジトリ、CI がプッシュに使うロール、Amazon ECR Public を上流にした pull through cache のルールの 3 つです。ロールは `-c githubRepository=owner/repo` を渡したときだけ、ルールは `-c pullThroughCache=on` を渡したときだけ作ります。何も渡さなければ、できるのはリポジトリ 1 つです。

リポジトリには 3 つの設定を付けました。タグの付け替えを例外なく拒否する設定、プッシュのたびに脆弱性を検査する設定、古いイメージを消すライフサイクルポリシーです。ライフサイクルポリシーは、消してはいけないイメージまで消す設定を書きやすいので、手元で評価する小さな evaluator を書き、テストで確かめられるようにしました。

リージョンをまたぐ複製、別アカウントからの取得、署名は、スタックに入れていません。複製と署名はレジストリ全体の設定で、1 つのスタックが持つと、同じアカウントのほかのリポジトリにも効いてしまうからです。これらは[次のページ](/ja/chapters/52-ecr/build.md)で、ドキュメントに沿って説明します。

## タグは名前、ダイジェストは中身

<!-- section: 52.digest -->

イメージを指す書き方は 2 つあります。`repository:v1.2.0` はタグで、`repository@sha256:...` はダイジェストです。ダイジェスト（digest）は、イメージのマニフェストの SHA-256 です。マニフェストはレイヤーのダイジェストを並べたものなので、中身が 1 バイトでも違えばダイジェストも変わります。

<<< @/examples/52-ecr/src/reference.ts{reference}

タグのほうは、リポジトリの中の表にすぎません。「`prod` は `sha256:aaa...` を指す」という 1 行があり、同じタグで別のイメージをプッシュすると、その行が書き換わります。元のイメージは消えずに、タグの無いイメージとして残ります。

この章の不変条件は、**タスク定義が指しているイメージが、実際に動くイメージである**ことです。タスク定義にタグを書き、そのタグが動くと、不変条件は 2 通りに壊れます。

```figure
type: sequence
caption: タスク定義は一度も書き換えていないのに、ロールバックで動くのは壊れたイメージになる
actor ci: CI
actor repo: リポジトリ
actor ecs: ECS
step ci -> repo: push prod = aaa
step ecs -> repo: リビジョン 1 をデプロイ, prod を取得
note repo: prod は aaa
step ci -> repo: push prod = bbb
note repo: prod は bbb, aaa はタグなし
step ecs -> repo: リビジョン 2 をデプロイ, prod を取得
note ecs: bbb が動き、壊れている
step ecs -> repo: リビジョン 1 にロールバック, prod を取得
note ecs: 動くのは bbb
```

1 つ目は、同じタスク定義から起動した 2 つのタスクが、別のイメージで動くことです。タグがどのイメージを指すかは、取得するときに決まるので、2 回の取得のあいだにタグが動けば結果が変わります。2 つ目は図のとおりで、ロールバックが効かなくなります。リビジョン 1 とリビジョン 2 は、どちらも `repository:prod` と書いてあるだけの同じ文字列です。リビジョン 1 に戻しても、`prod` はもう壊れたイメージを指しています。正しかったイメージはリポジトリに残っていますが、名前を失っているので、ダイジェストを控えていなければ探せません。

このモデルは、ドキュメントの記述をこの本が読み取って書いたもので、ECR そのものではありません。知っているのは、タグ、ダイジェスト、タグの付け替えを許すかどうかの設定だけです。

直し方は 2 つあり、両方使います。1 つはリポジトリの側で、タグを immutable にします。すでにあるタグで別のイメージをプッシュすると、ECR は `ImageTagAlreadyExistsException` を返します。もう 1 つは指す側で、タスク定義にダイジェストを書きます。ダイジェストで指したイメージは、タグがどう動いても同じものです。そのイメージが消されていた場合は、別のイメージが動くのではなく、起動が失敗します。黙って違うものが動くよりも、失敗するほうが気づけます。

ECS も、この問題の一部を引き受けています。ドキュメントによると、ECS のサービスは既定で、タスク定義のタグをデプロイのときにダイジェストへ解決します。デプロイで最初に起動したタスクがダイジェストを決め、同じサービスのほかのタスクはそのダイジェストで起動します。スケールアウトで増えたタスクだけが別のイメージになる、という 1 つ目の壊れ方は、サービスの中では起きにくくなっています。ただし、解決はデプロイごとです。新しいデプロイを強制するとダイジェストが取り直される、とドキュメントにあります。古いリビジョンへのデプロイもデプロイなので、動いたタグはそこで引き直されると読めます。circuit breaker による自動のロールバックが、前に解決したダイジェストを使うのかどうかは、確認できていません。

ダイジェストは、プッシュしたあとでリポジトリに聞けば分かります。`aws ecr describe-images` の応答には `imageDigest` があり、プッシュが終わったときに ECR が EventBridge に送るイベントにも `image-digest` が入っています。CDK では、`ecs.ContainerImage.fromEcrRepository(repository, "sha256:...")` のように、2 つ目の引数に `sha256:` で始まる文字列を渡すと、`@` でつないだ形になります。固定している版の aws-cdk-lib（2.273.0）のコードで確かめました。

12章のスタックは、`-c imageTag` のほかに `-c imageDigest=sha256:...` も受け取ります。immutable なリポジトリで、イメージを消せる人が限られていれば、タグでも同じイメージに決まります。それでもダイジェストを勧めるのは、設定に頼らずに済むからです。リポジトリの設定は、あとから誰かが変えられます。

## この章が要らない場合

12章のように、ひとりが手でイメージをプッシュしていて、タグが immutable で、古いイメージを消す規則が 1 つあれば、ECR についてそれ以上決めることはほとんどありません。この章の設定が要るようになるのは、CI が毎日プッシュし、複数の人がデプロイし、どのイメージが本番で動いているのかを設定から言えなければ困るようになってからです。

CDK の `ecs.ContainerImage.fromAsset` でイメージを渡している場合は、リポジトリもタグも CDK と cdkd が決めます（12章）。自分でリポジトリを持たないので、この章の設定の多くは出番がありません。

Cloudflare の Containers では、イメージは Cloudflare が管理するレジストリ（`registry.cloudflare.com`）に置かれ、`wrangler deploy` がビルドとプッシュまで行います。Docker Hub や Amazon ECR のイメージを取得する設定もあります。ここまでは 2026-10-13 時点の Cloudflare のドキュメントで確かめたことです。レジストリの側にライフサイクルや検査にあたる設定があるかどうかは、調べていません。デプロイの道具がレジストリまで面倒を見るので、利用者が決めることは少なくなっています。
