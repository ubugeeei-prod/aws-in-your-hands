# 62 CI Runner: GitHub Actions と GitLab Runner を自分の AWS で動かす

[20章](/ja/chapters/20-shipping.md)のワークフローは、GitHub が用意したランナーで動き、OIDC で AWS に入りました。この章では、そのランナーを自分の AWS アカウントで動かします。考えることは 1 つに集約できます。ランナーは、ワークフローに書かれたものを何でも実行します。したがって、自分で持つランナーは、ジョブ 1 件のために作られ、何の権限も持たず、ジョブが終わると消える環境でなければなりません。この章の設計は、どの部分もこの条件から決まっています。

作るのは GitHub Actions 用の最小の構成です。ジョブがキューに入ったことを知らせる webhook を Lambda で受け、署名と中身を確かめ、Fargate のタスクを 1 つ起動します。タスクはジョブを 1 件だけ実行して終わります。GitLab で同じことをする方法と、GitHub や AWS が用意しているほかの方法は、それぞれのドキュメントをもとに[実装のつづき](/ja/chapters/62-ci-runners/more.md)で説明します。

このスタックに時間課金のリソースはありません。ジョブが 1 件も無い月にかかるのは、シークレット 2 つの USD 0.80 と、端数だけです。ジョブが動いているあいだは、タスク 1 つにつき 1 分およそ USD 0.0020 かかります（東京、2 vCPU、8 GB、arm64。内訳は[料金](/ja/chapters/62-ci-runners/wrap.md)にあります）。

この章の構成は、一度も実際には動かしていません。GitHub App は作っておらず、ランナーは登録しておらず、ジョブは 1 件も実行していません。手元で確かめたのは、テスト、型検査、synth までです。GitHub と GitLab について書いたことは、2026-10-13 にそれぞれの公式ドキュメントを読んだ内容です。確かめられなかった点は、[章末の検証メモ](/ja/chapters/62-ci-runners/wrap.md)にまとめてあります。

前提は [20章](/ja/chapters/20-shipping.md)の OIDC、[11章](/ja/chapters/11-network.md)の VPC、[12章](/ja/chapters/12-containers.md)と [41章](/ja/chapters/41-fargate.md)の Fargate、[21章](/ja/chapters/21-security.md)のシークレットです。コードは `examples/62-ci-runners/` にあります。

## 自分でランナーを持つ理由と、持たない理由

<!-- section: 62.when -->

GitHub が用意するランナーは、ジョブごとに新しい仮想マシンで動き、終わると捨てられます。利用者が運用するものは何もありません。それでも自分でランナーを持つ理由は、おおよそ次の 4 つです。

- **VPC の中に届く必要がある。** プライベートサブネットのデータベースにマイグレーションを流す、内部のエンドポイントに対してテストを実行する、といったジョブは、外のランナーからは届きません
- **大きさやアーキテクチャを選びたい。** GitHub の標準の Linux ランナーは、非公開リポジトリでは 2 コア、8 GB です。それより大きいランナーは有料のプランで選べますが、自分で持てば Fargate の表にある大きさを選べます
- **量が多い。** 1 分あたりの単価は、この章の構成のほうが GitHub の定価より低くなります。ただし、差が運用の手間に見合うのは、[料金](/ja/chapters/62-ci-runners/wrap.md)で計算するとおり、月に数万分を使うようになってからです
- **コードやデータを、決めた場所の外に出せない。** ビルドの途中の成果物や、テストに使うデータを、自分のアカウントの中に留めておけます

持たないほうがよい場合のほうが、多くあります。公開リポジトリでは、GitHub のドキュメントが、セルフホストランナーはほぼ使うべきでないと書いています。理由は次の節で説明します。月の利用がプランに含まれる分数（Free で 2,000 分、Team で 3,000 分）に収まっているなら、自分で持っても料金は下がりません。そして、VPC の中に届く必要があるだけなら、ジョブを丸ごと移す前に、届く必要のあるステップだけを別の仕組みに切り出せないかを考えてください。たとえば、マイグレーションを [16章](/ja/chapters/16-long-jobs.md)の単発のタスクにして、ワークフローからは起動するだけにする方法があります。

自分で持つと決めたあとも、コードを書かずに済む方法があります。AWS CodeBuild は、GitHub Actions と GitLab のランナーを、ジョブごとに使い捨てのビルド環境として動かす機能を持っています。この章がそれを使わずに自分で組み立てるのは、ランナーの登録、webhook、起動、片付けを順に見せるためです。実際に使うなら、[実装のつづき](/ja/chapters/62-ci-runners/more.md)の比較を読んでから選んでください。

## ランナーは、ワークフローに書かれたものを何でも実行する

<!-- section: 62.rule -->

ワークフローのファイルは、リポジトリに push できる人なら誰でも書き換えられます。プルリクエストを出せる人も、自分のブランチのワークフローを書き換えられます。ランナーは、そこに書かれたコマンドを、ランナーが置かれた場所の権限で実行します。ランナーが VPC の中にあれば VPC の中から、IAM ロールを持っていればそのロールで実行します。

GitHub の secure use reference は、この点を次のように書いています（2026-10-13 に確認）。セルフホストランナーは、使い捨てのきれいな仮想マシンで動く保証がなく、ワークフローの信頼できないコードによって、あとまで残る形で侵害されうる。公開リポジトリでは、誰でもプルリクエストを出して環境を侵害できるので、ほぼ使うべきでない。非公開リポジトリでも、フォークしてプルリクエストを出せる人は、同じことができる。GitLab のドキュメントも、ジョブをまたいで使い回されるランナーを複数のプロジェクトで共有すると危険が大きくなると書いています。

この章の不変条件は、次の 1 文です。**あるジョブが書き込んだものは、次のジョブから見えない。** ファイルだけでなく、プロセス、メモリ、ネットワークの設定、認証情報のキャッシュも含みます。

この条件を壊す設計は、よく見かけます。

- **常駐のランナー。** EC2 インスタンスにランナーを 1 つ入れて動かし続ける構成です。前のジョブが置いたファイルやプロセスが、次のジョブの環境にそのまま残ります
- **同じホストの上の、ジョブごとのコンテナ。** コンテナは分かれていても、Docker のソケットをジョブに渡していれば、ジョブはホストとほかのコンテナを操作できます。特権つきのコンテナも同じです
- **ジョブのあとに掃除をするスクリプト。** 掃除をするのは、侵害されたかもしれない環境そのものです

GitHub は、ジョブごとに自動でランナーを破棄する仕組みについても、ランナーが 1 件のジョブしか実行しない保証はないと注意しています。そのための仕組みが just-in-time runner（JIT ランナー）です。API で登録を先に作り、その設定を渡して起動したランナーは、ジョブを多くても 1 件実行したところで、GitHub の側から登録を消されます。ただし、同じドキュメントは、JIT ランナーを動かすハードウェアを使い回すと情報が漏れうるとも書いています。登録が 1 回きりであることと、環境が 1 回きりであることは別で、後者は自分で用意します。

この章では、環境を Fargate のタスクにします。ECS のドキュメントは、Fargate のタスクはそれぞれ独立した境界を持ち、カーネル、CPU、メモリ、ネットワークインターフェースをほかのタスクと共有しないと書いています。タスクが終われば、その環境は残りません。

不変条件のほかに、同じ前提から決まる規則が 5 つあります。この章のコードとテストは、それぞれに対応しています。

- **フォークからのジョブと、公開リポジトリのジョブには、ランナーを起動しない。** 許可するリポジトリは完全一致の一覧で持ち、ワイルドカードを受け付けません
- **ランナーのロールは、デプロイのロールではない。** タスクロールには権限を 1 つも付けません。AWS に入る必要のあるジョブは、20章と同じく OIDC でロールを引き受けます。ロールの信頼ポリシーがブランチや環境を見ているので、ワークフローを書き換えただけでは本番のロールを引き受けられません
- **長く使える登録用のシークレットを、ランナーの環境に置かない。** GitHub App の秘密鍵は受信の Lambda だけが読み、タスクには 1 回きりの JIT の設定だけを渡します
- **外へ出る通信を絞る。** セキュリティグループは、入る通信を 1 つも許さず、出る通信を HTTPS だけにします
- **イメージを古いままにしない。** ランナーのイメージはダイジェストで固定し、新しい版が出たら更新します。GitHub は、新しい版が出てから 30 日以内に更新することを求めています

登場するものは多くありません。受信の Lambda は function URL で公開し、GitHub からの配送を受けます。DynamoDB のテーブルは、どのジョブのランナーを起動したかを覚えておくためのもので、同じ配送が 2 回届いてもタスクが 1 つしか起動しないようにします。ECS のクラスターとタスク定義は、ランナーを動かす場所です。もう 1 つ、15 分ごとに動く見回りの Lambda が、決めた時間より長く動いているタスクを止めます。

大きさは、GitHub の標準の Linux ランナー（非公開リポジトリで 2 コア、8 GB）に合わせてあります。イメージは、GitHub が Actions Runner Controller 用に公開しているランナーのイメージです。2026-10-13 に ghcr.io からマニフェストを読み、タグ `2.338.0` が linux/arm64 を含むことと、そのダイジェストを確かめました。このイメージの Dockerfile が入れているのは、ランナー本体のほかには、git、curl、jq、unzip、sudo、Docker の CLI くらいです。AWS CLI は入っていません。ジョブが使う道具は、ワークフローの中で入れるか、イメージを自分で作って足します。ランナーのユーザーはパスワードなしで sudo を使えるので、ジョブはタスクの中では root と同じことができます。タスクの外に届かないことが、そのまま守りの範囲になります。

ネットワークは 11章の VPC を読み込み、タスクをパブリックサブネットに置いて、パブリック IPv4 アドレスを付けます。NAT Gateway の月額を避けるためです。VPC の中のリソースに届かせたい場合は、タスクのセキュリティグループを相手のセキュリティグループで許可します。プライベートサブネットに置く場合の出口の選び方は、11章と 41章にあります。
