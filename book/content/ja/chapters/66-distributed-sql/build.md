# 66 Distributed SQL: しくみと実装

[前のページ](/ja/chapters/66-distributed-sql.md)で、3 台のノードをどこに置くかを図で見ました。このページでは、YugabyteDB が書き込みをどう守っているかを先に見て、そのあとで、クラスターの定義、クライアント、証明書、スタック、ノードの中身の順に実装を追います。

## 書き込みが 3 か所に届くまで

<!-- section: 66.architecture -->

13章の Aurora DSQL では、データがどこに何個あるかは見えませんでした。YugabyteDB では、それが設定として目の前に出てきます。以下は、公式文書の architecture の節と、固定した版のバイナリが表示するフラグの説明から読んだ内容です。

ノードでは 2 つのプロセスが動きます。`yb-tserver` はデータを持ち、PostgreSQL 互換の接続を受けます。`yb-master` はカタログを持ちます。カタログは、テーブルの定義と、どの tablet がどのノードにあるかの対応表です。`yb-master` はデータの読み書きの経路には入りません。tablet の配置を決め、リーダーの偏りをならし、ノードが死んだら写しを作り直す指示を出します。

テーブルは tablet に分かれます。行は主キーで 1 つの tablet に決まり、ハッシュで分ける場合は 0x0000 から 0xFFFF の範囲を tablet が分け合います。tablet にはそれぞれ replication factor の数だけ写しがあり、この章では 3 です。3 つの写しは Raft のグループを作り、1 つがリーダーに、残りがフォロワーになります。`yb-master` のカタログにも同じ数の写しがあり、こちらも Raft で 1 つのリーダーを選びます。3 台すべてで `yb-master` を動かすのはこのためです。

```figure
type: sequence
caption: リーダーは、自分を含む過半数が書き込みを記録してから応答する。ノード c が止まっていても、2 台で過半数になる
actor client: Client
actor a: Node a | tablet leader
actor b: Node b | follower
actor c: Node c | follower
step client -> a: COMMIT
step a -> a: append to the log
step a -> b: replicate
step a -x c: replicate
step b --> a: persisted
note a: 2 of 3 hold it
step a --> client: acknowledged
```

文書によれば、書き込みは、Raft のログが過半数の写しに複製され、そこで永続化されてから適用されます。3 つのうち 2 つです。応答を受け取った書き込みは、少なくとも 2 台のディスクにあるので、どの 1 台を失っても、残る 2 台のどちらかが持っています。新しいリーダーは過半数の票で選ばれるので、その書き込みを持たない写しがリーダーになることもありません。これが、1 つ目の不変条件の中身です。

読み取りと書き込みを受けるのは、既定では tablet のリーダーだけです。SQL を受けたノードにその tablet のリーダーがいなければ、リーダーのいるノードへ内部で回されます。どのノードに接続しても同じ答えが返るのは、このためです。

過半数を失うと、その tablet は応答しなくなります。間違った答えを返すのではなく、答えません。3 台のうち 2 台を失うと、すべての tablet とカタログがこの状態になります。

ノードが 1 台止まったままのときの動きも、フラグに書いてあります。リーダーは 500 ミリ秒ごとにハートビートを送ります（`raft_heartbeat_interval_ms`）。フォロワーに 900 秒届かないと（`follower_unavailable_considered_failed_sec`）、その写しはグループから外され、`yb-master` が別のノードに写しを作り直します。ただし、3 台しかないクラスターには「別のノード」がありません。4 台目を足すまで、写しは 2 つのままです。

### トランザクションと分離レベル

YugabyteDB が用意している分離レベルは 3 つで、Snapshot、Serializable、Read Committed です。Snapshot は SQL の `REPEATABLE READ` にあたります。13章のランナーは `BEGIN ISOLATION LEVEL REPEATABLE READ` と名前で指定しているので、Aurora DSQL のときと同じレベルで動きます。

指定しなかったときの既定には、落とし穴があります。PostgreSQL と同じく既定は `READ COMMITTED` ですが、文書によれば、`yb-tserver` を自分で起動したクラスターでは `yb_enable_read_committed_isolation` が `false` のままで、`READ COMMITTED` はより厳しい Snapshot として扱われます。手元のクラスターでも、`SHOW transaction_isolation` は `read committed` と答え、`SHOW yb_effective_transaction_isolation_level` は `repeatable read` と答えました。名前から保証を推測せず、実際に効いているレベルを確かめてください。

競合の届き方は、Aurora DSQL と少し違います。13章では、競合は `COMMIT` のときに `40001` として届きました。手元の YugabyteDB では、同じ行を先に更新したトランザクションがコミットした時点で、待っていたほうの `UPDATE` の文が `40001` で失敗しました。

<<< @/examples/66-distributed-sql/test/repository.test.ts{fixtures}

13章のループは、エラーがどの文で起きたかを見ません。SQLSTATE が `40001` なら `ROLLBACK` して、`BEGIN` からやり直します。そのため、届き方の違いは問題になりません。テストでは、このエラーを `UPDATE` の文に差し込み、ループがやり直して、ノートが 1 件、件数が 1 のまま終わることを確かめています。

デッドロック（`40P01`）は別です。YugabyteDB の文書は `40001` と同じように再試行するよう勧めていますが、13章のループが再試行するのは `40001` だけです。この章の repository は、どの操作も `app.owners` の行、`app.notes` の行の順に触るので、デッドロックは起きない作りです。手元のクラスターでも起こしていません。行を逆の順で触るトランザクションを足すなら、再試行の条件に `40P01` を加えてください。テストは、いまのループが `40P01` を再試行せずに呼び出し元へ返すことを固定しています。

### 時計

YugabyteDB は、トランザクションの順序を時刻で決めます。使うのは hybrid logical clock で、物理的な時刻に論理的なカウンターを組み合わせ、ノードどうしが通信のたびに値を交換して進めます。それでも、物理的な時計のずれ（clock skew）には上限が要ります。文書によれば、ずれが `max_clock_skew_usec`（既定で 500 ミリ秒）を超えたことを検出すると、`yb-tserver` や `yb-master` は自分で止まります。

借りているデータベースでは、時計のことを考える必要がありませんでした。自分で動かすなら、時刻合わせは可用性の一部です。YugabyteDB は chrony を使うことと、クラウドではその事業者のリンクローカルの時刻サービスを使うことを勧めています。AWS では Amazon Time Sync Service がそれにあたります。Amazon Linux 2023 の既定の設定がこのサービスを向いているかどうかは、この章では確かめていません。`vp run distsql:status` は各ノードの `chronyc tracking` を表示するので、参照先とずれの大きさを、起動する前に確かめてください。

## クラスターを 1 つの定義から作る

<!-- section: 66.topology -->

`yb-master` と `yb-tserver` は、起動するときのフラグで自分の役割を知ります。フラグは 2 つのプロセスに 3 台分で、6 つのファイルになります。手で書くと、アドレスを 1 か所だけ直し忘れる、といった事故が起きます。そこで、クラスターを 1 つの型で定義し、6 つのファイルをそこから生成します。

<<< @/examples/66-distributed-sql/src/topology.ts{schema}

スキーマは、形のほかに 3 つのことを確かめます。ノードが 3 台であること。同じアドレスとポートを 2 つのリスナーが使っていないこと。`127.0.0.1` 以外で動かすなら、証明書のディレクトリが指定されていること。3 つ目は、TLS のないクラスターをうっかりネットワークに出さないための検査です。

<<< @/examples/66-distributed-sql/src/topology.ts{flags}

`--placement_zone` には、ノードごとに違うゾーンを入れます。YugabyteDB は、この値を見て、同じ tablet の写しを別々のゾーンに分けます。3 台が 3 つのゾーンにあれば、ゾーンを 1 つ失うことは、ノードを 1 台失うことと同じになります。11章のネットワークは既定で 2 つのゾーンですが、この章では 3 つで作り直します。2 つのゾーンに 3 台を置くと、2 台のあるゾーンを失ったときに過半数が残らないからです。

リスナーは、どれもノード自身のアドレスにだけ結び付けます。`0.0.0.0` は使いません。

同じ関数を、手元のクラスターと EC2 のクラスターの両方に使います。違うのはアドレスとポートだけです。

<<< @/examples/66-distributed-sql/src/topology.ts{local}

文書の例では、手元の 3 ノードに `127.0.0.1`、`127.0.0.2`、`127.0.0.3` を使います。macOS の loopback には `127.0.0.1` しかなく、足すには `sudo` が要るので、この章ではアドレスを 1 つにしてポートで分けました。

<<< @/examples/66-distributed-sql/src/topology.ts{ec2}

EC2 では、インスタンスができるまでアドレスが決まりません。そこでアドレスの位置にはシェルの変数名を入れておき、ノードの上のスクリプトが、ファイルを書くときに実際の値を埋めます。アドレスのスキーマが通すのは、IPv4 のアドレスと、大文字と下線だけの `${NAME}` の 2 つの形だけです。空白や引用符を含む値は、フラグファイルに届く前に落ちます。

## 13章のコードを、そのままつなぐ

<!-- section: 66.client -->

13章の repository が知っているのは、`Db` というインターフェースだけです。Aurora DSQL 用と PGlite 用の実装があり、この章では YugabyteDB 用を 1 つ足します。

<<< @/examples/66-distributed-sql/src/yugabyte-db.ts{open}

Aurora DSQL との違いは、接続先が 1 つのエンドポイントではなく、3 つのノードであることです。どのノードも同じ SQL を受けるので、1 台が落ちていたら次のノードに接続します。

<<< @/examples/66-distributed-sql/src/failover.ts{failover}

別のノードで試し直すのは、接続を開くところだけです。開けなかった接続は何もしていないので、別のノードで開き直しても害がありません。接続したあとのエラーは、ここでは再試行しません。`COMMIT` を送ったあとに接続が切れた場合、コミットされたかどうかはクライアントからはわからないからです。YugabyteDB の文書も、`COMMIT` をむやみに再試行しないよう書いています。

この「わからない」を引き受けているのは、13章の repository です。`create` は、最初に同じ ID のノートがあるかを読み、あれば何もせずに `created` を返します。応答が届かなかった作成は、同じ ID のまま、別のノードへもう一度送れます。この性質を使って、[手元の検証](/ja/chapters/66-distributed-sql/local.md)では、ノードを落とした直後の書き込みを、確認が返るまで同じ ID で送り直しています。

YugabyteDB は、node-postgres を元にした専用のドライバー（`@yugabytedb/pg`）も配布しています。クラスターのノードの一覧を自分で取りに行き、ゾーンを考えて接続を振り分けるものです。この章では使っていません。接続先の切り替えで何が起きるかを、コードとして見えるところに置きたかったからです。

## 過半数のモデル

<!-- section: 66.quorum-model -->

実際のクラスターでノードを落とす検証は、3 台を起動する必要があり、落とすタイミングも選べません。「どのフォロワーに届いた時点で、どのノードが落ちても」を全通り試すために、写しが 3 つのログの小さなモデルを書きました。

<<< @/examples/66-distributed-sql/src/model/quorum.ts{model}

これは **この章のモデル** で、YugabyteDB でも Raft の実装でもありません。ネットワークも時間もなく、選出はテストが呼んだときに起きます。持っている規則は 2 つだけです。書き込みは過半数が持ってから確認すること。新しいリーダーは、生きている写しのうち、最後の記録がいちばん新しい任期のもので、その中でいちばん長いログを持つものであること。

テストは、この 2 つの規則から不変条件が出てくることを確かめます。書き込みがどのフォロワーに届いていたか（4 通り）、どのノードを失うか（3 通り）、その後の書き込みがどこに届くか（4 通り）を総当たりにして、確認した書き込みがいつも新しいリーダーから見えることを見ます。2 台を失うとモデルは「答えない」状態になり、1 台を戻すと、確認済みの書き込みを持って戻ってきます。

同じモデルで、規則を 1 つ変えた場合も試しています。リーダーが自分のログに書いた時点で確認する、つまり非同期の複製です。この場合、書き込みは一度見えて、確認も返り、リーダーを失うと消えます。リードレプリカの遅れ（[59章](/ja/chapters/59-rds.md)）や、データベースを移すときの複製（[39章](/ja/chapters/39-database-migration.md)）で気にしなければならないのは、これです。過半数を待つことで払っている遅延は、この「見えたあとで消える」を無くすための代金です。

確認されなかった書き込みについては、モデルは何も約束しません。残ることも、消えることもあります。手元のクラスターでも、2 台を落としている間に送った 1 件は、ある回では戻したあとに入っていて、別の回では入っていませんでした。

## 証明書は、鍵を動かさずに配る

<!-- section: 66.tls -->

ノードどうしの通信と、クライアントからの接続は、どちらも TLS にします。フラグは 3 つで、`use_node_to_node_encryption`、`use_client_to_server_encryption`、そして TLS を話さない相手を受け入れない `allow_insecure_connections=false` です。

証明書の置き方は、YugabyteDB が決めています。`--certs_dir` のディレクトリに、認証局の証明書と、ノードのアドレスを名前に含む証明書と鍵を置きます。

<<< @/examples/66-distributed-sql/src/certs.ts{names}

認証局は、このクラスターのためだけに `openssl` で作ります。文書の手順は `openssl ca` を使い、ノードの鍵も手元で作ってノードへ運ぶ形です。この章は、その手順を 2 点変えています。

<<< @/examples/66-distributed-sql/src/certs.ts{openssl}

1 つ目に、ノードの秘密鍵は、そのノードの上で作り、外へ出しません。ノードが出すのは署名のリクエスト（CSR）だけで、運用者の手元にある認証局がそれに署名し、証明書を返します。Run Command で運ぶのは CSR と証明書で、どちらも秘密ではありません。Run Command の引数と出力は記録に残るので、秘密鍵を通してはいけません。

<<< @/examples/66-distributed-sql/scripts/nodes.ts{certs}

2 つ目に、ノードの証明書の期限は 397 日にしました。文書の例は 3,650 日です。10 年有効な証明書は、入れ替えの手順を一度も試さないまま持ち続けることになります。

入れ替えの手順は、手動のデプロイ向けの文書には見つけられませんでした。同じ認証局で署名し直した証明書を置いて、1 台ずつ再起動すれば済むはずですが、これは推測で、確かめていません。認証局そのものの入れ替えは、さらに手順が要ります。認証局の秘密鍵は運用者のマシン（`.yugabyte/ca-aws/`、git には入りません）に残るので、本番ではその置き場所も決めてください。

もう 1 つ、手元で気づいたことがあります。TLS を有効にしても、`yb-master` と `yb-tserver` の管理用の Web インターフェース（7000、9000、13000）は、平文の HTTP のまま応答しました。ログインもありません。この章のセキュリティグループは、この 3 つのポートにルールを 1 つも置いていません。見たいときは、Session Manager のポートフォワードで入ります。

## スタック

<!-- section: 66.stack -->

スタックの設定は、CDK のコンテキストで渡します。

<<< @/examples/66-distributed-sql/src/config.ts{schema}

ノードの数は 0 か 3 だけです。2 台は 1 台も失えず、4 台は 3 台より多くを失えないので、選べるようにしていません。インスタンスタイプの既定は `t4g.medium`（2 vCPU、4 GiB）です。YugabyteDB の文書が挙げる最小（2 コア、2 GB）は満たしますが、文書が AWS で勧めているのは M ファミリーで、T2 は避けるよう書いています。T4g について書かれてはいませんが、同じバースト型です。練習のための選択で、本番の選択ではありません。

<<< @/examples/66-distributed-sql/infra/lib/distsql-stack.ts{network}

セキュリティグループは 2 つあります。ノードのグループは、複製のポート（7100、9100）を自分自身のメンバーからだけ受け、SQL のポート（5433）をクライアントのグループからだけ受けます。相手を VPC の CIDR ではなくグループで指定しているので、同じ VPC にいるだけの別のインスタンスからは届きません。

<<< @/examples/66-distributed-sql/infra/lib/distsql-stack.ts{nodes}

ノードは、ネットワークのプライベートサブネットに、ゾーンの順に 1 台ずつ置きます。データは、インスタンスとは別の暗号化した EBS ボリュームに置きます。ボリュームは既定でスタックを消しても残ります（`stateOnDestroy=retain`）。3 つのボリュームがデータベースそのものだからです。

<<< @/examples/66-distributed-sql/infra/lib/distsql-stack.ts{role}

ノードのロールが S3 でできることは 3 つです。`artifacts/` の下のアーカイブを読むこと、`backups/` の下に書いて読むこと、`backups/` の下を一覧することです。削除の権限はありません。ノードを乗っ取られても、取ってあるバックアップは消せません。ただし `s3:PutObject` は同じキーへの上書きを許すので、本番ではバケットのバージョニング（[22章](/ja/chapters/22-recovery.md)）を有効にしてください。

このスタックが使うリソースの種類と property は、24章のスタックと同じ範囲に収めてあります。固定した版の cdkd（0.296.28）がそれぞれをどう扱うかは、24章の検証メモに記録があり、この章のテストは、その範囲から出ていないことを固定しています。ルートボリュームの大きさを変える `BlockDeviceMappings` を使っていないのも、そのためです。

## ノードの中身

<!-- section: 66.node-files -->

インスタンスが最初に起動したときに実行されるユーザーデータは、データベースを入れません。ユーザーと、カーネルの設定と、systemd のユニットと、あとで使うスクリプトを置き、データボリュームをマウントするところまでです。

<<< @/examples/66-distributed-sql/src/machine.ts{user-data}

データベースの導入を分けているのは、ユーザーデータにバケットの名前やアドレスを埋め込まないためです。3 台のユーザーデータは 1 バイトも違いません。

<<< @/examples/66-distributed-sql/src/machine.ts{unit}

ユニットは、データボリュームがマウントされていなければ起動しません。マウントされていないまま起動すると、データベースはルートボリュームの上で空の状態から始まり、ほかの 2 台からは「データを失ったノード」に見えます。プロセスが落ちたら systemd が起こし直します。文書は cron で起こし直すよう書いていますが、やっていることは同じです。開けるファイルの数とプロセスの数の上限は、文書の値を systemd の書き方で入れています。

<<< @/examples/66-distributed-sql/src/machine.ts{install}

導入のスクリプトが外から受け取るのは、バケットの名前と、版と、その SHA-256 で、それぞれを形で検査します。版とダイジェストは、呼び出す側がリポジトリから渡すので、バケットの中身は信用しません。アーカイブは、展開する前に照合します。プライベートサブネットにはインターネットへの経路がないので、アーカイブは運用者がバケットに置き、ノードは S3 のゲートウェイエンドポイント経由で取ります。

<<< @/examples/66-distributed-sql/src/machine.ts{configure}

設定のスクリプトは、3 台のアドレスを受け取り、前の節の関数が作ったフラグファイルの変数を埋めます。自分のゾーンは、インスタンスメタデータから読みます。

生成されるファイルは、`examples/66-distributed-sql/deploy/` にそのまま置いてあります。`vp run distsql:render` は、置いてあるファイルが生成結果と違えば失敗します。
