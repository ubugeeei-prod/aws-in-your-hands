# 00 Introduction: 何を作り、どう読むか

この章では、まだ手を動かしません。この本で何を作るのか、どの順で読めばよいのか、各章がどんな決まりに沿って書かれているのかを、先に説明します。

## 何を作るか

<!-- section: 00.build -->

題材は、画像を添付できる小さなノートアプリです。静的な SPA を公開するところから始めて、章ごとに機能を 1 つずつ足していきます。次の 2 つの図は、どの章で何が加わるかを示しています。

```figure
caption: 矢印の数字は、その部分をノートアプリに足す章の番号です。
node browser: Browser
node api: API Gateway HTTP API
node cf: CloudFront
node cognito: Cognito
node lambda: Lambda
node s3: S3 | SPA
node ddb: DynamoDB
edge browser -> cf: 03
edge cf -> s3: 03
edge browser -> api: 04
edge api -> lambda: 04
edge lambda -> ddb: 05
edge browser -> cognito: 06 ログイン
group app: 06 API が誰のノートか確かめる = api, lambda
```

```figure
caption: 07章でブラウザが S3 に画像をアップロードし、08章で S3 のイベントから Lambda が画像を確かめます。
direction: right
node browser: Browser
node s3: S3
node sqs: SQS
node lambda: Lambda | 画像の確認
edge browser -> s3: 07 署名付きアップロード
edge s3 -> sqs: 08 S3 イベント
edge sqs -> lambda: 08
```

00章から 24章まで、すべての章を書き終えています。

ただし、すべての機能を 1 つの大きなサンプルに積み上げてはいません。章ごとに `examples/<章番号>-<名前>/` があり、その章の説明に必要なものだけを入れてあります。メール（[15章](/ja/chapters/15-email.md)）、AI（[17章](/ja/chapters/17-ai.md)）、ライブ配信（[18章](/ja/chapters/18-live.md)）、celld（[24章](/ja/chapters/24-celld.md)）の 4 つは、ノートアプリとは切り離して取り組める章です。

## 読む順番

<!-- section: 00.paths -->

サイドバーでは 25 章を、準備する（00〜02）、アプリを作る（03〜08）、動かす場所を選ぶ（09〜12）、データを置く（13〜14）、機能を足す（15〜18）、運用する（19〜22）、サーバーを持つ（23〜24）の 7 つに分けて並べています。

いちばん短い経路は、00章から 08章までを順に読み、19章でログとメトリクスを足すものです。ただ、作りたいものによっては、次の表にある別の経路のほうが合います。

| 経路 | 章 | 向いている人 |
| --- | --- | --- |
| 最短 | 00 → 01 → 02 → 03 → 04 → 05 → 06 → 07 → 08 → 19 | ノートアプリを一通り作りたい |
| SQL | 00 → 01 → 02 → 04 → 13 → 22 | データがリレーショナルで、SQL で書きたい |
| SSR | 00 → 01 → 02 → 03 → 04 → 09 → 10 | Nuxt などでサーバーサイドレンダリング（SSR）をしたい |
| コンテナ | 00 → 01 → 02 → 11 → 12 → 16 | 既存のコンテナを動かしたい |

01章と 02章は、どの経路でも通ります。01章でアカウントを安全に使える状態にし、02章でこの本のすべてのコマンドが動く環境を作るからです。

SQL で書きたいデータを、05章の DynamoDB に無理に載せる必要はありません。04章を終えたら、そのまま 13章へ進めます。ただし、13章で RDS や Aurora Serverless v2 も試すなら、先に 11章のネットワークが要ります。

Cloudflare の D1、Workers、Workers AI に慣れている人に向けた経路は、[Cloudflare から来た人へ](/ja/guides/cloudflare.md)にまとめました。

## この本の決まりごと

<!-- section: 00.conventions -->

手を動かす章には、おおむね次の項目があります。当てはまらない項目は、その章では省いています。

1. その章でできるようになることと、前提
2. 何がどこで動くかを示す小さな構成図
3. この構成を選ぶ理由と、別の選択肢にする条件
4. 説明に対応する完全なソース
5. ローカルでの起動、型検査、テストと、ローカルでは再現しないもの
6. 差分の確認、デプロイ、動作確認、ドリフト検出の手順
7. 使っていないとき、使ったとき、消した後の料金
8. 失敗例と調べ方
9. 本番に進めるなら変えること
10. 後片付けと、残るもの
11. 型で守ること、実行時に検証すること、テストする不変条件（invariant）

このほかに、本全体で守っている決まりが 5 つあります。

1 つ目は、コマンドを `vp run <タスク名>` で実行することです。タスクはリポジトリのルートにある `vite.config.ts` に定義してあり、ルートで実行します。`vp` は Vite+ というツールチェーンの CLI で、02章で導入します。

2 つ目は、AWS に触るタスクにはそう書くことです。タスクは、このリポジトリの中だけで完結するものと、AWS を読むか変えるものに分かれています。AWS に触るタスクは、実行する前に対象のアカウントとリージョンを表示します。

3 つ目は、検証の状態を次の 3 つに分けることです。

- 未検証: 書いたけれど、実行していない
- ローカル検証済み: 手元のマシンで実行して、通った
- AWS 検証済み: 実際の AWS アカウントで実行して、通った

ローカルで通ったことは、AWS 上で動くことの証拠にはなりません。IAM の権限、CDN の挙動、同時実行のときの振る舞いは、手元では確かめられないからです。執筆の進み具合（planned、complete）も、検証の状態とは別に記録しています。

4 つ目は、料金に前提を付けることです。金額には、リージョン、単価の出典、確認日、使用量の仮定を添えます。計算は[料金の計算](/ja/reference/pricing.md)のページにあり、入力を変えて計算し直せます。確認できなかった料金は「不明」と書き、0 や推測の数値で埋めません。

5 つ目は、所要時間を書かないことです。計測していない時間を、目安として出すことはしません。

## 使う道具

<!-- section: 00.stack -->

| 用途 | 使うもの |
| --- | --- |
| 開発環境 | Nix（flake と devShell） |
| 依存の導入とタスク実行 | Vite+（`vp`）と pnpm |
| インフラの定義 | TypeScript と AWS CDK v2 |
| インフラの作成と更新 | cdkd |
| アプリから AWS を呼ぶ | AWS SDK for JavaScript v3 |
| フロントエンドの例 | Vue と Vite。`.vue` のコンパイル、型検査、lint は Vize |
| この本のサイト | Ox Content、S3、CloudFront |

リージョンは東京（`ap-northeast-1`）、料金は USD、1 か月は 730 時間として計算します。

AWS Amplify は使いません。CDK と SDK を直接使うほうが、何がどこに作られるのかを追いやすいからです。

cdkd については、ここで 1 つ断っておきます。cdkd は CDK のコードを CloudFormation を通さずに AWS へ反映するツールで、公式ドキュメントは開発・テスト用途向けと説明し、本番には AWS CDK CLI を勧めています。それでもこの本が cdkd を使うのは、学習中に変更と確認を短い間隔で繰り返すのに向いているからです。本番向けの標準の経路は [20章](/ja/chapters/20-shipping.md)で、cdkd の詳しい説明は 02章で扱います。
