# 00 ようこそ: 何を作り、どう読むか

ようこそ。この章では、まだ手を動かしません。

何を作る本なのか、どの順で読めばいいのか、各章にどんな決まりごとがあるのか。先にそこだけ見ておきましょう。

## 何を作るの？

<!-- section: 00.build -->

題材は、画像を添付できる小さなノートアプリです。最初は静的な SPA を公開するだけ。そこへ機能を 1 つずつ足していきます。

```text
03  Browser -> CloudFront -> S3 (SPA)
04  Browser -> API Gateway HTTP API -> Lambda
05                                      Lambda -> DynamoDB
06  Browser -> Cognito (login)          API checks whose note it is
07  Browser -> S3 (presigned upload)
08  S3 event -> SQS -> Lambda (image check)
```

00章から 24章まで、すべての章を書き終えています。

全部の機能を 1 つの巨大なサンプルに積み上げる、ということはしません。章ごとに `examples/<章番号>-<名前>/` があって、その章の説明に必要なものだけが入っています。メール（[15章](/ja/chapters/15-email.md)）、AI（[17章](/ja/chapters/17-ai.md)）、ライブ配信（[18章](/ja/chapters/18-live.md)）、celld（[24章](/ja/chapters/24-celld.md)）は、ノートアプリとは独立に取り組めるレシピになっています。

## どの順で読む？

<!-- section: 00.paths -->

いちばん短い道は、00 から 08 までを順に読んで、19章でログとメトリクスを足すものです。とはいえ、みんながその道を通る必要はありません。

| 経路 | 章 | 向いている人 |
| --- | --- | --- |
| 最短 | 00 → 01 → 02 → 03 → 04 → 05 → 06 → 07 → 08 → 19 | ノートアプリを一通り作りたい |
| SQL | 00 → 01 → 02 → 04 → 13 → 22 | データが relational で、SQL で書きたい |
| SSR | 00 → 01 → 02 → 03 → 04 → 09 → 10 | Nuxt などで server rendering したい |
| コンテナ | 00 → 01 → 02 → 11 → 12 → 16 | 既存のコンテナを動かしたい |

01章と 02章は、どの経路でも通ります。01章でアカウントを安全に使える状態にして、02章でこの本のすべてのコマンドが動く環境を作るからです。

SQL で書きたいデータを、05章の DynamoDB に無理に載せなくて大丈夫です。04章を終えたら 13章へ進めます。13章で RDS や Aurora Serverless v2 も試すなら、先に 11章のネットワークが要ります。

Cloudflare の D1、Workers、Workers AI に慣れている人向けの経路は、[Cloudflare から来た人へ](/ja/guides/cloudflare.md)にまとめました。

## この本の決まりごと

<!-- section: 00.conventions -->

手を動かす章には、だいたい次のことが書いてあります。短い章では、当てはまらない項目は省きます。

1. その章でできるようになることと、前提
2. 何がどこで動くかを示す小さな構成図
3. この構成を選ぶ理由と、別の選択肢にする条件
4. 説明に対応する完全なソース
5. ローカルでの起動、型検査、テスト。そしてローカルでは再現しないもの
6. 差分確認、デプロイ、動作確認、drift 検出の手順
7. 料金。使っていないとき、使ったとき、消した後
8. 失敗例と調べ方
9. 本番に進めるなら変えること
10. 後片付けと、残るもの
11. 型で守ること、実行時に検証すること、テストする invariant

それから、本全体で守っている決まりが 5 つあります。

**コマンドは `vp run <タスク名>` で実行します。** タスクはリポジトリのルートの `vite.config.ts` に定義してあって、ルートで実行します。`vp` は Vite+ という toolchain の CLI で、02章で入れます。

**AWS に触るタスクは、そう書きます。** タスクは「このリポジトリの中だけで完結するもの」と「AWS を読む、または変えるもの」に分かれています。後者は、実行する前に対象のアカウントとリージョンを表示します。

**検証の状態は 3 つに分けます。**

- 未検証: 書いたけれど、実行していない
- ローカル検証済み: 手元のマシンで実行して、通った
- AWS 検証済み: 実際の AWS アカウントで実行して、通った

ローカルで通ったことは、AWS 上で動くことの証拠にはなりません。IAM の権限、CDN の挙動、同時実行のときの振る舞いは、手元では確かめられないんです。執筆の進み具合（planned、complete）と検証の状態も、別のものとして記録しています。

**料金には前提を付けます。** 金額には、リージョン、単価の出典、確認日、使用量の仮定を添えます。計算は[料金の計算](/ja/reference/pricing.md)のページにあって、入力を変えて計算し直せます。確認できなかった料金は「不明」と書いて、0 や推測の数値で埋めません。

**所要時間は書きません。** 計測していない時間を、目安として出すことはしません。

## 使う道具

<!-- section: 00.stack -->

| 用途 | 使うもの |
| --- | --- |
| 開発環境 | Nix（flake と devShell） |
| 依存の導入とタスク実行 | Vite+（`vp`）と pnpm |
| インフラの定義 | TypeScript と AWS CDK v2 |
| インフラの作成と更新 | cdkd |
| アプリから AWS を呼ぶ | AWS SDK for JavaScript v3 |
| フロントエンドの例 | Vue と Vite。`.vue` のコンパイル、型検査、lint は Vize |
| この本のサイト | Ox Content、S3、CloudFront |

リージョンは東京（`ap-northeast-1`）、料金は USD、1 か月は 730 時間として計算します。

AWS Amplify は使いません。CDK と SDK を直接使うほうが、何がどこに作られるのかを追いやすいからです。

cdkd については、先に 1 つだけ断っておきますね。cdkd は、CDK のコードを CloudFormation を通さずに AWS へ反映するツールです。公式ドキュメントは開発・テスト用途向けと説明していて、本番には AWS CDK CLI を勧めています。それでもこの本が cdkd を使うのは、学習中の短い反復に向いているから。本番向けの標準の経路は [20章](/ja/chapters/20-shipping.md)で扱います。詳しい話は 02章でします。
