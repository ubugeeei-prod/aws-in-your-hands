# 25 Events: EventBridge、SNS、Pipes、archive と replay

[08章](/ja/chapters/08-async.md)では、画像の検査という 1 種類の仕事を、1 本のキューで 1 つのワーカーに渡しました。送る側（S3）は、受け取る相手を 1 つだけ知っていました。

この章で扱うのは、同じ出来事を複数の相手が知りたがる場合です。ノートが作られた、書き換えられた、消された、添付が検査に落ちた。そのたびに、ノートごとの最新の状態を記録したい処理、利用者ごとの件数を数えたい処理、検査に落ちたことを知らせたい処理が、それぞれ動きます。

API がその 3 つを順に呼べば動きますが、知りたい相手が増えるたびに API を書き換えることになり、相手の 1 つが落ちているときに API がどう振る舞うかも決めなければなりません。この章では、出来事を「イベント」として 1 か所に流し、知りたい側がそこから受け取る形にします。API も 08章のワーカーも、1 行も変えません。

かわりに増えるのは部品です。イベントバスが 1 つ、ルールが 3 つ、関数が 3 つ、キューが 3 つ、トピックが 1 つ、テーブルが 1 つ、それに pipe と archive が加わります。何を得るために何を引き受けるのかを、最後まで並べて書きます。

前提は 08章です。コードは `examples/25-events/` にあります。時間で課金されるリソースはありませんが、pipe が stream を読みにいくぶんの料金が、使っていない月にもかかる見込みです。金額と仮定は[費用のページ](/ja/chapters/25-events/wrap.md)に書きました。

1 つ目の図が、イベントの作られ方です。05章から使っているノートのテーブルで stream を有効にすると、アイテムが書かれるたびに、変更の前と後の中身が stream に並びます。EventBridge Pipes がそれを読み、ノートと検査の記録だけを通し、関数（Shape）にイベントの形へ直させて、バスに載せます。

2 つ目の図が、イベントの配られ方です。バスには 3 つのルールがあり、それぞれが「自分はどのイベントが欲しいか」をイベントパターンで書いています。バスは、届いたイベントをすべてのルールと照合し、一致したルールのターゲットに渡します。イベントを載せる側は、ルールがいくつあるかを知りません。

図には描いていませんが、届けられなかったイベントは、どのルールからも `EventDeadLetters` という 1 つのキューによけられます。

コンシューマーは、わざと 3 通りの受け取り方にしました。Timeline はルールから直接呼ばれる関数です。Counter は 08章と同じく、キューを挟んで呼ばれます。検査に落ちた知らせは SNS のトピックに送り、そこから先の受け取り手はトピックに任せます。どれを選ぶと失敗の扱いがどう変わるかは、[しくみと実装のページ](/ja/chapters/25-events/build.md)で比べます。

### 書き込む側を変えない理由

API がノートを書いた直後に、同じ関数の中からバスにイベントを送る作りも考えられます。この章でそうしなかったのは、書き込みが 2 つになるからです。

テーブルへの書き込みとバスへの送信は、別々のリクエストです。1 つ目が成功して 2 つ目の前に関数が落ちれば、ノートはあるのにイベントは無いことになります。順序を逆にすれば、イベントはあるのにノートが無いことになります。どちらも、あとから気づく手段がありません。

stream は、テーブルへの書き込みそのものから作られます。DynamoDB のドキュメントによると、stream のレコードは変更 1 つにつきちょうど 1 回現れ、同じアイテムの変更は起きた順に並びます。書き込みが成功したのにレコードが無い、という状態は起きません。

引き換えにするものもあります。イベントは保存された中身から作るので、「なぜ変えたか」のような、テーブルに書かれていない事情は運べません。stream がレコードを持っているのは 24 時間で、pipe がそれより長く止まると、その間の変更はイベントになりません。そして、書き込みからイベントが届くまでには遅れがあります。どのくらい遅れるかは、この章では計測していません。

### 08章のスタックに足す

スタック（`AihEvents`）は、08章の `AsyncStack` を継承して、増えるものだけを書いています。08章が固定していた 3 つの名前（バケット、スケジュール、サインインのドメイン）を付け替えてあるので、`AihAsync` と同時にデプロイできます。そのかわり、バケットもテーブルも利用者も別々になります。

## キュー、トピック、バスの使い分け

<!-- section: 25.choices -->

メッセージを運ぶ部品が、この章で 4 種類になります。それぞれの持ち場を先に整理します。

キュー（SQS）は、1 種類の仕事を 1 種類のワーカーに渡す部品です。メッセージは受け取り手が取りにいくまで待っていて、取り出されたら他の受け取り手には渡りません。08章の構成がこれです。

トピック（SNS）は、1 つのメッセージをすべての購読者（subscription）に届けます。届け先には、キューや関数のほかに、メール、SMS、HTTP のエンドポイントがあります。購読者は、filter policy を付ければ一部だけを受け取れますが、付けなければすべてを受け取ります。

イベントバス（EventBridge）は、中身を見て行き先を決めます。行き先を決めるのは載せる側でも受け取る側でもなく、バスに付けたルールです。ルールごとに、再試行の方針、届けられなかったときの退避先、渡す前の形の変換を決められます。届いたイベントを保存しておいて、あとで流し直すこともできます。

Pipes は、1 つの入口から 1 つの出口へ運ぶ部品です。配るための部品ではなく、stream やキューの中身をバスに載せるところまでを受け持ちます。

| | SNS のトピック（standard） | EventBridge のバス（Classic） |
| --- | --- | --- |
| 誰が行き先を決めるか | 購読する側。トピックごと | バスの持ち主が書くルール。イベントの中身ごと |
| 絞り込み | 購読ごとの filter policy | ルールのイベントパターン |
| 届け先の数 | 1 トピックに 12,500,000 件の購読 | 1 ルールに 5 つのターゲット、1 バスに 300 のルール |
| 人に届ける | メール、SMS、モバイルの push | できない。SNS を挟む |
| 保存して流し直す | FIFO のトピックだけ | archive とリプレイ |
| 重複 | まれに重複して届く | まれに同じルールが 2 回動く |

数字は、2026-10-13 に公式ドキュメントで読んだものです。クォータは変わるので、使う前に [EventBridge のクォータ](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-quota.html)と [SNS のクォータ](https://docs.aws.amazon.com/general/latest/gr/sns.html)を見てください。

この章は両方を使います。どのイベントをどのコンシューマーに渡すかはバスのルールで決め、検査に落ちた知らせだけは、ルールの先に SNS のトピックを置きました。知らせを受け取りたい相手は増えたり減ったりしますし、メールのように EventBridge が直接は届けられない相手も入るからです。

### 新しい Custom Event Bus を使わなかった理由

2026-10-13 の時点で、EventBridge のドキュメントはバスを 2 種類に分けて説明しています。ルールとターゲットで配る従来のものが「Custom Event Bus - Classic」、購読する側が自分で subscriber を作る新しいものが「Custom Event Bus」で、新しいアプリケーションには後者から始めるよう書かれています。新しいバスは、イベントを 1〜365 日保持し、event group の中での順序を保って届け、載せるときに 5 分の幅で重複を取り除きます。

この章は Classic を使いました。理由は道具の側にあります。新しいバスのリソースは `AWS::EventsV2` という別の種類で、この本が固定している cdkd 0.296.28 には実装がありません。実装のない種類を cdkd は Cloud Control API 経由で作りますが、同じ日に読んだ Cloud Control API の対応一覧にも `AWS::EventsV2` はありませんでした。Pipes のターゲットに新しいバスを指定できるかも、ドキュメントからは読み取れませんでした。

この章の中身の大半は、どちらのバスでも変わりません。移行ガイドによると、ルールとターゲットの組が subscriber になり、イベントパターンは、ワイルドカードを除いてそのまま filter になり、archive とリプレイは、バスの保持期間と subscriber の開始位置になります。重複を取り除く幅は 5 分なので、保持してあるイベントを流し直せば、コンシューマーには同じイベントがもう一度届きます。コンシューマーを冪等に作る必要は残る、とこの章は考えていますが、新しいバスでは動かしていません。

### この構成にしないとき

受け取る相手が 1 つなら、08章のキューで足ります。バスとルールは、相手が 2 つ目、3 つ目と増えていくときに元が取れる部品です。

受け取る側が同じコードベースにあって、同じときに一緒に落ちてよいなら、関数を呼ぶだけで済みます。イベントにする意味があるのは、受け取る側が別の速さで動き、別のときに落ち、別の人が直すからです。

順序が正しさに関わる処理にも向きません。Classic のバスは順序を保って届けません。この章のコンシューマーは、順序が入れ替わっても同じ結果になるように作ってありますが、そう作れない処理は、stream を順に読むコンシューマーを直接つなぐか、FIFO のキューを使います。

Cloudflare と Vercel にも、近い部品があります。何があり、何が違うかは、[費用のページ](/ja/chapters/25-events/wrap.md)にまとめました。
