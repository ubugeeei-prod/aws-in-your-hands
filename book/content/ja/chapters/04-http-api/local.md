Lambda で動かすのと同じアプリを、ふつうの Node.js の HTTP サーバーにのせています。起動が軽く、料金もかかりません。ただし Lambda そのものではないので、次のものは再現しません。

- API Gateway のルート。本番では、定義していない path へのリクエストは Lambda に届く前に API Gateway が 404 を返します
- Lambda の制限。10 秒を超えた処理は打ち切られ、メモリにも上限があります
- IAM。許可していない AWS の操作は拒否されます
- API Gateway の CORS。本番では、preflight のリクエストは Lambda に届く前に API Gateway が答えます
- 実行環境の入れ替わり。メモリの中身が、次の呼び出しまで残っているとは限りません

最後の項目は、このページの「ノートの置き場所」で詳しく扱います。

### 本番にもう少し近づける

cdkd には、API Gateway と Lambda をローカルのコンテナで動かす機能があります。

```bash
vp run dev:api:cdkd
```

このタスクには、Docker の daemon が動いている必要があります。devShell に Docker は含まれていないので、Docker Desktop などを別に起動しておいてください。

注意が 1 つあります。cdkd のソースとドキュメントを読むかぎり、この機能はハンドラーを動かすコンテナに、既定で**あなた自身の認証情報**を渡します。ハンドラーが AWS SDK を呼ぶと、ローカルで動いていても本物の AWS に届き、料金もかかります。しかも実行ロールではなくあなたの権限で動くので、ここで動いたからといって、デプロイ後も権限が足りるとは言えません。この章のハンドラーは AWS を呼ばないので影響はありませんが、05章からは気をつけてください。

このタスクは、まだ実際には動かしていません。

## テスト

<!-- section: 04.tests -->

```bash
vp run test:unit
```

テストは 3 か所にあり、それぞれ確かめているものが違います。

| どこ | ファイル | 確かめているもの | 確かめていないもの |
| --- | --- | --- | --- |
| アプリ | `test/app.test.ts` | 入力の検証、エラーの形、request ID、CORS | Lambda と API Gateway を通したときの動き |
| クライアント | `test/client.test.ts` | クライアントとサーバーの契約。契約を破るレスポンスの扱い | 本物のネットワーク |
| インフラ | `infra/test/http-api-stack.test.ts` | 権限、ログの保持、タイムアウト、ルート | AWS がテンプレートどおりに動くこと |

アプリのテストはポートを開かず、Hono のアプリに `Request` を直接渡します。

クライアントのテストでは、モックを手で書いていません。本物のアプリを、クライアントの通信手段としてそのまま渡しています。サーバーの実装を変えて契約が崩れると、このテストが落ちます。

`hc<App>` によって、サーバーのルートとレスポンスの型が、コンパイル時にクライアントへ伝わります。path を打ち間違えると型エラーになります。

ただし、この型が表しているのは**このリポジトリにあるコード**です。実際に答えるサーバーが同じ版だとは限りません。古いデプロイが答えることも、途中のプロキシがエラーページを返すこともあります。そのためクライアントは、受け取ったレスポンスをスキーマと照合してから返します。状態コードは 200 なのに形が違う場合と、502 で HTML が返ってきた場合も、テストに入れてあります。

## ノートの置き場所

<!-- section: 04.state -->

Lambda は、関数を実行環境（execution environment）の中で動かします。実行環境はほかから隔離されていて、最初の呼び出しのときに作られ、初期化されます。最初の呼び出しで起きるこの作成と初期化が、コールドスタート（cold start）です。そのあとしばらくは、同じ実行環境が使い回されます。

<<< @/examples/04-http-api/src/lambda.ts{handler}

`composeApp` の呼び出しは、ファイルのいちばん外側にあります。ここが動くのはリクエストごとではなく、実行環境ごとに 1 回です。ノートを入れる `Map` も、そのときに 1 つ作られます。

次の図は、実行環境が 2 つになったときの動きです。

```figure
type: sequence
caption: 実行環境はそれぞれ自分の Map を持つので、同じ GET /notes でも t2 と t3 で答えが違います。
actor client: Client
actor a: 実行環境 A
actor b: 実行環境 B
step client -> a: t1 POST /notes
note a: 作られる。Map = {n1}
step client -> a: t2 GET /notes
step a --> client: 使い回し。[n1] を返す
step client -> b: t3 GET /notes
note a: 別のリクエストを処理中
note b: 作られる。Map = {}
step b --> client: [] を返す
note a: t4 しばらく使われない
note a: 破棄。n1 は消える
```

t3 では、実行環境 A が別のリクエストを処理している最中に次のリクエストが来たので、Lambda が 2 つ目の実行環境 B を作っています。B の `Map` は空なので、t2 と同じ URL を呼んだのに、返る内容が違います。t4 では、しばらく使われなかった A が破棄され、`n1` はどこにも残りません。

Lambda のメモリに置いたものは、キャッシュとしては使えても、**データの持ち主にはなれません**。実行環境は 1 つとは限らず、いつ消えるかも選べないからです。05章で DynamoDB を足すと、データの持ち主がテーブルになり、どの実行環境から読んでも同じ内容が返ります。

この動きは、デプロイした API で観察できます。

```bash
vp run api:smoke
```

`api:smoke` は、ノートを 1 件作ってすぐに読み戻すタスクです。読み戻しが別の実行環境に届くと 404 になりますが、タスクはそれを失敗として扱わず、別の実行環境が答えたと表示します。この章の作りでは、404 が返ることも正しい動きだからです。
