# 04 HTTP API: しくみと実装

[前のページ](/ja/chapters/04-http-api.md)で、API の形をスキーマに決めました。このページでは、リクエストが届いてからレスポンスが返るまでを、通る順に実装します。

## アプリを書く

<!-- section: 04.app -->

この本では、HTTP の処理にフレームワークを使いません。アプリは、`Request` を受け取って `Response` を返す 1 つの関数です。

<<< @/examples/04-http-api/src/http/router.ts{handler}

`Request` と `Response` は、ブラウザの `fetch` が使っているのと同じ Web 標準の型です。Node.js にも Workers にも同じ型があるので、この形で書いたアプリは、Lambda の上でも手元の Node.js のサーバーでも同じように動きます。

フレームワークを使えば、ルーティングも、CORS も、Lambda のイベントの変換も任せられます。それをこの章で自分で書くのは、AWS が初めての人にとって、任せた先で起きていることがいちばん見ておきたいところだからです。Lambda が関数に何を渡すのか、ルートがどう選ばれるのか、ボディをどこまで読むのかを、`src/http/` の 5 つのファイルに分けて書きました。合わせて 300 行ほどで、ここからリクエストが通る順に見ていきます。そのかわり、広く使われているフレームワークほどの機能はなく、確かめているのもこの本のテストだけです。していないことは、それぞれの箇所で書きます。

### Lambda のイベントを Request にする

Lambda は関数に `Request` を渡しません。渡すのは、API Gateway が HTTP のリクエストを書き写した JSON のオブジェクトです。次の関数が、このイベントを `Request` に組み立て直します。

<<< @/examples/04-http-api/src/http/api-gateway.ts{to-request}

URL は、イベントにあるドメイン名、送られたままのパス、クエリ文字列をつないで作ります。同じ名前のヘッダーが複数あったときは、API Gateway がカンマでつないで 1 つにしてあります。cookie だけはヘッダーとは別の配列で届くので、1 つの `cookie` ヘッダーに戻します。ボディは文字列で届き、テキストでないバイト列は base64 になっているので、`isBase64Encoded` を見て元に戻します。

この関数が読めるのは、HTTP API のペイロード形式 2.0（payload format version 2.0）のイベントだけです。REST API のイベントは形が違うので、読めません。

### ルートを選ぶ

<<< @/examples/04-http-api/src/http/router.ts{router}

`route` は、メソッドとパスと処理を 1 組にします。パスは `URLPattern` のパターンで書き、`/notes/:id` は `/notes/abc` に一致して、`abc` に `id` という名前を付けます。`URLPattern` もブラウザと同じ Web 標準の API で、Node.js 24 ではグローバルにあります。

`router` は、ルートを書いた順に調べ、メソッドとパスの両方が合った最初のルートに処理を任せます。どれにも合わなければ `notFound` が答えます。`URLPattern` が返すパスの部分は送られたままの形なので、`%20` のようなエンコードは `decode` で戻します。戻せない並びが来たときは、合うルートがなかったものとして扱います。

ルーターがするのはここまでです。パスは合うのにメソッドが違うリクエストに 405 を返すことも、`HEAD` を `GET` と同じに扱うこともしないので、どちらも 404 になります。

### ボディを読んで確かめる

<<< @/examples/04-http-api/src/http/body.ts{read-json}

`readJson` は、上限を超えるボディを最後まで読みません。まず `content-length` ヘッダーを見て、上限を超えていれば読まずに断ります。ただし、このヘッダーは付いていないことも、実際より小さい値が書かれていることもあるので、読みながらバイト数を数え、上限を超えたところで読むのをやめます。読み終えたら UTF-8 の文字列にして、JSON として解釈します。どちらかに失敗したときと、ボディが空のときは、`invalid_json` を返します。`content-type` ヘッダーは見ないので、`text/plain` と書かれたボディでも、JSON として読めれば受け取ります。

Lambda の上では、ボディはイベントに入って丸ごと届いたあとなので、途中でやめてもメモリは節約できません。数えながら読むことが効くのは、手元のサーバーのように、ボディがストリームで届く場所です。

ルートは次の 5 つです。

<<< @/examples/04-http-api/src/app.ts{routes}

`POST /notes` は `readJson` に 64 KiB の上限を渡し、超えていれば 413 を、JSON でなければ 400 を返します。

JSON として読めても、ノートの形をしているとは限りません。TypeScript の型は実行時には残っていないので、`readJson` が返す値の型は `unknown` です。`v.safeParse` がこの値を契約のスキーマと照合し、合っていれば、型が `CreateNote` の値を `input.output` に入れます。題名の前後の空白を落とし、本文がなければ空文字を入れた値です。合わなければ、`input.issues` に理由が並びます。`v.getDotPath` でどの項目かを取り出し、400 に添えて返します。

### CORS

ブラウザは、あるオリジンのページが別のオリジンの API から受け取ったレスポンスを、API が許可のヘッダーを付けていないかぎり、ページに読ませません。そのヘッダーを付けるのが `cors` です。

<<< @/examples/04-http-api/src/http/cors.ts{cors}

`cors` は、次に呼ぶハンドラーを受け取って、同じ形のハンドラーを返します。`createApp` がどこをこの関数で包むかは、次の節で見ます。

ブラウザは、`content-type` が `application/json` の `POST` のようなリクエストを送る前に、`OPTIONS` で許可を尋ねます。この問い合わせを preflight と呼びます。preflight には `cors` が答えるので、ルートには届きません。それ以外のリクエストは次のハンドラーに渡し、返ってきたレスポンスの複製に `access-control-allow-origin` を付けます。

許すオリジンは環境変数 `ALLOWED_ORIGIN` の 1 つだけで、呼んだ側のオリジンを見て出し分けることはしません。別のオリジンのページにも同じ値が届きますが、自分のオリジンと一致しないので、ブラウザがレスポンスを読ませません。複数のオリジンを許すことと、cookie を伴うリクエストを許すことは、この関数ではできません。

### すべてのリクエストにすること

<<< @/examples/04-http-api/src/app.ts{around}

`createApp` の残りは、どのリクエストにも同じようにすることです。フレームワークならミドルウェアに分けるところを、関数の入れ子で書いています。いちばん内側の `caught` は、ルートが投げた例外を捕まえて、いつもの形のエラーにします。`caught` を `cors` で包み、いちばん外側の関数が、リクエストごとの ID を作り、`x-request-id` ヘッダーを付けて、ログを 1 行書きます。ルートに見せたい値は `context` に入れて渡します。この章で入れているのは `requestId` だけです。

包む順番には理由があります。`caught` が `cors` の内側にあるので、409 や 500 のレスポンスにも `access-control-allow-origin` が付きます。付いていないと、ブラウザはエラーのレスポンスをページに読ませないので、ページは何が起きたのかを表示できません。

想定していない例外は、理由を外に出しません。ログに書き、呼んだ側には `requestId` だけを返します。スタックトレースをレスポンスに載せると、アプリの内部の作りを外に教えることになるからです。

### Response を Lambda の結果にする

Lambda が関数から受け取るのも、JSON のオブジェクトです。

<<< @/examples/04-http-api/src/http/api-gateway.ts{to-result}

`toResult` は、`Response` の状態コードとヘッダーとボディを、その形に移します。`set-cookie` は 1 つのヘッダーにまとめられないので、`cookies` の配列に分けます。結果は JSON なので、テキストでないボディは base64 にして `isBase64Encoded` を立てます。ボディは最後まで読み切ってから返すので、レスポンスを少しずつ送ることはできません。

<<< @/examples/04-http-api/src/http/api-gateway.ts{handle}

`handleApiGateway` は、ここまでの 2 つの変換でハンドラーを挟みます。イベントそのものも `context` として渡しています。API Gateway が検証した結果のように、`Request` には載らない情報を読むためで、この章のアプリは使いませんが、06章で使います。Lambda の入口になる `src/lambda.ts` は、[ノートの置き場所](/ja/chapters/04-http-api/local.md)で見ます。

### 外から渡すもの

`createApp` は、必要なものをすべて引数で受け取ります。時刻、ID の生成、ログの出力先、ノートの保存先がそうで、`createApp` の中では `Date.now()` にも `process.env` にも直接触りません。テストでは決まった値を、本番では本物を渡せます。

ノートの保存先はインターフェースにしてあります。

<<< @/examples/04-http-api/src/notes.ts{repository}

いまの実装はただの `Map` です。`Map` はメモリの上にあるので、誰でも `POST` できる API でそのままにしておくと、入れられただけ膨らみます。そこで 100 件で打ち切り、101 件目には `NoteLimitError` を投げます。`caught` は、この例外を 409 と `quota_exceeded` にします。429 ではなく 409 にしたのは、待っても空きはできず、1 件消せば空くからです。

05章で保存先を DynamoDB に差し替えますが、このインターフェースはそのまま使います。

## 設定は起動時に確かめる

<!-- section: 04.env -->

環境変数も、型の外から来る値です。`process.env` の型は、どの変数も `string` か `undefined` だと言っているだけなので、必要な変数が入っているかどうかは型からはわかりません。

<<< @/examples/04-http-api/src/env.ts{env}

環境変数は、起動するときに一度だけ確かめます。足りなければ、最初の呼び出しが、変数の名前を含むメッセージで失敗します。特定の条件のときだけ `undefined` を読んで壊れるより、ずっと早く原因にたどり着けます。

ここに置いているのは設定で、秘密の値ではありません。Lambda の環境変数は、コンソールで関数の設定を見られる人なら誰でも読めます。API キーのような秘密の値は環境変数に直接置かず、Secrets Manager などから実行時に取得します。この章のサンプルには秘密の値がないので、取得するコードもありません（[21章](/ja/chapters/21-security.md)で扱います）。
