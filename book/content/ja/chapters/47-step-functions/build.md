# 47 Step Functions: しくみと実装

[前のページ](/ja/chapters/47-step-functions.md)で、取り込みと照会の 2 つのステートマシンの形を見ました。このページでは、その定義を上から読みながら、ステートの言語、サービスの呼び方、`Retry` と `Catch`、saga の組み立て方を順に説明します。

## ステートの言語

<!-- section: 47.language -->

ステートマシンの定義は、Amazon States Language（ASL）という JSON です。この章では、JSON を TypeScript のオブジェクトとして書き、スタックがそれを文字列にして渡します。型は、この章が使う範囲だけを自分で書きました。

<<< @/examples/47-step-functions/src/saga.ts{definition}

定義の先頭にある `QueryLanguage` は、ステートの中でデータを選んだり組み替えたりする式の言語を決めます。選べるのは JSONPath と JSONata の 2 つで、省略すると JSONPath になります。16章の定義は JSONPath でした。AWS のドキュメントは、コンソールで新しく作るワークフローには JSONata を選ぶよう勧めています。この章は JSONata で書きます。

JSONata のステートでは、`{%` で始まり `%}` で終わる文字列が式として評価されます。それ以外の文字列は、書いたとおりの文字列です。データの出入りを決めるフィールドは 2 つだけで、`Arguments` が呼び出しに渡す値、`Output` が次のステートに渡す値です。JSONPath にあった `InputPath`、`Parameters`、`ResultSelector`、`ResultPath`、`OutputPath` の 5 つは使いません。

式の中から見えるものは、`$states` という 1 つの変数にまとまっています。

| 式 | 中身 | 使える場所 |
| --- | --- | --- |
| `$states.input` | ステートに入ってきた値 | どこでも |
| `$states.result` | 呼び出しの結果 | `Task`、`Map`、`Parallel` の `Output` と `Assign` |
| `$states.errorOutput` | `Error` と `Cause` を持つオブジェクト | `Catch` の `Output` と `Assign` |
| `$states.context` | 実行の名前、開始時刻、タスクトークンなど | どこでも |

<<< @/examples/47-step-functions/src/saga.ts{shared}

取り込みの定義は、この 5 つの式をあちこちで使い回します。どのステートも `Output` に `$states.input` をそのまま返すので、取り込みの入力（持ち主、ノート ID、タイトル、本文、アップロードの場所）は最後のステートまで同じ形で流れます。こうしておくと、補償処理のステートがどこから呼ばれても、消すべきノートとファイルを入力から求められます。

`Output` を省いたときに何が次へ渡るかは、仕様書の 2 か所で記述が食い違っています。`Arguments` と `Output` の節は「`Task` では結果」と書き、`Task` の節は「入力をそのまま」と書いています。どちらが正しいかを確かめていないので、この章の定義は `Task` と `Map` のすべてに `Output` を書きました。

JSONata には、気をつけるところが 2 つあります。1 つ目は、値のない式がエラーになることです。入力にないフィールドを `{% $states.input.missing %}` で読むと、ステートは `States.QueryEvaluationError` で失敗します。JSON には「値がない」を表す方法がないからです。2 つ目は、文字列をつなぐ `&` が、値のない側を空文字列として扱うことです。こちらはエラーにならず、キーが `attachments//` のような形になって、黙って別のものを指します。後者には、このページの saga の節でもう一度触れます。

Step Functions が実装している JSONata は 2.0.6 の仕様に基づき、`$eval` だけが使えません。代わりに `$parse` があり、ほかに `$uuid`、`$hash`、`$partition`、`$range`、`$random` が足されています。この章の定義は、足された関数を使っていません。

ステートをまたいで値を持ち回る方法は、`Output` のほかにもう 1 つあります。`Assign` で名前を付けて保存した値は、あとのどのステートからも `$名前` で読めます。変数 1 つは 256 KiB まで、1 回の実行の合計は 10 MiB までです。取り込みは入力をそのまま流せば足りるので、変数は使っていません。

### 入力は、起動する側で確かめる

<<< @/examples/47-step-functions/src/saga.ts{input}

ステートマシンには、入力のスキーマを宣言する場所がありません。形の合わない入力で起動すると、最初にそのフィールドを読んだステートが `States.QueryEvaluationError` で失敗するか、`&` のせいで失敗もせずに先へ進みます。そこで、起動する側が Valibot で確かめてから `StartExecution` を呼びます。持ち主とノート ID を英数字と `_`、`-` に限っているのは、どちらも DynamoDB のキーと S3 のキーの一部になるからです。`upload` は `inbox/` の下に限ります。こうしないと、取り込みを起動できる人が、バケットの中の好きなオブジェクトを自分の添付ファイルとしてコピーできてしまいます。

実行の名前は、持ち主とノート ID から作ります。Standard ワークフローでは、実行中の実行と同じ名前、同じ入力で `StartExecution` を呼ぶと、新しい実行は始まらず、同じ実行を指す応答が返ります。実行が終わったあとや、入力が違うときは `ExecutionAlreadyExists` です。名前は、実行が終わってから 90 日間は使い回せません。起動のリクエストが 2 回届いても、取り込みは 1 つしか始まりません。

## サービスの呼び方

<!-- section: 47.integrations -->

`Task` が何を呼ぶかは、`Resource` の文字列で決まります。形は ARN ですが、実在するリソースを指しているわけではなく、Step Functions が「どのサービスのどの API を、どう呼ぶか」を読み取るための名前です。

<<< @/examples/47-step-functions/src/saga.ts{steps}

`CreateNote` の `arn:aws:states:::dynamodb:putItem` は、DynamoDB の PutItem を呼びます。`Arguments` が、そのまま API のリクエストになります。16章のように Lambda の関数を挟んで SDK から呼ぶのと違い、コードも、バンドルも、関数のロールもありません。Step Functions のロールが `dynamodb:PutItem` を持っていれば足ります。

呼べる相手には 2 通りあります。DynamoDB、SQS、SNS、Lambda などは、Step Functions が専用に用意した統合（optimized integration）を持っています。それ以外の 200 を超えるサービスは、`AttachFile` の `arn:aws:states:::aws-sdk:s3:copyObject` のように、`aws-sdk:サービス名:API名` の形で呼びます。どちらも、パラメーターの名前は PascalCase で書きます。

関数を挟まないと、できないこともあります。JSONata で書ける範囲を超える計算、いくつかの API を条件つきで組み合わせる処理、外部の HTTP API との込み入ったやりとりは、関数に入れたほうが読みやすく、テストもしやすくなります。この章の取り込みは、どのステップも API を 1 回呼ぶだけなので、関数が要りませんでした。

エラーの名前は、呼び方で決まります。専用の統合の DynamoDB は `DynamoDB.ConditionalCheckFailedException` のように `DynamoDB.` で始まり、SDK 経由の統合は `サービス名.エラー名` の形で、サービス自身のエラー名に `Exception` が付いていなくても `Exception` を付けます。`Retry` や `Catch` に書く名前が 1 文字違うと一致しないので、ここは実機で確かめるべきところです。この章では確かめていません。

### 呼んだあとの待ち方

`Resource` の末尾で、呼んだあとの待ち方が変わります。

| 末尾 | 呼び出し方 | 次のステートへ進むとき |
| --- | --- | --- |
| なし | 応答を待つ（request response） | API が応答を返したとき |
| `.sync` | ジョブの完了を待つ（run a job） | 呼んだジョブが終わったとき |
| `.waitForTaskToken` | コールバックを待つ | 誰かがトークンを返したとき |

何も付けなければ、API の応答が返った時点で次へ進みます。取り込みの `Task` は、1 つを除いてこれです。

`.sync` は、ECS のタスク、AWS Batch のジョブ、Glue のジョブ、別のステートマシンの実行のように、呼んでから終わるまでに時間がかかるものに付けます。Step Functions が完了を見張り、終わってから次へ進みます。16章の最後で触れた「Lambda に入らないステップを ECS のタスクにする」ときの呼び方です。使えるサービスは決まっていて、SDK 経由の統合では使えません。この章のコードには出てきません。

`.waitForTaskToken` は、Step Functions が見張れないものを待つための呼び方です。人の承認、外部のサービス、自分で書いたワーカーなどが相手です。

<<< @/examples/47-step-functions/src/saga.ts{scan}

```figure
caption: WaitForScan は、トークンを入れたメッセージを送って止まり、トークンが返ってきたら進む
type: sequence
actor sfn: Step Functions
actor queue: SQS キュー
actor scanner: スキャナー
step sfn -> queue: SendMessage {taskToken, key}
note sfn: WaitForScan で止まる
step queue -> scanner: ReceiveMessage
step scanner --> sfn: SendTaskHeartbeat
step scanner --> sfn: SendTaskSuccess {verdict}
note sfn: Verdict へ進む
```

`WaitForScan` は、SQS にメッセージを 1 通送ります。メッセージには、`$states.context.Task.Token` で取り出したタスクトークンを入れておきます。SQS が応答を返しても、ステートは先へ進みません。誰かがそのトークンを添えて `SendTaskSuccess` を呼ぶと、そこで渡された値がステートの結果になり、`SendTaskFailure` を呼ぶと、ステートはそこで渡された名前のエラーで失敗します。`$states.result` は SQS の応答ではなく、スキャナーが返した値です。

<<< @/examples/47-step-functions/src/saga.ts{scan-message}

メッセージと返事の形は、スキーマにしてあります。スキャナーの役は、08章のワーカーのような、キューを読む関数が務めます。この章のスタックにはスキャナーを入れておらず、デプロイのページで、人が手でトークンを返すタスクを用意しています。

待ち合わせで必ず決めるのが、待つ時間の上限です。`TimeoutSeconds` と `HeartbeatSeconds` の既定値は、どちらも 99,999,999 秒です。書かなければ、トークンが返ってこないタスクは、実行の上限である 1 年まで待ち続けます。`WaitForScan` は、30 分以内に終わることと、5 分ごとに `SendTaskHeartbeat` で「まだ動いている」と知らせることを求めています。長い仕事の上限を 1 つの長いタイムアウトで決めると、スキャナーが最初の 1 分で落ちても、30 分たつまで気づけません。ハートビートを分けておけば、5 分で気づきます。

ハートビートが途切れたときのエラー名は、ドキュメントのページによって `States.Timeout` と `States.HeartbeatTimeout` に分かれています。どちらが正しいかを確かめていないので、`Retry` には両方を書きました。

タイムアウトしたタスクを再試行すると、新しいトークンが作られ、メッセージがもう 1 通送られます。古いトークンで `SendTaskSuccess` を呼ぶと、`TaskTimedOut` というエラーが返ります。API リファレンスは、このエラーを「トークンの期限が切れたか、そのトークンのタスクがすでに閉じている」と説明しています。スキャナーから見ると、同じファイルの依頼が 2 通届くことがあるわけです。スキャンは何度やっても結果が変わらないので、ここでは困りません。承認のメールを人に送るような待ち合わせでは、2 通目が届いたときに何が起きるかを、先に決めておく必要があります。

Express ワークフローは、`.sync` も `.waitForTaskToken` も使えません。

## Retry と Catch

<!-- section: 47.retry -->

16章は、`Retry` を「何が起きても同じステップをもう一度」と 1 つだけ書きました。ここでは、何を再試行して何を再試行しないかを分けます。

<<< @/examples/47-step-functions/src/asl.ts{retry}

<<< @/examples/47-step-functions/src/saga.ts{retry}

`Retry` は retrier の配列で、Step Functions は上から順に、エラー名が `ErrorEquals` に一致する最初の 1 つを使います。待ち時間は、`IntervalSeconds`（既定 1）から始まり、再試行のたびに `BackoffRate`（既定 2.0）倍になります。`MaxAttempts`（既定 3）は再試行の回数で、最初の 1 回は含みません。`transient` の設定では、最初の試行のあと 2 秒、4 秒、8 秒と待って、合わせて 4 回試します。

`MaxDelaySeconds` は、倍々に伸びる待ち時間の上限です。`MaxAttempts` を大きくするなら、必ず一緒に書きます。`transient` の間隔のまま上限を外すと、10 回目の再試行の前には 17 分待つことになります。

`JitterStrategy` を `FULL` にすると、それぞれの待ち時間が、0 から計算した値までの間でランダムに決まります。既定は `NONE` です。[32章](/ja/chapters/32-limits.md)で扱うとおり、同じ原因で同時に失敗した実行が、同じ間隔で同時に再試行すると、相手をもう一度同じ瞬間に叩くことになります。たくさんの実行が同じテーブルを書くワークフローでは、`FULL` にしておきます。

エラー名には、まとめて一致するものが 2 つあります。`States.TaskFailed` は、`States.Timeout` 以外のすべてのエラーに一致します。`States.ALL` は、ほぼすべてに一致しますが、`States.Runtime` と `States.DataLimitExceeded` には一致しません。`States.ALL` は、配列の最後に、それだけで書きます。`transient` が `States.Timeout` と `States.TaskFailed` を並べているのは、合わせると「サービスの呼び出しで起きたことのすべて」になるからです。

再試行しても直らないエラーは、`MaxAttempts: 0` の retrier を先に置いて、再試行から外します。`CreateNote` では、条件が成り立たなかったことを表す `DynamoDB.ConditionalCheckFailedException` がそうです。条件は、もう一度試しても成り立ちません。これを外しておかないと、結果のわかっている失敗に最大で 14 秒かけ、状態遷移を 3 回ぶん余計に払います。再試行も状態遷移として課金されるからです。

`Catch` は、再試行が尽きたあとの行き先です。こちらも上から順に見て、一致する最初の 1 つに進みます。JSONata のステートでは、catcher に `Output` を書けます。書かなければ、次のステートに渡るのは `Error` と `Cause` だけのオブジェクトで、ステートの入力は捨てられます。取り込みの catcher が `Output` で入力とエラーをまとめ直しているのは、そのためです。

`Catch` を書けるのは `Task`、`Map`、`Parallel` だけです。実行そのものが失敗したときに呼ばれる「最後の受け皿」は、定義の中にはありません。受け皿がほしいなら、実行の状態が変わったときに EventBridge に届くイベントを使います（[デプロイのページ](/ja/chapters/47-step-functions/deploy.md)）。

## saga

<!-- section: 47.saga -->

取り込みは、DynamoDB と S3 の両方を書き換えます。2 つのサービスにまたがるトランザクションはないので、「両方書くか、どちらも書かないか」を 1 回の操作では保証できません。そこで、ステップを 1 つずつ確定させていき、あとのステップが失敗したら、済んだステップを打ち消す操作を実行します。このやり方を saga、打ち消す操作を補償処理と呼びます。

守ることを 1 文で書きます。

**終わった取り込みは、公開されたノートとその添付ファイルの両方を残すか、どちらも残さない。例外は、取り消せないステップか補償処理そのものが失敗した実行だけで、その実行はそのステートで失敗として終わり、redrive でそこから続けられる。**

2 文目が要るのは、Step Functions にも保証できないことがあるからです。補償処理が失敗し続ければ、ワークフローにできるのは、そこで止まって、どこで止まったかを正確に残すことだけです。

### 失敗したステップ自身も取り消す

`CreateNote` の `Catch` は、`RemoveNote` へ進みます。「ノートを書くのに失敗したのだから、消すものはない」とは考えません。`Catch` に来たということは、再試行が尽きたということで、その中には、書き込みは済んでいるのに応答だけが届かなかった場合が含まれます。ステップが失敗したという事実からは、何も書かれていないとは言えません。

したがって、補償処理は「そのステップが実行されていても、されていなくても、安全に実行できる」ように書きます。`RemoveAttachment` は S3 の DeleteObject で、ないキーを消しても成功します。`RemoveNote` は条件つきの DeleteItem で、アイテムがなければ何もせずに成功します。

<<< @/examples/47-step-functions/src/saga.ts{compensations}

### 自分のものだけを書き、自分のものだけを消す

<<< @/examples/47-step-functions/src/saga.ts{conditions}

どの書き込みにも条件を付けています。`CreateNote` と `RemoveNote` の条件は、「アイテムがないか、この取り込みが書いた、まだ公開されていないアイテムである」です。「この取り込み」は、アイテムに書いておいた実行の名前で見分けます。

`CreateNote` がこの条件を付けているのは、再実行のためです。条件を「アイテムがない」だけにすると、1 回目の書き込みが済んでいて応答だけが失われたとき、2 回目は自分が書いたアイテムにぶつかって失敗します。ほかの取り込みが同じノート ID を使っている場合と区別が付きません。条件に「自分が書いたものなら通す」を足すと、再実行は同じアイテムをもう一度書くだけになり、他人のアイテムにぶつかったときだけ失敗します。後者は `NoteIdTaken` へ進み、何も取り消しません。取り消すものを書いていないからです。

`RemoveNote` が同じ条件を付けているのは、消しすぎないためです。条件がなければ、補償処理は、同じノート ID で先に取り込まれた他人のノートを消してしまいます。

### 取り消せないステップ

`CreateNote` が書くノートには `phase` という属性があり、最初は `pending` です。照会は `ready` のノートしか見せません。saga はステップごとに確定させていくので、途中の状態が外から見えます。ノートは書かれたが、添付ファイルはまだなく、スキャンも済んでいない、という状態です。途中のノートを読者に見せないために、公開の印を別に持ち、最後に切り替えます。

<<< @/examples/47-step-functions/src/saga.ts{commit}

`Publish` が、その切り替えです。このステートには `Catch` がありません。`Publish` の再試行が尽きたとき、ノートは公開されたかもしれず、されていないかもしれません。公開されていれば、誰かがもう読んだかもしれません。ここで補償処理に進むと、読者に見えていたノートが消えるか、ノートは残って添付ファイルだけが消えます。どちらも、止まっているより悪い結果です。

そこで、`Publish` より前は「失敗したら取り消す」、`Publish` から先は「失敗したら、もう一度やる」と分けます。`Publish` は何度実行しても同じ結果になるので、再試行が尽きたら実行を失敗させ、原因を直してから redrive で `Publish` をやり直します。それまでの間、ノートは `pending` のままで読者には見えないか、すでに `ready` で添付ファイルも揃っているかの、どちらかです。

`Notify` は `Publish` のあとにあります。送った通知は取り消せないので、取り消す可能性のあるステップより前には置きません。通知が送れなくても公開は取り消さず、`notified: false` を付けて成功で終わります。SNS の Publish は冪等ではないので、応答が失われて再試行されると、通知は 2 通届きます。メッセージの属性に実行の名前を入れてあるのは、受け取る側が重複を見分けられるようにするためです。

補償処理の 2 つにも `Catch` がありません。理由は `Publish` と同じで、redrive の動きにあります。redrive は、失敗したステートを、そのときの入力でもう一度実行します。補償処理の失敗を `Catch` で受けて `Fail` ステートへ進めてしまうと、redrive は `Fail` ステートに入り直して、すぐまた失敗するだけです。`Catch` を書かずにそのステートで実行を失敗させておけば、権限などの原因を直したあと、redrive が補償処理の続きを実行します。

### スキャンが断ったとき

`Verdict` は `Choice` で、スキャンの結果が `clean` でなければ `RemoveAttachment` へ進みます。誰もエラーを投げていませんが、取り消す理由としては同じです。`Catch` は「失敗したとき」の道で、`Choice` は「うまくいったが、先へ進めないとき」の道です。補償処理は、どちらからも同じステートに入れるように、入力の形を揃えてあります。

## Choice、Map、Parallel、Wait

<!-- section: 47.flow -->

`Map` は、配列の要素ごとに、`ItemProcessor` に書いた小さなステートマシンを 1 回ずつ実行します。`Items` が配列を選び、`ItemSelector` が繰り返し 1 回ぶんの入力を作ります。要素そのものは `$states.context.Map.Item.Value` で、何番目かは `.Index` で読めます。結果は、繰り返しの出力を入力と同じ順に並べた配列です。

`MaxConcurrency` は、同時に走らせる繰り返しの数の上限です。0 は「上限なし」という意味なので、書き忘れると、25 件の照会が 25 件の GetItem を同時に投げます。相手のスロットリングに合わせて、必ず数を書きます。

この `Map` は inline と呼ばれる動かし方で、繰り返しは親の実行の中で走ります。同時に走るのは 40 までで、繰り返しの履歴は親の履歴に足されます。1 つの繰り返しが失敗すると、`Map` 全体が失敗し、ほかの繰り返しも止まります。照会が 1 件の読み取りの失敗で全体を失敗にしているのは、この動きのままです。

もう 1 つの動かし方が distributed です。繰り返しを 1 つずつ別の子の実行として起動するので、同時に 10,000 まで走り、履歴も子ごとに分かれます。入力は、S3 に置いた JSON や CSV、オブジェクトの一覧から直接読めます。ステートの間で運べる 256 KiB や、履歴の 25,000 イベントの上限に当たる大きさの仕事のためのもので、Standard ワークフローでしか使えません。16章のエクスポートを、ノートが何百万件あっても動くように作り直すなら、これを使うことになります。distributed には `ToleratedFailurePercentage` と `ToleratedFailureCount` があり、失敗した要素がその割合か件数を超えるまでは、全体を失敗にしません。百万件のうち数件の壊れた行のために全体を止めたくないときに使います。許した失敗がどの要素だったかは、結果を調べないとわかりません。この章には、distributed のコードはありません。

`Parallel` は、互いに違うステートマシンを `Branches` に並べて、同時に走らせます。同じ処理を要素ごとに繰り返すのが `Map` で、違う処理を並べるのが `Parallel` です。結果は、ブランチの出力をブランチの順に並べた配列です。1 つのブランチが失敗すると、全体が失敗します。

`Wait` は、`Seconds` に書いた秒数か、`Timestamp` に書いた時刻まで待ちます。待てるのは、Standard で 1 年、Express で 5 分までです。前のページで計算したとおり、Standard は待つ時間に課金しません。

`Parallel` と `Wait`、それに何もせずに値を作る `Pass` は、この章のコードに出てきません。手元の実行器も扱いません。
