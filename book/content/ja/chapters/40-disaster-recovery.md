# 40 Disaster Recovery: Elastic Disaster Recovery（DRS）、復旧訓練、failback

[22章](/ja/chapters/22-recovery.md)では、消してしまったデータを戻しました。[23章](/ja/chapters/23-ec2.md)では、サーバーを 1 台持ち、止まれば全部が止まることを引き受けました。この章で扱うのは、そのサーバーが、置いてある場所ごと使えなくなったときの備えです。

使うのは AWS Elastic Disaster Recovery です。API と CLI での名前は `drs` なので、以下では DRS と書きます。DRS は、サーバーのディスクへの書き込みを別の場所へ複製し続け、必要になったときに、複製からサーバーを起動します。

この章の構成は、**置いてあるだけで時間単位の料金がかかります**。23章のインスタンス 1 台を保護すると、訓練を一度もしなくても、既定の構成で 1 日およそ USD 2.07、1 か月（730 時間）で USD 62.82 が、23章と 11章の料金に上乗せされます。金額のわからない項目がほかにもあり、このページの「置いてあるだけでかかる料金」に並べました。料金を止めるには、ソースサーバーを切り離して削除し、この章のスタックを消します。インスタンスを止めるだけでは止まりません。手順は[片付け](/ja/chapters/40-disaster-recovery/wrap.md)にあります。

もう 1 つ、先に書いておきます。DRS のドキュメントは、Amazon Linux 2023 をカーネル 6.12 まで対象としています。23章の既定の AMI は、23章が書いているとおり 2026 年 8 月からカーネル 6.18 なので、そのままでは対象外です。試すなら、23章のインスタンスを `-c amiId=` で古いカーネルの AMI に固定してください。

この章では、AWS に対して何も実行していません。デプロイも、エージェントの導入も、訓練もしていません。手元で確かめたのは、判断のコードとスタックの中身です。コードは `examples/40-disaster-recovery/` にあります。

## DRS がすること、しないこと

<!-- section: 40.what -->

DRS が複製するのは、サーバーのディスクです。保護したいサーバーに AWS Replication Agent というプログラムを入れると、エージェントはディスクへの書き込みをブロック単位で捉え、復旧先のリージョンにあるステージングエリア（staging area）へ送り続けます。サーバーは、データセンターの物理マシンでも、ほかのクラウドの仮想マシンでも、別のリージョンや別の AZ にある EC2 のインスタンスでも構いません。この章では、23章のインスタンスを、同じリージョンの別の AZ へ複製します。

ステージングエリアにあるのは、複製されたディスクと、それを受け取るための小さなインスタンスだけです。元のサーバーと同じ大きさのインスタンスが待機しているわけではありません。復旧するときに初めて、選んだ時点のスナップショットから、リカバリーインスタンス（recovery instance）を起動します。待機させておく費用を、復旧にかかる時間と引き換えに減らす設計です。

DRS がしないことも 3 つあります。

1 つ目は、マネージドサービスの複製です。エージェントを入れられるのは OS のあるサーバーだけなので、DynamoDB のテーブルや S3 のバケットは対象になりません。そちらには、それぞれの仕組みがあります（22章と [28章](/ja/chapters/28-multi-region.md)）。

2 つ目は、長く残すバックアップです。DRS が持つ時点は、直近 1 時間は 10 分ごと、直近 24 時間は 1 時間ごと、それより前は 1 日ごとで、日ごとのぶんの保持は既定で 7 日、設定できるのは 1 日から 365 日までです。22章で使った AWS Backup のスナップショットは、ドキュメントによれば 1 日から 100 年まで、指定しなければ無期限に残せます。半年前の状態に戻したい、という要求には DRS では応えられません。保持の外に出た時点は、消えています。

3 つ目は、通信の切り替えです。DRS はインスタンスを起動するところまでしかしません。利用者の通信をそちらへ向ける failover は、DRS の外で自分が行う、とドキュメントに書いてあります。

DRS が複製した状態は、crash consistent です。電源が突然切れた瞬間のディスクと同じ、という意味で、メモリにあってまだディスクに書かれていなかったデータは含まれません。23章のノート API は、書き込みがディスクに届いてから 201 を返すので、この性質と相性がよいほうです。

## 置いてあるだけでかかる料金

<!-- section: 40.cost -->

金額は USD で、東京リージョンの従量課金の定価、税別です。1 か月は 730 時間として計算しています。どれも 23章と 11章の料金に加わる金額で、ソースサーバーは 1 台、訓練はしていない状態です。

| 構成 | 1 日 | 1 か月 |
| --- | --- | --- |
| 既定（プライベートサブネット） | 2.07 | 62.82 |
| `-c placement=public` | 1.51 | 46.03 |

内訳は次のとおりです。

- DRS の料金: 複製しているソースサーバー 1 台につき 1 時間 USD 0.028 で、730 時間では 20.44。ディスクの数や大きさ、訓練の回数では変わりません
- レプリケーションサーバー: ステージングエリアでデータを受け取る EC2 のインスタンスです。既定の `t3.small` が 1 時間 USD 0.0272 で、730 時間では 19.86
- ステージング用のディスク: ソースのディスクと同じ大きさの EBS ボリュームです。125 GiB 以下のディスクは既定で magnetic になり、1 GB・1 か月あたり USD 0.08。23章のルートボリューム 8 GiB（23章の仮定）とデータボリューム 8 GiB で、1.28
- スナップショット: 料金ページは、ソースのディスクと同じ大きさの基準のスナップショットが 1 つずつ要る、と書いています。そのまま 16 GB として、1 GB・1 か月あたり USD 0.05 で 0.80
- インターフェースエンドポイント（既定の構成のときだけ）: この章のスタックが `drs` と `ec2` の 2 つを、1 つの AZ にだけ置きます。1 つ・1 時間 USD 0.014 で、730 時間では 20.44
- パブリック IPv4 アドレス（`placement=public` のときだけ）: レプリケーションサーバーが 1 つ持ちます。1 時間 USD 0.005 で、730 時間では 3.65

表に入れていない項目があります。金額は 0 ではなく、不明です。時点ごとの増分のスナップショット（書き込みの量で決まります）、レプリケーションサーバー自身のルートボリューム、magnetic のボリュームにかかる I/O リクエストの料金（100 万件あたり USD 0.08）、エンドポイントのデータ処理、AZ をまたぐデータ転送、`t3` の余剰の CPU クレジットです。無料利用枠は、当てはまるかどうかを確かめられないので引いていません。

訓練でインスタンスを起動すると、その間だけ EC2 と EBS の料金が加わります。`t4g.micro` を 2 時間置いて USD 0.03 ほどです。同じインスタンスを消し忘れて 1 か月置くと 9.42 になります。起動のたびに数分動く変換用のサーバーの料金は含めていません。料金ページは、1 回あたりおおむね USD 0.05 未満としています。

何がいつ課金されるかは、コードにしてあります。

<<< @/examples/40-disaster-recovery/src/cost.ts{billable}

手元で金額を出せます。AWS のアカウントは要りません。

```bash
vp run dr:plan kernel=6.1
vp run dr:plan kernel=6.1 placement=public
```

`kernel=` を付けずに実行すると、23章の既定の AMI のカーネル（6.18）を仮定するので、対象外という結果で終わります。

リージョンをまたいで複製する場合は、ここに無い料金がさらに加わります。最初の同期、その後の複製、failback のそれぞれで、リージョン間のデータ転送の料金がかかる、とドキュメントに書いてあります。この章は AZ をまたぐ構成なので、計算していません。

## 全体像

<!-- section: 40.pieces -->

```figure
caption: エージェントは書き込みをレプリケーションサーバーへ送り続け、リカバリーインスタンスは必要になったときにスナップショットから起動する
node src: EC2 インスタンス (23章) | zone 1, AWS Replication Agent
node drs: Elastic Disaster Recovery | ap-northeast-1
node rs: レプリケーションサーバー | t3.small, zone 2
node disk: ステージング用のディスク | EBS
node pit: 時点のスナップショット | 10 分, 1 時間, 1 日ごと
node ri: リカバリーインスタンス | 訓練か復旧のときだけ
edge src -> drs: HTTPS 443
edge src -> rs: tcp 1500 (ブロック)
edge rs -> drs: HTTPS 443
edge rs -> disk
edge disk -> pit
edge pit --> ri: StartRecovery
group staging: ステージングエリア = rs, disk, pit
mark ri
```

部品を、作られる順に見ていきます。

**サービスの初期化。** DRS は、使うリージョンごとに一度、初期化が要ります。初期化すると、サービスリンクロールと、レプリケーションサーバー用、変換用のサーバー用、リカバリーインスタンス用、エージェント用、failback 用のロールが作られます。

**レプリケーションの設定。** ステージングエリアにするサブネット、レプリケーションサーバーの種類、ディスクの暗号化、スナップショットを何日残すかを決めます。既定値を持つテンプレートが 1 つあり、ソースサーバーが増えるたびに、そこから写されます。

**エージェント。** ソースサーバーに入れるプログラムです。入れた時点でソースサーバーとして登録され、最初の同期が始まります。

**ソースサーバー（source server）。** DRS から見た、保護されているサーバー 1 台のことです。課金の単位でもあります。

**起動の設定と EC2 の起動テンプレート。** リカバリーインスタンスをどのサブネットに、どのインスタンスタイプで起動するかは、ソースサーバーごとに作られる EC2 の起動テンプレートが決めます。

**訓練と復旧。** どちらも同じ操作で、違うのは訓練かどうかを示す値 1 つです。訓練は元のサーバーにも複製にも影響しません。

**failback。** 復旧先で増えたデータを、元の場所へ複製し直すことです。EC2 どうしの場合は、リカバリーインスタンスの側から逆向きの複製を始めます。

このほかに、起動の後で SSM のドキュメントを走らせる post-launch action、複数のサーバーを順番に起動する recovery plan、VPC の設定を複製して CloudFormation のスタックとして復元する source network があります。この章のサーバーは 1 台で、VPC も同じなので、どれも使っていません。

## DRS を使わないほうがよい場合

<!-- section: 40.when-not -->

この本の読者の多くにとって、DRS は要りません。

03章から 22章までで作ったアプリには、複製するサーバーがありません。Lambda にも、API Gateway にも、DynamoDB にも、エージェントを入れる場所がないからです。このアプリの災害対策は、同じスタックを別のリージョンにデプロイすることと、データを運ぶことです。前者は 20章のパイプラインに、後者は 22章と [28章](/ja/chapters/28-multi-region.md)の仕組みにあります。

23章のインスタンスも、DRS が要るとは限りません。あのインスタンスは、コードから作り直せるようにしてあります。ユーザーデータがマシンを用意し、リリースは S3 にあり、ノートはデータボリュームのスナップショットから戻せます。AZ が使えなくなったら、別の AZ にスタックを作り、スナップショットからボリュームを戻せば済みます。失うのは最後のスナップショットより後のノートで、かかるのは作り直す時間です。その 2 つを受け入れられるなら、月に USD 62 を払い続ける理由はありません。

DRS が合うのは、次のような場合です。

- **コードから作り直せないサーバーがある。** 何年も手で設定を足してきたマシンや、インストールの手順が残っていないソフトウェアは、ディスクごと写すしかありません
- **オンプレミスやほかのクラウドのサーバーを、作り変えずに守りたい。** アプリを書き直す前に、まず災害対策だけを用意したい場合です
- **作り直す時間では、目標に間に合わない。** スナップショットの間隔より短い時間しかデータを失えない、あるいは、作り直しより早く戻したい場合です

1 つ目と 2 つ目は、この本が勧めてきた作り方の外にあるサーバーです。DRS は、そういうサーバーを抱えたまま災害に備える道具だと考えてください。作り直せるものは、作り直すほうが安く、仕組みも少なくて済みます。

どちらを選んでも、復旧の手順を一度も通していなければ、備えがあるとは言えません。この章の[デプロイ](/ja/chapters/40-disaster-recovery/deploy.md)のページは、ほとんどを訓練に使っています。
