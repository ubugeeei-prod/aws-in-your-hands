# 23 制御したいときの EC2: SSM、EBS、プロセス運用

ここまで、サーバーを 1 台も持たずに来ました。Lambda は呼ばれたときだけ動いて、OS のことは AWS が見てくれます。この章では逆に、OS ごと自分で持ちます。

作るのは EC2 の instance、つまり仮想マシンを 1 台です。SSH の port は開けません。[04章](/ja/chapters/04-http-api.md)のノート API を systemd の service として動かして、ノートは instance とは別の disk に置きます。

先にお金の話を。この章は、**置いてあるだけで時間で課金されるもの**を作ります。既定の構成だと 1 日でおよそ USD 2.33、1 か月（730 時間）置きっぱなしで USD 70.74。instance を止めても USD 62.86 かかり続けます。安いほうの構成なら 1 日 USD 0.43、1 か月 USD 13.07 です。内訳はすぐ後で話します。試したら、その日のうちに「片付け」まで進めてくださいね。

前提は [11章](/ja/chapters/11-network.md)の VPC です。コードは `examples/23-ec2/` にあります。

## なぜ今さら EC2？

<!-- section: 23.why -->

04章の Lambda で足りているなら、EC2 は要りません。使っていない間の料金が 0 で、patch も AWS がやってくれる。あれより楽な置き場所は、なかなかありません。

それでも machine を 1 台持ちたくなるのは、こんなときです。

- **プロセスを長く動かしたい。** Lambda の 1 回の実行は最長 15 分です。何時間も接続を持ち続ける、メモリに大きな index を載せたままにする、といった使い方には向きません
- **OS やカーネルを触りたい。** カーネルのパラメーター、ファイルシステム、ネットワークの細かい設定。Lambda にも Fargate にも、あなたが触れるカーネルはありません
- **特殊なハードウェアが要る。** GPU、大きなメモリ、instance に直接つながった高速な disk
- **managed なサービスに無いソフトウェアを動かしたい。** 自分で運用するデータベースや daemon。24章の celld がまさにそれです

引き換えに、いままで AWS がやってくれていたことが、あなたの仕事になります。

- OS と runtime の patch
- プロセスが落ちたら起こすこと、落ちたと気づくこと
- disk。あふれないか、壊れたらどう戻すか
- machine が起動したときに、何がどの順で立ち上がるか
- そして、その 1 台が止まったら全部止まる、という事実

この章は、この 5 つを 1 つずつ片付けていく章です。最後の 1 つだけは片付きません。「1 台は単一障害点」の節で、受け入れる条件を書きます。

## 置いてあるだけでかかるお金

<!-- section: 23.cost -->

金額は USD、東京リージョン、従量課金の定価、税別、1 か月は 730 時間です。計算の中身は[料金の計算](/ja/reference/pricing.md)にあります。

| 構成 | 動かしている 1 日 | 動かしている 1 か月 | 止めている 1 日 | 止めている 1 か月 |
| --- | --- | --- | --- | --- |
| 既定（private subnet） | 2.33 | 70.74 | 2.07 | 62.86 |
| `-c placement=public` | 0.43 | 13.07 | 0.05 | 1.54 |

中身はこうです。

- **instance**: `t4g.micro`（2 vCPU、1 GiB）が 1 時間 USD 0.0108。730 時間で 7.88
- **volume**: gp3 が 1 GB・1 か月あたり USD 0.096。root の 8 GiB と data の 8 GiB で 1.54。root の大きさは AMI が決めるもので、8 GiB は仮定です（実機で確かめていません）
- **public IPv4 アドレス**（`placement=public` のときだけ）: 1 時間 USD 0.005。730 時間で 3.65
- **interface endpoint**（既定の構成のときだけ）: 1 つ・1 AZ あたり 1 時間 USD 0.014。3 つを 2 つの AZ に置いて、730 時間で 61.32

表から読み取ってほしいことが 3 つあります。

**止めても、volume の料金は続きます。** instance を stop すると、止まるのは instance の料金だけです。disk は中身ごと残っているので、置き場所代がかかり続けます。「使わないときは止めておけば 0」にはなりません。

**既定の構成の料金は、ほとんどが endpoint です。** そして endpoint は 11章の stack のリソースなので、この章の instance を止めても消しても、止まりません。なぜそれでも既定にしたのかは、「SSH の port は開けない」で話します。

**public IPv4 アドレスは、種類で話が変わります。** この章の `placement=public` が使うのは、起動のたびに自動で割り当てられるアドレスです。instance を止めると手放されて、課金も止まります。次に起動すると別のアドレスになります。固定したくて Elastic IP アドレスを使うと、そちらは止めている間も課金されます。この章は Elastic IP アドレスを使っていません。

もう 1 つ、表に出てこない落とし穴があります。`t4g` のような T 系の instance は、普段は CPU を控えめに使い、貯めた CPU credit で一時的に全力を出す作りです。そして、何も指定しないと unlimited という設定で起動します。credit を使い切っても全力で走り続けられるかわりに、超えた分が 1 vCPU・1 時間あたり USD 0.04 で課金されます。暴走したプロセスが、そのまま請求になるわけです。この章の stack は standard にしてあります。credit が尽きたら遅くなるだけで、請求は増えません。

## SSH の port は開けない

<!-- section: 23.access -->

サーバーに入るといえば SSH でした。22 番の port を開けて、鍵を配って、踏み台を置く。この章はそれを全部やりません。開いている port は攻撃の入口ですし、鍵は誰かの laptop に残り続けるからです。

かわりに Systems Manager の Session Manager を使います。仕組みはこうです。instance の中で SSM Agent というプロセスが動いていて、Systems Manager に向かって HTTPS の接続を張ります。あなたが `aws ssm start-session` を呼ぶと、Systems Manager がその接続を通して shell をつないでくれます。接続を始めるのは、いつも instance の側。だから inbound の規則が 1 つも要りません。誰が入れるかは、鍵ではなく IAM で決まります。

要るものは 3 つです。

1. **SSM Agent。** AWS が配っている Amazon Linux 2023 の AMI には、最初から入っています
2. **権限。** instance の role に `AmazonSSMManagedInstanceCore` という managed policy を付けます（次の節）
3. **Systems Manager までの経路。** ここが、お金のかかるところです

経路の作り方は 3 通りあります。金額は、通信がなくてもかかる 1 か月ぶんです。

| instance の置き場所 | Systems Manager への道 | 道の料金 |
| --- | --- | --- |
| private subnet | interface endpoint を 3 つ（`ssm`、`ssmmessages`、`ec2messages`） | 61.32 |
| private subnet | NAT Gateway | 48.91（11章の `-c egress=nat`） |
| public subnet | internet gateway と、instance の public IPv4 アドレス | 3.65 |

どれを選んでも、inbound は空のままです。public subnet に置いても、外から instance に接続を始めることはできません。

### 既定は private subnet にしました

正直に言って、迷いました。試すだけなら public subnet のほうが 5 分の 1 以下で済みます。

それでも既定を private にした理由は 2 つです。1 つは、public IPv4 アドレスを持った machine は、security group の規則 1 行の差で外から届くようになること。いまは inbound が空でも、長生きする machine の設定は、誰かがいつか触ります。もう 1 つは、外向きの通信です。public subnet の instance は、443 番ならインターネットのどこへでも出られます。private subnet なら、届くのは Systems Manager と S3 だけです。中のソフトウェアが乗っ取られたときに、できることが違います。

長く置く machine、そして 24章のように複数台で動かすものは、private subnet に置くのが普通です。なので既定はそちらに合わせました。ただ、この章を一度通すだけなら `-c placement=public` で十分です。そのときも inbound は空で、テストがそれを固定しています。

### 11章の VPC につなぐ

interface endpoint は、11章の stack の切り替えで足します。

```bash

```

11章で見たとおり、`-c` はその 1 回のコマンドにしか効きません。あとで `-c` なしで 11章を deploy し直すと、endpoint は消えて、この章の instance は Systems Manager から見えなくなります。

endpoint が 3 つとも要るのかは、実は言い切れません。Systems Manager のドキュメントは 3 つを並べていますが、同じページに、SSM Agent 3.3.40.0 以降は `ec2messages` のかわりに `ssmmessages` を使う、とも書いてあります。`ec2messages` を省ければ月に USD 20.44 減ります。ただ、endpoint を省いてよいとは書かれておらず、実機でも試していないので、この章は 3 つとも置いています。

EC2 は role をそのまま受け取れません。instance profile という入れ物に role を 1 つ入れて、それを instance に付けます。CDK の高水準の construct はこれを黙ってやってくれますが、何が作られているのかを見たかったので、自分で書きました。

`AmazonSSMManagedInstanceCore` は AWS が管理している policy です。中を読むと、対象はすべて `"Resource": "*"` で、`ssm:GetParameter` も入っています。つまり、この instance の中のプロセスは、アカウントの Parameter Store の値を読もうとすれば読めます。04章からずっと「`*` を使わない」で来ましたが、ここは AWS の policy をそのまま使うぶん、例外です。自分で足した権限は 1 つだけ。release を置く bucket の、`releases/` の下を読むことです。

### 認証情報はどこから来る？

instance の中の AWS CLI や SDK は、アクセスキーを設定しなくても動きます。どこから認証情報を取っているのでしょう。

答えは IMDS（Instance Metadata Service）です。instance の中からだけ届く `169.254.169.254` というアドレスがあって、そこに問い合わせると、role の一時認証情報が返ってきます。期限つきで、自動で入れ替わります。disk に鍵を置かなくて済むのは、このおかげです。

便利ですが、弱点もあります。instance の中で動くものなら、誰でもこのアドレスに聞けるんです。たとえば、ユーザーが指定した URL を取りに行く機能がアプリにあったら。URL に `http://169.254.169.254/...` を渡されると、アプリが認証情報を取ってきて、応答として返してしまうかもしれません。

IMDS には版が 2 つあります。v1 は、ただの GET で答えます。いまの攻撃がそのまま通ります。v2 は、先に PUT で token をもらって、それをヘッダーに付けて問い合わせる方式です。「URL を 1 つ GET させる」だけの穴では、PUT もヘッダーの追加もできません。さらに、`X-Forwarded-For` ヘッダーの付いた PUT は拒否されます。proxy 越しのリクエストを弾くためです。

<<< @/examples/23-ec2/infra/lib/ec2-stack.ts{instance}

`httpTokens: "required"` で v2 だけにしています。`httpPutResponseHopLimit` は、token の返事がネットワークを何段まで渡れるかです。1 なら instance 自身にしか届きません。中でコンテナを動かして、コンテナにも role を使わせたいときは 2 にします。Amazon Linux 2023 の AMI は、何も指定しなくても v2 必須、hop limit 2 で起動するそうですが、AMI やアカウントの既定値に頼らず、書いて固定しました。

v2 にしても変わらないことが 1 つあります。role は instance に 1 つで、中のプロセス全員の共有物です。`notes` という権限の低い user で動かしているノート API も、token を取る手順を踏めば、同じ認証情報を手にできます。instance の role に付けた権限は、その machine で動く全部のコードに付けた権限だと思ってください。

## AMI を選ぶ

<!-- section: 23.ami -->

AMI（Amazon Machine Image）は、instance の最初の disk の中身になる雛形です。この章は Amazon Linux 2023 の arm64 版を使います。

AMI には `ami-0123...` という ID があって、リージョンごとに違い、新しい版が出るたびに変わります。ID をコードに書くと、すぐ古くなります。そこで AWS は、「いちばん新しい AMI の ID」を Parameter Store の公開の parameter として配っています。

<<< @/examples/23-ec2/infra/lib/ec2-stack.ts{ami}

これを synth すると、template に `AWS::SSM::Parameter::Value<AWS::EC2::Image::Id>` という型の parameter が 1 つできます。値を引くのは deploy のときで、synth は AWS に何も聞きません。テストは、parameter の名前が `/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-arm64` であることと、synth が問い合わせを残さないことを見ています。

ここは 2 回つまずきました。固定した版（aws-cdk-lib 2.273.0）での話です。

まず、よく紹介される `MachineImage.latestAmazonLinux2023()` は、`kernel` を渡しても無視して、カーネル 6.1 用の parameter を引きます。Amazon Linux のドキュメントによると、`kernel-default` のほうは 2026 年 8 月から 6.18 になっています。次に、かわりに `AmazonLinux2023ImageSsmParameter` を直接使うと、今度は既定で synth のときに AMI を調べに行こうとして、アカウントを指定していない stack では synth が落ちます。`cachedInContext: false` が要ります。

### 「最新」は、作り直しの引き金

便利な仕組みですが、長生きする machine とは相性が悪いんです。

AMI の ID が変わると、instance は**置き換え**になります。CloudFormation のドキュメントでは `ImageId` の変更は Replacement で、cdkd のソースでも同じ扱いです。新しい AMI は頻繁に出ます。つまり、先月と同じコードを deploy しただけで、machine が新品に入れ替わることがあります。root volume の中身は、古い instance と一緒に消えます。CDK の型定義のコメントにも、この image を使うなら instance に状態を置くな、と書いてあります。

だから、この章は 2 つのことをしています。1 つは、消えて困るデータを root volume に置かないこと（「データは別の volume に」）。もう 1 つは、AMI を固定できるようにしたことです。

```bash
aws ssm get-parameter --region ap-northeast-1 --name /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-arm64 --query Parameter.Value --output text
vp run ec2:infra:deploy -c amiId=ami-xxxxxxxxxxxxxxxxx
```

1 行目で、いまの ID がわかります（認証情報が要ります）。それを `-c amiId=` で渡すと、template には ID がそのまま入って、あなたが変えるまで変わりません。練習なら「最新」のままで構いません。置きっぱなしにする machine なら、固定して、patch は自分の予定で当てます（「patch を当てる」）。

どちらにしても、deploy の前に `vp run ec2:infra:diff` を見る癖をつけてください。正直に言うと、cdkd の diff が、parameter の先の AMI の変化を置き換えとして見せてくれるのかは、確かめていません。

### user data の限界

便利ですが、頼りすぎると痛い目を見ます。

**走るのは 1 回だけ。** 最初の起動のときだけです。あとで script を直して deploy しても、動いている instance では走り直しません。cdkd のソースを読むかぎり、`UserData` の変更は instance に届きもしません。CloudFormation なら instance を再起動しますが、それでも script は走りません。machine の作りを変えたければ、instance を作り直すか、中に入って手で変えるかです。

**失敗に気づきにくい。** script が 5 行目で落ちても、instance は running のままです。EC2 から見れば、OS は立ち上がっているからです。この script は `set -euo pipefail` で、最初に失敗したところで止まるようにしてあります。半分だけ設定された machine より、止まった machine のほうが見つけやすいので。結果は `vp run ec2:status` で見られます。出力は instance の `/var/log/cloud-init-output.log` に残ります。

**16 KB まで。** いまの script は 4 KB ほどです。アプリのコードを詰め込む場所ではありません。

最後の点が、設計を決めています。user data が用意するのは machine までで、アプリは入れません。アプリは何度も入れ替えるものだからです。入れ替えの道は「デプロイして、入る」で作ります。

## 止めるときの作法

<!-- section: 23.shutdown -->

service は、止められることがあります。release のたびに再起動しますし、OS の再起動もあります。そのとき systemd は、プロセスに SIGTERM という signal を送ります。「止まってください」というお願いです。

何もしなければ、Node.js はその場で終了します。処理の途中だったリクエストは、応答をもらえないまま切られます。ノートを保存している最中だったら、呼んだ側には、保存されたのかどうかもわかりません。

<<< @/examples/23-ec2/src/shutdown.ts{shutdown}

お願いされたら、新しい接続を断って、処理中のリクエストを最後までやって、書き込みが disk に届くのを待って、それから終わる。これが graceful shutdown です。

```text
time  systemd                    notes process                         client
t0    systemctl restart   --->   SIGTERM received
t1                               listening socket closed               new connection: refused
t2                               request in flight finishes  --->      201 for the request sent before t0
t3                               pending file writes flushed
t4                               exit 0
t5    starts the new process     listening again                       connections accepted

if t2 has not happened 20 s after t0:  remaining connections closed, exit 1
if the process is still there 30 s after t0 (TimeoutStopSec):  systemd sends SIGKILL
```

## snapshot と restore

<!-- section: 23.backup -->

data volume は 1 つしかありません。壊れたら、ノートは全部なくなります。備えは snapshot です。ある時点の volume の写しで、S3 に置かれ、リージョンの中のどの AZ にも volume として復元できます。差分で保存されるので、2 回目からは変わったぶんだけです。

この節の手順も、コマンドの flag を devShell の AWS CLI の help で確かめただけです。

### 取る

```bash
vp run ec2:data:unmount
aws ec2 create-snapshot --region ap-northeast-1 --volume-id vol-xxxxxxxxxxxxxxxxx --description "notes before the upgrade"
vp run ec2:data:mount
```

volume の ID は、stack の output の `DataVolumeId` です。

書いている途中の volume を写すと、中途半端な状態が写ることがあります。なので、先に service を止めて unmount します。snapshot は、取り始めた時点の中身を写すもので、完了まで待つ必要はありません。状態が `pending` になったら、3 行目で mount し直して service を起こせます。その間、API は止まっています。

`ec2:data:mount` が実行するのは、最初の起動のときと同じ script です。format しない、という判断も同じです。

### 戻す

いちばん素直なのは、snapshot から volume を作るところを、stack にやらせる方法です。

```bash
vp run ec2:infra:deploy -c dataSnapshotId=snap-xxxxxxxxxxxxxxxxx
```

stack を消した後なら、これで instance と、snapshot の中身を持った volume ができます。最初の起動の script は、ファイルシステムがあるのを見て、format せずに mount します。あとは `vp run ec2:app:release` で、ノートが戻ってきます。AZ が使えなくなったときも同じで、11章の VPC が別の AZ に subnet を持っていれば、そちらに復元できます（この章の stack は 1 つ目の AZ に固定しているので、コードの変更は要ります）。

動いている stack に対して `dataSnapshotId` を足すのは、別の話です。CloudFormation のドキュメントでは、volume の `SnapshotId` は更新できない property です。cdkd のソースでは volume の置き換えになり、`--force-stateful-recreation` を付けないと拒否されます。古い volume が消える操作だからです。この経路は読んだだけで、動かしていません。

snapshot から作った volume は、最初のうち遅いことがあります。中身は、読まれたときに初めて S3 から運ばれてくるからです。

最後に、いちばん忘れやすいこと。snapshot は stack のリソースではありません。stack を消しても残って、料金がかかり続けます。「片付け」で確かめます。

## patch を当てる

<!-- section: 23.patch -->

Lambda では、OS の patch は AWS の仕事でした。ここでは、あなたの仕事です。

Amazon Linux 2023 には、知らないと驚く性質があります。instance は、AMI が作られた時点の package の版に**固定されています**。`dnf upgrade` と打っても、新しいものは何も来ません。勝手に security update が当たることもありません。先月と今月で、同じコマンドが同じ結果になる。そのための作りです。

つまり、何もしなければ、machine は起動した日のまま古くなっていきます。当て方は 2 つあります。

**その場で上げる。** 新しい版が出ているかを調べて、版を名指しで上げます。

```bash
vp run ec2:patch:check
vp run ec2:patch:apply 2023.12.20260930
```

2 行目の引数は、1 行目が表示した版です。`latest` は受け付けません。Amazon Linux のドキュメントも、`latest` を指定するのは、試していない更新を本番でいきなり試すことになる、と書いています。カーネルが更新されたら、再起動するまで古いカーネルで動き続けます。`aws ec2 reboot-instances` で再起動してください。その間、API は止まります。

**作り直す。** 新しい AMI で instance を置き換えます。「AMI を選ぶ」の `-c amiId=` を新しい ID にして deploy するだけです。user data が最初から走り、data volume は付け直され、release をもう一度入れます。手で触った跡が何も残らないので、こちらのほうが結果を予想しやすい。Amazon Linux のドキュメントも、この方法を勧めています。

ただ、こちらにはわかっていないことがあります。置き換えのとき、volume attachment がどう動くのかを、cdkd のソースから読み切れませんでした。古い instance から外して新しい instance に付ける、という順序を cdkd がやってくれるのか、途中で失敗するのか。実機で試すまで、この経路は「できるはず」です。試すときは、先に snapshot を取ってください。

Systems Manager には Patch Manager という機能もあります。足りない patch を調べる、当てる、当たっているかを一覧にする。台数が増えたら、こちらが要ります。1 つ注意があって、ドキュメントによると、Patch Manager は Amazon Linux 2023 の版の固定を見ずに、いつも最新の repository を使います。この章では設定していません。

### 作り直せるようにしておく、という考え方

「作り直す」を突き詰めると、Auto Scaling group になります。instance の作り方（launch template）と台数を渡しておくと、instance が不健康になったときに、新しいものに置き換えてくれます。台数を 1 にしておけば、「常に 1 台いる」を AWS に任せられます。

この章では作っていません。理由は、置き換えが自動で起きるなら、置き換えのたびに必要なことも全部自動でなければならないからです。data volume の付け直し、release の入れ直し。いまの構成では、その 2 つに人の手が要ります。そこまで自動にする価値があるかは、次の節の話と一緒に決めることです。

### 長生きする machine で、あなたが持つもの

- **OS と runtime の patch。** Node.js も OS の package です。同じ道で上がります
- **disk の空き。** journald のログと、`/opt/notes/releases` の古い版は、放っておくと増えます。消すのはあなたです
- **コードと実物のずれ。** session で入って手で直したものは、どこにも記録されません。次に作り直した machine には、その修正がありません。drift の検査が見るのは AWS のリソースの設定で、OS の中までは見ません
- **backup。** 取っているだけでなく、戻せること

## 1 台は単一障害点

<!-- section: 23.spof -->

この章の構成で、状態を持っているのは 1 か所です。1 つの AZ の、1 つの volume の、1 つのファイル。それを 1 つのプロセスが読み書きしています。

何が起きたら、何が止まって、何が戻るのか。並べてみます。

```text
event                              API stops for        comes back by itself?                      the notes
process crashes                    about 2 s            yes: systemd, Restart=on-failure           kept
release, or a restart              a few seconds        yes: part of the same command              kept
OS hangs, kernel panics            until you act        no: the instance status check fails        kept
host hardware fails                minutes (unmeasured) usually: automatic recovery, same instance kept; memory is lost
instance terminated or replaced    until you redeploy   no: deploy again, then release again       kept: the volume is its own resource
data volume lost or damaged        until you restore    no: restore from a snapshot                back to the last snapshot
zone ap-northeast-1a impaired      as long as it lasts  no: this stack has nothing in another zone unreachable until the zone is back
```

上の 2 行は、この章で作ったものが面倒を見ます。

4 行目は、EC2 が見てくれます。EC2 は 1 分ごとに status check という検査をしていて、AWS の側の基盤（電源、ネットワーク、物理的な host）に問題があると、automatic recovery が instance を別の hardware に移します。この機能は、対応している instance では最初から有効です。instance の ID も、IP アドレスも、付いている volume も、AZ も同じまま。失われるのはメモリの中身だけです。ノート API にとっては、再起動と同じです。

ただ、これに頼りすぎないでください。recovery が動くのは、基盤の検査が落ちたときだけです。3 行目のように OS の中で固まった場合は、もう一方の検査（instance status check）が落ちますが、こちらは何もしてくれません。直すのはあなたです。それに、移る先の hardware に空きがないときや、AWS Health Dashboard に障害の event が出ている間は、recovery は動きません。大きな障害のとき、つまりいちばん助けてほしいときに、当てにできないわけです。

5 行目からは、人が動きます。夜中なら、朝まで止まっています。

### 1 台を受け入れる条件

だから「1 台はダメ」とは言いません。多くの用途には、1 台で十分です。ただ、受け入れるなら、条件を言葉にしておきましょう。

1. **止まっていてよい時間が、人が気づいて直すまでの時間より長い。** 数分から数時間、止まります。夜中と休日を含めて
2. **最後の snapshot まで戻ってよい。** あるいは、データをほかから作り直せる
3. **止まったことに、誰かが気づく。** 気づく仕組みが無ければ、1 の時間は無限です
4. **作り直す手順を、一度は通してある。** 初めて restore するのが障害の当日、というのは避けたい

4 つとも「はい」と言えるなら、1 台は正しい選択です。安くて、単純で、何が起きているかを全部見渡せます。

言えないなら、2 台目が要ります。別の AZ に、です。ここで気づくことがあります。この章の構成は、そのままでは 2 台にできません。ノートが片方の machine のファイルにあるからです。2 台にするには、状態を machine の外（05章の DynamoDB や、13章のデータベース）に出して、前に load balancer を置くことになります。そこまでやると、machine を自分で持っている理由が、だいぶ減ります。同じことを、12章の Fargate はもっと少ない手間でやってくれます。

EC2 を 1 台で使うのは、「machine の中に状態を置きたい、そして 1 台ぶんの信頼性でよい」ときです。24章の celld は、その先、つまり machine の中に状態を置いたまま複数台にする話です。

### テストが固定していること

この節の invariant は、前の節と同じ 1 文です。201 を返したノートは、プロセスが再起動しても、instance が作り直されても、読める。図の 1 行目、2 行目、5 行目が、これにあたります。`test/file-notes.test.ts` が書き込みの途中の停止で、`test/data-volume.test.ts` が instance の作り直しで、それを壊しに行きます。

守れないことも、テストにしてあります。`test/access.test.ts` は、11章の経路のモデルで instance のいる AZ を落として、instance がどこにも届かなくなることを見ています。「AZ が 1 つ止まっても API は応答する」は、この構成では成り立ちません。成り立たないことを、成り立たないと書いたテストです。

どのテストも、壊しているのはモデルと偽物の disk です。本物の instance を落としたわけではありません。

## Lambda、Fargate、EC2

<!-- section: 23.compare -->

同じ API を、3 つの場所に置けるようになりました（Fargate は [12章](/ja/chapters/12-containers.md)です）。並べてみます。

| | Lambda（04章） | Fargate（12章） | EC2（この章） |
| --- | --- | --- | --- |
| 動いているもの | 呼ばれたときだけの実行環境 | 動かし続けるコンテナ | 動かし続ける machine |
| 1 回の処理の長さ | 最長 15 分 | 決まりなし | 決まりなし |
| 誰も呼ばないときの料金 | 0 | かかる | かかる。止めても volume はかかる |
| カーネル | 触れない | 触れない | 自分のもの |
| 手元の disk | `/tmp`。実行環境ごとの一時的なもの | task ごとの一時的なもの（既定 20 GiB） | EBS volume。instance より長く残せる |
| OS の patch | AWS | host は AWS。image の中身は自分 | 全部自分 |
| 落ちたら | 次の呼び出しで新しい環境 | service が task を作り直す | systemd がプロセスを起こす。その先は自分 |

選び方は、上から順に考えるのがいいと思います。Lambda で済むなら Lambda。15 分に収まらない、つなぎっぱなしにしたい、なら Fargate。それでも足りないもの、つまりカーネル、hardware、machine の中の disk が要るときに、EC2 です。

下に行くほど、できることが増えて、やることも増えます。EC2 がいちばん自由なのは本当ですが、いちばん高機能という意味ではありません。自分でやる範囲がいちばん広い、という意味です。

Fargate の「かかる」に金額を入れていないのは、この章では単価を確かめていないからです。金額は [12章](/ja/chapters/12-containers.md)の「お金の話」にあります。

## 本番にするなら

- **1 台でよいかを決める。** 「1 台を受け入れる条件」の 4 つに答える。答えが「いいえ」なら、この章の構成ではありません
- **データを stack と一緒に消さない。** `-c dataOnDestroy=snapshot` か `retain`。そして snapshot を定期的に取り、restore を一度通しておく
- **AMI を固定して、patch の予定を持つ。** 「最新」のままだと、置き換えの日を AWS の release が決めます
- **ログと metrics を machine の外に出して、アラームを付ける。** machine が消えたときに、理由も一緒に消えないように（アラームの組み立て方は [19章](/ja/chapters/19-observability.md)）
- **誰が入れるかを絞る。** `ssm:StartSession` と `ssm:SendCommand` を持つのは誰か。session の記録も残せます
- **API を公開するなら、load balancer を前に置く。** instance の port を直接開けない（[12章](/ja/chapters/12-containers.md)）
- **instance の role を見直す。** `AmazonSSMManagedInstanceCore` は Parameter Store を広く読めます。置いているものを確かめる
- **終了保護を付ける。** instance には、API からの terminate を拒否する設定があります
- **反映の経路を AWS CDK CLI と CloudFormation にする。** cdkd の公式ドキュメントは、cdkd を開発・テスト用途向けとし、本番には AWS CDK CLI を勧めています（02章）
- **支出の通知を付ける。** 01章の budget は、instance を消し忘れたときに気づくための最後の網です。上限ではなく、通知です

## 片付け

<!-- section: 23.cleanup -->

順番があります。

```bash
vp run ec2:data:unmount
vp run ec2:releases:empty --yes
vp run ec2:infra:destroy
vp run net:infra:destroy
```

1 行目は、data volume を外せる状態にします。2 行目は、release 用の bucket を空にします。固定した版の cdkd は、空でない bucket を消しません（`--yes` を付けなければ、一覧を出すだけです）。3 行目で、instance、volume、bucket、role が消えます。ノートも消えます。4 行目で、VPC と interface endpoint が消えます。VPC を残したいなら、`vp run net:infra:deploy` を `-c` なしで実行すれば、endpoint だけ外せます。

3 行目だけで終わりにすると、endpoint の料金（月に USD 61.32）が続きます。この章でいちばん高い部品は、この章の stack の外にあります。

消えたことを、自分の目で確かめましょう。

```bash
aws ec2 describe-instances --region ap-northeast-1 --filters Name=instance-state-name,Values=pending,running,stopping,stopped
aws ec2 describe-volumes --region ap-northeast-1
aws ec2 describe-snapshots --region ap-northeast-1 --owner-ids self
aws ec2 describe-vpc-endpoints --region ap-northeast-1
```

1 つ目と 2 つ目が空で、4 つ目に Interface 型の endpoint が無ければ、時間課金は止まっています。3 つ目に snapshot が残っていたら、それは自分で取ったものか、`dataOnDestroy=snapshot` が残したものです。要らなければ `aws ec2 delete-snapshot` で消します。`dataOnDestroy=retain` にしていた場合は、2 つ目に volume が残ります。

残るのは、cdkd の bootstrap で作った保存場所（02章）だけです。

**手元で確かめたこと。** ユニットテスト（file に書く repository を書き込みの各段階で止めるテスト、本物の socket での SIGTERM、unit と user data の生成と injection の拒否、data volume の script を bash で実行するテスト、Run Command の引数、経路のモデル、料金の入力、stack の assertion）。型検査。`ec2:infra:synth`（既定、`-c placement=public`、`-c dataOnDestroy=snapshot`、`-c dataSnapshotId=snap-0123456789abcdef0`、`-c amiId=ami-0123456789abcdef0`）。`ec2:plan`（既定、`placement=public`、endpoint の足りない設定、不正な設定）。`ec2:render`。`ec2:app:build`。ビルドした `dist/server.mjs` と `src/server.ts` を Node.js 24 で起動して、作成、一覧、再起動の後も残ること、SIGTERM で exit code 0 で終わること、壊したファイルでは起動しないこと。本文の金額は、Price List の単価から `tools/src/pricing/calc.ts` が計算した値で、`examples/23-ec2/test/pricing.test.ts` が照合しています。本文に出てくる AWS CLI の flag は、devShell の AWS CLI 2.35.11 の help で確かめました。

一次情報で確かめられなかったこと。Amazon Linux 2023 の repository に S3 の gateway endpoint だけで届く、と書いたページは見つかりませんでした。`ec2messages` の interface endpoint を省いてよいかも、権限の話としてしか書かれていません。Amazon Linux 2023 の AMI の root volume の大きさと device 名は確認しておらず、そのため root volume の設定には手を入れていません（暗号化も、アカウントの既定に従います）。EC2 と EBS の無料利用枠が、どのアカウントにいつまで当てはまるかも確認できませんでした。systemd の directive は v252 の man page で読みましたが、Amazon Linux 2023 が積んでいる版は見ていません。Cloudflare に仮想マシンに当たる体験があるかは調べておらず、比較は書いていません。Fargate の単価も調べていません。

cdkd が扱うリソースの種類。`v0.296.28` タグの `src/provisioning/register-providers.ts` では、`AWS::EC2::Instance` と `AWS::EC2::SecurityGroup` が EC2 の provider に、`AWS::IAM::InstanceProfile`、`AWS::IAM::Role`、`AWS::IAM::Policy`、`AWS::S3::Bucket`、`AWS::S3::BucketPolicy` がそれぞれ専用の実装に登録されています。`AWS::EC2::Volume`、`AWS::EC2::VolumeAttachment`、`AWS::EC2::LaunchTemplate` は登録が無く、Cloud Control API 経由です（volume の削除だけは、cdkd が EC2 の `DeleteVolume` を直接呼びます）。この章は launch template を使っていません。CDK の `Instance` に `requireImdsv2` を渡すと launch template が作られますが、`CfnInstance` の `metadataOptions` なら instance の property だけで済み、cdkd の専用の実装がそれを書き込みます。専用の実装が書き込まない property を template が使うと、そのリソースは Cloud Control API に回される仕組みなので、テストで property の一覧を固定しています。ソースからは、`UserData` の変更が instance に反映されないこと、`ImageId`、`SubnetId`、`NetworkInterfaces` の変更が置き換えになること、SSM 型の parameter は参照されているものだけ deploy 時に `GetParameter` で解決されることも読み取りました。
