# 23 VM: EC2、SSM、EBS、プロセス運用

ここまでの章では、サーバーを 1 台も持ちませんでした。Lambda は呼ばれたときだけ動き、OS の面倒は AWS が見ています。この章では反対に、OS ごと自分で持ちます。

作るのは EC2 のインスタンス、つまり仮想マシン 1 台です。SSH のポートは開けません。[04章](/ja/chapters/04-http-api.md)のノート API を systemd のサービスとして動かし、ノートはインスタンスとは別のディスクに置きます。

この章で作るものは、**置いてあるだけで時間単位の料金がかかります**。既定の構成ではおよそ 1 日 USD 2.33、1 か月（730 時間）置いたままにすると USD 70.74 で、インスタンスを止めても USD 62.86 かかり続けます。安いほうの構成なら 1 日 USD 0.43、1 か月 USD 13.07 です。内訳はこのページの「置いてあるだけでかかる料金」に書きました。試したら、その日のうちに[片付け](/ja/chapters/23-ec2/wrap.md)まで進めてください。

前提は [11章](/ja/chapters/11-network.md)の VPC です。コードは `examples/23-ec2/` にあります。

## EC2 を選ぶ場面

<!-- section: 23.why -->

04章の Lambda で足りているなら、EC2 は要りません。Lambda は使っていない間の料金が 0 で、パッチも AWS が当てるので、これより手のかからない置き場所はなかなかありません。

それでもマシンを 1 台持ちたくなるのは、次のような場合です。

- **プロセスを長く動かしたい。** Lambda の 1 回の実行は最長 15 分なので、何時間も接続を持ち続けたり、メモリに大きなインデックスを載せたままにしたりする使い方には向きません
- **OS やカーネルを触りたい。** カーネルのパラメーター、ファイルシステム、ネットワークの細かい設定を変えたい場合です。Lambda にも Fargate にも、利用者が触れるカーネルはありません
- **特殊なハードウェアが要る。** GPU、大きなメモリ、インスタンスに直接つながった高速なディスクなどです
- **マネージドサービスに無いソフトウェアを動かしたい。** 自分で運用するデータベースやデーモンがこれに当たります。24章の celld もその 1 つです

そのかわり、これまで AWS がしていた次の仕事を、自分で引き受けることになります。

- OS とランタイムにパッチを当てる
- プロセスが落ちたことに気づき、起こし直す
- ディスクがあふれないように見張り、壊れたときに戻す
- マシンが起動したときに、何をどの順で立ち上げるかを決める
- その 1 台が止まれば全部が止まることを、引き受ける

この章では、この 5 つを順に扱います。最後の 1 つだけは解決できないので、[1 台は単一障害点](/ja/chapters/23-ec2/wrap.md)の節に、1 台で運用してよい条件を書きました。

## 置いてあるだけでかかる料金

<!-- section: 23.cost -->

金額は USD で、東京リージョンの従量課金の定価、税別です。1 か月は 730 時間として計算しています。計算の中身は[料金の計算](/ja/reference/pricing.md)にあります。

| 構成 | 動かしている 1 日 | 動かしている 1 か月 | 止めている 1 日 | 止めている 1 か月 |
| --- | --- | --- | --- | --- |
| 既定（プライベートサブネット） | 2.33 | 70.74 | 2.07 | 62.86 |
| `-c placement=public` | 0.43 | 13.07 | 0.05 | 1.54 |

内訳は次のとおりです。

- インスタンス: `t4g.micro`（2 vCPU、1 GiB）が 1 時間 USD 0.0108 で、730 時間では 7.88
- ボリューム: gp3 が 1 GB・1 か月あたり USD 0.096。ルートボリュームの 8 GiB とデータ用の 8 GiB を合わせて 1.54。ルートボリュームの大きさは AMI が決めるもので、8 GiB は仮定です（実機で確かめていません）
- パブリック IPv4 アドレス（`placement=public` のときだけ）: 1 時間 USD 0.005 で、730 時間では 3.65
- インターフェースエンドポイント（interface endpoint。既定の構成のときだけ）: 1 つ・1 AZ あたり 1 時間 USD 0.014。3 つを 2 つの AZ に置くので、730 時間で 61.32

この表で先に知っておきたいのは、インスタンスを止めてもボリュームの料金が続くことです。停止（stop）で止まるのはインスタンスの料金だけで、ディスクは中身ごと残っているので、その置き場所の料金がかかり続けます。使わないときに止めておいても、0 にはなりません。

既定の構成では、料金のほとんどをエンドポイントが占めます。しかもエンドポイントは 11章のスタックのリソースなので、この章のインスタンスを止めても消しても、課金は止まりません。それでも既定にした理由は、[SSH のポートは開けない](/ja/chapters/23-ec2/build.md)の節に書きました。

パブリック IPv4 アドレスの料金は、アドレスの種類によって変わります。この章の `placement=public` が使うのは、起動のたびに自動で割り当てられるアドレスです。インスタンスを止めると手放されて課金も止まり、次に起動すると別のアドレスになります。アドレスを固定するために Elastic IP アドレスを使うと、インスタンスを止めている間も課金されます。この章は Elastic IP アドレスを使っていません。

表に出てこない料金が、もう 1 つあります。`t4g` のような T 系のインスタンスは、普段は CPU を控えめに使い、貯めた CPU クレジットを使って一時的に全力を出します。何も指定しないと unlimited という設定で起動し、クレジットを使い切っても全力で走り続けられるかわりに、超えた分が 1 vCPU・1 時間あたり USD 0.04 で課金されます。プロセスが暴走すれば、それがそのまま請求になります。この章のスタックは standard にしてあるので、クレジットが尽きると遅くなるだけで、請求は増えません。

デプロイする前に、手元で金額を出せます。AWS のアカウントは要りません。

```bash
vp run ec2:plan
vp run ec2:plan placement=public
```

この表には、データ転送、スナップショット（1 GB・1 か月あたり USD 0.05）、リリースを置く S3 バケットの料金を入れていません。0 という意味ではなく、未算入です。Session Manager と Run Command は、EC2 のインスタンスに対して使うかぎり追加料金がありません。EC2 と EBS には無料利用枠の記述がありますが、読者のアカウントに当てはまるかを確かめられないので、差し引いていません。

## 全体像

<!-- section: 23.architecture -->

```figure
caption: 利用者もインスタンスも自分から Systems Manager と S3 に接続し、外からインスタンスに入る矢印は 1 本もない
type: sequence
actor you: Your machine | 自分の IAM identity
actor ssm: Systems Manager | ap-northeast-1
actor inst: EC2 インスタンス | VPC AihNetwork
actor s3: S3 バケット | releases
step inst -> ssm: HTTPS 443 (SSM Agent)
step you -> ssm: send-command (HTTPS)
step you -> ssm: start-session (HTTPS)
step you -> s3: aws s3 cp
step inst -> s3: 自分のロールで読む
```

```figure
caption: インスタンスから Systems Manager と S3 への経路は、プライベートでは VPC エンドポイント、パブリックではインターネットゲートウェイを通る
node inst: EC2 インスタンス | VPC AihNetwork (11章), zone ap-northeast-1a
node vpce: VPC endpoints (11章のスタック) | ssm, ssmmessages, ec2messages, S3 gateway
node igw: Internet gateway | インスタンスのパブリック IPv4 アドレス
node ssm: Systems Manager
node s3: S3 バケット | releases
edge inst -> vpce: Private1 (既定)
edge inst -> igw: Public1 (-c placement=public)
edge vpce -> ssm
edge vpce -> s3
edge igw -> ssm
edge igw -> s3
```

```figure
caption: インスタンスには、インバウンドの規則がないセキュリティグループ、権限を 2 つに絞ったロール、IMDSv2 の設定が付く
node inst: EC2 インスタンス AihEc2/instance | t4g.micro, Amazon Linux 2023 arm64
node sg: Security group | インバウンドなし, アウトバウンド tcp 443
node role: インスタンスプロファイルのロール
node imds: IMDSv2 | 必須, hop limit 1
node core: AmazonSSMManagedInstanceCore
node get: s3:GetObject | releases/*
edge inst -> sg
edge inst -> role
edge inst -> imds
edge role -> core
edge role -> get
```

```figure
caption: プログラムとサービスはインスタンスと一緒に消えるルートボリュームに、ノートは別のリソースであるデータボリュームにある
node inst: EC2 インスタンス AihEc2/instance
node root: ルートボリューム | AMI から, インスタンスと一緒に消える
node data: データボリューム AihEc2/data | 8 GiB gp3, encrypted, 同じ zone
node current: /opt/notes/current | releases/<version>/server.mjs
node service: notes.service | systemd, user notes, 127.0.0.1:8787
node notes: /var/lib/notes/notes.json
edge inst -> root
edge inst -> data
edge root -> current
edge root -> service
edge data -> notes
```

図は 4 つあり、上から順に、誰が誰に接続するか、その通信がどの経路を通るか、インスタンスに何の設定が付くか、ファイルがどのボリュームにあるかを表しています。

1 つ目の図には、外からインスタンスに入る矢印が 1 本もありません。利用者が接続する相手は Systems Manager で、インスタンスも自分から Systems Manager に接続しに行きます。ノート API も、インスタンスの中の `127.0.0.1` でしか待ち受けません。
