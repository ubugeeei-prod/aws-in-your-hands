# 59 RDS: デプロイ

ここまでは手元の話でした。このページでは、スタックをデプロイしてデータベースを使えるようにする手順と、動かし続けるあいだに起きること（バックアップ、バージョンアップ、監視）を扱います。このページの手順は、まだ一度も実際の AWS で通せていません。

## デプロイして、使えるようにする

<!-- section: 59.deploy -->

ここからは AWS を変更し、時間単位の課金が始まります。先に、11章の VPC を既定の構成でデプロイしておきます（`vp run net:infra:deploy`）。

```bash
vp run rds:infra:diff
vp run rds:infra:deploy
```

インスタンス、パラメーターグループ、サブネットグループ、セキュリティグループ、関数 2 つ、API、アラームができます。この時点のデータベースには、マスターユーザーと空の `notes` データベースしかありません。

```bash
vp run rds:db:bootstrap
vp run rds:db:migrate
vp run rds:db:status
```

`rds:db:bootstrap` は、あなたの認証情報でマスターユーザーのシークレットを読み、運用用の関数を呼んで、`notes_migrator` と `notes_api` を作ります。`secretsmanager:GetSecretValue` と `lambda:InvokeFunction` が要ります。`rds:db:migrate` は 13章の 4 つのマイグレーションを流し、`notes_api` に権限を渡します。どちらも、2 回実行して困ることはありません。`rds:db:status` は、つないだロール、PostgreSQL の版、接続が TLS かどうかを表示します。

```bash
vp run rds:smoke
```

API を通して、作成、読み戻し、削除を確かめます。ログを見るタスクは、この章には用意していません。スタックの出力にあるロググループの名前を使って、CloudWatch Logs で見てください。ドリフトの検査は `vp run rds:infra:drift` です。

リードレプリカを付けるときは、コンテキストを足します。インスタンスが 2 台になり、料金もおよそ 2 倍になります。

```bash
vp run rds:infra:deploy -c readReplica=true
```

### デプロイで止まりそうなところ

実機で確かめていないので、止まりそうな場所を先に書いておきます。

PostgreSQL の版は、スタックが `18.3` に固定しています。固定している CDK（aws-cdk-lib 2.273.0）が知っているいちばん新しい版です。RDS は古いマイナーバージョンを新しいインスタンスに出さなくなるので、この版が選べなくなっている可能性があります。そのときは、選べる版を調べて指定します。

```bash
aws rds describe-db-engine-versions --engine postgres --query 'DBEngineVersions[].EngineVersion'
vp run rds:infra:deploy -c postgresVersion=<版>
```

固定している版の cdkd（0.296.28）は、`AWS::RDS::DBInstance`、`AWS::RDS::DBSubnetGroup`、セキュリティグループ、アラームに専用の実装を持っています。`AWS::RDS::DBParameterGroup` には無く、Cloud Control API 経由で扱います。Cloud Control API の対応一覧にこの種類が載っていることは確かめましたが、作成と削除が実際に通るかは未確認です。

マイナーバージョンの自動アップグレードを有効にしているので、しばらくすると実際の版はテンプレートの `18.3` より新しくなります。このずれを cdkd のドリフト検査がどう報告するかも、確かめていません。

## バックアップとリストア

<!-- section: 59.backup -->

22章は、DynamoDB と S3 のデータを AWS Backup で守りました。RDS は、自分で自動バックアップを持っています。

自動バックアップは 2 つの部分からできています。1 日 1 回、バックアップウィンドウの中で取るボリューム全体のスナップショットと、5 分ごとに S3 に送られるトランザクションログです。この 2 つを組み合わせて、保持期間の中の好きな時刻の状態に戻せます。これがポイントインタイムリストアです。いちばん新しく戻せる時刻は `LatestRestorableTime` として見えます。ログが送られるのが 5 分ごとなので、現在の少し手前までです。

Single-AZ のインスタンスでは、バックアップの開始時に、ストレージの I/O が短く止まることがあります（ドキュメントの表現では、ふつう数秒未満）。Multi-AZ では、バックアップは待機系から取られるので、プライマリは止まりません。

13章の DSQL のところで書いたことは、RDS にも当てはまります。リストアは、元のインスタンスを巻き戻しません。常に**新しいインスタンス**を作ります。

そのため、戻したあとに 3 つの作業が残ります。新しいインスタンスはエンドポイントが違うので、アプリの接続先を変えます。パラメーターグループは、指定しなければ既定のものが付くので、付け直します。セキュリティグループも指定します。そして、新しいインスタンスはこの章のスタックの外にあります。スタックに戻す方法は、この章では用意していません。リストアの手順を一度も通していない仕組みは、戻せるとは言えない、というのが 22章の結論でした。RDS でも同じです。

自動バックアップとは別に、手動のスナップショットがあります。違いは寿命です。自動バックアップは保持期間が過ぎると消え、インスタンスを消すと、残す指定をしないかぎり一緒に消えます。手動のスナップショットは、自分で消すまで残り、インスタンスを消しても残ります。`production` のプロファイルは、スタックを消してもインスタンスと自動バックアップを残す設定にしています。

バックアップの置き場所の料金は、そのリージョンのデータベースのストレージの合計と同じ量までは無料です。20 GB のインスタンスなら 20 GB までです。保持期間を延ばしたり手動のスナップショットをためたりして超えた分は、1 GB 月あたり USD 0.095 です。

## バージョンを上げる

<!-- section: 59.upgrade -->

RDS は、放っておいても変わっていきます。変わる時刻を決めるのがメンテナンスウィンドウで、何が変わるかは次の 3 つです。

**OS の更新。** 必須の更新は、期日を過ぎるとメンテナンスウィンドウの中で適用され、そのあいだインスタンスは止まります。ドキュメントによれば、ふつう 10 分ほどです。Multi-AZ では、先に待機系を更新し、待機系をプライマリに昇格させてから、元のプライマリを更新します。止まるのはフェイルオーバーの時間だけになります。

**マイナーバージョン。** 18.3 から 18.6 のような、互換性を保った更新です。自動アップグレードを有効にしておくと、RDS が自動適用の対象に決めた版が、メンテナンスウィンドウの中で入ります。このときもインスタンスは止まります。Multi-AZ でも短くはなりません。エンジンの更新では、プライマリと待機系が同時に上げられるからです。

**メジャーバージョン。** 18 から 19 のような、互換性が保証されない更新です。自動では上がりません。自分で始め、そのあいだは止まり、終わったら元の版には戻せません。RDS は `pg_upgrade` を使い、自動バックアップが有効なら、途中で 2 回スナップショットを取ります。拡張は一緒には上がらないので、自分で `ALTER EXTENSION ... UPDATE` を流します。統計情報も引き継がれないので、`ANALYZE` を流します。パラメーターグループは版の系列ごとなので、この章の `postgres18` 用のグループとは別に、新しい版用のグループを先に用意します。

メンテナンスウィンドウは、作業が**始まる**時刻を決めるだけです。30 分の枠でも、作業がそれより長くかかれば、枠を過ぎても続きます。

### blue/green deployment

メジャーバージョンの更新で止まる時間を短くする仕組みが、blue/green deployment です。いまの環境（blue）の複製（green）を RDS が作り、レプリケーションで同期させ続けます。green の側で版を上げて確かめたあと、切り替えます。切り替えで止まる時間は、ドキュメントによればふつう 1 分未満で、エンドポイントの名前は green が引き継ぐので、アプリの設定は変わりません。

この章のスタックでは、そのままでは使えません。理由は 2 つあります。マスターユーザーのパスワードを RDS に管理させているインスタンスには使えないことと、blue/green deployment が CloudFormation に対応していないことです。使うなら、コンソールか CLI で、スタックの外の操作として行うことになり、切り替えのあとの実物はテンプレートと食い違います。その整理のしかたは、この章では確かめていません。

### 標準サポートの終わりと Extended Support

メジャーバージョンには、RDS が標準サポートを終える日が決まっています。2026-10-13 に見たリリースカレンダーでは、次のとおりでした。

| メジャーバージョン | RDS の標準サポートの終了 |
| --- | --- |
| 14 | 2027-02-28 |
| 15 | 2028-02-29 |
| 16 | 2029-02-28 |
| 17 | 2030-02-28 |
| 18 | 2031-02-28 |

13 はすでに 2026-02-28 に終わっています。

終了日を過ぎたインスタンスがどうなるかは、作るときの設定で決まります。CLI、API、CloudFormation では、何も指定しないと RDS Extended Support に入る設定になります。Extended Support は、古い版を最長 3 年使い続けられる代わりに、vCPU 1 つにつき 1 時間いくらの追加料金がかかる仕組みです。

その単価が、インスタンスの料金とは桁が違います。Price List に載っている PostgreSQL 13 の単価は、1〜2 年目が 1 vCPU 時間あたり USD 0.12、3 年目が USD 0.24 です。2 vCPU の db.t4g.micro に当てはめると、1 か月で USD 175.20、3 年目は USD 350.40 になります。インスタンスそのものは USD 18.25 です。Multi-AZ なら、待機系の vCPU にもかかります。

この章のスタックは、Extended Support に入らない設定（`open-source-rds-extended-support-disabled`）にしてあります。この設定のインスタンスは、標準サポートが終わると、RDS によって次の版へ自動で上げられます。料金は増えませんが、メジャーバージョンの更新が、自分で選んでいない時刻に起きます。どちらも避けるには、終了日より前に自分で上げます。カレンダーの日付を、チームの予定に入れておいてください。

ストレージがいっぱいになると、インスタンスは `storage_full` という状態になり、自動バックアップも取られなくなります。アラームは、残りが 4 GiB を切った状態が 15 分続いたら鳴ります。通知先は付けていないので、鳴っても誰にも届きません。届け方は [19章](/ja/chapters/19-observability.md)にあります。

ストレージを自動で増やす設定もあります。上限（`maxAllocatedStorage`）を決めておくと、残りが割り当ての 10% 以下の状態が 5 分続いたときに、RDS がストレージを増やします。増える量は、10 GiB、いまの 10%、直近の減り方から見た 7 時間分の 3 つのうち、いちばん大きいものです。増やせるのは 24 時間に 4 回までです。`production` のプロファイルは上限を 100 GiB にしています。練習用で切ってあるのは、増えたストレージは減らせず、料金が上がったままになるからです。

ほかに見ておくメトリクスは、接続の数（`DatabaseConnections`）、db.t のクラスなら CPU クレジットの残り（`CPUCreditBalance`）と超過分（`CPUSurplusCreditBalance`）、レプリカがあれば `ReplicaLag` です。`ReplicaLag` は秒で、レプリカが最後に再生したトランザクションの時刻と、いまの時刻の差です。プライマリに書き込みが無いあいだは、遅れていなくても最大 5 分まで増えて見えます。

遅い文は、ログで見ます。パラメーターグループの `log_min_duration_statement` で、500 ミリ秒以上かかった文がロググループ `/aws/rds/instance/aih-notes/postgresql` に書かれます。ログには文そのものが残ります。値を SQL の文字列に埋め込んでいれば、値も残ります。

どの文がデータベースの時間を使っているかを見る道具は、名前が変わりました。以前の Performance Insights は 2026-07-31 に提供を終え、CloudWatch Database Insights に引き継がれています。Standard と Advanced の 2 つのモードがあり、ドキュメントによれば、Standard は既定で有効で、7 日分の履歴までは無料です。CloudFormation のプロパティは、以前の名前（`EnablePerformanceInsights`）のまま残っています。この章のスタックは、このプロパティに何も指定していません。デプロイしたインスタンスでどう設定されるかは、確かめていません。
