# 59 RDS: 実装のつづき

[前のページ](/ja/chapters/59-rds/build.md)で、インスタンスを 1 台置き、そこへつなぐところまで作りました。このページでは、インスタンスを 2 台以上にしたときに何が起きるかを扱います。待機系を持つ話と、読み取りを別のインスタンスに逃がす話は、似て見えて別のものです。

## 待機系を持つ: Multi-AZ の 2 つの形

<!-- section: 59.multi-az -->

Single-AZ のインスタンスは、1 つの Availability Zone の 1 台です。そのホストやボリュームが壊れると、RDS が復旧させるまで API は止まります。AZ ごと使えなくなれば、その間ずっと止まります。

RDS は、これに対して 2 つの構成を用意しています。名前が似ているので、表で並べます。

| | Single-AZ | Multi-AZ DB instance | Multi-AZ DB cluster |
| --- | --- | --- | --- |
| インスタンス | 1 台 | プライマリと待機系 | 書き込み用 1 台と読み取りもできる 2 台 |
| 複製のしかた | なし | 同期 | 準同期。2 台のうち 1 台の確認でコミット |
| 待機系から読めるか | | 読めない | 読める。ただし遅れることがある |
| フェイルオーバーの時間（ドキュメントの記述） | | ふつう 60〜120 秒 | ふつう 35 秒未満 |
| 止められるか | 7 日まで | 7 日まで | 止められない |
| いちばん小さい構成の 1 か月 | USD 18.25 | USD 36.50 | USD 239.37 |

金額はインスタンスの分だけで、ストレージは含みません。Multi-AZ DB instance は、インスタンスもストレージも単価がちょうど 2 倍です。Multi-AZ DB cluster は使えるインスタンスクラスが限られていて、いちばん小さいものが db.c6gd.medium です。

Multi-AZ DB instance の待機系は、別の AZ にあって、プライマリと同期して書かれます。コミットが成功したと返った書き込みは、待機系にも書かれています。その代わり、書き込みとコミットにかかる時間は Single-AZ より長くなることがあります。待機系はフェイルオーバーのためだけにあり、読み取りには使えません。

Multi-AZ DB cluster は、3 つの AZ に 1 台ずつ置く構成です。名前に cluster とありますが、Aurora のクラスターとは別のものです。読み取り用の 2 台は、PostgreSQL 自身のレプリケーションで変更を受け取ります。コミットに要るのは 2 台のうち 1 台の確認だけなので、読み取り用のインスタンスは遅れることがあります。この遅れは、次の節のリードレプリカと同じ問題を起こします。

`production` のプロファイルが選ぶのは、Multi-AZ DB instance です。

### フェイルオーバーが接続に起こすこと

フェイルオーバーが起きるのは、プライマリのホストやストレージが壊れたとき、ネットワークから届かなくなったとき、応答しなくなったときだけではありません。OS の更新や、インスタンスクラスの変更のような自分の操作でも起きます。

フェイルオーバーのとき、RDS はエンドポイントの名前の DNS レコードを、待機系のアドレスに書き換えます。エンドポイントの名前は変わりません。アプリから見ると、次のことが起きます。

開いていた接続は、すべて使えなくなります。前のページの接続プールは、データベースが答えたエラー以外のエラーが出た接続を捨てるようにしてあるので、次のリクエストは新しい接続を張り、名前を引き直して、新しいプライマリにつながります。クライアントが DNS の答えを長く覚えていると、古いアドレスにつなぎ続けます。ドキュメントは、覚えておく時間を 30 秒未満にするよう勧めています。

切り替わるまでの間、リクエストは失敗します。この章の関数は接続を 5 秒であきらめ、13章のアプリが 500 を返します。

実行中だったトランザクションは、結果がわからなくなります。`COMMIT` を送って応答が来る前に接続が切れた場合、コミットされたのか、されなかったのかを、アプリは知れません。13章の作成の処理は、同じ ID でもう一度呼んでも 1 件にしかならない作りでした。送り直してよいのは、そういう処理だけです。この問題は 60章が、接続を途中で切るテストと一緒に詳しく扱います。

フェイルオーバーは、この章では一度も起こしていません。60〜120 秒はドキュメントの記述で、ドキュメント自身が、自分の構成で試して時間を測るよう勧めています。

## リードレプリカは遅れる

<!-- section: 59.replica -->

リードレプリカは、プライマリの変更を受け取り続ける、読み取り専用の別のインスタンスです。重い集計や一覧をそちらに逃がして、プライマリの負荷を下げるために使います。1 つのプライマリに、同じリージョンで 15 台まで作れます。レプリカはそれぞれ自分のエンドポイントを持ちます。

待機系との違いは、複製が**非同期**であることです。プライマリは、レプリカに届いたかどうかを待たずにコミットを返します。レプリカは、プライマリより少し古いデータを持っています。どのくらい古いかは決まっておらず、プライマリに書き込みが集中したときや、レプリカで重いクエリが走っているときに伸びます。この遅れをレプリカラグと呼びます。

ノートのアプリで読み取りをレプリカに向けると、次のことが起きます。

```figure
caption: 書き込みはプライマリで確定しているが、レプリカにはまだ届いていない。書いた本人が、直後に自分のノートを見失う
type: sequence
actor client: Client
actor primary: Primary
actor replica: Read replica
step client -> primary: t1 POST /notes
note primary: t2 COMMIT
step primary --> client: t3 201 Created
step client -> replica: t4 GET /notes/{id}
step replica --x client: t5 404 Not Found
step primary --> replica: t6 変更が届く
note replica: t7 再生
step client -> replica: t8 GET /notes/{id}
step replica --> client: t9 200 OK
```

t5 の 404 は、障害ではありません。プライマリもレプリカも正常に動いていて、それぞれ正しく答えています。それでも、保存したはずのノートが消えたように見えます。

この章の不変条件は、**書いた本人は、そのあとの読み取りで自分の書き込みを必ず見られる**、です。read-your-writes と呼ばれる性質です。

### レプリカは待機系の代わりにならない

リードレプリカは、手で昇格させれば独立したインスタンスになります。プライマリが失われたときの逃げ道に見えますが、昇格の時点でレプリカに届いていなかった書き込みは、失われます。

<<< @/examples/59-rds/test/routing.test.ts{promote}

失われるのは、プライマリが成功を返した書き込みです。同期で書かれる Multi-AZ の待機系では、これは起きません。障害に備えるのは Multi-AZ、読み取りを逃がすのはリードレプリカ、と役割を分けて考えます。昇格は元に戻せない操作でもあります。

リードレプリカには、ほかにも条件があります。元のインスタンスで自動バックアップが有効でなければ作れません。レプリカを持つインスタンスも、レプリカ自身も、止めることができません。レプリカに対するポイントインタイムリストアもありません。そして前のページで書いたとおり、マスターユーザーのパスワードを RDS に管理させているインスタンスには、作れません。

## 自分の書き込みを読む

<!-- section: 59.read-your-writes -->

対策の考え方は単純です。書き込んだ人は「プライマリのここまでを見た」という位置を覚えておき、読むときに、レプリカがその位置まで追いついているかを確かめます。追いついていればレプリカから、いなければプライマリから読みます。

### 位置

PostgreSQL は、すべての変更を write-ahead log に順に書きます。その中の位置が LSN（log sequence number）です。

<<< @/examples/59-rds/src/lsn.ts{lsn}

LSN は `16/B374D848` のような 16 進数 2 つの形で表示されます。文字列のまま比べると `9/0` が `10/0` より後ろになってしまうので、数に直してから比べます。

プライマリがどこまで書いたかは `pg_current_wal_lsn()` で、レプリカがどこまで再生したかは `pg_last_wal_replay_lsn()` でわかります。

<<< @/examples/59-rds/src/position.ts{position}

2 つの関数は、聞く相手が決まっています。`pg_current_wal_lsn()` はレプリカでは実行できず、`pg_last_wal_replay_lsn()` はレプリカでなければ NULL を返します。接続先を取り違えると、前者はエラーになり、後者は「位置がわからない」になります。

位置を覚えて更新するのが、次の部分です。

<<< @/examples/59-rds/src/routing.ts{session}

書き込みのあとには、プライマリの位置を覚えます。コミットが終わってから位置を聞くので、返ってくる位置は、そのコミットと同じか、それより後ろです。少し後ろすぎる位置を覚えても、プライマリから読む回数が増えるだけで、不変条件は破れません。

位置を覚えるのは、書き込みのあとだけではありません。プライマリから読んだあとにも、プライマリの位置を覚えます。これを省くと、読み取りが時間をさかのぼることがあります。

<<< @/examples/59-rds/test/routing.test.ts{monotonic}

このテストでは、自分が書いたあとに、ほかの人が同じ一覧に 1 件足しています。プライマリから読んだ一覧は 2 件です。そのあとレプリカが「自分の書き込み」までだけ追いついたとします。書き込みの位置しか覚えていなければ、レプリカは条件を満たすので、次の一覧は 1 件に減ります。さっき見えたノートが消えるわけです。読んだ位置も覚えておけば、レプリカがそこに追いつくまで、プライマリが答え続けます。

位置がわからないときは、すべてプライマリに倒します。レプリカが位置を答えなければプライマリから読みます。書き込みのあとにプライマリの位置を聞けなかったときは、どのレプリカも届かない位置（`LSN_MAX`）を覚えて、そのセッションをプライマリに固定します。

<<< @/examples/59-rds/src/app.ts{app}

### この対策が守らないこと

守っているのは、位置を持っているセッションだけです。同じ人が別の端末で開いた画面は、位置を持っていないので、古い一覧を見ることがあります。ほかの人の書き込みが、いつ見えるようになるかも保証しません。

料金と負荷の面でも、ただではありません。読み取りのたびに、レプリカの位置を聞くクエリが 1 つ増えます。書き込みのたびに、プライマリの位置を聞くクエリが 1 つ増えます。そして、レプリカが遅れているあいだは読み取りがプライマリに戻ってくるので、プライマリには、読み取りを全部受けても倒れない余裕が要ります。レプリカを足しても、プライマリを小さくできるとは限りません。

もっと単純な方法もあります。書き込んだあとの数秒間は、その人の読み取りをプライマリに向ける、という時間で決める方法です。位置を聞くクエリが要らない代わりに、数秒という値は推測になり、ラグがそれを超えた瞬間に不変条件が破れます。

`-c readReplica=true` を付けてデプロイすると、スタックはレプリカを 1 台足し、関数に 2 つ目のエンドポイントを渡します。この構成は実際の RDS では動かしていません。レプリカの位置がプライマリの位置と比べられる値で返ってくることも、ドキュメントの関数の説明から読んだだけです。
