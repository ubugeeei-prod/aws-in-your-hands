# 59 RDS: しくみと実装

[前のページ](/ja/chapters/59-rds.md)で、構成と、最初に決めることを見ました。このページでは、インスタンスを定義し、誰がどうやってサインインするかを決め、Lambda からの接続の数を考えます。

## インスタンスを定義する

<!-- section: 59.instance -->

### ネットワーク

<<< @/examples/59-rds/infra/lib/rds-stack.ts{network}

VPC は 11章のスタックの出力を読んで使います。セキュリティグループは 2 つ作り、互いを名指しします。関数のグループから出られるのはデータベースのグループの 5432 番だけ、データベースのグループに入れるのは関数のグループからの 5432 番だけです。IP アドレスの範囲を書いたルールは 1 つもありません。

DB サブネットグループは、インスタンスを置いてよいサブネットの一覧です。RDS は、2 つ以上の Availability Zone にまたがることを求めます。Single-AZ のインスタンスでも同じで、あとで Multi-AZ に変えるときに待機系を置く場所になります。

### パラメーターグループとログ

<<< @/examples/59-rds/infra/lib/rds-stack.ts{parameters}

PostgreSQL の設定（`postgresql.conf` に書く値）は、RDS ではパラメーターグループに入れます。何も指定しないと既定のグループが付きますが、既定のグループは書き換えられません。設定を 1 つでも変える日が来るなら、最初から自分のグループを付けておきます。あとから付け替えると、再起動が要るからです。

パラメーターには 2 種類あります。動的なパラメーターは変えるとすぐ効き、静的なパラメーターは手で再起動するまで効きません。静的なパラメーターを変えたインスタンスは `pending-reboot` と表示されますが、次のメンテナンスウィンドウで勝手に再起動されることはありません。変えたつもりで効いていない、という状態がそのまま続きます。

ここで入れているのは 2 つです。`log_min_duration_statement` は、500 ミリ秒以上かかった文を、その文と一緒にログに書きます。`rds.force_ssl` は TLS を使わない接続を断る設定で、PostgreSQL 15 以降の RDS では既定で有効です。既定のままでよい値をあえて書いたのは、誰かが外したときに差分として見えるようにするためです。

ロググループを自分で先に作っているのには理由があります。PostgreSQL のログを CloudWatch Logs に送る設定にすると、RDS は `/aws/rds/instance/<インスタンス名>/postgresql` という名前のロググループに書きます。無ければ RDS が作りますが、RDS が作ったロググループには保持期間が無く、スタックを消しても残ります。同じ名前で先に作っておけば、1 週間で古いログが消え、スタックと一緒に無くなります。インスタンスに `aih-notes` という固定の名前を付けたのは、この名前を先に知るためです。

### インスタンス

<<< @/examples/59-rds/infra/lib/rds-stack.ts{instance}

上から順に見ていきます。

`publiclyAccessible: false` で、インスタンスはパブリックなアドレスを持ちません。エンドポイントの名前はプライベートなアドレスに解決されるので、VPC の外からは届きません。

`storageEncrypted` は、作るときにしか選べません。暗号化していないインスタンスを、あとから暗号化することはできず、スナップショットを暗号化つきでコピーして作り直すことになります。

`backupRetention` は自動バックアップを保つ日数で、0 から 35 まで選べます。0 にすると自動バックアップが止まり、ポイントインタイムリストアもリードレプリカも使えなくなります。0 とそれ以外を行き来する変更は、それだけでインスタンスが止まります。練習用でも 1 にしてあるのはそのためです。

バックアップとメンテナンスの時刻は UTC で書きます。メンテナンスの時刻を指定しないと、東京リージョンでは 13:00〜21:00 UTC（日本時間の 22 時から翌朝 6 時）の中のどこかの 30 分に、RDS が決めます。この章は、バックアップを日本時間の午前 2 時、メンテナンスを月曜の午前 3 時に置きました。2 つの時間帯は重ねられません。

`engineLifecycleSupport` は、あとで請求書に効く設定です。[デプロイ](/ja/chapters/59-rds/deploy.md)のページの「バージョンを上げる」で説明します。

最後の `credentials` が、マスターユーザーのパスワードの扱いです。`manageMasterUserPassword` を有効にすると、RDS がパスワードを作って Secrets Manager に置き、既定では 7 日ごとに入れ替えます。テンプレートにも、スタックの state にも、パスワードは現れません。ただし、この機能を使っているインスタンスにはリードレプリカを作れない、という制約があります。blue/green deployment も使えません。そこで、リードレプリカを付ける構成（`-c readReplica=true`）では、CloudFormation にパスワードを 1 回だけ生成させる、ふつうのシークレットに切り替えています。こちらは誰も入れ替えません。

`production` のプロファイルにすると、待機系が付き、削除保護が入り、スタックを消してもインスタンスと自動バックアップが残るようになります。

## 誰がどうやってサインインするか

<!-- section: 59.auth -->

データベースのユーザー（PostgreSQL のことばではロール）は 3 つに分けました。

| ロール | サインインの方法 | できること | 使う場面 |
| --- | --- | --- | --- |
| `notes_admin` | Secrets Manager にあるパスワード | ロールを作る、権限を渡す | 最初の 1 回だけ |
| `notes_migrator` | IAM のトークン | スキーマとテーブルを作る、変える | マイグレーションのたび |
| `notes_api` | IAM のトークン | `app` スキーマの行の読み書き | リクエストのたび |

13章の Aurora DSQL には、`admin` と `notes_api` の 2 つしかありませんでした。ここで 1 つ増やしたのは、マスターユーザーのパスワードをふだん使わないようにするためです。

### IAM データベース認証

<<< @/examples/59-rds/src/rds.ts{token}

RDS の IAM データベース認証は、13章の DSQL のトークンとよく似ています。IAM の認証情報で署名した文字列を、パスワードの欄に入れます。トークンは 15 分で切れますが、確かめられるのは接続するときだけで、つながった接続はそのまま使えます。

署名は手元の計算だけで終わり、AWS には何も送りません。この性質が、この章の構成では決め手になります。関数のいるサブネットからは AWS の API に届かないので、Secrets Manager からパスワードを取ってくる作りにするには、インターフェースエンドポイント（11章。1 つの AZ あたり 1 時間 USD 0.014）を足す必要があります。トークンなら、何も足さずに済みます。

誰がどのデータベースユーザーになれるかは、IAM のポリシーで決まります。

<<< @/examples/59-rds/infra/lib/rds-stack.ts{roles}

`rds-db:connect` のリソースは、インスタンスではなく「このインスタンスの、このデータベースユーザー」です。API の関数のロールは `notes_api` にだけ、運用用の関数のロールは `notes_migrator` にだけなれます。インスタンスを指す部分はエンドポイントの名前ではなく、RDS が振る `db-` で始まるリソース ID で、CloudFormation では `DbiResourceId` という属性から取ります。

同じポリシーにある `ec2:` の 6 つのアクションは、関数を VPC に入れるために Lambda が要求するものです。Lambda のドキュメントが「すべてのリソースに対して許可する」よう書いているので、この章のポリシーで `*` を使っているのは、ここだけです。

データベースの側では、ユーザーに `rds_iam` というロールを付けます。

<<< @/examples/59-rds/src/roles.ts{bootstrap}

`rds_iam` を付けたユーザーは、パスワードではサインインできなくなります。IAM の認証が優先されるからです。`notes_migrator` に渡しているのは、データベースと `public` スキーマに物を作る権限だけで、ロールを作る権限やデータベースを作る権限はありません。

マイグレーションのあとには、`notes_api` に行の読み書きを渡します。

<<< @/examples/59-rds/src/roles.ts{grants}

3 行目は、13章の DSQL では書けなかった文です。`ALTER DEFAULT PRIVILEGES` は、この文を実行したロールがこれから作るテーブルに、あらかじめ権限を付けておきます。あとのマイグレーションでテーブルを足しても、grant を流し直す必要がありません。

IAM データベース認証には、知っておくべき点が 2 つあります。サインインのたびにインスタンスの CPU とメモリを使うことと、誰がいつサインインしたかが CloudTrail にも CloudWatch にも残らないことです。接続を開いたり閉じたりを高い頻度で繰り返すアプリには向きません。

### TLS と認証局

<<< @/examples/59-rds/src/rds.ts{pool}

`rejectUnauthorized: true` は、サーバーの証明書の連鎖と、ホスト名が一致することを確かめます。ここで 13章と違う点が 1 つあります。RDS のサーバー証明書は Amazon RDS 専用の認証局が発行していて、その認証局の証明書は、Node.js が最初から持っている一覧に入っていません。

Lambda の Node.js ランタイムは、Amazon の認証局の証明書をまとめたファイルを `/var/runtime/ca-cert.pem` に持っています。Node.js 20 以降のランタイムは、このファイルを自動では読み込みません。そこで、スタックが関数の環境変数 `NODE_EXTRA_CA_CERTS` にこのパスを入れています。このファイルに RDS の認証局が入っていて、Node.js 24 のランタイムで検証が通ることは、実機では確かめていません。

認証局は 3 種類（`rds-ca-rsa2048-g1`、`rds-ca-rsa4096-g1`、`rds-ca-ecc384-g1`）から選べ、既定は 1 つ目です。この 3 つを使っているかぎり、サーバー証明書は期限の前に RDS が自動で入れ替えます。

接続先は、必ずエンドポイントの名前で指定します。IP アドレスを設定に書くと、証明書の検証が通らないだけでなく、次のページで見るフェイルオーバーのあと、古いインスタンスを指したままになります。環境変数の検査が、名前以外を受け付けないようにしています。

## Lambda からの接続の数

<!-- section: 59.connections -->

13章と同じく、プールの `max` は 1 です。Lambda の実行環境は一度に 1 つのリクエストしか処理しないので、接続の数は、同時に動いている実行環境の数とほぼ同じになります。

<<< @/examples/59-rds/src/lambda.ts{handler}

DSQL では、この数を気にする場面がほとんどありませんでした。クラスターの上限は 10,000 接続だったからです。RDS は事情が違います。PostgreSQL は接続 1 本ごとにプロセスを 1 つ立ち上げ、その分のメモリを使います。上限（`max_connections`）の既定値はインスタンスのメモリから決まり、式は `LEAST({DBInstanceClassMemory/9531392}, 5000)` です。メモリが 1 GiB の db.t4g.micro では、1 GiB をそのまま当てはめても 112 にしかなりません。式の `DBInstanceClassMemory` が正確に何バイトになるかは確かめていないので、実際の値は、つないでから `SHOW max_connections` で見てください。

Lambda は、リクエストが増えると実行環境を増やします。実行環境が 200 になれば、接続も 200 本になります。上限に達したデータベースは、新しい接続を `too many connections` で断ります。リクエストが引いても、実行環境が残っているあいだは、その接続が開いたまま残ることがあります。

この章のスタックは、入口で流量を絞っています。API Gateway のステージのスロットリング（1 秒に 10 件）です。これだけで接続の数が決まるわけではありませんが、際限なく増えることは防げます。もっと確実に抑えるなら、関数に予約済み同時実行数を付けます（[29章](/ja/chapters/29-lambda-tuning.md)）。

### RDS Proxy

接続の数の問題に対して AWS が用意している答えが、RDS Proxy です。アプリとデータベースの間に入る接続プールで、アプリはプロキシのエンドポイントにつなぎ、プロキシが少数の接続をデータベースとの間に張って使い回します。

使い回しの単位はトランザクションです。あるクライアントのトランザクションが終わると、そのデータベースの接続は別のクライアントに貸し出されます。数百の実行環境がプロキシにつないでいても、データベースの側の接続は、同時に実行中のトランザクションの数で済みます。さばき切れない分は待たされ、設定した上限を超えた分は断られます。

プロキシには、もう 1 つ役目があります。Multi-AZ のフェイルオーバーのとき、プロキシは同じアドレスで接続を受け付け続け、新しいプライマリへ向け直します。クライアントが DNS の答えを覚えていても影響を受けません。ドキュメントは、Multi-AZ のインスタンスでフェイルオーバーの時間が最大 66% 短くなると書いています。

ただし、使い回しが効かなくなる場合があります。接続に状態を残す操作をすると、プロキシはそのクライアントを 1 本の接続に固定します。これを pinning と呼びます。PostgreSQL で pinning を起こすものとして、ドキュメントは次を挙げています。

- `SET` でセッションの設定を変える
- `PREPARE`、`EXECUTE`、`DEALLOCATE` で prepared statement を扱う
- 一時テーブル、一時シーケンス、一時ビューを作る
- カーソルを宣言する
- `LISTEN` で通知を待つ
- `pg_advisory_lock` のような、セッション単位の advisory lock を取る（トランザクション単位の `pg_advisory_xact_lock` は pinning を起こしません）
- `nextval` や `setval` でシーケンスを操作する
- 16 KB を超える文を送る

全部の接続が pinning されると、プロキシはただの中継になり、料金だけが残ります。13章のトランザクションのランナーは `BEGIN ISOLATION LEVEL REPEATABLE READ` を送ります。この文は `SET` ではなく、効くのはそのトランザクションの中だけなので、上の一覧には当たりません。node-postgres が値つきのクエリを送るときに使うプロトコル（extended query）が pinning を起こすかどうかは、この一覧からは読み取れず、確かめていません。

料金は、後ろにあるインスタンスの vCPU の数で決まります。1 vCPU あたり 1 時間 USD 0.018 で、最低でも 2 vCPU 分です。db.t4g.micro の前に置くと 1 か月で USD 26.28 になり、インスタンスそのもの（USD 18.25）より高くなります。

この章のスタックには、プロキシを入れていません。1 秒 10 件までの API では接続が足りなくなる場面が無く、料金が倍以上になるからです。プロキシを足すのは、`too many connections` が実際に出たとき、同時に動く実行環境が接続の上限に近づいたとき、Multi-AZ のフェイルオーバーを短くしたいときです。Lambda のドキュメントは、直接の接続は単純な場面向けで、本番ではプロキシを勧める、と書いています。

プロキシを使うときの条件も書いておきます。プロキシはデータベースと同じ VPC に置き、パブリックにはできません。レプリケーションを組んだインスタンスでは、プロキシを付けられるのは書き込みを受ける側だけで、リードレプリカには付けられません。
