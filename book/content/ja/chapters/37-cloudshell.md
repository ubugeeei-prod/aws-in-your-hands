# 37 CloudShell と Cloud9: AWS の中にある作業環境

この本のコマンドは、すべて手元のマシンで実行してきました。AWS には、ブラウザの中で使う作業環境として Cloud9 と CloudShell があります。この章では、その 2 つがいまどういう状態にあり、この本の読者が何に使えるのかを確かめます。

先に結論を書きます。**Cloud9 は、新しい利用者を受け付けていません。** AWS は 2024 年 7 月 25 日に新規の受付を閉じました。それまでに使っていたアカウントは引き続き使えますが、これから AWS を始める人は Cloud9 の環境を作れません。そのため、この章には Cloud9 の手順を書いていません。Cloud9 が何だったのかと、代わりに何を使えるのかだけを説明します。

CloudShell は、いまも誰でも使えます。コンソールの中で開くシェルで、サインインしている identity の認証情報を最初から持っています。追加の料金はかかりません。ただし、[02章](/ja/chapters/02-toolchain.md)で用意した道具をそのまま持ち込める場所ではありません。この章の後半では、その理由を公式ドキュメントに書かれた制約から説明し、CloudShell に向いている仕事を小さなスクリプトにまとめます。

前提は、[01章](/ja/chapters/01-account.md)のアカウントと `aws login`、02章の道具、[11章](/ja/chapters/11-network.md)の VPC、[23章](/ja/chapters/23-ec2.md)の Session Manager です。コードは `examples/37-cloudshell/` にあります。

この章には CDK のスタックがありません。CloudShell は、コンソールを開ける identity に最初から用意されている機能で、スタックとして作るものが無いからです。使える人を絞るポリシーは作りますが、付ける先のロールは読者のアカウントごとに違うので、スタックにはせず、JSON を出力するスクリプトにしました。

この章の内容は、2026 年 10 月 13 日に公式ドキュメントを読んで確かめたものです。CloudShell を実際に開いての確認はしていません。CloudShell の中での動作について書いた文は、ドキュメントに書かれていることか、「試していません」と断ったことのどちらかです。

## Cloud9 のいま

<!-- section: 37.cloud9 -->

Cloud9 は、ブラウザで使う統合開発環境でした。エディタ、デバッガ、ターミナルがブラウザの中にあり、実体は自分のアカウントの EC2 インスタンスか、SSH で届く自分のサーバーの上で動きます。前者を EC2 環境、後者を SSH 環境と呼びます。

Cloud9 のユーザーガイドを開くと、冒頭に次の告知が出ます。

```text
AWS Cloud9 is no longer available to new customers. Existing customers of
AWS Cloud9 can continue to use the service as normal.
```

告知のリンク先は AWS の公式ブログの記事です。記事には、2024 年 7 月 25 日に新規の利用者への提供を閉じたこと、既存の利用者はこれまでどおり使えること、セキュリティと可用性と性能への投資は続けるが新しい機能を足す予定はないことが書かれています。サービスを終える日付は、確認した範囲では示されていません。

記事が代わりに勧めているのは 2 つです。1 つは AWS IDE Toolkits で、手元の IDE に AWS の操作を足すオープンソースのプラグインです。もう 1 つが CloudShell です。つまり AWS の答えは、エディタは手元に置き、ブラウザの中にはシェルだけを残す、というものです。

すでに Cloud9 を使っているアカウントでは、環境はそのまま動きます。Cloud9 そのものに料金はなく、EC2 環境ならインスタンスと EBS のボリュームの料金がかかります。記事は、移行を終えたら Cloud9 のインスタンスを消すように念を押しています。消し忘れたインスタンスは、23章で見たとおり、置いてあるだけで課金されるからです。

ブラウザの中のエディタが欲しい読者のための選択肢は、[費用、注意点、片付け](/ja/chapters/37-cloudshell/wrap.md)のページにまとめました。

## CloudShell の環境

<!-- section: 37.environment -->

CloudShell は、コンソールから開くシェルです。コンソールの画面の左下にあるツールバーか、CloudShell のページから開きます。開くと、Amazon Linux 2023 をもとにした環境が AWS の側に 1 つ作られ、ブラウザとその環境が WebSocket でつながります。

```figure
caption: CloudShell は、コンソールにサインインした identity の認証情報を持つシェルを、AWS の側に用意します。手元のターミナルは aws login で同じ identity の認証情報を受け取ります。
node browser: ブラウザ | コンソール
node laptop: 手元のターミナル | aws login
node shell: CloudShell | 1 vCPU、2 GiB、$HOME 1 GB
node api: AWS の API
edge browser -> shell: WebSocket
edge shell -> api: aws コマンド
edge laptop -> api: aws コマンド
group machine: 手元のマシン = browser, laptop
group aws: AWS = shell, api
mark shell
```

東京リージョン（`ap-northeast-1`）を含む多くのリージョンで使えます。環境はリージョンごとに別で、コンソールでリージョンを切り替えると、別の環境につながります。

環境の大きさは決まっていて、変えられません。

- CPU は 1 vCPU、メモリは 2 GiB
- ホームディレクトリ（`$HOME`）は 1 GB で、セッションをまたいで残る。リージョンごとに 1 GB ずつ
- ホームディレクトリの外は、セッションが終わると元に戻る

最初から入っているものは、ユーザーガイドの一覧によると次のとおりです。ガイドは版を書いていません。環境が定期的に更新されるので、版は `node --version` のようにその場で確かめるように、と書かれています。

- シェル: Bash（既定）、Z shell、PowerShell
- AWS のコマンド: AWS CLI（v2）、AWS CDK の `cdk`、SAM CLI、EB CLI、ECS CLI、AWS Tools for PowerShell
- ランタイム: Node.js と npm、Python 3 と pip、Java（Amazon Corretto 21）
- 道具: git、jq、make、tmux、vim、nano、`edit`、tar、zip と unzip、wget、SSH クライアント、psql、kubectl、Docker、sudo

この一覧に、pnpm、`vp`、Nix、cdkd はありません。

セッションには 2 つの時間制限があります。キーボードやマウスの操作が 20〜30 分ないとセッションは終わり、動かしているプロセスは操作に数えられません。操作を続けていても、およそ 12 時間で終わります。長く走らせる仕事には向かないので、ドキュメントは EC2 を勧めています。

量の上限もあります。1 つのアカウントで同時に開けるシェルは、リージョンごとに 10 までです。使える時間は、アカウントの全員を合わせて、リージョンごとに月 200 時間です。この 2 つは Service Quotas から引き上げを申請できます。ホームディレクトリの 1 GB は変えられません。

ホームディレクトリの中身は、そのリージョンで最後にセッションを終えてから 120 日使わないと消えます。CloudShell のホームディレクトリは、長く置いておく場所ではありません。残したいものは S3 かリポジトリに置きます。

ファイルは、画面の Actions メニューからアップロードとダウンロードができます。大きなファイルでは遅くなることがあるので、ドキュメントは S3 を経由する方法も挙げています。

## 認証情報の届き方

<!-- section: 37.credentials -->

CloudShell のシェルは、開いた時点で認証情報を持っています。コンソールへのサインインに使った認証情報を、CloudShell が環境に渡すからです。`aws configure` も `aws login` も要りません。

01章の `aws login` と比べると、手順は違っても、結果は同じ identity の一時認証情報です。

| | 手元のターミナル（01章） | CloudShell |
| --- | --- | --- |
| 始め方 | `aws login` を実行し、ブラウザでサインインする | コンソールにサインインして、CloudShell を開く |
| 認証情報の置き場所 | `~/.aws/login/cache` | AWS の側の環境。置き場所はドキュメントに書かれていない |
| 誰の権限か | サインインした identity | サインインした identity |
| 既定のリージョン | プロファイルの `region` | CloudShell を開いたときのコンソールのリージョン（環境変数 `AWS_REGION`） |
| 終わり方 | 最長 12 時間。`aws logout` で消せる | 操作が 20〜30 分ないとき、または約 12 時間 |

ドキュメントは CloudShell の認証情報を、一時的で、定期的に入れ替わり、利用者の権限の範囲に限られたもの、と説明しています。入れ替わる間隔は書かれていません。

権限は増えも減りもしません。CloudShell の中の `aws` コマンドにできることは、コンソールでその identity にできることと同じです。01章の `aih-dev` は `AdministratorAccess` を持っているので、CloudShell を開けば、管理者の権限を持ったシェルが手に入ります。

この性質には、もう 1 つの面があります。**そのロールでコンソールを開ける人は誰でも、そのロールのシェルを持てます。** 手元のマシンに認証情報を置かないようにしていても、コンソールにサインインできれば、ブラウザだけで `aws` コマンドを好きなだけ実行できます。しかも CloudShell は、既定でインターネットに出られます。強い権限のロールに CloudShell を使わせるかどうかは、IAM のポリシーで決められます。作り方は[しくみと実装](/ja/chapters/37-cloudshell/build.md)のページに書きました。

リージョンの決まり方には注意が要ります。CloudShell は、開いたときのコンソールのリージョンを環境変数 `AWS_REGION` に入れます。環境変数は `aws configure` の設定より優先されるので、バージニアのコンソールで開いた CloudShell は、何も指定しなければバージニアを見に行きます。この章のスクリプトは、すべての呼び出しに `--region` を付けて、この違いを避けています。

## ネットワーク

<!-- section: 37.network -->

ふつうに開いた CloudShell の環境は、インターネットへ出ていけますが、外から入ってくる通信は受けられません。パブリック IP アドレスも付きません。したがって、`npm install` や `git clone` はできますが、環境の中で開発サーバーを立てて、ブラウザからそこへつなぐことはできません。Cloud9 にあったプレビューに当たるものは、CloudShell にはありません。

外へ出ていけることは、危険にもなります。ドキュメントは、利用者が CloudShell からデータを持ち出せることを警告として書いています。そして、この出口を絞る設定は、ふつうの環境にはありません。

絞りたいときのために、CloudShell には VPC の中に環境を作る方法があります。VPC とサブネットとセキュリティグループを選んで環境を作ると、その環境は選んだサブネットの中にいるものとして通信します。11章の VPC のプライベートサブネットにあるリソースへ、踏み台なしで届くようになります。

ただし、VPC の環境はふつうの環境より不便です。ドキュメントに書かれている制約は次のとおりです。

- ホームディレクトリが残らない。環境がタイムアウトするか、消すか、再起動すると、中身は消える
- Actions メニューからのファイルの上げ下ろしが使えない
- パブリック IP アドレスが付かないので、インターネットへ出るには、NAT のあるプライベートサブネットに置く必要がある。パブリックサブネットに置いても出られない
- 1 つの identity が作れる環境は 2 つまで。セキュリティグループは 5 つまで
- VPC のローカルの DNS ゾーンは、既定では使われない

11章の既定の構成には NAT Gateway がありません。その VPC に CloudShell の環境を作ると、インターネットへ出られず、ゲートウェイエンドポイントのある S3 と DynamoDB 以外の AWS の API にも届かないはずです。これはドキュメントからの推論で、試してはいません。

## この本の道具を CloudShell で動かせるか

<!-- section: 37.toolchain -->

02章の道具は、Nix が版を固定し、`vp` がタスクを動かし、cdkd がデプロイする、という組み合わせでした。これを CloudShell に持ち込めるかを、ドキュメントに書かれた制約から順に考えます。

**Nix は、セッションをまたいで残せません。** Nix はパッケージを `/nix` に置きます。Nix の公式のマニュアルには、`/nix` 以外に置く方法は書かれていません。一方 CloudShell では、ホームディレクトリの外に置いたファイルは、セッションが終わると消えます。`/nix` はホームディレクトリの外です。

CloudShell では sudo を使えるので、セッションのたびに Nix を入れ直すことは、できるかもしれません。試していません。ただ、入れ直せたとしても割に合いません。この本の devShell が使う 5 つの道具（Node.js、pnpm、AWS CLI、git、`vp`）と、その依存を合わせた大きさを手元で測ると、166 個のパッケージで 1.83 GiB ありました。測ったのは 2026 年 10 月 13 日の macOS（Apple silicon）で、CloudShell が動く Linux では値が変わります。それでも、20〜30 分で切れるセッションのたびに、1 vCPU の環境へ取得する量ではありません。ホームディレクトリの外にどれだけの空きがあるかは、ドキュメントに書かれていません。

Nix を使わずに、入っている Node.js で動かすのも難しいです。まず、CloudShell の Node.js の版はドキュメントに書かれていません。この本のコードは、Node.js が TypeScript の型を取り除いて実行することを前提にしていて、古い Node.js では動きません。次に、依存を入れる場所がありません。このリポジトリの `node_modules` は、手元で測ると 1.9 GB あり、1 GB のホームディレクトリに収まりません。ホームディレクトリの外に置けば、セッションのたびに入れ直しになります。

cdkd の代わりに、入っている `cdk` を使うこともできません。CloudShell には AWS CDK の CLI が入っていて、AWS のチュートリアルには CloudShell から `cdk deploy` する手順もあります。しかし、この本のスタックは cdkd が作り、cdkd が state に記録しています。02章に書いたとおり、同じスタックを 2 つの経路で管理すると、記録が食い違います。

そこで、この本では役割を分けます。

- 手元に残すのは、synth、diff、デプロイ、ドリフトの検出、destroy、テストです。リポジトリと固定した道具が要る仕事は、すべて手元で実行します
- CloudShell でするのは、AWS CLI だけで済む確認と、小さな後始末です。いまの identity とアカウント、予算の状況、cdkd がまだ記録しているスタック、ログの確認、destroy の前にバケットを空にすることがこれに当たります

後者は、手元のマシンが無いときに役に立ちます。出先で「あのスタックを消し忘れていないか」が気になったときや、マシンを入れ替えている途中がそうです。次のページから、そのための 1 ファイルのスクリプトを作ります。

## CloudShell を使わないほうがよい場合

<!-- section: 37.when-not -->

手元に 02章の環境があるなら、CloudShell を開く理由はほとんどありません。同じ確認は `vp run account:whoami` や各章のタスクでできて、そちらは版が固定されています。

次の場合は、使わないほうがよいでしょう。

- 長く走らせる仕事。操作しなければ 20〜30 分で切れ、動いているプロセスは操作に数えられません
- 再現したい作業。入っている道具の版は AWS の都合で変わり、ドキュメントにも書かれていません。同じコマンドが来月も同じ結果になる保証はありません
- 残したいファイルの置き場所。120 日使わなければ消え、リージョンごとに別で、1 GB しかありません
- 本番のアカウントでの、強い権限での作業。出口を絞れないシェルに管理者の権限を持たせることになります。使うなら、次のページのポリシーで、誰が開けるかを先に決めてください
