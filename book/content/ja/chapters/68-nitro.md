# 68 Nitro: EC2 を支えるしくみ、Nitro Enclaves、Graviton

[23章](/ja/chapters/23-ec2.md)では、サーバーを 1 台持ちました。この章では、そのインスタンスが載っている土台を見ます。AWS Nitro System です。[09章](/ja/chapters/09-ssr.md)で Nuxt のサーバーエンジンとして出てきた Nitro とは、名前が同じだけの別物です。

Nitro System がしたことは、1 つにまとめられます。仮想化の仕事のうち、ネットワークとストレージの入出力をホストの CPU から専用のカードへ移し、ホストに残るハイパーバイザーには CPU とメモリを分ける仕事だけを残しました。データボリュームのデバイス名が起動のたびに入れ替わること、インスタンスタイプの名前の付き方、ベアメタルのインスタンスがあること、インスタンスの管理者にも読めない計算の場所を切り出せることは、どれもこの設計から説明できます。

この章のスタックは、**置いてあるだけで時間単位の料金がかかります**。既定の構成で 1 日およそ USD 2.23、1 か月（730 時間）で USD 67.91 が、11章の料金に上乗せされます。インスタンスを止めれば 1 か月 USD 1.77 まで下がり、スタックを消せば 0 になります。手順は[片付け](/ja/chapters/68-nitro/wrap.md)にあります。

この章は、読者が直接触れない場所の話が多くなります。そこで、3 つを分けて書きます。AWS の資料に書いてあること、そこから言えること、AWS の外にいる人には確かめられないことです。資料は、EC2、Nitro Enclaves、KMS のドキュメントと、AWS が公開しているホワイトペーパー「The Security Design of the AWS Nitro System」（2022 年 11 月公開、2024 年 2 月更新）です。

AWS に対しては、何も実行していません。エンクレーブのイメージを作ってもいないし、エンクレーブを起動してもいません。この本を書いている機械は macOS で、Docker も無いからです。手元で確かめたのは、名前の読み取り、キーポリシーとその評価、そして親インスタンスとエンクレーブと KMS のやり取りを写したモデルです。コードは `examples/68-nitro/` にあります。

## 置いてあるだけでかかる料金

<!-- section: 68.cost -->

金額は USD で、東京リージョンの従量課金の定価、税別です。1 か月は 730 時間として計算しています。11章のネットワークの料金は含みません。

| 状態 | 1 日 | 1 か月 |
| --- | --- | --- |
| 起動したまま | 2.23 | 67.91 |
| 停止したまま | 0.06 | 1.77 |

内訳は次のとおりです。

- インスタンス: `c6g.large` が 1 時間 USD 0.0856 で、730 時間では 62.49。止めている間はかかりません
- パブリック IPv4 アドレス: 1 時間 USD 0.005 で、730 時間では 3.65。自動で割り当てたアドレスなので、止めると解放されます
- ルートボリューム: gp3 が 1 GB・1 か月あたり USD 0.096。大きさは AMI が決めるので、23章と同じく 8 GiB と仮定して 0.77。止めていてもかかります
- KMS の鍵: 1 つにつき 1 か月 USD 1 で、時間で按分されます（21章で確かめた料金ページの記述）。一度も使わなくてもかかります

エンクレーブには料金がありません。ドキュメントは、Nitro Enclaves に追加の料金はなく、インスタンスと、一緒に使うほかのサービスの料金だけがかかる、と書いています。エンクレーブは、インスタンスがすでに払っている vCPU とメモリの一部を使うからです。

表に入れていないものがあります。KMS へのリクエスト（1 万件あたり USD 0.03）、データ転送、11章の VPC です。無料利用枠は、当てはまるかどうかを確かめられないので引いていません。`-c instanceType=m6g.large` にすると、1 日 USD 2.55、1 か月 USD 77.69 になります。

## Nitro System の部品

<!-- section: 68.system -->

ホワイトペーパーは、Nitro System を 3 つの部品で説明しています。

```figure
caption: 入出力は Nitro Card が受け持ち、ホストの基板に残るハイパーバイザーは CPU とメモリを分けるだけになる
node cp: EC2 control plane
node ctrl: Nitro Controller | Nitro Card, root of trust
node hv: Nitro Hypervisor | CPU とメモリだけ
node chip: Nitro Security Chip | ファームウェアを守る
node guest: EC2 インスタンス | 自分の OS とコード
node vpc: Nitro Card for VPC | ネットワーク
node ebsc: Nitro Card for EBS | ボリューム
edge cp -> ctrl: 認証された API
edge ctrl -> hv: 起動, 停止
edge ctrl -> chip
edge hv -> guest: vCPU, メモリ
edge guest -> vpc: ENA
edge guest -> ebsc: NVMe
group board: system main board = hv, chip, guest
mark hv
```

**Nitro Card。** AWS が設計した、基板とは別のハードウェアです。インスタンスに見せるネットワークと、EBS とインスタンスストアのストレージは、すべてここが受け持ちます。EC2 のコントロールプレーンからの指示を受ける窓口もここにあり、その役の 1 枚を Nitro Controller と呼びます。カードは、ストレージを NVMe のデバイスとして、ネットワークを ENA（Elastic Network Adapter）のデバイスとして、PCIe 越しにインスタンスへ見せます。

**Nitro Security Chip。** 基板に載っている部品で、ファームウェアへの書き込みをすべて仲介します。起動のときには、Nitro Controller が基板のファームウェアを検査し終えるまで、CPU をリセットのまま押さえておきます。

**Nitro Hypervisor。** ホストの CPU の上で動くソフトウェアです。Nitro Controller から起動や停止の指示を受け、プロセッサーの仮想化の機能を使って CPU とメモリを分け、カードが出すデバイスをインスタンスに割り当てます。ホワイトペーパーによれば、ネットワークスタックも、汎用のファイルシステムも、周辺機器のドライバーも、シェルも、対話的に入る手段も持っていません。KVM をもとにした、とも書いてあります。

Nitro System より前の EC2 は、Xen を使っていました。ホストには dom0 と呼ばれる特別な仮想マシンがあり、その中の Amazon Linux が、デバイスの模倣とホストの管理を受け持っていました。Nitro System はその仕事を 1 つずつカードへ移し、2017 年の C5 で dom0 を無くした、とホワイトペーパーは書いています。2018 年の初め以降に出たインスタンスタイプは、すべて Nitro System の上にあります。23章の `t4g.micro` もそうです。

資料に書いてあるのは、ここまでです。カードの中のソフトウェア、カードの数や世代ごとの違い、ハイパーバイザーのソースコードは公開されていません。インスタンスの種類ごとの「Nitro v2」から「Nitro v6」という版の番号はドキュメントに載っていますが、載っているのは版ごとのネットワークの機能の違いだけです。

## 読者の目に見えるところ

<!-- section: 68.claims -->

この設計は、インスタンスを使う側には 4 つの形で見えます。

**ボリュームは NVMe、ネットワークは ENA として見える。** ドキュメントは、Nitro System のインスタンスでは EBS ボリュームが NVMe のブロックデバイスとして現れ、ネットワークには ENA を使う、と書いています。ここから言えるのは、OS に見えるデバイスの名前は NVMe のドライバーが決めるのであって、ボリュームを付けるときに指定した `/dev/sdf` ではない、ということです。23章のデータボリュームに関わる話なので、[次のページ](/ja/chapters/68-nitro/build.md)で扱います。

**ホストの資源のほとんどがインスタンスに渡る。** AWS の製品ページは、Nitro System がホストの計算資源とメモリの「practically all」をインスタンスに渡す、と書いています。管理用のソフトウェアをホストの CPU で動かさないのだから、そのぶんが空くという理屈は通ります。どれだけ残っているのかを示す数字は、資料にありません。外から測る方法もありません。

**ハイパーバイザーなしでも動かせる。** 入出力をカードが受け持ち、ファームウェアを Security Chip が守るので、ハイパーバイザーを置かずに基板をまるごと貸し出せます。これがベアメタルのインスタンス（サイズが `metal` のもの）です。ドキュメントは使いみちとして、仮想化された環境では使えないハードウェアの機能（Intel VT など）が要る場合を挙げています。microVM を自分で動かす話は、[67章](/ja/chapters/67-firecracker.md)にあります。

**EBS 最適化が既定になっている。** EBS への通信に専用の帯域を割り当てる EBS 最適化は、古い世代では時間あたりの料金を払って有効にする機能でした。ドキュメントの一覧では、`t4g.micro` も `c6g.large` も、既定で有効な側に入っています。設定する項目ではなくなった、と言えます。

もう 1 つ、目には見えない主張があります。ホワイトペーパーは、Nitro System のホストにログインする手段、インスタンスのメモリに触れる手段、暗号化したインスタンスストアや EBS ボリュームの中身に触れる手段は、どのシステムにも人にも無い、と書いています。保守には、認証と認可と記録のある限られた API だけを使い、そのどれも顧客のデータには届かない、という説明です。引き換えに、その場で調べられない不具合があり、再現用の機材で調べ直すことになる、とも書いてあります。

これは AWS の主張です。AWS は、NCC Group に設計の評価を依頼し、その報告が主張を裏づけたと 2023 年 5 月のブログで発表しています。ブログが引いている一文は「設計上、AWS のセキュリティの主張を損なう欠落は見つからなかった」という趣旨です。この章では、報告書そのものは読んでいません。

読者がここから言えることは、限られています。AWS がこう設計したと文書で約束していること、そして第三者が設計を評価したと AWS が発表していることです。実物のホストがその設計どおりに作られ、動いているかどうかは、AWS の外にいる人には確かめられません。インスタンスの中からホストを調べる手段は、設計のとおりなら、存在しないからです。

## この章で作るもの

<!-- section: 68.when-not -->

ここまでの話に、読者が作るものはありません。作れるのは、Nitro System が読者に貸してくれる仕組みを使う部分です。Nitro Enclaves です。

エンクレーブ（enclave）は、インスタンスの vCPU とメモリの一部を切り出して作る、もう 1 つの仮想マシンです。ネットワークも、永続的なストレージも、ログインする手段もありません。元のインスタンス（親インスタンス）とのあいだに、ソケットが 1 本あるだけです。ドキュメントは、親インスタンスのプロセスも、root の利用者も、エンクレーブの中のデータとアプリには触れない、と書いています。

この章では、ノートのアプリに次の設計を足します。**ノートを暗号化する鍵は、エンクレーブの中でしか平文にならない。** 親インスタンスは、ノートの暗号文と、KMS の鍵で包まれたデータキーを持ちます。包みを解けるのはエンクレーブだけで、それを KMS のキーポリシーが決めます。

スタックが作るのは、エンクレーブを有効にしたインスタンス、KMS の鍵、ロールの 3 つです。

`measurement` に既定値がないのは、わざとです。エンクレーブのイメージを作るまで、その値は存在しません。値を渡さずにデプロイすると、誰も使えない鍵ができます。

先に、使わないほうがよい場合を書いておきます。この本のアプリの大半には、エンクレーブは要りません。Lambda にも Fargate にも、エンクレーブを作る場所がありません。23章のインスタンスも `t4g.micro` で、エンクレーブの対象外です。ノートを保存時に暗号化したいだけなら、DynamoDB や S3 や EBS の暗号化で足ります（[21章](/ja/chapters/21-security.md)）。鍵を使える人を絞りたいだけなら、キーポリシーと IAM で足ります。

エンクレーブが答えになるのは、インスタンスに入れる人や、インスタンスで動くほかのソフトウェアからも、鍵や個人のデータを隠したいときです。決済の秘密鍵、署名用の鍵、本人確認の書類といったものがそれに当たります。引き換えに、時間課金のインスタンスを 1 台持ち、イメージを作り直すたびにキーポリシーを書き換え、デバッグモードでなければコンソールも見られない仕組みを運用することになります。できないことも多く、[費用、注意点、片付け](/ja/chapters/68-nitro/wrap.md)にまとめました。
