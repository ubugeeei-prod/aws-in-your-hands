# 61 SQS: FIFO、visibility timeout、batch、redrive

[08章](/ja/chapters/08-async.md)では、標準キューを 1 本使いました。標準キューは順序を保たず、同じメッセージを 2 回届けることがあるので、順序も重複もワーカーの側で片付けました。

SQS には、FIFO キューというもう 1 つの種類があります。名前と、ドキュメントの「exactly-once processing」ということばからは、順序どおりに 1 回だけ処理されるキューに見えます。実際にキューが受け持つ範囲は、それより狭いものです。FIFO キューが守るのは、メッセージグループの中の順序と、送信から 5 分間の重複の排除で、それもコンシューマーが可視性タイムアウトの内に処理を終えている間に限られます。その外側で「順に、1 回分だけ効く」ことを守るのは、この章でもワーカーです。

題材は、ノートへの編集コマンドです。行を 1 つ足す、題を変える、の 2 種類を、キューを通してワーカーに渡します。順序が入れ替われば題は古いものに戻り、同じコマンドが 2 回効けば同じ行が 2 つ並びます。順序と重複の両方が結果に出るので、キューがどこまで守り、どこから守らないかをテストで確かめられます。

FIFO のほかに、08章が既定値のまま通り過ぎた設定も扱います。可視性タイムアウトの決め方と延ばし方、ロングポーリング、バッチ、メッセージの大きさの上限、遅延、Lambda がキューを読むときの設定、デッドレターキューと redrive、キューポリシーと暗号化、そして料金です。

前提は 08章です。コードは `examples/61-sqs/` にあります。時間で課金されるリソースはありません。置いてあるだけの月は、アラーム 2 つと空のキューの読み取りで、定価の見積もりが USD 0.53、毎月の無料枠に収まれば 0 です。仮定は[費用のページ](/ja/chapters/61-sqs/wrap.md)に書きました。

## 全体像

<!-- section: 61.overview -->

```figure
caption: コマンドは FIFO キューに入り、イベントソースマッピングがノートごとの順序を保ったまま Worker に渡す
node producer: 送る側 | sqs:send、または自分のアプリ
node q: SQS キュー "Commands" | FIFO, 可視性タイムアウト 60 s, 4 日保持
node esm: Lambda イベントソースマッピング | 1 バッチは最大 10 件、同時に最大 2 バッチ
node worker: Lambda function "Worker" | タイムアウト 10 s
node table: DynamoDB テーブル "Edits" | ノートと、適用済みの目印
node dlq: SQS キュー "DeadLetters" | FIFO, 14 日保持
edge producer -> q: SendMessageBatch
edge q -> esm
edge esm -> worker
edge worker -> table: TransactWriteItems
edge q --> dlq: 5 回受信されて削除されない
edge worker --> dlq: 読めないメッセージ
mark q
```

送る側は、コマンドを 1 件ずつメッセージにして、FIFO キューに送ります。メッセージには、どのノートのコマンドかを表す message group ID と、どのコマンドかを表す重複排除 ID（deduplication ID）を付けます。Lambda のイベントソースマッピングがキューを読み、ワーカーを呼びます。ワーカーは、コマンドをテーブルのノートに適用し、適用したことを示す目印を同じトランザクションで書きます。

デッドレターキューへの矢印は 2 本あります。1 本は 08章と同じで、5 回受け取られても削除されなかったメッセージを SQS が移します。もう 1 本は、この章で足したものです。読めないメッセージを、ワーカーが自分で移します。そうした理由は、[しくみと実装のページ](/ja/chapters/61-sqs/build.md)で説明します。

図には描いていませんが、アラームが 2 つあります。デッドレターキューにメッセージがあるときと、キューのいちばん古いメッセージが 2 分以上待ち続けているときに鳴ります。

### スタックを独立させた理由

スタック（`AihSqs`）は、05〜08章のスタックを継承していません。キューが 2 つ、関数が 1 つ、テーブルが 1 つ、アラームが 2 つで、CloudFront も Cognito も含みません。SQS の設定だけを読めるようにするためです。

そのかわり、ワーカーが書く先は `Edits` というこの章のテーブルで、05章のノートのテーブルではありません。05章のテーブルに書くなら、05章の楽観ロックが使っているバージョンと、この章のコマンドの適用をどう両立させるかを決める必要があります。この章では、そこまで作っていません。

## 標準キューと FIFO キュー

<!-- section: 61.fifo -->

2 種類のキューの違いを、2026-10-13 に読んだ公式ドキュメントと Price List から並べます。

| | 標準キュー | FIFO キュー |
| --- | --- | --- |
| 順序 | できるだけ送った順。保証はしない | メッセージグループの中では、送った順 |
| 重複 | 少なくとも 1 回。重複して届くことがある | 送信の重複を 5 分間取り除く |
| スループット | ほぼ無制限 | API ごとに毎秒 300 回。バッチを使って毎秒 3,000 件 |
| 遅延 | キューごと、メッセージごと | キューごとだけ |
| Lambda のバッチ | 最大 10,000 件。batch window あり | 最大 10 件。batch window なし |
| デッドレターキュー | 標準キュー | FIFO キュー |
| 100 万リクエストの料金（東京） | USD 0.40 | USD 0.50 |

FIFO キューの名前は `.fifo` で終わります。標準キューを後から FIFO キューに変えることはできないので、作るときに決めます。

スループットの上限は、high throughput mode という設定で上げられます。メッセージのクォータのページによると、東京リージョンでは毎秒 9,000 回までです。別のページ（キューの種類の比較）には「メッセージグループの中の順序を緩めて毎秒 30,000 回まで」とあり、2 つのページの書き方は一致していません。この章のスタックは high throughput mode を使っておらず、どちらの数字も確かめていません。クォータは変わるので、使う前に [メッセージのクォータ](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/quotas-messages.html)を見てください。

### メッセージグループ

FIFO キューに送るメッセージには、message group ID が必ず要ります。付けずに送ると、送信が失敗します。

順序が保たれるのは、同じ message group ID を持つメッセージの間だけです。グループが違えば、どちらが先に処理されるかは決まっていません。そして、あるグループのメッセージが 1 件でも受け取られたままになっている間、つまり削除もされず、可視性タイムアウトも切れていない間は、同じグループの次のメッセージはどのコンシューマーにも渡りません。ほかのグループは、その間も進みます。

メッセージグループは、順序の単位であり、同時に並行処理の単位でもあります。この章では、ノート 1 つを 1 つのグループにしました（`owner/noteId`）。同じノートのコマンドは 1 件ずつ順に処理され、違うノートのコマンドは並行して進みます。グループの数に上限はありません。すべてのメッセージに同じ ID を付ければ、キュー全体が 1 列になり、一度に 1 つしか処理できなくなります。

コンシューマーの側から、特定のグループを指定して受け取ることはできません。

### 重複排除

FIFO キューは、送られてきたメッセージの重複排除 ID を覚えています。受け付けてから 5 分のあいだに同じ ID のメッセージが送られてくると、SQS は送信を成功として受け付けますが、キューには入れません。最初のメッセージがすでに受け取られて削除された後でも、5 分のあいだは同じです。

ID の決め方は 2 つあります。送る側が `MessageDeduplicationId` を付ける方法と、キューの content-based deduplication を有効にして、本文の SHA-256 を ID にしてもらう方法です。後者は本文だけを見ていて、メッセージ属性は見ません。

この章は前者を使い、コマンド自身の名前を ID にしています。content-based deduplication は切ってあるので、ID を付けない送信は失敗します。本文から決めると、同じ内容の別のコマンドが 1 件にまとめられ、再試行のときに本文が少しでも変われば別のメッセージになります。どちらも、送る側が意図して決めることです。

### 「exactly-once processing」が指す範囲

ドキュメントは FIFO キューの特徴を「exactly-once processing」と呼び、その中身を 2 つの文で説明しています。重複がキューに入らないこと、そして、メッセージは 1 回渡され、コンシューマーが処理して削除するまでほかには渡らないことです。

この約束には、API リファレンスが自分で書いている穴が 2 つあります。

1 つ目は `ReceiveMessage` の説明にあります。コンシューマーが処理を続けている間に可視性タイムアウトが切れると、メッセージはまた見えるようになり、別のワーカーが受け取って重複して処理できます。

```figure
caption: 可視性タイムアウトを過ぎたワーカー A の横で、同じメッセージがワーカー B に渡る。FIFO キューでも起きる
type: sequence
actor a: ワーカー A
actor q: queue "Commands"
actor b: ワーカー B
step q -> a: t0 M1 を受信: 60 秒隠される
note a: M1 の処理が長引く
note q: t0+60 M1 がまた見える
step q -> b: M1 を再び受信 (receive count 2)
step b -> q: M1 を適用して削除
step q -> b: 同じグループの M2 を受信
note a: 遅れて M1 を適用しようとする
step a -x q: 古い receipt handle で削除: 消えない
```

2 つ目は `SendMessage` の説明にあります。送信の応答が失われ、送る側が 5 分を過ぎてから同じ ID で送り直すと、SQS は重複を見分けられません。キューには、同じコマンドのメッセージが 2 件入ります。

どちらの場合も、キューは約束したとおりに動いています。この章が守りたいことを、1 文で書きます。

**ノートごとに、コマンドはキューが受け付けた順に効き、どのコマンドも、何回届いても 1 回分だけ効く。**

このうちキューが受け持つのは、グループの中の順序と、5 分以内の送り直しです。可視性タイムアウトを過ぎた二重の処理、5 分を過ぎた送り直し、バッチの途中で失敗したときの順序は、ワーカーが受け持ちます。それぞれを壊すテストと、直した実装を、[しくみと実装のページ](/ja/chapters/61-sqs/build.md)で読みます。

## この構成にしないとき

<!-- section: 61.choices -->

順序が結果に関わらないなら、08章の標準キューで足ります。標準キューのほうが安く、スループットの上限もなく、08章で見た S3 のイベント通知のように、FIFO キューには送れない送り手もあります。

順序が関わるように見えても、ワーカーを冪等に作るだけで済むことがよくあります。08章のワーカーは、イベントに付いた `sequencer` を条件にして書き込み、古いイベントが後から届いても新しい記録を上書きしないようにしていました。「新しいほうを残す」で正しい結果になる処理は、順序をキューに頼らずに済みます。FIFO キューが要るのは、行を足すコマンドのように、古いものを捨てては済まず、順に全部を適用しなければならないときです。

FIFO キューでは、1 つのグループの中は 1 件ずつしか進みません。メッセージが少数のグループに集中する処理は、コンシューマーを増やしても速くなりません。

同じメッセージを複数のコンシューマーが読みたい、過去のメッセージを後から読み直したい、という場合は、キューではなくログが合います。[54章](/ja/chapters/54-kinesis.md)の Kinesis Data Streams です。出来事を複数の相手に配るなら [25章](/ja/chapters/25-events.md)のイベントバスとトピック、いくつもの手順の進み具合を管理したいなら [47章](/ja/chapters/47-step-functions.md)の Step Functions を見てください。

1 本のキューを複数の利用者が共有していて、1 人の大量のメッセージがほかの利用者を待たせるのを避けたいだけなら、fair queues という機能があります。標準キューに message group ID を付けて送ると、SQS がほかの利用者のメッセージを先に渡します。順序は保ちません。この章では使っていません。

Cloudflare と Vercel について、2026-10-13 に公式ドキュメントで確かめたことを書いておきます。Cloudflare Queues は、少なくとも 1 回の配送で、発行した順に届く保証はないと書いています。読んだ範囲では、順序を保つ種類のキューは見当たりませんでした。メッセージの大きさは 128 KB までで、遅延は 24 時間まで指定できます。SQS の遅延は 15 分までなので、ここは Queues のほうが広く取れます。Vercel Queues はベータで、少なくとも 1 回の配送です。発行のときに idempotency key を付けると、メッセージの保持期間のあいだ、同じキーの発行が落とされます。順序の保証は、概要のページには書かれていませんでした。順序が要らない処理なら、どちらのキューでも足ります。移る理由にはなりません。
