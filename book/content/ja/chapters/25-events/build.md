# 25 Events: しくみと実装

[最初のページ](/ja/chapters/25-events.md)で、テーブルの変更をイベントにしてバスに載せ、3 つのコンシューマーに配る構成を見ました。このページでは、イベントの形、stream からイベントを作る部分、ルールのパターン、コンシューマー、リプレイの順に、コードを読みます。このページのコードは、どれも AWS を呼ばずにテストできる部分です。

## イベントの契約

<!-- section: 25.contract -->

イベントは、載せる側と受け取る側が別々にデプロイされる前提で交わす約束です。API のリクエストと違って、受け取る側が何人いるかを載せる側は知らないので、形を変えたときに誰が困るかも、載せる側からは見えません。そこで、形をスキーマとして 1 か所に書き、載せる側も受け取る側も同じスキーマで確かめます。

<<< @/examples/25-events/src/contract.ts{envelope}

すべてのイベントが持つ欄は 5 つです。このうち `id` と `version` には、役割があります。

`id` は、配送ではなく出来事に付ける名前です。08章で、SQS のメッセージ ID を冪等性の鍵に使えない理由を説明しました。EventBridge もイベントに `id` を付けますが、これも配送の名前です。同じ変更が 2 回バスに載れば、EventBridge の `id` は 2 つになります。この章の `id` は、ノートの ID とバージョンから作るので、同じ変更なら何回載せても同じ値になります。

`version` は、`detail` の形の版です。いまは 1 だけです。

イベントに題名も本文も入れていないのは、意図したものです。イベントは archive に 7 日残り、デッドレターキューには 14 日残ります。ノートを消した利用者の本文が、消した後もそこに残るのは避けたいので、イベントが運ぶのは ID と版と時刻だけにしました。中身が要るコンシューマーは、ID を使って自分で読みにいきます。

<<< @/examples/25-events/src/contract.ts{events}

イベントは 4 種類です。ノートの 3 つは `v.variant` でまとめ、`type` を見てどの形かを決めます。検査のイベントには、「rejected なら理由がある」という検査を足してあります。あとで出てくる input transformer が理由を文面に埋め込むので、理由のない rejected を通すわけにいかないからです。

### 版の上げ方

スキーマは `v.strictObject` ではなく `v.object` で書いています。`v.object` は、知らない欄を黙って落とします。載せる側が欄を 1 つ足しても、受け取る側は今日のコードのまま読み続けられます。

決まりは次の 2 つにしました。

- 欄を足すだけなら、`version` は変えない。受け取る側は、知らない欄を無視する
- 欄を消す、名前を変える、意味を変えるときは、`version` を上げる。移行の間は、載せる側が古い版と新しい版の両方を載せる

ルールのパターンには `version: [1]` が入っているので、版 2 のイベントは、版 1 のためのコンシューマーには届きません。届いてしまったとしても、スキーマが `v.literal(1)` なので、読み違えずに失敗します。テストは、欄が増えたイベントを読めること、次の版と欄の欠けたイベントを断ることを確かめています。

EventBridge には、スキーマを登録しておく schema registry もあります。この章では使っていません。受け取る側がスキーマを取りにいく先を、リポジトリの中の 1 つのファイルにしたかったからです。チームやリポジトリが分かれるなら、スキーマを置く場所を別に決める必要があります。

<<< @/examples/25-events/src/contract.ts{bus-event}

ターゲットが受け取るのは、`detail` を EventBridge 自身の欄で包んだものです。`replay-name` は、リプレイされたイベントにだけ付きます。

## stream からイベントへ

<!-- section: 25.pipe -->

```figure

type: sequence
actor table: Notes | テーブル
actor pipe: Changes | pipe

actor bus: aih-events | バス
note table: UpdateItem: version 2

step pipe -> table: GetRecords
note pipe: filter を通る
step pipe -> shape: [レコード]

step pipe -> bus: PutEvents
```

pipe は、stream を 1 秒に 4 回読みにいきます。レコードがあれば、まず filter に通します。

<<< @/examples/25-events/src/routes.ts{pipe-filter}

filter の書き方は、あとで出てくるルールのイベントパターンと同じです。通すのは、ソートキーが `NOTE#` か `INSPECTION#` で始まるアイテムのレコードだけにしました。同じテーブルには、添付の記録（`ATTACHMENT#`）も、05章の件数の上限のためのアイテム（`QUOTA`）もあります。それらの変更は、ここで落とします。Pipes の料金は filter を通ったぶんにだけかかるので、要らないものを関数に渡す前に落とすと、関数の実行もそのぶん減ります。

filter に使えない欄があります。ドキュメントによると、`eventName`（INSERT、MODIFY、REMOVE）や `eventID` は pipe が読むときに足す欄で、パターンには書けません。変更の種類で分けるのは、次の関数の仕事になります。

<<< @/examples/25-events/src/shape.ts{record}

stream のレコードは、値が型の名前で包まれた DynamoDB の表記で届きます。ここも型の外から来る値なので、スキーマと照合してから、ふつうのオブジェクトに直します。読むのは、このテーブルのノートと検査の記録が使っている 4 つの型だけです。それ以外の型が来たら、失敗させます。

<<< @/examples/25-events/src/shape.ts{shape}

レコード 1 つを、イベント 1 つに直すか、何も返さないかを決める関数です。見てほしいところが 3 つあります。

1 つ目は `id` の作り方です。stream のレコードにも `eventID` がありますが、使っていません。ノートの ID とバージョンから作っておけば、pipe が同じレコードを 2 回読んでも、いつか別の経路から同じ変更を流し直しても、同じ `id` になります。検査のイベントは、08章が冪等性の鍵にしていたオブジェクトのキーと `sequencer` の組を、そのまま `id` にしました。

2 つ目は、何も返さない場合です。バージョンが変わっていない書き直しと、検査の記録の削除は、どのコンシューマーにも知らせることがないので、イベントにしません。

3 つ目は、読めないレコードで例外を投げることです。`NOTE#` で始まるのにノートとして読めないアイテムは、黙って飛ばすと、その変更があったことを誰も知らないままになります。

<<< @/examples/25-events/src/shape.ts{enrich}

<<< @/examples/25-events/src/shape-lambda.ts{handler}

Pipes の用語では、この関数は enrichment（情報を足す段）です。pipe は関数を同期で呼び、返ってきた配列の要素を 1 つずつターゲットに送ります。空の配列を返せば、何も送りません。ターゲットがイベントバスのとき、返した要素はそのままイベントの `detail` になり、`detail-type` には、pipe の設定に書いた `$.type` が要素の `type` から入ります。

### pipe が止まるとき

関数が例外を投げると、pipe は同じレコードをもう一度渡します。何回まで繰り返すかの既定値は「無制限」で、レコードが stream から消える 24 時間後まで続きます。その間、同じ shard の後ろのレコードは待たされます。読めないアイテムが 1 つあるだけで、他のすべてのノートのイベントが 1 日止まることになります。

この章の pipe は、再試行を 3 回までにして、それでも通らないレコードはデッドレターキューによけます。1 回に渡すレコードも 1 件にしました。まとめて渡すと、1 件の失敗で同じ束の他のレコードもやり直しになるからです。ドキュメントには、束の一部だけを失敗として扱う方法も書かれていますが、enrichment の段では使えないとあります。1 件ずつにすると 1 つの shard で同時に流れるのは 1 件になり、たくさんの変更を速くさばくことはできません。ノートのアプリでは困らないと判断しましたが、どのくらいで詰まるかは計測していません。

pipe が約束する配送も「少なくとも 1 回」です。同じレコードが 2 回関数に渡り、同じイベントが 2 回バスに載ることがあります。そのとき EventBridge の `id` は 2 つになり、`detail.id` は 1 つです。

## ルールとイベントパターン

<!-- section: 25.rules -->

<<< @/examples/25-events/src/routes.ts{rules}

イベントパターンは、イベントと同じ形をした JSON です。書いた欄は、すべて一致しなければいけません。欄ごとの配列は「このどれか」で、書いていない欄は見られません。

3 つのルールを読みます。timeline は、`detail-type` が `Note` で始まるイベントをすべて受け取ります。counter は、件数が動く作成と削除だけです。rejections は、検査のイベントのうち `verdict` が `rejected` のもので、しかも `replay-name` が無いもの、つまりリプレイではないものだけを受け取ります。最後の条件を付けた理由は、リプレイの節で説明します。

どのパターンにも `source` を入れてあります。バスには、いつか別のアプリケーションもイベントを載せるかもしれません。`detail-type` だけで受け取っていると、他人の `NoteCreated` まで受け取ることになります。

このオブジェクトは、スタックとテストの両方が import します。デプロイされるパターンと、手元で確かめたパターンが別物になることはありません。

### 手元でパターンを評価する

パターンが思ったとおりに一致するかを、デプロイせずに確かめたいので、小さな評価器を書きました。

<<< @/examples/25-events/src/pattern.ts{compile}

実装したのは、次の 4 つだけです。

- 値の一致。文字列、数値、真偽値、`null` で、配列に並べたどれかに一致すればよい
- `prefix` と `suffix`
- `exists`
- `numeric`。比較は 1 つか 2 つ

`$or`、`anything-but`、`equals-ignore-case`、`wildcard`、`cidr`、それに `prefix` の中に `equals-ignore-case` を入れるような組み合わせは、実装していません。使おうとすると、ルールを足す時点で `UnsupportedPatternError` を投げます。推測で「たぶん一致しない」と答えるより、止まるほうを選びました。

EventBridge と結果が変わりうるところも、3 つわかっています。数値の一致は、この評価器では `JSON.parse` した後の値で比べますが、EventBridge は書かれた文字列で比べるので、`300` と `300.0` を別の値として扱います。`exists` は、ドキュメントに「leaf でだけ働く」とあるので、オブジェクトが入っている欄を「無い」と扱いましたが、EventBridge がそこでどう答えるかは確かめていません。イベントの中の配列は扱わず、パターンがその欄を見にいったら例外を投げます。

この評価器は、EventBridge の実装ではありません。確かめられるのは、自分が書いたパターンの意図です。実物での答えは、`aws events test-event-pattern` で確かめられます。この章では実行していません。

テストは、一致する場合としない場合を、ルールごとに固定しています。

| イベント | timeline | counter | rejections |
| --- | --- | --- | --- |
| NoteCreated | 一致 | 一致 | 不一致 |
| NoteUpdated | 一致 | 不一致 | 不一致 |
| NoteDeleted | 一致 | 一致 | 不一致 |
| AttachmentInspected、ok | 不一致 | 不一致 | 不一致 |
| AttachmentInspected、rejected | 不一致 | 不一致 | 一致 |
| 同じ rejected のリプレイ | 不一致 | 不一致 | 不一致 |
| `source` が違う NoteCreated | 不一致 | 不一致 | 不一致 |
| `version` が 2 の NoteCreated | 不一致 | 不一致 | 不一致 |

## コンシューマー

<!-- section: 25.consumers -->

守ることを、先に 1 文で書きます。

**同じ変更が何回届いても、どの順で届いても、timeline と件数は、それぞれの変更が 1 回ずつ届いたときと同じになる。**

途中の部品が約束していることを並べると、こうなります。pipe は少なくとも 1 回届けます。EventBridge のドキュメントは、まれに同じルールが 1 つのイベントで 2 回以上動くことがあると書いています。Lambda のドキュメントは、非同期の呼び出しでは関数がエラーを返していなくても同じイベントを複数回受け取ることがあると書いています。そして、リプレイをすれば、同じイベントがもう一度届きます。「ちょうど 1 回」は、どこにもありません。

### 比べて書く: timeline

<<< @/examples/25-events/src/timeline.ts{timeline}

timeline は、ノートごとに「いちばん新しい出来事」を 1 行だけ持ちます。考え方は 08章の検査の記録と同じで、順序を表す値（`rank`）を一緒に保存し、いま持っているものより新しいときだけ書きます。`rank` はノートのバージョンで、削除はどのバージョンよりも後に置きます。

<<< @/examples/25-events/src/dynamodb-projections.ts{timeline-store}

同じイベントがもう一度来れば `rank` が等しいので弾かれ、古いイベントが遅れて来れば `rank` が小さいので弾かれます。重複と順序の入れ替わりを、1 つの条件で両方扱えます。保存するものが「最新の状態」のときは、このやり方がいちばん簡単です。

### 覚えて足す: counter

件数は、同じやり方では守れません。「1 を足す」は、2 回やれば 2 増えます。順序を比べる相手もありません。

<<< @/examples/25-events/src/counter.ts{counter}

`createNaiveCounter` は、届いたら足すだけの実装です。すべてのイベントがちょうど 1 回届くなら正しく動きます。この章ではデプロイせず、テストの中で `createCounter` と並べて動かして、どこで数字がずれるかを見るために置いてあります。

`createCounter` は、足したイベントの `id` を覚えておきます。大事なのは、覚えることと足すことを 1 つの手順にすることです。

<<< @/examples/25-events/src/dynamodb-projections.ts{counter-store}

DynamoDB のトランザクションに、書き込みを 2 つ入れています。1 つは「このイベントは数えた」という印で、まだ無いときだけ書けます。もう 1 つが件数の加算です。両方が成功するか、両方が何も起きないかのどちらかになります。08章は、印を書いた後に S3 の操作が続くので、トランザクションを使えませんでした。ここでは 2 つとも同じテーブルへの書き込みなので、使えます。

印がすでにあれば、DynamoDB はトランザクションを取り消して、1 つ目の書き込みの条件が通らなかったと知らせてきます。それは失敗ではなく、もう数えたという答えなので、成功として返します。他の理由による取り消し（他のトランザクションとの衝突など）は、失敗のまま投げます。

印は増え続けるので、期限を付けました。テーブルの TTL の設定で、DynamoDB が期限を過ぎた印を消します。期限の長さには条件があります。

<<< @/examples/25-events/src/routes.ts{retention}

archive が 7 日ぶんのイベントを持っているなら、7 日前のイベントがリプレイで戻ってくることがあります。そのとき印が消えていたら、もう一度数えてしまいます。印は、リプレイで戻ってきうるイベントより長く残さなければいけません。スタックのテストが、この大小関係を確かめています。

### キューを挟む: counter の入口

<<< @/examples/25-events/src/counter-queue.ts{batch}

counter は、ルールから直接呼ばれるのではなく、キューを挟んで呼ばれます。作りは 08章のワーカーと同じで、失敗したメッセージの ID だけを返します。「もう数えた」は成功なので、リプレイされたイベントがデッドレターキューに溜まることはありません。

timeline のように直接呼ばれる関数と、counter のようにキューを挟む関数では、失敗したときの道筋が違います。

| | ルールから直接（timeline） | キューを挟む（counter） |
| --- | --- | --- |
| 呼ばれ方 | 非同期の呼び出し。1 回に 1 イベント | イベントソースマッピング。最大 10 件 |
| 関数が失敗したとき | Lambda が 2 回やり直し、だめなら on-failure の送り先へ | メッセージがキューに戻り、5 回受信されたら DLQ へ |
| 一度に動く数 | 関数の同時実行数まで | イベントソースマッピングの上限（この章は 2） |
| 溜まったものを見る場所 | 無い。Lambda の中の見えないキュー | SQS のキュー |
| 増える部品 | 無し | キュー 1 本と、空のキューを読みにいくリクエスト |

直接呼ぶほうが部品は少なく済みます。キューを挟むと、流れ込む速さとさばく速さを切り離せて、溜まっている量が見えます。下流に同時実行の上限をかけたい相手（データベースや外部の API）があるなら、キューを挟む理由になります。

### 順序を固定して壊すテスト

テストは、メモリ上のバスに 3 つのルールと 3 つのコンシューマーをつなぎ、4 つ目のルールで何も覚えない counter も動かします。配送の順序と回数はテストが決めます。

| 注入すること | timeline | counter | 覚えない counter |
| --- | --- | --- | --- |
| 同じ配送を 2 回 | 変わらない | 1 | 2 |
| 同じ変更を 2 回載せる（バスの `id` は別） | 変わらない | 1 | 2 |
| 作成、更新、更新を逆順に届ける | 最後の更新 | 対象外 | 対象外 |
| 削除を作成より先に届ける | 削除のまま | 0 | 0 |

4 行目の右 2 列が同じ値なのは、足し算と引き算が順序によらないからです。順序の入れ替わりだけなら、何も覚えない実装でも件数は合います。ずれるのは、同じものが 2 回届いたときです。

このほかに、2 回失敗して 3 回目に成功するターゲットにイベントが 1 回だけ届くこと、どのコンシューマーにも読めないイベントが 3 回試された後によけられること、1 つのコンシューマーが失敗し続けても他のコンシューマーには届くことを確かめています。

コードをわざと 4 か所壊して、テストが落ちることも確かめました。counter が印を見ないようにすると 5 件、timeline が `rank` を比べないようにすると 3 件、更新のイベントの `id` を stream の `eventID` から作ると 2 件、パターンの「どれか」を「すべて」に変えると 11 件が落ちます。

## archive とリプレイ

<!-- section: 25.replay -->

archive は、バスに届いたイベントのうちパターンに一致するものを、決めた日数だけ保存します。リプレイは、archive の中の、指定した時間の幅のイベントを、同じバスにもう一度流します。ルールを指定すれば、そのルールにだけ流せます。

使いどころは 2 つあります。コンシューマーの不具合を直した後で、取りこぼしたぶんを流し直すことと、後から足したコンシューマーに過去のイベントを読ませることです。

ドキュメントが書いている性質を並べます。

- リプレイされたイベントには、`replay-name` という欄が付く。ドキュメントが書いている違いは、この欄だけである
- archive に入った順には流れない。イベントの時刻で 1 分ごとに区切り、古い区切りから流す
- イベントが archive に入るまでに遅れがある。直近のイベントをリプレイするなら、10 分待つように勧められている
- リプレイされたイベントが、もう一度 archive に入ることはない
- リプレイしても、archive からは消えない。同じ幅を何度でも流せる

受け取る側から見れば、リプレイは、まとまった数の重複が順不同で届くことです。前の節のコンシューマーは、そのために作ってあります。

| リプレイの相手 | 結果 |
| --- | --- |
| timeline | 何も変わらない。どの順で届いても同じ |
| counter | 何も変わらない。すべて「もう数えた」 |
| 覚えない counter | 1 だった件数が 2 になる。作成 2、削除 1 をもう一度足すため |
| 後から足した timeline | 元の timeline と同じ中身になる |
| rejections | 1 件も届かない。ルールがリプレイを通さない |

3 行目が、冪等でないコンシューマーにリプレイを届けたときに起きることです。エラーは出ません。数字が黙ってずれます。リプレイは、すべてのコンシューマーが冪等であることを確かめてから実行するか、冪等なコンシューマーのルールだけを指定して実行します。

### 取り消せないコンシューマー

検査に落ちた知らせは、冪等にできません。SNS がメールを送ったら、同じメールをもう一度送らないようにする手段は、この構成の中にありません。

そこで、rejections のルールには、`replay-name` が無いことを条件に入れました。リプレイされたイベントは、このルールに一致しません。EventBridge 自身も、リプレイされたイベントを archive に入れないために、同じ条件を使っています。

この選択で手放すものがあります。知らせの経路が半日止まっていたとしても、その間のイベントをリプレイで流し直すことはできません。その場合は、デッドレターキューに残ったイベントから送り直すことになります。同じ知らせを 2 回送るより、止まっていた間の知らせを人が見て送り直すほうを選びました。逆の選択が正しい知らせもあります。

rejections のルールが実物でリプレイを通さないことは、確かめていません。確かめる手順は[デプロイのページ](/ja/chapters/25-events/deploy.md)にあります。
