# 08 Queue: SQS、DLQ、冪等性、Scheduler

[07章](/ja/chapters/07-uploads.md)でノートに画像を付けられるようになりましたが、宿題が 3 つ残っています。アップロードされたファイルの中身を誰も見ていないこと、孤立したオブジェクトの掃除が手で実行するタスクのままであること、完了した後に同じフォームをもう一度送ると、添付した画像が 1 日後に消えてしまうことです。

この章では、利用者のリクエストの外で動く処理を 2 つ足して、3 つとも片付けます。1 つはアップロードのたびに動いて画像の中身を確かめるワーカーで、もう 1 つは 1 時間ごとに動く掃除です。

章の大半は、道具の使い方ではなく、キューを通した処理の作り方に使います。キューを通ったメッセージは 2 回届くことがあり、順序が入れ替わることも、処理の途中でワーカーが落ちることもあります。そのどれが起きても結果が 1 つになるように、ワーカーを作ります。

前提は 07章です。コードは `examples/08-async/` にあります。アップロードの API も画面も 07章のものをそのまま import して使うので、この章で書くのは増える部分だけです。

新しく出てくるのは、キューが 2 つ、関数が 2 つ、スケジュールが 1 つです。バケットとテーブルは 07章のものを使います。

1 つ目と 2 つ目の図は、イベントで動く部分です。画像が置かれるたび、消されるたびに S3 がキューにメッセージを入れ、Lambda がそれをワーカーに渡し、ワーカーが 4 つの手順を実行します。3 つ目の図は、時計で動く部分です。イベントが来ても来なくても、1 時間ごとにバケットとテーブルを見比べます。両方を持つ理由は、「時計で動かす掃除」の節で説明します。

### 完了のリクエストの中で検査しない理由

07章の「完了」（`PUT /notes/{id}/attachments/{attachmentId}`）の中で、ついでに画像を読んで確かめるのがいちばん素直に見えますが、そうはしません。

完了のリクエストは、利用者が応答を待っています。その中で画像を S3 から読むと、最大 5 MB を読み終わるまで応答を返せませんし、途中で失敗すれば利用者にやり直しを頼むことになります。加えて、完了が呼ばれなかったアップロードは、誰にも確かめられないまま残ります。

検査をリクエストの外に出せば、利用者は待たずに済み、失敗しても利用者の知らないところでやり直せます。そのかわり、処理がいつ終わるかわからないことと、同じ仕事が 2 回走るかもしれないことを引き受けます。この章の残りでは、その 2 つをどう扱うかを説明します。

### サムネイルではなく検査にした理由

章のアウトラインでは、ここでサムネイルを作る予定でした。それを検査に変えた理由を書いておきます。

画像を縮小するには、画像をデコードしてエンコードするライブラリが要ります。よく使われるライブラリは、OS と CPU ごとに違うネイティブのコードを含んでいます。この本の Lambda は arm64 で動き、関数のコードは synth のときに esbuild で 1 つにまとめているので、ネイティブのコードはそのままではまとまりません。Docker の中でビルドするか、Lambda layer を別に用意することになり、章の主題から遠い話が増えます。

そこで、ワーカーの仕事を軽くしました。ファイルの先頭を読んで、本当に画像かどうかと、縦横が何ピクセルかを確かめて記録するだけで、デコードはしません。07章が「S3 は中身を見ない」と書いて残した宿題は、これで片付きます。

キュー、再試行、冪等性の話は、ワーカーの中身がサムネイルでも検査でも変わりません。

### 07章のスタックに足す

スタック（`AihAsync`）は、07章の `UploadsStack` を継承して、増えるものだけを書いています。07章のスタック（`AihUploads`）とは別のスタックなので、両方をデプロイすると、バケットもテーブルも利用者も別々になります。

## 配送の保証は「少なくとも 1 回」

<!-- section: 08.delivery -->

画像がバケットに置かれてからワーカーが動くまでに、メッセージは 3 つのサービスを通ります。それぞれの公式ドキュメントが約束していることを、先に並べます。

- S3 のイベント通知は、少なくとも 1 回届くように設計されている。起きた順に届く保証はない。まれに、同じイベントが重複して届く。ふつうは数秒で届くが、1 分以上かかることもある
- SQS の標準キューは、少なくとも 1 回届ける。メッセージの複製が 2 つ以上届くことがあり、順序が入れ替わることもある
- Lambda のイベントソースマッピング（event source mapping）は、各イベントを少なくとも 1 回処理する。重複して処理することがある

3 つとも「少なくとも 1 回」で、「ちょうど 1 回」はどこにも書いてありません。SQS のドキュメントは、アプリケーションを冪等（idempotent）に、つまり同じメッセージを 2 回処理しても困らないように作ることを求めています。Lambda のドキュメントも、同じことを「強く勧める」と書いています。

SQS には FIFO キューという別の種類があり、そちらは重複を取り除く仕組みを持っています。ただし、S3 のイベント通知は FIFO キューに送れません。それに、キューが重複を取り除いても、ワーカーが処理の途中で落ちれば、同じメッセージはもう一度渡されます。FIFO キューが受け持つ範囲と、リースとしての可視性タイムアウト、redrive は、[61章](/ja/chapters/61-sqs.md)で扱います。

### 受け取っただけでは消えない

SQS のメッセージは、受け取っただけではキューから消えず、一定の時間だけ隠されます。

```figure
caption: 受け取られたメッセージは隠されるだけで、削除されなければまた見えるようになり、別のワーカーに渡る
type: sequence
actor a: ワーカー A
actor q: queue "UploadEvents"
actor b: ワーカー B
note q: t0 メッセージ M が見えている
step q -> a: t1 M を受信: 180 秒隠される
note a: M の処理を始める
note a: t2 まだ動いている、または消えた
note q: t1+180 M がまた見える
step q -> b: t3 再び受信 (receive count 2)
note b: M の処理を始める
note q: ...
note q: 5 回受信されて削除されない:
note q: 次の受信で M は "DeadLetters" へ移る
```

メッセージが隠されている時間を、可視性タイムアウト（visibility timeout）と呼びます。その間に削除のリクエストが届かなければ、メッセージはまた見えるようになり、次に受信したワーカーに渡されます。だから、ワーカーが落ちてもメッセージは失われません。

同じ仕組みのせいで、t3 の時点でワーカー A がまだ動いていれば、2 つのワーカーが同じメッセージを同時に処理することになります。キューは約束したとおりに動いているだけです。SQS のドキュメントは、標準キューについては「隠している間は他の誰にも渡さない」ことさえ保証していません。

この章の可視性タイムアウトは 180 秒、ワーカーのタイムアウトは 30 秒です。Lambda のドキュメントが、キューの可視性タイムアウトを関数のタイムアウトの少なくとも 6 倍にするよう勧めているので、そのとおりにしました。

### メッセージを読む

キューから来るメッセージの本文は、S3 が書いた JSON です。型の外から来る値なので、スキーマと照合します。

メッセージを読むときに気をつけることが 3 つあります。どれも公式ドキュメントに書いてありますが、忘れやすいものです。

1 つ目は、テスト用のイベントが届くことです。通知を設定すると、S3 は `s3:TestEvent` というメッセージを 1 つ送ってきます。このメッセージはふつうのイベントと形が違い、`Records` がありません。読めないメッセージとして失敗させると、デプロイした直後にデッドレターキューに 1 件入ることになるので、ワーカーは受け取ったことをログに書いて、何もせずに成功にします。

2 つ目は、キーがエンコードされていることです。イベントの中のオブジェクトキーは URL エンコードされていて、空白は `+` になっています。この章のキーは英数字とハイフンと `/` だけなので実害はありませんが、デコードしてから使います。

3 つ目は、`sequencer` が入っていないかもしれないことです。`sequencer` はイベントの順序を知るための値で、冪等性の節で使います。ドキュメントは、この値が「PUT と DELETE のリクエストでだけ使われる」と書いています。作成のイベントに `sequencer` が付いていなければ、ワーカーはそのメッセージを失敗にします。順序がわからないイベントを、推測で処理しないためです。

この 3 つ目は、実機で確かめられていません。この章のアップロードはフォームによる POST で、POST で作られたオブジェクトのイベントに `sequencer` が入るかどうかは、ドキュメントからは読み取れませんでした。確かめる手順は[デプロイのページ](/ja/chapters/08-async/deploy.md)に、確かめていないことの一覧は[検証メモ](/ja/chapters/08-async/wrap.md)にあります。

### バッチの一部だけが失敗したとき

Lambda は、キューから最大 10 件をまとめて読んで、ワーカーを 1 回呼びます。何も設定しなければ、ワーカーが例外を投げたときに 10 件すべてがキューに戻り、成功した 9 件ももう一度処理されます。

これを避ける仕組みが partial batch response です。イベントソースマッピングに `ReportBatchItemFailures` を設定すると、ワーカーは失敗したメッセージの ID だけを返せるようになります。

<<< @/examples/08-async/src/worker.ts{batch}

ワーカーはメッセージごとに `try` で囲み、失敗したメッセージの ID だけを集めて返します。Lambda は、返された一覧に ID がないメッセージをキューから削除します。

返し方には決まりがあります。空の一覧を返せば全部が成功の扱いになり、関数が例外を投げれば全部が失敗の扱いになります。返した ID がバッチの中にないものだったり、空文字だったりした場合も、全部が失敗の扱いです。失敗を報告したつもりで形を間違えていて、全部がやり直しになることがあるので、テストはワーカーが返す形を固定しています。

### 何度渡しても処理できないメッセージ

本文が JSON ですらないメッセージは、何度渡されても処理できません。放っておくと、可視性タイムアウトが切れるたびに戻ってきて、ワーカーを呼び続けます。

そこで、5 回受け取られても削除されなかったメッセージを別のキューによける規則（redrive policy）を、キューに付けます。よける先のキューが、デッドレターキュー（dead-letter queue、DLQ）です。5 は、Lambda のドキュメントが勧める下限です。

ワーカーは、読めないメッセージを黙って捨てずに、失敗として報告して DLQ まで行かせます。捨ててしまうと、何かがおかしいことに誰も気づけないからです。DLQ は、人が見るための場所です。

保持期間は、DLQ を 14 日、元のキューを 4 日にしました。標準キューでは、メッセージの期限は最初にキューに入った時刻から数え、DLQ に移っても数え直しません。DLQ の保持期間を元のキューと同じにすると、移ってきたメッセージは人が見る前に消えてしまいます。

## 2 回届いても、結果は 1 つ

<!-- section: 08.idempotency -->

この節が章の本題です。守ることを、先に 1 文で書きます。

**1 つのオブジェクトキーに対して、検査の記録は高々 1 つで、それはワーカーが処理した中でいちばん新しい作成イベントのものである。同じイベントがもう一度届いても、古いイベントが後から届いても、2 つのワーカーが同時に同じイベントを持っても、変わらない。**

前の節で見たとおり、SQS を使っているから 1 回しか処理されない、とは言えません。1 回分の結果しか残らないようにするのは、ワーカーの側の仕事です。

### 同じ仕事を見分ける鍵

2 回目の配送を見分けるには、前に見た仕事だと言える値が要ります。この値を、冪等性の鍵（idempotency key）と呼びます。

最初に思いつくのは SQS のメッセージ ID ですが、鍵には使えません。メッセージ ID は配送に付いた名前で、仕事に付いた名前ではないからです。

- S3 が同じイベントを 2 回送ると、SQS には別々のメッセージとして入り、ID は 2 つになる
- DLQ から元のキューに戻したメッセージは、新しいメッセージとして扱われて、新しい ID が付く

どちらの場合も、中身は同じ仕事です。鍵は、仕事の中身から取らなければいけません。

この章では、オブジェクトキーと `sequencer` の組を鍵にします。`sequencer` は、S3 が作成と削除のイベントに付ける 16 進の文字列で、同じキーのイベントどうしなら、値が大きいほうが後に起きたイベントです。AWS のブログ記事によると、重複して届いた通知は同じ `sequencer` を持っています。

<<< @/examples/08-async/src/sequencer.ts{sequencer}

`sequencer` は、長さが揃っていないことがあります。公式ドキュメントは、比べる前に短いほうの左を 0 で埋めるように求めています。この関数は、すべての値を同じ長さの大文字に揃えます。揃えておけば、ふつうの文字列の比較がそのまま順序の比較になります。DynamoDB の条件式でできる比較は文字列の比較だけなので、この形にしておく必要があります。

### イベントが指すバイト列を読む

ワーカーがイベントを受け取ってからオブジェクトを読むまでの間に、オブジェクトが置き換えられて、同じキーに別のバイト列が入っているかもしれません。それを読んでこのイベントの結果として記録すると、記録と中身がずれます。

<<< @/examples/08-async/src/object-reader.ts{port}

<<< @/examples/08-async/src/s3-object-reader.ts{read}

イベントには、そのとき置かれたオブジェクトの ETag が入っています。`GetObject` に `If-Match` でその ETag を付けると、S3 は、いまのオブジェクトが同じ ETag を持つときだけ中身を返し、違えば 412 を返します。こうすると、いまこのキーにあるものではなく、このイベントが指しているバイト列を読めます。

412 が返ったら、ワーカーは何もしません。置き換えた側の作成イベントが別にあり、そのイベントを受け取ったときに処理するからです。404（もう無い）のときも同じです。

`Range` は、読む量の上限です。アップロードの上限（5 MB）より多くは読みません。フォームを通らずに大きなオブジェクトがこのキーに置かれたとしても、関数のメモリを使い切らないようにするためです。

### 手順と、その順序

<<< @/examples/08-async/src/worker.ts{handle-event}

作成イベント 1 つの処理は 4 つの手順で、どこで止まっても困らない順に並べてあります。

```text
one create event (key K, sequencer S, ETag E)         if the worker stops right after this step
  1. GetObject K, If-Match E                           nothing has changed
  2. judge the bytes (no request to anything)          nothing has changed
  3. PutItem INSPECTION#K, only if absent or older     the record is written; a retry finds it and writes nothing
  4. DeleteObjectTagging K, if ATTACHMENT#K exists     everything is done
  (Lambda deletes the message)                         the message comes back; steps 1 to 4 run again and change nothing

never, in any order of deliveries:
  two records for K, or a record from an older event replacing one from a newer event
```

手順 1 と 2 は読むだけなので、何度実行しても何も変わりません。最初の書き込みは手順 3 で、この書き込みには条件が付いています。

<<< @/examples/08-async/src/dynamodb-inspection-repository.ts{put-if-newer}

条件は、このキーの記録がまだ無いか、あっても `sequencer` がこのイベントより小さいときだけ書く、というものです。[05章](/ja/chapters/05-dynamodb.md)の楽観ロックと同じで、DynamoDB は条件の検査と書き込みを 1 つの手順として実行します。2 つのワーカーが同じイベントを同時に持っていても、両方が検査を通ることはありません。古いイベントが後から来ても、新しい記録を上書きできません。

条件で弾かれたとき、ワーカーは失敗を返しません。もう済んでいる仕事は、成功として扱います。ここで失敗を返すと、何も壊れていないのに、メッセージがキューに戻り、5 回弾かれて DLQ に入ってしまいます。

記録は、07章と同じテーブルの、同じ持ち主のパーティションに置いています。

### 記録があっても手順 4 を飛ばさない

手順 4 は、07章が残した穴を閉じるためのものです。

その穴は、次のようなものでした。署名付き（presigned）のフォームは、期限の 5 分までは何度でも使えます。完了した後に同じフォームをもう一度送ると、S3 はオブジェクトを置き換えて、`upload-state=pending` のタグをもう一度付けます。添付の記録はあるのに、オブジェクトは 1 日後にライフサイクルルールで消されてしまいます。

ただ、置き換えは作成の一種なので、S3 はイベントを送ってきます。ワーカーは、検査を記録したあとで、そのキーに添付の記録があるかを見て、あればタグを外します。数秒後には元の状態に戻ります。

注意が要るのは、手順 4 を置く位置です。ワーカーが手順 3 の直後、手順 4 の前で落ちたとします。メッセージは戻ってきて、2 回目のワーカーは手順 3 で、もう記録があることを知ります。ここで `return` すると、タグは永遠に外れません。1 回目は手順 4 にたどり着かず、2 回目は手順 4 を飛ばしたからです。

そのため、ワーカーは手順 3 の結果がどちらでも手順 4 に進みます。タグを外す操作は何度実行しても結果が同じなので、やり直しても困りません。処理済みの印があることと、処理がすべて終わっていることは別です。印を書いた後に続きがあるなら、印を見て続きを飛ばしてはいけません。

別のやり方が 2 つあります。印をすべてが終わった後に書く方法と、印と残りの書き込みを 1 つのトランザクションに入れる方法です。トランザクションは、すべてが同じ DynamoDB のテーブルへの書き込みなら使えますが、この章の手順 4 は S3 への操作なので使えません。

### 順序を固定して壊すテスト

テストは、メッセージが届く順序と、ワーカーが止まる場所を 1 つずつ固定して、そのあとの記録を調べます。メッセージをワーカーの関数に直接渡しているので、キューも時計も乱数も要りません。

| 注入すること | 結果 |
| --- | --- |
| 同じメッセージを 2 回渡す | 2 回目は何も書かない。記録は時刻まで同じ |
| 同じイベントを、別の ID の 2 つのメッセージで渡す | 記録は 1 つ |
| ワーカー A が書く直前で止まっている間に、同じメッセージをワーカー B に渡す | B が書く。A は再開しても何も書かず、失敗も返さない |
| 置き換えの後、新しいイベント、古いイベントの順に渡す | 古いほうは 412 で何もしない。記録は新しいほう |
| 同じバイト列で置き換えた後、新しいイベント、古いイベントの順に渡す | 古いほうは読めるが、条件で弾かれる |
| 削除のイベントを、作成のイベントより先に渡す | 記録は残らない |
| 削除、再作成の後、再作成のイベント、削除のイベントの順に渡す | 遅れてきた削除は、新しい記録を消さない |
| 記録の書き込みを失敗させる | 記録なし。再配送で 1 つできる |
| 記録を書いた後、タグを外すところで失敗させる | 記録あり、タグは付いたまま。再配送でタグが外れる |

表の 3 行目は、可視性タイムアウトが切れて二重に実行される場合です。テスト用の仕掛けで、ワーカー A の書き込みを合図があるまで待たせ、その間にワーカー B を最後まで走らせています。

削除のイベントも扱っているのは、オブジェクトが消えたあとに検査の記録を残さないためです。ここでも `sequencer` を使います。表の 7 行目のように、遅れてきた削除のイベントをそのまま実行すると、その後に置かれたオブジェクトの記録まで消してしまいます。削除には「この削除より古い記録だけを消す」という条件を付けて、それを防いでいます。

コードをわざと 2 か所壊して、上の表のテストが 4 つ落ちることも確かめました。壊したのは、手順 4 を記録が書けたときだけ実行するようにする変更と、同じ `sequencer` でも書けるようにする変更です。

### 残っている穴

閉じていないところを書いておきます。

検査の記録が、オブジェクトのないまま残る経路が 2 つあります。1 つは、ワーカー A が作成イベントの手順 3 の直前にいるときに、ワーカー B が同じキーの削除イベントを処理し終えた場合です。B が見た時点では記録がまだ無いので何も消えず、そのあとで A が記録を書きます。もう 1 つは、ライフサイクルルールによる削除です。この通知（`LifecycleExpiration:Delete`）に `sequencer` が入るかどうかを、確かめられていません。入っていなければ、ワーカーは何もしません。順序がわからない削除で記録を消すより、古い記録が残るほうを選びました。

どちらの場合も、利用者には見えません。検査の記録は、添付の記録がなければ誰にも読まれないので、困るのはテーブルに小さな行が残ることだけです。この穴を閉じるには、削除のときに記録を消すかわりに、`sequencer` を持った「消えた」という印（tombstone）を同じ条件で書き、DynamoDB の TTL で片付けます。この章では実装していません。

05章が記録していた、作成の再試行でノートが 2 件できる問題も、同じ形をしています。呼び出し側が、同じ依頼であることを示す値（`Idempotency-Key` のようなヘッダー）を送り、サーバーがその値を鍵にして条件付きで書けば直ります。考え方はこの節と同じですが、この章では直していません。

## 時計で動かす掃除

<!-- section: 08.housekeeping -->

イベントで動くワーカーは速く動きますが、イベントが来なければ動きません。通知が 1 分遅れることもあれば、メッセージが DLQ に入ったまま誰にも気づかれないこともあります。

そこで、イベントを待たない処理をもう 1 つ持ちます。バケットとテーブルのいまの中身を見比べて、ずれていたら直す処理で、突き合わせ（reconciliation）と呼ばれるやり方です。イベントは早く直すための合図で、必ず直ることを受け持つのは突き合わせです。

<<< @/examples/08-async/src/housekeeping.ts{housekeeping}

掃除の関数は、3 つの仕事をします。

1 つ目は、07章の掃除（`sweep`）そのものです。添付の記録もノートもないオブジェクトを消します。07章の関数を、変えずに呼んでいます。

2 つ目は、検査で「だめ」と判定された添付を消すことです。順序は 07章の削除と同じで、記録を先に、オブジェクトを後に消します。ワーカーが判定した時点ですぐ消さないのは、意図したものです。アップロードされたばかりのオブジェクトには、完了のリクエストがまだ来るかもしれません。07章は、その衝突を「1 時間より新しいオブジェクトには触らない」という時間の区切りで避けていました。消す処理はすべて、その区切りより古いオブジェクトだけを対象にします。

消す前に、判定がいまのオブジェクトについてのものかも確かめます。判定の時刻がオブジェクトの更新時刻より前なら、その判定は置き換えられる前のバイト列についてのものなので、使いません。

3 つ目は、添付されている画像の pending のタグを、もう一度外すことです。ワーカーの手順 4 と同じことを、イベントに頼らずに実行します。対象は、作成から 1 時間以上たっていて 2 日より新しいオブジェクトで、2 つ目の仕事でいま消したものは飛ばします。2 日より古いのにまだ残っているオブジェクトは、pending のタグが付き直していないか、もう手遅れかのどちらかだからです。ライフサイクルルールが pending のオブジェクトを消すのは、早くても作成の 1 日後です。1 時間ごとに動く掃除は、それまでに 20 回以上、同じオブジェクトを通ります。

手順 4 だけでは、ごく狭い隙間が残ります。完了の処理がタグを外してから添付の記録を書くまでの間にフォームが再送されて、しかもその通知を、記録が書かれる前にワーカーが処理した場合です。3 つ目の仕事は、その隙間もふさぎます。

### 重なっても同じ状態に行き着く

掃除は、起動されるときに時刻も入力も受け取らず、何を消すかを毎回バケットとテーブルから読みます。そのため、2 回続けて動いても、2 つが同時に動いても、途中で止まっても、行き着く状態は同じです。テストは、その 3 つの場合を確かめています。記録を消してからオブジェクトを消すまでの間に落ちた場合は、次の回に 07章の掃除が、記録のないオブジェクトとして拾います。

<<< @/examples/08-async/src/housekeeping-lambda.ts{handler}

この関数を 1 時間ごとに起動するのが、EventBridge Scheduler です。公式ドキュメントによると、Scheduler はターゲットへの配送を「少なくとも 1 回」保証します。つまり、掃除の起動も 2 回届くことがあります。掃除を重なっても困らない作りにしたのは、そのためでもあります。

Scheduler は、Lambda 関数を非同期に呼びます。非同期の呼び出しでは、関数が失敗すると Lambda が自分で 2 回までやり直します（[15章](/ja/chapters/15-email.md)でもう一度出てきます）。掃除では、これを 0 回にしました。失敗した回をやり直さなくても、1 時間後に次の回が動くからです。

何が消されるかは、手元から先に見ることもできます。使い方は 07章の `uploads:sweep` と同じです。

```bash
vp run async:housekeeping
vp run async:housekeeping --delete
```

このタスクはあなたの認証情報で動き、デプロイされた関数は関数自身のロールで動きます。

最後に、費用について 1 つ断っておきます。この掃除は、動くたびにバケットのすべてのオブジェクトを見るので、置いてある枚数に比例して時間も料金もかかります。数字は[費用のページ](/ja/chapters/08-async/wrap.md)の「料金」に書きました。
