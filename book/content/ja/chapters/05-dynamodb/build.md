# 05 KV Store: しくみと実装

[前のページ](/ja/chapters/05-dynamodb.md)で、テーブルのキーと、`version` を足した契約を決めました。このページでは、保存先を DynamoDB に差し替え、同時の更新、件数の上限、ページ送り、届かなかったレスポンスを順に実装します。

## 条件付き書き込みで上書きを防ぐ

<!-- section: 05.conditional -->

同じノートを 2 つのタブで開き、両方で編集して保存した場合を考えます。

```figure
caption: 2 つのタブが同じ version から保存すると、先の保存だけが通り、後の保存は 409 になります。
type: sequence
actor a: タブ A
actor store: 保存されているノート
actor b: タブ B
note store: v1 "draft"
step a -> store: t1 GET
step store --> a: version 1
step b -> store: t1 GET
step store --> b: version 1
step a -> store: t2 PUT expectedVersion=1
step store --> a: 200
note store: v2 "from A"
step b -> store: t3 PUT expectedVersion=1
step store --x b: 409
note store: v2 "from A"
note b: t4 A の文面を自分のと並べて表示
```

t3 でタブ B の保存を通してしまうと、タブ A の変更は誰にも知られないまま消えます。これを防ぐ方法が楽観ロック（optimistic locking）です。先にロックを取るのではなく、書き込む瞬間に、保存されているノートが自分の見ていた版のままかどうかを確かめます。

ノートを読んで `version` を比べ、同じなら書くという手順をアプリのコードで 2 回のリクエストに分けると、その間に別の書き込みが割り込めます。比較と書き込みは、データベースの中で 1 つの操作として実行される必要があります。DynamoDB では、条件式（condition expression）がその役目を果たします。

<<< @/examples/05-dynamodb/src/dynamodb-repository.ts{update}

楽観ロックの実体は `ConditionExpression: "version = :expected"` の 1 行です。DynamoDB は条件の評価と更新を 1 つの操作として実行するので、同じ `version` を持った 2 つの書き込みが両方通ることはありません。条件が成り立たなければ、DynamoDB は `ConditionalCheckFailedException` を返します。

そのあとの読み取りは、更新とは別の操作です。条件が成り立たなかった理由がノートが無いからなのか `version` が進んだからなのかを知り、いまの内容を呼び出し側に渡すために読んでいます。元の更新とこの読み取りの間に、ノートがもう一度変わることはあり得ます。したがって `current` は 409 を返した時点に近い内容であって、いまも正しい内容とは限りません。

作成にも同じ仕組みを使います。

<<< @/examples/05-dynamodb/src/dynamodb-repository.ts{create}

アプリは、`conflict` を HTTP の 409 にして返します。

### 件数に上限を付ける

この API は誰でも `POST` できるので、何もしなければ、テーブルは入れられただけ大きくなります。そこで、持ち主 1 人のノートを 100 件までにします。

いまの件数を数えて 100 未満なら書くという手順には、更新のときと同じ問題があります。数えてから書くまでの間に別の作成が割り込めるので、作成が同時に 2 つ来ると、どちらも 99 件と数えて、どちらも書きます。

そこで、件数を 1 つのアイテムに持たせます。

<<< @/examples/05-dynamodb/src/dynamodb-repository.ts{quota}

持ち主ごとに `sk` が `QUOTA` のアイテムを 1 つ置き、そこに件数を入れます。作成するときは、まずこのアイテムに「100 未満なら 1 足す」という条件付きの書き込みをして、枠を 1 つ取ります。条件の評価と加算は 1 つの操作なので、最後の 1 枠を 2 人が取ることはありません。枠が取れたらノートを書きます。取れなければ リポジトリが `quota_exceeded` を返し、アプリが 409 にします。

枠を取る書き込みとノートの書き込みは、別々の 2 回のリクエストです。その間で関数が止まると、枠だけが取られてノートが無い状態が残り、件数は実際より 1 多いままになります。逆のずれは起きません。したがって、この上限が守るのは 100 件を超えないことで、ちょうど 100 件まで入ることは約束しません。ずれるとしたら、入る件数が少なくなる側だけです。削除も同じ順序で、ノートを消してから枠を返します。

DynamoDB には、2 つのアイテムを 1 回でまとめて書くトランザクションの機能もあります。この章では使っていません。[30章](/ja/chapters/30-data-modeling.md)で使います。

上限の値は `composeApp` が決めています。上限を渡さずに作ったリポジトリは、件数を数えません。

## 読み取りの整合性を選ぶ

<!-- section: 05.consistency -->

DynamoDB の読み取りには 2 種類あります。

| | 結果整合（eventually consistent） | 強整合（strongly consistent） |
| --- | --- | --- |
| 直前の書き込みが見えるか | 見えないことがある。少し待って読み直せば見える | 成功した書き込みはすべて反映されている |
| 料金 | 強整合の半分 | 4 KB までのアイテム 1 件で 1 read request unit |
| 既定 | こちら | `ConsistentRead: true` を指定する |

公式ドキュメントによると、書き込みは、成功のレスポンスを返した時点で永続化されています。結果整合の読み取りで直前の書き込みが見えないことがあるのは、書き込みが消えたからではなく、読みに行った先にまだ届いていないからです。

この章では、整合性を操作ごとに選びます。

<<< @/examples/05-dynamodb/src/dynamodb-repository.ts{get}

1 件の取得は強整合にしました。保存した直後に同じノートを読み直して保存前の内容が返ってくると、利用者には保存が失敗したように見えるからです。

<<< @/examples/05-dynamodb/src/dynamodb-repository.ts{list}

一覧は結果整合のままにしました。料金が半分で、一覧が一瞬古くても困らないからです。そのかわり、作成した直後のノートが次の一覧に出ないことがあり得ます。06章で画面を作るときは、作成のレスポンスで受け取ったノートを一覧に足して表示すれば、このずれを利用者に見せずに済みます。

操作ごとに選べるのは、条件付き書き込みが読み取りの整合性に頼っていないからです。古い一覧を見て更新を送っても、`version` の条件は DynamoDB の中で最新の値に対して評価されます。古い読み取りは 409 を増やすことはあっても、上書きを起こすことはありません。

なお、強整合の読み取りが使えるのはテーブル本体と local secondary index だけで、global secondary index では使えません。この章はインデックスを使いません。global secondary index は [30章](/ja/chapters/30-data-modeling.md)で足します。

## 取りこぼさずにページを送る

<!-- section: 05.pagination -->

`Query` が 1 回で返す結果は最大 1 MB で、超えたぶんは返ってきません。エラーにもなりません。この API はそれに加えて、`Limit` で 1 ページの件数も絞っています。どちらの理由で途中で止まっても、DynamoDB が出す合図は同じです。この合図を見ずに、全部取れたものとして一覧を返していると、ノートが増えたある日から、古いノートがエラーもなく表示されなくなります。

DynamoDB は、続きがあるかもしれないとき、レスポンスに `LastEvaluatedKey` を付けます。この値を次の `Query` の `ExclusiveStartKey` に渡すと、続きから読めます。この API は、この値をカーソル（cursor）として呼び出し側に渡します。

<<< @/examples/05-dynamodb/src/app.ts{list}

クエリ文字列の値は文字列で届くので、`limit` は数値に直してから、整数であることと範囲を確かめます。1 ページは 20 件までで、それより大きい `limit` は 400 で断ります。一覧に載せるのは `noteSummarySchema` の 5 つのフィールドだけで、本文は載せません。04章と同じく、1 回のレスポンスが 20 KiB を超えないようにするためです。本文が要るときは `GET /notes/:id` で取ります。`version` を載せてあるのは、一覧を取ったあとでノートが変わったかどうかを、クライアントが見分けられるようにするためです。

本文を外しているのは、レスポンスを組み立てる `app.ts` です。リポジトリはアイテムを本文ごと読むので、DynamoDB から読み取る量は、本文を返していたときと変わりません。

カーソルは呼び出し側に渡り、次のリクエストで戻ってきます。戻ってきたカーソルは、ほかの入力と同じく信用できない値です。そのまま DynamoDB に渡さず、復号して形を確かめます。

<<< @/examples/05-dynamodb/src/repository.ts{cursor}

公式ドキュメントも注意しているとおり、`LastEvaluatedKey` があっても、まだアイテムがあるとは限りません。結果がちょうどページの境目で終わった場合にも付きます。その場合、次のページは空で、カーソルは `null` になります。したがって呼び出し側は、`nextCursor` が `null` になるまで読むことを終わりの条件にします。返ってきた件数が `limit` より少ないことを、終わりの合図にしてはいけません。

## レスポンスが届かなかったとき

<!-- section: 05.lost-response -->

ネットワーク越しの書き込みには、成功と失敗のほかに、どちらだったのかが分からないという 3 つ目の結果があります。

```figure
caption: レスポンスが失われた保存を再試行すると、自分の 1 回目の書き込みが原因で 409 が返ります。
type: sequence
actor client: クライアント
actor server: サーバー
step client -> server: t1 PUT expectedVersion=1
step server -> server: 更新を適用する
note server: v2 "final"
step server --x client: t2 200 OK（レスポンスが失われる。タイムアウト）
step client -> client: t3 保存されたかどうか分からない。再試行
step client -> server: t3 PUT expectedVersion=1
step server -> server: version は 1 ではなく 2
note server: v2 "final"
step server --> client: t4 409 conflict, current = v2 "final"
```

t2 の時点で、呼び出し側は保存が済んだかどうかを知りません。再試行しなければ、保存されていなかった場合に変更を失うので、再試行します。すると t4 で 409 が返ってきます。原因は他人の書き込みではなく、**自分の 1 回目の書き込み**です。

この場面で、楽観ロックは 2 つの役に立っています。まず、再試行が二重に適用されませんでした。`version` は 2 のままで、3 にはなっていません。そして、409 に `current` が付いているので、呼び出し側は何が起きたのかを判断できます。

<<< @/examples/05-dynamodb/src/client.ts{outcome}

保存されているノートが、ちょうど 1 つ先の `version` で、送ったとおりの内容なら、望んだ書き込みは済んでいます。型付きのクライアントは、この場合を成功として返します。

<<< @/examples/05-dynamodb/src/client.ts{update}

この判断には限界があります。別の誰かが、まったく同じ内容を同じ `version` で保存していた場合と区別できません。ただ、その場合も保存されている内容は望んだとおりなので、成功として扱っても困りません。逆に、自分の書き込みが済んだあと、再試行までに別の誰かがさらに保存していた場合は、conflict として返ります。自分の保存は 1 回済んでいますが、いま保存されているのは他人の内容なので、その内容を見せるのが安全な側の結果です。

作成には、この守りがありません。`POST /notes` は、再試行と新しいノートの作成を見分ける手がかりを持っていないので、レスポンスを失って再試行すると、同じ内容のノートが 2 件できます。テストは、この挙動を仕様として記録しています。直すには、同じ依頼であることを示す値を呼び出し側が送る必要があります。この本では、そこまでは直していません（考え方は、[08章](/ja/chapters/08-async.md)でワーカーを冪等にするときと同じです）。
