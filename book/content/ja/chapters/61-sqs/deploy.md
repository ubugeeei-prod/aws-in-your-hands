# 61 SQS: デプロイ

[しくみと実装のページ](/ja/chapters/61-sqs/build.md)で読んだワーカーを AWS にのせるスタックを読み、キューを誰が使えるかを整理してから、デプロイと確認の手順を並べます。この章の執筆では、AWS に対して何も実行していません。手順は用意したもので、結果は確かめていません。

## スタックを読む

<!-- section: 61.stack -->

スタックが使うリソースの種類は 9 つです。どれも、この本が固定している cdkd 0.296.28 が専用の実装を持っています。

### 2 本のキュー

<<< @/examples/61-sqs/infra/lib/sqs-stack.ts{queues}

FIFO キューのデッドレターキューは FIFO キューでなければならないので、2 本とも `fifo: true` です。

名前を自分で書いているのは、道具の都合です。FIFO キューの名前は `.fifo` で終わらなければなりません。この本が固定している cdkd 0.296.28 は、名前の書かれていないキューに論理 ID から名前を付けますが、そのときに `.fifo` を足しません。導入済みのパッケージのソースで確かめました。名前を書かずに FIFO キューをデプロイすると、作成が断られるはずです。名前を固定したので、同じアカウントの同じリージョンには、このスタックを 1 つしか置けません。

`contentBasedDeduplication` は、既定値と同じ `false` を、あえて書いています。送る側が重複排除 ID を必ず付ける、という取り決めをここに残すためです。

数字は、08章と同じ考え方で決めています。可視性タイムアウトはワーカーのタイムアウトの 6 倍、`maxReceiveCount` は Lambda のドキュメントが勧める下限の 5、保持期間は元のキューが 4 日でデッドレターキューが 14 日です。`receiveMessageWaitTime` は、待ち時間を指定しない受信をロングポーリングにする設定です。

暗号化は、SQS が管理する鍵（SSE-SQS）です。`enforceSSL` は、TLS を使わないリクエストを断るステートメントを、キューポリシーに足します。

### テーブル

<<< @/examples/61-sqs/infra/lib/sqs-stack.ts{table}

テーブルには、ノートと目印の 2 種類のアイテムが入ります。`timeToLiveAttribute` に指定した `expiresAt` を持つのは目印だけなので、DynamoDB が消すのも目印だけです。DynamoDB のドキュメントによると、期限を過ぎたアイテムは、ふつう数日以内に消されます。期限ちょうどに消えるわけではありませんが、目印が長く残るぶんには害がありません。

`maxReadRequestUnits` と `maxWriteRequestUnits` は、[05章](/ja/chapters/05-dynamodb/deploy.md)から使っている、テーブルが 1 秒に受ける読み書きの上限です。コマンド 1 件の適用は書き込み 4 ユニットなので、1 秒 25 件までになります。それを超えたぶんは DynamoDB に断られ、メッセージはキューに戻ります。

### ワーカーとロール

<<< @/examples/61-sqs/infra/lib/sqs-stack.ts{worker}

ロールに許しているのは 4 つです。自分のロググループへの書き込み、コマンドのキューからの受信と削除、デッドレターキューへの送信、テーブルへの `PutItem` と `UpdateItem` です。

トランザクションのための権限は、中に入れる書き込みの権限と同じものです。`TransactWriteItems` という名前の操作を許す必要はありません。デッドレターキューについては、送信だけを許しています。ワーカーがデッドレターキューを読むことはないからです。

### イベントソースマッピング

<<< @/examples/61-sqs/infra/lib/sqs-stack.ts{mapping}

`maxConcurrency` は、このキューのために同時に動くワーカーの上限です。設定できるのは 2 から 1,000 までで、この章は下限の 2 にしました。FIFO キューでは、もう 1 つ上限があります。メッセージを持つグループの数です。待っているコマンドが 1 つのノートのものだけなら、動くワーカーは 1 つです。

Lambda には、イベントソースマッピング専用のポーラーを確保しておく provisioned mode という設定もあります。追加の料金がかかり、maximum concurrency とは一緒に使えません。この章では使っていません。

### アラーム

<<< @/examples/61-sqs/infra/lib/sqs-stack.ts{alarms}

1 つ目は、デッドレターキューに 1 件でもメッセージがあれば鳴ります。SQS のガイドが勧めている指標です。ワーカーが自分でよけたメッセージも、SQS が移したメッセージも、ここに出ます。

2 つ目は、コマンドのキューのいちばん古いメッセージの年齢です。この指標は、標準キューと FIFO キューで意味が少し違います。標準キューでは、3 回以上受け取られて削除されないメッセージは列の後ろに回され、指標から外れます。FIFO キューは順序を変えないので、失敗し続けるメッセージがあれば、年齢はそのまま伸びていきます。しきい値は 2 分で、1 分ごとの値が 2 回続けて超えたときに鳴ります。1 回失敗しただけのメッセージは、可視性タイムアウトの 60 秒後に戻って処理されるので、鳴りません。失敗し続けるメッセージがデッドレターキューに移るのは 5 分後なので、1 つのノートが止まっていれば、こちらが先に鳴ります。ワーカーが動いていない、処理が追いついていない、という場合も、この指標に出ます。

アラームは、既定では誰にも通知しません。[19章](/ja/chapters/19-observability.md)のスタックが出力するトピックの ARN を渡すと、2 つとも、そのトピックに通知します。

```bash
vp run sqs:infra:deploy -c alarmTopicArn=<19章の AlarmTopicArn>
```

## 誰がキューを使えるか

<!-- section: 61.access -->

SQS のキューを使う権限は、2 か所で決まります。使う側の IAM ポリシーと、キューに付けるキューポリシーです。IAM のドキュメントによると、同じアカウントの中では、2 つのポリシーが許す範囲を合わせたものが使え、どちらかに明示的な拒否があれば拒否が優先されます。この章のワーカーは、自分のロールのポリシーだけで受信しています。

既定のキューポリシーにあるのは、TLS を使わないリクエストを断るステートメントだけです。許可のステートメントはありません。あなたの認証情報で `sqs:send` が送れるのは、あなたの IAM ポリシーが許しているからです。

### 別のアカウントから送る

<<< @/examples/61-sqs/infra/lib/sqs-stack.ts{queue-policy}

別のアカウントから送らせるには、キューポリシーに許可を足します。この章のスタックは、`senderAccountId` を渡したときだけ、そのアカウントに `sqs:SendMessage` を許します。受信も削除も許しませんし、デッドレターキューには何も足しません。

```bash
vp run sqs:infra:deploy -c senderAccountId=<送る側のアカウント ID>
```

キューポリシーが許すのは、相手のアカウントまでです。相手のアカウントの中で、どのロールが送れるかは、相手の側の IAM ポリシーが決めます。両方が許して、はじめて送れます。この経路は、手元にアカウントが 1 つしか無いので、テンプレートのアサーションで形を確かめただけです。

### SNS から受け取る

SNS のトピックからキューにメッセージを流すときも、キューポリシーが要ります。トピックに `sqs:SendMessage` を許すステートメントを足してから、キューをトピックに購読させます。[25章](/ja/chapters/25-events.md)のスタックが、標準のトピックと標準キューでこの形を作っています。

FIFO のトピックは、FIFO キューにも標準キューにも配送できます。順序と重複排除が保たれるのは、FIFO のトピックから FIFO キューへ流す場合です。標準キューに流すと、順序はできるだけ、配送は少なくとも 1 回になります。この章のスタックに、トピックはありません。

### 暗号化と KMS

キューの暗号化には 2 通りあります。SQS が管理する鍵を使う SSE-SQS と、KMS の鍵を使う SSE-KMS です。どちらも暗号化するのは本文で、キューの名前、メッセージの ID と属性、メトリクスは暗号化されません。

SSE-SQS では、使う側に追加の権限は要りません。SSE-KMS にすると、送る側には `kms:GenerateDataKey` と `kms:Decrypt` が、受け取る側には `kms:Decrypt` が要ります。Lambda のワーカーなら、実行ロールに `kms:Decrypt` を足します。S3 や SNS のような AWS のサービスに送らせる場合について、ガイドは、自分で管理する鍵を作り、その鍵のポリシーでサービスを許すよう書いています。SQS 用の AWS 管理の鍵（`alias/aws/sqs`）では足りません。

KMS の鍵にすると、鍵の月額と、SQS が KMS を呼ぶ回数ぶんの料金がかかります。見積もりは[費用のページ](/ja/chapters/61-sqs/wrap.md)にあります。この章が SSE-SQS を選んだのは、コマンドの本文を、アカウントの中のほかの人から隠す必要がないからです。鍵を使える人をキューの権限とは別に絞りたい、という要件があるときに、SSE-KMS にします。

### デッドレターキューとして使えるキュー

何も設定しなければ、同じアカウントとリージョンのどのキューも、あるキューを自分のデッドレターキューに指定できます。指定できる元のキューを絞る設定が、redrive allow policy です。元のキューを 10 本まで名指しするか、すべて断るかを選べます。この章のスタックでは設定していません。

## デプロイして確かめる

<!-- section: 61.deploy -->

ここから先は、AWS を変更します。02章の bootstrap が済んでいることが前提です。

```bash
vp run sqs:infra:diff
vp run sqs:infra:deploy
```

デプロイが終わったら、コマンドを送ります。

```bash
vp run sqs:send
vp run sqs:status
```

`sqs:send` は、`smoke/demo` というノートに 4 回送信します。題を `Shopping` にするコマンド、`milk` を足すコマンド、同じ `milk` のコマンドをもう一度、最後に `eggs` を足すコマンドです。3 回目は、重複排除 ID が 2 回目と同じなので、キューに入らないはずです。

`sqs:status` は、2 本のキューのおよその件数、デッドレターキューの中身、ノートの状態を表示します。期待する結果は、題が `Shopping`、行が `milk` と `eggs` の 2 つ、適用されたコマンドが 3 件です。`milk` が 2 行あれば、重複排除が期待どおりに働いていません。

読めないメッセージの扱いも確かめられます。

```bash
vp run sqs:send --poison
vp run sqs:status
```

`--poison` を付けると、`milk` と `eggs` の間に、コマンドでない本文のメッセージを 1 件送ります。期待する結果は、ノートの行が待たされずに増え、デッドレターキューに 1 件あり、その 1 件に、ワーカーがよけたことを示す属性が付いていることです。数分のうちに、デッドレターキューのアラームも鳴るはずです。ワーカーのログは、スタックの出力 `WorkerLogGroupName` のロググループにあります。

デッドレターキューのメッセージを元のキューに戻すには、`--redrive` を付けます。

```bash
vp run sqs:status --redrive
```

このタスクは、行き先としてコマンドのキューを名指しします。行き先を省くと、SQS は、メッセージを元いたキューに戻します。ワーカーが自分で送ったメッセージには「元いたキュー」の記録が無いはずなので、名指しにしました。この動きは確かめていません。読めないメッセージは、戻してもまたワーカーによけられます。戻す意味があるのは、ワーカーを直した後か、待てば直る失敗で移ったメッセージです。

最後に、ドリフトを確かめます。

```bash
vp run sqs:infra:drift
```
