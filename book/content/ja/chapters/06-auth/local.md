# 06 Auth: 手元で動かす

[前のページ](/ja/chapters/06-auth.md)では、API が呼び出し元を確かめ、自分のノートにしか届かないようにする仕組みを見ました。このページでは、そのアプリを Cognito なしで手元で動かし、SPA の側のサインインの実装を読みます。

## 手元で 2 人の利用者として動かす

ターミナルを 2 つ使い、それぞれで次のタスクを実行します。

```bash

vp run dev:app:web
```

<http://localhost:5173> を開き、利用者名（既定は `alice`）を入れてサインインします。ノートを作ったら、別のブラウザかプライベートウィンドウで `bob` としてサインインしてみてください。Bob の一覧は空のはずです。同じノートを 2 つのタブで開いて両方で保存すると、後から保存したタブに、保存済みの内容と自分の入力の両方が出ます。

Docker も、AWS の認証情報も、ユーザープールも要りません。

`POST /local/token` は、利用者名を送ると、その利用者のトークンを無条件に返します。パスワードはありません。手元でアプリを 2 人の利用者として動かすための道具です。

このエンドポイントがデプロイに混ざると、誰でも任意の利用者になれてしまいます。混ざらないことは、次の 2 つの仕組みで保証しています。

- このエンドポイントと開発用の検証は、`dev.ts` と `local-auth.ts` にだけあります。Lambda の入口（`lambda.ts`）はどちらも import しないので、バンドルに入りません
- 開発用のトークンは、共有の秘密で署名します（HS256）。API Gateway の JWT オーソライザーが受け付けるのは RSA 系の署名だけなので、このトークンをデプロイした API に送っても通りません

開発用のサインインは、Cognito の模擬ではありません。次のものは再現しません。

- マネージドログインとパスワード。実際のサインイン画面、パスワードの規則、初回のパスワード変更がこれにあたります
- 認可コードと PKCE の往復。SPA の Cognito 用のコード（`web/src/auth/cognito.ts`）は、手元では一度も実行されません
- API Gateway の JWT オーソライザー。不正なトークンが関数に届く前に拒否されることと、そのときのレスポンスの形は再現しません
- トークンの期限、更新、失効。1 時間後に何が起きるかは、手元ではわかりません

とくに 2 つ目が重要です。手元で動いているのはサインインした後のアプリで、Cognito でのサインインそのものではありません。

### 設定は実行時に読む

<<< @/examples/06-auth/web/src/config.ts{config}

SPA は、起動するときに `/config.json` を読み、API の場所とサインインの方法を知ります。`web/public/config.json` は手元用で、デプロイするときは、スタックの出力から作った `config.json` に置き換えます。そのため、SPA は一度ビルドすれば、どのデプロイにも向けられます。

この設定に秘密の値はありません。クライアント ID もサインイン用のドメインも、ページを読み込んだ人なら誰でも見られます。ブラウザで動くアプリは秘密の値を持てないので、そのようなアプリをパブリッククライアント（public client）と呼びます。

## SPA からサインインする

SPA は、authorization code grant と PKCE の組み合わせでサインインします。手順は、[章の最初のページ](/ja/chapters/06-auth.md)にある、サインインからアクセストークンの交換までを示した図の 1 から 4 です。

<<< @/examples/06-auth/web/src/auth/cognito.ts{cognito}

Cognito でのサインインは、まだ**一度も実行していません**。この `web/src/auth/cognito.ts` は型検査を通っただけで、本物のユーザープールを相手に動かしたことがありません。この章でいちばん大きな未検証の部分なので、そのつもりで読んでください。

`signIn` は乱数を 2 つ作ります。

1 つ目は state で、戻ってきたリダイレクトが、このタブが送った依頼への答えであることを確かめるために使います。攻撃者が、自分のサインインで得た認可コードを含むリンクを踏ませても、state が合わないので受け付けません。

2 つ目は code verifier で、PKCE の秘密の値です。サインイン画面へ送るのは、そのハッシュ（code challenge）だけです。認可コードをトークンと交換するときに、元の値を示します。途中で認可コードを盗み見た人は元の値を知らないので、交換できません。

パブリッククライアントは client secret を持てないので、PKCE がその代わりをします。Cognito が対応する challenge の方式は `S256` だけです。

サインイン画面へ移動すると、SPA のページは破棄されます。戻ってくるまでの間、2 つの値はタブごとの sessionStorage に置いておきます。

<<< @/examples/06-auth/web/src/auth/pending.ts{pending}

置いた値を取り出せるのは 1 回だけで、state が合わないときと、古すぎるときは、何も返しません。テストは、偽の state、同じコールバック URL の再利用、10 分を過ぎた依頼のそれぞれを拒否することを確かめています。

Cognito には、認可コードを使わずに、トークンを直接 URL に載せて返す implicit grant もあります。公式ドキュメントは、トークンを利用者の側に露出させるので安全性が低い、と説明しています。この章のクライアントは implicit grant を無効にしています。

### トークンの置き場所

SPA は、アクセストークンをメモリの変数にだけ持ちます。localStorage にも cookie にも入れません。

| 置き場所 | 再読み込み後 | ページに入り込んだスクリプトから |
| --- | --- | --- |
| メモリ（この章） | 消える。もう一度サインインする | ページが開いている間は読める |
| localStorage | 残る | いつでも読める。タブを閉じた後も残る |
| サーバー側のセッションと cookie（[09章](/ja/chapters/09-ssr.md)） | 残る | 読めない（`HttpOnly` の場合） |

再読み込みのたびにサインインし直すのは不便です。ただ、マネージドログイン自身が 1 時間有効のセッション cookie を持っているので、その間はパスワードを打ち直さずに戻ってこられます。

トークンエンドポイントのレスポンスには、リフレッシュトークンも入っています。SPA はそれを保存せずに捨てています。持たせればサインインした状態をもっと長く保てますが、長く使えるトークンをブラウザに置くことになるので、この章では短く保つほうを選びました。

どの方式でも、ページに悪意のあるスクリプトが入り込めば（XSS）、そのページが開いている間、スクリプトは利用者として API を呼べます。トークンの置き場所によって被害の範囲は変わりますが、置き場所の工夫は XSS そのものの対策の代わりにはなりません。

型付きのクライアントは、リクエストのたびにトークンを取りに来ます。

<<< @/examples/06-auth/api/src/client.ts{client}

API が 401 を返したら、SPA は持っているトークンを捨てて、サインインし直すよう促します。

「Sign out」を押したときも、まず手元のトークンを捨てます。そのうえでマネージドログインの `/logout` へ移動して、サインイン画面側のセッションも終わらせます。手元の開発用サインインには移動する先がないので、トークンを捨てるだけです。

### 競合は利用者に見せる

05章では、古い version からの更新を 409 で拒否し、保存済みのノートを `current` として返すようにしました。この章の画面は、その競合を利用者に見せます。自分の入力は欄に残したまま、保存済みの内容を並べて表示し、自分の入力で保存し直すか、保存済みの内容を採るかを選んでもらいます。どちらを残すかを、アプリが勝手に決めることはしません。
