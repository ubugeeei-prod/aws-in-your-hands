# 06 Auth: デプロイ

[手元で動かした](/ja/chapters/06-auth/local.md)アプリを、このページで AWS にのせます。ユーザープールと JWT オーソライザーを CDK で定義し、利用者を無効にしたときに何が起きるかを確かめてから、デプロイします。

## AWS にのせる準備

<!-- section: 06.infra -->

インフラは CDK で定義します。この章のスタック（`AihNotesApp`）は、アプリ全体を 1 つにまとめたものです。03章の SPA の配信（バケット、ディストリビューション、fallback の関数）と、05章のテーブルと API に、ユーザープールとオーソライザーを足します。

### ユーザープール

<<< @/examples/06-auth/infra/lib/notes-app-stack.ts{user-pool}

`selfSignUpEnabled` は `false` にしています。誰でも登録できる設定のまま練習用のアプリを公開すると、見知らぬ人が利用者になれますし、登録の確認メールもあなたのアカウントから送られます。利用者は、このページの「デプロイする」で使うタスクで作ります。

`removalPolicy` は `DESTROY` です。スタックを消すと、ユーザープールと中の利用者がすべて消えます。

### アプリクライアント

<<< @/examples/06-auth/infra/lib/notes-app-stack.ts{client}

アプリクライアント（app client）の設定は次のとおりです。

- `generateSecret: false` なので、パブリッククライアントです
- 許可する flow は authorization code だけで、implicit は無効です
- `authFlows` は、指定した 4 つ（`userSrp`、`userPassword`、`adminUserPassword`、`custom`）を `false` にしています。パスワードを API に直接送ってサインインする経路を閉じ、入口をマネージドログインへのリダイレクトだけにするためです
- callback URL は、デプロイした SPA の `/callback` と、手元の開発サーバーの `/callback` の 2 つだけです。Cognito は、登録していない URL へは認可コードを返しません
- アクセストークンの寿命は 1 時間です

`enableTokenRevocation` は、利用者のトークンを失効させられるようにする設定です。ただし、失効が効く範囲には限りがあります。その範囲は「無効にしても、しばらく通る」で説明します。

### JWT オーソライザー

<<< @/examples/06-auth/infra/lib/notes-app-stack.ts{authorizer}

公式ドキュメントによると、JWT オーソライザーが確かめるのは次の 5 つです。

1. トークンの署名。発行者の公開鍵で検証する。対応するのは RSA 系の方式だけ
2. `iss` が設定した発行者と一致すること
3. `aud`、それがなければ `client_id` が、設定した audience のどれかと一致すること
4. `exp`、`nbf`、`iat` が現在時刻と矛盾しないこと
5. ルートにスコープを設定していれば、トークンがそのどれかを持つこと

どれかに失敗すると、API Gateway がリクエストを拒否し、関数は起動しません。

`authorizationScopes: ["openid"]` を付けているのは、ID トークンを入口で落とすためです。同じドキュメントは、アクセストークンと ID トークンを区別する標準の方法はないと述べ、ID トークンを API の認可に使うのでなければルートにスコープを要求するよう勧めています。ID トークンはスコープのクレームを持たないので、ここで拒否されます。アプリの側の `token_use` と `client_id` の検査は、5 と 3 に対する二重の守りにあたります。

テストは、テンプレートに対して次のことを確かめます。

- `/health` 以外のすべてのルートに JWT オーソライザーが付いている
- 保護されたルートがすべてスコープを要求している
- クライアントが secret を持たず、flow が authorization code だけである
- CORS で許可するオリジンが 2 つだけで、`*` を含まない

ルートを足してオーソライザーを付け忘れると、最初の検査が落ちます。

### 受けるリクエストを絞る

オーソライザーは、トークンのないリクエストを断ります。しかし断るだけで、送ってくる速さを抑えるわけではありません。また `/health` は、トークンがなくても関数まで届きます。そこで、04章と同じスロットリングをステージに設定します。

<<< @/examples/06-auth/infra/lib/notes-app-stack.ts{throttle}

受けるのは 1 秒あたり 10 リクエストまでで、瞬間的には 20 まで受けます。超えたぶんは API Gateway が 429 で返し、関数は動きません。

このスロットリングは、利用者ごとではありません。誰か 1 人が使い切ると、ほかの人のリクエストも 429 になります。料金は守れますが、1 人の使いすぎからほかの人を守ることはできません。この設定の単位はステージとルートで、呼ぶ相手ではないからです。

テーブルにも、05章と同じ上限（1 秒あたり読み取り 150 ユニット、書き込み 40 ユニット）を付けてあります。超えたぶんは DynamoDB が断り、課金もしません。テストは、この 2 つの上限がテンプレートにあることも確かめています。

## 無効にしても、しばらく通る

<!-- section: 06.revocation -->

アクセストークンは、発行された後は誰にも問い合わせずに検証できます。これは JWT の利点であり、同時に限界でもあります。

次の図は、サインインした利用者を管理者が無効にしたときの流れです。

```figure
caption: 利用者を無効にしても、発行済みのアクセストークンは期限が切れるまで API Gateway を通る
type: sequence
actor cognito: Cognito
actor alice: Alice のブラウザ
actor api: API Gateway | JWT authorizer
step alice -> cognito: t0 サインイン
step cognito --> alice: access token (exp = t0 + 1h)
note cognito: t0+10m 管理者が Alice を無効にする /
note cognito: トークンを失効させる
note cognito: Cognito 自身の API はもう拒否する
step alice -> api: t0+11m GET /notes
step api --> alice: 200（署名は正しい、期限内）
note alice: t0+1h トークンの期限が切れる
step alice -> api: GET /notes
step api --x alice: 401
```

無効にした 1 分後の t0+11m でも、リクエストは通っています。

公式ドキュメントによると、失効させたトークンは、トークンを必要とする Cognito の API では使えなくなります。しかし、署名と期限を検証するだけの JWT ライブラリでは、引き続き有効と判定されます。API Gateway の JWT オーソライザーが確かめるのは、「JWT オーソライザー」に挙げた 5 項目で、失効したかどうかを Cognito に問い合わせる項目はそこにありません。

したがって、**利用者を無効にしても、発行済みのアクセストークンは期限が切れるまでこの API を通ります。** 通る時間は最長で、アクセストークンの寿命のぶん（この章では 1 時間）です。

これは、状態を複数の場所が別々に持つときに起きる、分散システムの典型的なずれです。アカウントが無効だという事実は Cognito にあり、このトークンが有効だという判断は、API Gateway が手元の情報だけで下します。

対処は 3 つあり、どれも何かと引き換えです。

| 対処 | 得るもの | 払うもの |
| --- | --- | --- |
| アクセストークンの寿命を短くする（最短 5 分） | 失効が効くまでの時間が短くなる | トークンの更新が増える。マネージドログインを使う場合、公式ドキュメントは 1 時間未満を勧めていない |
| アプリが、リクエストごとに失効の一覧を引く | すぐ効く | すべてのリクエストに読み取りが 1 回増える。問い合わせずに検証できるという JWT の利点を手放す |
| 受け入れる | 何も足さない | 最長 1 時間、無効にした利用者が通る |

この章では 3 つ目を選びました。ノートアプリで、利用者を無効にしてから 1 時間以内に読まれて困る場面は多くないと判断したからです。扱うものが変われば、判断も変わります。

API Gateway は、発行者の公開鍵も最長 2 時間キャッシュします。ユーザープールの鍵が替わるときには、この時間も考えに入れてください。

## デプロイする

<!-- section: 06.deploy -->

```bash
vp run app:infra:diff
vp run app:infra:deploy
vp run app:user:create you@example.com
vp run app:publish
vp run app:smoke:web
vp run app:smoke:api
```

`app:infra:deploy` は、ディストリビューション、バケット、テーブル、関数、API、ユーザープールをまとめて作ります。

`app:user:create` は、利用者を 1 人作ります。Cognito がそのアドレスに仮のパスワードをメールで送り、初回のサインインで利用者自身がパスワードを決めます。このタスクは、パスワードを見ることも表示することもありません。

`app:publish` は、SPA をビルドし、スタックの出力から `config.json` を書き出して、バケットに置きます。公開の順序とキャッシュの方針は、03章と同じ実装です。

出力された `DistributionDomainName` の URL を開くと、「Sign in」のボタンが出ます。押すと Cognito のサインイン画面へ移動し、サインインすると SPA に戻ってきます。

`app:smoke:api` は、人がサインインしなくても確かめられることを確かめます。トークンなしのリクエストと、でたらめなトークンのリクエストが拒否されることです。サインイン後の経路は、環境変数 `AIH_ACCESS_TOKEN` にアクセストークンを入れたときだけ実行します。入れなかった場合、タスクは、サインイン後の経路は確かめていないと表示します。

手元の SPA を、デプロイした API とユーザープールに向けることもできます。`http://localhost:5173/callback` を callback URL に、`http://localhost:5173` を CORS で許可するオリジンに、あらかじめ登録してあります。`web/public/config.json` をデプロイ先の値に書き換えて、`vp run dev:app:web` を起動してください。ただし本番のアプリでは、手元のオリジンを許可したままにしないでください。

ドリフトの検査は、これまでの章と同じです。

```bash
vp run app:infra:drift
```

このスタックには、固定した版の cdkd が専用の実装を持たないリソースの種類が 3 つあります。`AWS::CloudFront::Function`、`AWS::Cognito::UserPoolClient`、`AWS::Cognito::UserPoolDomain` です。この 3 つは Cloud Control API 経由で扱われます。実際に作成と読み戻しができるかどうかは、確かめていません。
