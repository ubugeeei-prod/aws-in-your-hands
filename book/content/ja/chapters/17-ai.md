# 17 AI: Bedrock

Workers AI なら、`env.AI.run()` を 1 行書けばモデルが答えてくれますよね。AWS で同じことをするのが Amazon Bedrock です。

この章では、まず数行でモデルを 1 回呼びます。そのあと、ノートの本文を要約して、できた分から少しずつ返す API を作ります。呼び出しそのものは Workers AI と同じくらい短いんです。長くなるのはそのまわり、つまり「誰が呼べるか」「いくらまで使うか」「途中で切れたらどうするか」のほうです。

先に 1 つだけ。モデルを呼ぶと、token の数だけ課金されます。手元のサーバーから呼んでも同じです。この章のテストと既定の開発サーバーは、モデルを呼ばずに動くようにしてあります。課金されるタスクには、そのつど印を付けますね。

前提は [04章](/ja/chapters/04-http-api.md)です。コードは `examples/17-ai/` にあります。

## 全体像

```figure

```

```figure
caption: Bedrock が返す event を、Lambda が server-sent events にして呼び出し元へ中継する
type: sequence

step caller -> fn: HTTPS、SigV4 で署名
step fn -> bedrock: ConverseStream

step bedrock --> fn: contentBlockDelta…
step fn --> caller: delta…
step bedrock --> fn: messageStop, metadata
step fn --> caller: 最後に done か error
```

04章と違うところが 2 つあります。

1 つは入口です。04章の API Gateway HTTP API は、Lambda の応答を最後まで受け取ってから返します。少しずつ返す、ができません。そこでこの章では、Lambda に直接付く HTTPS の endpoint、**function URL** を使います。function URL には、関数が書いた分から呼び出し元へ送る response streaming のモードがあります。

もう 1 つは、Lambda の先に Bedrock がいること。あなたの関数は文章を生成しません。Bedrock に頼んで、返ってくるイベントを中継するだけです。

### 入口の選び方

Lambda の response streaming を外へ出す道は、公式ドキュメントによると 3 つあります。

- function URL（`RESPONSE_STREAM`）
- API Gateway の REST API。proxy integration の応答の転送モードを `STREAM` にする。HTTP API にはこの機能がない
- `InvokeWithResponseStream` を SDK から直接呼ぶ

この章が function URL にしたのは、リソースが 1 つ増えるだけで済むからです。そのかわり、function URL が自分で持っている認証は IAM の署名だけです。API キーや WAF、Cognito の authorizer が要るなら REST API のほうです（04章の表を見てください）。ブラウザから呼ばせたい場合の話は「本番にするなら」でします。

### 誰でも呼べる状態にしない

function URL の認証は `AWS_IAM` か `NONE` の 2 択です。`NONE` にすると、URL を知っている人は誰でも関数を呼べます。この関数は呼ばれるたびにモデルを動かすので、それは「知らない人があなたの料金で推論できる」という意味になります。

なのでこの章は `AWS_IAM` にします。Lambda が、関数を動かす前にリクエストの署名（SigV4 署名。AWS の API が呼び出し元を確かめる仕組み）を調べます。呼べるのは、同じアカウントの中で `lambda:InvokeFunctionUrl` と `lambda:InvokeFunction` を許可された人だけ。この章の呼び出し元は、あなたの認証情報で署名するスクリプトです。

SPA から直接は呼べません。ブラウザに AWS の認証情報は置けないからです。アウトラインでは SPA からつなぐ予定でしたが、そのためには [06章](/ja/chapters/06-auth.md)のサインインが要ります。この章の前提は 04章だけなので、「認証のない公開 endpoint を作らない」を優先して、ここで止めました。

## モデルを選ぶ

<!-- section: 17.models -->

`modelId` に何を書くか。ここが Workers AI よりずっと面倒なところです。

Bedrock では、モデルごとに「どのリージョンで、どういう経路で呼べるか」が違います。経路は 3 種類あります。

- **In-Region**: 呼んだリージョンの中だけで処理する。モデル ID をそのまま渡す
- **Geo**: 決まった地域の中の、どこかのリージョンで処理する
- **Global**: 世界中のどこかの商用リージョンで処理する

Geo と Global は、モデル ID の代わりに **inference profile** の ID を渡します。モデルと、リクエストを送ってよいリージョンの組に付いた名前です。この仕組みを cross-Region inference と呼びます。

つまり、東京の endpoint を呼んでも、推論が東京で動くとは限りません。`jp.` で始まる profile なら東京か大阪。`global.` なら世界のどこか。データをどこで処理してよいかに決まりがあるなら、ここは先に確かめてください。公式ドキュメントも、ID の接頭辞だけで判断せず、行き先を確認するように書いています。

既定は Amazon Nova 2 Lite の `jp.` profile にしました。理由は 3 つ。行き先が日本の中に収まること、Amazon のモデルなので使い始める手続きがないこと、そして安いことです。ちなみに Nova 2 Lite は、東京では In-Region で呼べません。model card の表では Geo と Global だけに印が付いています。

モデルは環境変数 `BEDROCK_MODEL_ID` で差し替えられます。デプロイするときは `-c modelId=...` です。ただし、上の表にない ID を渡すと synth が止まります。意地悪ではなくて、次に話す IAM のためです。

### 使い始める手続き

以前の Bedrock には、コンソールでモデルごとにアクセスを申請する画面がありました。いまのドキュメントでは、多くのモデルは最初から使える、となっています。残っている手続きは 2 つです。

- **Anthropic のモデル**は、最初に 1 回、用途を書くフォームの提出が要ります（アカウントか organization ごとに 1 回）
- **AWS Marketplace 経由で売られているモデル**（Anthropic など）は、最初の呼び出しのときに Bedrock が裏で subscription を始めます。呼んだ人に `aws-marketplace:Subscribe` などの権限が要り、完了まで最大 15 分かかることがあります。Amazon のモデルは Marketplace を通りません

2 つ目には落とし穴があります。この章の Lambda の実行 role には、Marketplace の権限を付けていません。なので Anthropic のモデルに替えるなら、先にあなた自身の権限で `vp run ai:hello` を 1 回通してください。一度有効になれば、呼ぶ側に Marketplace の権限は要らなくなります。
