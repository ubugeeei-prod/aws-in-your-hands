# 17 AI: Bedrock

Workers AI では、`env.AI.run()` を 1 行書けばモデルが答えを返します。AWS でこの役目を担うサービスが Amazon Bedrock です。

この章では、最初に数行のコードでモデルを 1 回呼び、そのあとで、ノートの本文を要約して、生成できた分から順に返す API を作ります。モデルを呼ぶコードそのものは、Workers AI と同じくらい短く済みます。長くなるのは、誰が呼べるか、いくらまで使うか、途中で切れたらどうするかを決める、呼び出しのまわりのコードです。

モデルを呼ぶと、トークンの数に応じて課金されます。手元のサーバーから呼んでも同じです。そのため、この章のテストと既定の開発サーバーは、モデルを呼ばずに動くようにしてあります。課金されるタスクは、出てくるたびにそう書きます。

前提は [04章](/ja/chapters/04-http-api.md)です。コードは `examples/17-ai/` にあります。

04章との違いは 2 つあります。

1 つ目は入口です。04章の API Gateway HTTP API は、Lambda のレスポンスを最後まで受け取ってから呼び出し元へ返すので、できた分から順には返せません。そこでこの章では、Lambda の関数に直接付く HTTPS のエンドポイントである **function URL** を使います。function URL には、関数が書き込んだ分から呼び出し元へ送る、レスポンスストリーミング（response streaming）のモードがあります。

2 つ目は、Lambda の先に Bedrock があることです。文章を生成するのは Bedrock で、この章の関数は、Bedrock から返ってくるイベントを呼び出し元へ中継するだけです。

### 入口の選び方

公式ドキュメントによると、Lambda のレスポンスストリーミングを外へ出す方法は 3 つあります。

- function URL（`RESPONSE_STREAM`）
- API Gateway の REST API。proxy integration のレスポンスの転送モードを `STREAM` にする。HTTP API にはこの機能がない
- `InvokeWithResponseStream` を SDK から直接呼ぶ

この章が function URL を選んだのは、増えるリソースが 1 つで済むからです。その代わり、function URL が自前で持つ認証は IAM の署名しかありません。API キー、WAF、Cognito の authorizer が必要なら、REST API を選びます（04章の表を見てください）。ブラウザから呼べるようにする方法は、[本番にするなら](/ja/chapters/17-ai/wrap.md)で扱います。

### 誰でも呼べる状態にしない

function URL の認証は `AWS_IAM` か `NONE` のどちらかです。`NONE` にすると、URL を知っている人なら誰でも関数を呼べます。この関数は呼ばれるたびにモデルを動かすので、知らない人があなたの料金で推論できることになります。

そこでこの章では `AWS_IAM` にします。`AWS_IAM` では、Lambda が関数を動かす前に、リクエストの SigV4 署名を調べます。SigV4 署名は、AWS の API が呼び出し元を確かめる仕組みです。呼べるのは、同じアカウントの中で `lambda:InvokeFunctionUrl` と `lambda:InvokeFunction` を許可された相手だけで、この章では、あなたの認証情報で署名するスクリプトが呼び出し元になります。

ブラウザに AWS の認証情報は置けないので、SPA からは直接呼べません。執筆前のアウトラインでは SPA からつなぐ予定でしたが、それには [06章](/ja/chapters/06-auth.md)のサインインが必要です。この章の前提は 04章だけなので、認証のない公開エンドポイントを作らないことを優先し、SPA にはつないでいません。

## モデルを選ぶ

<!-- section: 17.models -->

`modelId` に書く値を決めるのは、Workers AI よりずっと手間がかかります。Bedrock では、どのリージョンから、どの経路で呼べるかが、モデルごとに違うからです。経路は 3 種類あります。

- In-Region は、呼んだリージョンの中だけで処理する。モデル ID をそのまま渡す
- Geo は、決まった地域の中にある、いずれかのリージョンで処理する
- Global は、世界中の商用リージョンのいずれかで処理する

Geo と Global では、モデル ID の代わりに **inference profile** の ID を渡します。inference profile は、モデルと、リクエストを送ってよいリージョンの組に付いた名前です。この仕組みを cross-Region inference と呼びます。

したがって、東京のエンドポイントを呼んでも、推論が東京で動くとは限りません。`jp.` で始まる profile なら東京か大阪、`global.` なら世界のどこかで処理されます。データを処理してよい場所に決まりがあるなら、モデルを選ぶ前に行き先を確かめてください。公式ドキュメントも、ID の接頭辞だけで判断せずに、行き先を確認するよう書いています。

既定は Amazon Nova 2 Lite の `jp.` profile です。行き先が日本の中に収まり、Amazon のモデルなので使い始める手続きがなく、安いからです。なお、Nova 2 Lite は、東京では In-Region で呼べません。モデルカードの表では、Geo と Global にだけ印が付いています。

モデルは環境変数 `BEDROCK_MODEL_ID` で差し替えられ、デプロイするときは `-c modelId=...` で指定します。ただし、上の一覧にない ID を渡すと synth が止まります。止める理由は IAM にあり、「実行ロールに書く ARN」で説明します。

### 使い始める手続き

以前の Bedrock には、コンソールでモデルごとにアクセスを申請する画面がありました。現在のドキュメントは、多くのモデルは最初から使えるとしています。残っている手続きは、次の 2 つです。

- Anthropic のモデルは、最初に 1 回、用途を書くフォームを提出する必要があります。提出は、アカウントか organization ごとに 1 回です
- AWS Marketplace 経由で販売されているモデル（Anthropic など）は、最初の呼び出しのときに、Bedrock が裏でサブスクリプションを開始します。呼んだ人には `aws-marketplace:Subscribe` などの権限が必要で、完了まで最大 15 分かかることがあります。Amazon のモデルは Marketplace を通りません

2 つ目の手続きは、この章の Lambda からは済ませられません。Lambda の実行ロールに、Marketplace の権限を付けていないからです。Anthropic のモデルに替えるなら、先にあなた自身の権限で `vp run ai:hello` を 1 回通してください。一度有効になれば、呼ぶ側に Marketplace の権限は要らなくなります。

### 実行ロールに書く ARN

inference profile を使うと、IAM のポリシーに書く対象が増えます。profile そのものに加えて、行き先の各リージョンにあるモデルも書く必要があります。

<<< @/examples/17-ai/infra/lib/models.ts{arns}

`jp.amazon.nova-2-lite-v1:0` なら、profile が 1 つと、東京と大阪のモデルが 2 つです。行き先を 1 つでも書き忘れると、そのリージョンへ送られたリクエストだけが拒否されます。たまにしか起きない失敗は原因を見つけにくいので、行き先を確かめた ID だけを一覧に置き、一覧にない ID は synth で止めています。
