# 17 Workers AI に親しんだ人の AI 開発: Bedrock

Workers AI なら、`env.AI.run()` を 1 行書けばモデルが答えてくれますよね。AWS で同じことをするのが Amazon Bedrock です。

この章では、まず数行でモデルを 1 回呼びます。そのあと、ノートの本文を要約して、できた分から少しずつ返す API を作ります。呼び出しそのものは Workers AI と同じくらい短いんです。長くなるのはそのまわり、つまり「誰が呼べるか」「いくらまで使うか」「途中で切れたらどうするか」のほうです。

先に 1 つだけ。モデルを呼ぶと、token の数だけ課金されます。手元のサーバーから呼んでも同じです。この章のテストと既定の開発サーバーは、モデルを呼ばずに動くようにしてあります。課金されるタスクには、そのつど印を付けますね。

前提は [04章](/ja/chapters/04-http-api.md)です。コードは `examples/17-ai/` にあります。

## 全体像

<!-- section: 17.architecture -->

```text
Caller (a script with AWS credentials; later a browser behind your own auth)
  |  HTTPS, signed with SigV4
  v
Lambda function URL (ap-northeast-1)   AuthType: AWS_IAM, InvokeMode: RESPONSE_STREAM
  |  unsigned or unauthorized: 403, the function is not invoked
  v
Lambda function (Node.js 24, arm64, 256 MB, timeout 40 s)
  |  Hono app -> summarizer -> ModelGateway
  |  execution role: its own log group, and one inference profile
  v
Amazon Bedrock ConverseStream (inference profile jp.amazon.nova-2-lite-v1:0)
  |  the request is processed in ap-northeast-1 or ap-northeast-3
  v
events: messageStart, contentBlockDelta..., messageStop, metadata
  ^
  |  relayed to the caller as server-sent events: delta..., then done or error
```

04章と違うところが 2 つあります。

1 つは入口です。04章の API Gateway HTTP API は、Lambda の応答を最後まで受け取ってから返します。少しずつ返す、ができません。そこでこの章では、Lambda に直接付く HTTPS の endpoint、**function URL** を使います。function URL には、関数が書いた分から呼び出し元へ送る response streaming のモードがあります。

もう 1 つは、Lambda の先に Bedrock がいること。あなたの関数は文章を生成しません。Bedrock に頼んで、返ってくるイベントを中継するだけです。

### 入口の選び方

Lambda の response streaming を外へ出す道は、公式ドキュメントによると 3 つあります。

- function URL（`RESPONSE_STREAM`）
- API Gateway の REST API。proxy integration の応答の転送モードを `STREAM` にする。HTTP API にはこの機能がない
- `InvokeWithResponseStream` を SDK から直接呼ぶ

この章が function URL にしたのは、リソースが 1 つ増えるだけで済むからです。そのかわり、function URL が自分で持っている認証は IAM の署名だけです。API キーや WAF、Cognito の authorizer が要るなら REST API のほうです（04章の表を見てください）。ブラウザから呼ばせたい場合の話は「本番にするなら」でします。

### 誰でも呼べる状態にしない

function URL の認証は `AWS_IAM` か `NONE` の 2 択です。`NONE` にすると、URL を知っている人は誰でも関数を呼べます。この関数は呼ばれるたびにモデルを動かすので、それは「知らない人があなたの料金で推論できる」という意味になります。

なのでこの章は `AWS_IAM` にします。Lambda が、関数を動かす前にリクエストの署名（SigV4 署名。AWS の API が呼び出し元を確かめる仕組み）を調べます。呼べるのは、同じアカウントの中で `lambda:InvokeFunctionUrl` と `lambda:InvokeFunction` を許可された人だけ。この章の呼び出し元は、あなたの認証情報で署名するスクリプトです。

SPA から直接は呼べません。ブラウザに AWS の認証情報は置けないからです。アウトラインでは SPA からつなぐ予定でしたが、そのためには [06章](/ja/chapters/06-auth.md)のサインインが要ります。この章の前提は 04章だけなので、「認証のない公開 endpoint を作らない」を優先して、ここで止めました。

## モデルを選ぶ

<!-- section: 17.models -->

`modelId` に何を書くか。ここが Workers AI よりずっと面倒なところです。

Bedrock では、モデルごとに「どのリージョンで、どういう経路で呼べるか」が違います。経路は 3 種類あります。

- **In-Region**: 呼んだリージョンの中だけで処理する。モデル ID をそのまま渡す
- **Geo**: 決まった地域の中の、どこかのリージョンで処理する
- **Global**: 世界中のどこかの商用リージョンで処理する

Geo と Global は、モデル ID の代わりに **inference profile** の ID を渡します。モデルと、リクエストを送ってよいリージョンの組に付いた名前です。この仕組みを cross-Region inference と呼びます。

つまり、東京の endpoint を呼んでも、推論が東京で動くとは限りません。`jp.` で始まる profile なら東京か大阪。`global.` なら世界のどこか。データをどこで処理してよいかに決まりがあるなら、ここは先に確かめてください。公式ドキュメントも、ID の接頭辞だけで判断せず、行き先を確認するように書いています。

2026-10-11 に、各モデルのページ（model card）で確かめた ID がこちらです。

<<< @/examples/17-ai/infra/lib/models.ts{models}

既定は Amazon Nova 2 Lite の `jp.` profile にしました。理由は 3 つ。行き先が日本の中に収まること、Amazon のモデルなので使い始める手続きがないこと、そして安いことです。ちなみに Nova 2 Lite は、東京では In-Region で呼べません。model card の表では Geo と Global だけに印が付いています。

モデルは環境変数 `BEDROCK_MODEL_ID` で差し替えられます。デプロイするときは `-c modelId=...` です。ただし、上の表にない ID を渡すと synth が止まります。意地悪ではなくて、次に話す IAM のためです。

### 使い始める手続き

以前の Bedrock には、コンソールでモデルごとにアクセスを申請する画面がありました。いまのドキュメントでは、多くのモデルは最初から使える、となっています。残っている手続きは 2 つです。

- **Anthropic のモデル**は、最初に 1 回、用途を書くフォームの提出が要ります（アカウントか organization ごとに 1 回）
- **AWS Marketplace 経由で売られているモデル**（Anthropic など）は、最初の呼び出しのときに Bedrock が裏で subscription を始めます。呼んだ人に `aws-marketplace:Subscribe` などの権限が要り、完了まで最大 15 分かかることがあります。Amazon のモデルは Marketplace を通りません

2 つ目には落とし穴があります。この章の Lambda の実行 role には、Marketplace の権限を付けていません。なので Anthropic のモデルに替えるなら、先にあなた自身の権限で `vp run ai:hello` を 1 回通してください。一度有効になれば、呼ぶ側に Marketplace の権限は要らなくなります。

<<< @/examples/17-ai/src/contract.ts{events}

応答は server-sent events（SSE）にします。1 つの HTTP 応答の中で、サーバーがイベントを順に送り続ける形式です。`delta` が何回か来て、最後に `done` か `error` が 1 回だけ来る。この「最後に必ずどちらか 1 回」が、この章の後半で効いてきます。

## stream を読む

<!-- section: 17.stream -->

`ConverseStream` は、`Converse` の streaming 版です。返ってくるのは、イベントの列。

```text
order  event              carries
1      messageStart       role
2      contentBlockDelta  a piece of text (repeats)
3      contentBlockStop
4      messageStop        stopReason: end_turn, max_tokens, ...
5      metadata           usage: inputTokens, outputTokens
```

## 止める、待つ、やり直す

<!-- section: 17.failures -->

モデルの呼び出しは、失敗の種類が多いです。混んでいる、上限を超えた、権限がない、途中で切れた。全部を同じ「エラー」にすると、やり直すべきものと、やり直しても無駄なものの区別がつきません。

<<< @/examples/17-ai/src/failure.ts{classify}

分け方の基準は 1 つ。同じリクエストをもう一度送ったら、通る可能性があるか。

`ThrottlingException` は、アカウントの quota（モデルごとに決まっている、token の使用量の上限）を超えたときに返ります。少し待てば通るかもしれません。`ServiceUnavailableException` は Bedrock 側の容量の問題で、これも待つ価値があります。一方、`AccessDeniedException` や `ValidationException` は、何度送っても同じです。role かモデル ID かリクエストが間違っています。

名前を知らないエラーには、何も言いません（`undefined`）。知らないものを勝手に「やり直せる」と決めないためです。

待ち方はこうです。

<<< @/examples/17-ai/src/failure.ts{backoff}

待ち時間の上限を 2 倍ずつ伸ばして、その中からランダムに選びます。ランダムにするのは、同時に失敗した人たちが同時にやり直して、また同時に失敗するのを避けるため。乱数は引数でもらうので、テストでは待ち時間が決まった値になります。

これを使う側がこちら。

<<< @/examples/17-ai/src/summarize.ts{start}

ポイントが 3 つあります。

**やり直すのは、まだ何も送っていない間だけ。** stream が開く前の失敗は、呼び出し元から見えません。だから黙ってやり直せます。でも `delta` を 1 つでも送ったあとは、やり直すと同じ文章の頭がもう一度流れます。送ったものは取り消せないので、そこからは `error` を返して、やり直すかどうかは呼び出し元に任せます。

**締め切りは、全部の試行をまとめて 1 つ。** 30 秒の締め切りを試行ごとに持つと、3 回で 90 秒待たせることになります。`AbortSignal.timeout` を最初に 1 つ作って、全部の試行で共有します。

**止める理由が何であれ、モデルへのリクエストを中止する。** 呼び出し元がいなくなった、締め切りが来た、中継が終わった。3 つの signal を `AbortSignal.any` でまとめて SDK に渡しています。モデルは、誰も読まない文章を書き続けても課金するので。

SDK 自身も、何もしなければ最大 3 回まで再試行します。この章ではそれを切って（`maxAttempts: 1`）、再試行を自分のコードに置きました。締め切りと一緒に管理できて、テストもできるからです。

## 手元で動かす

<!-- section: 17.local -->

`examples/17-ai/.env.example` を、同じ場所に `.env` という名前でコピーします。

<<< @/examples/17-ai/.env.example

```bash
vp run dev:ai
```

<http://localhost:8788> で立ち上がります。別のターミナルから。

```bash
curl -s http://localhost:8788/health
curl -sN -X POST http://localhost:8788/summaries -H 'content-type: application/json' -d '{"title":"release","body":"Finish the payment tests before Friday."}'
curl -s -X POST http://localhost:8788/summaries -H 'content-type: application/json' -d '{"title":"","body":"x"}'
```

2 つ目で、`delta` が少しずつ流れて、最後に `done` が来ます。`-N` は、curl に溜め込まずに表示させるオプションです。

ここで大事な話をします。**API サーバーが手元で動いていることと、推論が手元で動いていることは、別の話です。**

<<< @/examples/17-ai/src/dev.ts{dev}

`AI_BACKEND=fixture` のとき、サーバーは用意しておいたイベントの列を再生します。AWS は呼びません。課金もされません。認証情報も要りません。

`AI_BACKEND=bedrock` に変えると、同じサーバーが、あなたの認証情報で本物の Bedrock を呼びます。サーバーは `localhost` にいますが、モデルは AWS の中で動いて、token の数だけ課金されます。Bedrock を手元で模擬するものは、付いてきません。

これは Workers AI も同じです。Cloudflare のドキュメントは、Workers AI は手元の開発でも常にあなたのアカウントにつないでモデルを動かし、利用料がかかる、と書いています。04章で触れた、手元の模擬につながる binding とは、ここが違います。

開発サーバーが `127.0.0.1` だけで待ち受けているのも、そのためです。`bedrock` のときにこのポートへ届く人は、あなたの料金で推論できてしまうので。

fixture は 5 種類あって、`AI_FIXTURE` で選べます。失敗する stream を、手元で好きなだけ眺められます。

```bash
AI_FIXTURE=truncated vp run dev:ai
```

これで同じ `curl` を打つと、`delta` が 3 つ来たあと、`done` ではなく `error`（`interrupted`）で終わります。

もう 1 つ、試してほしいことがあります。`complete` の fixture で `curl` を打って、流れている途中で Ctrl+C してみてください。サーバーの log に、`outcome` が `cancelled` の行が出ます。接続が切れたことをサーバーが知って、モデルへのリクエストを中止した、という記録です。

ただし、これは手元の話です。Lambda にのせると事情が変わります。あとで話しますね。

これは課金されます。`check:all` からは呼ばれません。fixture では確かめられないこと、つまりモデル ID が通るか、権限が足りるか、本物のイベントが schema に合うか、を見るためのものです。さっき書いたとおり、まだ実行できていません。

## 途中で切れたら

<!-- section: 17.partial -->

stream は途中で切れます。モデルが止まることもあれば、Lambda が timeout することも、Wi-Fi が切れることもあります。

```text
time  Bedrock                Lambda                    caller
t1    messageStart      -->  (opens the SSE stream)
t2    delta "金曜の"      -->  delta              -->   shows "金曜の"
t3    delta "リリース…"   -->  delta              -->   shows "金曜のリリース…"
t4    (connection drops)     error: interrupted  -->   partial text + "incomplete"
t4'   or: the caller's own connection drops here       no terminal event at all
```

t4 では、Lambda が `error` を送れます。でも t4' のように、Lambda と呼び出し元の間が切れたら、何も届きません。届かないものは検証できないので、client は「最後のイベントが来なかった」こと自体を失敗として扱います。

<<< @/examples/17-ai/src/client.ts{events}

サーバーが `done` も `error` も送らずに終わったら、client が自分で `error` を足します。これで、読む側から見た stream は、必ず `done` か `error` で終わります。

SSE を読む部分は短いので、自前です。

<<< @/examples/17-ai/src/client.ts{sse}

イベントとして数えるのは、区切りの空行まで届いたものだけ。`data:` の行が途中まで届いていても、使いません。

さて、切れたときに手元に残った文章をどうするか。決めないといけません。この章の答えはこうです。

<<< @/examples/17-ai/src/client.ts{collect}

**部分的な出力は、見せてもいいが、要約として保存しない。** `complete` になるのは、`done` を受け取って、しかも `complete` が `true` のときだけ。それ以外は全部 `incomplete` で、届いた分は `partial` に入ります。画面に「途中まで」と添えて出すのは構いません。でも、それをノートの要約として保存すると、次に開いたとき、文の途中で切れた要約が「完成品」として出てきます。どこで切れたのかは、もう誰にもわかりません。

invariant を 1 文で書くと、**`done` を受け取っていない出力は、完了した要約として扱われない**、です。

これを壊そうとするテストがあります。完了する応答のバイト列を、0 バイト目から最後の 1 バイト手前まで、1 バイトずつ切り詰めて client に読ませます。接続が静かに閉じた場合と、エラーで切れた場合の両方で。どこで切っても、結果は `incomplete`。そして `partial` は、必ず本物の文章の頭の部分になっています。

この章のサンプルは、要約を保存しません（保存先が 05章からなので）。保存を足すときは、`status` が `complete` の結果だけを書き込んでください。

### 関数

<<< @/examples/17-ai/infra/lib/ai-stack.ts{function}

`timeout` の話をします。ここが、手元と一番違うところです。

Lambda のドキュメントには、こう書いてあります。streaming の応答は、呼び出した側の接続が切れても中断されない。課金は関数の実行時間ぶんすべて。

手元の開発サーバーでは、切断すると `cancelled` になりましたよね。Lambda ではそうならない、ということです。Hono の `streamHandle` のソースを読んでも、書き込みの失敗を応答の body の中止につなぐ処理はありませんでした。なので Lambda の上では、呼び出し元がいなくなっても、モデルは最後まで書き続けると考えておきます。

## Workers AI から来た人へ

<!-- section: 17.workers-ai -->

違うところを並べます。Cloudflare 側は、公式ドキュメントで確かめた範囲です。

| | Cloudflare Workers AI | この章（Bedrock） |
| --- | --- | --- |
| 呼び方 | binding。設定に書くと `env.AI` に現れて、`env.AI.run(model, options)` | AWS SDK の client。`ConverseCommand` か `ConverseStreamCommand` を送る |
| 権限 | binding を宣言した Worker が呼べる | IAM。実行 role に、モデルと inference profile の ARN を書く |
| モデルの指定 | `@cf/meta/llama-3.1-8b-instruct` のような名前 | モデル ID か inference profile の ID。リージョンと経路で使えるものが変わる |
| 動く場所 | Cloudflare のネットワーク | profile が決めるリージョンのどれか |
| streaming | `stream: true` を渡すと `text/event-stream` で返る。そのまま応答にできる | イベントの列が SDK の async iterable で返る。SSE にするのは自分 |
| 課金の単位 | Neurons。1 日 10,000 まで無料、超えた分は 1,000 Neurons あたり USD 0.011。モデルごとの token 単価も載っている | モデルとリージョンごとの、入力と出力の token 単価 |
| 手元の開発 | 模擬はない。常に remote で動いて、課金される | 模擬はない。常に remote で動いて、課金される |

Workers AI のほうが、始めるまでが短いです。binding を 1 行書けば、権限もモデルの置き場所も考えずに呼べます。streaming も、返ってきたものをそのまま `Response` に渡せば終わりです。

Bedrock は、そこを全部自分で決めます。どの ARN を許すか、どのリージョンで処理されるか、stream をどういう形で外に出すか。手間は増えますが、「この関数はこのモデルしか呼べない」「推論は日本の中で処理される」を、設定として書けます。どちらがいいかは、作るものと、守らないといけない決まり次第です。

最後の行は同じでした。どちらも、手元で API を動かしていても、推論は向こうで動いて課金されます。

## お金の話

金額は USD、東京リージョン、従量課金、税別です。計算の中身は[料金の計算](/ja/reference/pricing.md)にあります。

**誰も呼ばない月は 0 です。** function URL にも Lambda にも、置いてあるだけでかかる料金はありません。Bedrock の従量課金は、呼んだ token のぶんだけです。log は 7 日で消えます。

呼ばれると、こうなります。月 1,000 件の要約で、1 件あたり入力 2,000 token、出力 150 token という仮定です。token 数は仮定で、あなたのノートでの実際の値は、log の `summary` 行の `usage` でわかります。

| 対象 | 数量 | 定価 | 毎月の無料枠の適用後 |
| --- | --- | --- | --- |
| Nova 2 Lite の入力 | 200 万 token | 0.79 | 0.79（無料枠は確認できず、引いていない） |
| Nova 2 Lite の出力 | 15 万 token | 0.50 | 0.50（同上） |
| Lambda のリクエスト | 1,000 件 | 0.00 | 0 |
| Lambda の実行時間 | 1,000 GB 秒 | 0.01 | 0 |
| CloudWatch Logs の取り込み | 0.001 GB | 0.00 | 0 |
| 小計 | | **1.30** | **1.29** |

単価は、Nova 2 Lite が入力 1,000 token あたり USD 0.000396、出力 1,000 token あたり USD 0.003311 です（AWS Price List、2026-10-11 確認）。出力は入力の 8 倍以上します。`maxTokens` を決める意味が、ここにあります。

Lambda の実行時間は、1 件あたり平均 4 秒と仮定しました。推論を待っている間も、関数は動いていて課金されます。応答をインターネットへ送るデータ転送の料金は、この表に入れていません（0 という意味ではなく、未算入です）。

上限の話もしておきます。出力は 1 件あたり最大 400 token なので、1,000 件すべてが上限まで書いたとしても、出力のぶんは USD 1.32 です。入力のほうは、さっき書いたとおり文字数でしか抑えていないので、こういう言い切りはできません。

モデルを替えると、単価が変わります。同じ token 数を Claude Haiku 4.5（東京、入力 100 万 token あたり USD 1.10、出力 USD 5.50）で計算すると、推論のぶんだけで USD 3.03。Nova 2 Lite の 2 倍以上です。ただし token の数え方はモデルごとに違うので、同じ文章が同じ token 数になるわけではありません。単価の比較として見てください。

確かめられなかったこともあります。Bedrock に無料枠があるか。途中で中止した呼び出しに、どこまでの token が課金されるか。どちらも一次情報で確認できていないので、不明としておきます。

stack を消せば、この章のぶんの料金は止まります。

## 本番にするなら

- **ブラウザから呼べるようにする。** function URL の前に CloudFront を置いて、origin access control で CloudFront に署名させる方法が、公式ドキュメントにあります。URL は `AWS_IAM` のままです。ただ、それだけだと CloudFront の URL を知っている人が誰でも呼べるので、アプリの中で 06章の access token を確かめる処理が要ります。POST のときは、本文の SHA-256 を `x-amz-content-sha256` ヘッダーで送る必要がある、とも書かれています。この章ではどれも作っていません
- **利用者ごとの上限を作る。** いまの上限は「1 回あたり」だけです。同じ人が 1 万回呼べば、1 万回ぶん払います。回数の上限には、利用者を区別できる認証と、数える場所が要ります
- **アカウントの quota を確かめる。** 推論には、モデルごとに token の使用量の上限があります。ドキュメントによると、アカウントに実際に適用される値は、公開されている既定値より低いことがあります。Service Quotas で自分の値を見てください（この章では値を確かめていません）
- **予算の通知を付ける。** 01章の Budgets です。通知は支出を止めません。止めるのは、上に書いた上限のほうです
- **データの行き先を決める。** `jp.` の profile は日本の中、`global.` は世界中です。どこで処理してよいデータなのかを、モデルを選ぶ前に決めます
- **モデルの終了日を追う。** model card には、モデルごとに終了の目安が載っています。たとえば Claude Haiku 4.5 は「2026-10-16 より前には終了しない」。モデル ID を環境変数にしてあるのは、いずれ替える日が来るからです
- **反映の経路を AWS CDK CLI と CloudFormation にする。** 02章で話したとおりです
