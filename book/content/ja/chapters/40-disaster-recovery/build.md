# 40 Disaster Recovery: しくみと実装

[前のページ](/ja/chapters/40-disaster-recovery.md)で、DRS の部品と料金を見ました。このページでは、23章のインスタンスをソースサーバーにするために足りないものを順に埋め、訓練の判断をコードにします。

## ソースサーバーになれる条件

<!-- section: 40.source -->

エージェントは、どのサーバーにも入るわけではありません。対応する OS とカーネルの一覧がドキュメントにあり、23章のインスタンスに関係するのは次の 3 点です。

- Amazon Linux 2023 は対象ですが、カーネルは 6.12 までです
- arm64 に対応しているのは、Graviton の EC2 インスタンスを AWS へ復旧する場合だけです。オンプレミスやほかのクラウドの arm64 のサーバーは対象外です
- 複製されるのは、マウントされているディスクです。接続しただけでフォーマットしていないボリュームは複製されません

23章のインスタンスは `t4g.micro`（Graviton）で、データボリュームは XFS でマウントされているので、2 点目と 3 点目は満たします。問題は 1 点目で、23章の既定の AMI のカーネルは 6.18 です。

この 3 点を、導入の前に確かめる関数にしました。

<<< @/examples/40-disaster-recovery/src/source.ts{source}

この関数は、ドキュメントの一覧を写したものです。インストーラーが実際に何を受け付けるかは、動かしていないのでわかりません。一覧は版が上がるたびに変わるので、試す日にもう一度読んでください。

arm64 のサーバーには、もう 1 つ決まりがあります。リカバリーインスタンスのインスタンスタイプも Graviton でなければならず、合っていなければ起動の前の検査で失敗します。

## エージェントに必要な経路

<!-- section: 40.network -->

23章のインスタンスは、NAT のないプライベートサブネットにいます。そこから届くのは、11章のエンドポイントがある Systems Manager と S3 だけでした。DRS を使うには、経路が 3 本増えます。

```figure
caption: エージェントとレプリケーションサーバーは、どちらも自分から接続を開く。既定の構成では、DRS と EC2 へはこの章のエンドポイントを、S3 へは 11章のゲートウェイエンドポイントを通る
node src: EC2 インスタンス (23章) | Private1, zone 1
node rs: レプリケーションサーバー | Private2, zone 2
node vpce: Interface endpoints (この章) | drs, ec2, zone 2 のみ
node gw: S3 gateway endpoint (11章)
node drs: Elastic Disaster Recovery
node ec2: EC2 API
node s3: S3 | installer, AL2023 packages
edge src -> rs: tcp 1500
edge src -> vpce: HTTPS 443
edge rs -> vpce: HTTPS 443
edge src -> gw
edge rs -> gw
edge vpce -> drs
edge vpce -> ec2
edge gw -> s3
group vpc: VPC AihNetwork = src, rs, vpce, gw
mark rs
```

1 本目は、エージェントから DRS への HTTPS です。エージェントは、複製の状態の報告や指示の受け取りのために、`drs.ap-northeast-1.amazonaws.com` と 443 番でつながり続けます。

2 本目は、エージェントからレプリケーションサーバーへの 1500 番です。ディスクのブロックは、この経路で流れます。DRS のインターフェースエンドポイントを置いても、通るのは管理の通信だけで、複製のデータは通りません。

3 本目は、ステージングエリアの側の経路です。レプリケーションサーバーは、DRS と、EC2 の API と、S3 に届く必要があります。S3 からは、複製のためのソフトウェアと、Amazon Linux 2023 のパッケージを取ります。レプリケーションサーバー自身が Amazon Linux 2023 で動いているからです。

エンドポイントを置く AZ は 1 つだけにしました。インターフェースエンドポイントは AZ ごとに課金されるので、2 つの AZ に置くと月に USD 20.44 増えます。置くのは、障害のときに残る側、つまりステージングエリアの AZ です。zone 1 のエージェントは、AZ をまたいでこのエンドポイントを使います。

経路について、確かめていないことが 2 つあります。1 つは、エージェントが、プライベート DNS で解決されるエンドポイントをそのまま使えるかどうかです。ドキュメントは、オンプレミスから VPN 越しにエンドポイントを使う場合について、インストーラーに `--endpoint` でエンドポイントの DNS 名を渡す、と書いています。VPC の中からなら通常のホスト名がエンドポイントに解決されるはずですが、試していません。もう 1 つは、ステージングエリア用に専用のサブネットを作っていないことです。ドキュメントは専用のサブネットを勧めています。この章は 11章のサブネットをそのまま使いました。

`-c placement=public` にすると、エンドポイントは作りません。ソースもレプリケーションサーバーも、インターネットゲートウェイを通って DRS に届きます。そのかわり、レプリケーションサーバーにパブリック IPv4 アドレスが要ります。

### 23章のセキュリティグループには 1500 番がない

23章のインスタンスのセキュリティグループは、アウトバウンドを 443 番だけに絞っていました。このままでは、エージェントは DRS には届いても、ブロックを送る 1500 番で止まります。

セキュリティグループは 23章のスタックのリソースです。この章のスタックからは、ID を受け取って、アウトバウンドの規則を 1 つ足すだけにしました。

<<< @/examples/40-disaster-recovery/infra/lib/dr-stack.ts{agent}

コードの後半がその部分です。宛先は VPC の中に限り、ポートは 1500 番だけです。受ける側のレプリケーションサーバーには、DRS が用意するセキュリティグループを使います。このグループは 1500 番のインバウンドを開けていて、規則が変えられると DRS が元に戻す、とドキュメントにあります。

別のスタックのリソースに、外から規則を足すやり方には代償があります。23章のソースには 1500 番の規則が書かれていないので、23章の側でドリフトを調べると、差として見える可能性があります（見えるかどうかは確かめていません）。本来は、インスタンスを持っている 23章のスタックに書くべき設定です。

## エージェントの権限

<!-- section: 40.agent -->

エージェントを入れるには、AWS の認証情報が要ります。ドキュメントが挙げる方法は 2 つです。

オンプレミスのサーバーでは、`AWSElasticDisasterRecoveryAgentInstallationPolicy` を付けたロールを作り、STS の `AssumeRole` で取った一時的な認証情報をインストーラーに渡します。ドキュメントは、長く使えるアクセスキーではなく、一時的な認証情報を勧めています。

EC2 のインスタンスでは、認証情報を作る必要がありません。インスタンスプロファイルのロールに `AWSElasticDisasterRecoveryEc2InstancePolicy` が付いていれば、エージェントは 23章で見た IMDS から認証情報を取ります。この章は、こちらを使います。鍵をどこにも置かずに済むからです。

AWS が管理している `AWSElasticDisasterRecoveryEc2InstancePolicy` には、この章では使わない権限も入っています。別のアカウントのロールを引き受ける `sts:AssumeRole` と、source network を作る権限です。そこで、同じ内容からその 2 つを除き、リソースをこのリージョンとアカウントのソースサーバーに絞ったポリシーを作りました。さきほどのコードの前半が、それです。

導入と登録のための 4 つのアクションだけは、リソースが `*` のままです。AWS のポリシーでも `*` で、登録の前には名前を指定できるソースサーバーが存在しないからです。テストは、アクションの一覧がこの 15 個であること、`*` がこのステートメントにしか無いこと、タグを付けられるのがソースサーバーを作るときだけであることを固定しています。

絞ったポリシーでエージェントが動くことは、確かめていません。動かなければ、まず AWS が管理しているポリシーに付け替えて、権限の不足かどうかを切り分けてください。

ロールも 23章のスタックのリソースなので、名前を受け取って、このポリシーを付けるだけにしています。ロールの名前とセキュリティグループの ID は、23章をデプロイした後に、インスタンスの ID から調べます。

```bash
aws ec2 describe-instances --region ap-northeast-1 --instance-ids i-xxxxxxxxxxxxxxxxx --query 'Reservations[].Instances[].[SecurityGroups[].GroupId,IamInstanceProfile.Arn]'
aws iam get-instance-profile --instance-profile-name <上の ARN の末尾の名前> --query 'InstanceProfile.Roles[].RoleName'
```

23章で見たとおり、インスタンスのロールに付けた権限は、そのマシンで動くすべてのコードに付けた権限です。ノート API のプロセスも、同じ認証情報で DRS のエージェント用の API を呼べるようになります。

## 宣言できるもの、できないもの

<!-- section: 40.declarable -->

ここまでの本では、リソースはスタックに書いてきました。DRS では、それができる範囲が狭くなります。

CloudFormation のリソースの種類として存在するのは、レプリケーションの設定のテンプレート、起動の設定のテンプレート、source network、recovery plan の 4 つです。サービスの初期化、エージェントの導入、ソースサーバー、訓練と復旧の開始、リカバリーインスタンスの終了、failback は、どれもリソースではなく API の呼び出しです。ソースサーバーは、エージェントが自分を登録したときにできるもので、テンプレートには書けません。

さらに、その 4 つがどのリージョンでも使えるわけではありません。CloudFormation は、リージョンごとに、使えるリソースの種類の定義を zip で配っています。2026-10-13 に取得したもので見ると、`AWS::DRS` の定義は us-east-1 と us-west-2 にはあり、ap-northeast-1 には 1 つもありませんでした。ap-northeast-3、us-east-2、eu-west-1、ap-southeast-1 にもありません。CloudFormation のテンプレートリファレンスの目次にも、`AWS::DRS` の項目は見当たりませんでした。

cdkd にとっても事情は同じです。固定した版の cdkd（0.296.28）は `AWS::DRS` の専用の実装を持たないので、Cloud Control API 経由になります。Cloud Control API が扱えるのは、そのリージョンに登録されている種類だけです。

そこで、2 つのテンプレートは、既定ではスタックに入れていません。内容は純粋な関数が組み立てます。

EC2 の起動テンプレートは、また別です。ソースサーバーが登録されたときに DRS が作り、切り離すと DRS が消します。名前とデバイス名は変えるな、とドキュメントにあります。DRS が持ち主であるリソースを、自分のスタックに取り込むことはしません。サブネット、セキュリティグループ、インスタンスタイプ、インスタンスプロファイルを、コンソールか EC2 の API で設定します。

## 訓練の判断

<!-- section: 40.planner -->

訓練を始める API は `StartRecovery` で、渡すのは、ソースサーバーの ID、どの時点から起動するか、訓練かどうかの 3 つです。時点を省くと、DRS はその場でスナップショットを取ろうとします。

その前に決めることを、関数にしました。どのサーバーを起動できるか、どの時点から起動するか、そのときどれだけのデータを失うか、それは自分の決めた RPO に収まるか、です。

<<< @/examples/40-disaster-recovery/src/drill.ts{plan}

**この関数は、ドキュメントに書いてある挙動を写したモデルです。DRS ではありません。** 変換にかかる時間も、インスタンスの空きも、クォータも知りません。ここで「起動できる」と出ても、DRS が起動に成功するとは限りません。

ドキュメントから写した決まりは、3 つあります。

最初の同期が終わっていないサーバーは、起動できません。終わっていれば、遅れていても、複製が止まっていても、訓練はできます。

時刻を指定したときは、その時刻か、それより少し前のスナップショットが使われます。関数は、指定した時刻以前でいちばん新しいものを選びます。近いからといって、後のスナップショットは選びません。事故より後の状態に戻しては意味がないからです。

「いちばん新しいデータ」を選ぶと、DRS はソースサーバーに接続してスナップショットを取ろうとします。ソースが落ちているときは、時間切れを待つことになります。本当の災害では、その待ち時間が RTO に入るので、すでにあるスナップショットを選んだほうが早いことがあります。

失うデータの長さが「不明」になる場合を、「収まる」とは別の値にしてあります。遅れが報告されていないサーバーを、遅れ 0 として扱わないためです。遅れは API の `lagDuration` で返りますが、API リファレンスにあるのは「1 文字から 64 文字の文字列」という記述だけで、書式がありません。

## 復旧の順序

<!-- section: 40.order -->

復旧には順序があります。データを持っているサーバーが先で、それを使うアプリが次、利用者の通信を切り替えるのは最後です。この順序を、データとして書きました。

<<< @/examples/40-disaster-recovery/src/order.ts{graph}

ノートのアプリでは、インスタンスが 1 台で、データもアプリも同じマシンにあるので、段は 4 つです。アドレスを切り替える前に、元のサーバーがもう書き込みを受けないことを確かめる段を入れてあります。理由は[分散システムとして見ると](/ja/chapters/40-disaster-recovery/wrap.md)で扱います。

サーバーが何台もある場合、起動の順序は DRS の recovery plan に任せられます。起動の後の確認と切り替えは、どちらにしても自分の仕事です。

順序を実行する関数は、途中で失敗したら止まり、もう一度呼ぶと続きから始めます。

<<< @/examples/40-disaster-recovery/src/order.ts{run}

テストは、アプリの確認が失敗する場合を決まった順序で再現します。1 回目は確認で止まり、アドレスの切り替えには進みません。2 回目は確認からやり直し、インスタンスを 2 台目まで起動することはありません。

もう 1 つのテストは、切り替えが成功したのに応答だけが失われた場合です。関数からは失敗に見えるので、再実行で切り替えがもう一度走ります。どの段も、2 回実行して困らない操作でなければなりません。DNS のレコードを同じ値に書き換えるのは問題ありませんが、インスタンスの起動を 2 回走らせると 2 台できます。
