# 03 Static Hosting: デプロイ

このページでは、定義したバケットとディストリビューションを AWS に作り、ビルドした SPA を公開して、読者に届いたことを確かめます。

## デプロイする

<!-- section: 03.deploy -->

`.env` の設定と `vp run infra:bootstrap` は、02章で済ませてあるものとして進めます。

```bash
vp run spa:infra:diff
vp run spa:infra:deploy
```

ディストリビューションを作ると、API がレスポンスを返したあとも、各地のエッジロケーションへの反映が続きます。この本の deploy タスクは cdkd に `--full-wait` を渡して、反映が終わるまで待ちます。どれだけかかるかは計測していません。

デプロイが終わると、`DistributionDomainName` に `dxxxxxxxxxxxx.cloudfront.net` の形のドメイン名が出力されます。この時点ではバケットが空なので、開いても何も表示されません。

ここから先の AWS に触るタスクは、まだ実際のアカウントで通して実行できていません。内訳は[章末の検証メモ](/ja/chapters/03-spa/wrap.md)にまとめてあります。

### インフラの作成と、内容の公開は別の作業

Cloudflare Pages や Vercel と進め方が違うのは、インフラの作成と内容の公開を別のタスクで実行する点です。

- インフラの作成と変更は `spa:infra:deploy` で実行します。変わるのはバケット、ディストリビューション、関数で、実行する機会は多くありません
- 内容の公開は `spa:publish` で実行します。変わるのはバケットの中のオブジェクトで、アプリを変更するたびに実行します

`spa:infra:deploy` を実行しても、アプリの新しい版は公開されません。反対に、`spa:publish` はバケットやディストリビューションの設定に触れません。こうして分けておくと、内容だけをすばやく更新でき、インフラを管理するのは cdkd だけになります。

## 公開する

<!-- section: 03.publish -->

```bash
vp run spa:publish:plan
vp run spa:publish
```

`spa:publish:plan` は、何をアップロードして何を消すかを表示するだけで、何も変えません。実際に公開するのは `spa:publish` です。どちらのタスクも、先に `vp run build:spa` を実行します。

公開の処理は、何をするかを決める部分と、それを実行する部分に分けてあります。決める部分は純粋な関数なので、AWS なしでテストできます。

### キャッシュの方針

<<< @/tools/src/site/plan.ts{cache}

Vite は、`assets/` 以下のファイル名に内容のハッシュを入れます。内容が変わればファイル名も変わるので、同じ URL の内容が変わることはありません。そのため、1 年間キャッシュさせ、再確認もさせません。

`index.html` はファイル名が変わりません。長くキャッシュさせると、新しい版を公開しても、読者には古い `index.html` が届き続けます。そこで、キャッシュはしてよいが、使う前に必ずオリジンに確かめるように指示します。CloudFront はこの確認を S3 への条件付きリクエストとして送り、変わっていなければ本体を転送しません。

この方針をとっているので、通常の公開では**キャッシュの無効化（invalidation）が要りません**。invalidation は、エッジのキャッシュを期限前に捨てさせる操作です。誤ったヘッダーで公開してしまったときの復旧用に `vp run spa:invalidate` を用意していますが、ふだんは使いません。

### 公開の順序

公開は次の順で進めます。

1. ハッシュ付きのアセットをアップロードする
2. `index.html` などをアップロードする
3. ビルドに含まれなくなったページを消す
4. いまのビルドに含まれず、アップロードから 30 日以上経ったアセットを消す
5. どのリビジョンを公開したかを記録した `aih-revision.json` を置く

1 と 2 を逆にすると、新しい `index.html` が、まだ存在しない JavaScript を指している時間ができてしまいます。

古いアセットをすぐに消さないのも、同じ理由からです。公開の直前にページを開いた読者は、古い `index.html` を持っています。その読者があとで画面を切り替えると、古いアセットが要求されます。

途中で失敗しても、もう一度実行すれば続きから進みます。内容が同じファイルはアップロードを省くからです。1 の途中で止まった場合は、どこからも参照されないファイルがバケットに増えるだけで、公開中のサイトは変わりません。

この公開の手順は、小さな分散システムになっています。バケット、各地のエッジのキャッシュ、読者のブラウザは、それぞれ別の時点の内容を持っていて、全員が同時に新しい版へ切り替わる瞬間はありません。この手順が守っている不変条件は、読者が手にしている `index.html` の指すファイルを、必ず取得できることです。

## 届いたことを確かめる

<!-- section: 03.smoke -->

```bash
vp run spa:smoke
```

公開のコマンドが成功して終わったことは、内容が読者に届いたことの証明にはなりません。このタスクは、公開した URL を実際に取得して、次のことを確かめます。

- `/` が HTML を返し、再確認を求める `Cache-Control` が付いている
- `/notes/aih-smoke-deep-link` が、アプリの `index.html` を返す
- `/assets/aih-smoke-missing.js` が 404 になる（HTML と 200 ではない）
- ハッシュ付きのアセットに、1 年間の `Cache-Control` が付いている
- HTTP で開くと HTTPS に転送される
- `aih-revision.json` のリビジョンが、手元の commit と一致する

最後の検査で、新しい内容が CloudFront に反映されたことを確かめています。一致するまで 15 秒おきに再試行し、10 分で打ち切ります。

## ドリフトを確かめる

```bash
vp run spa:infra:drift
```

02章と同じ判定を使います。この章では、気をつける点が 1 つあります。このスタックには `AWS::CloudFront::Function` が含まれていて、固定した版の cdkd は、この種類のリソースを専用の実装ではなく Cloud Control API 経由で扱います。読み戻しの結果がどうなるかは、実際の AWS で確かめていません。`unsupported` や `incomplete` が出た場合、判定は不合格（終了コード 11）になります。この不合格は、ドリフトがあるという意味ではなく、確かめられなかったという意味です。
