# 20 CI/CD: デプロイ

[前のページ](/ja/chapters/20-shipping/build.md)で、CloudFormation にデプロイする経路とワークフローを組み立てました。このページでは、デプロイが失敗したときに何が起きるかと、デプロイのあとに実物がテンプレートからずれていないかを確かめる方法を扱います。

## 戻せるもの、戻せないもの

<!-- section: 20.rollback -->

失敗したらロールバックされる、というときに、実際に戻るものと戻らないものを分けておきます。

戻せるのは、テンプレートに書いてあるものです。関数のコード、環境変数、メモリの設定、IAM のポリシー、ルートがこれにあたります。CloudFormation が自動で戻す場合も、`git revert` してデプロイし直す場合も、戻るのはこの範囲です。

戻せないのは、新しいコードが動いている間に起きたことです。

- 書き込まれたデータ。新しいコードが保存した行やオブジェクトは、コードを戻しても残ります
- 変えてしまったスキーマ。列を消したあとでは、消す前のコードに戻しても動きません
- 消したバケットやテーブルの中身。`RemovalPolicy.RETAIN` にしていなければ、戻す先がありません
- 外に出ていったもの。送ったメール（15章）や、呼び出した外部の API です

Cloudflare Workers でも事情は同じです。公式ドキュメントはロールバックについて、Worker につながったリソースは変わらないこと、データの構造がバージョンの間で変わっているとエラーになりうることを注意しています。

### バージョンとエイリアス

Lambda には、コードを速く戻すための仕組みがあります。

<<< @/examples/20-shipping/infra/lib/ship-api-stack.ts{version}

Lambda のバージョン（version）は、関数のコードと設定の番号付きの写しで、発行したあとは変えられません。エイリアス（alias）は、バージョンを指す名前つきのポインタです。このスタックでは、API Gateway は関数そのものではなく `live` というエイリアスを呼びます。デプロイで関数が変わると、新しいバージョンが発行され、`live` が新しいバージョンを指すようになります。

古いバージョンは、消さずに残しています（`RemovalPolicy.RETAIN`）。CloudFormation が更新をロールバックするときに、`live` を前のバージョンに戻せるようにするためです。そのかわり、バージョンはデプロイのたびに増えていき、スタックを消して関数が消えるまで残ります。

エイリアスは、2 つのバージョンに重みを付けてリクエストを振り分けることもできます。新しいバージョンに 10% だけ流して様子を見る、という使い方です。AWS のドキュメントによれば、振り分けは確率的なので、リクエストが少ないと、設定した割合から大きくずれることがあります。CodeDeploy には、この振り分けを時間をかけて自動で進める設定が用意されています。この章では、どちらも実装していません。エラー率のアラーム（[19章](/ja/chapters/19-observability.md)）につないで止める仕組みがないまま段階的に切り替えても、問題に気づくのが遅くなるだけだからです。

急いでいるときには、コンソールで `live` を前のバージョンに付け替えたくなるかもしれません。付け替えれば戻りますが、CloudFormation の外で加えた変更なので、ドリフトになります。テンプレートは新しいバージョンを指したままなので、次のデプロイで `live` はまた新しいバージョンを指します。戻すときは、コードを戻してデプロイしてください。緊急で手で戻した場合は、あとで必ずコードを合わせます。このページの後半で扱うドリフト検出は、こうした手作業の変更を見つけるためのものでもあります。

### スキーマは、古いコードが動く順に変える

コードと DB のスキーマは、同時には変わりません。しかも、ロールバックで戻るのはコードだけです。

そのためスキーマの変更は、1 つ前の版のコードが新しいスキーマでも動く順番に分けます。

1. 足す。新しい列やテーブルを足すだけにする。古いコードは、足されたものを知らなくても動く
2. 新しいコードを出す。ここでロールバックしても、古いコードは 1 のスキーマで動く
3. 古い行を埋める
4. 古い列を、もう誰も読んでいないことを確かめてから消す。消すのは別のデプロイにする

4 を 2 と同じデプロイに入れると、そのデプロイは戻せなくなります。動いている DB のスキーマを変えるときの同じ話を、[13章](/ja/chapters/13-sql.md)では DSQL について書いています。スキーマのない DynamoDB（[05章](/ja/chapters/05-dynamodb.md)）でも、アイテムの形について同じことが言えます。コンテナで新旧の版が同時に動く時間の扱いは、[12章](/ja/chapters/12-containers.md)にあります。

## デプロイは途中で止まる

<!-- section: 20.partial -->

ここまでデプロイを 1 つの出来事として書いてきましたが、実際には何十回もの API 呼び出しが順に並んだもので、その途中のどこででも止まります。

```figure
caption: スタックがロールバックを終えるまでのあいだに、API を呼ぶ側には新しいコードが応えている時間がある
type: sequence
actor cfn: CloudFormation スタック
actor caller: API を呼ぶ側
note cfn: t1: UPDATE_IN_PROGRESS
note caller: 古いコード (alias live -> version 7)
step cfn -> cfn: t2: AWS::Lambda::Version 8 を作る
note caller: 古いコード
step cfn -> cfn: t3: alias live を version 8 に移す
note caller: 新しいコード
step cfn -x cfn: t4: 別のリソースの更新が失敗
note caller: 新しいコード
note cfn: t5: UPDATE_ROLLBACK_IN_PROGRESS
note caller: 新しいコード、エイリアスが戻ると古いコード
note cfn: t6: UPDATE_ROLLBACK_COMPLETE
note caller: 古いコード、t3..t5 に書かれたものは残る
```

この図は一例で、どのリソースがどの順で更新されるかは、テンプレートの依存関係で決まります。注目してほしいのは t3 から t5 の間です。この間は、新しいコードが本番のリクエストに応えています。そのあとスタックは元の状態に戻ったと報告しますが、t3 から t5 の間に書かれたデータは戻っていません。

ロールバック自体が失敗することもあります。たとえば、戻す先のリソースが誰かの手で消されていた場合です。そうなるとスタックは `UPDATE_ROLLBACK_FAILED` になり、一部は新しく、一部は古いまま止まります。この状態のスタックは更新できません。

この章が守る不変条件は 1 つです。**ほかの操作が動いているスタックと、人が直さないと先へ進めないスタックには、デプロイを始めない。**

<<< @/examples/20-shipping/src/stack-status.ts{next-step}

CloudFormation が返しうるすべての状態について、次に何をしてよいかを決めてあります。`switch` に `default` がないので、SDK の型に新しい状態が増えると、型検査が失敗します。

```bash
vp run ship:cfn:status
```

このタスクは、スタックの状態と、次にとるべき操作を表示します。終了コードが 1 になるのは、人が直さないと進めない状態のときだけです。[デプロイのワークフロー](/ja/chapters/20-shipping/build.md)がデプロイの前に呼んでいたのが、このタスクです。

テストは、この不変条件が破れる場合を探します。名前が `_IN_PROGRESS` で終わる状態が、1 つでも「デプロイ可」になっていないかを確かめます。更新が失敗して元に戻るまでの状態を順に並べ、途中で一度でも「デプロイ可」と答えないかも確かめます。ロールバックにも失敗したスタックを「デプロイ可」としていないことも確かめます。

最初の作成に失敗したスタックの状態である `ROLLBACK_COMPLETE` は、扱いが少し特殊です。CloudFormation では、この状態のスタックは消すことしかできません。ところが、固定した版の CDK CLI は、次の `cdk deploy` のときに、この状態のスタックを自分で消してから作り直します（CLI のコードで確かめました）。そのため「デプロイ可」にしてありますが、表示する文には「CloudFormation にできるのは削除だけ」と書いてあります。

失敗したあとに、先へ進めるか戻すかで迷ったときの目安を書いておきます。スタックが `UPDATE_ROLLBACK_COMPLETE` になっているなら、すでに戻っています。イベントから最初の失敗を探し、原因を直して、もう一度デプロイします。`UPDATE_ROLLBACK_FAILED` なら、まず `cdk rollback` で最後まで戻すことを優先します。半分だけ新しい状態の上に、さらに変更を重ねないでください。

## CloudFormation のドリフトを同じ判定に通す

<!-- section: 20.drift -->

02章で、ドリフトの判定を作りました。「差が見つからなかった」と「すべて比べて一致した」を区別し、後者のときだけ合格にする判定です。ただし、02章の判定は cdkd 用でした。CloudFormation で作ったスタックには cdkd の state がないので、cdkd のドリフト検出は使えません。反対に、cdkd で作ったスタックは CloudFormation のスタックとして存在しないので、CloudFormation のドリフト検出では調べられません。

そこで、CloudFormation のドリフト検出を呼び、結果を 02章と同じ形の report に変換して、同じ判定に通します。

CloudFormation のドリフト検出は非同期で、次の順に API を呼びます。

1. `DetectStackDrift` で検出を始める。返ってくるのは、検出の ID だけ
2. `DescribeStackDriftDetectionStatus` を、検出が終わるまで繰り返し呼ぶ
3. `DescribeStackResourceDrifts` で、リソースごとの結果を読む

## `IN_SYNC` は「全部一致」ではない

<!-- section: 20.drift-coverage -->

CloudFormation がスタックを `IN_SYNC` と報告しても、すべてが一致しているとは限りません。公式ドキュメントを読むと、検査の範囲は次のように限られています（確認日 2026-10-12）。

- 検査するのは、対応している種類のリソースだけ。対応していないリソースは、何も言わずに飛ばされます。対応するリソースが 1 つも無いスタックも、`IN_SYNC` になります
- 比べるのは、テンプレートで明示したプロパティだけ。既定値のままにした設定を誰かが変えても、ドリフトにはなりません
- ネストされたスタック（nested stack）の中は見ない。親で検出しても、子は別に検出する必要があります
- 比べられないプロパティがある。Lambda 関数のコード、`KMSKeyId`、パスワードのようにサービスが値を返さない項目です
- 結果が古いことがある。リソースごとの結果には、それぞれ検査した時刻が付いています

この章の判定は、これらを 1 つずつ拾います。前の節で `ListStackResources` を足したのは、1 つ目を拾うためです。`DescribeStackResourceDrifts` は検査したリソースしか返さないので、スタックにあるリソースの一覧と突き合わせ、結果が無いものを「未検査」として数えます。5 つ目は、結果の時刻が今回の検出の開始より前のリソースを、検査済みに数えないことで拾っています。

2 つ目だけは、判定では拾えません。report の `clean` が意味するのは、テンプレートに書いたプロパティがすべて一致した、ということまでです。そのため、ドリフトを見張りたい設定は、既定値と同じであっても、CDK のコードに明示しておく価値があります。

この点は cdkd と違います。cdkd のドキュメントによると、cdkd はデプロイのときに、AWS が返したプロパティをすべて state に写しておきます。そのため cdkd のドリフト検出は、コードに書かなかったプロパティの変更も見つけます。どちらが優れているかではなく、比べている対象が違います。

### この章のスタックの場合

`AihShipApi` が使うリソースの種類を、公式の対応表と照らし合わせました。

<<< @/examples/20-shipping/src/drift-coverage.ts{coverage}

API Gateway の統合（integration）は、ルートと Lambda をつなぐ設定です。対応表では、この種類のドリフトの欄が「No」になっています。したがってこのスタックは、何もずれていなくても `clean` にはならず、`unsupported` になって、判定は 11 を返します。

毎日 11 で失敗する検査は、3 日もすれば誰も見なくなります。かといって 11 を合格と読み替えると、02章で作った区別が意味を失います。そこで、検査できないと分かっていて、それを承知している種類の一覧を、コードに置きました。

<<< @/tools/src/drift/cloudformation.ts{acknowledge}

未検査のリソースがすべてこの一覧にある種類のときだけ、タスクは 0 で終わります。そのときも report の状態は `unsupported` のままで、判定も不合格のままです。表示にも「比べていない」と出ます。変わるのは、タスクの終了コードだけです。ドリフトがあった場合や、一覧にない種類が未検査だった場合は、これまでどおり失敗します。

一覧に種類を足すにはコードを変更することになるので、プルリクエストで、理由と一緒にレビューされます。また、スタックに新しい種類のリソースを足すと、その種類を「検査される」一覧か「承知のうえで検査されない」一覧のどちらかに入れるまで、テストが失敗するようにしてあります。

未検査を減らすために、設計の側でできることもあります。このスタックは、関数のロールの権限を、`AWS::IAM::Policy` という別のリソースにせず、ロールの中にインラインで書いています。

<<< @/examples/20-shipping/infra/lib/ship-api-stack.ts{role}

04章の書き方（`grantWrite`）では、権限は `AWS::IAM::Policy` という別のリソースになります。この種類は、対応表に載っていません。ロールの中に書けば、権限はロールのプロパティになり、ロールは検査の対象です。同じ理由で、`AWS::CDK::Metadata` というリソースも出力しないようにしました。未検査のリソースが 1 つ減るたびに、report が保証できる範囲が広がります。

ただし、ここまでの内容は対応表を読んで判断したものです。統合が本当に未検査になるのか、ロールの権限を手で変えたらドリフトとして検出されるのかは、次の節の手順を実際に通すまで分かりません。

## わざとずらしてみる

<!-- section: 20.drift-lab -->

dev のスタック（`AihShipApi`）をデプロイしてあれば、次の順に試せます。

1. `vp run ship:cfn:drift` を実行する。統合が未検査として表示され、状態は `unsupported`、タスクは 0 で終わるはず
2. コンソールの Lambda の画面で、関数のメモリを 256 MB から 512 MB に変える
3. `vp run ship:cfn:diff` を実行する。変更なしと出るはず。いま synth したテンプレートも、CloudFormation が覚えているテンプレートも、変わっていないため
4. `vp run ship:cfn:drift` を実行する。`drifted` になり、`/MemorySize` が表示され、終了コードが 10 になるはず
5. 戻す。コードは 256 のままなので、コンソールで 256 に戻すか、`vp run ship:cfn:deploy --revert-drift` を試す
6. もう一度 `vp run ship:cfn:drift` を実行し、1 と同じ結果に戻ったことを確かめる

どの手順にも「はず」と書いたのは、この手順をまだ実際のアカウントで通していないからです。5 の `--revert-drift` は、固定した版の CLI のヘルプに載っているフラグですが、動作は確かめていません。また、テンプレートが変わっていないとき、通常の `cdk deploy` は「変更なし」と判断して何もしません。そのため、デプロイし直すだけではドリフトが直らないことがあります。

02章の cdkd には、ドリフトを解消するタスク（revert と accept）がありました。この章には用意していません。CloudFormation で実物のほうを正しいものとして扱うには、コードを実物に合わせて直してからデプロイするのが、本来の手順だからです。
