# 11 Network: しくみと実装

このページでは、[前のページ](/ja/chapters/11-network.md)で計画した VPC を、スタックのコードにしていきます。扱うのは、経路、通信の許可、VPC の外への出口、料金、AZ の障害です。

<<< @/examples/11-network/infra/lib/network-stack.ts{routes}

サブネットの種類は、`0.0.0.0/0`（すべての宛先）をインターネットゲートウェイへ送る経路が 1 行あるかどうかで決まります。この 1 行があるルートテーブルを持つサブネットがパブリックで、ないサブネットがプライベートです。「プライベート」という設定項目がどこかにあるわけではありません。

どのルートテーブルにも、VPC の中どうしで通信するための経路（local route）が最初から入っています。そのため、プライベートサブネットのリソースも、同じ VPC のパブリックサブネットのリソースとは通信できます。届かないのは VPC の外だけです。

サブネットごとにルートテーブルを作っているのは、main route table に頼らないためです。VPC には最初から main route table があり、どのルートテーブルにも関連付けていないサブネットは、main route table に従います。誰かが main route table にインターネットへの経路を足すと、関連付けを忘れたサブネットがすべてパブリックになってしまうので、4 つとも明示的に関連付けています。

パブリックサブネットでは、`mapPublicIpOnLaunch` も `false` にしています。パブリックサブネットに置いただけでは、リソースはインターネットと通信できず、public IPv4 アドレスも必要です。public IPv4 アドレスには 1 つにつき 1 時間 USD 0.005、月に USD 3.65 かかるので、自動では配らず、必要なリソースが自分で求める形にしました。

テストは、既定の構成で、インターネットへの経路がパブリックの 2 つのルートテーブルにしかないことを確かめています。

## セキュリティグループとネットワーク ACL

<!-- section: 11.firewall -->

経路があることと、通信が許されることは別です。ルートテーブルが決めるのは通信をどこへ届けられるかで、届いた通信を受け取るかどうかは、セキュリティグループ（security group）が決めます。

セキュリティグループは、インスタンスなどのリソースに付ける規則で、書けるのは許可だけです。また、ステートフル（stateful）なので、許可した通信への返事は、逆向きの規則がなくても通ります。

この章でセキュリティグループが出てくるのは、インターフェイスエンドポイントを足したときだけです。

<<< @/examples/11-network/infra/lib/network-stack.ts{interface-endpoints}

入ってくる向きに「VPC の中から、443 番」を許しているだけで、エンドポイントからの返事を通す規則は書いていません。ステートフルなので、書かなくても返事は通ります。

似た名前のものに、ネットワーク ACL（network ACL）があります。ネットワーク ACL はサブネットの境界に付き、許可と拒否の両方を書けて、規則は番号順に評価されます。こちらはステートレス（stateless）で、行きを許しても、帰りを別に許さなければ通りません。

VPC には、すべてを許可するネットワーク ACL が最初から付いていて、この章はそれに手を入れていません。AWS のドキュメントも、セキュリティグループだけでリソースを守れると書いています。ネットワーク ACL が要るのは、「この範囲からの通信はサブネットごと拒否したい」のように、拒否を書きたいときです。

この節で説明した振る舞い（返事が通ること、ネットワーク ACL との違い）は、ドキュメントで読んだ内容で、実際の AWS で通信して確かめたものではありません。

## プライベートサブネットから AWS を呼ぶ 3 つの方法

<!-- section: 11.egress -->

プライベートサブネットに置いたコンテナが、S3 からファイルを読み、ECR からイメージを取得し、CloudWatch Logs にログを送るとします。どれも AWS のサービスですが、入口は VPC の外にあるので、経路がなければ届きません。

届かせる方法は 3 つあります。

1 つ目はゲートウェイエンドポイント（gateway endpoint）で、S3 と DynamoDB だけに使えます。作ると、ルートテーブルに「このサービス宛てはここへ」という経路が 1 行入ります。追加料金がかからないので、既定で作っています。

<<< @/examples/11-network/infra/lib/network-stack.ts{gateway-endpoints}

2 つ目はインターフェイスエンドポイント（interface endpoint）で、サービスへの入口を、プライベート IP アドレスつきでサブネットの中に置きます（AWS PrivateLink）。対応しているサービスは多いのですが、サービスごと、AZ ごとに 1 時間 USD 0.014 かかり、通したデータにも 1 GB あたり USD 0.01 かかります。コードは、セキュリティグループの節で見たものです。`privateDnsEnabled` を有効にしてあるので、SDK がいつもどおりのホスト名を呼べば、エンドポイントに届きます。

3 つ目は NAT Gateway で、プライベートサブネットからインターネット全体へ出られるようにする中継点です。パブリックサブネットに置いて、Elastic IP アドレスを 1 つ持たせます。AWS のサービスだけでなく、外部の API や npm のレジストリにも届きます。料金は 1 つにつき 1 時間 USD 0.062、通したデータに 1 GB あたり USD 0.062 です。

<<< @/examples/11-network/infra/lib/network-stack.ts{nat}

どれを選ぶかは、何を呼びたいかで決まります。

| | 届く先 | 置いてあるだけの料金 | 通したデータ |
| --- | --- | --- | --- |
| ゲートウェイエンドポイント | 同じリージョンの S3 と DynamoDB | なし | なし |
| インターフェイスエンドポイント | 足したサービスだけ | 1 つ・1 AZ あたり USD 0.014／時 | USD 0.01／GB |
| NAT Gateway | インターネット全体 | 1 つ USD 0.062／時、加えて public IPv4 が USD 0.005／時 | USD 0.062／GB |

## 置いてあるだけでかかる料金

<!-- section: 11.cost -->

金額は USD、東京リージョン、従量課金、税別で、1 か月は 730 時間です。計算の中身は[料金の計算](/ja/reference/pricing.md)にあります。

| 構成 | 時間で課金されるもの | 通信がなくてもかかる月額 | 月 10 GB 通したとき |
| --- | --- | --- | --- |
| 既定 | なし | 0 | 0 |
| `-c egress=nat` | NAT Gateway 1、public IPv4 1 | 48.91 | 49.53 |
| `-c egress=nat-per-az` | NAT Gateway 2、public IPv4 2 | 97.82 | 98.44 |
| `-c interfaceEndpoints=ecr.api,ecr.dkr,logs` | インターフェイスエンドポイント 3 × 2 AZ | 61.32 | 61.42 |

既定の 0 は、料金がわからないので 0 と書いたものではありません。VPC、サブネット、ルートテーブル、インターネットゲートウェイ、ゲートウェイエンドポイントには、もともと料金がありません。

表から読み取れることが 3 つあります。

NAT Gateway は、通信がなくても月 USD 45.26 かかります。そこに Elastic IP アドレスの USD 3.65 が加わります。public IPv4 アドレスは、使っていてもいなくても同じ単価で課金されます。

インターフェイスエンドポイントの料金は、数と AZ の掛け算になります。1 つを 2 つの AZ に置くと月 USD 20.44 で、3 つ置けば、通信がなくても NAT Gateway 1 つより高くなります。エンドポイントのほうが得になるのは、通すデータが多いときです。表の `-c egress=nat` の構成と、インターフェイスエンドポイントを 3 つ足した構成を比べると、月におよそ 240 GB を超えたあたりで逆転します（1 GB あたりの差が USD 0.052、固定費の差が USD 12.41）。

1 時間に満たない利用も、1 時間ぶんとして請求されます。NAT Gateway もインターフェイスエンドポイントも、作って 5 分で消しても 1 時間ぶんです。

この表に入れていないものもあります。インターネットへ出ていくデータ転送の料金と、AZ をまたぐデータ転送の料金です（0 という意味ではなく、未算入です）。10 GB という通信量も仮定にすぎません。public IPv4 アドレスには無料利用枠の記述がドキュメントにありますが、NAT Gateway の Elastic IP が対象になるかは確かめられなかったので、引いていません。

## Lambda を VPC に入れる条件

<!-- section: 11.lambda -->

Lambda を VPC に入れるのは、RDS のデータベースのように、VPC の中にあるものと通信する必要があるときだけです。DynamoDB や S3 を呼ぶだけの関数を VPC に入れる理由はありません。

VPC に入れると、失うものが 3 つあります。

1 つ目は、インターネットへの経路です。何も設定していない Lambda はインターネットに出られますが、VPC につないだ関数は、その VPC から届く範囲にしか届きません。Lambda のドキュメントには、パブリックサブネットにつないでも、インターネットへの接続も public IP アドレスも得られないと明記されています。

そのため、VPC に入れた関数から Secrets Manager や SQS を呼ぶには、「プライベートサブネットから AWS を呼ぶ 3 つの方法」のどれかが要ります。DynamoDB と S3 にはゲートウェイエンドポイントで届くので、この章の既定の構成のままで足ります。それ以外のサービスには、インターフェイスエンドポイントか NAT Gateway が必要です。Lambda の構成に、置いてあるだけでかかる料金が入ってくるのは、このときが初めてです。

2 つ目は、絞った権限です。VPC につなぐには、実行ロールに、network interface を作ったり消したりするための EC2 の権限が 6 つ要ります。ドキュメントは、この権限を全リソース（`"Resource": "*"`）に対して許すよう求めています。しかも、この権限は関数のコードにも渡ります。04章から `*` を使わない方針で書いてきましたが、ここは例外になります。

3 つ目は、すぐに呼び出せることです。関数を最初に VPC につないだとき、Lambda は network interface を用意します。用意が終わるまで関数は Pending の状態で、呼び出せません。ドキュメントによると、数分かかることがあります。また、14 日間呼ばれなかった関数は、network interface を回収されて Inactive になり、次の呼び出しは失敗します。

この章には、VPC に入れた Lambda のサンプルがありません。VPC の中に、通信する相手がまだいないからです。13章で、データベースと一緒に扱います。

## AZ が 2 つあっても、リージョンは 1 つ

<!-- section: 11.zones -->

サブネットを 2 つの AZ に分けたのは、片方の AZ が止まっても、もう片方で動き続けられるようにするためです。AZ どうしは電源もネットワークも別で、同時に壊れにくいように作られています。RDS も、異なる 2 つの AZ のサブネットを要求します。

ただし、AZ を 2 つにしただけで安心はできず、確かめることが 2 つあります。

1 つ目は、AZ をまたいで共有しているものがないかどうかです。`-c egress=nat` は、NAT Gateway を 1 つだけ、1 つ目の AZ に置きます。安く済みますが、AZ が止まったときの動きは次のようになります。

```text
layout: -c egress=nat  (one NAT gateway, in ap-northeast-1a)

step  event                  Private1 (1a) -> internet   Private2 (1c) -> internet
1     both zones up          via NAT gateway in 1a       via NAT gateway in 1a
2     zone 1a goes down      down with its zone          no way out: its NAT gateway was in 1a
3     same, traffic to S3    down with its zone          still works: gateway endpoint, no NAT involved

layout: -c egress=nat-per-az  (one NAT gateway per zone)

2'    zone 1a goes down      down with its zone          via NAT gateway in 1c

any layout

4     the whole region is impaired: nothing in this VPC is reachable; a second zone does not help
```

step 2 の行では、止まったのは 1a なのに、無事なはずの 1c もインターネットに出られなくなっています。1c が、出口を 1a の NAT Gateway に頼っていたからです。AZ を 2 つに分けた意味が、NAT Gateway を 1 つにしたことで失われています。

テストは、この順序をそのまま再現します。

<<< @/examples/11-network/test/reach.test.ts{zone-failure}

`nat-per-az` なら 1c は出口を失いませんが、固定費は倍になります。開発用なら 1 つ、止まると困るなら AZ ごとに 1 つ、と用途で決めればよく、どちらかが正しいわけではありません。大事なのは、選んだ構成で何が一緒に止まるかを知っておくことです。

2 つ目は、step 4 の行です。AZ はリージョンの中の区切りで、VPC は 1 つのリージョンにしか存在しません。リージョン全体に障害が起きたら、AZ がいくつあっても、この VPC の中のものにはすべて届かなくなります。複数の AZ で備えられるのは AZ 1 つぶんの障害までで、リージョンの障害には備えられません。リージョンの障害に備えるなら、別のリージョンにもう 1 式を置く別の設計になり、この章では扱いません。

この節の invariant を 1 文で書くと、「止まっていない AZ のプライベートサブネットは、ほかの AZ が止まっても、止まる前に届いていた先に届く」です。`nat-per-az` と既定の構成はこの条件を満たし、`nat` は満たしません。テストで、そのとおりに固定してあります。

なお、このテストが壊しているのは計画のモデルで、本物の AZ を止めたわけではありません。
