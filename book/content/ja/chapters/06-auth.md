# 06 Auth: Cognito と認可

SPA は公開でき、ノートはテーブルに残るようになりましたが、誰のノートなのかはまだ区別していません。この章では SPA にサインインを足し、サインインした人が自分のノートだけを読み書きできるようにします。03章の SPA と 05章の API は、この章で初めて 1 つのアプリとしてつながります。

この章のアプリでは、パスワードがアプリのコードを一度も通りません。誰からの呼び出しかを確かめられないリクエストは、関数が起動する前に拒否されます。他人のノートには、ID を知っていても届きません。手元では、Cognito を使わずに 2 人の利用者としてアプリを動かせます。

前提は [03章](/ja/chapters/03-spa.md)と [05章](/ja/chapters/05-dynamodb.md)です。コードは `examples/06-auth/` にあります。ノートの保存と楽観ロックは 05章のコードをそのまま使うので、この章で書くのは、認証と認可のために変わる部分だけです。

## 全体像

```figure

```

```figure
caption: API Gateway の JWT オーソライザーがアクセストークンを検証し、通ったリクエストだけが Lambda とテーブルに届く

edge fn -> table
edge api -x browser: 失敗は 401/403。Lambda は呼ばれない
mark api
```

この章で新しく使うものは 3 つあります。ユーザープール（user pool）は Amazon Cognito が持つ利用者の名簿で、パスワードの検証とトークンの発行を受け持ちます。マネージドログイン（managed login）は Cognito が配信するサインイン画面で、あなたのアプリとは別のドメインで動きます。JWT オーソライザーは API Gateway HTTP API の機能で、リクエストに付いたトークンを検証し、通らなければ関数を呼びません。

### 認証と認可は別の問い

この章では、2 つの問いを分けて扱います。

1 つ目は**認証**（authentication）で、この呼び出しは誰からのものか、という問いです。Cognito と、API Gateway の JWT オーソライザーが答えます。

2 つ目は**認可**（authorization）で、その人はこのノートに触ってよいか、という問いです。Lambda の中のアプリのコードと、テーブルのキーが答えます。

サインインしていても、どのノートにでも触ってよいわけではありません。認証だけを足して認可を忘れると、サインインさえすれば、ID を知っている他人のノートを読める API になります。

### パスワードは Cognito に任せる

パスワードを自分で保存し、照合し、再設定の手順を作ることもできますが、この本ではしません。漏れたときの被害が大きく、正しく作るために気をつける細部も多いからです。Cognito に任せると、このアプリが扱うのは検証済みのトークンだけになります。

Amplify は使いません。Cognito のユーザープールは、OAuth 2.0 と OpenID Connect（OIDC）の標準の手順で使えます。この章の SPA は、汎用の OAuth ライブラリ（oauth4webapi）で標準のエンドポイントを呼んでいるだけです。Cognito を OIDC に対応した別のサービスに替えても、SPA のコードの大半は変わりません。

SPA と API は別のオリジンのままにして、トークンを `Authorization` ヘッダーで送ります。cookie は使いません。別の方法として、サーバー側（BFF）がトークンを持ち、ブラウザには cookie だけを渡すやり方もあります。この方法には、ブラウザの JavaScript からトークンが見えなくなる利点があり、[09章](/ja/chapters/09-ssr.md)で扱います。

## この章の用語

<!-- section: 06.terms -->

この章で使う用語を、先にまとめておきます。

- アクセストークン（access token）は、API を呼ぶためのトークンです。この章で API に送るのは、このトークンです
- ID トークン（ID token）は、サインインした事実と利用者の属性をアプリ自身に伝えるトークンです。API には送りません
- リフレッシュトークン（refresh token）は、新しいアクセストークンを受け取るためのトークンです。トークンエンドポイントのレスポンスには入っていますが、この章の SPA は保存せずに捨てます
- 認可コード（authorization code）は、サインイン後に SPA が受け取る、短命の引換券です。トークンエンドポイントでトークンと交換します
- PKCE は、認可コードを横取りされても交換できないようにする仕組みです
- スコープ（scope）は、トークンに付く、許可の範囲を表す文字列です
- `sub` は、ユーザープールが利用者ごとに発行する、変わらない識別子です

アクセストークンと ID トークンは、どちらも JWT という形式で、同じユーザープールが署名します。見た目では区別がつかないので、API の側では、送られてきたのがアクセストークンであることを設定とコードで確かめる必要があります。

`unauthenticated`（401）は、誰からの呼び出しかわからないことを表します。

`quota_exceeded`（409）は、05章のリポジトリが数えている上限に当たったことを表します。1 人が持てるノートは 100 件までです。05章では持ち主が 1 人（`anonymous`）だったので、全体で 100 件でした。この章からは持ち主がトークンの `sub` になるので、利用者ごとに 100 件です。この章で書いたのは、上限をリポジトリに渡す 1 行（`api/src/compose.ts`）と、エラーを 409 にする数行（`api/src/app.ts`）だけで、数え方は 05章のままです。

ノートについて権限がないこと（403）を表すエラーは、意図して作っていません。他人のノートを指定したときは、存在しないノートを指定したときと同じ `not_found` を返します。403 を返すと、その ID のノートが存在することを教えてしまうからです。

## 呼び出し元を確かめる

<!-- section: 06.identity -->

アプリは、呼び出したのが誰かを調べる処理を、1 つの関数として受け取ります。

<<< @/examples/06-auth/api/src/identity.ts{identity}

実装は 2 つあります。AWS の上では API Gateway が検証した結果を読み、手元では開発用のトークンを検証します。アプリの本体は、どちらの実装が使われているかを知りません。

### AWS では、API Gateway が確かめた結果を読む

<<< @/examples/06-auth/api/src/identity.ts{api-gateway}

関数が動く時点で、API Gateway はトークンの署名、発行者、期限、発行先のクライアントを確かめ終えています。トークンの中身であるクレーム（claims）は、イベントの `requestContext.authorizer.jwt.claims` に入っています。関数は署名を検証せず、検証済みの結果を読むだけです。

それでもアプリの側で、次の 2 つをもう一度確かめます。どちらも API Gateway が入口で見ているものなので、守りが二重になります。

- `token_use` が `access` であること。ID トークンも同じユーザープールが署名しているので、署名と発行者の検証は通ります。しかし、API に送ってよいのはアクセストークンだけです。入口では、[デプロイのページ](/ja/chapters/06-auth/deploy.md)で設定するスコープの要求が ID トークンを落とします
- `client_id` がこのアプリのクライアントであること。同じユーザープールに別のアプリのクライアントを足したとき、そちらに発行されたトークンでこの API を呼べてはいけません。入口では、オーソライザーが audience として同じことを確かめています

イベントにオーソライザーの情報がまったくない場合は、誰でもないものとして扱います。オーソライザーを付け忘れたルートがあっても、そのルートが誰でも通す状態にならないようにするためです。

## 自分のノートにしか届かない

<!-- section: 06.authorization -->

<<< @/examples/06-auth/api/src/app.ts{routes}

認可のためのコードは、ほとんどありません。この利用者がこのノートに触ってよいかを確かめる if 文は、どこにもありません。かわりに、決まりが 2 つあります。

1. service に渡す持ち主は、いつもトークンの `sub` にする。path、query、body からは決して取らない
2. ノートは持ち主の下に保存されている（05章の `pk = OWNER#<持ち主>`）

この 2 つがあると、他人のノートは見つからないことになります。Bob が Alice のノートの ID を指定して `GET /notes/<id>` を呼ぶと、アプリは `OWNER#bob` の下でその ID を探します。そこにはないので、404 が返ります。ここで `bob` と書いた部分に実際に入るのは `sub` で、手元の開発用サインインなら `local-bob`、実環境ならユーザープールが発行する ID です。

ノートを読んでから持ち主が一致するかを比べる方法だと、確認をルートごとに書くことになり、新しいルートを足すたびに書き忘れるおそれがあります。持ち主をキーに入れる方法には、書き忘れる対象がありません。05章で、利用者がまだ 1 人しかいないうちからキーに持ち主を入れておいたのは、このためです。

守っている不変条件は、次の 1 文です。

**リクエストが読み書きできるのは、そのトークンの `sub` を持ち主とするノートだけである。**

テストは、この不変条件を破ろうとします。

- Bob の一覧に Alice のノートが出ない
- Bob が Alice のノートの ID を指定すると、存在しない ID と同じ 404 が返る
- Bob は、ID と version を知っていても、Alice のノートを更新も削除もできない
- Bob が query、ヘッダー、body のすべてに `owner: alice` と書いても、ノートは Bob の下に作られる

`sub` はメールアドレスではありません。メールアドレスは変更でき、別の人に再利用されることもあります。`sub` はユーザープールが発行する変わらない識別子で、公式ドキュメントも、利用者を識別するには `sub` を使うよう勧めています。

### ログに残すもの

誰がどの操作をしたかは、リクエストのログに `sub` として残します。トークンそのものは、決してログに書きません。アクセストークンがログから読めると、ログを見られる人は、期限が切れるまでその利用者になりすませるからです。ログにトークンが含まれないことは、テストで確かめてあります。
