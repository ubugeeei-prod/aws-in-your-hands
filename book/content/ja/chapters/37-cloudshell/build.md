# 37 CloudShell と Cloud9: しくみと実装

このページでは、CloudShell に持っていくスクリプトと、CloudShell を使える人を決めるポリシーを作ります。スクリプトは 1 つのファイルで、4 つのコマンドを持ちます。`whoami` はいまの identity とアカウントを、`budget` は 01章の予算の状況を、`left` は cdkd がまだ記録しているスタックを表示し、`empty` はバケットを空にします。

## 1 つのファイルにまとめる

<!-- section: 37.bundle -->

[概要](/ja/chapters/37-cloudshell.md)のページで見たとおり、CloudShell には依存を入れておく場所がなく、Node.js の版もドキュメントに書かれていません。そこで、スクリプトは次の 2 つの条件を満たすように作ります。

- 1 つのファイルで動く。`npm install` を必要としない
- 古めの Node.js でも動く構文にする

ソースは、これまでの章と同じ TypeScript で、検証には Valibot を使います。それを esbuild で 1 つの `.mjs` にまとめます。ビルドは手元で実行し、できたファイルだけを CloudShell に持っていきます。

<<< @/examples/37-cloudshell/scripts/bundle.ts

`target` を `node18` にしたので、esbuild は Node.js 18 が読める構文で出力します。23章のバンドルが `node24` だったのは、インスタンスに入る Node.js の版を自分で決められたからです。CloudShell では決められないので、低いほうに合わせます。Node.js 18 で実際に動かしての確認はしていません。手元にあるのは Node.js 24 だけだからです。

スクリプトは起動すると、まず Node.js の版を確かめます。

<<< @/examples/37-cloudshell/src/cli.ts{guard}

AWS を呼ぶ手段には、SDK ではなく AWS CLI を使います。CloudShell に AWS CLI が入っていることはドキュメントに書かれていて、認証情報もそのまま使えるからです。SDK をバンドルに含める方法もありますが、ファイルが大きくなり、読者が実行前に中身を読めなくなります。自分の認証情報で動かすファイルは、読める大きさにしておくほうが安心です。

プロセスを起動するのは、次の関数だけです。

<<< @/examples/37-cloudshell/src/aws-cli.ts{run}

`aws` に渡す引数は、別のファイルの関数が組み立てます。この関数は何も実行しないので、どのコマンドがどの引数になるかをテストで確かめられます。

<<< @/examples/37-cloudshell/src/commands.ts{args}

すべての呼び出しに `--region` を付けています。CloudShell は、開いたときのコンソールのリージョンを `AWS_REGION` に入れるので、付けなければ、この本のスタックがある東京ではないリージョンを見に行くことがあるからです。予算だけは `us-east-1` を指定します。01章で見たとおり、AWS Budgets の API の窓口がそこにあるからです。

## いまの identity とアカウントを確かめる

<!-- section: 37.whoami -->

どのコマンドも、最初に `aws sts get-caller-identity` を呼び、アカウントと呼び出し元を表示します。CloudShell では、この確認が手元よりも大事です。コンソールで複数のアカウントやロールを切り替えていると、開いているシェルがどのアカウントのものかを取り違えやすいからです。

<<< @/examples/37-cloudshell/src/account.ts{caller}

アカウントの照合には、01章の `checkTarget` をそのまま使います。手元では `.env` の `AIH_AWS_ACCOUNT_ID` と比べましたが、CloudShell に `.env` はないので、`--account` で渡します。AWS を変更するコマンドは、`--account` が無ければ実行を断ります。

<<< @/examples/37-cloudshell/src/cli.ts{target}

予算は、`aws budgets describe-budget` の答えから、上限、今期の実績、予測の 3 つを取り出して比べます。

<<< @/examples/37-cloudshell/src/account.ts{budget}

金額は 10 進の文字列で届きます。ここでは上限のどちら側にあるかを知りたいだけなので、数値に直して比べています。請求額の計算には使えません。出力の最後の行は、どの状態でも同じです。01章に書いたとおり、予算は通知を送るだけで、支出を止めません。

## cdkd が記録しているスタックを読む

<!-- section: 37.left -->

消し忘れを調べるには、何がデプロイされているかを知る必要があります。この本のスタックは cdkd が作ったものなので、CloudFormation のスタックの一覧には出てきません。記録があるのは、02章で作った state のバケットです。

固定した版の cdkd は、スタックごとの state を `cdkd-state-<アカウント ID>` というバケットの `cdkd/<スタック名>/<リージョン>/state.json` に置きます。cdkd が無くても、このキーを S3 から読めば、何が記録されているかはわかります。

<<< @/examples/37-cloudshell/src/stacks.ts{keys}

同じプレフィックスには、ロックなどの別のファイルも置かれます。スタックとして数えるのは `state.json` だけです。リージョンが入らない古い形のキーも、固定した版のソースにあるので読めるようにしました。

state には、スタックが持つリソースの種類と ID が入っています。バケットは名前を表示します。`empty` に渡す名前が、ここでわかるからです。そのうえで、これまでの章が「置いてあるだけで料金がかかる」と書いた種類を拾います。

<<< @/examples/37-cloudshell/src/stacks.ts{idle}

この表は料金表ではありません。どの種類を「置いてあるだけで料金がかかる」とみなすかを、章の番号と一緒に書いただけのものです。金額は、表が指している章に書いてあります。表にある種類が、指している章のサンプルで本当に使われていることは、テストで確かめています。表に無い種類のリソースにも、料金がかかるものはあります。

VPC エンドポイントだけは、種類では決まりません。11章で見たとおり、ゲートウェイエンドポイントに時間あたりの料金はなく、インターフェースエンドポイントにはあります。そこで、state に残っているプロパティで見分けます。

出力の最後には、必ず次の 2 行が付きます。

<<< @/examples/37-cloudshell/src/stacks.ts{render}

`left` が読むのは cdkd の記録で、リソースそのものではありません。記録に無ければ、このコマンドには見えません。コンソールで手で作ったものや、cdkd 以外でデプロイしたものがこれに当たります。反対に、手で消したリソースは、記録に残っているかぎり表示され続けます。記録と実物の食い違いを調べるのは、02章のドリフトの検出の仕事で、こちらは手元で実行します。

## destroy の前にバケットを空にする

<!-- section: 37.empty -->

cdkd は、中身のあるバケットを消しません。そのため、これまでの章には `uploads:empty` のような、バケットを空にするタスクがありました。同じことを AWS CLI だけで実行します。

バージョニングが有効なバケットでは、`aws s3 rm --recursive` では空になりません。バージョン ID を指定しない削除は、削除マーカーを足すだけで、それまでのバージョンをすべて残すからです。空にするには、すべてのバージョンと削除マーカーを、バージョン ID を指定して消します。

<<< @/examples/37-cloudshell/src/empty.ts{plan}

S3 の DeleteObjects が 1 回に受け取るキーは 1,000 個までなので、1,000 個ずつに分けます。この章の不変条件は、「1 回のリクエストに 1,000 個を超えるキーを入れず、一覧に出たバージョンと削除マーカーを、どれも 1 回ずつ消す対象にする」です。

cdkd の 2 つのバケットは、名前で断ります。state のバケットはすべてのスタックの記録で、02章では、最後に手で消すものとしていました。スクリプトが機械的に消してよいものではありません。

消す処理は、一覧を取り、見えたものを消し、また最初から一覧を取る、という繰り返しです。

<<< @/examples/37-cloudshell/src/empty.ts{loop}

続きの位置を覚えておかないのは、覚える必要がないからです。消したものは次の一覧に出てこないので、いつも最初から読めば、残っているものだけが見えます。この作りには利点が 2 つあります。途中でセッションが切れても、同じコマンドをもう一度実行すれば、残りから再開できます。一覧を取ったあとに誰かが書き込んだオブジェクトも、次の周で見つかります。

S3 は、一部のキーだけを断ることがあります。権限が足りないキーや、Object Lock で守られたバージョンがそうです。断られたキーがあった周で、スクリプトは止まります。同じキーは次の周でも同じ理由で断られるので、続けても終わらないからです。断られたキーとエラーコードを表示し、終了コード 1 で終わります。

AWS を呼ぶ部分は、この繰り返しとは別のファイルにあります。

<<< @/examples/37-cloudshell/src/aws-cli.ts{bucket}

消すキーの一覧は、引数ではなくファイルで渡します。1,000 個のキーとバージョン ID は、1 つの引数にするには長すぎるからです。`--expected-bucket-owner` には、いまのアカウントの ID を渡します。バケットが別のアカウントのものなら、S3 がリクエストを断ります。打ち間違えた名前が別のアカウントのバケットに当たっても、そこで止まります。

## CloudShell を使える人を決めるポリシー

<!-- section: 37.iam -->

CloudShell を使えるかどうかは、IAM で決まります。CloudShell の操作は `cloudshell:` で始まるアクションになっていて、確認日の時点で 11 個あります。

<<< @/examples/37-cloudshell/src/policy.ts{actions}

コンソールから CloudShell を開くには、このうち 4 つが要ります。1 つでも欠けると、プロンプトのかわりに権限のエラーが出ます。`PutCredentials` は、コンソールの認証情報をシェルに渡すアクションです。これが無くてもシェルは開きますが、認証情報を持たないシェルになり、`aws` コマンドを使うには自分で設定することになります。

AWS が用意している管理ポリシーは `AWSCloudShellFullAccess` で、中身は `cloudshell:*` の許可です。ドキュメントによると、管理者（Administrator）と開発者向けのパワーユーザーの管理ポリシーを持つ identity も CloudShell を開けます。01章の `aih-dev` が何も足さずに CloudShell を使えるのは、このためです。

権限を絞ったロールに CloudShell を使わせるなら、必要なアクションだけを名前で許可します。

<<< @/examples/37-cloudshell/src/policy.ts{documents}

`allowShell` は、ワイルドカードを使いません。AWS がアクションを足しても、許可は広がりません。`cloudshell:*` で許可したロールは、アクションが足されるたびに、何もしなくてもそれを使えるようになります。たとえば `ApproveCommand` は、ほかのサービスのコンソールから CloudShell に送られたコマンドを承認するアクションで、シェルを開くだけなら要りません。

このポリシーが決めるのは、シェルを開けるかどうかだけです。開いたシェルで何ができるかは、そのロールのほかのポリシーが決めます。CloudShell を許可しても、S3 を読む権限が無ければ、シェルの中の `aws s3 ls` は断られます。

反対に、強い権限のロールから CloudShell を取り上げたいときは、`denyShell` を足します。明示的な拒否は、どの許可よりも優先されます。`AdministratorAccess` を持っていても、CloudShell は開けなくなります。組織のすべてのアカウントに同じ制限をかけるなら、[21章](/ja/chapters/21-security.md)で扱った SCP に同じステートメントを書きます。

`denyPublicEnvironments` は、VPC の中の環境だけを許すためのものです。VPC を指定しない環境の作成を拒否するので、出口を絞れない環境は作れなくなります。ただし、ドキュメントによると、すでに作ってある環境には引き続き入れます。入れなくするには、各自が画面から環境を消す必要があります。VPC の環境を作るには、ほかに EC2 の権限（ネットワークインターフェースの作成など）も要ります。その一覧は公式ドキュメントにあり、この章のコードには含めていません。

3 つのポリシーが、どのアクションを通すかは、小さな関数で確かめます。

<<< @/examples/37-cloudshell/src/policy.ts{evaluate}

この関数は、IAM の評価を再現したものではありません。見るのはアクションの名前と 2 種類のワイルドカードだけで、条件の付いたステートメントは無いものとして扱います。確かめられるのは、このファイルが出すポリシーに書き間違いが無いことです。実際のロールで開けるかどうかは、IAM のポリシーシミュレーターか、そのロールでコンソールを開いて確かめます。どちらも、この本では実行していません。

CloudShell の操作は CloudTrail に残ります。環境の作成、セッションの開始、認証情報の受け渡し、ファイルの上げ下ろし用の URL の発行は、それぞれ `createEnvironment`、`createSession`、`putCredentials`、`getFileUploadUrls` と `getFileDownloadUrls` という名前のイベントになります。誰がいつ CloudShell を開いたかは、ここからわかります。一方、シェルの中で打ったコマンドを記録するイベントは、ドキュメントの一覧にありません。シェルから AWS を呼べば、その呼び出しは、ほかの API 呼び出しと同じように CloudTrail の対象になります。しかし、`curl` で外へ送ったデータは、CloudTrail には残りません。
