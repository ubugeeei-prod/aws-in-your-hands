# 63 Agent Sandbox: 実装のつづき

[前のページ](/ja/chapters/63-agent-sandbox/build.md)は、依頼がタスクになり、タスクの中で Claude Code が起動するまでを扱いました。このページは、そのタスクを外側から囲うものを順に扱います。エージェントが持つ IAM のロール、ネットワークの出口、時間と料金の上限、記録、人が中に入る手段です。

## エージェントのロール

<!-- section: 63.role -->

タスクには、ロールが 2 つ付きます。[12章](/ja/chapters/12-containers.md)で見たとおり、実行ロールは ECS と Fargate がイメージを取得してログを書くために使い、タスクロールはコンテナの中のコードが使います。ECS のドキュメントによれば、タスクロールの認証情報は、コンテナの中から決まったアドレスに問い合わせれば取れます。エージェントが実行するどのコマンドも、この認証情報を使えます。タスクロールに付けたものが、そのままエージェントの AWS での権限です。

<<< @/examples/63-agent-sandbox/infra/lib/agent-sandbox-stack.ts{task-role}

ステートメントは 2 つです。固定した推論プロファイルを呼ぶことと、そのプロファイルを経由する場合に限って、後ろにあるモデルを呼ぶことです。[36章](/ja/chapters/36-bedrock.md)と同じ形で、モデルを直接呼ぶことはできません。Claude Code は Bedrock の Invoke API を使うとドキュメントにあるので、アクションは `InvokeModel` と `InvokeModelWithResponseStream` の 2 つです。

ドキュメントの IAM ポリシーの例には、`ListInferenceProfiles` と `GetInferenceProfile` もあります。プロファイルの一覧を調べるためのもので、調べられないときは確認なしで進むと書かれています。この章では付けていません。付けない状態で起動できることは確かめていないので、[検証メモ](/ja/chapters/63-agent-sandbox/wrap.md)に再開の手順を残しました。

ログを書く権限もありません。コンテナの標準出力は、`awslogs` のログドライバーが実行ロールで CloudWatch Logs に書きます。エージェントは、自分の記録に触る権限を持ちません。

不変条件は、このロールについてのものです。**エージェントが中から何をしても、本番のデータとデプロイ用のロールには届かない。** これを、合成したテンプレートを読んで確かめます。そのために、小さなポリシーの評価器を書きました。

<<< @/examples/63-agent-sandbox/src/policy.ts{statements}

評価器は、テンプレートの中から、あるロールに付いたステートメントを集めます。インラインのポリシーと、`AWS::IAM::Policy` のリソースです。読めないものは、黙って飛ばさずに `unread` に入れます。マネージドポリシーはテンプレートの外にあるので中身が読めません。`NotAction` と `NotResource` は扱いません。`unread` が空でないロールは、確かめたことにしません。

ARN は、CDK が書いた組み込み関数のままテンプレートに入っています。

<<< @/examples/63-agent-sandbox/src/policy.ts{render}

`Ref` と `Fn::GetAtt` は、このスタックのリソース 1 つを指す目印の文字列に置き換えます。目印は実在の ARN には一致しないので、「このスタックのテーブルへの許可」が「別のアカウントのテーブルへの許可」に見えることはありません。

問いは 1 つです。

<<< @/examples/63-agent-sandbox/src/policy.ts{can}

この関数が答えるのは、「これらのステートメントで、このアクションが許される可能性があるか」です。条件は評価しません。条件の付いた Allow は許されるものとして数え、条件の付いた Deny は無いものとして扱います。届く側に倒してあるので、「いいえ」は「どのステートメントも届かない」を意味し、「はい」は「届くかもしれない」を意味します。

**これは IAM ではありません。** IAM の実際の判定には、リソースの側のポリシー、アクセス許可の境界、Organizations の SCP、セッションポリシーが加わります（[21章](/ja/chapters/21-security.md)）。評価器が見るのは、このスタックがロールに付けたポリシーだけです。たとえば、同じアカウントの中に、このロールを名指しで許すバケットポリシーがあっても、評価器には見えません。サンドボックスを本番とは別のアカウントに置く理由の 1 つがこれです。Claude Code のドキュメントも、費用の追跡とアクセス制御を簡単にするために、専用の AWS アカウントを作ることを勧めています。

テストは、合成したスタックのタスクロールに、届いてはいけないものを 1 つずつ尋ねます。次のタスクで、同じことを手元で見られます。

```bash
vp run sandbox:policy
```

出力のうち、タスクロールの部分と、最後の問い合わせの部分は次のとおりです（このコマンドの実際の出力から抜き出しました。アカウント ID は、サンドボックスと本番を表す作りものです）。

```text
TaskRole30FC0FBB
  Allow bedrock:InvokeModel, bedrock:InvokeModelWithResponseStream
      on arn:aws:bedrock:ap-northeast-1:111111111111:inference-profile/jp.anthropic.claude-haiku-4-5-20251001-v1:0
  Allow bedrock:InvokeModel, bedrock:InvokeModelWithResponseStream  (with a condition, not evaluated)
      on arn:aws:bedrock:ap-northeast-1::foundation-model/anthropic.claude-haiku-4-5-20251001-v1:0
      on arn:aws:bedrock:ap-northeast-3::foundation-model/anthropic.claude-haiku-4-5-20251001-v1:0

Could the agent's role be allowed to...
  no   sts:AssumeRole on arn:aws:iam::999999999999:role/aih-deploy
  no   dynamodb:GetItem on arn:aws:dynamodb:ap-northeast-1:999999999999:table/notes
  no   s3:GetObject on arn:aws:s3:::aih-attachments/owner/file
  no   secretsmanager:GetSecretValue on arn:aws:secretsmanager:ap-northeast-1:111111111111:secret:aih/agent-sandbox/github-app-AbCdEf
  no   ecs:RunTask on arn:aws:ecs:ap-northeast-1:111111111111:task-definition/any:1
  no   iam:PassRole on arn:aws:iam::111111111111:role/any
```

テストはこれに加えて、タスクロールを引き受けられるのが ECS のタスクだけであること、タスクロールを渡せる（`iam:PassRole`）のがランチャーのロールだけであること、GitHub App の鍵を読めるのがランチャーのロールだけであることを確かめています。ワイルドカードのリソースは、[33章](/ja/chapters/33-production-readiness.md)のルールを workspace の依存として読み込んで数えています。スタック全体で 5 つあり、タスクロールには 1 つもありません。5 つの内訳は、実行ロールの `ecr:GetAuthorizationToken` と、2 つの関数それぞれの `ecs:ListTasks` と `cloudwatch:GetMetricData` です。`ecs:ListTasks` は、クラスターを条件で絞ってあります。

## 出口の許可リスト

<!-- section: 63.egress -->

タスクから届いてよい宛先は 4 つです。

<<< @/examples/63-agent-sandbox/src/egress.ts{allowlist}

モデルの宛先は、Bedrock のランタイムの、東京リージョンのエンドポイントです。推論プロファイルは、リクエストを別のリージョンに回すことがありますが、それは Bedrock の中で起きることで、タスクが話す相手は東京のエンドポイントだけです。GitHub は、Git の通信用と API 用で名前が分かれています。パッケージレジストリは npm のものです。

この一覧に無いものは、届きません。インストールのときに別のホストからバイナリを取得するパッケージは、失敗します。そのリポジトリに必要なホストは、理由を添えて足してください。足すたびに、エージェントが読んだものを送れる先が増えます。Claude Code のドキュメントは、`github.com` のような広いドメインを許すこと自体が、持ち出しの経路になりうると注意しています。GitHub にプッシュできるトークンと GitHub への経路があれば、別のリポジトリに送ることを試みられるからです。トークンをリポジトリ 1 つに限っているのは、このためでもあります。

リストを評価する関数は、この章のものです。

<<< @/examples/63-agent-sandbox/src/egress.ts{allows}

決まりは短くしてあります。ポートは 443 だけ。ホスト名は、完全に一致するか、先頭がドットの項目の配下にあるか。IP アドレスは名前ではないので、一致しません。URL として渡された場合は、`https:` であること、URL に認証情報が入っていないことも確かめます。`https://github.com@evil.example/` の行き先は `evil.example` です。テストには、許可した名前を含むだけの名前（`github.com.evil.example`、`evilgithub.com`）と、別のリージョンの Bedrock、STS、S3 が、どれも断られることが入っています。

同じ一覧を、強制する 2 つの仕組みの形に書き出します。

<<< @/examples/63-agent-sandbox/src/egress.ts{renderings}

1 つは、前のページで見た Claude Code のサンドボックスの設定です。もう 1 つは、AWS Network Firewall のドメインリストのルールです。一覧が 1 つなので、内側の壁と外側の壁が別々のことを言う状態にはなりません。

外側の壁として実際に何を置くかが、この章でいちばん料金に響く判断です。タスクはプライベートサブネットで、パブリック IP アドレスなしで動きます。セキュリティグループは、インバウンドを何も許さず、アウトバウンドは 443 番だけです。

<<< @/examples/63-agent-sandbox/infra/lib/agent-sandbox-stack.ts{network}

セキュリティグループは、ドメインを指定できません。443 番でどのホストに届くかは、サブネットから外への経路で決まります。選択肢と、置いておくだけでかかる月額は次のとおりです（東京、730 時間、データ量に応じた料金は別）。

| 経路 | タスクから届くもの | 月額（USD） |
| --- | --- | --- |
| なし（11章の既定） | S3 のゲートウェイエンドポイントだけ。イメージも取得できない | 0 |
| インターフェースエンドポイント 4 つ | Bedrock のランタイム、ECR、CloudWatch Logs。GitHub とレジストリには届かない | 81.76 |
| NAT Gateway | 443 番で応答するすべてのホスト | 48.91 |
| 自分で動かすプロキシ | プロキシが許したホスト名 | 11.53 と運用の手間 |
| Network Firewall と NAT Gateway | TLS の SNI が一覧にあるホスト | 292.00 |

**経路なし**では、タスクは起動しません。Fargate は、起動のたびに ECR からイメージを取得するからです（[41章](/ja/chapters/41-fargate.md)）。

**インターフェースエンドポイントだけ**の構成は、いちばん堅い出口です。インターネットへの経路そのものがありません。ECR の 2 つと CloudWatch Logs は 11章のスタックのオプション（`-c interfaceEndpoints=ecr.api,ecr.dkr,logs`）で、Bedrock のランタイムは、この章のスタックのフラグ（`-c modelEndpoint=true`、月 USD 20.44）で作ります。ただし、この構成では GitHub にもレジストリにも届きません。リポジトリをクローンしてプッシュするこの章の流れは、そのままでは動きません。リポジトリを S3 経由で受け渡し、プルリクエストを外側で開く仕組みに変えれば成り立ちますが、この章では作っていません。

**NAT Gateway** を置くと（11章の `-c egress=nat`）、この章の流れは動きます。ただし、外側の壁は「443 番ならどこへでも」になります。宛先を絞っているのは、Claude Code のサンドボックスという内側の壁だけです。**この章のスタックを 11章の NAT Gateway と組み合わせただけの状態は、出口の許可リストを外側では強制していません。** 試すだけならこの構成になりますが、そのことは知っておいてください。

**Network Firewall** は、AWS のサービスだけで外側の許可リストを作る方法です。ドキュメントによれば、ドメインリストのルールは、HTTPS では TLS のハンドシェイクの SNI を見て、一覧にない名前への通信を落とします。IP アドレスは見ないので、SNI を偽る通信に備えるには、IP アドレスのルールを別に書くよう書かれています。料金は、エンドポイント 1 つにつき 1 時間 USD 0.395 で、1 か月置くと USD 288.35 です。料金のページによれば、同じ経路に置いた NAT Gateway の時間料金とデータ処理料は、ファイアウォールの料金と同じ量まで免除されます。表の金額は、Elastic IP アドレスの料金を足したものです。ルールの中身は、`vp run sandbox:plan` が出力します。スタックには入れていません。ファイアウォール用のサブネットと、プライベートサブネットからファイアウォールへ向かうルートは、11章のスタックの持ち物だからです。

**プロキシ**は、Claude Code のドキュメントがクラウドでの構成として挙げている方法です。エージェントのコンテナをインターネットゲートウェイのないサブネットに置き、外へ出る通信をすべてプロキシに通し、プロキシがドメインの許可リストを強制して記録を残します。月額は小さなインスタンス 1 つぶんですが、プロキシのソフトウェアを選び、更新し、止まったときに気づく仕事が増えます。ドキュメントは注意点も書いています。HTTPS の通信は、プロキシからは中身の見えないトンネルで、見えるのは宛先の名前だけです。そして、すべてのプログラムが `HTTPS_PROXY` に従うわけではありません。この章では作っていません。

Route 53 Resolver の DNS Firewall は、この表に入れていません。ドキュメントによれば、DNS の問い合わせに出てくる名前で絞るだけで、HTTPS などの通信そのものは見ません。IP アドレスを直接指定した通信は素通りします。

`modelEndpoint` のフラグで作るエンドポイントには、ポリシーを付けています。

<<< @/examples/63-agent-sandbox/infra/lib/agent-sandbox-stack.ts{model-endpoint}

エンドポイントのポリシーは、そのエンドポイントを通る呼び出しを、誰に、どのアクションで、どのリソースについて許すかを決めます。既定はすべて許可です。ここでは、タスクロールが、固定したモデルを呼ぶ場合だけを通します。IAM のロールと同じことを、ネットワークの側でもう一度言っているだけですが、ロールの設定を誰かが広げてしまったときに、このエンドポイントは広がりません。

## 時間と料金の上限

<!-- section: 63.limits -->

上限は、内側と外側の 2 か所にあります。

内側は、前のページで見た Claude Code のフラグです。`--max-turns` と `--max-budget-usd` は、エージェントのプロセス自身が数えて、自分で止まります。タスクの手順も、期限の 2 分前にエージェントのプロセスへ SIGTERM を送ります。ドキュメントによれば、Claude Code は SIGTERM を受けると、動いているコマンドのプロセスを終わらせて、終了コード 143 で終わります。

内側の上限は、守る側と守られる側が同じコンテナの中にあります。だから、外側にも置きます。

<<< @/examples/63-agent-sandbox/src/limits.ts{reap}

リーパーが止めるタスクは 3 種類です。期限を過ぎたもの、1 日の予算を使い切ったあとに動いているもの、そしてランチャーが起動したのではないものです。最後の 1 つは、クラスターに見知らぬタスクがあった場合です。期限を読めないタスクは、期限を守らせることができないので、止めます。

<<< @/examples/63-agent-sandbox/src/reaper.ts{sweep}

リーパーは、EventBridge Scheduler が 1 分ごとに起動します。タスクが期限を超えて動けるのは、長くても 1 分と、停止の猶予の 30 秒です。ECS の StopTask は、コンテナに SIGTERM を送り、30 秒後に SIGKILL を送ります。動いているタスクが 1 つも無いときは、CloudWatch に何も尋ねずに終わります。1 つのタスクが止められなかった場合も、残りのタスクは止めに行き、止められなかったものは関数のエラーとして残します。次の実行が、1 分後にもう一度試します。

料金の上限は、Bedrock が CloudWatch に出すメトリクスから見積もります。

<<< @/examples/63-agent-sandbox/src/aws.ts{tokens}

<<< @/examples/63-agent-sandbox/src/limits.ts{spend}

Bedrock のドキュメントによれば、`AWS/Bedrock` の名前空間に、入力、出力、キャッシュの読み出し、キャッシュの書き込みのトークン数が出ます。メトリクスは、`ModelId` のディメンションが付いたものと、付かないものの両方が出ます。リーパーは付かないほうを合計します。アカウント全体の数字です。サンドボックスのアカウントで Bedrock を使うのがサンドボックスだけなら、それがそのままサンドボックスの使用量になります。単価は、[36章](/ja/chapters/36-bedrock.md)が Price List から記録した値を読み込んでいます。

この見積もりは粗いものです。金額はメトリクスが届くぶんだけ遅れます。遅れの長さは確かめていません。アカウントのすべてのトークンを、固定したモデルの単価で計算します。`InputTokenCount` がキャッシュのトークンを含むのかどうかは、ドキュメントからは分かりませんでした。含むのなら、この計算は多めに出ます。多めに出るぶんには、早く止まるだけです。既定の上限は 1 日 USD 20 で、これを超えると、ランチャーは新しい依頼を断り、リーパーは動いているタスクをすべて止めます。

これとは別に、アカウントに予算を置いてください（[32章](/ja/chapters/32-limits.md)）。ただし、予算の数字は 1 日に数回しか更新されません。暴走したタスクを止める役には立ちません。月の合計が想定を超えたことに気づくためのものです。

タスクの時間のほうは、上限まで動いても小さな金額です。1 vCPU と 4 GB のタスクが 50 分動いて、USD 0.05 ほどです。同時に動けるタスクは 2 つまでにしてあります。エージェントがランチャーを呼べるわけではありませんが、依頼を出す側のスクリプトが暴走した場合の歯止めです。

## 記録

<!-- section: 63.audit -->

何が起きたかは、エージェントが書き換えられない場所に残します。記録は 3 か所に分かれます。

タスクの標準出力は、CloudWatch Logs に入ります。

<<< @/examples/63-agent-sandbox/infra/lib/agent-sandbox-stack.ts{logs}

`--output-format stream-json` を付けた Claude Code は、道具の呼び出しとその結果を、1 行に 1 つずつ標準出力に書きます。実行したコマンドの文字列も、そこに入ります。書き込むのは実行ロールで、タスクロールにはロググループへの権限が何もありません。テストは、タスクロールが `logs:PutLogEvents` も `logs:DeleteLogStream` も許されないことを確かめています。

この記録には限界があります。標準出力に行を書いているのは、エージェントと同じコンテナの中のプロセスです。エージェントは、すでに送られた行を消せませんが、コンテナの中で動いたことのすべてが行になる保証を、外側から与えているわけではありません。

モデルの呼び出しは、CloudTrail に残ります。Bedrock のドキュメントによれば、`InvokeModel` と `InvokeModelWithResponseStream` は管理イベントとして記録されます。ECS のドキュメントによれば、タスクからの呼び出しの `userIdentity` には、引き受けたロールの名前のあとにタスクの ID が付きます。どのタスクが、いつ、どのモデルを呼んだかは、コンテナの中の何にも頼らずに分かります。CloudTrail のイベント履歴は 90 日ぶんです（[21章](/ja/chapters/21-security.md)）。プロンプトと応答の中身は、CloudTrail には入りません。残したいなら、Bedrock のモデル呼び出しのログを有効にします（[36章](/ja/chapters/36-bedrock.md)）。既定では無効です。

ランチャーの判断は、ランチャーのロググループに残ります。断った依頼も、理由と一緒に 1 行になります。依頼の文章そのものは書きません。タスクの起動と停止は、CloudTrail の `RunTask` と `StopTask` に残ります。

Claude Code には、OpenTelemetry で出来事を送る機能もあります。この章では使っていません。送り先のコレクターという部品が 1 つ増えるからです。

## 人が中に入る手段

<!-- section: 63.entry -->

タスクには、外から入る口がありません。セキュリティグループはインバウンドを何も許さず、パブリック IP アドレスも、SSH も、開いたポートもありません。動いているタスクの中を人が見る必要があるときは、ECS Exec を使います。[41章](/ja/chapters/41-fargate.md)で見たとおり、中身は Systems Manager の Session Manager です。

この章のスタックでは、既定で切ってあります。コンテキストで `-c exec=true` を渡したときだけ有効になります。

有効にすると、失うものが 2 つあります。ECS Exec のエージェントはコンテナにファイルを書くので、ルートファイルシステムを読み取り専用にできません。エージェントが自分の設定ファイルを書き換えられないという前提が崩れます。そして、タスクロールに `ssmmessages` の 4 つのアクションが付きます。タスクロールはエージェントが持っているので、エージェントもこの 4 つを持ちます。テストは、フラグを付けたときに増えるのがこの 4 つだけであることを確かめています。

誰が入ったかは、CloudTrail の `ExecuteCommand` のイベントに残ります。入ってから何を打ったかの記録は、ECS Exec がコマンドと出力を CloudWatch Logs か S3 に送る機能で残せます。この章のスタックは、そのための権限をタスクロールに付けていません。付ければ、エージェントがログに書けることになるからです。権限が無いときにセッションの記録がどうなるかは、確かめていません。

したがって、ECS Exec は、調べたいことがあるあいだだけ有効にするものとして扱ってください。調べ終わったら、フラグを外してデプロイし直します。
