# 63 Agent Sandbox: しくみと実装

[概要](/ja/chapters/63-agent-sandbox.md)で、仕事 1 つにつきタスクを 1 つ起動する構成を示しました。このページは、依頼がタスクになるまでを順に追います。ランチャーの判断、リポジトリの受け渡し、タスクの中での Claude Code の起動の 3 つです。エージェントに持たせる権限と出口、上限、記録は[次のページ](/ja/chapters/63-agent-sandbox/more.md)で扱います。

```figure
caption: 依頼 1 つの流れ。認証情報が作られるのは、断る理由がすべて消えたあと
type: sequence
actor launcher: ランチャー
actor github: GitHub
actor task: タスク
actor model: Bedrock
step launcher -> launcher: 検査と上限
step launcher -> github: トークンの発行
step launcher -> task: RunTask
step task -> github: clone
step task -> model: claude -p
step task -> github: push, pull request
note task: 終了。ボリュームは消える
```

## ランチャーの判断

<!-- section: 63.launch -->

依頼の形は、Valibot のスキーマで決めています。知らないキーがあれば、捨てずに断ります。

<<< @/examples/63-agent-sandbox/src/job.ts{request}

`requestId` は、依頼に付ける名前です。同じ ID の依頼が 2 回届いても、起動するタスクは 1 つです。`task` はエージェントに渡す文章で、2000 文字までにしています。この文章は RunTask の上書きとして渡すので、API リファレンスにある「上書きは JSON の記号も含めて全部で 8192 文字まで」という上限に収める必要があるからです。

起動するかどうかは、純粋関数が決めます。AWS も時計も呼びません。

<<< @/examples/63-agent-sandbox/src/job.ts{decide}

断る理由は 5 つあり、どれも外から来た値とスタックの設定を比べるだけです。許可するリポジトリの一覧は、スタックのコンテキスト（`-c repositories=owner/name`）から来ます。既定では空なので、何も設定していないスタックは、どの依頼も断ります。リポジトリ名の比較では、大文字と小文字を区別しません。GitHub がそう扱うからです。

作業用のブランチは `agent/<requestId>` です。依頼で指定できるのはベースのブランチだけで、作業用のブランチの名前は選べません。

通った依頼は、起動の計画になります。計画のうち `startedBy` は、RunTask の同じ名前のパラメーターに入れる値です。

<<< @/examples/63-agent-sandbox/src/job.ts{started-by}

`startedBy` に期限を入れておくのは、リーパーが使うからです。リーパーはタスクの一覧からこの値を読み、期限を過ぎたものを止めます。期限をタグに入れる方法もありますが、起動と同時にタグを付けるには `ecs:TagResource` の権限が要ります。`startedBy` なら要りません。使える文字は英数字、ハイフン、スラッシュ、アンダースコアで、128 文字までです。

ランチャーの本体は、外の世界への問い合わせを、すべて引数で受け取ります。

<<< @/examples/63-agent-sandbox/src/launcher.ts{launch}

順序に意味があります。GitHub にトークンを作らせるのは、断る理由がすべて消えたあとです。断られる依頼のために、認証情報が 1 つ余計に存在する時間を作りません。テストは、断ったすべての場合について、GitHub とも ECS とも話していないことを確かめています。

同じ依頼が 2 回届いた場合の扱いは 2 段になっています。まず、動いているタスクの中に同じ `requestId` のものがあれば、それを返して終わります。2 つの配送がほぼ同時に来て、どちらもタスクを見つけられなかった場合は、RunTask の `clientToken` が受け止めます。ECS は、同じトークンで中身の違う依頼が来ると `ConflictException` を返し、すでに起動したタスクの ARN を教えてくれます。2 回目の依頼はトークンが違うので、中身は必ず違います。ランチャーはこの例外を「起動済み」として返します。

GitHub から返ってきたトークンも、そのまま信じません。

<<< @/examples/63-agent-sandbox/src/github.ts{token}

頼んだのは、リポジトリ 1 つと、権限 2 つ（`contents` と `pull_requests` の書き込み）です。返ってきたトークンがそれより広ければ、タスクを起動しません。期限がタスクの期限より前に来る場合も同じです。GitHub のドキュメントによれば、`repositories` を指定しないトークンは、App がインストールされたすべてのリポジトリに届きます。指定を忘れる間違いは起こりやすいので、応答の側でも確かめています。

## リポジトリの受け渡し

<!-- section: 63.repository -->

リポジトリに触るための認証情報は、GitHub App の installation access token です。ドキュメントによれば、作ってから 1 時間で失効し、発行のときにリポジトリと権限を絞れます。個人のアクセストークンや SSH の鍵と違って、置き忘れても 1 時間後には使えません。

トークンを作るには、App の秘密鍵で署名した JWT が要ります。秘密鍵は長く使う認証情報なので、Secrets Manager に置き、ランチャーだけが読みます。タスクは鍵を見ません。

<<< @/examples/63-agent-sandbox/src/github.ts{jwt}

JWT の中身は、GitHub のページのとおりです。署名は RS256、発行時刻は時計のずれに備えて 60 秒前、期限は 10 分以内です。テストは、その場で作った鍵で署名させ、公開鍵で検証しています。実際の GitHub App は使っていません。

シークレットの形も決めてあります。スタックはこのシークレットを作らず、名前で参照するだけです。

<<< @/examples/63-agent-sandbox/src/github.ts{app-secret}

トークンは、RunTask の環境変数の上書きとしてタスクに渡します。これには弱点があります。ECS の API リファレンスは、秘密の値には Secrets Manager か Parameter Store を使うよう案内しています。RunTask の応答の形を見ると、タスクの情報には上書きした環境変数がそのまま入っています。サンドボックスのアカウントでタスクの情報を見られる人は、トークンも見られることになります。この章がそれでも上書きを使うのは、上書きにはシークレットを参照する欄が無く、仕事ごとのシークレットを作って消す仕組みを足すと部品が増えるからです。見えるのは、リポジトリ 1 つに限った 1 時間のトークンです。CloudTrail の RunTask のイベントに値が残るかどうかは、確かめていません。

タスクの中での手順は、次の関数にまとめてあります。コマンドの実行とネットワークは引数で受け取るので、テストでは偽のものを渡します。

Git に認証情報を渡す部分は、次のとおりです。

<<< @/examples/63-agent-sandbox/src/run.ts{git}

GitHub のドキュメントは、installation token を HTTP のパスワードとして使う方法を示しています。ユーザー名は `x-access-token` です。ドキュメントの例は URL にトークンを書きますが、この章では Git の credential helper から渡します。URL に書くと、プロセスの一覧と `.git/config` に残るからです。helper は環境変数からトークンを読み、その環境変数を渡すのは、クローンとプッシュの 2 つのコマンドだけです。

フックは切ってあります（`core.hooksPath=/dev/null`）。エージェントは作業中に `.git/hooks` にファイルを書けます。プッシュのときにそれが動けば、トークンを持ったプロセスの中で、エージェントの書いたコードが動くことになります。プッシュ先の URL とブランチも、リポジトリの設定から読まずに、コマンドに書いています。

ここで正直に書いておくべきことがあります。これらの工夫は、トークンをエージェントから隠してはいません。エージェントのコマンドは、手順を進めるプログラムと同じユーザーで、同じコンテナの中で動きます。同じユーザーのプロセスの環境は、読もうと思えば読めます。この章の設計は、トークンがエージェントに読まれるものとして成り立つようにしてあります。届くのはリポジトリ 1 つで、1 時間で切れ、送り先は許可リストで絞られています。トークンを本当に渡さない設計は、Claude Code のドキュメントが勧めるプロキシの方式です。エージェントの境界の外にプロキシを置き、認証情報はプロキシがリクエストに足します。

結果は、作業用のブランチとプルリクエストとして出ていきます。

<<< @/examples/63-agent-sandbox/src/github.ts{pull-request}

**既定のブランチへのプッシュを止めるのは、このコードではありません。** `contents` の書き込み権限を持つトークンは、保護されていないブランチならどれにでもプッシュできます。エージェントがトークンを読めば、ベースのブランチにも直接プッシュできます。止めるのは GitHub の側のルールです。リポジトリのルールセットで、既定のブランチに「マージの前にプルリクエストを必須にする」を設定し、承認の数を 1 以上にし、強制プッシュを禁止してください。ルールセットのページによれば、プルリクエストを必須にするだけでは承認は要らないので、承認の数も設定します。エージェントのトークンで付けた承認が数に入らないことは、確かめていません。

エージェントがエラーで終わった場合と、期限に達した場合は、何もプッシュしません。途中までの変更を人に見せる価値はありますが、失敗した実行の結果を、成功した実行と同じ形で出さないことを優先しました。

## Claude Code を起動する

<!-- section: 63.agent -->

タスクの中で Claude Code を動かすコマンドは、次の関数が組み立てます。使っているフラグは、すべて CLI のリファレンスに載っているものです。

<<< @/examples/63-agent-sandbox/src/agent.ts{command}

**`-p`** は、端末の画面なしで 1 回だけ実行する指定です。成功すれば終了コード 0 で終わります。

**`--bare`** は、この章でいちばん大事なフラグです。ドキュメントによれば、`--bare` を付けない `-p` の実行は、プロジェクトの `.claude/settings.json` にあるフックを実行し、`.mcp.json` にあるサーバーに接続します。信頼するかどうかを尋ねる画面は出ません。つまり、クローンしたリポジトリの中身が、エージェントの設定として働きます。`--bare` は、フック、スキル、プラグイン、MCP サーバー、`CLAUDE.md` の自動的な読み込みを止めます。代わりに、リポジトリに置いた `CLAUDE.md` の指示も読まれなくなります。必要な指示は、依頼の文章に書きます。

**`--permission-mode dontAsk`** は、許可を尋ねる場面で、尋ねずに断るモードです。答える人がいない環境のためのものです。権限の確認をすべて飛ばす `bypassPermissions` は使いません。ドキュメントはこのモードを、インターネットに出られない隔離された環境でだけ使うよう書いています。このタスクは、許可リストの範囲でインターネットに出られます。

**`--tools`** は、使える道具そのものを絞ります。シェル、ファイルの読み書き、編集だけにして、Web の取得と検索は外しました。あとで見るように、この 2 つは Claude Code のサンドボックスの外で動くからです。

**`--max-turns`** と **`--max-budget-usd`** は、エージェント自身が数える上限です。`--max-budget-usd` の金額は、ドキュメントによれば、ビルド時に同梱された単価表から手元で計算した見積もりで、請求額とは違うことがあり、上限を少し超えることもあります。これは内側の上限です。外側の上限は[次のページ](/ja/chapters/63-agent-sandbox/more.md)で扱います。

**`--output-format stream-json`** は、出来事を 1 行に 1 つの JSON として標準出力に書かせます。道具の呼び出しとその結果が、タスクのログにそのまま残ります。

設定ファイルは、次の関数の返す値です。

<<< @/examples/63-agent-sandbox/src/agent.ts{settings}

Claude Code のサンドボックスは、シェルのコマンドを OS の仕組みで囲います。Linux では bubblewrap と socat を使い、コマンドのネットワークは、ホスト名を許可リストと照らすプロキシを通ります。この章では、その許可リストを、ネットワークの側で使うものと同じ 1 つのリストから作っています。

設定のうち 3 つは、既定の動きを閉じるためのものです。`failIfUnavailable` が無いと、サンドボックスが起動できないとき、Claude Code はサンドボックスなしでコマンドを実行します。`allowUnsandboxedCommands` を `false` にしないと、サンドボックスの中で失敗したコマンドを、外でやり直す道が残ります。`strictAllowlist` が無いと、リストにないホストは、断られるのではなく許可を尋ねる対象になります。

`enableWeakerNestedSandbox` は、弱める側の設定です。ドキュメントによれば、特権のないコンテナの中では bubblewrap が新しい `/proc` をマウントできないので、この設定でコンテナの `/proc` をそのまま見せます。安全性は下がり、外側のコンテナが境界になっている場合にだけ使うよう書かれています。この章では、外側の境界は Fargate のタスクです。**Fargate の中でこのサンドボックスが実際に起動できるかどうかは、確かめていません。** 起動できなければ、`failIfUnavailable` によって Claude Code は始まらず、タスクは失敗して終わります。黙ってサンドボックスなしで動くことはありません。

ドキュメントは、このサンドボックスの限界も書いています。囲うのはシェルのコマンドだけで、ファイルを読み書きする組み込みの道具は外で動きます。プロキシは TLS の中を見ずに、クライアントが名乗ったホスト名で判断するので、domain fronting のような手口で、リストにないホストへ届く可能性があります。そして、この壁を守っているのは、エージェントと同じコンテナの中のプロセスです。この章がこれを内側の壁と呼ぶ理由です。

設定ファイルは、イメージの中の `/etc/claude-code/managed-settings.json` に置きます。Linux で Claude Code が管理者の設定として読む場所です。タスクのルートファイルシステムは読み取り専用なので、エージェントは自分のルールを書き換えられません。`--bare` を付けた実行がこの場所を読むかどうかはドキュメントで確かめられなかったので、同じファイルを `--settings` でも渡しています。

エージェントのプロセスに渡す環境変数は、残す名前の一覧から作ります。

<<< @/examples/63-agent-sandbox/src/agent.ts{environment}

消す名前の一覧ではなく、残す名前の一覧にしてあるのは、あとから足された環境変数が黙って渡らないようにするためです。Git のトークンは一覧にないので、渡りません。

モデルは Bedrock 経由で呼びます。ドキュメントによれば、`CLAUDE_CODE_USE_BEDROCK=1` を設定した Claude Code は、AWS SDK の既定の認証情報の連鎖を使い、ECS のタスクの認証情報もそこに含まれます。API キーをタスクに置く必要がありません。タスクロールがそのまま、モデルを呼ぶ資格になります。

モデルは `ANTHROPIC_MODEL` で 1 つに固定します。固定しないと、Claude Code は Bedrock での既定のモデルを使います。ドキュメントによれば、それは Opus の系統で、単価が高く、タスクロールが許していないモデルです。既定の設定では、[17章](/ja/chapters/17-ai.md)で確認した Claude Haiku 4.5 の日本向けの推論プロファイルを使います。このモデルは、Bedrock での提供終了が早ければ 2026-10-16 と[36章](/ja/chapters/36-bedrock.md)に記録されています。動かす前に、モデルカードを見てください。別のモデルにするには、17章の確認済みの一覧にプロファイルを足し、`-c model=...` で渡します。
