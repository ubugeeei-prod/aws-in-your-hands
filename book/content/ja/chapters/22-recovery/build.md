# 22 Backup: しくみと実装

[前のページ](/ja/chapters/22-recovery.md)では、テーブルを PITR で過去の時刻に戻しました。このページでは、バケットの画像を戻し、戻したテーブルとバケットの食い違いを見つけて直します。

## 画像はバージョンから戻す

<!-- section: 22.versioning -->

バケットのほうは、全体をある時刻に戻す 1 回の操作では戻しません。使うのはバージョニング（versioning）です。

<<< @/examples/22-recovery/infra/lib/recovery-stack.ts{bucket}

バージョニングを有効にしたバケットでは、2 つの動きが変わります。同じキーに書くと、上書きされずに新しいバージョンが積まれます。バージョンを指定せずに消すと、オブジェクトは消えず、削除マーカー（delete marker）という目印がいちばん新しいバージョンとして置かれます。ふつうに読むと 404 が返りますが、中身は削除マーカーの下に残っています。

戻し方は、キーに何が起きたかで変わります。

- **消されたキー。** 削除マーカーを、そのバージョン ID を指定して消します。下にあったバージョンが、またいちばん上になります
- **上書きされたキー。** 古いバージョンを、同じキーにコピーします。コピーが新しいバージョンとして積まれて、いちばん上になります

上書きされたキーは、新しいほうのバージョンを消しても戻せます。この章がその方法を使わないのは、バージョンの削除が取り消せない操作で、新しいほうが正しかったと後でわかっても戻れないからです。コピーなら何も失いません。

削除マーカーを消すときには注意がいります。バージョン ID を付けずに消そうとすると、S3 は削除マーカーを消さずに、もう 1 つ積みます。戻すための削除には、必ずバージョン ID を付けます。

### どのキーをどう戻すかを決める

バケット全体をある時刻の状態に近づける計画は、キーごとに立てます。計画を立てる関数も、AWS を呼びません。

<<< @/examples/22-recovery/src/object-restore.ts{plan}

指定した時刻より後にできたキーは消さず、名前を挙げてそのまま残します。復元のつもりでデータを消せば、それは 2 つ目の事故になるからです。

計画を実行する側は短く済みます。

<<< @/examples/22-recovery/src/object-restore.ts{apply}

計画は、毎回バケットを読み直して作ります。そのため、途中で止まってからもう一度実行しても、済んだ手順は計画に出てきません。コピーで戻したキーは、いちばん上のバージョンの ETag が戻したいバージョンの ETag と同じになるので、済んでいると判定できます。ETag が同じになるのは、このバケットのように S3 が管理する鍵で暗号化していて、分割しないアップロードで書いた場合です。この条件に当てはまらないバケットでは、この判定は使えません。

S3 からバージョンの一覧を読む部分には、気をつける点が 1 つあります。

<<< @/examples/22-recovery/src/s3-versioned-bucket.ts{list-versions}

`ListObjectVersions` は、中身のあるバージョンと削除マーカーを別々のリストで返すので、両者の前後関係は時刻から組み立て直すしかありません。同じキーの 2 つが同じ時刻を持っていたら、S3 が最新だと示しているほうを上にしています。実物でこの並びが正しく出るかは、確かめていません。

### バージョニングは、ほかの章の前提を変える

07章の「本番にするなら」は、バージョニングを有効にするとライフサイクルルールの動きが変わる、と一言だけ触れていました。変わるのは次の点です。

07章のバケットには、完了していないアップロードを 1 日で消すルールがあります。バージョニングが有効だと、このルールはオブジェクトを消さずに削除マーカーを置き、中身は古いバージョンとして残り続けます。残った中身を実際に消すのは、この章のルールにある `noncurrentVersionExpiration` で、古くなってから 30 日で消します。この 30 日が、画像を戻せる期間です。`noncurrentVersionExpiration` を付けないと、アップロードされたすべてのバイトが永久に保存され、課金されます。

08章のワーカーにも影響があります。バージョニングが有効なバケットでは、ふつうの削除は `ObjectRemoved:DeleteMarkerCreated` というイベントになります。08章のスタックが購読しているのは `ObjectRemoved:Delete` なので、そのままでは削除がワーカーに届きません。07章・08章のバケットでバージョニングを有効にするなら、購読するイベントも直す必要があります。この章のスタックを 08章のスタックに足さず、別のスタックにしたのは、そのためです。

## 2 つの置き場所は、別の時刻に戻る

<!-- section: 22.skew -->

テーブルだけを過去に戻すと、バケットとの間に食い違いが生まれます。画像が後で消されていた場合と、アップロードが後で終わっていた場合を、それぞれ図にしました。

```figure
caption: テーブルだけを T1 に戻してバケットを「いま」のままにすると、何も指していない記録が残る
type: sequence
actor table: table
actor bucket: bucket
note table: T0: 記録 A を書く
note bucket: T0: オブジェクト A を書く
note table: T1: 戻す先の時刻
note table: T2: 記録 A を消す
note bucket: T2: A に削除マーカー
step table -> table: いま: テーブルを T1 に戻す
note bucket: いま: そのまま
note table: 「A には画像がある」
note bucket: 「A は消された」
step table -x bucket: 何も指していない記録
```

```figure
caption: T2 にアップロードが終わっていた場合にテーブルを T1 に戻すと、誰も指していないオブジェクトが残る
type: sequence
actor table: table
actor bucket: bucket
note table: T1: 戻す先の時刻
note bucket: T2: アップロードが終わる
step table -> table: いま: テーブルを T1 に戻す
note table: それについて何も言わない
note bucket: 「バイトはここにある」
step bucket -x table: 誰も指していないオブジェクト
```

テーブルは 1 秒単位で好きな時刻に戻せますが、バケットはキーごとにバージョンを選び直して戻します。2 つを同じ瞬間に揃える仕組みは AWS にないので、揃えるのはあなたの仕事になり、たいていは少しずれます。テーブルだけ戻してバケットを忘れることも、よくあります。

ずれて壊れるのは、07章と 08章が書く順序を工夫して守ってきた約束です。07章は「記録が、オブジェクトより長生きしてはいけない」と決めて、消す順序と作る順序を逆にしました。テーブルだけを過去に戻すと、順序の工夫は役に立ちません。

助かっている点もあります。ノートと添付の記録と検査の記録は同じテーブルに入っているので、この 3 つは同じ時刻に戻り、食い違うのはテーブルとバケットの間だけです。05章がテーブルを 1 つにまとめたことが、復元で役に立っています。

### 約束として検査するもの

検査は、テーブルとバケットを読んで、次のどれかに当たるものを数えます。

<<< @/examples/22-recovery/src/invariants.ts{findings}

見つかるものは 2 種類に分けています。`broken` は、アプリが当てにしていることが成り立っていない状態で、画像のない添付や、別のバイトについての検査結果がこれに当たります。`leftover` は、誰も指していないゴミで、掃除が片付けるはずのものです。切り替えを止めるべきなのは、`broken` があるときだけです。

検査そのものは、読んだ結果だけを見る関数です。

<<< @/examples/22-recovery/src/invariants.ts{check}

`graceMs` は、07章の「完了を待っているアップロード」のための猶予です。動いているサービスでは、置かれたばかりのオブジェクトに記録がないのはふつうのことなので、新しいオブジェクトは数えません。書き込みを止めた状態で検査するなら、待っているアップロードはないので、猶予を 0 にできます。タスクでは `--frozen` を付けます。

読む側にも決めごとが 1 つあります。

<<< @/examples/22-recovery/src/items.ts{classify}

復元したテーブルは、アプリにとって外から来たデータで、半年前の形のアイテムが入っているかもしれません。そこで、すべてのアイテムをスキーマに通してから信じます。読めないアイテムは例外にせず、`unreadable_item` として報告します。1 件読めないだけで検査全体が止まると、残りの状態がわからなくなるからです。

キーの形（`NOTE#...`、`ATTACHMENT#...`、`INSPECTION#...`）は、05章・07章・08章がそれぞれ自分のファイルの中に持っていて、外に出していません。この章は同じ形を書き写し、3 つの章のリポジトリが実際に書くアイテムを読めることを、テストで固定しています。どれかの章がキーの形を変えれば、このテストが落ちます。

### 戻し方ごとに、見つかるもの

| 起きたこと | 見つかるもの |
| --- | --- |
| テーブルとバケットを、同じ時刻に戻した | なし |
| テーブルだけ戻した。その時刻より後に、画像が消されていた | `attachment_without_object`、`inspection_without_object` |
| テーブルだけ戻した。その時刻より後に、アップロードが完了していた | `object_without_record` |
| テーブルだけ戻した。その時刻より後に、画像が上書きされていた | `inspection_for_other_bytes`、`attachment_size_mismatch` |
| 何も戻していない。事故の直後 | なし |

最後の行は当たり前に見えますが、大事です。きれいに消されたデータは整合しているので、検査には何も出ません。検査が見つけるのは食い違いで、間違いではありません。事故に気づくのは、人か、別の監視です。

## 食い違いを直す

<!-- section: 22.repair -->

直すには、どちらが正しいかを決める必要があります。この章は、**テーブルを正として、バケットを合わせます。** テーブルは好きな 1 秒に戻せるので、どの時刻のデータが正しいかという判断を、テーブルの側で表せるからです。

<<< @/examples/22-recovery/src/repair.ts{repair}

見つかったものの種類ごとに、直し方を説明します。

画像のない添付の記録は、バケットのバージョンを見て直します。中身のあるバージョンが残っていれば、その上の削除マーカーを消して画像を戻します。残っていなければ、記録のほうを消します。記録を消した場合は、データを失ったことになります。報告に `record_deleted` と出るので、訓練の記録に書きます。

オブジェクトのない検査の記録は、08章が「残っている穴」として書いた 2 つの経路の結果と同じ形です。削除のイベントが届かなかったか、順序がわからなくて無視されたかで、記録だけが残ります。検査は、復元をしていなくても、この記録を見つけます。直すときは、消す前にオブジェクトをもう一度見ます。同じ実行の中で、1 つ前の手順が画像を戻しているかもしれないからです。

別のバイトについての検査結果は、08章のワーカーの手順 1〜3 を、いま置いてあるバイトに対してやり直して直します。

### イベントのない修復が使う sequencer

08章の記録は、S3 のイベントが持つ sequencer で順序を決めていました。修復にはイベントがないので、sequencer もありません。

<<< @/examples/22-recovery/src/repair.ts{sequencer}

修復は、古い記録の sequencer に 1 を足した値を使います。この値は古い記録には勝ちますが、ほかの何にも勝ちません。同じキーのもっと後のイベントは、必ずこの値以上の sequencer を持っているからです。遅れて届いた本物のイベントは、ふつうに上書きするか、同じバイトについての重複として正しく無視されます。

消すときも同じ値を使います。「この sequencer より古い記録だけを消す」という 08章の条件に渡すと、検査で見た記録だけが消えて、その後に本物のイベントが書いた新しい記録は残ります。

### 何度動かしても、途中で止まっても

修復は、慌てている人が、失敗した後にもう一度実行するものです。そこで、テストは修復を途中で壊しながら書きました。08章と同じやり方で、時計と順序を固定し、止める場所を注入しています。待ち時間には頼っていません。

| 注入すること | 結果 |
| --- | --- |
| ドライランで実行する | 何も変わらない。報告される手順は、本番の実行と同じ |
| 同じ検査結果で、修復を 2 回実行する | 2 回目は、すべて「することがない」。状態は 1 回目の後と同じ |
| 2 つ目の削除マーカーを消すところで失敗させる | 1 つ目だけが戻った状態で止まる。もう一度の検査と修復で、全部戻る |
| 中身のあるバージョンをすべて消してから修復する | 画像は戻らない。記録を消して、そう報告する |
| 検査と修復の間に、新しいアップロードとそのイベントを挟む | 新しい記録は消えない |
| 修復が検査をやり直した後に、本物のイベントを届ける | 本物のイベントの記録が残る |
| オブジェクトの復元を、コピーの 1 回目で失敗させる | 途中の状態で止まる。もう一度の実行で、元の状態に揃う |
| オブジェクトの復元を、成功した後にもう一度実行する | 計画は空 |

コードのほうをわざと 6 か所壊して（コピー済みの判定を外す、オブジェクトを見直さずに検査の記録を消す、古い sequencer のまま書く、新しい記録まで消す、ETag を比べない、version のフェンスを 1 つ手前で止める）、どれもテストが落ちることも確かめました。

### 人に残すもの

修復が手を出さないものが 2 つあります。

1 つは、記録のないオブジェクトです。片付けるのは 07章の掃除ですが、復元の後では掃除が害になります。テーブルを過去に戻すと、その時刻より後に完了したアップロードは、すべて記録のないオブジェクトになります。08章の掃除は 1 時間ごとに動いて、猶予を過ぎた記録のないオブジェクトを消します。つまり、**テーブルを戻して 1 時間ほど放っておくと、復元で記録を失った画像を、掃除が消し始めます。** 手元のテストでは、07章の掃除のコードをそのまま使って、この動きを再現しました。バージョニングが有効なら、消されてもバージョンから戻せます。有効でなければ戻せません。切り替える前に、掃除のスケジュールを止めてください。

もう 1 つは、記録と大きさの合わない画像です。上書きされたのか、記録のほうが古いのかを、修復は決められません。バケットを同じ時刻に戻せば解消します。戻せないなら、添付を消すかそのままにするかを、人が決めます。

## 巻き戻った version 番号

<!-- section: 22.versions -->

テーブルを戻すと、05章の約束にも穴が開きます。この穴は、検査では見つかりません。

05章の楽観的ロックは、ノートの version の番号を比べていました。「私が見たのは version 3 で、いまも 3 なら、4 にして保存する」という比べ方です。番号は増える一方なので、同じ番号は同じ内容を指す、というのが前提でした。

復元は、その番号を巻き戻します。

1. ノートが version 3 まで編集される。誰かのブラウザが、version 3 を表示したまま開いている
2. テーブルを、version 1 だった時刻に戻して、切り替える
3. 別の人が、戻ったノートを 2 回編集する。version は 2、そして 3 になる
4. 開いたままだったブラウザが、「version 3 から」の保存を送る

4 の保存は、番号が合っているので通ります。しかし、復元の後の version 3 は、ブラウザが見ていた version 3 とは別の内容です。ブラウザは、見たこともない編集を上書きします。テストでは、この順序をそのまま再現しています。

直すには、戻したテーブルの番号を、元のテーブルが配った番号より先に進めておきます。

<<< @/examples/22-recovery/src/table-diff.ts{fence}

元のテーブルで version 3 だったノートは、戻したテーブルで version 4 にします。古いブラウザの「3 から」は、もう通りません。DynamoDB への書き込みには、条件を付けています。

<<< @/examples/22-recovery/src/dynamodb-table.ts{raise-version}

番号は上げるだけで、下げません。2 回実行しても、フェンスの後に誰かが編集していても、何も壊しません。

ただし、この方法で塞げるのは半分だけです。事故で**消された**ノートは元のテーブルに残っていないので、番号がどこまで進んでいたかがわかりません。きちんと塞ぐには、version の比較に「何回目の復元の後か」を混ぜます。この章では実装していません。

### 切り替えで失うものを、先に数える

フェンスの材料は、元のテーブルと戻したテーブルの差分です。同じ差分から、切り替えで何を失うかもわかります。

<<< @/examples/22-recovery/src/table-diff.ts{diff}

`returning` は戻ってくるノートで、復元の目的です。`lost` は復元の時刻より後に作られたノートで、切り替えると見えなくなります。`rolledBack` は、巻き戻る編集です。

**失ったデータにあたるのは、`lost` と `rolledBack` です。** 訓練の記録に書く数は、この 2 つから取ります。事故の 5 分前に戻せば、その 5 分間に書かれたものは、切り替えた先にはありません。元のテーブルには残っているので、拾って書き戻すことはできますが、そのための道具はこの章にはありません。
