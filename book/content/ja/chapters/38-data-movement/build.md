# 38 Data Movement: しくみと実装

[前のページ](/ja/chapters/38-data-movement.md)では、運ぶ手段を見比べて、添付のアーカイブには DataSync を使うと決めました。このページでは、DataSync の部品と設定を順に見て、スタックを組み立て、タスクが何をコピーして何を消すのかを手元のモデルで確かめます。

## DataSync の部品

<!-- section: 38.datasync -->

DataSync のことばは 4 つです。

- **エージェント（agent）。** 自分のネットワークに置く仮想マシンです。オンプレミスの NFS や SMB のストレージを相手にするときに要ります。この章では使いません
- **ロケーション（location）。** コピーの元か先になる置き場所の登録です。S3 なら、バケットと、DataSync がそのバケットに届くためのロールの組です
- **タスク（task）。** ソースのロケーション、デスティネーションのロケーション、コピーのしかたの設定、スケジュールをまとめたものです。12章の ECS のタスクとは関係がありません
- **タスク実行（task execution）。** タスクを 1 回動かしたものです。`QUEUED`、`LAUNCHING`、`LAUNCHED`、`PREPARING`、`TRANSFERRING`、`VERIFYING` と進み、`SUCCESS` か `ERROR` で終わります

エージェントが要るかどうかは、相手で決まります。ドキュメントの表から、この章に関係する行を抜き出すと、次のようになります。S3 から S3 は、同じアカウントでも別のアカウントでも、エージェントは要りません。ほかのクラウドのオブジェクトストレージから S3 は、次に説明する Enhanced モードならエージェントなしで動き、Basic モードではエージェントが要ります。NFS と SMB は、どちらのモードでもエージェントが要ります。

### Basic モードと Enhanced モード

タスクには 2 つのモードがあり、作ったあとでは変えられません。

Enhanced モードは、一覧、準備、転送、検証を並行して進めます。1 回の実行で扱えるオブジェクトの数は「事実上、無制限」とされ、ログは JSON の形で出ます。Basic モードは、準備、転送、検証を順に進めます。1 回の実行で扱える数にはクォータがあり、AWS のストレージどうしでは、ファイルとオブジェクトとディレクトリを合わせて 2,500 万です。S3 のプレフィックスもディレクトリとして数えられます。

ドキュメントは、S3 どうしのコピーには Enhanced モードを勧めています。それでも、この章は Basic モードを選びました。

<<< @/examples/38-data-movement/src/task.ts{archive-task}

理由は料金です。AWS Price List によると、大阪リージョンの Basic モードは、コピーした 1 GB あたり USD 0.0125 です。Enhanced モードは 1 GB あたり USD 0.015 で、これに実行 1 回あたり USD 0.55 が加わります。毎日 1 回動かすと、実行料だけで月に USD 16.50 になります。ノートアプリの添付は、数も量も、Basic モードのクォータからは遠いところにあります。

Enhanced モードに替えるのは、オブジェクトとプレフィックスの合計が 2,500 万に近づいたとき、大きなオブジェクトの転送に時間がかかりすぎるとき、ほかのクラウドからエージェントなしで運びたいときです。モードはタスクを作り直さないと変わりません。CloudFormation のリファレンスでも、`TaskMode` の変更はリソースの置き換えになると書かれています。

クォータの数字は、2026-10-13 に DataSync のクォータのページで読んだものです。同じページから、あと 4 つ挙げておきます。1 つのアカウントとリージョンに作れるタスクは 100 個で、引き上げを申請できます。1 つのタスクのフィルターは、合わせて 102,400 文字までです。1 つのタスクに積める実行待ちは 50 個です。実行の履歴は 30 日で消えます。いまの値は、Service Quotas のコンソールで AWS DataSync を選ぶと見られます。

## タスクの設定

<!-- section: 38.task -->

コピーのしかたは、タスクのオプションで決めます。この章が使うものを、型にしました。

<<< @/examples/38-data-movement/src/task.ts{options}

`TransferMode` は、何をコピーの対象にするかを決めます。`CHANGED` は、最初に全部をコピーしたあとは、ソースとデスティネーションで違っているデータとメタデータだけをコピーします。`ALL` は、デスティネーションを見ずに、ソースにあるものを毎回すべてコピーします。

`OverwriteMode` は、デスティネーションにすでにあるオブジェクトの扱いです。既定の `ALWAYS` は、ソースの中身かメタデータが変わっていれば上書きします。`NEVER` は、ソースが変わっていても上書きしません。ドキュメントは `NEVER` を、デスティネーション側で加えた変更を上書きから守るための設定だと説明しています。

`PreserveDeletedFiles` は、ソースから消えたものの扱いです。既定の `PRESERVE` は、デスティネーションに残します。`REMOVE` は、ソースにないものをデスティネーションから消します。

組み合わせられない設定があります。`ALL` は、デスティネーションを調べないので、何を消せばよいかがわかりません。ドキュメントは、`ALL` と `REMOVE` を一緒には設定できないと書いています。こういう組み合わせは、デプロイの前に手元で断ります。

### 検証

DataSync は、転送のあいだ、必ずチェックサムで中身を確かめます。`VerifyMode` で決めるのは、転送が終わったあとに追加で行う検証です。

- `ONLY_FILES_TRANSFERRED` は、コピーしたデータについて、ソースで計算したチェックサムと、デスティネーションで計算したチェックサムを比べます。ドキュメントが勧めている設定です
- `POINT_IN_TIME_CONSISTENT` は、転送の最後に、ソースとデスティネーションの全体を調べて、2 つが揃っているかを確かめます。Basic モードの既定で、Enhanced モードでは使えません
- `NONE` は、追加の検証をしません

この章は `ONLY_FILES_TRANSFERRED` を明示しています。ソースは動いているアプリのバケットで、実行の最中にもアップロードが届きます。全体を比べる検証は、その 1 枚が届いただけで「2 つは揃っていない」と判定するはずです。手元のモデルでは、そのとおり `ERROR` になりました。実物でどうなるかは確かめていません。

### メタデータ、タグ、ストレージクラス、バージョン

ドキュメントによると、S3 とオブジェクトストレージのあいだでは、ユーザーが定義したメタデータ、オブジェクトのタグ、そして `Content-Type`、`Content-Disposition`、`Content-Encoding`、`Content-Language` がコピーされます。ACL、過去のバージョン、`Last-Modified` はコピーされません。アーカイブにあるオブジェクトの更新時刻は、コピーされた時刻になります。

タグのコピーは `ObjectTags` で決まり、既定の `PRESERVE` のままにしています。07章のアップロードは、完了するまで `pending` のタグが付いています。実行がその瞬間に当たると、タグも一緒にアーカイブへ運ばれます。完了してタグが外れたあと、DataSync がその変化を「違い」と判定してコピーし直すのかは、ドキュメントからは読み取れませんでした。

ストレージクラスは、デスティネーションのロケーションで決めます。新しいオブジェクトは、ロケーションに指定したクラスで書かれます。すでにあるオブジェクトのクラスは、`TransferMode` が `ALL` でない限り、そのままです。この章は S3 Standard にしました。Standard-IA や Glacier Instant Retrieval を指定した場合、ドキュメントによると、128 KB より小さいオブジェクトは指定したクラスではなく S3 Standard に書かれます。この 2 つのクラスでは、上書き、削除、取り出しに追加の料金がかかることがあるとも書かれています。添付の多くは小さな画像なので、クラスを変えても、思ったほどは安くなりません。Glacier Flexible Retrieval と Deep Archive のオブジェクトは、ソースにある場合、先に復元しないと DataSync は読めません。

バージョニングについては、3 つのことが書かれています。ソースからコピーされるのは、各オブジェクトの最新のバージョンだけです。デスティネーションでバージョニングが有効なら、ソースで変わったオブジェクトは新しいバージョンとして書かれます。バージョン ID は、ソースとデスティネーションで別のものになります。

### 削除

アーカイブのバケットは、バージョニングを有効にしました。

<<< @/examples/38-data-movement/infra/lib/archive-stack.ts{archive-bucket}

DataSync は、変わったオブジェクトをその場で上書きします。アプリが壊れた画像で添付を上書きすれば、次の実行で、その壊れた画像がアーカイブにも届きます。22章で書いたとおり、写しを 2 つ持つことと、過去の状態を取っておくことは別の仕事です。アーカイブの古いバージョンを 30 日残すのは、後者のためです。

既定の `PRESERVE` では、ソースで消えた添付はアーカイブに残り続けます。事故で消したものが残るのは助かりますが、利用者が自分の意思で消したデータも残ります。消したものを消えたままにする約束があるアプリでは、`-c deletes=remove` で `REMOVE` に切り替えます。`REMOVE` にした場合、バージョニングが有効なバケットでは、バージョン ID を指定しない削除は削除マーカーを置くだけで、中身は古いバージョンとして 30 日残ります。DataSync のロールには、バージョンを指定して消すための `s3:DeleteObjectVersion` を与えていません。ただし、DataSync の削除が実際に削除マーカーになることは、実物では確かめていません。

### フィルターとマニフェスト

コピーの範囲を絞る方法は 2 つあります。

フィルターは、パターンを `|` でつないだ文字列です。パターンはロケーションのパスからの相対で、大文字と小文字を区別します。`/dir` と `/dir/` は同じ意味で、フォルダーとその中身に一致します。S3 では、キーの中の `/` がフォルダーの区切りとして扱われます。ワイルドカードは `*` で、include フィルターでは、パターンの最後の 1 文字としてしか使えません。`/u/alice*` は書けますが、`*.png` は書けません。exclude フィルターには、その制約がありません。

マニフェストは、コピーするファイルやオブジェクトを 1 つずつ並べた CSV です。S3 がソースなら、バージョン ID も指定できます。フィルターとは一緒に使えません。マニフェストを使う実行は、デスティネーションから何も消しません。

この章のタスクは、既定ではどちらも使いません。`-c excludes='<フィルター>'` を付けると、exclude フィルターが入ります。

### スケジュール

タスクは、cron 式か rate 式のスケジュールを自分で持てます。間隔は 1 時間より短くできません。時刻は UTC です。この章は `cron(0 18 * * ? *)`、日本時間の午前 3 時にしました。

<<< @/examples/38-data-movement/infra/lib/archive-stack.ts{task}

オプションのキーの名前は、DataSync の API と CDK で同じなので、計画のモデルが読むオブジェクトを、そのままタスクに渡しています。最初の実装では、キーを CloudFormation の綴り（`TransferMode`）に変換してから渡していました。CDK は知らないキーを黙って捨てるので、できあがったテンプレートの `Options` は空でした。スタックのテストが、この誤りを見つけました。

ドキュメントには、同じエラーで失敗が続くと、DataSync がスケジュールを自分で無効にすることがある、とも書かれています。無効にされたスケジュールは、静かです。この話は、このページの最後でもう一度扱います。

### 別のアカウントのバケットへ

アーカイブを別のアカウントに置きたいこともあります。事故や侵害がアカウントごと及んだときに、写しが同じアカウントにあっては意味がないからです。DataSync のチュートリアルは、次の形を示しています。

- DataSync のロール、2 つのロケーション、タスクは、すべてソース側のアカウントに作ります
- デスティネーション側のアカウントは、バケットを持ち、バケットポリシーで、ソース側のロールに 10 個のアクションを許可します

## 計画を手元で読む

タスクを実行する前に、何がコピーされ、何が飛ばされ、何が消されるのかを知りたくなります。DataSync には、実行せずに計画だけを見る方法が見当たりませんでした。そこで、ドキュメントの記述から、計画を立てる関数を書きました。

入力は、両側の一覧です。

「違う」の判定には、大きさと、中身のハッシュを使います。DataSync が S3 のオブジェクトの違いを何で判定しているのかは、ドキュメントからは読み取れませんでした。S3 の ETag は使えそうに見えますが、S3 の API リファレンスによると、マルチパートアップロードで書かれたオブジェクトの ETag は、中身の MD5 ではありません。DataSync は大きなオブジェクトをマルチパートで書くので、実物の一覧の ETag をこの関数の `checksum` に入れると、同じ中身のオブジェクトが「違う」と判定されることがあります。

`NEVER` にすれば、その書き込みは守られます。その代わり、ソースで添付が差し替えられても、アーカイブには届かなくなります。テストは両方を固定しています。アーカイブには誰も直接書かない、と決めるほうが単純です。

モデルを作るときに、ドキュメントに書かれていなくて、著者が決めたことが 3 つあります。

- ワイルドカードは `/` をまたぎます。ドキュメントの例に、どの深さのフォルダーにも一致する `*/folder-to-exclude` があるので、そう読みました

## 途中で変わるソース

<!-- section: 38.execution -->

計画は、ある瞬間の一覧から作られます。実行はそのあと何分も、ときには何時間も続き、そのあいだもアプリはバケットに書き続けます。この食い違いを見るために、メモリ上のバケットを 2 つ用意して、実行を段階ごとに進めるモデルを書きました。

<<< @/examples/38-data-movement/src/memory-bucket.ts{memory-bucket}

バケットには、S3 と同じ性質を 1 つだけ持たせています。書き込みは、オブジェクトを丸ごと置き換えます。読む側に見えるのは、古い中身か新しい中身のどちらかで、混ざったものは見えません。

<<< @/examples/38-data-movement/src/execution.ts{run}

実行は、最初に両側を一覧し、そのあとは一覧を見直しません。ただし、オブジェクトを読むのは、その順番が来たときです。テストは、段階のあいだにソースを書き換えて、何が起きるかを固定しています。

- **コピーされたあとに差し替えられた添付は、古いままアーカイブに残ります。** 実行は `SUCCESS` で終わります。コピーしたものだけを検証するので、差し替えに気づきません。次の実行が、その 1 つを運びます
- **一覧のあと、順番が来る前に差し替えられた添付は、新しい中身で届きます。** 次の実行は何もしません
- **一覧のあとにアップロードされた添付は、その実行では運ばれません。** 次の実行まで待ちます
- **一覧のあとに消された添付は、コピーされません。** モデルでは、これを失敗にしていません。実物がどう報告するかは確かめていません
- **途中で止まった実行のあと、アーカイブにあるのは、ソースの一部です。** 1 つ 1 つのオブジェクトは完全です。次の実行は、残りだけを運びます。5 個のオブジェクトに対して、2 回の実行を合わせた書き込みは 5 回でした

最後の項目が、再実行しても安全だという性質です。`TransferMode` が `CHANGED` なら、実行は「いま足りないもの」を計算し直すので、何回動かしても、同じところに落ち着きます。`ALL` にすると、同じ 5 個に対する 2 回の実行で、書き込みは 10 回になります。

検証のモデルは、2 つの設定を分けて書いています。

<<< @/examples/38-data-movement/src/execution.ts{verify}

全体を比べる検証では、実行中に差し替えとアップロードが 1 つずつあっただけで、結果が `ERROR` になります。Basic モードの既定はこちらなので、何も指定せずに動いているバケットを毎晩コピーすると、毎晩失敗の通知が届くことになります。繰り返しますが、これはモデルの結果です。実物の DataSync が同じ判定をするかは、確かめていません。

## 終わった実行を知る

<!-- section: 38.events -->

実行の結果を知る手段は、3 つあります。

**CloudWatch Logs。** Basic モードのタスクは、`CloudWatchLogGroupArn` で指定したロググループにログを書きます。書き込みの許可はロールではなく、CloudWatch Logs のリソースポリシーで与えます。

<<< @/examples/38-data-movement/infra/lib/archive-stack.ts{copy-logs}

ドキュメントの例は、リソースをアカウントのすべてのロググループにしています。ここでは、このスタックのロググループ 1 つに絞りました。`LogLevel` は `BASIC` で、転送のエラーだけが書かれます。`TRANSFER` にすると、コピーしたオブジェクトが 1 つずつ書かれ、そのぶんログの料金が増えます。Enhanced モードのタスクは事情が違い、`/aws/datasync` という名前のロググループに自動で書きます。そのロググループは、DataSync がサービスリンクロールを使って作ります。

**タスクレポート。** 実行ごとに、何をコピーし、飛ばし、検証し、消したかを JSON にして、指定した S3 のバケットに書き出す機能です。要約だけにも、オブジェクトごとの一覧にもできます。この章のスタックでは設定していません。

**EventBridge のイベント。** DataSync は、タスク実行の状態が変わるたびに、EventBridge にイベントを送ります。配送はベストエフォートだと、ドキュメントに書かれています。

イベントの形は、DataSync のユーザーガイドにも、EventBridge のイベントリファレンスにも載っていませんでした。見つけられたのは、AWS のナレッジセンターの記事にある見本 1 つです。その見本から読み取れるのは、`source` が `aws.datasync` であること、`detail-type` が `DataSync Task Execution State Change` であること、`resources` にタスク実行の ARN が 1 つ入ること、`detail.State` に状態が入ることです。スキーマは、その範囲だけを書きました。

<<< @/examples/38-data-movement/src/execution-event.ts{schema}

`detail.State` の値として確かめられた綴りは、`SUCCESS` と `ERROR` だけです。ほかの状態がどんな綴りで届くのかは、わかりません。そこで、スキーマは文字列なら何でも受け取り、判断のほうで 2 つだけを拾います。

<<< @/examples/38-data-movement/src/execution-event.ts{decide}

人に知らせるのは、2 つの場合です。1 つは、アーカイブのタスクの実行が `ERROR` で終わったときです。もう 1 つは、ルールに一致したのに読めないイベントが届いたときです。イベントの形は見本 1 つから書いたので、実物が違っていることは十分にありえます。そのとき、関数が黙って捨てると、失敗の通知が届かない夜と、何も起きなかった夜の区別がつきません。読めないことを知らせておけば、最初の実行でわかります。

同じアカウントのほかのタスクの失敗は、無視します。ルールの側でも、ARN の先頭で絞っています。

<<< @/examples/38-data-movement/infra/lib/archive-stack.ts{alert}

関数の本体は短く、判断と通知を分けてあります。

<<< @/examples/38-data-movement/src/alert.ts{handle}

通知の送信に失敗したら、関数は失敗します。EventBridge のルールは関数を非同期で呼び出し、関数がエラーを返した呼び出しは、Lambda が既定であと 2 回やり直します。テストは、通知が失敗したときに例外がそのまま外に出ることを固定しています。

### 届かない通知

この仕組みには、穴があります。知らせるのは「失敗した」ことで、「成功していない」ことではありません。イベントの配送はベストエフォートなので、`ERROR` のイベントが届かないことがありえます。スケジュールが DataSync に無効にされれば、実行そのものが始まらず、イベントは 1 つも出ません。どちらの場合も、アーカイブは静かに古くなっていきます。

アーカイブがどれだけ古くてよいかは、スケジュールから数字にできます。

<<< @/examples/38-data-movement/src/lag.ts{lag}

毎日 1 回、実行に 2 時間まで、1 回の失敗は翌日の実行に任せる、と決めると、上限は 50 時間になります。最後の `SUCCESS` がそれより前なら、アーカイブは約束より古くなっています。この関数はテストしてありますが、スタックにはつないでいません。つなぐには、最後に成功した時刻をどこかに書き、別のスケジュールでそれを読む部品が要ります。[19章](/ja/chapters/19-observability.md)のアラームに「データが来ないこと」を見張らせる形にするのが、素直な作り方です。
