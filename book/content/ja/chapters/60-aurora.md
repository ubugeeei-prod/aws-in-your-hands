# 60 Aurora: storage と compute が分かれた PostgreSQL

Aurora は、データを置くストレージと、SQL を実行するインスタンスを、別々の部品にした PostgreSQL です。データは 3 つの AZ に複製された 1 つのボリュームに入っていて、インスタンスはそのボリュームを読み書きする計算機にすぎません。フェイルオーバーが速いことも、読み取り用のインスタンスをすぐ足せることも、使っていないあいだ計算機を 0 まで縮められることも、この分け方から出てきます。

その代わり、インスタンスが入れ替わる瞬間は、アプリの側が引き受けます。接続は切れ、実行中だったトランザクションの結果は、アプリにはわからなくなります。この章は、Aurora のしくみを順に見たうえで、そのときにデータを壊さない書き方を作ります。守る不変条件は、フェイルオーバーで中断されたトランザクションは、コミットされたか、丸ごとやり直されるかのどちらかで、半分だけ適用されることも、2 回適用されることもない、というものです。

[13章](/ja/chapters/13-sql.md)は、ノートの API のデータベースに Aurora DSQL を選び、Aurora は表で比べるだけにしました。この章はその続きで、13章のスキーマとマイグレーション、PGlite のテストをそのまま使います。パラメーターグループ、保守、バックアップ、RDS Proxy、IAM 認証のように RDS と Aurora で共通する部分は [59章](/ja/chapters/59-rds.md)が扱うので、ここでは繰り返しません。ネットワークは [11章](/ja/chapters/11-network.md)の VPC を使います。コードは `examples/60-aurora/` にあります。

料金を先に書いておきます。**この章のスタックは、置いてあるだけで料金がかかります。** 接続が 5 分なければインスタンスが止まる設定にしてあり、1 か月ずっと止まっていれば、1 GB のストレージとシークレット 1 つで月 USD 0.52 です。止まらなかった場合、たとえば接続を 1 本開いたままにした場合は、上限の 1 ACU が 730 時間続いて月 USD **110.02** になります。金額は東京リージョンの定価で、内訳は[費用のページ](/ja/chapters/60-aurora/wrap.md)にあります。11章の VPC の料金は別です。使い終わったら `vp run aurora:infra:destroy` で消してください。

## 全体像

<!-- section: 60.architecture -->

```figure

node app: アプリ
node cep: クラスターエンドポイント | いまの writer を指す DNS 名
node rep: reader エンドポイント | reader のどれかを指す DNS 名
node writer: writer | 書き込みを受ける 1 台
node reader: reader | 0〜15 台、読み取り専用
node volume: クラスターボリューム | 3 つの AZ に 6 つの複製
edge app -> cep: 読み書き
edge app -> rep: 読み取りだけ
edge cep -> writer
edge rep -> reader
edge writer -> volume: 同期で書く
edge reader -> volume: 同じボリュームを読む
group cluster: Aurora DB クラスター = cep, rep, writer, reader, volume

```

RDS for PostgreSQL のインスタンスは、自分のディスクを持っています。レプリカを足すと、プライマリのデータがレプリカのディスクへ流れていき、インスタンスの数だけデータの写しができます。

Aurora では、データはクラスターボリューム（cluster volume）という 1 つの仮想ボリュームにあります。writer が書くと、Aurora はそのデータを 3 つの AZ にある 6 つのストレージノードへ同期で複製します。この複製はインスタンスの数と無関係で、インスタンスが 1 台でも、6 つの複製は作られます。

インスタンスには 2 つの役割があります。writer は書き込みを受ける 1 台で、reader は同じボリュームを読む読み取り専用のインスタンスです。reader は 15 台まで足せます。reader を足してもデータは複製されないので、足すのは速く、ストレージの料金も増えません。ただし、reader がメモリーに持っているページは、writer に非同期で追いつきます。reader の遅れを表す `ReplicaLag` は、Aurora PostgreSQL では、reader のページキャッシュが writer のものからどれだけ遅れているかを示す値です。

クラスターという名前が指すのは、ボリュームと、次の節のエンドポイントです。クラスター自体は計算機を持ちません。CDK で書くと、この区別がそのまま 2 種類のリソースになります。

```figure
caption: この章のスタック。クラスターとインスタンスはプライベートサブネットにあり、手元からは Data API を通して SQL を送る
node laptop: 手元のマシン | vp run aurora:db:schema, aurora:smoke
node dataapi: RDS Data API | HTTPS, IAM で認可
node secret: Secrets Manager | Aurora が作って回すパスワード
node cluster: DBCluster | Aurora PostgreSQL, 0〜1 ACU
node writer: DBInstance | db.serverless, writer
node sg: セキュリティグループ | インバウンドのルールなし
edge laptop -> dataapi: SQL とパラメーター
edge dataapi -> secret: 認証情報を読む
edge dataapi -> writer: SQL を実行
edge cluster -> writer: 容量の範囲を決める
group vpc: 11章の VPC のプライベートサブネット = cluster, writer, sg
group stack: AihAurora = cluster, writer, sg, secret
mark cluster
```

この章が作るのは、最小の構成です。インスタンスは writer の 1 台だけで、Aurora Serverless v2 の容量を 0 から 1 ACU の範囲にしてあります。クラスターはプライベートサブネットにあり、セキュリティグループはどこからの接続も通しません。手元からは、HTTPS で SQL を送る RDS Data API を使います。Data API と Serverless v2 は[しくみと実装](/ja/chapters/60-aurora/build.md)のページで説明します。

インスタンスが 1 台でも、データは 3 つの AZ にあります。ただし、動いている計算機は 1 つの AZ にしかありません。この違いが、次の 2 つの節の中身です。

## エンドポイント

<!-- section: 60.endpoints -->

インスタンスは入れ替わるので、アプリはインスタンスの名前ではなく、役割を指す DNS 名につなぎます。この名前をエンドポイントと呼びます。

| エンドポイント | 指す先 | 使う場面 |
| --- | --- | --- |
| クラスターエンドポイント | いまの writer | 書き込みと、書いた直後の読み取り |
| reader エンドポイント | reader のどれか | 少し古くてもよい読み取り |
| カスタムエンドポイント | 自分で選んだインスタンスの組。クラスターごとに 5 つまで | 集計用の大きい reader だけに流す、など |
| インスタンスエンドポイント | 特定の 1 台 | 調査のとき。フェイルオーバーしても付け替わらない |

reader エンドポイントが振り分けるのは接続で、クエリではありません。1 本の接続を張りっぱなしにすると、その接続のクエリはすべて同じ reader に行きます。reader が 1 台もないクラスターでは、reader エンドポイントは writer を指し、書き込みも通ります。この章のスタックがそうです。

reader で読むと、自分が直前に書いたものがまだ見えないことがあります。reader は writer に非同期で追いつくからです。書いた本人にすぐ見せる読み取りはクラスターエンドポイントへ送る、という振り分けは 59章のリードレプリカと同じ考え方なので、そちらに任せます。

エンドポイントは DNS 名なので、指す先が変わっても、名前を引き直すまでクライアントは気づきません。AWS のドキュメントは、フェイルオーバーで writer が替わるとクラスターエンドポイントの IP アドレスが変わること、接続プールを使うなら DNS のキャッシュを捨てるか、有効期間を短くする用意をしておくことを書いています。そうしないと、もう使えないインスタンスや、読み取り専用になったインスタンスに、読み書きの接続を張ろうとするからです。エンドポイントの DNS レコードの更新は、ふつう 30 秒以内に終わるとされています。

## フェイルオーバーとアプリの仕事

<!-- section: 60.failover -->

writer が動かなくなると、Aurora は新しい writer を用意します。やり方は、reader がいるかどうかで変わります。

- reader がいれば、そのうちの 1 台を writer に昇格させます。そのあいだ、読み書きは例外で失敗します。AWS のドキュメントによれば、サービスはふつう 60 秒以内、多くの場合 30 秒以内に戻ります
- reader がいなければ、同じ AZ に writer を作り直します。こちらは、ふつう 10 分以内とされています
- インスタンスが 1 台だけのクラスターで、その AZ 全体が止まった場合、Aurora は別の AZ にインスタンスを作ってくれません。自分で作ることになります

どの場合も、コミット済みのデータは失われません。データはインスタンスではなく、3 つの AZ のボリュームにあるからです。失われるのは、インスタンスのメモリーにあったもの、つまり接続と、コミットの途中だったトランザクションです。

フェイルオーバーの時間を短くする手段は、別の AZ に reader を 1 台置くことです。reader には 0 から 15 の昇格の優先順位があり、小さいものから選ばれます。この章のスタックは reader を置いていないので、writer の故障は分の単位の停止になります。練習には十分ですが、本番の構成ではありません。

アプリから見ると、フェイルオーバーは次の順に起きます。

```figure
caption: COMMIT を送ったあとで接続が切れると、アプリにはコミットされたかどうかがわからない
type: sequence
actor app: アプリ
actor old: 古い writer
actor new: 新しい writer
step app -> old: BEGIN, UPDATE
step app -> old: COMMIT
note old: 故障。応答は返らない
step old --x app: 接続が切れる
note new: reader から昇格
step app -> new: 名前を引き直して接続
step app -> new: さっきの変更は入っているか
```

アプリがすることは 3 つあります。

1 つ目は、壊れた接続を捨てて、つなぎ直すことです。接続プールは、エラーになった接続を使い回さないようにします。前の節で見たとおり、読み取り専用になったインスタンスにつながったままの接続もありうるので、書き込みが読み取り専用のエラーで断られた接続も捨てます。新しい接続は、エンドポイントの名前を引くところから始まります。

## ストレージが分かれていることで使える機能

<!-- section: 60.features -->

この章では作りませんが、同じ分け方から出てくる機能を、何のためのものかだけ書いておきます。

**クローン。** クラスターのクローンは、元のクラスターとデータのページを共有して始まる、新しいクラスターです。作るときにデータは複製されず、どちらかがページを書き換えたときに、そのページだけが別に持たれます。共有しているページのストレージ料金は、元のクラスターにだけかかります。本番のデータでスキーマの変更を試す、重い集計を本番と別のインスタンスで走らせる、といった使い方ができます。copy-on-write のクローンは 15 個までで、それを超えると丸ごとの複製になります。別のリージョンには作れません。クローンにも自分のインスタンスが要るので、計算機の料金は別にかかります。

**Global Database。** 1 つのリージョンで書き、最大 10 のリージョンへストレージの層で複製します。遅れは、ふつう 1 秒未満とされています。書けるのはプライマリのリージョンだけです。リージョンをまたぐ構成の考え方は [28章](/ja/chapters/28-multi-region.md)にあります。Global Database に入れたクラスターは auto-pause で止まらなくなります。

**zero-ETL。** クラスターのデータを、Amazon Redshift か Amazon SageMaker AI の lakehouse に、ほぼリアルタイムで複製する連携です。これを付けた writer も止まらなくなります。

**Backtrack。** バックアップからリストアせずに、クラスターを過去の時点へ巻き戻す機能です。Aurora MySQL だけのもので、Aurora PostgreSQL にはありません。Aurora PostgreSQL で過去に戻すには、[22章](/ja/chapters/22-recovery.md)と同じく、ある時点の状態を新しいクラスターとしてリストアします。

## Aurora PostgreSQL と Aurora DSQL

<!-- section: 60.choices -->

13章は、D1 から来た人が入りやすいという理由で Aurora DSQL を選びました。名前は似ていますが、2 つは別のデータベースです。以下は 2026-10-13 に読んだドキュメントに基づきます。

| | Aurora PostgreSQL（この章） | Aurora DSQL（13章） |
| --- | --- | --- |
| SQL | AWS の説明では PostgreSQL の drop-in replacement。トリガー、PL/pgSQL、一時テーブル、拡張（pgvector、pg_cron など、版ごとの一覧あり） | PostgreSQL 16 互換の一部。トリガー、PL/pgSQL、一時テーブルはない。拡張に対応しているかどうかは、読んだページでは確かめられなかった |
| トランザクション | PostgreSQL と同じ。既定は READ COMMITTED で、行ロックで待つ。デッドロックがありうる | REPEATABLE READ に固定。ロックを取らず、コミットのときに競合を調べ、負けた側に `40001` を返す |
| 1 トランザクションの上限 | この種の上限はない | 3,000 行、10 MiB、5 分 |
| 計算機 | インスタンス。writer は 1 台。フェイルオーバーがある | インスタンスがない。AWS は、従来のフェイルオーバーは無いと書いている |
| 接続 | VPC の中から。接続の上限は容量で決まる（最小 0 か 0.5 ACU なら 2,000 まで）。Data API なら接続を持たない | 公開のエンドポイントへ IAM のトークンで。クラスターあたり 10,000 接続、60 分で切れる |
| 使っていないとき | 最小を 0 ACU にすれば止まる。再開に 15 秒ほど | DPU は 0 |
| 料金の単位 | ACU 時間、ストレージ、I/O（Standard のとき） | DPU、ストレージ |
| 複数リージョン | Global Database。書くのは 1 つのリージョン | peered cluster。どのリージョンでも読み書きでき、強い整合性 |

選び方は、アプリが PostgreSQL に何を求めるかで決まります。

PostgreSQL の機能がそのまま要るなら、Aurora PostgreSQL です。拡張、トリガー、PL/pgSQL、長いトランザクション、大きな一括更新を使うアプリや、既存の PostgreSQL のアプリを書き換えずに動かしたい場合がこれに当たります。同じ行に書き込みが集まる場合も、Aurora PostgreSQL のほうが素直です。ロックで順番に待たせるので、DSQL のように再試行が積み重なりません。

新しく書くアプリで、DSQL の制約の中に収まるなら、DSQL のほうが運用するものが少なくて済みます。VPC も、インスタンスも、パスワードも、フェイルオーバーもありません。この章で書く再試行は DSQL でも要りますが、接続が切れる頻度と理由が違います。

RDS for PostgreSQL との違いは、ここまでの節で見たとおりストレージの持ち方にあります。データが小さく、停止の時間が分の単位でよく、月の料金を固定したいなら、小さな RDS のインスタンス 1 台のほうが安く、わかりやすい構成です。59章が扱います。

D1 や、Vercel の Marketplace から入れる Postgres で足りているなら、移る理由はありません。Aurora を選ぶと、VPC と、容量の設定と、この章で書くフェイルオーバーの扱いが付いてきます。その中身を、次のページから見ていきます。
