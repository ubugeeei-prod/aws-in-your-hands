# 27 Search: 全文検索、ベクトル検索、RAG

05章のノートは、ID を知っていれば読めますが、探せません。この章では、ノートを言葉で探せるようにし、言葉が一致しなくても意味の近いノートが見つかるようにします。そのうえで、見つかったノートだけを材料にして、モデルに質問の答えを書かせます。

AWS には、検索に使えるサービスがいくつもあります。なかには、1 回も検索しなくても、置いてあるだけで毎月数百ドルかかる構成があります。どれを選ぶかで、作るものも毎月の料金も大きく変わるので、この章は選ぶところに紙幅を使います。

もう 1 つの主題は、検索用のデータが元のテーブルの写しであることです。写しは遅れ、ずれます。それでも、ある人の検索に別の人のノートが出てはいけません。この章の不変条件は「検索は、他の所有者のノートを決して返さない」で、インデックスの中身が間違っていても成り立つように作ります。

前提は [05章](/ja/chapters/05-dynamodb.md)と [17章](/ja/chapters/17-ai.md)です。コードは `examples/27-search/` にあります。テストと既定の開発サーバーは AWS を呼ばず、課金されるタスクは、出てくるたびにそう書きます。

## 全体像

<!-- section: 27.architecture -->

書き込みと検索は、別の経路を通ります。

```figure
caption: ノートへの変更が、ストリームを通ってベクトルのインデックスに届く
node table: DynamoDB table | notes, stream: NEW_AND_OLD_IMAGES
node indexer: Lambda function | indexer
node titan: Amazon Bedrock | Titan Text Embeddings V2
node index: S3 Vectors | vector index, 1024 dimensions, cosine
node dlq: SQS queue | dead letters
edge table --> indexer: stream records, at least once
edge indexer -> titan: InvokeModel
edge indexer -> index: PutVectors, DeleteVectors
edge indexer --x dlq: after 3 retries
mark index
```

ノートは 05章と同じテーブルに書きます。違いは、テーブルにストリームを付けたことです。DynamoDB Streams は、アイテムへの変更を 1 件ずつ記録し、Lambda がそれを読んで関数に渡します。関数はノートを短い部分（パッセージ）に切り、それぞれを Bedrock のモデルでベクトルに変えて、S3 Vectors のインデックスに書きます。文章をベクトルに変えたものを、埋め込み（embedding）と呼びます。

```figure
caption: 検索は、所有者のノートをテーブルから読み、インデックスの答えをそのノートと照らし合わせる
type: sequence
actor caller: Caller
actor fn: Lambda | search
actor table: DynamoDB
actor bedrock: Bedrock
actor index: S3 Vectors
step caller -> fn: POST /search
step fn -> table: Query
note fn: BM25
step fn -> bedrock: InvokeModel
step fn -> index: QueryVectors
note fn: 照合、順位の統合
step fn --> caller: hits
```

検索の関数は、まずテーブルから所有者のノートを読みます。言葉の検索は、読んだノートに対して関数の中で計算します。意味の検索は、クエリをベクトルに変えて S3 Vectors に問い合わせます。そのあと、インデックスが返した当たりを、いま読んだノートと照らし合わせ、テーブルにないものを捨てます。呼び出し元に返す文章は、すべてテーブルから読んだものです。インデックスには、ノートの文章そのものを入れていません。

`POST /answers` は、同じ検索の結果を 17章の `ConverseStream` に渡して、答えを少しずつ返します。入口は 17章と同じ function URL で、認証は `AWS_IAM` です。

## 何で検索するか

<!-- section: 27.choice -->

候補は 3 つあります。OpenSearch Serverless、S3 Vectors、Bedrock Knowledge Bases です。以下の内容と料金は、2026-10-13 に公式ドキュメントと AWS Price List で確かめたものです。どれもこの 1 年で大きく変わったサービスなので、読むときにもう一度確かめてください。

### OpenSearch Serverless

OpenSearch は検索エンジンです。OpenSearch Serverless は、そのクラスターを自分で持たずに使う形で、コレクションという単位でインデックスをまとめます。コレクションには全文検索用（search）とベクトル検索用（vector search）の種類があり、S3 のドキュメントは、ハイブリッド検索、集計、高度な絞り込みが要る用途に OpenSearch を挙げています。

料金は、OCU（OpenSearch Compute Unit）という計算資源の単位に、時間をかけて決まります。東京リージョンの単価は、索引用も検索用も 1 OCU 時間あたり USD 0.334 です。

料金ページによると、従来の形（Classic コレクション）では、アカウントで最初のコレクションに、少なくとも 2 OCU が課金されます。**1 件も検索しなくても、月に USD 487.64 です**（0.334 × 2 × 730 時間）。待機用の複製を持たない設定にすると 1 OCU になりますが、それでも USD 243.82 です。練習のつもりで作って消し忘れると、この金額がそのまま請求されます。

2026-05-28 に、NextGen という新しい世代が一般提供になりました。ドキュメントと料金ページには、NextGen のコレクショングループは OCU の下限を 0 にでき、10 分間リクエストがないと索引も検索も 0 まで縮む、と書かれています。保存量の料金は別にかかります。置いてあるだけで OCU が課金されるという Classic の難点は、NextGen にはないことになります。

ただし、NextGen について確かめられなかったことが 3 つあります。東京リージョンで使えるかどうか、東京での単価が上の値と同じかどうか、0 まで縮んだ状態から最初の検索に答えるまでの時間です。OpenSearch Serverless のエンドポイントは東京にあり、AWS のブログは、NextGen はサービスを提供している商用リージョンのすべてで使えると書いていますが、リージョンの名前は挙げていません。Price List の東京の行は、世代を区別していません。

料金のほかに、扱うものの数も増えます。コレクショングループ、暗号化とネットワークとデータアクセスの 3 種類のポリシー、SigV4 で署名する OpenSearch のクライアントが必要です。書いたものが検索に現れるまで約 10 秒かかる、ともドキュメントにあります。

### S3 Vectors

S3 Vectors は、ベクトルを保存して、近いものを返すだけのサービスです。言葉の検索はできません。その代わり、時間で課金されるものがありません。料金は、保存量、書き込んだバイト数、問い合わせの回数と、問い合わせが処理したデータ量で決まります。

| 対象 | 東京リージョンの単価 |
| --- | --- |
| 保存 | 1 GB・月あたり USD 0.066 |
| 書き込み（PutVectors） | 1 GB あたり USD 0.219。1 回の最低課金は 128 KB |
| 問い合わせ（QueryVectors） | 1,000 回あたり USD 0.0027 |
| 問い合わせが処理したデータ | 1 GB あたり USD 0.000004278（10 万ベクトルまでの単価） |

1,024 次元のベクトルは 1 本あたり約 4 KB なので、2,000 本を置いても 8 MB ほどで、保存の料金は月に USD 0.0005 です。

ドキュメントには、書き込みは強い整合性を持ち、書いた直後から読める、とあります。応答時間は、頻度の低い問い合わせで 1 秒未満、頻度の高い問い合わせで 100 ミリ秒程度と説明されています。計測はしていません。検索はたまにしか行われない、という使い方に向けたサービスです。

### Bedrock Knowledge Bases

Knowledge Bases は、文書を取り込み、切り分け、埋め込み、検索するまでをまとめて引き受ける仕組みです。現在は 2 種類あります。

マネージド型は、保存先も埋め込みのモデルも Bedrock が用意します。東京リージョンで使えます。料金ページは、保存した量と取り出した回数にだけ課金すると書いていて、値は、取り込んだ元データ 1 GB あたり月 USD 5.00 と、Retrieve の呼び出し 1,000 回あたり USD 1.00 です。ただし、この 2 つの値は Price List の東京の行としては見つけられず、料金ページもリージョンを書いていません。

カスタマーマネージド型は、ベクトルの保存先を自分で用意します。保存先には OpenSearch Serverless や S3 Vectors を選べるので、料金は選んだ保存先のものになります。

どちらの型も、取り込み元に DynamoDB を選べません。選べるのは S3 や、文書を API で直接送るカスタムデータソースなどです。ノートを Knowledge Bases に入れるには、テーブルの変更を追いかけて文書として送る処理が要ります。この章が作るものと同じ問題を、別の場所で解くことになります。

### この章の選択

この章は、意味の検索に S3 Vectors を使い、言葉の検索は Lambda の関数の中で計算します。

言葉の検索に検索エンジンを使わないのは、探す範囲が小さいからです。05章は、1 人の所有者のノートを 100 件までに制限しました。1 件は 10,000 文字までなので、所有者のノートをすべて読んでも約 3 MB です。検索のたびに全部読んで順位を付けても、DynamoDB の読み込みは最大で約 375 ユニット、USD 0.00005 ほどで済みます。この大きさなら、インデックスを別に持つより、毎回テーブルを読むほうが単純で、しかも常に最新です。

意味の検索は、毎回の計算では済みません。ノートをベクトルに変えるにはモデルを呼ぶ必要があり、検索のたびに全ノートを埋め込み直すわけにはいかないので、ベクトルは保存しておきます。保存先に S3 Vectors を選んだのは、使っていない間の料金がほぼ 0 だからです。

Knowledge Bases を使わないのは、ノートが DynamoDB にあるからです。同期の処理を自分で書くことは変わらず、切り分けと埋め込みは数十行で書けます。自分で書けば、どの文章がどこに写されるかが見え、不変条件を自分のコードで守れます。

この構成で、使っていない月の料金は USD 0.00 です（小数第 2 位までの表示。内訳は[費用、注意点、片付け](/ja/chapters/27-search/wrap.md)）。

## 別の構成にする条件

<!-- section: 27.when-not -->

この構成は、ノートの数が所有者ごとに限られている、という前提に寄りかかっています。前提が外れたら、選び直します。

- 所有者をまたいで探す場合や、1 人のノートが数千件を超える場合は、検索のたびに全部を読む方法が成り立ちません。言葉の検索にもインデックスが要るので、OpenSearch Serverless を選びます。NextGen が自分のリージョンで使えるなら、置いてあるだけの料金の問題も小さくなります
- 表記のゆれ、活用形、打ち間違いを吸収したい場合は、言語を解析する検索エンジンが要ります。この章の言葉の検索は、文字の並びが一致するかどうかしか見ません。OpenSearch Serverless でどの解析器が使えるかは、この章では確かめていません
- 元の文書が PDF や Office のファイルで、S3 にある場合は、Knowledge Bases が向いています。ファイルの解析と切り分けを引き受けてくれます
- 検索が絶え間なく来て、応答時間が大事な場合は、S3 Vectors の想定する使い方から外れます。OpenSearch を検討します
- 意味の検索が要らない場合は、この章の半分で足ります。ストリームもインデックスも埋め込みも持たず、テーブルを読んで言葉で順位を付けるだけなら、追加の料金も、ずれる写しもありません

Cloudflare や Vercel で同じことをする方法は、[費用、注意点、片付け](/ja/chapters/27-search/wrap.md)で比べます。
