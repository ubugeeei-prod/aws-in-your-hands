# 41 Fargate: しくみと実装

[概要](/ja/chapters/41-fargate.md)で挙げた判断のうち、このページでは、タスクの大きさ、Fargate Spot、auto scaling の 3 つを扱います。どれも、ドキュメントに書かれた決まりを手元のコードに写し、テストで確かめられる形にしてから、スタックの設定に入れています。

## タスクの大きさ

<!-- section: 41.sizing -->

Fargate のタスクの CPU とメモリは、好きな数値を書けるわけではありません。選べる組み合わせが決まっていて、表に無い組み合わせのタスク定義は登録できません。Linux のタスクで選べるのは、2026-10-13 時点で次の組み合わせです。

| CPU | メモリ |
| --- | --- |
| 256（0.25 vCPU） | 512 MiB、1 GB、2 GB |
| 512（0.5 vCPU） | 1〜4 GB を 1 GB きざみ |
| 1024（1 vCPU） | 2〜8 GB を 1 GB きざみ |
| 2048（2 vCPU） | 4〜16 GB を 1 GB きざみ |
| 4096（4 vCPU） | 8〜30 GB を 1 GB きざみ |
| 8192（8 vCPU） | 16〜60 GB を 4 GB きざみ |
| 16384（16 vCPU） | 32〜120 GB を 8 GB きざみ |
| 32768（32 vCPU） | 60 GB、120 GB、244 GB |

表から読み取れることは、メモリだけを大きくはできないことです。0.25 vCPU のタスクは 2 GB までで、3 GB 必要なら CPU も 0.5 vCPU に上げることになり、使わない CPU にも料金を払います。逆も同じで、CPU を上げるとメモリの下限も上がります。

**どう決めるか。** 大きさは、計った値から決めます。ECS は、サービスごとの `CPUUtilization` と `MemoryUtilization` を、何も設定しなくても 1 分ごとに CloudWatch へ送っています。ただし、この 2 つはサービス全体の平均で、タスクが確保したぶんに対する割合です。タスク 1 つが瞬間的にどこまで使ったかは見えません。

実際に使った量を見るには、Container Insights を有効にします（[19章](/ja/chapters/19-observability.md)）。`CpuUtilized` が CPU ユニットで、`MemoryUtilized` が MiB で記録されます。単位の表示は megabytes ですが、ドキュメントは実際には MiB だと注記しています。タスクごと、コンテナごとの値まで見るには、enhanced observability のほうが必要です。

Container Insights は無料ではなく、集めたメトリクスがカスタムメトリクスとして課金されます。CloudWatch の料金のページにある計算例は、Fargate の場合のメトリクスの数を、クラスターごとに 13、サービスごとに 15（うち `RunningTaskCount` は 2026-10-01 から無料）、タスクごとに 10 と数えています。この数え方をこの章の構成（クラスター 1、サービス 1、タスク定義 1 種類）に当てはめると 37 個で、東京のカスタムメトリクスの単価 USD 0.30 を掛けると月 USD 11.10 です。これは計算例の数え方を借りた見積もりで、請求で確かめた額ではありません。enhanced observability は数え方も単価も別で、東京の Price List には 1 メトリクスあたり月 USD 0.07 の単価があります。この章のスタックは、Container Insights を有効にしていません。大きさを決めたい期間だけ有効にして、決まったら切る使い方ができます。

`maxUtilization` は、最大のときにタスクの何割まで使ってよいかです。0.7 なら、3 割を余裕として残します。この数値に正解はありません。平均の 1 分値は瞬間の山を隠すので、余裕を 0 にする理由は無く、余裕を大きく取るほど料金が増えます。関数は、条件を満たす組み合わせのうち、単価から計算した料金がいちばん安いものを返します。

必要な量は 258 ユニットで、256 をわずかに超えただけですが、料金は 2 倍になります。きざみが粗いので、境目の近くでは、余裕の取り方を見直すか、タスクを小さいまま数を増やすかを考える価値があります。

**arm64 と x86。** 同じ大きさなら、arm64 のほうが 2 割安くなります。タスク 1 つを 1 か月（730 時間）動かしたときの定価は、次のとおりです。

| 大きさ | arm64 | x86 |
| --- | --- | --- |
| 0.25 vCPU、512 MiB | 9.00 | 11.25 |
| 0.5 vCPU、1 GB | 17.99 | 22.49 |
| 0.5 vCPU、4 GB | 27.67 | 34.60 |
| 1 vCPU、2 GB | 35.98 | 44.98 |

arm64 を選べるかどうかは、イメージ次第です。12章のイメージは `linux/arm64` でビルドしています。OS のパッケージや、ネイティブのモジュールに x86 しか無いものがあるなら、選べません。

**エフェメラルストレージ。** タスクには、動いている間だけ使えるディスクが 20 GiB 付きます。タスク定義の `ephemeralStorage` で 21〜200 GiB を指定でき、料金がかかるのは 20 を超えたぶんだけです。東京の単価は 1 GB 時あたり USD 0.000133 で、50 GiB を指定したタスク 1 つなら、超過の 30 GB ぶんが月 USD 2.91、上限の 200 GiB なら月 USD 17.48 です。取得したイメージも、圧縮されたものと展開されたものの両方がここに置かれるので、アプリが使えるのは 20 GiB からイメージのぶんを引いた残りです。ディスクがいっぱいになったときに何が起きるかは、読んだページには書かれていませんでした。12章とこの章のコンテナは、ルートのファイルシステムを読み取り専用にしていて、ディスクには何も書きません。

**メモリの上限に達したとき。** タスクのメモリは、ドキュメントの言い方では、タスクに見せるメモリの hard limit です。コンテナがメモリの上限を超えようとすると、コンテナは強制終了されます。止まったタスクには、`OutOfMemoryError` の分類で、container killed due to memory usage と記録されます。サービスのタスクなら、代わりが起動されます。警告も、遅くなるだけの段階もありません。処理中だったリクエストは、SIGTERM のときと違って、終わらせる機会がありません。正確な `stoppedReason` の文面と終了コードは、Fargate については一次情報で確認できませんでした。メモリの余裕は、CPU の余裕より多めに取ってください。CPU が足りないと遅くなりますが、メモリが足りないとタスクが落ちます。

## Fargate Spot と capacity provider strategy

<!-- section: 41.spot -->

12章のサービスは、launch type に `FARGATE` を指定していました。もう 1 つの指定の仕方が、**capacity provider strategy** です。Fargate には `FARGATE` と `FARGATE_SPOT` の 2 つの capacity provider があり、タスクをどちらにどの割合で置くかを書けます。

`FARGATE_SPOT` は、AWS の空いている容量でタスクを動かします。料金のページは、通常の Fargate より最大 70% 安いと書いています。そのかわり、AWS がその容量を必要としたときには、2 分前の予告だけでタスクが止められます。容量が空いていなければ、タスクは起動を待たされます。ドキュメントは、Fargate が Spot の容量をオンデマンドで埋め合わせることはしない、と明記しています。

strategy には、決まりがいくつかあります。

- strategy に書ける capacity provider は、クラスターに関連付けてあるものだけです
- `base` は、その provider に最低限置くタスクの数です。`base` を持てるのは 1 つの provider だけで、`weight` より先に満たされます
- `weight` は、`base` を超えたぶんを分ける比です。ドキュメントの例では、A が 1、B が 4 なら、A の 1 つにつき B に 4 つ置かれます
- 少なくとも 1 つの provider の `weight` が 0 より大きい必要があります
- launch type と strategy は、同時には指定できません

クラスターのコンストラクトには `enableFargateCapacityProviders` というプロパティもありますが、使っていません。手元で synth して確かめたところ、このプロパティは関連付けを別のリソース（`AWS::ECS::ClusterCapacityProviderAssociations`）として作り、サービスはそのリソースに依存しませんでした。関連付けより先にサービスが作られると、strategy が拒否されるおそれがあります。クラスター自身の `CapacityProviders` に書けば、クラスターを参照するサービスは必ずあとに作られます。cdkd が専用の実装で扱えるのも、こちらの書き方です。

**中断のときに起きること。** Spot のタスクが止められるとき、2 分前に予告が出ます。予告は、EventBridge のタスク状態変化イベントと、タスクへの SIGTERM の 2 つの形で届きます。タスクが止まったあとのイベントには、`stopCode` に `SpotInterruption` が入ります。サービスのスケジューラーは、Spot に空きがあれば代わりのタスクを起動しようとします。

タスクの側から見ると、中断は SIGTERM です。Spot から来たのか、デプロイから来たのかは区別できず、区別する必要もありません。12章のサーバーは、SIGTERM を受けると新しい接続を受け付けるのをやめ、処理中のリクエストを終えてから終了コード 0 で終わります。次のテストは、12章のサーバーを workspace の依存から起動して、その動きが 2 分の予告に収まることを確かめています。

確かめられていないことが 1 つあります。デプロイやスケールインでは、ECS が先に ALB からタスクの登録を解除し、deregistration delay のあとで SIGTERM を送ります。Spot の中断でも同じ順序になるのかどうかは、読んだページからは確定できませんでした。登録解除より先に SIGTERM が届くなら、サーバーが接続を受け付けなくなってから ALB が振り分けをやめるまでのあいだ、そのタスクに送られたリクエストは失敗します。この章のテストとモデルは、2 つが同時に起きる場合を最悪として扱っています。

**Spot に置いてはいけないもの。** 判断の基準は、2 分の予告だけで止められて困るかどうかです。

- サービスが最低限必要とするタスク。`base` をオンデマンドの側に置くのは、このためです。ドキュメントも、タスクが 1 つだけのサービスは、容量が戻るまで中断されたままになると書いています
- そこにしかない状態を持つタスク。この章のアプリは、ノートをタスクのメモリに持っているので、Spot のタスクが止められると、そのタスクのノートは消えます。練習用だから許されている設計で、状態を外に置いたサービスなら問題になりません
- やり直せない仕事と、止めるのに 2 分より長くかかる仕事。途中から再開できない長いバッチや、切れると困る長い接続がこれに当たります

Spot の単価は、需要に応じて AWS が少しずつ動かします。東京の単価は Price List の bulk API に入っておらず、料金のページの表はスクリプトで埋められるので、この本では取得できていません。料金の計算では、Spot のタスクもオンデマンドの単価で数え、上限として扱っています。

## タスクの数を増減させる

<!-- section: 41.scaling -->

12章は、CPU 使用率 60% を目標にした target tracking を 1 つ付けていました。この章では、何を見て増減させるかを選び直し、増えるときと減るときに何が起きるかを確かめます。

ECS のサービスに付けられる auto scaling は、target tracking、step scaling、scheduled scaling、predictive scaling です。ドキュメントは、target tracking をいちばん簡単な方式としています。メトリクスと目標値を決めると、アラームを Application Auto Scaling が作って管理します。step scaling は、しきい値と増減の数を自分で決めるので、急な変化に速く反応させられます。scheduled scaling は、決まった時刻に最小と最大の数を変えます。平日の朝に増えるとわかっているなら、増える前に最小の数を上げておけます。

**何を見るか。** あらかじめ用意されているメトリクスは、サービスの平均 CPU 使用率、平均メモリ使用率、ALB のターゲット 1 つあたりのリクエスト数（`ALBRequestCountPerTarget`）です。ドキュメントは、スケーリングに使うメトリクスの条件を 2 つ挙げています。需要と一緒に動くこと、そして容量に比例して動くことです。タスクを 2 倍にしたら値が半分になるメトリクスでなければ、目標値に合わせる計算が成り立ちません。メモリ使用率は、GC のあるランタイムでは需要と関係なく動くことが多いので勧められていません。Node.js も GC のあるランタイムです。

この章のサービスには、ポリシーを 2 つ付けています。

<<< @/examples/41-fargate/infra/lib/fargate-stack.ts{scaling}

ポリシーが複数あるとき、サービスは、どれか 1 つが増やすべきだと判断すれば増え、すべてが減らしてよいと判断したときだけ減ります。CPU を使う処理が増えても、リクエストの数が増えても増え、両方が落ち着くまで減りません。

リクエスト数の目標値は、ターゲット 1 つあたり 1 分間の件数です。600 という値は仮定で、計って決めたものではありません。負荷試験（[32章](/ja/chapters/32-limits.md)）で、タスク 1 つが何件までなら応答時間を保てるかを計り、その手前の値にします。`ALBRequestCountPerTarget` は、blue/green のデプロイでは使えません。

**cooldown。** cooldown は、前の増減が効いてくるのを待つ時間です。スケールアウトの cooldown のあいだは、前より大きい増やし方が必要になったときだけ、さらに増えます。スケールインの cooldown のあいだは、減らす動きが止められます。そのあいだにスケールアウトが必要になれば、すぐに増えます。ECS のサービスでは、どちらも既定で 300 秒です。この章は、12章と同じく、スケールアウトを 60 秒、スケールインを 300 秒にしています。増やしすぎたときに失うのは料金ですが、減らしすぎたときに失うのはリクエストなので、戻りを遅くしています。

**増えるのが間に合わない時間。** target tracking は、負荷が上がった瞬間には増えません。メトリクスが 1 分ごとに届き、アラームが目標を超えた状態を何回か続けて見てから、タスクの数が変わります。そこから新しいタスクがイメージを取得し、起動し、ヘルスチェックに通って、ようやくリクエストを受け始めます。

この遅れがどのくらいの影響を持つかを、モデルで確かめます。モデルは、ドキュメントに書かれた動きをこの章が写したもので、Application Auto Scaling そのものではありません。ドキュメントに数値が無いところは、モデルのパラメーターにしてあります。

<<< @/examples/41-fargate/src/model-defaults.ts{defaults}

このモデルからわかることは 2 つあります。target tracking は、数分で 5 倍になるような立ち上がりには間に合いません。そして、間に合わない量は、タスクが起動するまでの時間でほぼ決まります。対策は、イメージを小さくして起動を速くすること、目標値を低くして普段から余裕を持つこと、増える時刻がわかっているなら scheduled scaling で先に増やしておくことです。モデルは、スケールインを 1 回で 3 つ減らしていますが、ドキュメントはスケールインを段階的だとしていて、実際に 1 回で何個減るかは確かめていません。

**減らすときに切らない。** スケールアウトで起きる失敗は、遅れです。スケールインで起きる失敗は、処理中のリクエストが途中で切れることで、利用者にはエラーとして見えます。減らす対象になったタスクは、その瞬間にもリクエストを処理しているからです。

```figure
caption: Application Auto Scaling が desired count を下げると、ECS は減らすタスクを先に ALB から外し、処理中のリクエストを終える時間を与えてから SIGTERM を送る

actor ecs: ECS
actor alb: ALB
actor task: 減らされるタスク
note ecs: desired count 5 -> 2
step ecs -> alb: 登録解除
note alb: draining
step alb -> task: 処理中のぶんだけ
step task --> alb: レスポンス
```
