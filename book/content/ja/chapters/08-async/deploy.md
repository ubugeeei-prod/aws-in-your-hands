# 08 Queue: デプロイ

## AWS にのせる準備

<!-- section: 08.infra -->

このページでは、[最初のページ](/ja/chapters/08-async.md)で作ったワーカーと掃除を AWS にのせるためのスタックを読み、デプロイの手順と、キューにメッセージが溜まったときの見方を説明します。スタックは 07章のものを継承しているので、読むのは増えた部分だけです。

### キューと、その入口

<<< @/examples/08-async/infra/lib/async-stack.ts{queues}

<<< @/examples/08-async/infra/lib/async-stack.ts{queue-policy}

キューポリシーは、キューに付ける権限の文書です。このキューにメッセージを入れてよいのは S3 だけで、それも、このバケットについての通知で、このアカウントの中から来たものに限ります。`aws:SourceArn` と `aws:SourceAccount` の 2 つの条件は、公式ドキュメントの例と同じです。条件がないと、S3 を経由しさえすれば、他人のバケットからでもこのキューにメッセージを入れられることになります。

DLQ のほうには、`Allow` が 1 つもありません。どのキューがこの DLQ を使えるかは、redrive allow policy という別の設定で決まります。既定ではすべてのキューに許されていて、この章は既定のままにしています。

### バケットの名前を決める理由

<<< @/examples/08-async/infra/lib/async-stack.ts{bucket-name}

<<< @/examples/08-async/infra/lib/async-stack.ts{notification}

この部分は、リソースを作る順序の都合で少し込み入っています。

S3 は、通知の設定を受け取った時点で、送り先のキューに本当に送れるかを確かめます。そのため、キューポリシーはバケットより先に存在していなければいけません。ところが、キューポリシーにはバケットの ARN が書いてあります。バケットの名前を自動で付けていると、ARN はバケットができるまで決まりません。バケットはポリシーを待ち、ポリシーはバケットを待つことになります。CloudFormation のドキュメントも、この循環を名指しして注意しています。

CDK の `bucket.addEventNotification` は、この循環をカスタムリソースで解決します。バケットとポリシーを両方作った後で、通知の設定だけを別の Lambda 関数に書かせるやり方です。この章では使いません。関数が 1 つ増え、その関数にはバケットの設定を書き換える権限が要り、通知の設定がテンプレートから見えなくなるからです。

かわりに、バケットの名前を固定しました。名前が決まっていれば、バケットを参照せずに ARN を書けるので、循環は起きません。

そのために手放したものもあります。バケットの名前は、世界中の AWS アカウントを通じて重複できません。アカウント ID を含めているのでぶつかる可能性は低いですが、ゼロではありません。また、名前を固定したバケットは、作り直しが必要な変更（リージョンの移動など）がやりにくくなります。

もう 1 つの選択肢は、S3 の通知を EventBridge に送り、EventBridge のルールからキューに入れることです。バケットの側には EventBridge に送ると書くだけなので、循環がありません。そのかわり、イベントの形と、途中に挟まるサービスが変わります。この章では試していません。EventBridge のバスとルールで、同じ出来事を複数の相手に配る構成は、[25章](/ja/chapters/25-events.md)で扱います。

通知するのは、`u/` で始まるキーの、作成と削除だけです。

### ワーカーと、その呼ばれ方

<<< @/examples/08-async/infra/lib/async-stack.ts{worker}

ワーカーのロールは、API の関数のロールとは別です。許しているのは、キューから読む 3 つの操作、`u/` のオブジェクトを読むことと、そのタグを外すこと、バケットの一覧（`s3:ListBucket`）、テーブルの 3 つの操作です。一覧を許しているのは 07章と同じ理由で、無いキーを読んだときに 403 ではなく 404 が返るようにするためです。オブジェクトを消す権限はありません。消すのは掃除の仕事です。

キューを読みにいくのは、あなたのコードではなく Lambda で、そのときに使われるのがこの関数のロールです。AWS が用意している管理ポリシー（`AWSLambdaSQSQueueExecutionRole`）も同じ 3 つの操作を許しますが、対象が「すべてのキュー」になります。この章では、対象を 1 つのキューに絞っています。

<<< @/examples/08-async/src/worker-lambda.ts{handler}

<<< @/examples/08-async/src/env.ts{env}

<<< @/examples/08-async/infra/lib/async-stack.ts{mapping}

イベントソースマッピングは、Lambda がこのキューを読んでこの関数に渡す、という設定です。決めることが 3 つあります。

`batchSize` は 10 で、1 回の呼び出しで渡されるメッセージの最大数です。

`maxConcurrency` は 2 で、このキューのために同時に動くワーカーの数の上限です。2 は設定できる最小の値です。何も設定しないと、Lambda はメッセージが溜まっているかぎりワーカーを増やします。ドキュメントによると、5 つから始めて、1 分ごとに最大 300 ずつ、1,250 まで増えます。ワーカーが増えれば、ワーカーが書き込む先（DynamoDB）や読む先（S3）へのリクエストも同じだけ増えます。

`reportBatchItemFailures` は、[最初のページ](/ja/chapters/08-async.md)で説明した partial batch response を有効にします。ドキュメントは、これを指定して初めて、関数が一部の成功を返せるようになると説明しています。付け忘れたら、ワーカーが返した一覧は使われないはずです。

関数の同時実行数を抑える方法には、もう 1 つ、関数に付ける予約済み同時実行数（reserved concurrency）があります。ドキュメントは、この 2 つが別の設定であることを強調しています。予約済み同時実行数のほうが小さいと、Lambda はキューから受け取ったメッセージを関数に渡せず、スロットリングされます。そのメッセージは、処理されていないのに、受け取られた回数が 1 つ増えてキューに戻ります。

### 掃除とスケジュール

<<< @/examples/08-async/infra/lib/async-stack.ts{housekeeping}

掃除のロールは、3 つ目のロールです。許しているのは、オブジェクトの一覧と削除、タグを外すこと、テーブルの読み取りと削除で、キューには触れません。

タイムアウトは、Lambda の上限の 15 分にしました。この関数はバケットのオブジェクトを 1 つずつ順に見るので、枚数が増えると時間がかかります。

<<< @/examples/08-async/infra/lib/async-stack.ts{schedule}

EventBridge Scheduler は、決めた時刻や間隔で AWS の API を 1 つ呼ぶサービスです。呼ぶときに使う権限が、スケジュールの実行ロールです。関数の実行ロールとは別のもので、Scheduler があなたの代わりに関数を呼ぶために使います。

このロールにできるのは、掃除の関数を呼ぶことだけです。また、このロールを使えるのは、このアカウントの default の schedule group に属するスケジュールだけです。公式ドキュメントは、条件に書く ARN を個々のスケジュールではなく schedule group にするよう指定しています。

`retryPolicy` は、Scheduler が関数を呼ぶこと自体に失敗したときの再試行です。15 分以内に 3 回までやり直し、それでも呼べなければその回はあきらめます。1 時間後に次の回が来るからです。

### テストが見ていること

テストは、テンプレートに対して次を確かめます。synth は、ファイルの先頭で 1 回だけ実行します。

- キューポリシーの `Allow` が 1 つだけで、principal が S3、アクションが `sqs:SendMessage`、条件がバケットの ARN とアカウントである
- キューポリシーがバケットのリソースを参照していない。バケットはキューポリシーの後に作られる
- 通知の設定がテンプレートに直接書かれていて、`Custom::` で始まるリソースが 1 つもない
- 可視性タイムアウトがワーカーのタイムアウトの 6 倍で、DLQ の保持期間が元のキューより長い
- イベントソースマッピングが、バッチ 10、同時実行 2、`ReportBatchItemFailures` である
- ワーカーと掃除のロールのアクションが、上に書いたものちょうどで、`*` がない
- スケジュールのロールを使えるのが Scheduler だけで、できるのが掃除の関数の呼び出しだけである

使っているリソースの種類は、07章の 19 種類に 5 種類を足した 24 種類です。足した 5 つ（`AWS::SQS::Queue`、`AWS::SQS::QueuePolicy`、`AWS::Lambda::EventSourceMapping`、`AWS::Lambda::EventInvokeConfig`、`AWS::Scheduler::Schedule`）は、固定した版の cdkd がどれも専用の実装を持っていることを、`v0.296.28` のタグのソースで確かめました。`AWS::S3::Bucket` の実装が `BucketName` と `NotificationConfiguration` を扱うことも、同じソースで確かめています。

## デプロイして確かめる

<!-- section: 08.deploy -->

ここから先の手順は、実行していません。用意したのは手順とタスクまでです。

```bash
vp run async:infra:diff
vp run async:infra:deploy
vp run async:smoke
```

`async:smoke` は、あなたの認証情報でバケットに小さな PNG を直接置き、ワーカーの記録がテーブルに現れるのを待ちます。続けて、同じキーを画像でないもので置き換え、記録が「だめ」に変わって `sequencer` が大きくなることを確かめます。最後にオブジェクトを消して、記録が消えるのを待ちます。S3、SQS、Lambda、DynamoDB を 1 周する確認で、それぞれの段階で最大 90 秒待ちます。

ブラウザからも使うなら、07章と同じ手順を踏みます。

```bash
vp run async:user:create you@example.com
vp run async:publish
vp run async:smoke:web
```

サインインして得たアクセストークンを環境変数 `AIH_ACCESS_TOKEN` に入れて `async:smoke` を実行すると、フォームでのアップロードも確かめます。完了した後に同じフォームをもう一度送り、pending のタグが外れるのを待ちます。この章で確かめられていないことのうち、いちばん大事なもの（POST のイベントに `sequencer` が入るか）は、この実行でわかります。

スケジュールは、作られるとすぐに 1 回目を起動します。開始日を指定していない rate のスケジュールはそう動く、とドキュメントにあります。

ドリフトの検査は、これまでの章と同じです。

```bash
vp run async:infra:drift
```

## 溜まったとき、落ちたとき

<!-- section: 08.operate -->

### キューが伸びる

アップロードが急に増えてワーカーが追いつかなくなっても、何も失敗しません。メッセージがキューに溜まるだけです。ワーカーは同時に 2 つまでしか動かないので、DynamoDB や S3 へのリクエストが急に増えることもありません。遅れは、検査の結果が出るのが遅くなる形で現れます。これが backpressure で、キューは流量の差を待ち行列の長さとして引き受けます。

ただし、キューが引き受けられるのは保持期間までです。この章のキューは、メッセージを 4 日保持します。4 日たっても処理されなかったメッセージは消え、DLQ にも行きません。そのため、見るべき数字はキューの長さよりも、いちばん古いメッセージの年齢（CloudWatch の `ApproximateAgeOfOldestMessage`）です。アラームの組み立て方は [19章](/ja/chapters/19-observability.md)にあります。

次に、キューに入ってくる量を何が絞っているかを見ます。

このキューに送れるのは S3 だけで、それも、このバケットの `u/` の下で起きたことだけです。そこにオブジェクトを置けるのは、許可証を持った人です。許可証は 07章の API が出すもので、API には 1 秒 10 リクエストのスロットリングがあり、1 人が受け取れるのは 1 日 100 枚までです。イベントは、作成で 1 件、削除やライフサイクルの失効でもう 1 件起きます。ふつうに使われているかぎり、1 人が 1 日に起こせるイベントは数百件で、ワーカーが追いつけない量にはなりません。

絞れていない道が 1 つあります。07章で説明したとおり、許可証は 5 分間、何度でも使えます。同じフォームを送り直すたびに、S3 はオブジェクトを置き換えて、作成のイベントをもう 1 件送ります。この送り直しは API を通らないので、スロットリングも、1 日 100 枚の上限も効きません。サインインした利用者が同じフォームを送り続けると、キューは伸びます。

そのときに守られるものと、守られないものを分けて書きます。

- ワーカーは増えません。同時に動くのは 2 つまでです。1 件 200 ミリ秒という[「料金」](/ja/chapters/08-async/wrap.md)の仮定なら、さばけるのは 1 秒に 10 件ほど、1 日で約 86 万件です
- DynamoDB へのリクエストも増えません。ワーカーが 2 つなら、書き込みも読み取りも、それに比例した量までです。それに、テーブルには 07章と同じ request unit の上限があります
- 追いつけなかったぶんは、4 日で消えます。上の仮定なら、4 日でさばけるのは約 346 万件です。それより多く溜まったメッセージは、処理されないまま消えます。その画像は、検査されていません
- 料金は、届いたイベントの数に比例します。キューにメッセージが入ること自体は、止まりません

キューは流量の差を引き受けますが、流量そのものは絞りません。絞るのは、入口の仕事です。

### DLQ を見る

```bash
vp run async:queue
vp run async:logs
```

`async:queue` は、2 つのキューに溜まっているおよその件数と、DLQ の先頭 10 件までの中身を表示します。メッセージは動かしません。可視性タイムアウトを 0 にして受け取っているので、見た後もメッセージはそのまま見えています。ただし、受信回数は増えます。

DLQ にメッセージがあったら、まずワーカーのログで、そのキーの `message failed` の行を探してください。失敗の理由が書いてあります。理由は、次の 3 つのどれかに分かれます。

- 理由が一時的なもの（DynamoDB や S3 の一時的なエラー、デプロイ直後の権限の反映待ち）で、もう直っている
- 理由がコードや設定の誤りで、まだ直っていない
- メッセージそのものが読めない

元のキューに戻してよいのは、1 つ目だけです。2 つ目は、直してから戻します。3 つ目は、戻しても同じことが起きるだけです。

```bash
vp run async:queue --redrive
```

このコマンドは、DLQ のメッセージを元のキューに戻します（redrive）。公式ドキュメントによると、戻されたメッセージは新しいメッセージとして扱われ、新しい ID が付き、保持期間も数え直されます。redrive の途中でメッセージを選んだり書き換えたりはできず、全部が戻ります。

戻したメッセージがすでに処理済みのイベントだったとしても、何も起きません。ワーカーを冪等に作ったのは、このためです。
