# 39 Database Migration: しくみと実装

主キーのないテーブルは、CDC で `UPDATE` と `DELETE` が無視されます。PostgreSQL が既定で WAL に残す変更前の行は主キーの列だけなので、主キーがなければ、どの行を直すのかを DMS が知る方法がありません。full load と CDC を組み合わせたタスクで行が重複することも、データ検証ができないことも、ドキュメントに書かれています。`audit_log` がこれに当たります。

主キーが LOB の型のテーブルは、複製できません。DMS は LOB の列をいったん null で入れてから更新するので、主キーが null になる最初の `INSERT` が失敗する、という説明です。そして PostgreSQL をソースにしたときの型の対応表では、`text` は NCLOB、つまり LOB です。13章のスキーマの `owner text PRIMARY KEY` がこれに当たります。この 2 つの記述を組み合わせて「`text` の主キーは移せない」と読んだのはこの章で、DMS を動かして確かめてはいません。

主キーでない `text` の列も LOB として扱われ、上限を超えた分は切り詰められます。シーケンスで番号を振る列は、番号は運ばれてもシーケンスは運ばれません。この 2 つは止める理由ではなく、タスクの設定と切り替えの手順で受け止めます。

### ロジカルレプリケーションとスロット

CDC は、PostgreSQL のロジカルレプリケーションの仕組みで変更を読みます。RDS for PostgreSQL では、パラメーターグループの `rds.logical_replication` を 1 にします。静的なパラメーターなので、反映にはインスタンスの再起動が要ります。WAL の量が増えるので、使うときだけ有効にするよう書かれています。

タスクが始まると、DMS はソースにレプリケーションスロット（replication slot）を作ります。スロットは、読み手がどこまで読んだかをデータベースが覚えておく仕組みで、読み手が読み終えるまで WAL を消しません。変更を取りこぼさないための仕組みですが、裏返すと、読み手がいなくなったスロットは WAL を溜め続けます。PostgreSQL のドキュメントは、スロットが `pg_wal` の領域を埋めることがあると警告しています。上限を決める `max_slot_wal_keep_size` の既定値は -1、つまり無制限です。

DMS のドキュメントによると、スロットはタスクが動いていない間も残り、DMS が作ったスロットはタスクを消したときに消されます。止めたまま忘れたレプリケーションは、DCU の料金のほかに、ソースのディスクを埋めていくことになります。RDS には `OldestReplicationSlotLag` と `TransactionLogsDiskUsage` というメトリクスがあるので、移行の間はソースのインスタンスにアラームを付けておきます。スロットは `pg_replication_slots` で見え、`active` が false のものが読み手のいないスロットです。残ってしまったものは `pg_drop_replication_slot` で消します。

この章のエンドポイントは `HeartbeatEnable` を有効にしています。書き込みが少ないソースでは、スロットの `restart_lsn` が進まず古い WAL が残ります。DMS が定期的に小さな書き込みをして、それを進めるための設定です。

長いトランザクションにも注意が要ります。トランザクションが終わるまで `restart_lsn` は進まないと書かれているので、移行の間は、何時間も開いたままのトランザクションを作らないようにします。

## タスクの設定

<!-- section: 39.settings -->

タスクの設定も JSON です。項目は多いのですが、この章が既定値から変えるのは次のものだけです。

<<< @/examples/39-database-migration/src/task-settings.ts{settings}

`TargetTablePrepMode` は、full load を始めるときにターゲットのテーブルをどうするかです。`DROP_AND_CREATE` は消して作り直し、`TRUNCATE_BEFORE_LOAD` は中身を消し、`DO_NOTHING` は触りません。この章はインデックスも制約も付けたテーブルを先に作っているので、`DO_NOTHING` にします。その代わり、失敗したタスクを最初からやり直すときは、前回入った行が残っています。そのままでは主キーの重複のエラーになるので、やり直す前にターゲットのテーブルを自分で空にします。

LOB の設定は、`text` の列のためにあります。limited LOB mode は、上限の大きさまでをまとめて運び、超えた分を切り詰めます。設定例の上限は 32 KB ですが、ノートの本文は 10,000 文字まであり、UTF-8 では 1 文字が最大 4 バイトなので 40 KB になりえます。上限を 64 KB にし、ソースのエンドポイントに `FailTasksOnLobTruncation` を付けて、切り詰める代わりにタスクを失敗させます。黙って短くなった本文は、あとで見つけるのが難しいからです。

エラーの扱いは、既定値のままにしています。既定では、すでにある行への `INSERT` と、行が見つからない `UPDATE` はログに書いて先へ進み、行が見つからない `DELETE` は無視します。テーブル単位のエラーは `SUSPEND_TABLE` で、そのテーブルだけを止めてタスクは続きます。タスクが動いていても、止まったテーブルがあるかもしれないということです。切り替えの前に、テーブルごとの状態を必ず見ます。

データ検証（`EnableValidation`）を有効にすると、DMS は full load が済んだテーブルから、ソースとターゲットの行を 1 行ずつ比べ、その後の変更も比べていきます。比べるのは行の中身で、インデックスや制約、シーケンスは対象ではありません。主キーか一意インデックスのないテーブルは検証できず、`varchar` の主キーは 1024 未満の長さが宣言されている必要があります。検証の間にターゲットを DMS 以外が書き換えると結果が正しく出ないことがある、絶えず書き換えられている行は検証できない、失敗が 10,000 件を超えると検証を止める、とも書かれています。検証はソースとターゲットの両方に追加のクエリを投げるので、その負荷も見込みます。

premigration assessment は、タスクを動かす前に、型や主キーの問題を DMS 自身に調べさせる機能です。Serverless では、レプリケーションを開始する API に評価の設定を渡して実行します。上の `preflight` は、ドキュメントを読んで書いた小さな写しにすぎません。本番では DMS の評価を実行し、その結果を正とします。

失敗したレプリケーションをやり直す方法は 2 つあり、選び間違えると結果が変わります。`resume-processing` は、止まった位置から変更の適用を再開します。`reload-target` は、テーブルを最初から読み込み直します。full load の途中で止まったテーブルは、途中から再開できません。スキーマを変えるような transformation のルールは、再開では効かず、最初からのやり直しが要ると書かれています。Serverless では、一度開始したレプリケーションは `resume-processing` で再開するもので、開始しないまま 48 時間たつと容量が解放されて再開できなくなる、ともあります。

スタックは、11章の VPC を import して、その中に DMS の部品を置きます。データベースは作らず、ホスト名とセキュリティグループの ID を `-c` で受け取ります。

レプリケーションは VPC のプライベートサブネットで動き、そこから 2 つのデータベースと Secrets Manager につなぎます。

<<< @/examples/39-database-migration/infra/lib/migration-stack.ts{network}

出ていく通信は 3 種類に絞りました。2 つのデータベースの 5432 番と、VPC の中の 443 番です。443 番は、Secrets Manager のインターフェースエンドポイントに届くためのものです。DMS Serverless は Secrets Manager に VPC エンドポイント経由で届く必要がある、とドキュメントにあるので、11章のスタックを `-c interfaceEndpoints=secretsmanager` でデプロイしておきます。このエンドポイントは時間単位で課金されます。レプリケーションがほかの宛先への通信を必要とするかどうかは、確かめていません。

データベースの側のセキュリティグループには、レプリケーションからの 5432 番を許すルールを足します。ルールはこのスタックのものなので、スタックを消すと一緒に消えます。

DMS は、アカウントに決まった名前の IAM ロールがあることを前提にしています。

<<< @/examples/39-database-migration/infra/lib/migration-stack.ts{account-roles}

`dms-vpc-role` と `dms-cloudwatch-logs-role` は、DMS が名前で探すロールです。別の名前では見つけてもらえません。名前が決まっているので、アカウントに 1 つずつしか作れず、すでにあるアカウントでこのスタックをデプロイすると名前がぶつかります。その場合は `-c accountRoles=existing` を渡します。Serverless はこのほかに、`AWSServiceRoleForDMSServerless` というサービスリンクロールを使います。こちらは、レプリケーションを開始したときに DMS が作ります。

接続の認証情報は、スタックが作るシークレットに入れます。

<<< @/examples/39-database-migration/infra/lib/migration-stack.ts{secrets}

DMS が読むシークレットは、`username`、`password`、`host`、`port` を持つ JSON です。RDS が管理するマスターユーザーのシークレットは、ホストとポートを含まないので使えないと書かれています。パスワードは [21章](/ja/chapters/21-security.md)と同じく、デプロイのときに生成させます。DMS はエンドポイントのパスワードに一部の記号を受け付けないので、記号を含めない設定にしました。

シークレットを読むロールの信頼ポリシーは、リージョンつきのサービス名 `dms.ap-northeast-1.amazonaws.com` です。権限は、この 2 つのシークレットの `GetSecretValue` だけにしています。

<<< @/examples/39-database-migration/infra/lib/migration-stack.ts{endpoints}

ソースのエンドポイントでは、`CaptureDdls` を false にしました。既定では、DMS は DDL を拾うための監査テーブルとイベントトリガーをソースに作ります。この章は、移行の間はスキーマを変えないと決めるので、それらを作らせません。決めたことは守る必要があります。移行の途中でソースに `ALTER TABLE` を流すと、ターゲットには届きません。

ターゲットのエンドポイントの `AfterConnectScript` は、外部キーのための設定です。full load はテーブルを 1 つずつ運び、順序は保証されないので、ノートがその持ち主より先に届くことがあります。`session_replication_role` を `replica` にすると、そのセッションでは外部キーとユーザーのトリガーが働きません。ドキュメントが勧めている方法ですが、ターゲットのユーザーがこの `SET` を実行できる権限を持っているかは、確かめていません。

<<< @/examples/39-database-migration/infra/lib/migration-stack.ts{replication}

`AWS::DMS::ReplicationConfig` は、レプリケーションの設定です。テーブルマッピングとタスクの設定は、上でテストしたオブジェクトをそのまま渡します。容量は最小 1 DCU、最大 2 DCU にしました。最大値は、1 時間に払ってもよい上限を決める数字でもあります。Multi-AZ は付けていません。CDC には Multi-AZ を勧めるとドキュメントにあるので、数日にわたる移行では有効にすることを考えてください。料金は 2 倍です。

最後に、失敗を知らせる経路です。

<<< @/examples/39-database-migration/infra/lib/migration-stack.ts{failure}

ロググループは、このスタックに入っていません。DMS Serverless のログは `dms-serverless-replication-<設定のリソース ID>` という名前のロググループに出ますが、作るのは DMS で、作られるのはレプリケーションを初めて動かしたときです。スタックの外にあるので、スタックを消しても残ります。保持期間がどう設定されるかは確かめていません。動かした後に見て、必要なら自分で設定します。

## 切り替え

<!-- section: 39.cutover -->

切り替えは、次の順に進めます。

1. full load が終わり、溜まっていた変更の適用も終わって、CDC が追いついているのを確かめる
2. ターゲットに足りないインデックスや制約がないことを確かめる
3. アプリの書き込みを止め、ソースを読み取り専用にする
4. 残りの変更がターゲットに届くのを待つ
5. 件数と中身を比べ、データ検証の状態を見る
6. レプリケーションを止める
7. ターゲットのシーケンスを進める
8. アプリの接続先をターゲットに替え、書き込みを再開する
9. 決めた期間、ソースを読み取り専用のまま残す

書き込みを止めずに両方へ書く（dual write）やり方もありますが、この章では採りません。2 つのデータベースへの書き込みは 1 つのトランザクションにならないので、片方だけ成功した書き込みをどう直すかという、別の問題を抱えることになるからです。

### 遅れの読み方

CDC の遅れは、2 つのメトリクスで読みます。`CDCLatencySource` は、ソースから最後に読んだ変更の時刻と現在との差で、読むほうの遅れです。`CDCLatencyTarget` は、ターゲットへの反映を待っているいちばん古い変更の時刻と現在との差で、書くほうの遅れです。ターゲットのほうだけが大きいときは、ターゲットのインデックスが足りないか、ターゲットかレプリケーションの資源が足りていません。

`CDCLatencySource` は、ソースに新しい変更がないときにも 0 になります。0 という値だけでは「追いついた」のか「読めていない」のかが区別できないので、テーブルごとの統計で、適用された件数が増えていることを合わせて見ます。

書き込みを止めてよいか、接続先を替えてよいかの判断は、集めた数字を受け取る純粋な関数にしました。

<<< @/examples/39-database-migration/src/cutover.ts{freeze}

書き込みを止めた瞬間から、利用者にとっては停止が始まります。止めた時点の遅れは、停止時間の下限です。遅れが 10 分あるときに止めれば、少なくとも 10 分は待つことになります。この関数は上限の秒数を引数で受け取ります。何秒にするかは測った値ではなく、決める値です。たとえば「停止は 5 分まで」と決めたなら、確認と切り替えの作業に 4 分を残して、遅れが 60 秒以下のときだけ止める、という決め方になります。

メトリクスにデータがないときは「遅れなし」ではなく「不明」として扱い、止めません。

<<< @/examples/39-database-migration/src/cutover.ts{switch}

接続先を替える判断は、すべての項目が確かめられていることを求めます。DMS が検証できなかったテーブル（主キーがない、検証が無効）は、自分で比べた結果があるときだけ通します。何も確かめていないテーブルを、問題なしとは数えません。

### 件数と中身を比べる

DMS のデータ検証とは別に、自分でも比べます。

<<< @/examples/39-database-migration/src/verify.ts{compare}

テーブルごとに、行を JSON にしてハッシュを取り、ハッシュを並べ替えてもう一度ハッシュを取ります。件数だけの比較では、本文が切り詰められた行を見逃しますが、この比較は見つけます。

この比較が見ないものも、テストにしてあります。インデックスと制約は見ません。それらを落としたターゲットでも、行は一致します。そのため、名前で突き合わせる別の関数（`missingSecondaryObjects`）を用意しました。シーケンスの状態も見ません。次の節の衝突は、すべてのテーブルが一致した後で起きます。そして、ソースとターゲットを別々に読むので、書き込みが続いている間は、まだ届いていないだけの変更を「不一致」と報告します。書き込みを止めてから比べるのは、このためです。大きなテーブルを丸ごと読むので、本番の大きなデータベースでは、DMS のデータ検証を主にして、この比較は小さなテーブルや検証できないテーブルに使います。

### シーケンスを進める

`note_revisions` の `id` は、データベースが番号を振ります。行は番号ごと運ばれますが、ターゲットのシーケンスは一度も使われていません。接続先を替えた直後の最初の `INSERT` は 1 番を取ろうとして、運ばれてきた行とぶつかります。

<<< @/examples/39-database-migration/src/sequences.ts{plan}

### 戻り道

切り替えた後に問題が見つかったとき、ソースに戻れるかどうかは、切り替えてからターゲットに書かれたデータをどうするかで決まります。

この章の手順では、切り替えの後、ソースには何も書かれません。ソースは切り替えの時点の正しい写しのまま残ります。戻るとは、ターゲットに書かれた分を捨ててソースに接続先を戻すことです。切り替えから時間がたつほど、捨てるデータが増えます。

そこで、戻る判断の期限を先に決めておきます。たとえば「切り替えから 1 時間は、エラー率とシーケンスの衝突を見て、戻すかどうかを決める。1 時間を過ぎたら戻さず、前へ直す」という決め方です。この 1 時間も、決める数字です。期限を過ぎた後のソースは、戻り先ではなく、[22章](/ja/chapters/22-recovery.md)の意味でのバックアップです。残す期間を決め、最後のスナップショットを取ってから消します。

ターゲットへ書かれた分を捨てずに戻りたいなら、逆向きのレプリケーションをあらかじめ用意することになります。その構成は、この章では作っていません。

## 分散システムとして見る

<!-- section: 39.distributed -->

移行の間、データベースは 2 つあり、どちらも自分が最新だと思っています。どちらが正なのかを決めるのは、データベースではなく手順です。

<<< @/examples/39-database-migration/src/cutover.ts{phases}

`replicating` の間は、正はソースです。ターゲットは遅れた写しで、誰もそこへは書きません。`frozen` と `verified` の間は、どちらにも書けません。この間に、遅れた写しが正確な写しになります。`switched` からは、正はターゲットです。書き込みを受けるデータベースが 2 つになる段階はありません。

守りたい不変条件は、切り替えをまたいで、応答を返した書き込みが 1 つも失われず、1 つも二重に適用されないことです。

この条件は、いくつかの決まった順序で壊れます。テストは、この章のモデルの上でその順序を作ります。

ソースへの遅れた書き込み。切り替えの後も、古い接続先を持ったままのインスタンスが 1 つ残っていて、ソースに書きます。ソースが書き込みを受け付ければ、アプリは成功を返し、その行はどこにも運ばれません。テストは、ソースを読み取り専用にしてあれば同じ書き込みが SQLSTATE 25006 で失敗することも確かめます。失敗した書き込みは応答を返していないので、不変条件は守られます。アプリの設定を替えるだけでは足りず、ソースの側で断らせる必要があります。

切り替え後のレプリケーションの再開。ターゲットでアプリが行を更新した後に、誰かがレプリケーションを古い位置から再開すると、ソースの古い更新がもう一度適用され、ターゲットの新しい書き込みが上書きされます。テストはこの上書きを再現します。レプリケーションを止めてから接続先を替える順序と、切り替えた後は再開しないこと（できれば設定ごと消すこと）が、これを防ぎます。

再開による二重適用。レプリケーションが、適用はしたがどこまで適用したかを記録する前に止まると、再開のときに同じ変更をもう一度適用します。主キーのあるテーブルなら、同じ `INSERT` は重複として退けられ、同じ `UPDATE` は同じ値を書くだけなので、結果は変わりません。主キーのないテーブルでは、行が 2 つになります。テストは両方を見せます。

アプリの側が受け止めることも、ここから決まります。`frozen` の間、書き込みは失敗します。アプリは、失敗を利用者に伝えるか、再試行するかを選びます。再試行するなら、[08章](/ja/chapters/08-async.md)で扱ったように、同じ書き込みが 2 回届いても結果が変わらない作りになっている必要があります。接続先を替える瞬間には、開いていた接続が切れます。切り替えをまたぐトランザクションは存在できないので、長いトランザクションを持つ処理は、切り替えの前に止めます。
