# 32 Limits: 手元で動かす

## 手元で動かす

<!-- section: 32.local -->

[ここまでのページ](/ja/chapters/32-limits/build.md)で作った 2 つの制限を、AWS を使わずに手元で動かします。`examples/32-limits/.env.example` を `.env` にコピーして、起動します。

<<< @/examples/32-limits/.env.example

```bash
vp run dev:limits
```

<<< @/examples/32-limits/src/dev.ts{dev}

リクエストは、AWS で通るのと同じ順に 2 つの制限を通ります。先に全員で 1 つのバケット、次に呼び出し元ごとの窓です。呼び出し元ごとのカウンターはプロセスのメモリに置いています。開発サーバーはプロセスが 1 つなので、これで正しく数えられます。Lambda では実行環境ごとに別のカウンターになってしまうので、関数には入れていません。AWS で呼び出し元ごとに数えるには、14章のようにカウンターを外のストアに置きます。

別のターミナルから、30 件を続けて送ってみます。

```bash
for i in $(seq 1 30); do curl -s -o /dev/null -w '%{http_code} ' http://localhost:8787/health; done; echo
```

最初の 20 件ほどは 200 で、そのあとに 429 が混ざります。`curl -i` で 1 件だけ送ると、429 に `retry-after` が付いているかどうかで、どちらの制限に断られたかがわかります。

テストは次のコマンドで動かします。

```bash
vp run test:unit
```

## 手元で負荷をかける

<!-- section: 32.load -->

負荷試験の目的は、どの上限に最初に当たるかと、そのとき何が返るかを知ることです。この章の負荷生成スクリプトは、手元の開発サーバーにだけ送ります。

<<< @/examples/32-limits/src/load.ts{target}

送り先は、スクリプトが 1 バイトも送る前に検査します。`localhost` で始まる別のホスト名や、`localhost@example.com` のような書き方も断ることを、テストで確かめています。デプロイした API の URL を渡しても動きません。理由は、このページの最後の「実環境に負荷をかける前に」に書きました。

リクエストを送る時刻は、始める前にすべて決めます。

「前の返事が来たら次を送る」作りにすると、サーバーが遅くなったときに、送る側も一緒に遅くなります。負荷が勝手に下がるので、サーバーがいちばん苦しい時間の応答が記録に残りません。時刻を先に決めておけば、返事が遅れても次のリクエストは予定どおりに出ます。

集計では、断られたリクエストを応答時間に入れません。

<<< @/examples/32-limits/src/load.ts{summary}

429 は速く返ります。混ぜて平均やパーセンタイルを出すと、ほとんどを断っているサーバーほど速く見えてしまいます。また、`retry-after` の付いた 429 は別に数えます。どの制限が断ったのかが、最初に知りたいことだからです。

開発サーバーを起動したまま、別のターミナルで実行します。

```bash
vp run limits:load
```

```text
target http://localhost:8787/health, 5 s at each rate

req/s   sent   p50 ms   p95 ms   max ms   answers
5       25     1.6      4.1      45.3     200: 25
10      50     1.3      2.4      3.0      200: 37, 429 retry-after: 13
20      100    1.2      4.0      9.9      200: 27, 429: 31, 429 retry-after: 42
40      200    1.4      3.5      13.0     200: 39, 429: 131, 429 retry-after: 30

The first limit shows at 10 requests a second.
```

これは著者の端末での出力で、ポート番号だけ既定の値に書き直してあります。応答時間は、端末と、そのとき動いているほかのプロセスで変わります。

最初に当たったのは、全員で毎秒 10 件のバケットではなく、呼び出し元ごとの制限でした。負荷を送っているのが 1 つのアドレスなので、10 秒に 50 件の窓を、毎秒 10 件の流量が先に使い切ります。`retry-after` の付いた 429 がそれです。毎秒 20 件にすると、バケットの 429 も混ざり始めます。

1 台の端末から負荷をかけると、呼び出し元ごとの制限のほうが先に効くことは、実環境でもよくあります。入口のスロットリングを確かめたつもりで、WAF のレートベースのルールや自分のレート制限を測っていた、ということが起こりえます。

呼び出し元ごとの制限を事実上外すと、バケットが見えます。

```bash
CALLER_LIMIT=100000 vp run dev:limits
```

```text
target http://localhost:8787/health, 5 s at each rate

req/s   sent   p50 ms   p95 ms   max ms   answers
5       25     1.9      4.9      44.7     200: 25
10      50     1.2      1.9      2.8      200: 50
20      100    1.3      1.8      2.1      200: 69, 429: 31
40      200    1.1      2.4      4.3      200: 69, 429: 131

The first limit shows at 20 requests a second.
```

毎秒 10 件までは全部通り、毎秒 20 件では 100 件のうち 69 件が通りました。バーストの 20 件に、5 秒ぶんの 50 件を足した数とほぼ同じです。毎秒 40 件でも、通る数は変わりません。流量を増やしても通る数が増えなくなったところが上限です。

### 手元の負荷試験でわからないこと

手元で確かめられるのは、断り方と、クライアントの振る舞いです。次のことはわかりません。

- 応答時間。相手は同じ端末の Node.js のプロセスで、メモリの中の Map を読んでいるだけです。ネットワークも、Lambda のコールドスタートも、DynamoDB もありません。表の数ミリ秒は、AWS での数字の手がかりになりません
- Lambda の同時実行数。開発サーバーは 1 つのプロセスがすべてを受けます。同時実行数の上限も、実行環境が増える速さの上限（10 秒ごとに 1,000）も、手元にはありません
- テーブルのスロットリング。メモリのストアは断りません。SDK の再試行が実際に働く場面は、手元では偽のハンドラーに対してしか作れません
- API Gateway の実際の数え方。代役のバケットは正確に数えますが、実物は best-effort です
- 送る側の限界。この負荷生成スクリプトは、1 つのプロセスが `fetch` を並べているだけです。流量を上げていくと、先に詰まるのはスクリプトのほうで、そのことは出力からはわかりません。スクリプトが受け付ける流量を毎秒 500 件までにしてあるのは、そのためです

### 実環境に負荷をかける前に

デプロイした API に負荷をかける場合は、先に AWS のポリシーを読みます。2026 年 10 月 12 日に読んだ内容は次のとおりです。

EC2 のテストポリシーは、EC2 のインスタンスから大量の通信を送る試験についてのもので、ネットワークのストレステストを次のように定義しています。

```text
In these guidelines we consider a "network stress test" to be when a test sends a large volume
of legitimate or test traffic to a specific intended target application. The endpoint and
infrastructure are expected to be able to handle this traffic, and this traffic meets their
network stress testing policy.
```

相手や基盤を意図して溢れさせようとする試験は、ストレステストではなく DDoS のテストとして扱われ、EC2 からの大量の通信による DDoS の模擬は禁止されています。試験の相手が AWS の中にあるなら、同じリージョンに置くように、ともあります。

ペネトレーションテストのポリシーは、禁止する行為の中に、次の 1 行を挙げています。

```text
Request flooding (login request flooding, API request flooding)
```

2 つのページからわかるのは、受けきれるはずの量を送って性能を測る試験と、溢れさせることを狙った試験が区別されていることです。上限を探すために流量を上げていく試験は、やり方によっては後者に近づきます。

わからなかったこともあります。EC2 のページには、流量の閾値も、事前の申請の手順も書かれていませんでした。AWS の外にある端末から自分の API に負荷をかける場合に、何が要るのかも、どちらのページからも読み取れませんでした。実環境で試験をする前に、2 つのページを読み直し、判断がつかなければ AWS Support に計画を伝えて確かめてください。この章では、実環境への負荷試験はしていません。

実環境で試験をするなら、費用にも気をつけます。断られた 429 のリクエストに API Gateway の料金がかかるかどうかは、19章と同じく、確かめられていません。通ったリクエストは、Lambda、DynamoDB、ログのすべてで、ふつうに課金されます。
