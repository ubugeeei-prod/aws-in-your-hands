# 32 Limits: しくみと実装

[前のページ](/ja/chapters/32-limits.md)では、上限がどこにあるかと、クォータの調べ方を見ました。このページでは、断る側の数え方、断られた側の待ち方、再試行が障害を大きくする仕組みとその抑え方、自分で置く歯止めを、順に実装します。

## 断る側の数え方

<!-- section: 32.bucket -->

API Gateway のドキュメントによると、スロットリングはトークンバケット（token bucket）で数えています。バケットには一定の速さでトークンがたまり、リクエスト 1 件がトークンを 1 つ使います。トークンが無ければ、そのリクエストは断られます。設定する値は 2 つで、たまる速さがレート、バケットに入る数の上限がバーストです。

<<< @/examples/32-limits/src/token-bucket.ts{bucket}

レートは、いつまでも続けられる速さを決めます。バーストは、静かな時間のあとに一度に受けられる数を決めます。レート 10、バースト 20 なら、しばらく誰も呼ばなかったあとの 20 件は同時に通り、そこからは 1 秒に 10 件ずつしか通りません。テストでは、50 件を同時に送ると 20 件だけが通ること、その後 3 秒間に毎秒 100 件を送っても通るのは 30 件であること、何時間待ってもバーストより多くはたまらないことを確かめています。

トークンは 1,000 分の 1 の単位の整数で持っています。小数のまま足していくと、0.1 を 10 回足しても 1 にならず、通るはずの 1 件が断られるからです。

この関数は、API Gateway の中身ではありません。同じ数え方を、手元で動く形に書いたものです。ドキュメントには、スロットリングは best-effort で適用され、保証された上限ではなく目標として考えるように、とあります。実物は、設定した値を少し超えて通すことがあります。

開発サーバーでは、この関数をステージのスロットリングの代役として、アプリの前に置きます。

<<< @/examples/32-limits/src/throttle.ts{stage}

バケットは全員で 1 つです。誰が呼んだかを見ないので、1 人が使い切れば、ほかの全員が 429 を受け取ります。テストでは、あるアドレスが 50 件送ったあとで、別のアドレスの 1 件目が断られることを確かめています。

429 のボディは、このファイルが決めたものです。API Gateway が実際に何を返すか、`Retry-After` ヘッダーを付けるかどうかは、ドキュメントからは読み取れませんでした。代役は、ヘッダーを付けていません。

呼び出し元ごとの制限は、14章のレート制限をそのまま使います。

<<< @/examples/32-limits/src/throttle.ts{caller}

14章のレート制限は窓を数えているので、次にいつ通るかがわかり、それを `retry-after` で返せます。2 種類の 429 は、このヘッダーの有無で見分けられます。

## 断られた側の待ち方

<!-- section: 32.retry -->

429 は、失敗ではなく返事です。「いまは受けられないので、あとで来てほしい」と言われています。呼び出す側が決めることは、もう一度送ってよいか、どれだけ待つか、何回で諦めるかの 3 つです。

まず、送り直してよいかどうかです。

<<< @/examples/32-limits/src/retry.ts{retryable}

429 は、仕事を始める前に断られた返事なので、メソッドが何であっても送り直せます。503 や 504 はそうではありません。処理は済んでいて、返事だけが届かなかったのかもしれないからです。`POST /notes` を 503 のあとで送り直すと、ノートが 2 件できることがあります。そこで、502、503、504 を送り直すのは、繰り返しても結果が変わらないメソッドだけにしています。500 は送り直しません。このアプリの 500 は、待っても直らない不具合を表すことが多いからです。

「429 なら何もしていない」は、この章のスタックでは成り立ちます。ステージのスロットリングも、14章のレート制限も、アプリの手前で断るからです。よそのサービスの 429 がそうであるかは、そのサービスのドキュメントで確かめてください。

次に、待つ時間です。

<<< @/examples/32-limits/src/backoff.ts{backoff}

待つ時間の上限を、再試行のたびに 2 倍にします。これが指数バックオフ（exponential backoff）です。相手が立ち直るのに時間がかかるほど、送る間隔が自然に開いていきます。上限には頭打ち（`capMs`）を付けます。

`jitter` は、待つ時間に乱数を混ぜるかどうかです。`"full"` なら、0 から上限までのどこかで待ちます。なぜ混ぜるのかは、次の節のシミュレーションを見るとわかります。AWS の SDK も、同じ式で待ち時間を決めています。

サーバーが `Retry-After` で待つ時間を伝えてきたら、そちらを下限にします。

<<< @/examples/32-limits/src/retry.ts{retry-after}

ヘッダーの値は外から来る文字列なので、秒数か HTTP の日付の形だけを受け付けます。`Date.parse` に任せると、`-1` のような値まで日付として読んでしまいます。

全体をまとめると、次のようになります。

<<< @/examples/32-limits/src/retry.ts{send}

待つ時間は、自分のバックオフとサーバーの指示の、長いほうです。空きがいつ戻るかを知っているのはサーバーのほうだからです。ただし、指示が `maxWaitMs` より長ければ、待たずに諦めて、断られた返事をそのまま返します。1 時間待てと言われて、そのとおりに待つ呼び出しは、利用者から見れば固まっているのと同じです。

`sleep`、`random`、`now` は引数で受け取ります。テストでは、待つ代わりに時計を進め、乱数を 0.5 に固定して、待った時間をそのまま検査しています。開発サーバーと同じ構成に対しては、バケットが空のときに `POST /notes` を送っても、再試行のあとでノートがちょうど 1 件できること、呼び出し元ごとの制限に当たったときは `retry-after` の 10 秒を待ってから通ることを確かめています。バックオフだけなら 50 ミリ秒で送り直して、もう一度断られていたところです。

## 再試行が障害を大きくする

<!-- section: 32.storm -->

再試行は、呼び出す 1 件にとっては得です。全員が同じことをすると、話が変わります。相手が受けきれないから断っているのに、断られた全員がもう一度送れば、相手に届く量は増えます。Amazon Builders' Library の記事は、再試行を「利己的」と呼んでいます。サーバーの容量を余計に使って、自分の成功率を上げる行為だからです。

この様子を、手元で再現します。ネットワークは使わず、時刻を 10 ミリ秒刻みで進めるだけの模型です。

<<< @/examples/32-limits/src/simulation.ts{scenario}

呼び出しは、成功するまで再試行します。サービスは、前の節と同じトークンバケットで受け付け、入りきらないぶんをすぐに断ります。乱数は種を固定してあるので、何度動かしても同じ数字になります。

<<< @/examples/32-limits/src/random.ts{seeded}

場面は 2 つ用意しました。

<<< @/examples/32-limits/src/simulation.ts{scenarios}

```bash
vp run limits:simulate
```

```text
1,000 callers start at once; the service lets 200 a second through (burst 100)

                      sent        succeeded   gave up     peak retries in 10 ms
jitter: none          6060        640         360         900
jitter: full          5635        988         12          130

500 calls a second; the service refuses everything for 3 seconds

                      sent        in outage   held back   gave up
no retry budget       7968        4388        0           1420
retry budget          5100        1600        1464        1500

First attempts in those 3 seconds: 1500. Everything above that is retries.
```

### 同時に始めた 1,000 件

1 つ目の場面は、1,000 件の呼び出しが同じ瞬間に始まります。サービスが復旧した直後や、毎時 0 分に動くジョブで起きる形です。サービスが通すのは毎秒 200 件で、最初の 100 件だけがバーストで通ります。

ジッターが無いと、断られた 900 件は、全員が同じ 100 ミリ秒を待って、同じ 10 ミリ秒の中に戻ってきます。その瞬間に通れるのは、たまっていた 20 件ほどです。残りはまた同じ時間を待ち、また一緒に戻ります。待つ時間は 2 倍ずつ延びますが、集団はばらけません。8 回試しても通れなかった 360 件が、失敗で終わります。

ジッターを入れると、同じ 900 件が待ち時間の幅いっぱいに散らばります。10 ミリ秒の中に戻ってくるのは最大でも 130 件で、988 件が成功します。サービスが見たリクエストの数も、6,060 件から 5,635 件に減りました。変えたのは `jitter` の 1 か所だけで、サービスの容量も、試行回数も、待ち時間の上限も同じです。

### 3 秒間すべて断るサービス

2 つ目の場面は、毎秒 500 件の呼び出しがふだんは余裕で通っているところに、3 秒間だけ、サービスがすべてを断ります。呼び出しは 3 回まで試します。

再試行に歯止めが無いと、その 3 秒間にサービスへ届くリクエストは、最初の試行の 1,500 件に対して 4,388 件になります。3 倍近い量です。立ち直ろうとしているサービスに、ふだんの 3 倍を浴びせていることになります。呼び出しの経路が何段も重なっていれば、段ごとに倍率が掛かります。Builders' Library の記事には、5 段の経路でそれぞれが 3 回再試行すると、いちばん下の負荷が 243 倍になる例が載っています。この増え方をリトライストーム（retry storm）と呼びます。

抑える方法が、再試行の予算です。

<<< @/examples/32-limits/src/retry-budget.ts{budget}

予算は、1 つのクライアントが出すすべての呼び出しで共有します。再試行のたびにトークンを払い、成功すると少し戻ります。失敗が続けば尽きて、それ以降は再試行をせず、最初の失敗をそのまま返します。予算が止めるのは再試行だけで、最初の試行は止めません。

シミュレーションで使った数字は、AWS の SDK が持っているものと同じで、容量が 500、再試行 1 回が 5、最初の試行で成功すると 1 戻ります。この予算があると、障害の 3 秒間に届くのは 1,600 件です。最初の 100 回の再試行で予算が尽き、あとは最初の試行だけになります。

予算には代償もあります。失敗で終わった呼び出しは、予算なしの 1,420 件に対して 1,500 件でした。差の 80 件は、障害の終わりぎわに始まり、再試行していれば復旧後に通っていたはずの呼び出しです。予算は、助からない再試行を止めるのと引き換えに、助かったかもしれない再試行も少し止めます。

この模型が教えてくれるのは、形だけです。実際のネットワークには遅延があり、断るのにもサーバーの資源を使い、クライアントは 1 つの予算を共有してはいません。数字そのものを、自分のサービスに当てはめないでください。

## SDK の再試行

<!-- section: 32.sdk -->

アプリが DynamoDB を呼ぶところでは、これらの仕組みを自分で書く必要はありません。AWS SDK for JavaScript が、バックオフも、ジッターも、予算も持っているからです。必要なのは、何が既定で、どこを自分で決めるかを知っておくことです。

<<< @/examples/32-limits/src/sdk-retry.ts{sdk}

上の 2 つは、この本が固定している版（`@aws-sdk/client-dynamodb` 3.1149.0 と、その中の `@smithy/util-retry` 4.6.2）のソースで読んだ値です。再試行のモードは `standard`、試行は最初の 1 回を含めて 3 回、スロットリングのときの待ち時間は 500 ミリ秒を基準にした full jitter、予算は 500 です。テストは、この定数をパッケージが export している定数と比べています。

3 つ目は、AWS が 2026 年の新しい再試行の動作として公開しているものです。SDK のリファレンスによると、この動作は既定になるまで `AWS_NEW_RETRIES_2026=true` を環境変数に設定して選ぶもので、スロットリングのときの基準が 1,000 ミリ秒に、DynamoDB のクライアントの既定の試行回数が 4 回になります。導入済みの版のソースにも、この環境変数を読む箇所があります。

既定が変わる予定の値に頼りたくないので、この章のクライアントには回数とモードを書いておきます。

<<< @/examples/32-limits/src/sdk-retry.ts{table-client}

<<< @/examples/32-limits/src/compose.ts{repository}

05章のリポジトリのコードは変えていません。渡すクライアントを、この章で作っているだけです。

SDK が本当に 3 回試行するかは、テストで数えました。クライアントの `requestHandler` を、DynamoDB がスロットリングのときに返すのと同じ形の応答（HTTP 400 と `ProvisionedThroughputExceededException`）を返すだけの偽物に差し替えています。プロセスの外には何も出ません。スロットリングなら偽物が 3 回呼ばれ、`ValidationException` なら 1 回で終わることを確かめています。本物の DynamoDB がスロットリングしたときの挙動は、確かめていません。

モードには `adaptive` もあります。スロットリングを受けると、クライアントの側で送る速さを落とすモードです。リファレンスは、1 つのリソースだけを相手にするクライアント向けだとし、一般の既定には勧めていません。1 つのテーブルでスロットリングが起きると、同じクライアントから出るほかの呼び出しまで遅くなるからです。

### タイムアウトとのつり合い

再試行は時間を使います。関数のタイムアウトは、再試行が終わるより長くなければなりません。そうでないと、SDK が 3 回目を送る前に関数が打ち切られます。

<<< @/examples/32-limits/src/backoff.ts{worst-case}

3 回の試行のあいだに待つ時間は、いちばん長くて、いまの動作で 1.5 秒、2026 年の動作で 3 秒です。関数のタイムアウトは 10 秒にしてあり、HTTP API の統合のタイムアウトの 30 秒より短くなっています。試行を 4 回にすると、2026 年の動作では待ち時間だけで最大 7 秒になり、10 秒では心もとなくなります。回数を書いておいた理由がこれで、スタックのテストがこの関係を見張っています。

SDK の再試行が尽きると、例外はアプリまで上がってきます。05章のアプリは例外を 500 にするので、テーブルがスロットリングしていると、利用者には 500 が返ります。呼び出し元から見れば、不具合なのか、待てば通るのかの区別がつきません。「本番にするなら」で、この点に戻ります。

## 自分で置く歯止め

<!-- section: 32.brakes -->

クォータは AWS を守るための枠なので、自分の請求や、後ろにある自分のデータベースを守るには大きすぎます。そこで、手前に自分の上限を置きます。

入口の上限は、ステージのスロットリングです。

<<< @/examples/32-limits/infra/lib/limits-stack.ts{throttle}

04章から付けてきた設定に、ルートごとの値を 1 つ足しました。ノートを作る `POST /notes` だけは、毎秒 2 件、バースト 4 件です。書き込みは読み取りより高くつき、テーブルの上限にも先に当たるので、入口で絞っておきます。

`routeSettings` は、CloudFormation では型のない JSON です。CDK の型もそこで終わるので、プロパティの名前は API Gateway の綴りのまま書いています。ステージに `DependsOn` を足したのは、まだ無いルートを名指しするとステージの作成が失敗する、と考えているからです。この組み合わせを cdkd が正しく反映するかは、まだ動かして確かめていません。

HTTP API には、REST API にある使用量プラン（usage plan）と API キーがありません。API キーごとにスロットリングと期間あたりの上限を付けるこの機能は、REST API のものです。そして公式ドキュメントは、使用量プランのスロットリングと上限は厳密な上限ではなく、費用の制御やアクセスの遮断をこれに頼らないように、と書いています。呼び出し元ごとの制限が要るなら、14章のように自分で数えるか、21章の AWS WAF を使います。

関数の上限は、予約済み同時実行数です。

<<< @/examples/32-limits/infra/lib/limits-stack.ts{function}

予約済み同時実行数は、上限と取り分を兼ねています。5 を指定すると、この関数は同時に 5 つまでしか動かず、アカウントのほかの関数は、その 5 を使えなくなります。設定に料金はかかりません。0 にすると、関数は 1 件も処理しなくなります。障害のときに関数を止める、いちばん手早いスイッチです。

既定では付けていません。[前のページ](/ja/chapters/32-limits.md)で見たとおり、アカウントは 100 を予約せずに残す必要があり、新しいアカウントにはその余裕が無いことがあるからです。付けるときは `-c reservedConcurrency=5` を渡します。

テーブルの上限は、05章と同じ `maxReadRequestUnits` と `maxWriteRequestUnits` です。オンデマンドのテーブルには、既定で毎秒 40,000 unit までという大きなクォータしかないので、その手前に自分の値を置いています。

Lambda が関数を断ったことは、アラームで知ります。

<<< @/examples/32-limits/infra/lib/limits-stack.ts{alarm}

`Throttles` が増えるのは、予約した数を使い切ったときか、アカウント全体の同時実行数を使い切ったときです。後者なら、原因は別の関数かもしれません。19章が症状にだけアラームを付けたのに対して、このアラームは原因の側にあります。歯止めが効いたこと自体を知りたいので、あえて付けました。通知先は、19章のスタックのトピックを `-c alarmTopicArn=` で渡します。渡さなければ、アラームはコンソールに出るだけで、誰にも届きません。

Lambda が関数を断ったとき、HTTP API が呼び出し元に何のステータスを返すかは、確かめていません。

## 最初に当たる上限

<!-- section: 32.first-limit -->

上限が何段もあると、どれが最初に効くのかがわかりにくくなります。そこで、すべてを「毎秒何件のリクエストで断り始めるか」に直して並べます。

<<< @/examples/32-limits/src/ceilings.ts{ceilings}

同時実行数を流量に直す式は、Lambda のドキュメントのものです。必要な同時実行数は、1 秒あたりのリクエスト数に、1 件にかかる秒数を掛けた値になります。逆に言うと、同時実行数が 5 で 1 件に 2 秒かかるなら、受けられるのは毎秒 2.5 件です。もう 1 つ、実行環境 1 つが受けられるのは毎秒 10 件まで、という決まりがあります。どれほど速い関数でも、同時実行数が 5 なら毎秒 50 件で頭打ちです。

この章のスタックを既定値のまま計算すると、最初に効くのはステージの毎秒 10 件で、次がテーブルの読み取りの毎秒 150 件です。テストでは、条件を変えたときに順番が入れ替わることも確かめています。ステージの値を上げればテーブルが先に効き、1 件が遅ければ同時実行数が先に効きます。

Lambda のドキュメントは、既定値どうしの食い違いを例に挙げています。API Gateway は毎秒 10,000 件まで受けますが、Lambda の同時実行数は 1,000 です。1 件に 0.5 秒かかる関数なら、受けられるのは毎秒 2,000 件で、入口が通した残りは Lambda が断ります。ドキュメントは、どのクォータが制限になるかを本番の前に負荷試験で見つけるように勧めています。

この計算の入力は仮定です。1 件にかかる時間も、1 件が使う unit の数も、実測しなければわかりません。計算は当たりを付けるためのもので、確かめるには実際に流してみる必要があります。手元でできる範囲は、[次のページ](/ja/chapters/32-limits/local.md)で試します。
