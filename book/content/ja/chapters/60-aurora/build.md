# 60 Aurora: しくみと実装

[前のページ](/ja/chapters/60-aurora.md)で、フェイルオーバーのときにアプリがすることを 3 つ挙げました。このページでは、3 つ目の「結果のわからないトランザクション」を冪等性の鍵で解き、接続を落とすテストで確かめます。そのあと、Serverless v2 の容量、Data API、スタックの順に進みます。

## 不変条件と、1 回だけ適用する仕組み

<!-- section: 60.invariant -->

守りたいことを 1 文で書くと、こうなります。

> フェイルオーバーで中断されたトランザクションは、コミットされたか、丸ごとやり直されるかのどちらかで、半分だけ適用されることも、2 回適用されることもない。

前半の「半分だけ適用されない」は、データベースが守ります。接続が切れると、サーバーはコミットされていないトランザクションをロールバックします。後半の「2 回適用されない」は、アプリが守るしかありません。

13章の作成と更新は、たまたま 2 回実行しても安全な形をしていました。作成はノートの ID をトランザクションの外で決めていたので、やり直しても同じ 1 件になります。更新は期待するバージョンを指定するので、2 回目は条件に合わず何も書きません。この章では、そうなっていない操作を 1 つ足します。ノートの本文の末尾に文字を足す、追記です。

<<< @/examples/60-aurora/src/append.ts{append}

追記のリクエストには、どのバージョンに足すのかが入っていません。2 回実行すれば 2 回足されます。カウンターを 1 増やす、残高から引く、といった操作も同じ形をしています。

`CAST($2 AS uuid)` のように型を SQL の側に書いているのは、あとで出てくる Data API でも同じ文を使うためです。文字列で渡したパラメーターがどの型として扱われるかはドライバーによって違いうるので、それに頼らず、列の型に合わせる変換を文に書いておきます。

### リクエストを記録するテーブル

やり直してよいかどうかを知るには、前の試行がコミットされたかどうかを、あとから確かめられなければなりません。そこで、適用したリクエストを 1 行ずつ記録するテーブルを用意します。

<<< @/examples/60-aurora/migrations/0005_create_requests.sql

`key` が冪等性の鍵です。クライアントが、利用者の 1 回の操作ごとに 1 つ作って送ります。応答が返らずにクライアントが送り直すときは、同じ鍵を付けます。鍵は持ち主ごとに区別するので、他人の鍵を当てても、その人の結果は読めません。

このマイグレーションは、13章の 4 つのあとに番号を続けています。13章の lint（1 ファイルに 1 文、`IF NOT EXISTS` を付ける）もそのまま通ります。

### トランザクションの入口

再試行する側は、データベースへの入口を 1 つの型で受け取ります。1 回の試行、つまり、始めて、本体を実行して、コミットするまでです。

<<< @/examples/60-aurora/src/once.ts{port}

13章の `Db`（PGlite と node-postgres）をこの形にするのが `transactional` です。13章は Aurora DSQL に合わせて `REPEATABLE READ` を指定していましたが、ここでは PostgreSQL の既定の `READ COMMITTED` のままにしています。Data API 用の実装は、あとの節で書きます。

### 1 回だけ適用する

<<< @/examples/60-aurora/src/once.ts{once}

やっていることは 3 つです。

1. トランザクションの最初に、鍵を探します。見つかれば、前の試行がコミットされていたということなので、本体を実行せずに、記録してあった結果を返します
2. 見つからなければ本体を実行し、その結果を鍵と一緒に、**同じトランザクションの中で**書き込みます
3. 途中で答えのないまま終わったら、最初からやり直します

2 が要です。追記と鍵の記録は 1 つのトランザクションなので、両方入るか、両方入らないかのどちらかです。そのため、鍵があるかどうかを見るだけで、追記が入ったかどうかがわかります。鍵を別のトランザクションや別のデータストアに書くと、この関係が崩れます。

記録するのは「適用した」という印ではなく、結果そのものです。やり直しの試行は、ノートがいまどうなっているかではなく、最初の試行が何と答えるはずだったかを返します。あいだに別の追記が入っていても、クライアントが受け取る答えは変わりません。保存した結果は、データベースの行と同じく型の外から来る値なので、読み出すときにスキーマで確かめます。

`INSERT ... ON CONFLICT DO NOTHING` が行を返さなかった場合は、同じ鍵の別のリクエストが、自分より先にコミットしたということです。自分の本体はすでに実行してしまっているので、例外を投げてロールバックし、やり直します。次の試行は、手順 1 で相手の結果を見つけます。

何回やり直しても答えが得られなければ、`AttemptsExhaustedError` を投げます。この例外の意味は「失敗した」ではなく「結果がわからない」です。クライアントは同じ鍵でもう一度送れば、適用済みならその結果を、まだなら新しく適用した結果を受け取ります。

鍵は、クライアントが送り直す可能性のある期間だけ残っていれば足ります。古い行は消します。

<<< @/examples/60-aurora/src/once.ts{purge}

## 接続を落とすテスト

<!-- section: 60.faults -->

不変条件は、壊そうとして確かめます。手元のデータベースは、13章と同じ PGlite です。PGlite はプロセスの中の PostgreSQL で、フェイルオーバーも、複数の接続もありません。そこで、接続が切れたときにクライアントから見えることを、次の包みで再現します。

<<< @/examples/60-aurora/test/support.ts{drop}

落とし方は 2 通りあります。`before` は、文がサーバーに届く前に切れた場合です。`after` は、文は実行されたのに、答えが届く前に切れた場合です。どちらの場合も、サーバーはコミットされていないものをロールバックし、クライアントは `ConnectionLostError` だけを受け取ります。`COMMIT` を `after` で落とすと、変更は入っているのに、クライアントにはそれがわからない、という状況になります。

再現しているのは、クライアントから見た順序だけです。本物のフェイルオーバーで node-postgres がどんなエラーを返すか、切れるまでに何秒かかるかは、この包みからはわかりません。

追記は、何も起きなければ 5 つの文になります。`BEGIN`、鍵を探す `SELECT`、追記の `UPDATE`、鍵を書く `INSERT`、`COMMIT` です。この 5 つのそれぞれの前と後、合わせて 10 か所で接続を落とします。

<<< @/examples/60-aurora/test/once.test.ts{every-point}

どこで落ちても、呼び出した側は何も起きなかったときと同じ答えを受け取り、ノートには 1 回だけ追記されています。

鍵がなければどうなるかも、テストにしてあります。

<<< @/examples/60-aurora/test/once.test.ts{naive}

<<< @/examples/60-aurora/test/once.test.ts{twice}

`COMMIT` の答えが失われたあと、同じ追記をもう一度実行しているので、本文は `abb` になります。呼び出した側が受け取るのは 2 回目の結果で、2 回足されたことには気づけません。

PGlite ではできないことが 1 つあります。同じ鍵の 2 つのリクエストが、別々の接続で同時に走る場合です。PGlite のセッションは 1 本なので、この場合は「`INSERT` が行を返さなかった」という応答を台本で与えるテストにとどめています。実際の PostgreSQL で 2 本の接続を使って確かめることは、していません。

テストは次のコマンドで実行します。

```bash
vp test run examples/60-aurora
```

## Serverless v2 の容量

<!-- section: 60.serverless -->

Aurora のインスタンスには、大きさを決めて借りる provisioned と、負荷に合わせて大きさが変わる Serverless v2 があります。1 つのクラスターに両方を混ぜることもできます。この章のインスタンスは Serverless v2 で、インスタンスクラスは `db.serverless` です。AWS のいまのドキュメントはこの機能を Aurora serverless と呼んでいて、Serverless v1 は別の設計の、非推奨になった製品です。

容量の単位は ACU（Aurora capacity unit）です。1 ACU はおよそ 2 GiB のメモリーと、それに見合う CPU とネットワークです。クラスターに最小と最大を設定すると、各インスタンスがその範囲で 0.5 ACU 刻みで伸び縮みします。範囲は 0 から 256 ACU で、料金は実際に使った ACU に時間をかけたものです。

伸び縮みは、接続が開いていても、トランザクションの途中でも起き、実行中の処理を止めません。伸びる速さはそのときの容量で決まり、大きいほど速く伸びます。小さい最小容量から急に大きな負荷を受けると、追いつくまでに時間がかかります。最小を 0 か 0.5 ACU にした PostgreSQL では、`max_connections` の上限も 2,000 に抑えられます。

設定は、スタックのコンテキストで受け取り、サービスが断る値を synth の前に断ります。

<<< @/examples/60-aurora/src/config.ts{config}

### 0 まで縮む

最小を 0 ACU にすると、利用者の接続が一定の時間なかったときにインスタンスが止まります。これを auto-pause と呼びます。待つ時間は 300 秒から 86,400 秒のあいだで、既定は 300 秒です。Aurora PostgreSQL では 13.15、14.12、15.7、16.3 以降で使えます。止まっているあいだ、インスタンスの料金は 0 で、ストレージの料金は残ります。

止まったインスタンスは、次の接続で再開します。再開にはふつう 15 秒ほどかかり、24 時間を超えて止まっていた場合は 30 秒以上かかることがあります。再開した直後の容量は、止まる前の容量にかかわらず小さいところから始まります。

止まらない条件は、料金に直結するので覚えておく価値があります。

- 利用者の接続が 1 本でも開いている。何も実行していなくても同じです
- RDS Proxy を付けている。proxy が接続を持ち続けます
- 論理レプリケーション、zero-ETL、Global Database を使っている

Aurora は保守のためにインスタンスを再開することがあり、そのあとは少なくとも 20 分は止めません。「1 か月ずっと止まっていた」は、いちばん都合のよい場合です。

接続プールを使うアプリは、この性質とぶつかります。プールが接続を持ち続けるかぎり、インスタンスは止まりません。VPC の中から node-postgres でつなぐための adapter では、使っていない接続を 10 秒で閉じ、接続のタイムアウトを再開にかかる時間より長くしています。

<<< @/examples/60-aurora/src/pg.ts{pool}

`keepAlive` は、フェイルオーバーのための設定です。相手のインスタンスが消えると、TCP の接続は切れたことに気づかないまま待ち続けることがあります。AWS のドキュメントは、keepalive を短くしてこれを早く検出するよう勧めています（OS の設定として、最初の確認まで 1 秒、間隔 1 秒、5 回）。node-postgres で指定できるのは、最初の確認までの時間だけです。

この adapter は型検査を通しただけで、実際のクラスターにつないだことはありません。この章のスタックには VPC の中で動くものがなく、手元からは次の節の Data API を使うからです。

## Data API

<!-- section: 60.data-api -->

Data API は、Aurora に HTTPS で SQL を送る API です。呼び出す側は接続を持たず、データベースのパスワードも知りません。IAM が「このクラスターにこの API を呼んでよいか」と「このシークレットを読んでよいか」を決め、Data API が Secrets Manager から認証情報を取り出して、自分の持っている接続で SQL を実行します。

VPC の外にある Lambda 関数や手元のマシンから、プライベートサブネットのクラスターに届くのは、このためです。Lambda 関数を VPC に入れる設定も、接続プールも、RDS Proxy も要りません。接続を持たないので、auto-pause を妨げることもありません。

向かない場面もはっきりしています。2026-10-13 に読んだドキュメントでは、次の制限があります。

- 実行されるのは writer だけです。読み取りを reader に逃がせません
- 1 回の呼び出しは、既定で 45 秒で打ち切られます。レスポンスは 1 MiB まで、結果の 1 行は 64 KB までです
- トランザクションは、ID を使う呼び出しが 3 分なければ自動でロールバックされ、長くても 24 時間です
- 1 回の呼び出しに書ける文は 1 つです
- T 系のインスタンスクラスでは使えません
- 文ごとに HTTPS の往復が 1 回あり、リクエストの数に課金されます（東京で 100 万件あたり USD 0.42）

東京リージョンでは、Aurora PostgreSQL の 13.11、14.8、15.3、16.1、17.4 以降で、Serverless v2 と provisioned の両方に使えます。

まとめると、Data API が合うのは、呼び出しが多くなく、1 回の処理が短く、呼ぶ側を VPC に入れたくない場合です。Lambda 関数から時々書く、管理用のスクリプトから触る、といった使い方がこれに当たります。リクエストごとに何本もクエリを投げる API や、reader を使いたい読み取りの多いアプリは、VPC の中から接続したほうが向いています。

### SDK に再試行させない

Data API のクライアントは、1 つだけ既定と違う設定で作ります。

<<< @/examples/60-aurora/src/data-api.ts{client}

AWS SDK は、応答が返らなかった呼び出しを、既定では自分で送り直します。トランザクションの中でこれが起きると、最初の呼び出しが実は届いていた場合、同じ文が 1 つのトランザクションの中で 2 回実行されます。追記は 2 回足され、そのままコミットされます。鍵は 1 つのトランザクションに 1 回しか書かれないので、この重複は鍵では防げません。

AWS のドキュメントも、SDK がタイムアウトを返したのに操作は完了していた場合、再試行が重複したデータを作りうること、SDK が自動で再試行することがあると書いています。そこで SDK の再試行を止め、やり直しはすべて、トランザクションを最初から始め直す `createOnce` に任せます。

### adapter

13章の SQL は `$1` の形のパラメーターを使っています。Data API は名前付きのパラメーターなので、書き換えます。

<<< @/examples/60-aurora/src/data-api.ts{parameters}

受け付ける値は、文字列、数値、真偽値、`null` だけです。日付や UUID は文字列で渡し、型は SQL の `CAST` で決めます。Data API には `typeHint` という、文字列をタイムスタンプや UUID として送る指定もありますが、使うと SQL がドライバーごとに違ってしまうので使っていません。

結果は、列の値の配列と、列のメタデータに分かれて返ります。これを、node-postgres と同じ、列名をキーにした行に直します。

<<< @/examples/60-aurora/src/data-api.ts{rows}

結果を 1 つの JSON 文字列で受け取る `formatRecordsAs` という指定もあります。ただし、固定した版の SDK の型定義によると、これが効くのは `SELECT` だけです。追記は `UPDATE ... RETURNING` の行を読むので、こちらの形を使っています。

エラーは、フェイルオーバーのページで作った分類に合わせて仕分けます。

<<< @/examples/60-aurora/src/data-api.ts{errors}

`DatabaseResumingException` は、止まっていたインスタンスが再開している最中だという応答で、auto-pause を使うなら扱えるようにしておきます。`TransactionNotFoundException` は、トランザクションがもう存在しないという応答で、3 分のタイムアウトのほか、writer が入れ替わった場合にも起きると考えられます。どちらも「この試行は終わらなかった」として扱います。

接続する場合と違うところが 1 つあります。`DatabaseErrorException` には SQLSTATE を持つメンバーがないので、デッドロックや serialization failure を、ほかの SQL のエラーと見分けられません。この経路では、競合は再試行されず、エラーとして呼び出し側に返ります。

<<< @/examples/60-aurora/src/data-api.ts{adapter}

`transaction` の形は、前の節の `transactional` と同じです。違いは、`BEGIN` と `COMMIT` が SQL の文ではなく API の呼び出しになっていることだけです。

## スタック

<!-- section: 60.stack -->

スタックは 4 つのリソースでできています。固定している版の CDK には `rds.DatabaseCluster` という高水準のコンストラクトもありますが、クラスターとインスタンスが別のリソースであることを見せたいので、CloudFormation のリソースをそのまま表す `Cfn` のコンストラクトで書きました。

<<< @/examples/60-aurora/infra/lib/aurora-stack.ts{network}

サブネットグループは、インスタンスを置いてよいサブネットの一覧です。11章の VPC のプライベートサブネットを、スタックの出力のインポートで受け取ります。ストレージが 3 つの AZ にあることは、ここに何を書いても変わりません。

セキュリティグループには、インバウンドのルールを 1 つも書いていません。VPC の中からつなぐクライアントを足すときは、そのクライアントのスタックが、このグループに自分用のルールを足します。Data API がこのグループのルールなしで届くことは、ドキュメントの「VPC に入れずに使える」という説明から読んだもので、実際には確かめていません。

<<< @/examples/60-aurora/infra/lib/aurora-stack.ts{cluster}

クラスターの定義に、インスタンスの大きさはありません。あるのは、エンジンと版、置き場所、暗号化、認証情報の扱い、そして Serverless v2 の容量の範囲です。

`manageMasterUserPassword` を指定すると、Aurora がパスワードを作って Secrets Manager に置き、既定では 7 日ごとに回します。テンプレートにパスワードは現れません。シークレットの回し方そのものは 59章と [21章](/ja/chapters/21-security.md)が扱います。この章のスクリプトは、このシークレットの ARN を Data API に渡します。本番では、アプリ用に権限を絞ったデータベースユーザーと、そのシークレットを別に作ります。管理者の認証情報でアプリを動かすのは、練習のあいだだけにしてください。

エンジンの版は `17.9` を既定にしました。リリースノートに 2026 年 4 月の版として載っていて、Serverless v2、Data API、auto-pause のどの条件も満たします。ただし、今日の東京リージョンでこの版の新しいクラスターを作れるかどうかは、確かめていません。作れない場合は `-c engineVersion=` で別の版を指定します。

<<< @/examples/60-aurora/infra/lib/aurora-stack.ts{writer}

インスタンスは、クラスターを指す別のリソースです。reader を足すには、同じリソースをもう 1 つ書きます。最初の 1 台が writer になります。

練習用なので、削除保護を切り、スタックと一緒に消えるようにしました。最後のスナップショットも取りません。本番では逆にします。

テンプレートは次のコマンドで作れます。AWS には問い合わせません。

```bash
vp run aurora:infra:synth
```
