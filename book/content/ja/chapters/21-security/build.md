報告するのは次の 6 つです。

- アクションのワイルドカード（`s3:*`、`s3:Get*`、`*`）
- リソースが `"*"` そのもの
- `Allow` と `NotAction` の組み合わせ（「これ以外はすべて許可」になる）
- `Allow` と `NotResource` の組み合わせ
- 広い AWS 管理ポリシー（`AdministratorAccess`、`PowerUserAccess`、`〜FullAccess`）
- 条件なしで誰でも引き受けられる信頼ポリシー

これに加えて、読めなかったポリシーを合格にせず、`unreadable` として報告します。知らない形のポリシーを「問題なし」と判定しないためです。

テンプレートを読むところにも、同じ考え方を入れています。

<<< @/examples/21-security/src/json-object.ts{json-object}

Valibot の `v.object` と `v.record` は、配列もオブジェクトとして受け取ります。そのままでは、`[]` を渡されたときに「リソースが 1 つも無いテンプレート」として合格にしてしまいます。また `v.record` は、`__proto__`、`prototype`、`constructor` という名前のキーを、エラーにせずに結果から外します。`constructor` は論理 ID として有効な名前なので、その名前のロールだけが調べられずに通ることになります。そこで、配列は断り、キーは `Object.entries` ですべて取り出してから調べます。

`Deny` のステートメントは調べません。`Deny` に書かれた `*` は、たいてい意図したものだからです。

1 つ目に、応答をスキーマで確かめています。SDK の型は `SecretString?: string` としか言っておらず、中身が JSON であることも、`key` があることも保証しないからです。

鍵の長さは、文字の数で数えています。`v.minLength` が数えるのは UTF-16 の単位なので、絵文字 16 個が 32 として通ってしまうからです。

2 つ目に、一度もローテーションしていないシークレットには `AWSPREVIOUS` が無いので、そのときは `null` を返します。このときのエラー名を `ResourceNotFoundException` としているのは、API リファレンスと SDK の型からの想定で、実機では確かめていません。想定が違っていた場合は、例外がそのまま上がって鍵の読み込みが失敗します。黙って先に進むことはありません。

3 つ目に、権限が無いときは専用のエラーにします。「Secrets Manager が落ちている」ときと「読む権限が無い」ときとでは、対処が違うからです。このエラーは、[実装のつづき](/ja/chapters/21-security/more.md)で IAM の変更が行き渡るまでの待ちを扱うときに使います。

## キャッシュとローテーションのあいだ

<!-- section: 21.keyring -->

リクエストのたびに Secrets Manager を呼ぶと、遅くなり、料金もかかります（API 呼び出し 1 万回で USD 0.05）。AWS も、値を呼び出す側でキャッシュするよう勧めています。

ただ、公式のキャッシュ用の部品は Java、Python、.NET、Go、Rust 用で、JavaScript 用は挙がっていません。Lambda 向けには、Parameters and Secrets Lambda Extension と Powertools for AWS Lambda があります。この章では、キャッシュしたときに何が起きるかを見たいので、小さなキャッシュを自分で書きました。本番で自作を勧めているわけではありません。

<<< @/examples/21-security/src/keyring.ts{keyring}

キャッシュを持つと、分散システムの問題が 1 つ生まれます。Lambda の実行環境はそれぞれ自分のキャッシュを持っていて、読み込んだ時刻もばらばらです。この状態でシークレットを入れ替えると、次の図のようになります。

```figure
caption: シークレットを入れ替えると、キャッシュを読み込んだ時刻が違う 2 つの実行環境が、しばらく別々の鍵で署名する
type: sequence
actor sm: Secrets Manager
actor a: 実行環境 A
actor b: 実行環境 B
note sm: t0: v1 = AWSCURRENT
note a: v1 をキャッシュ
note b: v1 をキャッシュ
step sm -> sm: t1: rotate, v2 = AWSCURRENT
note sm: v1 = AWSPREVIOUS
note a: まだ v1 で署名
note b: まだ v1 で署名
step a -> sm: t2: キャッシュが切れて読み直す
note a: v2 で署名
step a -> b: t3: v2 で署名したトークン
step b -> sm: キャッシュに v2 がないので読み直す
note b: 受け入れる
step b -> a: t4: v1 で署名したトークン
note a: v1 = AWSPREVIOUS なので受け入れる
step b -> sm: t5: キャッシュが切れて読み直す
note b: v2 で署名
```

t1 から t5 のあいだは、2 つの鍵が同時に使われています。どちらの鍵で署名したトークンも、どちらの実行環境でも検証を通らなければなりません。守りたい不変条件は、次の 1 文です。

**期限内のトークンは、ローテーションの前に発行されたものも後に発行されたものも、どの実行環境でも検証を通る。**

この条件を守るために、3 つのことをしています。

1 つ目に、どのバージョンの鍵で署名したかをトークンに入れます。

<<< @/examples/21-security/src/token.ts{sign}

2 つ目に、検証する側は `AWSCURRENT` と `AWSPREVIOUS` の両方を持ちます。図の t4 で、A が古い鍵のトークンを通せるのはこのためです。

3 つ目に、知らないバージョン id を見たら読み直します。図の t3 の B がそうです。ここには危険があります。バージョン id はトークンの一部なので、誰でも好きな文字列を送れます。でたらめな id が届くたびに Secrets Manager を呼んでいると、攻撃者が請求額を好きなだけ増やせることになります。そこで、読み直しには最短の間隔（30 秒）を設けました。

<<< @/examples/21-security/src/app.ts{check}

「知らないバージョン」と「署名が違う」には、同じ応答を返します。どのバージョンが存在するかを、外から探れないようにするためです。

テストは、1 つの時計と 1 つのシークレットを複数の実行環境で共有する形で書いてあります。図の t3 と t4 は、そのままテストになっています。ほかに、次の場面も再現しています。

- でたらめなバージョン id を 1000 回送っても、Secrets Manager への読み取りは増えない。30 秒たつと、1 回だけ読み直す
- 50 個のリクエストが同時に来ても、読み込みは 1 回
- Secrets Manager が応答しなくなっても、持っている鍵で検証を続ける。失敗した読み込みを、リクエストのたびに繰り返さない
- 一度も鍵を読めていない実行環境は、エラーにする。このとき API は 503 を返す

不変条件をわざと壊すテストも 1 つあります。ローテーションを 2 回続けると、最初の鍵は `AWSPREVIOUS` からも外れ、その鍵で署名したトークンは期限内でも通らなくなります。これはキャッシュの側では防げないので、次の節で、ローテーションの手順の側で防ぎます。

## ローテーションの手順

<!-- section: 21.rotation -->

このシークレットは自分で決めて自分で使う鍵なので、データベースのパスワードと違って、相手側の設定を変える必要がありません。ローテーションは、新しい値を書くだけで済みます。

`PutSecretValue` は、ステージングラベルを指定せずに呼ぶと、新しいバージョンに `AWSCURRENT` を付け、それまで `AWSCURRENT` だったバージョンに `AWSPREVIOUS` を付け直します。2 つの実行環境の図の t1 が、API 1 回で起きるわけです。

<<< @/examples/21-security/src/secrets-manager-source.ts{rotation-adapter}

重要なのは `ClientRequestToken` です。API リファレンスによると、この値が新しいバージョンの id になり、同じトークンと同じ値でもう一度呼んでも、何も起きずに成功します。値が違えば失敗します。

この性質を使うと、途中で止まってももう一度実行すれば済む手順にできます。

<<< @/examples/21-security/src/rotation.ts{rotate}

このコードがしていることを、順に説明します。

最初に、いまのラベルを読みます。`AWSCURRENT` がすでに今回のバージョン id になっていれば、前回の実行は成功していて、応答だけが失われたということなので、何もしません。ここで確かめずに書き込むと、新しい id で 2 回目のローテーションが走り、前の節で見た「2 回続けると壊れる」状態を自分で作ってしまいます。

次に、前回のローテーションからの時間を見ます。トークンの有効期間（5 分）とキャッシュの期間（5 分）を足した 10 分が過ぎるまでは、次のローテーションを断ります。鍵が漏れたときは待っていられないので、`--force` を付ければ断られずに実行できます。その場合、期限内のトークンの一部が通らなくなります。

書いたあとで、もう一度ラベルを読みます。確かめるのは、呼び出しが成功を返したことではなく、ラベルが期待した位置にあることです。検証する側が見るのはラベルだからです。

```bash
vp run sec:secret:versions
vp run sec:secret:rotate
```

`rotate` は、最初に今回のバージョン id を表示します。応答が失われて失敗したら、`--version-id <表示された id>` を付けて再実行します。新しい鍵はスクリプトの中で作り、そのまま Secrets Manager に送ります。画面にもファイルにも出しません。

テストは、応答が失われる場面を決まった順序で再現します。書き込みを成功させてから例外を投げ、同じバージョン id で再実行して、書き込みが 1 回で、バージョンが 2 つのままであることを確かめます。

ローテーションの頻度にも上限があります。API リファレンスは、`PutSecretValue` を 10 分に 1 回より速いペースで呼び続けないよう書いています。Secrets Manager が残すバージョンは直近 100 個ですが、24 時間以内に作られたものは消さないので、速く呼びすぎるとバージョンの数が上限に届きます。

### 自動のローテーション

Secrets Manager には、決まった間隔で自動的にローテーションする仕組みもあります。Lambda 関数が、新しいバージョンを作る、相手のサービスに設定する、試す、ラベルを付け替える、という 4 段階を実行します。データベースのパスワードなら、こちらを使うのが本筋です。

この章では実装していません。入れ替える相手のサービスが無いので、4 段階のうち 2 つは空になるからです。加えて、ローテーション用の関数はシークレットを書ける権限を持つので、守る対象が 1 つ増えます。

## 鍵の持ち主

<!-- section: 21.kms -->

Secrets Manager は、シークレットを AWS KMS の鍵で暗号化して保存します。どの鍵を使うかは選べます。

何も指定しなければ、`aws/secretsmanager` という AWS マネージドキー（AWS managed key）が使われます。AWS があなたのアカウントの中に作り、管理する鍵で、月額はかかりません。KMS のドキュメントも、「鍵を自分で管理する必要が無いなら、AWS managed key は良い選択」と書いています。

`-c cmk=on` を付けると、自分で作る鍵であるカスタマーマネージドキー（customer managed key）に変わります。

<<< @/examples/21-security/infra/lib/security-stack.ts{key}

カスタマーマネージドキーにすると、鍵の扱いを自分で決められます。誰がこの鍵を使えるかをキーポリシーで決められますし、鍵を無効にすれば、シークレットを読む権限を持つ人も読めなくなります。別のアカウントに使わせることもできます。

代わりに、月 USD 1 がかかります。時間割りで、鍵を消すまで続きます。自動のローテーションを有効にしていると、1 回目と 2 回目のローテーションのたびに月 USD 1 ずつ増え、3 年目からは月 USD 3 で止まります。

関数の権限も 1 つ増えます。カスタマーマネージドキーで暗号化したシークレットを読むには、その鍵で復号する権限が要るからです。[最初のページの「権限を絞る」](/ja/chapters/21-security.md)に載せたロールのコードでは、`kms:Decrypt` に `kms:ViaService` という条件が付いています。「Secrets Manager 経由でだけ使える」という意味の条件で、関数がこの鍵を直接呼んで別のものを復号することはできません。

カスタマーマネージドキーには、気づきにくい副作用もあります。Inspector のドキュメントによると、Inspector は、カスタマーマネージドキーで暗号化された Lambda 関数を検査しません。この章の関数は環境変数を暗号化する鍵を指定していないので当てはまりませんが、「鍵はすべて自分で持つ」という方針にすると、別の守りが 1 つ外れることがあります。

消し方も、ほかのリソースとは違います。KMS の鍵はすぐには消えず、7 日から 30 日の待機期間があります。待機期間のあいだ鍵は使えず、削除を取り消せば元に戻ります。こうなっているのは、鍵が消えると、その鍵で暗号化したデータを二度と読めなくなるからです。固定した版の cdkd は、テンプレートに指定した日数（この章は 7 日）で削除を予約します。

個人のアカウントなら、AWS マネージドキーで十分です。カスタマーマネージドキーが要るのは、誰が復号できるかをシークレットの権限とは別に管理したいとき、監査で鍵の管理を求められるとき、アカウントをまたいで共有するときです。
