# 21 Security: 実装のつづき

[前のページ](/ja/chapters/21-security/build.md)では、関数とシークレットの側を作りました。このページでは、入口の WAF と、IAM の変更が行き渡るまでの遅れを扱い、そのあとで、この章のスタックには入れていない検出のサービスと Organizations を説明します。

## WAF を付けられる入口、付けられない入口

<!-- section: 21.waf -->

AWS WAF は、リクエストがアプリに届く前に検査して、条件に合うものを止めるサービスです。設定の単位を web ACL と呼びます。

web ACL は、どの入口にでも付けられるわけではありません。公式ドキュメントが挙げているのは、次のリソースです（確認日 2026-10-12）。

- CloudFront のディストリビューション
- API Gateway の REST API
- Application Load Balancer
- AppSync の GraphQL API、Cognito のユーザープール、App Runner のサービス、Bedrock AgentCore Gateway、Verified Access のインスタンス、Amplify

この本で使ってきた入口のうち、API Gateway の HTTP API（04章）と Lambda の関数 URL（09章、17章）は、この一覧にありません。付けたければ、手前に CloudFront を置いて、CloudFront に付けます。この章の構成が CloudFront から始まっているのは、そのためです。

WAF が付かない入口にも、歯止めが無いわけではありません。04章からの HTTP API を使う章は、ステージのスロットリングで API 全体を毎秒 10 件に抑えています。料金はかかりません。ただし、この制限は全員をまとめた上限で、IP アドレスごとには分かれていません。関数 URL には、これにあたる設定がありません。

web ACL を CloudFront に付けただけでは足りません。裏の入口が開いていれば、CloudFront を通らずに入れるからです。

<<< @/examples/21-security/infra/lib/security-stack.ts{entry}

関数 URL の `AuthType` を `AWS_IAM` にして、CloudFront の origin access control に署名させます。09章と同じ形です。署名のないリクエストは、関数が動く前に Lambda が断ります。CloudFront を迂回する道が無いので、web ACL を迂回する道もありません。

HTTP API を CloudFront の裏に置く構成は、この本では実装も検証もしていません。試すなら、裏の入口をどう閉じるかを先に決めてください。

署名には制約もあります。CloudFront は署名を `Authorization` ヘッダーに入れるので、この API はトークンを `x-aih-token` という別のヘッダーで受け取ります。また、09章で説明したとおり、POST や PUT では、呼ぶ側が本文の SHA-256 をヘッダーに入れる必要があります。そこで、CloudFront が通すメソッドを GET と HEAD だけにしました。アプリが答えるのは GET だけで、HEAD には 404 を返します。

### web ACL

<<< @/examples/21-security/infra/lib/waf-stack.ts{web-acl}

CloudFront 用の web ACL は、ディストリビューションやオリジンがどこにあっても、us-east-1 に作ります。このスタックは、ほかのリージョンを指定すると synth で止まります。

ルールは 3 つです。

1 つ目はレートベースのルール（rate-based rule）で、1 つの IP アドレスからのリクエストが 5 分間に 300 回を超えたらブロックします。[14章](/ja/chapters/14-kv-cache.md)のレート制限とは、置く場所と目的が違います。14章のレート制限はアプリの中にあり、利用者に公平に配るためのものです。このルールはアプリの手前にあり、Lambda を呼ばせないためのものです。

正確さは期待できません。AWS WAF がレートを確かめる間隔は、CloudFormation のリファレンスには約 10 秒ごととありますが、AWS WAF の開発者ガイドは「頻繁に」としか書いていません（どちらも 2026-10-13 に確認）。開発者ガイドによると、制限がかかるのは設定した上限の「近く」で、ぴったり上限で止めることは保証されていません。上限を超えてからブロックが始まるまで、ふつうは 30 秒未満、長いと数分かかります。その間のリクエストは通ります。

2 つ目と 3 つ目は、AWS が保守しているマネージドルールグループ（managed rule group）です。評判の悪い IP アドレスの一覧と、よくある攻撃のパターンを集めた core rule set を使っています。

core rule set は、最初は `count` にしてあります。`count` はリクエストを止めず、止めるはずだった件数を数えるだけです。このルールグループには、8 KB を超える本文をブロックするルールなどが入っていて、正当なリクエストを止めることがあります。AWS も、本番のトラフィックに対して count で様子を見てから有効にするよう勧めています。ブロックに切り替えるには `-c wafCommonRules=block` を付けます。

### 付ける手順

スタックが 2 つのリージョンに分かれているので、2 段階でデプロイします。

```bash
vp run sec:waf:infra:deploy
vp run sec:infra:deploy -c webAclArn=<WebAclArn の出力>
```

web ACL の月額は、1 行目を実行した時点から始まります。ディストリビューションに付けていなくても同じです。

料金は、web ACL 1 つが月 USD 5、ルール 1 つが月 USD 1（マネージドルールグループは 1 つと数えます）、検査したリクエスト 100 万件ごとに USD 0.60 です。この章の構成では、リクエストが 0 でも月 USD 8.00、100 万件で USD 8.60 になります。Bot Control のような追加のルールグループは、別に月額とリクエスト料金がかかるので、入れていません。入っていないことは、テストでも固定しています。

外すときは逆の順です。先に `webAclArn` なしで `sec:infra:deploy` を実行してディストリビューションから外し、それから `sec:waf:infra:destroy` を実行します。

## IAM の変更が行き渡るまで

<!-- section: 21.iam-consistency -->

この章で扱う分散システムの問題は、IAM にあります。

IAM のドキュメントには、次の内容の一節があります。IAM は世界中のデータセンターのコンピューターを通じて使われるサービスなので、結果整合性（eventual consistency）と呼ばれる分散のモデルを使っている。変更がすべてのエンドポイントから見えるようになるまでには時間がかかる。キャッシュもあるので、古い情報が期限切れになるまで変更が見えないこともある。

そのため、ロールに権限を足した直後の呼び出しは拒否されることがあり、権限を消した直後の呼び出しは通ることがあります。どのくらいの時間そうなるのか、ドキュメントは数字を書いていません。この本でも計っていません。

AWS は 2 つのことを勧めています。IAM の変更を、止まっては困る処理の途中に入れないことと、変更が行き渡ったのを確かめてからその変更に頼ることです。

### 許可したあと

デプロイは、ロールを作って、すぐにそのロールで関数を動かします。変更の直後そのものなので、動作確認のスクリプトは、一度拒否されただけでは失敗にしません。

<<< @/examples/21-security/src/propagation.ts{until-allowed}

再試行するのは拒否だけです。ほかのエラーは待っても直らないので、すぐに上げます。回数にも上限があります。上限まで拒否され続けたら、原因は行き渡るまでの遅れではなく、ポリシーの書き間違いです。待てば直るものと待っても直らないものを、どこかで切り分ける必要があります。

関数の側は、ルーターの呼び出しを `try` で囲んでいて、リクエストの処理中にエラーが起きると、原因が何であっても 503 と `retry-after` を返します。シークレットを読む権限が無いときもその 1 つで、区別できるのはレスポンスのメッセージだけです。

<<< @/examples/21-security/src/app.ts{unavailable}

<<< @/examples/21-security/scripts/smoke.ts{wait-for-iam}

デプロイ直後に実際に 503 が返るのかどうかは、確かめていません。返らないかもしれません。返らなければ、この待ちは一度も使われず、害もありません。

### 取り消したあと

危険なのは、権限を取り消す側です。鍵が漏れたときやロールを乗っ取られたとき、人は権限を消し、一度試して、拒否されたのを見て安心します。

<<< @/examples/21-security/src/propagation.ts{until-denied}

1 回拒否されたことから分かるのは、その 1 回が、変更を知っているエンドポイントに届いたことだけです。この関数は、続けて何回か拒否されるまで、止まったと判定しません。テストは、拒否、許可、拒否、拒否、拒否という順序を再現して、最初の拒否で確認済みにしないことを確かめています。

それでも、分かるのは「数回続けて拒否された」ことまでです。本当に急ぐときは、権限を消すのに加えて、守っているもの自体を変えます。この章なら、`--force` を付けてシークレットをローテーションします。漏れた鍵が正しい鍵でなくなれば、IAM の変更がどこまで行き渡ったかを気にしなくて済みます。

この関数は、この章のタスクからは呼んでいません。試す手順は、[検証記録](/ja/reference/validation.md)の再開手順に書いてあります。

### 変更した時刻を CloudTrail で調べる

```bash
vp run sec:trail:iam
```

このタスクは、直近 24 時間の IAM への変更について、誰が、いつ、どの操作をしたかを一覧にします。デプロイしたあとなら、`CreateRole` や `PutRolePolicy` が並ぶはずです。

注意が 1 つあります。IAM はグローバルなサービスで、そのイベントは us-east-1 に記録されます。東京リージョンのイベント履歴（event history）を探しても、IAM の変更は出てきません。このタスクは、最初から us-east-1 を見に行きます。

また、一覧に出る時刻は API が呼ばれた時刻で、その変更がすべてのエンドポイントで効き始めた時刻ではありません。

## 検出と記録の 4 つのサービス

<!-- section: 21.detect -->

Inspector、GuardDuty、CloudTrail、AWS Config は、名前や説明が似ていて混同しやすいので、並べて比べます。

```text
service      question it answers                          looks at                               result
Inspector    does my code have known vulnerabilities?     Lambda packages, ECR images, EC2       findings per CVE
GuardDuty    is someone acting like an attacker?          CloudTrail events, VPC flow, DNS logs  findings per suspicious activity
CloudTrail   who called which API, and when?              every management API call              events, 90 days free
AWS Config   what did this resource look like last week?  resource configurations over time      configuration items
```

Inspector と GuardDuty はどちらか一方を選ぶものと思われがちですが、見ているものが違う別のサービスです。

Inspector は脆弱性を検査します。Lambda 関数に入っているパッケージ、ECR のコンテナイメージ、EC2 のインスタンスを調べて、既知の脆弱性（CVE）が無いかを見ます。攻撃が起きているかどうかは見ません。検査し直すのは、関数をデプロイしたときと、新しい CVE が公開されたときです。この本のように依存をバンドルして Lambda に載せる構成では、デプロイしたあとで見つかった脆弱性に気づく手段になります。

GuardDuty は脅威を検出します。CloudTrail のイベントや VPC の通信の記録を分析して、「漏れた認証情報が、知らない場所から使われている」「暗号通貨の採掘らしい通信がある」といった怪しい動きを見つけます。コードに穴があるかどうかは見ません。

CloudTrail は記録するだけで、判断はしません。イベント履歴は最初から有効で、管理イベント（management event）を 90 日ぶん、リージョンごとに持っています。無料です。90 日より長く残したいとき、S3 に置いて検索したいとき、Access Analyzer に読ませたいときは、証跡を作ります。管理イベントの 1 つ目のコピーを S3 に届けるぶんは無料で、かかるのは S3 の保存料金です。

AWS Config は、リソースの設定の履歴を記録します。「このセキュリティグループは、いつ、どう変わったか」に答えるサービスです。[02章](/ja/chapters/02-toolchain.md)のドリフト検出が調べるのは「いま、コードと違うか」で、Config が記録するのは「これまで、どう変わってきたか」です。記録する設定 1 件ごとに料金がかかります。

### スタックに入れていない理由

GuardDuty と Inspector は 2 段目に置きました。守るものができたら、入れる価値があります。それでもこの章の CDK に入れていないのは、次の 3 つの理由からです。

1 つ目に、どちらもアカウントとリージョンに 1 つの設定です。練習用のスタックを消したときに、一緒に無効になっては困ります。

2 つ目に、既定で有効になる範囲が広いからです。GuardDuty のドキュメントによると、初めて有効にすると、そのリージョンで使える保護プラン（protection plan）が既定ですべて有効になります。Inspector も、コンソールから有効にすると、すべての種類の検査が始まります。何が有効になったかは、画面で見ながら決めてください。

3 つ目に、料金は使ってみないと分からないからです。どちらにも無料の試用期間があり（GuardDuty は 30 日、Inspector は 15 日）、その間にコンソールが、このまま使い続けた場合の月額を見積もります。その数字を見てから決めるのが、いちばん確かです。

そのため、コンソールで有効にして、`vp run sec:posture` で確かめる手順にしています。01章の root ユーザーの MFA と同じ扱いです。固定した版の cdkd が GuardDuty の detector に専用の実装を持っていない、という事情もあります。

この節の内容は、ドキュメントを読んで書いたものです。どちらのサービスも有効にしておらず、検出結果（finding）がどんな形で出るのかも見ていません。

## 組織になったら

<!-- section: 21.organizations -->

1 人で 1 つのアカウントを使っているあいだは、ここまでの内容で足ります。人とアカウントが増えると、全員が正しく設定してくれることには頼れなくなります。

AWS Organizations は、複数のアカウントを 1 つの組織（organization）にまとめるサービスで、追加料金はかかりません。組織を作ったアカウントが管理アカウント（management account）になり、請求をまとめ、ほかのアカウント（メンバーアカウント）にポリシーを付けられるようになります。

20章で、「dev と prod を同じアカウントに置くかぎり、名前でしか分かれていない」と書きました。アカウントを分けて Organizations でまとめるのが、その次の段階です。

### SCP は、権限を与えない

SCP（service control policy）は、メンバーアカウントの IAM ユーザーとロールに許せる権限の上限を決めるポリシーです。見た目は IAM のポリシーとそっくりですが、働きが違います。

SCP は権限を与えません。上限を決めるだけです。

<<< @/examples/21-security/src/policy-model.ts{decide}

このコードは、IAM と SCP の組み合わせ方をテスト用に小さくモデルにしたもので、IAM の実際の評価ではありません。それでも、要点は次の 3 行に入っています。

- どこかに明示的な `Deny` があれば、拒否
- root から、途中の OU、アカウントまで、すべての階層の SCP が許していて
- かつ、本人の IAM ポリシーも許しているときだけ、許可

SCP を初めて使う人が事故を起こすのは、2 行目です。SCP を有効にすると、Organizations は `FullAWSAccess` という「すべて許可」の SCP を、すべての階層に付けます。これを外して `Deny` だけの SCP に付け替えると、許可する SCP が無くなり、そのアカウントでは何もできなくなります。テストに、その順序を入れてあります。

もう 1 つ注意があります。SCP は管理アカウントには効かず、サービスにリンクされたロール（service-linked role）にも効きません。管理アカウントでふだんの作業をしないのは、このためです。

4 つのステートメントは、どれも `Deny` です。`FullAWSAccess` を付けたまま、その上に重ねて使います。

テストは、この JSON をモデルに通して、次のことを確かめます。

- 管理者でも、`cloudtrail:StopLogging` や `organizations:LeaveOrganization` は拒否される

- IAM ポリシーを何も持たない人は、SCP がすべて許可でも、何もできない
- `Principal` を含むステートメントは、読み込みで落ちる（SCP は `Principal` を持てません）
- 空白を除いた長さが、SCP の上限の 10,240 文字より短い
- モデルが知らない条件を含むポリシーは、評価を断る。知らない条件を「真」として扱わない

### Organizations と SCP を CDK で作らない理由

Organizations と SCP は、この章のスタックに入っていません。タスクもありません。

組織を作る、アカウントを移す、SCP を付けるといった操作は、どれも実際のアカウントの構成を変えるもので、練習用のスタックのように消せば元どおりにはなりません。SCP を root に付けて間違えると、すべてのアカウントが止まります。AWS も、SCP を root にいきなり付けず、専用の OU を作って、アカウントを 1 つずつ入れて試すよう強く勧めています。

そのため、この章が用意するのは、ポリシーの JSON と、付ける前に確かめるテストまでです。どの組織のどの OU に付けるかを決めて実際に付けるのは、あなたの作業です。

モデルには限界があります。知っている条件は `aws:RequestedRegion` と `aws:PrincipalArn` の 2 つだけで、リソースの一致も見ていません。「テストが通った」は、「このモデルの範囲では、意図どおりに書けている」という意味です。実際の組織に付けて確かめてはいません。
