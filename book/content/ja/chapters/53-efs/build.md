# 53 EFS: しくみと実装

[前のページ](/ja/chapters/53-efs.md)では、S3、EBS、EFS の違いと料金を見ました。このページでは、ファイルシステムへの入口を作り、NFS が何を約束しているかを確かめてから、書き手が何人いても壊れないノートの書き方を実装して、関数にマウントします。

## マウントターゲットとアクセスポイント

<!-- section: 53.mount -->

EFS のファイルシステムは、作っただけではどこからも届きません。VPC の中に入口を作ります。入口は 2 段になっています。

**マウントターゲット**は、ネットワークの入口です。サブネットの中に IP アドレスを 1 つ持ち、そこで NFS を待ち受けます。AZ ごとに 1 つ作れて、クライアントは自分と同じ AZ のマウントターゲットにつなぎます。別の AZ のマウントターゲットにもつなげますが、AZ をまたぐデータ転送の料金がかかるので、使う AZ すべてに置くのが基本です。1 つのファイルシステムがマウントターゲットを持てる VPC は 1 つだけです。

セキュリティグループは、マウントターゲットに付きます。この章のスタックは 2 つのセキュリティグループを作り、互いを名指しします。関数から出られるのはマウントターゲットの 2049 番ポートだけで、マウントターゲットに入れるのは関数からの 2049 番ポートだけです。

`creationInfo` を省くと、EFS はディレクトリを作りません。ディレクトリが無いままマウントしようとすると失敗するので、3 つとも指定します。ユーザー ID を 0（root）にすると、`ClientRootAccess` の権限が別に要ります。この章では root を使いません。

1 つのファイルシステムを複数のアプリケーションで使うときは、アプリケーションごとにアクセスポイントを分けて、ディレクトリとユーザーを別にします。アクセスポイントは、既定で 1 つのファイルシステムに 10,000 個まで作れます。

Fargate と EC2 の欄は、ドキュメントから書きました。この章が実際に作るのは Lambda だけです。Fargate のタスクに付ける場合は [41章](/ja/chapters/41-fargate.md)のタスク定義にボリュームを足し、EC2 でマウントする場合は 23章のユーザーデータにマウントのコマンドを足します。

Lambda の「転送中の暗号化」について、いまのドキュメントのページには記述を見つけられませんでした。Lambda と EFS のあいだは TLS 1.2 で暗号化される、という文は、この機能が出たときの AWS の公式ブログ（2020 年 6 月）にあります。このスタックのポリシーは TLS を使わない接続を拒否するので、もしブログの記述がいまの動作と違っていれば、マウントが失敗します。デプロイして確かめてはいません。

## 性能、スループット、ストレージクラス

<!-- section: 53.modes -->

ファイルシステムを作るときに決めることは、ほかに 4 つあります。2026-10-13 時点のドキュメントにもとづいて、この章の選択と理由を書きます。

**ファイルシステムの種類。** Regional は、データを複数の AZ に冗長に持ちます。One Zone は 1 つの AZ にだけ持ち、保存の単価がおよそ半分（1 GB・1 か月 0.192）になりますが、その AZ が失われるとデータも失われることがあります。マウントターゲットも 1 つしか作れません。東京リージョンで One Zone を作れる AZ は、`apne1-az1` と `apne1-az4` の 2 つです。この章は Regional を使います。作り直せるデータ、たとえばビルドのキャッシュなら、One Zone が候補になります。

**パフォーマンスモード。** General Purpose と Max I/O があり、あとから変えられません。ドキュメントは、すべてのファイルシステムで General Purpose を使うよう勧めています。Max I/O は前の世代の方式で、1 回ごとの操作が遅く、Elastic スループットとも One Zone とも組み合わせられません。

**スループットモード。** 次の 3 つです。

- Elastic は、何も確保せず、読み書きしたバイト数に課金します。ドキュメントが勧める既定の方式です
- Provisioned は、スループットを MiBps で確保し、使わなくても毎月課金します。平均と最大の差が小さく、必要な量が分かっているとき向きです
- Bursting は、Standard に置いた量に比例してスループットが決まります。基準は 1 GiB あたり 50 KiBps で、どのファイルシステムにも最低 1 MiBps が与えられます。置いた量が少ないと、クレジットを使い切ったあとはこの最低の速さになります

この章は Elastic を使います。置く量が数百 KiB なので Bursting では基準が最低の 1 MiBps になり、Provisioned は使わない時間にも課金されるからです。Elastic の注意点は、上限がないことです。読み書きした分だけ請求が増えます。ドキュメントも、`MeteredIOBytes` のメトリクスを見張るよう勧めています。

**ストレージクラスとライフサイクル。** ファイルは Standard に書かれ、ライフサイクルのポリシーを付けると、一定の日数アクセスのないファイルが Infrequent Access（IA）や Archive に移ります。IA は保存の単価が Standard の 18 分の 1 ですが、読むたびにデータアクセスの料金がかかり、最初の 1 バイトが返るまでの時間も、Standard の 1 ミリ秒前後に対して数十ミリ秒になります。Archive は 90 日の最低保存期間があります。

この章のスタックは、ライフサイクルのポリシーを付けません。理由は、ファイルの大きさです。IA と Archive は、1 つのファイルを最低 128 KiB として課金します。ノートは 4 KiB に収まるので、単価から計算すると次のようになります。

```text
kept in Standard   (2 KiB + 4 KiB) x 0.36           = 2.16
moved to IA        2 KiB x 0.36 + 128 KiB x 0.02    = 3.28
```

数字は、KiB の量に GB あたりの単価をそのまま掛けた相対値で、金額ではありません。

小さなファイルは、IA に移すとかえって高くなります。同じ計算で、データが 4 KiB を超えるファイルからは、保存の料金は IA のほうが安くなります（読むときの料金は別にかかります）。数 MB 以上のファイルを長く置く用途なら、ライフサイクルを付ける意味があります。ドキュメントは、ライフサイクルの既定を 30 日で IA、90 日で Archive としています。小さなファイルを大量に置くファイルシステムをコンソールで作るときは、この設定を外すかどうかを考えてください。CloudFormation で `LifecyclePolicies` を書かずに作ったファイルシステムにポリシーが付かないことは、実機では確かめていません。

## NFS の約束

<!-- section: 53.semantics -->

EFS にマウントしたディレクトリは、手元のディスクのディレクトリと同じ API で読み書きできます。違うのは、同じファイルを別のマシンも開いていることと、操作のたびにネットワークを通ることです。ドキュメントと Linux の man ページから、当てにできることと、できないことを分けます。

当てにできることは 3 つあります。

1 つ目は、**close-to-open の整合性**です。EFS のドキュメントは、NFS のアプリケーションが期待する close-to-open の整合性を提供する、と書いています。あるクライアントがファイルを閉じたあとで、別のクライアントがそのファイルを開けば、書いた内容が見えます。Linux の NFS クライアントの man ページは、これを「開くときにサーバーに確かめ、閉じるときに変更を送る」動作として説明しています。

2 つ目は、**いつ耐久性が得られるか**です。Regional のファイルシステムへの書き込みは、アプリケーションが `fsync` を呼んだとき、またはファイルを閉じたときに、複数の AZ に保存されます。それより前は、クライアントのメモリにあるだけかもしれません。

3 つ目は、**rename が 1 回の操作であること**です。同じファイルシステムの中の `rename` は、移動先に同じ名前のファイルがあれば、それを 1 回の操作で置き換えます。ほかのプロセスから見て、名前が消えている瞬間はありません。

当てにできないことは 4 つあります。

- **開いたままのファイルの中身。** close-to-open が約束するのは、閉じたあとに開いた場合だけです。あるクライアントが書いている最中のファイルを別のクライアントが読むと、どこまで見えるかは決まっていません。クライアントは、ファイルの属性を数秒から数十秒キャッシュします（Linux の既定では、ファイルが 3〜60 秒、ディレクトリが 30〜60 秒）。Lambda がどのマウントオプションを使っているかは、読んだドキュメントには書かれていませんでした
- **ロック。** EFS のロックは、すべてアドバイザリロックです。ロックを取っていないプロセスの読み書きは止まりません。全員が同じ約束でロックを取るコードを書いたときにだけ働きます。1 つのファイルに掛けられるロックは、全クライアントを合わせて 512 個までです
- **追記。** `open(2)` の man ページには、NFS の上で複数のプロセスが同時に追記すると、ファイルが壊れることがあると書かれています。NFS には「末尾に書く」という操作がなく、クライアントの側でそれを代用しているためです。2 つの関数が同じログファイルに 1 行ずつ追記すると、行が重なったり、途中で切れたりすることがあります
- **失敗した rename の結果。** `rename(2)` の man ページには、NFS では rename が失敗を返しても、実際には rename されていることがある、と書かれています。応答が届かなかっただけかもしれないからです

EFS のドキュメントには、同期的に書き、追記ではない書き込みをするアプリケーションには、読み取りに read-after-write の整合性がある、という一文もあります。これがどのマウントオプションと API の組み合わせを指すのかは、読み切れませんでした。この章の設計は、close-to-open と rename だけに頼ります。
