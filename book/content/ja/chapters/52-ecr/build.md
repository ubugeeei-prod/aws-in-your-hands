# 52 ECR: しくみと実装

[前のページ](/ja/chapters/52-ecr.md)では、タグとダイジェストの違いと、タスク定義が指すイメージを動かさないための 2 つの直し方を見ました。このページでは、リポジトリの設定を 1 つずつ決めていきます。順番は、タグと暗号化とポリシー、ライフサイクルポリシー、脆弱性の検査、pull through cache、複製と別アカウントからの取得、CI からのプッシュです。最後に、手元で確かめる手順を書きます。

### タグの immutability と例外

タグの設定には 4 つの値があります。`MUTABLE` と `IMMUTABLE` に加えて、例外を付けられる `IMMUTABLE_WITH_EXCLUSION` と `MUTABLE_WITH_EXCLUSION` です。例外はフィルターで書き、フィルターの種類は `WILDCARD` の 1 つだけです。`*` を含められる文字列で、1 つのリポジトリに 5 個まで付けられます。

`IMMUTABLE_WITH_EXCLUSION` に `latest` というフィルターを付けると、「すべてのタグは付け替えられないが、`latest` だけは動かせる」リポジトリになります。`MUTABLE_WITH_EXCLUSION` に `v*` を付ければ、逆に「どのタグも動かせるが、`v` で始まるタグだけは固定」になります。テストでは、この読み方を次の関数にして確かめています。

フィルターの `*` が空の文字列にも一致するかどうかは、immutability のページには書かれていません。ライフサイクルポリシーのページには、`prod*` が `prod` に一致すると書かれているので、同じ規則だと仮定しました。

この章のリポジトリは、例外なしの `IMMUTABLE` です。`latest` を動かせるようにすると、前のページの壊れ方が `latest` についてそのまま戻ってきます。動くタグが欲しくなるのは、たいてい「いちばん新しいもの」を指したいときですが、それはタグではなく、デプロイの設定が持つべき情報です。

immutability が止めるのは、すでにあるタグへのプッシュだけです。イメージを消すことは止めません。消したあとで同じタグを付け直せるかどうかは、ドキュメントに記述が見つからず、試してもいません。どちらであっても困らないように、この章のプッシュ用のロールには、イメージを消す権限も、リポジトリの設定を変える権限も与えていません。

### 暗号化

何も指定しないと、ECR はイメージを S3 が管理する鍵（AES-256）で暗号化して保存します。追加の料金はかかりません。KMS の鍵を使うこともでき、その場合は AWS マネージドキーの `aws/ecr` か、同じリージョンにあるカスタマーマネージドキーを選びます。

暗号化の設定は、リポジトリを作るときに決まり、あとから変えられません。変えたくなったら、リポジトリを作り直してイメージを移すことになります。この章は既定のままにしました。KMS の鍵には料金がかかり（21章）、鍵に付いた grant を取り消すと、リポジトリのイメージを取得できなくなります。鍵を自分で持つ理由がはっきりしているときにだけ選ぶ設定です。

### リポジトリポリシーとレジストリポリシー

ECR には、リソースの側に付けるポリシーが 2 種類あります。

リポジトリポリシーは、1 つのリポジトリに付けます。既定では、リポジトリを作ったアカウントだけがアクセスできます。同じアカウントの中なら、IAM のポリシーかリポジトリポリシーのどちらかが許可していれば、操作は通ります。どちらかに明示の拒否があれば、通りません。この章のリポジトリにはリポジトリポリシーを付けていないので、誰が何をできるかは、IAM のポリシーだけで決まります。

レジストリポリシーは、アカウントのリージョンごとのレジストリ全体に付けます。複製の受け入れ、pull through cache、リポジトリの自動作成といった、レジストリの単位の操作を許可するためのものです。

どちらのポリシーでも許可できない操作が 1 つあります。レジストリにログインするための `ecr:GetAuthorizationToken` で、これは IAM のポリシーで許可する必要があります。

## ライフサイクルポリシー

<!-- section: 52.lifecycle -->

置いたままのイメージには、保存料金がかかり続けます。ライフサイクルポリシーは、消すイメージを選ぶ規則の集まりです。条件を満たしたイメージは 24 時間以内に消され、その操作は CloudTrail に記録されます。

ルール 1 つは、どのイメージを対象にするか、いくつ（何日）を超えたら消すか、の組です。対象は `tagStatus` で選びます。`tagged` はタグのパターン（`tagPatternList`）に一致するイメージ、`untagged` はタグの無いイメージ、`any` はすべてのイメージです。超えたかどうかの数え方は、`imageCountMoreThan`（新しいほうから数えて、指定した数より後ろ）と `sinceImagePushed`（プッシュから指定した日数より古い）を使います。ほかに、最後の取得からの日数で数える `sinceImagePulled` と、アーカイブ用のストレージへ移す `transition` がありますが、この章では使いません。

### ルールが評価される順序

複数のルールがあるとき、どのルールがどのイメージを消すかは、直感と少し違います。ドキュメントの評価規則のうち、結果を左右するのは次の 3 つです。

- すべてのルールは、優先度に関係なく、同時に評価される。そのあとで、`rulePriority` の小さい順に適用される
- 1 つのイメージを消すのは、多くても 1 つのルールである
- あるルールのタグの条件に一致したイメージは、それより優先度の低いルールには消されない。ただし、優先度の低いルールは、そのイメージを数には入れる

3 つ目が要点です。この章のポリシーでは、リリースのタグが付いたイメージはルール 1 のもので、ルール 3 はそれを消せません。しかし、ルール 3 が「新しいほうから 30 個」を数えるときには、リリースのイメージも 30 個のうちに入ります。直近の 30 個のうち半分がリリースなら、リリースでないビルドで残るのは 15 個です。「ルール 3 がリリース以外を 30 個残す」と読むと、残る数を見誤ります。

## 脆弱性の検査

<!-- section: 52.scan -->

ECR の検査には 2 種類あり、レジストリごとにどちらかを選びます。

basic scanning は、ECR 自身が OS のパッケージの脆弱性を調べます。検査のタイミングは、プッシュのときか、手動で始めたときです。1 つのイメージを検査できるのは 24 時間に 1 回までで、プッシュのときの検査もこの 1 回に数えます。ECR からの追加料金は、料金のページにも Price List にも見当たりませんでした。

enhanced scanning は、Amazon Inspector（21章）が検査します。OS に加えて、言語のパッケージ（この本なら npm のパッケージ）も調べます。タイミングは、プッシュのときだけにするか、継続的にするかを、リポジトリのフィルターで選びます。継続的な検査では、新しい脆弱性が公表されるたびに、すでにあるイメージが検査し直されます。料金は Inspector のもので、東京リージョンでは最初の検査が 1 イメージ USD 0.11、検査し直しが 1 回 USD 0.01 です。

2 つの違いは、時間の扱いに出ます。プッシュのときの検査は、その時点で知られていた脆弱性しか見つけません。3 か月前にプッシュして、いまも本番で動いているイメージに、先週見つかった脆弱性があるかどうかは、検査し直さなければ分かりません。basic scanning では手動で検査し直すことになり、enhanced scanning の継続的な検査では Inspector が受け持ちます。

この章のリポジトリは、`imageScanOnPush: true` で、basic scanning をプッシュのときに走らせます。この設定はリポジトリごとのものですが、対応する API のリファレンスには、レジストリの単位の設定に置き換えていく、という非推奨の注記があります。レジストリの設定にしなかったのは、前のページに書いたとおり、スタック 1 つがアカウント全体のリポジトリの設定を持つのを避けたからです。チームでレジストリを運用するなら、レジストリの設定を、それだけを持つスタックで管理するのが筋です。

### 結果の行き先

basic scanning の結果は、`DescribeImageScanFindings` で読みます。検査が終わると、ECR は EventBridge に `ECR Image Scan` というイベントを送ります。イベントには、重大度ごとの件数が入っています。ECR のイベントは best effort で送られる、とドキュメントにあるので、イベントが来ないことを「検査が終わっていない」の意味に使うことはできません。

enhanced scanning の結果は、同じ API と Inspector の両方から読めます。検査の完了と、結果が作られた・変わった・閉じられたときのイベントは、Inspector が EventBridge に送ります。イベントを通知につなぐ方法は [25章](/ja/chapters/25-events.md)と [19章](/ja/chapters/19-observability.md)にあります。

通すのは、「これからデプロイするダイジェストについて、検査が終わっていて、しきい値以上の結果が無い」ときだけです。それ以外は止めます。この関数には、止め方についての判断が 3 つ入っています。

1 つ目に、検査結果が無いことを、問題が無いこととして扱いません。検査の状態には、失敗（`FAILED`）、対応していないイメージ（`UNSUPPORTED_IMAGE`）、1 日の上限に達した（`LIMIT_EXCEEDED`）などがあり、どれも「調べられなかった」という意味です。これらを通してしまうと、検査が壊れている日にだけ、何でもデプロイできることになります。

## pull through cache

<!-- section: 52.cache -->

12章の Dockerfile は、ベースイメージを Docker Hub から取得します。ビルドのたびに外のレジストリへ取りに行く構成には、弱いところが 2 つあります。

1 つは取得の回数の制限です。Docker Hub は、認証していない取得を、IPv4 アドレス 1 つ（IPv6 なら /64 のサブネット 1 つ）につき 6 時間に 100 回までに制限しています（2026-10-13 時点の Docker のドキュメント）。CI のランナーや NAT Gateway は、1 つのアドレスを多くのジョブで共有するので、自分がほとんど取得していなくても制限に当たることがあります。もう 1 つは経路です。11章のプライベートサブネットのように外へ出る経路が無い場所からは、外のレジストリに届きません。

pull through cache は、外のレジストリのイメージを、自分の ECR のレジストリ経由で取得する仕組みです。ルールを作ると、`<レジストリ>/<接頭辞>/<上流のリポジトリ>` という名前で取得できるようになります。最初の取得のときに、ECR が上流からイメージを取ってきて、自分のレジストリにリポジトリを作り、写しを置きます。2 回目からは写しが返ります。同じタグの取得があると、ECR は多くても 24 時間に 1 回、上流に新しいイメージが無いかを確かめます。上流に届かないときは、最後に取った写しが返ります。

上流にできるレジストリは決まっています。2026-10-13 時点のドキュメントでは、認証なしで使えるのが Amazon ECR Public、Kubernetes のレジストリ、Quay です。Docker Hub、GitHub Container Registry、GitLab Container Registry、Azure Container Registry、Chainguard は、認証情報を Secrets Manager のシークレットに置く必要があります。ほかの ECR のレジストリも上流にできます。

この章のルールは、Amazon ECR Public を上流にしています。

<<< @/examples/52-ecr/infra/lib/ecr-stack.ts{cache}

Docker Hub ではなく ECR Public にしたのは、シークレットが要らないからです。Docker Hub を上流にするには、Docker Hub のアクセストークンを `ecr-pullthroughcache/` で始まる名前のシークレットに置く必要があり、シークレットには月額がかかります（21章）。ECR Public には Docker の公式イメージが `docker/library/` の下に公開されていて、12章の `node:24-bookworm-slim` も `public.ecr.aws/docker/library/node:24-bookworm-slim` として存在します（2026-10-13 に、認証なしでマニフェストを要求して確かめました）。ルールがあれば、これを `<レジストリ>/ecr-public/docker/library/node:24-bookworm-slim` として取得できる、というのがドキュメントの説明です。キャッシュ経由の取得そのものは試していません。

使う前に知っておくことが、いくつかあります。

- ルールが作るリポジトリは、スタックの外にできる。設定は既定のもので、タグは mutable、ライフサイクルポリシーは無い。設定を決めておきたいときは、repository creation template を使う。この章では作っていない
- キャッシュのリポジトリのタグを immutable にすると、ECR は同じタグの写しを更新できなくなる。上流のタグは動くものなので、ここでは mutable のままにし、自分の Dockerfile の側で、ベースイメージをダイジェストで指す
- 最初の取得には、`ecr:BatchImportUpstreamImage` と、リポジトリがまだ無ければ `ecr:CreateRepository` が要る
- インターフェースエンドポイント経由で ECR に届く構成でも、最初の取得にはインターネットへの経路が要ることがある、とドキュメントにある。2 回目からは要らない。プライベートサブネットで使うなら、経路のある場所から一度取得しておく
- 複数のアーキテクチャをまとめたイメージをタグで取得すると、manifest list と、そこから参照されるすべてのアーキテクチャのイメージがキャッシュに入る。`node:24-bookworm-slim` はこの形のイメージである
- Lambda は、pull through cache 経由のイメージを使えない
- ルールはリージョンごとに作る

## 複製と、別アカウントからの取得

<!-- section: 52.replication -->

この節の内容は、スタックに入れていません。ドキュメントから読んだことだけを書きます。

イメージを別のリージョンや別のアカウントに置きたい理由は、主に 2 つあります。リージョンの障害に備えて、別のリージョンでも同じイメージからタスクを起動できるようにすること（[28章](/ja/chapters/28-multi-region.md)）と、ビルド用のアカウントと本番のアカウントを分けること（[33章](/ja/chapters/33-production-readiness.md)）です。

**複製**（replication）は、レジストリの設定です。「このレジストリにプッシュされたイメージを、あのリージョン（あのアカウント）のレジストリにも置く」というルールを、リポジトリ名の接頭辞で絞って書きます。知っておくべき性質は次のとおりです。

- 複製されるのは、設定したあとにプッシュされたイメージだけ。すでにあるイメージは複製されない
- リポジトリ名は、複製先でも同じになる
- ほとんどのイメージは 30 分以内に複製されるが、まれにそれより長くかかる。プッシュの直後に別のリージョンでデプロイすると、イメージがまだ無いことがある
- 複製は、消す操作を伝えない。元のリポジトリでライフサイクルポリシーがイメージを消しても、複製先には残る。ライフサイクルポリシーも複製されないので、複製先には複製先のポリシーが要る
- タグの immutability などのリポジトリの設定も、既定では複製されない
- 複製先のリポジトリが immutable で、同じタグのイメージがすでにあると、イメージは複製されるが、タグは付かない
- 別のアカウントへ複製するときは、複製先のアカウントのレジストリポリシーで、元のアカウントに `ecr:ReplicateImage` と `ecr:CreateRepository` を許可する。元の側にポリシーは要らない

ダイジェストは中身から決まるので、複製先でも同じです。タスク定義がダイジェストでイメージを指していれば、リージョンが変わっても、変わるのはレジストリのホスト名だけです。

**別アカウントからの取得**には、複製しないやり方もあります。リポジトリポリシーで、相手のアカウントに `ecr:BatchGetImage` と `ecr:GetDownloadUrlForLayer` を許可します。相手のアカウントの側では、取得するロールに、同じ操作と `ecr:GetAuthorizationToken` を IAM のポリシーで許可します。アカウントをまたぐ場合は、リソースの側と相手の IAM の側の両方に許可が要ります。

複製は、相手のアカウントの中にイメージの写しを作ります。元のリポジトリが消えても、写しは残ります。リポジトリポリシーによる取得は、写しを作らないぶん安く済みますが、取得のたびに元のリージョンと元のアカウントに依存します。リージョンの障害に備えるなら複製、アカウントを分けるだけならリポジトリポリシー、と使い分けます。

信頼ポリシーは、トークンの `sub` を完全一致で確かめます。引き受けられるのは、1 つのリポジトリの 1 つのブランチで動くジョブだけです。フォークからのプルリクエストや、別のブランチのジョブは、`sub` の値が違うので引き受けられません。リポジトリ名とブランチ名に `*` が入らないことは、設定のスキーマが確かめています。20章と同じ考え方です。

ロールにできることは、3 つのステートメントに分かれています。

`LogIn` は `ecr:GetAuthorizationToken` です。ログイン用のトークンはレジストリに対するもので、この操作はリポジトリを指定できません。スタックの中で `*` を対象にしているのは、この 1 か所だけです。

`PushToOneRepository` は、ドキュメントが「1 つのリポジトリへのプッシュに必要」として挙げている 6 つの操作を、このリポジトリの ARN に対して許可します。

`ReadScanResults` は、プッシュしたイメージのダイジェストと検査結果を読むためのものです。前の節の関数を CI で使うときに要ります。

与えていない操作のほうが大事です。このロールは、イメージを消せず、タグの設定もライフサイクルポリシーもリポジトリポリシーも変えられません。CI のワークフローは、依存パッケージのスクリプトを含めて、多くのコードを実行します。そのどれかが悪意のあるものだったとしても、このロールでできるのは、新しいタグでイメージを足すことまでです。すでにあるタグを動かすことも、検査を止めることもできません。テストは、許可した操作の一覧を固定し、消す操作と設定を変える操作が入っていないことを確かめています。

`-c pullThroughCache=on` のときは、ステートメントが 1 つ増え、キャッシュの接頭辞の下からベースイメージを取得できるようになります。

### 署名

イメージが「自分たちの CI が作ったもの」であることを、取得する側で確かめたい場合には、署名があります。2026-10-13 時点の ECR のドキュメントは、2 つの方法を挙げています。managed signing は、レジストリに署名の設定を置いておくと、プッシュのたびに ECR が AWS Signer で署名を作る方法で、ドキュメントはこちらを勧めています。manual signing は、Notation の CLI と AWS Signer のプラグインを使って、プッシュする側で署名します。

署名は、イメージに紐づく別の成果物（reference artifact）として、同じリポジトリに保存されます。署名 1 つは、リポジトリあたりのイメージ数のクォータに 1 つとして数えられ、元のイメージがライフサイクルポリシーで消されると、24 時間以内に一緒に消されます。managed signing を使うには、プッシュするロールに、署名プロファイルに対する `signer:SignPayload` が要ります。料金は、東京リージョンの Price List で、署名 1 回につき USD 0.02 です。

署名は、検証する側があって初めて意味を持ちます。ECS や Kubernetes の側で、署名の無いイメージを動かさないようにする設定については、読み切れていないので、この章では扱いません。SBOM や attestation も、reference artifact として同じリポジトリに置ける、という範囲までがドキュメントで確かめたことです。

## 手元で確かめる

<!-- section: 52.local -->

手元で動くのは、テスト、ライフサイクルポリシーの evaluator、スタックの synth です。どれも AWS に触りません。

```bash
vp test run examples/52-ecr
vp run ecr:lifecycle:preview
vp run ecr:infra:synth
```

`ecr:lifecycle:preview` は、`aws ecr describe-images` の出力の形をしたファイルを読み、この章のポリシーで消されるイメージを表示します。既定で読むのは `fixtures/describe-images.json` で、この章のために書いた架空の 46 個のイメージです。実際のリポジトリから取ったものではありません。
