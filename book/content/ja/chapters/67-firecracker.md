# 67 Firecracker: Lambda と Fargate の下で動く microVM

Lambda の関数は、ほかの利用者の関数と同じ物理マシンの上で動いています。それでも互いに触れないのは、実行環境が microVM という小さな仮想マシンの中にあり、境界を CPU の仮想化機能が守っているからです。その microVM を作っているのが Firecracker です。この章では、Firecracker が何をして何をしないかを公開されている資料から読み、これまでの章で見てきた Lambda と Fargate の振る舞いを、その上に置き直します。

Firecracker はオープンソースで、ソースも設計文書も API の仕様も読めます。一方、AWS が自分のサービスの中でそれをどう使っているかは、AWS が書いた範囲でしかわかりません。そこでこの章では、3 種類の文を書き分けます。資料に書いてあること、そこから導けること、AWS の外からは確かめられないことです。

先に断っておくと、この章を書いたマシンは macOS で、Firecracker は動きません。Firecracker には Linux と KVM が要ります。章の中の起動時間やメモリの数字は、すべて Firecracker のプロジェクトか AWS が公表している値で、この本が測ったものは 1 つもありません。手元で実行したのは、Firecracker の API に送るリクエストを組み立てて仕様と照らすコードと、そのテストです。Linux のマシンを持つ読者のための手順は書いてありますが、実行していません。

前提は、[04章](/ja/chapters/04-http-api.md)のアプリ、[29章](/ja/chapters/29-lambda-tuning.md)の実行環境とコールドスタート、[12章](/ja/chapters/12-containers.md)と [41章](/ja/chapters/41-fargate.md)の Fargate、[23章](/ja/chapters/23-ec2.md)の EC2 です。コードは `examples/67-firecracker/` にあります。内容は 2026 年 10 月 13 日に、Firecracker v1.17.0 のリポジトリと AWS のドキュメントを読んで確かめました。

## Firecracker とは

<!-- section: 67.what -->

Firecracker は**仮想マシンモニター**（virtual machine monitor、VMM）です。仮想マシンを動かすには 2 つの部品が要ります。1 つは CPU の仮想化機能を使ってゲストのコードを直接走らせる部分で、Linux ではカーネルの KVM が受け持ちます。もう 1 つは、ゲストにディスクやネットワークといったデバイスを見せ、ゲストがそれらに触れたときの処理をする部分で、これが VMM です。広く使われている VMM は QEMU で、Firecracker はその位置に入る別の実装です。

リポジトリの README は、Firecracker を次のように説明しています。KVM を使って microVM を作り、動かす。不要なデバイスとゲスト向けの機能を省いて、microVM ごとのメモリの使用量と攻撃される面を小さくする。AWS が Lambda や Fargate のようなサービスのために開発し、Apache License 2.0 で公開している。

```figure
caption: Firecracker のプロセス 1 つが microVM 1 つを受け持ちます。ゲストから見えるデバイスは、ホストの TAP デバイスとファイルにつながっています。
node client: API クライアント
node fc: Firecracker | プロセス 1 つ
node guest: microVM | ゲストのカーネルとコード
node kvm: KVM | ホストのカーネル
node tap: TAP デバイス
node file: ファイル | ゲストのディスク
edge client -> fc: Unix ソケットの HTTP
edge fc -> guest: virtio のデバイス
edge fc -> kvm: /dev/kvm
edge fc -> tap: パケット
edge fc -> file: ブロック
group host: ホスト = client, fc, kvm, tap, file
mark fc
```

設計文書から、形を決めている点を拾います。

- Firecracker のプロセス 1 つが受け持つ microVM は 1 つだけです。ホストで `ps` を実行すれば、microVM の数だけプロセスが並びます
- プロセスの中のスレッドは、API、VMM、そして vCPU ごとに 1 本です。vCPU のスレッドは、起動した時点から悪意のあるコードを動かしているものとして扱う、と設計文書は書いています
- ゲストのネットワークはホストの TAP デバイスに、ゲストのディスクはホストのファイルにつながります。ファイルシステムをゲストに貸す仕組みはありません
- 設定はすべて、プロセスが Unix ドメインソケットで待ち受ける HTTP の API から送ります。仕様は OpenAPI の形式でリポジトリに入っています
- ホストもゲストも Linux です。CPU は x86_64 と aarch64 で、ゲストはホストと同じアーキテクチャでなければなりません

省いたものが、Firecracker の特徴です。FAQ は、エミュレートするデバイスを virtio-net、virtio-balloon、virtio-block、virtio-vsock、シリアルコンソール、microVM を止めるためだけの最小限のキーボードコントローラーの 6 つと書いています。同じ版の README には、乱数のデバイスや pmem など、これより新しい機能も載っています。2020 年の論文は、BIOS が無いこと、任意のカーネルを起動できないこと、VM のマイグレーションが無いことを挙げ、Firecracker が置き換えるのは QEMU であって Docker や Kubernetes ではない、と書いています。イメージの配布も、何台ものホストへの配置も、Firecracker の仕事ではありません。

プロジェクトが約束している数字は、仕様書（`SPECIFICATION.md`）にあります。どれも、プロジェクトが自分のテスト環境で守っている値です。

- 測る場所は EC2 の M5D.metal と M6G.metal で、ホストに余裕があることが条件です
- vCPU 1 つ、メモリ 128 MiB の microVM で、VMM 自身のメモリの上乗せは 5 MiB 以下。ワークロードと設定によって増える、と但し書きがあります
- `InstanceStart` の API 呼び出しを受けてから、ゲストの `/sbin/init` が始まるまでが 125 ミリ秒以下。シリアルコンソールを無効にし、最小限のカーネルとルートファイルシステムを使ったときの値です
- VMM のプロセスが API ソケットを使えるようになるまでが CPU 時間で 8 ミリ秒以内。実時間は 6 ミリ秒から 60 ミリ秒まで広がる、とあります

125 ミリ秒は「アプリが最初のリクエストに答えるまで」の時間ではありません。計り終わるのは init が始まった時点で、そのあとに来るランタイムの起動とアプリの初期化は入っていません。

## プロセス、コンテナ、isolate、microVM

<!-- section: 67.boundaries -->

他人のコードを同じマシンで動かす方法はいくつもあり、違いは、壊れてはいけない境界がどこにあるかです。この本にはすでに 3 つが出てきました。Lambda Managed Instances のコンテナ（[35章](/ja/chapters/35-lambda-managed-instances.md)）、Workers の isolate（[64章](/ja/chapters/64-isolates.md)）、そして Lambda と Fargate の microVM です。並べると次のようになります。

| | 共有するもの | 境界を守っているもの | 起動と上乗せについて資料が言うこと |
| --- | --- | --- | --- |
| プロセス | カーネル、ファイルシステム、ネットワーク | OS のユーザーと権限 | 比較の基準。数値は引いていません |
| コンテナ | カーネル | 名前空間、cgroup、seccomp で絞ったシステムコール | 論文は、安全にするほど動かないコードが増える、と書いています。数値は引いていません |
| isolate | プロセスとランタイム | V8 と、その外側のプロセスのサンドボックス | Cloudflare は、コンテナや VM の上の Node のプロセスの約 100 分の 1 の時間で始まり、起動時のメモリは 1 桁少ない、と書いています |
| microVM | ハードウェアだけ | CPU の仮想化機能、KVM、VMM | Firecracker の仕様書は、init の開始まで 125 ミリ秒以下、VMM の上乗せ 5 MiB 以下と書いています |

右の列は、それぞれの資料が自分の条件で述べている値で、同じ条件で比べたものではありません。この本ではどれも測っていません。

コンテナの行の意味を、論文は次のように説明しています。コンテナの中のコードは、ホストのカーネルを直接呼びます。境界はシステムコールの入口にあり、守りを固めるには、使えるシステムコールを減らすしかありません。ところが Lambda は任意の Linux のバイナリを動かす約束をしているので、減らせる量に限りがあります。仮想化では、ゲストは自分のカーネルを丸ごと使えて、境界は CPU の仮想化機能と、ずっと小さい VMM に移ります。代わりに、ゲストごとにカーネルと VMM の分のメモリと起動時間がかかります。Firecracker は、その上乗せを削るために作られた VMM です。

isolate は境界をさらに内側に置きます。1 つのプロセスの中に何千もの isolate があり、互いのメモリに触れないことを V8 が保証します。カーネルもプロセスも起動しないので、始まるのは速く、メモリも少なくて済みます。動かせるのは JavaScript と WebAssembly です。Cloudflare 自身が、V8 は仮想マシンより攻撃される面が広いと書いたうえで、プロセス全体を名前空間と seccomp で囲み、ファイルシステムとネットワークに触れさせない層を足している、と説明しています。論文は、言語の仮想マシンによる分離は任意のバイナリを動かす必要のある Lambda と Fargate には合わなかった、と 1 文で片付けています。優劣ではなく、何を動かすと約束したかの違いです。

microVM の境界は強いものの、Firecracker だけで完成するわけではありません。本番ホストの設定の文書は、Firecracker はホストのハードウェアの脆弱性を緩和できないと明記し、テナントを分けるなら SMT を無効にすること、Firecracker のプロセス 1 つを 1 つのテナントに対応させることを求めています。

## AWS のどこで動いているか

<!-- section: 67.aws -->

ここが、3 種類の文を分ける場所です。

**資料に書いてあること。**

- Firecracker の README と FAQ は、Lambda と Fargate のために AWS が開発したと書いています。FAQ によれば、2014 年に始まった Lambda は、当初、利用者ごとの EC2 インスタンスで分離していました
- Lambda のデベロッパーガイドは、Lambda Managed Instances を説明するページで、既定の Lambda を「共有のフリートの上で、Firecracker の microVM の技術で実行環境どうしを分離する」と書いています。同じページに、Lambda Managed Instances は Firecracker ではなくコンテナで分離する、とあります
- ホワイトペーパー「Security Overview of AWS Lambda」（最後の改訂は 2022 年 12 月 27 日）は、実行環境が置かれる Worker を、Lambda が別のアカウントで管理するベアメタルの EC2 Nitro インスタンスとし、その上に Firecracker が作る microVM が 1 つ以上ある、と書いています。実行環境は、関数のバージョンや利用者をまたいで使い回されません
- 2020 年の論文は、当時の Lambda について、もっと細かく書いています。Worker 1 台に数百から数千の microVM があり、microVM 1 つがスロット 1 つにあたる。スロットは 1 つの関数の、同時には 1 件の呼び出しだけに使われ、続けて来る呼び出しには使い回される。起動の待ち時間を隠すために、起動済みの microVM を少数プールしておく。スロットは長くても 12 時間で作り直す
- SnapStart のページは、関数のバージョンを公開したときに、初期化の済んだ実行環境のメモリとディスクを Firecracker の microVM のスナップショットとして取り、新しい実行環境をそこから再開する、と書いています。対応するランタイムは Java 11 以降、Python 3.12 以降、.NET 8 以降で、`nodejs24.x` は対応していないと明記されています
- 2026 年 6 月 22 日に発表された Lambda MicroVMs は、利用者や AI が書いたコードを動かすための環境で、ガイドは Firecracker の仮想化で提供すると書いています
- Fargate については、2018 年 11 月の AWS の Open Source Blog が、以前はタスクごとに専用の EC2 の VM で動かしていたものを、Firecracker の microVM で動かすようにした、と書いています。いまの ECS のデベロッパーガイドは、Fargate はタスクをそれぞれハードウェア仮想化の環境で動かし、タスクはカーネル、CPU、メモリ、ネットワークインターフェースをほかのタスクと共有しない、と書いています。この 2 つのページに Firecracker の名前は出てきません

**そこから導けること。**

- 29章で見た「1 つの実行環境が同時に処理するのは 1 件」は、設定ではなく構造です。境界が microVM にあり、その中に関数が 1 つ、呼び出しが 1 件、という作りになっています
- コールドスタートのうち、Firecracker が受け持つ部分は小さいはずです。仕様書の値は init の開始まで 125 ミリ秒以下で、論文によればその分もプールで隠しています。REPORT 行の `Init Duration` に入るのは、29章で見たとおり、extension とランタイムの起動、ハンドラーの外のコードです
- SnapStart は、この本の Node.js の関数には使えません。使えるランタイムでも、1 つのスナップショットから何個もの実行環境が始まるので、初期化の中で作った乱数や ID は実行環境ごとに違うものになりません。Firecracker のスナップショットの文書が「同じ状態から 2 回以上再開するのは、一意性を保つ仕組みが無ければ安全でない」と書いているのと同じ問題です

**AWS の外からは確かめられないこと。**

- いまの Lambda で、実行環境 1 つがそのまま microVM 1 つなのか。論文は 2020 年の構成で、ホワイトペーパーは「Worker に microVM が 1 つ以上」としか書いていません
- AWS が動かしている Firecracker が、公開されている版と同じかどうか。本番での起動時間、プールの大きさ、メモリの上乗せ
- 関数に設定したメモリが、そのまま microVM のメモリになるのか
- Fargate のすべてのタスクが、いまも Firecracker の上にあるのか。プラットフォームバージョンごとの違い、EKS の Fargate での扱いは、読んだページからはわかりません。ホワイトペーパー「Security Overview of AWS Fargate」は、配布元が 403 を返して読めませんでした
- SnapStart のスナップショットが、公開されている Firecracker のスナップショットの形式と同じものか

## これまでの章で見たことの説明

<!-- section: 67.explains -->

29章のコールドスタートは、次のように読み直せます。空いている実行環境が無いとき、Lambda は新しいスロットを用意します。そこには、microVM を 1 つ使えるようにすること、関数のコードを置くこと、ランタイムを起動すること、ハンドラーの外のコードを走らせることが含まれます。最初の 1 つは Firecracker の速さとプールで短くされていて、利用者が変えられるのは後ろの 3 つです。バンドルを小さくし、初期化を軽くするという 29章の作業は、利用者に残された部分を削る作業でした。

実行環境の使い回しも、同じ構造から説明できます。論文には、モジュールのスコープに置いた変数を 1 ずつ増やして返す関数が載っていて、続けて呼ぶと数が増えていきます。microVM も、その中のプロセスも、呼び出しをまたいで残るからです。29章でクライアントをハンドラーの外に置いたのは、この性質を使っていました。呼び出しが終わってから次が来るまでのあいだ、実行環境がメモリを持ったまま CPU を使わないことを、論文は Lambda の経済性の中心だと書いています。

35章の Lambda Managed Instances は、同じ Lambda の名前でも境界が違います。ガイドは、Managed Instances は Firecracker ではなくコンテナで分離し、セキュリティの境界はキャパシティプロバイダーだと書いています。インスタンスは利用者のアカウントにあるので、ほかの利用者との境界は EC2 が受け持ち、その内側のコンテナは信頼できる関数どうしを分けるだけです。35章で見たとおり、1 つの実行環境が同時に何件も処理するので、モジュールのスコープは同時のリクエストのあいだで共有されます。microVM のスロットに 1 件ずつ入っていたときには起きなかった取り違えが、ここで起きるようになります。

41章で、Fargate のタスクが 1 つの単位である理由もここにあります。ECS のガイドは、コンテナはセキュリティの境界ではないと書き、境界をタスクに置いています。タスクの中のコンテナどうしは、同じ境界の内側にいます。信頼できないものどうしを分けたければ、コンテナではなくタスクを分けます。41章で見た、タスクが起動のたびにイメージ全体を取得することも、同じ境界の裏返しと読めます。前のタスクのキャッシュを次のタスクが読めるなら、タスクのあいだに共有しているものがあることになるからです。

料金の単位も、境界の単位と重なっています。Lambda は実行環境が呼び出しを処理している時間に、Fargate はタスクに割り当てた vCPU とメモリの時間に課金します。どちらも、分離の単位がそのまま計量の単位になっています。ただし、これは料金表と上の資料を並べて読んだもので、AWS が課金の理由として述べていることではありません。

## 自分で動かす人、動かさない人

<!-- section: 67.who -->

Firecracker を自分で運用する理由が立つのは、他人のコードを預かって動かすサービスを作っていて、テナントごとにカーネルを分けたい場合です。利用者が書いたコードの実行環境、CI のジョブ、コーディングエージェントのサンドボックス（[63章](/ja/chapters/63-agent-sandbox.md)）がこれにあたります。

その場合に Firecracker が持ってくるのは VMM だけで、残りは自分の仕事になります。資料から拾うと、次のものです。

- jailer を使った起動と、ホストの設定。本番ホストの設定の文書にある項目は、やらなければ保証が成り立たない、と文書自身が書いています
- ゲストのネットワークの出口の絞り込み。Firecracker はパケットを選別しません
- カーネルとルートファイルシステムのイメージの作成と配布、パッチ
- どのホストにどの microVM を置くかの判断と、ホストが落ちたときの扱い
- スナップショットを使うなら、そのファイルの保護と、再開したゲストの中の乱数や ID の作り直し

ほとんどの読者には、これを自分で持つ理由がありません。2026 年 10 月 13 日の時点で、先に検討できるものは次のとおりです。

- 自分のコードを動かすだけなら、Lambda と Fargate がすでに microVM の境界を提供しています
- 他人のコードを AWS で動かすなら、Lambda MicroVMs があります。東京リージョンでも使える、と発表にあります。料金と上限は、この章では調べていません
- エージェントのための実行環境は、[50章](/ja/chapters/50-agentcore.md)が AgentCore を扱っています
- Vercel には Vercel Sandbox があり、ドキュメントは、サンドボックス 1 つを Firecracker の microVM 1 つで動かすと書いています
- Cloudflare の Workers は、isolate という別の境界を選んでいます。動かすのが JavaScript と WebAssembly で、プラットフォームの約束で足りるなら、microVM を持ち込む理由はありません。isolate を自分のマシンで動かす話は 64章にあります

Firecracker が動く物理的な土台、つまりベアメタルのインスタンスと Nitro の話は、[68章](/ja/chapters/68-nitro.md)に続きます。次のページでは、Firecracker の API を、仕様と照らしながら TypeScript から呼ぶコードを書きます。
