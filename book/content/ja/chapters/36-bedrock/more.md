# 36 Bedrock: 実装のつづき

[前のページ](/ja/chapters/36-bedrock/build.md)で、ループと JSON の受け取り方を実装しました。このページでは、呼び出しのまわりに付けるものを扱います。ガードレール、prompt caching、使用量と予算、batch inference です。

## ガードレール

<!-- section: 36.guardrails -->

Amazon Bedrock Guardrails は、モデルへの入力とモデルの出力を、決めたフィルターで調べる機能です。設定の単位をガードレールと呼びます。フィルターは 6 種類あります。

- content filters は、憎悪、侮辱、性的、暴力、不正行為と、プロンプト攻撃を検出します
- denied topics は、扱わないと決めた話題を検出します
- word filters は、決めた単語や語句が、語の単位で一致したときに反応します
- sensitive information filters は、個人情報や認証情報を検出して、止めるか、伏せ字にします。正規表現も使えます
- contextual grounding checks は、答えが渡した資料に基づいているかを調べます
- Automated Reasoning checks は、答えを論理の規則と照らします

### 日本語で使えるもの

フィルターによって、対応する言語が違います。ドキュメントは、対応していない言語ではガードレールは効かない、とはっきり書いています。

content filters と denied topics には、Classic と Standard の 2 つの段階（tier）があります。Classic が対応するのは英語、フランス語、スペイン語だけです。日本語は Standard で「Optimized and supported」になっています。プロンプト攻撃の検出は content filters の一種なので、日本語のノートで使うなら Standard が要ります。

sensitive information filters には段階がなく、日本語に対応しています。word filters と contextual grounding checks の対応言語は、英語、フランス語、スペイン語です。

Standard には条件があります。Standard のガードレールは、cross-Region の仕組みを通して動きます。モデルの inference profile と同じ考え方ですが、行き先は別に決まっています。

<<< @/examples/36-bedrock/infra/lib/guardrail.ts{profile}

東京から使える profile は `apac.guardrail.v1:0` で、行き先にはムンバイ、ソウル、シンガポール、シドニーが入っています。モデルを `jp.` の profile で呼んで推論を日本の中に収めても、Standard のガードレールを付けると、質問と答えの文章は、検査のために日本の外へ出ることがあります。

この章のスタックは、既定ではこのフィルターを付けません。既定のガードレールは sensitive information filters だけで、AWS のアクセスキーとシークレットキーを、質問と答えの両方で止めます。ノートに貼り付けた鍵を、アシスタントが答えの中で繰り返さないようにするためです。プロンプト攻撃のフィルターは、`-c promptAttackFilter=standard` を付けてデプロイしたときだけ有効になります。スタックの中身は[デプロイのページ](/ja/chapters/36-bedrock/deploy.md)で見ます。

### 呼び出しに付ける

ガードレールは、リクエストの `guardrailConfig` に ID とバージョンを書くと有効になります。

<<< @/examples/36-bedrock/src/prompt.ts{guardrail}

バージョンには、番号を渡します。ガードレールには作業中の下書き（`DRAFT`）と、番号の付いたバージョンがあります。下書きを指定することもできますが、設定を変えるたびに動作が変わるので、アプリからは番号で固定します。

`streamProcessingMode` は、ストリームのときの検査のしかたです。`sync` では、断片を検査してから送るので、そのぶん遅くなります。`async` では、断片をすぐ送り、検査は裏で進みます。問題が見つかれば以降の断片は止まりますが、それまでに送った分は呼び出し元に届いています。伏せ字にする処理は `async` では使えません。この章は `sync` です。

### 止められた答えの形

ガードレールが止めると、エラーにはなりません。`stopReason` が `guardrail_intervened` になり、ガードレールに設定しておいたメッセージが、モデルの文章の代わりに届きます。ストリームでは、そのメッセージが文章の断片として流れてきます。ドキュメントの例では、入力で止められたときのトークン数は 0 です。

つまり、何もしなければ、止められた答えはふつうの答えと同じ見た目で画面に出ます。ループは、これを別のイベントにします。`blocked` にガードレールのメッセージを入れ、`done` の `complete` を `false` にします。

クライアントは、`blocked` が届いたら、それまでに表示した文章を捨てて、メッセージに置き換えます。

<<< @/examples/36-bedrock/src/client.ts{collect}

出力の途中で止められた場合に、それより前の断片がどこまで届いているかは、この章では確かめていません。`sync` の説明からは、検査を通った断片は届いていると読めます。そのため、クライアントは「届いた文章は、`done` が完成と言うまで答えではない」という 17章の決まりを、そのまま使います。

### 見ていないもの

ガードレールには、調べない場所があります。ツールを使う章では、ここが大事です。ドキュメントは、次の 3 つを調べないと書いています。

- アプリが返す tool result の中身
- アプリが渡すツールの定義
- モデルが書くツールの入力

調べるのは、文章として送った入力と、モデルの文章の出力です。ノートの本文は tool result としてモデルに渡るので、ノートに書かれた指示も、ノートに書かれた個人情報も、入力の検査を通りません。モデルがそれを答えの文章に書いたとき、出力の検査に初めてかかります。

system prompt も、既定では調べません。調べさせるには `guardContent` で囲みます。ただし、メッセージのどこかに `guardContent` を 1 つでも置くと、囲んでいない部分は調べなくなります。この章は `guardContent` を使わず、質問と答えの全体を調べさせています。モデルの推論の過程（reasoning）のブロックも、調べる対象に入りません。

ガードレールは、[前のページ](/ja/chapters/36-bedrock/build.md)の作りの代わりにはなりません。ツールが読むだけであること、呼び出した人のノートにしか届かないことは、ガードレールがあってもなくても、コードと IAM が守ります。ガードレールは、その上に重ねる検査です。確率で動く検査なので、すり抜けも、止めすぎもあります。

料金は、フィルターごとに、調べた文章の量で決まります。単位は text unit で、1,000 文字までが 1 unit です。金額は[費用のページ](/ja/chapters/36-bedrock/wrap.md)にまとめます。

## prompt caching

<!-- section: 36.caching -->

ループは、往復のたびに会話の全体を送り直します。prompt caching は、毎回同じ内容で始まる部分を、モデルの側で使い回す機能です。使い回せた分は、入力より安い単価で課金されます。

Bedrock の prompt caching には 2 種類あります。implicit は、何も指定しなくても、Bedrock が使い回せる先頭を探します。当たる保証はありません。explicit は、ここまでを使い回してよい、という目印（cache checkpoint）をリクエストに置きます。目印を置いても、当たる保証がないことは同じです。

目印には、モデルごとの決まりがあります。

- 目印より前のトークン数に下限があります。Nova 2 Lite は 1,000、Claude Haiku 4.5 は 4,096 です。下限に届かない目印は、エラーにはならず、ただ無視されます
- 目印は 1 つのリクエストに 4 つまでです
- 置ける場所が違います。Nova 2 Lite は `system` と `messages`、Claude Haiku 4.5 は `tools` にも置けます
- キャッシュの寿命は 5 分で、当たるたびに延びます。Claude Haiku 4.5 は 1 時間も選べます。5 分だけのモデルに寿命を指定すると、`ValidationException` になることがあります
- Nova のモデルは、キャッシュできるのが 20,000 トークンまでです

下限は、`tools`、`system`、`messages` の順に数えた、目印までの合計で判定されます。順序も同じで、前のほうを変えると、後ろのキャッシュは使えなくなります。変わらないものを前に、変わるものを後ろに置きます。

この章のループは、目印を 2 か所に置きます。

<<< @/examples/36-bedrock/src/prompt.ts{cache-points}

system prompt の終わりと、ツールの結果を返した各メッセージの終わりです。次の呼び出しは、そこまでが前回と同じ内容で始まります。目印が 4 つを超えるときは、古いものから外します。

このアシスタントの system prompt とツールの定義は、合わせても数百トークンで、下限に届きません。効く可能性があるのは、ノートを読んだあとの呼び出しです。長いノートを 1 件読めば、会話は Nova 2 Lite の下限を超えます。実際に当たるかどうかは、モデルを呼んでいないので確かめていません。

### 使用量の読み方

キャッシュを使うと、使用量の数字の意味が変わります。

<<< @/examples/36-bedrock/src/usage.ts{usage}

`inputTokens` は、キャッシュから読んだ分も、キャッシュに書いた分も含みません。送った入力の合計は、3 つを足した値です。`inputTokens` だけを見ていると、キャッシュが効いた途端に入力が減ったように見えます。この章のトークンの上限は、4 つの合計で数えています。

### 得になる条件

キャッシュに書く分と読む分は、通常の入力と別の単価です。

<<< @/examples/36-bedrock/src/usage.ts{cache-math}

Claude Haiku 4.5（東京、AWS Price List、2026-10-13 確認）は、通常の入力が 100 万トークンあたり USD 1.10、書き込みが USD 1.375、読み出しが USD 0.11 です。書き込みは通常より 25% 高く、読み出しは 10 分の 1 です。1 回しか送らない先頭に目印を置くと、損をします。2 回目が 5 分以内に来て、キャッシュに当たれば、得になります。5,000 トークンの同じ先頭を 4 回送る会話が月に 1,000 回あるとすると、先頭の分は、キャッシュなしで USD 22.00、ありで USD 8.53 です。

Nova 2 Lite は、Price List の上では、書き込みが USD 0、読み出しが 1,000 トークンあたり USD 0.000099 で、通常の入力（USD 0.000396）の 4 分の 1 です。2,000 トークンの先頭を 4 回送る会話が月に 1,000 回なら、キャッシュなしで USD 3.17、ありで USD 0.59 です。書き込みが 0 という行が、実際の請求でどう数えられるかは、確かめていません。

どちらの計算も、2 回目以降がすべて当たったと仮定しています。当たらなければ、Claude Haiku 4.5 では書き込みの割り増しだけが残ります。ドキュメントには、cross-Region の profile では、混雑時に書き込みが増えることがある、とも書かれています。得かどうかは、ログの `cacheReadInputTokens` を見て判断してください。

## 使用量、予算、クォータ

<!-- section: 36.budget -->

17章の「本番にするなら」には、利用者ごとの上限が無い、と書きました。この章には、呼び出した人の ID があります。上限を作れます。

### 使用量を金額にする

`metadata` イベントの使用量を、ループは応答ごとに足していきます。それを、モデルの単価で金額にします。

<<< @/examples/36-bedrock/src/usage.ts{cost}

単位は 100 万分の 1 ドルです。単価は、最初のページの表に、Price List から写したものを持っています。これは見積もりで、請求の根拠ではありません。単価は変わりますし、失敗した呼び出しがどこまで課金されるかは、17章と同じく確認できていません。

### 呼ぶ前に確保する

<<< @/examples/36-bedrock/src/budget.ts{ledger}

予算は、モデルを呼ぶ前に調べます。あとで調べると、超えたことがわかるのは、もう払ったあとです。

呼ぶ前には、今回いくらかかるかがわかりません。そこで、最悪の額を先に確保し、終わったら実際の額に置き換えます。最悪の額は、トークンの上限のすべてが、いちばん高い単価で課金された場合の額です。Nova 2 Lite で上限が 20,000 トークンなら、USD 0.066 です。

<<< @/examples/36-bedrock/src/app.ts{budget}

確保できなければ、モデルを呼ばずに 429 を返します。この答えには料金がかかりません。

確保と精算のあいだで関数が落ちると、最悪の額が残ったままになります。予算は実際より多く使ったことになり、その日の残りは、断る側に倒れます。逆に倒れる作りにすると、落ちるたびに無料の呼び出しが生まれます。

本番の置き場所は DynamoDB です。

<<< @/examples/36-bedrock/src/dynamodb-ledger.ts{ledger}

「残りを読んで、足りれば足す」を 2 回の操作に分けると、同時に来た 2 つのリクエストが、どちらも最後の残りを見て、どちらも通ります。05章の条件付き書き込みと同じ形で、調べることと足すことを 1 回の更新にします。

確保の額はトークンの上限から決めていますが、上限そのものが、越えたあとで止まる作りでした。そのため、最後の 1 回の呼び出しの分だけ、確保を超えることがあります。精算は実際の額で行うので帳簿は合いますが、「1 日の予算を 1 円も超えない」とまでは言えません。

### ログに残す

呼び出しごとに、19章の形の JSON を 1 行書きます。

<<< @/examples/36-bedrock/src/log-shape.ts{shape}

誰の、どのモデルの、何回の往復で、何トークンで、いくらだったかが、1 行でわかります。質問も、ノートも、答えも入れません。スキーマが `v.strictObject` なのは 19章と同じ理由で、誰かが本文をログに足すと、テストが落ちます。

Bedrock の側にも、呼び出しを記録する機能（model invocation logging）があります。既定では無効で、有効にすると、リクエストとレスポンスの全文が CloudWatch Logs か S3 に保存されます。ノートの本文が入るので、有効にするなら、保存先の権限と保持期間を先に決めてください。

### クォータとスロットリング

Bedrock は、アカウントごと、モデルごとに、1 分あたりのリクエスト数とトークン数を制限しています。公開されている既定値は、cross-Region の呼び出しで、Nova 2 Lite が 1 分あたり 2,000 リクエストと 800 万トークン、Claude Haiku 4.5 が 10,000 リクエストと 500 万トークンです（AWS General Reference、2026-10-13 確認）。ただし、アカウントに実際に適用される値は、これより低いことがあります。Service Quotas で自分の値を確かめてください。

トークンのクォータは、請求とは数え方が違います。

- リクエストの開始時に、入力のトークン数と `maxTokens` の合計が、クォータから引かれます。出力が短くても、終わるまでは `maxTokens` の分が押さえられます。`maxTokens` を必要以上に大きくすると、同時に通るリクエストが減ります
- 出力のトークンには、モデルごとの倍率（burndown rate）が掛かります。Claude Haiku 4.5 は 5 倍で、出力 1 トークンがクォータを 5 トークン減らします。Nova 2 Lite は 1 倍です。課金されるのは実際のトークン数だけです
- キャッシュから読んだトークンは、クォータに数えません

クォータを超えると 429 の `ThrottlingException` が返ります。503 は別の原因で、サービス側の容量が足りないときに返り、アカウントのクォータとは関係がありません。どちらも、この章のループは待ってからやり直します。

ループでは、スロットリングの影響が大きくなります。1 つの質問で 3 回呼ぶなら、どの回で断られても、質問全体が待たされます。利用者ごとの予算は、ここでも役に立ちます。1 人が大量に呼んで、ほかの全員のクォータを使い切ることを防げます。

### タイムアウト

17章の関数は、推論を 30 秒で打ち切り、関数は 40 秒で止まりました。この章は、ループの全体に 60 秒の締め切りを置き、関数のタイムアウトを 70 秒にしています。締め切りは、すべての往復とすべての再試行で共有します。往復ごとに 30 秒ずつ与えると、4 往復で 2 分になり、呼び出し元はその間、答えが来るのかどうかもわかりません。

締め切りが来ると、ループは `timeout` のエラーを 1 つ送って終わります。関数のタイムアウトを締め切りより長くしているのは、このエラーを書いて、予算を精算する時間を残すためです。

## 急がない仕事は batch に

<!-- section: 36.batch -->

全員のノートに要約を付け直す、といった仕事は、いま答えが要るわけではありません。batch inference は、リクエストをファイルにまとめて S3 に置き、結果をあとで S3 から受け取る機能です。料金は、on-demand の半額です。Price List でも、Nova 2 Lite の batch の単価は、入力も出力も、ちょうど半分になっています。要約 10,000 件を、1 件あたり入力 2,000 トークン、出力 150 トークンで計算すると、on-demand で USD 12.89、batch で USD 6.44 です。

入力は JSON Lines で、1 行が 1 件です。

ジョブには大きさの決まりがあります。

batch には、使えないものがあります。

- 東京では、Nova 2 Lite も Claude Haiku 4.5 も、cross-Region の profile 経由でだけ batch を使えます
- prompt caching は使えません
- tool use は使えません。1 行は 1 回の呼び出しで、往復がないからです
- structured outputs は、ドキュメントの記述が食い違っています。batch inference のページは使えないと書き、structured outputs のページは使えると書いています。どちらが正しいかは、この章では確かめていません

この章は、ジョブを作るところまでは用意していません。ジョブには、入力と出力の S3 のバケットと、Bedrock が引き受けるサービスロールが要ります。ロールの信頼ポリシーは `bedrock.amazonaws.com` を相手にし、条件で自分のアカウントのジョブに絞ります。profile を使うなら、ロールには profile と、行き先の各リージョンのモデルに対する `bedrock:InvokeModel` も要ります。ここまではドキュメントで確かめましたが、スタックにもスクリプトにもしていません。

急がない仕事には、もう 1 つ選択肢があります。Flex という service tier で、リクエストごとに指定すると、処理が遅くなる代わりに半額になります。ファイルも S3 も要らず、`Converse` のまま使えます。Nova 2 Lite は対応していますが、Claude Haiku 4.5 のモデルカードでは非対応です。この章では使っていません。

反対に、処理能力を先に買う方法もあります。Provisioned Throughput は、モデルの処理能力を時間単位で確保する買い方で、消すまで課金が続きます。inference profile とは一緒に使えません。Reserved という service tier は、1 分あたりのトークン数を 1 か月か 3 か月の単位で予約します。どちらも、on-demand のクォータで足りなくなってから検討するもので、この章の規模では要りません。
