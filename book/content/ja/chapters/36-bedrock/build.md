# 36 Bedrock: しくみと実装

[最初のページ](/ja/chapters/36-bedrock.md)では、ループの全体と、モデルごとに違うことを見ました。このページでは、ツール、ストリームの読み方、ループ、JSON の受け取り方を実装します。

## ツールを定義する

<!-- section: 36.tools -->

tool use は、モデルが関数を実行する機能ではありません。モデルは「この名前のツールを、この入力で実行してほしい」と答えるだけで、実行するのはアプリです。アプリは結果を次のリクエストに入れて返し、モデルはそれを読んで続きを書きます。

ツールは、説明、入力のスキーマ、実行する関数の 3 つでできています。

<<< @/examples/36-bedrock/src/tools.ts{tool}

スキーマは 2 つ持ちます。`jsonSchema` は、モデルに入力の形を伝えるための JSON Schema です。`input` は、モデルが書いてきた入力を調べる Valibot のスキーマです。モデルは伝えたとおりに書くとは限らないので、実行の前に必ず調べます。

このアシスタントのツールは 2 つで、どちらもノートを読むだけです。

<<< @/examples/36-bedrock/src/tools.ts{note-tools}

この章の不変条件は、**モデルは、呼び出した人以外のノートに届かない**です。

守り方は、`createNoteTools` の引数にあります。`owner` は、入口が確かめた呼び出し元の ID で、ツールを作るときに一度だけ渡します。ツールの入力に `owner` はありません。モデルが何を書いても、ほかの人を指す方法がそもそも無い、という形にしています。

入力のスキーマが `v.strictObject` なのも、そのためです。`v.object` は知らないキーを黙って捨てますが、`v.strictObject` は拒否します。モデルが `{"owner": "bob"}` を付けてきたら、捨てて続けるのではなく、失敗として返します。

`read_note` は、ほかの人のノートの ID を渡されると、存在しない ID のときと同じ答えを返します。05章のテーブルは、キーが持ち主で始まるので、持ち主が違えば見つかりません。「あるけれど読めない」と答えると、その ID のノートが存在することを教えてしまいます。

ノートの本文は 10,000 文字まであります。ツールの結果は次のリクエストの入力になり、入力は課金されるので、返すのは先頭の 4,000 文字までにして、切ったことを `truncated` で伝えます。

`ConverseStream` は、ツールの要求も断片で送ってきます。順序は次のとおりです。

```text
order  event              carries
1      messageStart       role
2      contentBlockStart  toolUse: toolUseId, name      (tool use only)
3      contentBlockDelta  text, or toolUse.input: a piece of JSON text (repeats)
4      contentBlockStop
       2 to 4 repeat for each content block, tied together by contentBlockIndex
5      messageStop        stopReason: end_turn, tool_use, guardrail_intervened, ...
6      metadata           usage: inputTokens, outputTokens, cacheReadInputTokens, ...
```

ツールの名前と ID は `contentBlockStart` で届き、入力は JSON の文字列が何回かに分かれて届きます。途中の断片は JSON として読めないので、全部そろうまで文字列のまま貯めます。

<<< @/examples/36-bedrock/src/converse.ts{events}

1 回の応答を最後まで読む関数が `readTurn` です。

<<< @/examples/36-bedrock/src/turn.ts{turn}

文章の断片は届いた順に `yield` しますが、ツールの要求は `messageStop` が届くまで外に出しません。ツールの要求の途中でストリームが切れると、名前と入力の前半だけが手元に残ります。それを実行してはいけません。`messageStop` が届かなかった応答は、17章と同じく `interrupted` で、中身は何も使いません。

`toolUseId` について、ドキュメントに注意書きがあります。`toolConfig` で定義したツールの ID は Bedrock が作りますが、モデルによっては、モデルの提供元が返した ID がそのまま通ることがあります。この章のコードは ID を、結果を対応づける文字列としてだけ使い、形を仮定しません。

## ループを状態機械にする

どれを選ぶかは、純粋な関数 1 つで決めます。

<<< @/examples/36-bedrock/src/loop.ts{decide}

`stopReason` の値は、API リファレンスが 9 つ挙げています。答えが完成したと言えるのは `end_turn` だけです。知らない値が来たときも、完成していないものとして扱います。

`tool_use` のときに、上限を調べます。

<<< @/examples/36-bedrock/src/loop.ts{limits}

モデルが「まだ調べたい」と言い続けるかぎり、ループは終わりません。止めるのはこの数字です。

回数の上限は、1 つの質問でモデルを呼ぶ回数で、4 にしています。上限に達したときの答えは `turn_limit` で、完成した答えではありません。

トークンの上限には弱いところがあります。調べられるのは、モデルが報告した使用量を足した値だけなので、止まるのは上限を越えたあとの、次の呼び出しの手前です。呼ぶ前に入力のトークン数を数える `CountTokens` という API がありますが、Nova 2 Lite のモデルカードでは非対応になっています。

トークンの数え方には、ループならではの事情もあります。`Converse` は会話を覚えていないので、往復のたびに、それまでの会話の全体を送り直します。3 回目の呼び出しの入力には、質問と、1 回目の要求と結果と、2 回目の要求と結果が入っています。往復が 1 つ増えるごとに、それまでの全部がもう一度課金されます。ツールの結果を小さく保つことと、回数を抑えることが、費用に直接効きます。

ループの本体です。

<<< @/examples/36-bedrock/src/loop.ts{loop}

### やり直してよいとき

17章には「最初のイベントが届く前だけ再試行する」という決まりがありました。呼び出し元に送った文章は、取り消せないからです。

ループでは、この決まりを 1 回の応答ごとに当てはめます。応答が失敗したとき、その応答の文章がまだ 1 文字も呼び出し元に届いていなければ、同じリクエストをもう一度送れます。ツールの要求の途中で切れた応答は、この条件に当てはまります。ツールの要求は `messageStop` まで外に出していないので、やり直しても、何も二重には起きません。

文章を送り始めたあとに切れたら、やり直しません。呼び出し元の画面には、もう前半が出ています。

スロットリングも同じ場所で扱います。Bedrock が 429 の `ThrottlingException` で断ったら、17章の関数で待ち時間を決めて、もう一度送ります。待ち時間は指数的に延ばし、全体をランダムにします。試行は 1 回の応答につき 3 回までで、すべての応答とすべての試行が、1 つの締め切り（60 秒）を共有します。SDK の自動の再試行は切ってあります。SDK とアプリの両方が再試行すると、回数が掛け算になるからです。再試行の考え方は [32章](/ja/chapters/32-limits.md)で扱っています。

## ノートに書かれた指示

<!-- section: 36.injection -->

17章では、ノートに「これまでの指示を忘れて…」と書かれていても、出力がただの文字列なので害は限られる、と書きました。ツールがあると、話が変わります。モデルが従えば、ツールが呼ばれます。

しかも、指示が入ってくる経路が増えます。利用者の質問だけでなく、ツールが返すノートの本文も、モデルはそのまま読みます。ノートは、本人が書いたものとは限りません。共有されたノートや、取り込んだメールの本文かもしれません。

AWS のドキュメントは、プロンプトインジェクションを SQL インジェクションと同じ、アプリの側の責任だと書いています。

system prompt には、ノートはデータだと書いてあります。

<<< @/examples/36-bedrock/src/prompt.ts{system}

これは頼んでいるだけで、守られる保証はありません。この章が当てにしているのは、モデルが指示に従ってしまっても何も起きない、という作りのほうです。

- ツールは読むだけです。ノートを書く、消す、送るツールはありません。実行ロールにも、ノートのテーブルへの書き込みの権限がありません
- ツールは呼び出した人のノートしか読めません。`owner` はモデルの入力から来ません
- 外へ出る経路がありません。URL を取りに行くツールも、メールを送るツールもありません
- 回数とトークンに上限があります

テストでは、ノートに書かれたとおりに動くモデルを用意しました。フィクスチャの `injected` は、ノートを読んだあと、ノートの指示どおりに、ほかの人のノートを ID で求め、`owner` を付けて一覧を求めます。それでも、ほかの人のノートの中身は、モデルへのどのリクエストにも、呼び出し元へのどのイベントにも現れません。

残る危険もあります。モデルが読めるのは呼び出した人のノートだけですが、その範囲の中では、指示に従った答えを書けます。要約をねじ曲げる、嘘の連絡先を答えに混ぜる、といったことです。答えを HTML や Markdown として表示するなら、画像の URL にノートの中身を埋め込んで外へ送らせる、という手口もあります。この章の API は文章を返すだけですが、表示する側で、答えを信用できる HTML として扱わないでください。

## JSON を受け取る

<!-- section: 36.structured -->

ノートから、やることの一覧を取り出します。文章ではなく、プログラムが使える JSON が欲しい場面です。

<<< @/examples/36-bedrock/src/contract.ts{action-items}

Bedrock には、出力を JSON Schema に合わせる structured outputs という機能があり、頼み方は 2 つあります。`outputConfig.textFormat` に JSON Schema を渡すと、モデルの文章がそのスキーマに合う JSON になります。ツールの定義に `strict: true` を付けると、ツールの入力がスキーマに合うようになります。

ただし、対応はモデルごとです。Nova 2 Lite のモデルカードでは、structured outputs は非対応の側に載っています。Claude Haiku 4.5 は対応していますが、インドの profile 経由では使えない、という但し書きがあります。

そこで、同じ頼みを 2 つの形で書きます。

<<< @/examples/36-bedrock/src/structured.ts{request}

structured outputs が使えるモデルには、スキーマを渡します。使えないモデルには、ツールを 1 つだけ定義し、`toolChoice` でそのツールを名指しします。モデルは必ずそのツールを求めてくるので、入力を答えとして読みます。この形では、入力がスキーマに合う保証はなく、モデルが合わせてくれることに頼っています。`toolChoice` の名指しは、API リファレンスによると Anthropic Claude 3 と Amazon Nova のモデルだけが対応しています。

渡す JSON Schema は、Valibot のスキーマより緩くなります。

<<< @/examples/36-bedrock/src/structured.ts{json-schema}

structured outputs が受け付けるのは JSON Schema の一部です。文字列の長さと数値の範囲は書けず、`additionalProperties` は `false` 以外にできません。「期日は YYYY-MM-DD」「タスクは 200 文字まで」「20 件まで」といった条件は、スキーマでは伝えられません。

そのため、どちらの形で受け取っても、境界で Valibot に通します。

<<< @/examples/36-bedrock/src/structured.ts{validate}

structured outputs が保証するのは、JSON がスキーマの形をしていることまでです。値が業務として正しいかは、アプリが調べます。

検証に落ちたら、1 回だけ直させます。

<<< @/examples/36-bedrock/src/structured.ts{extract}

直させるときは、モデルの答えをそのまま会話に残し、どのフィールドがなぜ落ちたかを添えて、もう一度頼みます。それでも落ちたら `bad_output` で終わります。回数を 1 回にしているのは、直させるたびに会話が長くなり、入力の課金が増えるからです。`max_tokens` で切れた答えは、直させません。切れた原因は長さで、もう一度頼んでも同じところで切れます。

structured outputs には、遅延についての注意がドキュメントにあります。新しいスキーマは最初の利用のときにコンパイルされ、数分かかることがあります。コンパイルした結果は 24 時間キャッシュされます。スキーマを変えた直後の最初の呼び出しは、遅いものとして扱ってください。
