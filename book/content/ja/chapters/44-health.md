# 44 Health: AWS 側の障害とメンテナンスを知る

午前 3 時に、[19章](/ja/chapters/19-observability.md)のアラームが鳴ったとします。5xx の割合が上がっています。直前のデプロイが原因かもしれませんし、東京リージョンの Lambda で障害が起きているのかもしれません。前者なら自分たちで直せますが、後者なら待つしかなく、やるべきことがまったく違います。

もう 1 つ、別の場面があります。[23章](/ja/chapters/23-ec2.md)のインスタンスが載っているハードウェアが傷み、AWS が来週の火曜にそのインスタンスを止める予定を立てたとします。その知らせが誰に届くのかを、たいていのチームは決めていません。

どちらも AWS Health が扱う話です。この章では、AWS Health が知らせてくれること、知らせてくれないこと、知らせを受けたあとの動き方を整理します。そのうえで、Health のイベントを 19章と同じ通知の経路に流す小さなスタックを作ります。

前提は [19章](/ja/chapters/19-observability.md)です。イベントで関数を動かす考え方は [08章](/ja/chapters/08-async.md)、退役の対象になるインスタンスは [23章](/ja/chapters/23-ec2.md)で扱いました。コードは `examples/44-health/` にあります。

## 全体像

<!-- section: 44.overview -->

```figure

node health: AWS Health
node bus: default event bus | ap-northeast-1
node rules: ルール | source: aws.health
node fn: Lambda | 検証、分類、重複の排除
node ledger: DynamoDB テーブル | イベントごとの最後の状態
node topic: SNS topic
node mail: email
node dlq: SQS | デッドレターキュー
edge health -> bus: 少なくとも 1 回
edge bus -> rules
edge rules -> fn
edge fn -> ledger: 読んで、条件付きで書く
edge fn -> topic: 状態が変わったときだけ
edge topic -> mail
edge fn --x dlq: 3 回失敗したイベント
mark fn
```

AWS Health は、AWS のサービスに代わって利用者に知らせを送る仕組みです。知らせの 1 件を Health イベントと呼びます。コンソールで見るぶんには設定は要りませんが、見にいかなければ気づけない点は、19章の冒頭で書いたログと同じです。

この章のスタックは、Health イベントを EventBridge のルールで受け取り、関数で読み、短い文面にして SNS のトピックへ送ります。関数の仕事は 3 つあります。届いた JSON がドキュメントどおりの形かを Valibot で確かめること、イベントを「無視」「知らせるだけ」「期日までに対応」「障害」の 4 つに分けること、同じ状態を 2 回知らせないことです。

3 つ目が必要な理由は、Health のイベントが 1 回だけ届くものではないからです。配送は「少なくとも 1 回」で、障害が続くあいだは同じイベントが何度も更新されて届きます。何も考えずに転送すると、同じメールが重なり、順序が入れ替われば、終わった障害がもう一度始まったように見えます。

スタックは 2 つのリージョンに同じものを置きます。ルールは自分のリージョンに届いたイベントしか見られないからで、理由は[次のページ](/ja/chapters/44-health/build.md)で説明します。イベントが届かないあいだ、このスタックに料金はかかりません。

## 見る場所と届く経路

<!-- section: 44.pieces -->

Health の情報を見る場所は 2 つあります。

1 つは Service health のページ（`https://health.aws.amazon.com/health/status`）で、アカウントが無くても、サインインしなくても見られます。すべてのサービスとリージョンについて、AWS が公表した障害が並びます。過去 12 か月の履歴もここにあります。

もう 1 つは、サインインして開く自分のアカウントのダッシュボード（`https://health.aws.amazon.com/health/home`）です。「Your account health」には、公表された障害に加えて、自分のリソースに関わるイベントが出ます。タブは Open and recent issues、Scheduled changes、Other notifications、Event log の 4 つで、Event log には過去 90 日のイベントが残ります。

イベントには、公開の範囲による区別があります。public イベントは、アカウントに関係なく公表されるもので、そのサービスやリージョンを使っていなくても届きます。アカウント固有（account-specific）のイベントは、自分のリソースに関わるもので、影響を受けるリソースの ID が付きます。

内容による区別もあります。ドキュメントはカテゴリを 3 つ挙げています。

- issue: 予期しない障害です。サービスの劣化や、特定のリソースで起きている問題を知らせます
- scheduled change: 予定された変更です。インスタンスの退役やメンテナンス、ランタイムやバージョンのサポート終了がここに入ります。このカテゴリのイベントは、すべてアカウント固有です
- account notification: アカウントやサービスの管理、セキュリティに関する通知です。読むだけでよいものもあれば、急いで対応が要るものもあります

EventBridge に届くイベントの仕様には、4 つ目の値として `investigation` も載っていますが、何が入るのかは説明されていません。

イベントを受け取る経路は、次のとおりです。

| 経路 | 届くもの | 要るもの |
| --- | --- | --- |
| ダッシュボード | public とアカウント固有の両方 | サインインして見にいくこと |
| メール（AWS User Notifications の managed notifications） | アカウント固有のイベント。public イベントは届かない | 何もしなくても、アカウントの連絡先に届く |
| EventBridge（source は `aws.health`） | 両方。影響を受けるリソースの ID と状態も入る | リージョンごとのルール |
| AWS Health API | ダッシュボードと同じ情報 | 有料のサポートプラン |

メールについては、2025 年 12 月 15 日から、AWS User Notifications の managed notifications が配送を受け持っています。差出人は `health@aws.com` で、宛先は既定ではアカウントの連絡先（ルートユーザー、operations、billing、security のアドレス）です。User Notifications のコンソールで、受け取るカテゴリと、メール以外の届け先（チャット、モバイルアプリへのプッシュ通知）を選べます。User Notifications に料金はかかりません。

注意が要るのは、**public イベントが managed notifications では届かない**点です。東京リージョンの Lambda の障害は、自分のリソースに紐づけられないかぎり、メールでは来ません。public イベントを受け取るには、EventBridge のルールか、User Notifications の user-configured notification を自分で用意します。この章は前者を作ります。

### Health API とサポートプラン

Health API は、ダッシュボードに出る情報をプログラムから読むための API です。使うには、AWS Business Support+、AWS Enterprise Support、AWS Unified Operations のいずれかのサポートプランが要ります。これらのプランが提供されていないリージョンのアカウントや、まだ移行していないアカウントでは、以前の Business、Enterprise On-Ramp、Enterprise のプランでも使えます。どれにも入っていないアカウントから呼ぶと、`SubscriptionRequiredException` が返ります。ここまでは 2026-10-13 時点のユーザーガイドの記述です。同じ日の API リファレンスの冒頭は以前の 3 つのプランだけを挙げていて、2 つのページは揃っていません。

すべてのアカウントに付いている Basic Support だけの読者は、Health API を呼べません。それでも、ダッシュボード、メール、EventBridge は追加料金なしで使えます。イベントの中身はどの経路でも同じなので、この章は API を使わずに組み立てます。

サポートプランの料金は、いちばん安い Business Support+ で、アカウントごとに月 29 USD か、AWS の月額利用料の 9%（1 万 USD までの部分。それを超える部分は率が下がります）の、どちらか大きいほうです。

### アカウントが複数あるとき

AWS Organizations でアカウントを分けている場合は、organizational view を有効にすると、組織の全アカウントの Health イベントを 1 か所で見られます。コンソールで見るぶんには、どのサポートプランでも追加料金はかかりません。有効にする操作は管理アカウントで行います。

管理アカウントにふだんの作業を持ち込まないために、ドキュメントは、メンバーアカウントを委任された管理者（delegated administrator）として登録することを勧めています。登録できるのは 5 アカウントまでです。organizational view を有効にすると、管理アカウントか委任された管理者のアカウントの EventBridge に、全アカウントのイベントが 1 本の流れで届きます。この章のスタックは、そのアカウントに置けばそのまま使えるように、イベントをアカウント ID とイベントの ARN の組で区別しています。ただし、複数アカウントでの動作は確かめていません。

アカウントの分け方そのものは [33章](/ja/chapters/33-production-readiness.md)が扱います。

## 届かないもの

<!-- section: 44.silence -->

Health に何も出ていないことは、AWS に問題が無いことを意味しません。次の 3 つは、Health からは届きません。

1 つ目は、AWS がまだ公表していない劣化です。Health イベントは AWS が書いて出すもので、障害が始まってから公表されるまでには時間がかかります。その時間に上限があるという記述は、ドキュメントに見当たりませんでした。アラームが鳴った時点でダッシュボードが静かでも、AWS 側の障害である可能性は残ります。

2 つ目は、自分のクォータの使い切りです。Lambda の同時実行数の上限に当たって 429 が返るのは、サービスが仕様どおりに動いた結果で、障害ではありません。クォータは [32章](/ja/chapters/32-limits.md)で扱います。

3 つ目は、自分の設定の誤りです。IAM のポリシーを間違えて 403 が返っても、Health には何も出ません。

したがって、最初の合図はこれからも 19章のアラームです。Health は、アラームが鳴ったあとに「自分たちだけの問題かどうか」を確かめるための、もう 1 つの意見として使います。Health のイベントが来ないからといってアラームを疑う理由にはならず、Health のイベントが来たからといって、自分たちの障害の原因がそれだと決まるわけでもありません。

**使っているサービスとリージョンの障害。** まず、進行中のインシデントの記録に、Health イベントの ARN と時刻を書き足します。原因の切り分けが一段進みます。次に、新しいデプロイを始めないようにします。AWS 側が不安定なあいだにデプロイすると、失敗したときに原因を見分けられなくなります。[20章](/ja/chapters/20-shipping.md)のパイプラインなら、production の承認を出さずに置いておきます。すでに走っているジョブは、止めても CloudFormation の更新が途中のまま進むので、終わるのを待ちます。別のリージョンへ切り替えるかどうかは、Health の文面ではなく、前もって決めておいた自分たちの基準で判断します。基準と切り替えの手順は [28章](/ja/chapters/28-multi-region.md)と [40章](/ja/chapters/40-disaster-recovery.md)の主題です。Health の障害イベントには、対応が必要かどうかのラベル（actionability）が付きません。必要な対応はアプリの構成によって違うから、というのがドキュメントの説明です。

**予定された変更。** 担当者と期日を決めます。インスタンスの退役では、23章のインスタンスのようにルートボリュームが EBS なら、予定の時刻にインスタンスが停止されます。停止したインスタンスは起動し直せて、そのときに新しいハードウェアへ移ります。期日より前の都合のよい時間に、自分で停止して起動すれば済みます。インスタンスストアがルートボリュームのインスタンスは終了され、戻せません。メンテナンスの予定のイベントは、開始のおよそ 2 週間前に届くとされています。

**アカウントへの通知。** 期日のあるチケットにします。たとえば Lambda のランタイムのサポート終了は、該当するランタイムの関数があるアカウントに、少なくとも 180 日前に知らされます。半年先の話は、チケットにしなければ忘れられます。Health はこの種の変更を planned lifecycle event と呼び、イベントの開始時刻を変更の日付として扱うよう求めています。対応が済んだリソースは `PENDING` から `RESOLVED` に変わりますが、反映には最大で 72 時間かかることがあります。

**abuse とセキュリティの通知。** いちばん急ぎます。ドキュメントが例に挙げている abuse の報告は、対応しないとアカウントが停止されうるものです。EventBridge では `AWS Health Abuse Event` という別の種類のイベントとして届きますが、その中身の形はドキュメントに載っていません。この章の関数は、読めなかったイベントを捨てずに、「読めないイベントが届いた。ダッシュボードを開くこと」という通知にして送ります。不正利用への備えそのものは [21章](/ja/chapters/21-security.md)にあります。

## この構成にしなくてよい場合

ひとりで持っているアカウントなら、アカウントの連絡先のメールアドレスを、実際に読むアドレスにしておくだけで足ります。予定された変更とアカウントへの通知は、何も作らなくてもそこへ届きます。届かないのは public イベントですが、Service health のページを障害対応の手順書に載せておけば、見にいけます。

コードを書かずに public イベントも受け取りたいなら、User Notifications の user-configured notification があります。EventBridge のルールにあたる条件をコンソールで指定し、メールやチャットへ送れます。この章でそれを使わなかったのは、重複の排除と分類を自分で決めたかったからです。User Notifications にも通知をまとめる機能がありますが、この章では試していません。

反対に、この章の関数で足りなくなるのは、通知をチケットやオンコールの仕組みに直接つなぎたいときです。その場合も、分類と重複の排除までは同じで、SNS のトピックの先を替えるだけです。
