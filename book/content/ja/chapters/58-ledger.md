# 58 Ledger: QLDB のいまと、検証できる追記専用の台帳

「誰がいつ何をしたか」の記録を、あとから誰にも書き換えられない形で残したいことがあります。AWS にはそのためのサービスとして Amazon QLDB がありましたが、2025 年 7 月 31 日にサポートが終わり、いまは使えません。この章では QLDB の使い方は扱わず、QLDB が約束していた性質を、この本ですでに使った部品で組み立てます。

考え方は 1 つです。書き換えられない記録を、権限の設定だけで作ることはできません。そこで、書き換えたら必ず分かる形で記録し、その証拠を、自分でも消せない場所に置きます。記録は DynamoDB のテーブルに追記し、1 件ごとに前の 1 件のハッシュを持たせます。証拠は、末尾のハッシュを書き留めた小さなオブジェクトで、S3 の Object Lock をかけたバケットに置きます。

前提は [05章](/ja/chapters/05-dynamodb.md)の条件付き書き込み、[07章](/ja/chapters/07-uploads.md)の S3、[21章](/ja/chapters/21-security.md)の IAM と CloudTrail、[22章](/ja/chapters/22-recovery.md)のバックアップです。テーブルの読み書きには [30章](/ja/chapters/30-data-modeling.md)のインターフェースと、そのメモリ上のモデルを使います。コードは `examples/58-ledger/` にあります。

スタックに、置いてあるだけで時間課金されるリソースはありません。ただし、**ダイジェストを置くバケットは、スタックを消しても残ります**。ロックされたオブジェクトは、保持期間が過ぎるまで消せないからです。既定の設定では 1 日で、そのあとに自分で消します。手順は[費用、注意点、片付け](/ja/chapters/58-ledger/wrap.md)にあります。

## QLDB のいま

<!-- section: 58.qldb -->

AWS の General Reference には、提供を終えたサービスの一覧があります。2026-10-13 に読んだ時点で、Amazon Quantum Ledger Database（Amazon QLDB）は「Services in Full Shutdown」に載っていて、サポート終了日は 2025 年 7 月 31 日です。この段階のサービスは、AWS の品ぞろえから外され、どんな形でも提供もサポートもされません。同じ日に確かめたところ、QLDB の製品ページは Aurora のページへ転送され、開発者ガイドは 404 を返しました。

そのため、QLDB が何だったかは、AWS が移行のために書いたブログ記事から引きます。記事によると、QLDB の中心はジャーナルでした。ジャーナルは追記専用のデータ構造で、コミットされたトランザクションが順番に、変更できない記録として入ります。記録のブロックは暗号学的ハッシュで前のブロックとつながっていて、そのつながりを使って、履歴が書き換えられていないことを検証できました。記事は、変更できないことと、暗号で検証できることの 2 つを、QLDB に固有の性質と呼んでいます。

移行先として AWS が示したのは Aurora PostgreSQL です。記事は、台帳のデータを Aurora PostgreSQL に移す手順と、監査の用途で QLDB の機能を何で置き換えるかを説明しています。置き換えに挙がっているのは、pgAudit と CloudWatch Logs、トリガーで書く監査用のテーブル、AWS DMS、Database Activity Streams です。同じ記事は、Aurora PostgreSQL が変更の不変な記録を持たないことも書いています。履歴は監査データとして自分で作り、データベースの外に保存することになります。暗号による検証に当たるものは、記事の置き換えの中にありません。

既存のアカウントで QLDB の名前を見かけるとしたら、古い IAM ポリシーや、設計の資料の中です。新しく作れるものはありません。なお、同じ一覧の「Services in Sunset」には Amazon Managed Blockchain も載っていて、2027 年 9 月 29 日にサポートが終わります。「台帳」と名の付く AWS のサービスは、どちらも今から選ぶものではなくなりました。

## 全体像

<!-- section: 58.overview -->

```figure
caption: アプリは台帳に追記するだけです。1 時間ごとの関数が末尾のハッシュをロックつきのバケットに書き、監査する人は両方を読んで突き合わせます。
node app: ノートのアプリ | AppendAccess ポリシー
node table: DynamoDB テーブル | 番号つきの記録、ハッシュでつながる
node fn: Lambda 関数 | 1 時間ごと
node bucket: S3 バケット | Object Lock、バージョニング
node auditor: 監査する人 | AuditorRole
edge app -> table: PartiQL INSERT, Query
edge fn -> table: Query
edge fn -> bucket: PutObject (If-None-Match)
edge auditor -> table: Query
edge auditor -> bucket: ListObjectVersions, GetObject
mark bucket
```

台帳（ledger）は、番号の付いた記録の列です。記録は 1 件ごとに、自分の内容と 1 つ前の記録のハッシュから計算したハッシュを持ちます。この列をハッシュチェーン（hash chain）と呼びます。途中の 1 件を書き換えると、その後ろのハッシュがすべて合わなくなります。

ただし、テーブルを自由に書き換えられる人なら、後ろのハッシュもすべて計算し直せます。そうなると、テーブルだけを見ても書き換えには気づけません。そこで、ある時点の末尾の番号とハッシュを、テーブルの外に書き留めます。これをダイジェスト（digest）と呼びます。末尾のハッシュは、それまでの記録すべてから決まるので、1 つのダイジェストが、その時点までの履歴全体を代表します。

ダイジェストは、図で強調してある S3 のバケットに置きます。バケットには Object Lock をかけてあり、書いたオブジェクトのバージョンは、保持期間が過ぎるまで削除できません。検証では、テーブルの記録からハッシュを計算し直し、ロックされたダイジェストと突き合わせます。

状態の持ち主は 2 つあります。記録の持ち主は DynamoDB のテーブルで、証拠の持ち主は S3 のバケットです。2 つを同じ権限で書き換えられないようにすることが、この設計の中身です。

## 証明できることと、できないこと

<!-- section: 58.trust -->

この章の不変条件は、次の 1 文です。ダイジェストがロックされた時点より前の記録に対する変更、入れ替え、削除は、どれも検証で見つかる。

検証が何も見つけなかったときに言えるのは、最新のダイジェストまでの記録が、そのダイジェストを書いた時点のままだ、ということです。内容も、順番も、件数も変わっていません。この結論は、SHA-256 で同じハッシュになる別の内容を作れないことと、S3 がロックを守ることに依っています。

言えないことも、同じ重さで書いておきます。

- 追記された内容が事実かどうかは、台帳には分かりません。アプリが嘘を書けば、嘘が正しく保存されます。書かなかった出来事も、検証には出てきません
- 最新のダイジェストより後ろの記録は、まだ何にも守られていません。この部分を書き換えても、末尾を切り落としても、検証は通ります。既定では、この隙間は最長で 1 時間です。`test/verify.test.ts` に、検出できないことを確かめるテストを入れてあります
- 記録の時刻は、書いた側の時計の値です。S3 がオブジェクトを受け取った時刻のほうが信用できますが、この章の検証はそこまで見ていません
- テーブルを書き換えること自体は防げません。十分な権限を持つ運用者は、テーブルのアイテムを置き換えることも、テーブルごと消すこともできます。この設計が約束するのは、防ぐことではなく、あとから分かることです

信用しなければならない相手も決まっています。S3 が Object Lock を守ることは、AWS を信用します。governance モードでは、`s3:BypassGovernanceRetention` を持つ管理者がロックを外せるので、その管理者も信用することになります。compliance モードなら、root ユーザーを含めて誰も消せません。ダイジェストを書く関数のコードとロール、検証するコードも、信用の対象です。関数を乗っ取った人は、書き換えたあとの台帳のダイジェストをロックできます。それでも、乗っ取る前にロックされたダイジェストは消せないので、そこまでの履歴の書き換えは見つかります。

運用者と監査する人を本当に分けたいなら、ダイジェストのバケットを別のアカウントに置きます。アプリのアカウントの管理者は、そのバケットに対して何の権限も持ちません。アカウントを分ける話は [33章](/ja/chapters/33-production-readiness.md)にあります。この章のスタックは、1 つのアカウントに両方を置いています。

## 別の手段を選ぶとき

<!-- section: 58.fit -->

この台帳は、変更の履歴を残す仕組みとしては重いほうです。まず、もっと軽い手段で足りないかを考えます。

誰がどの API を呼んだかを知りたいだけなら、CloudTrail があります（21章）。DynamoDB のテーブルの作成や削除は既定で記録され、アイテムの読み書きは、証跡でデータイベントの記録を有効にすると記録されます。アプリの判断の履歴が要るだけなら、消さないと決めた監査用のテーブルと、22章のバックアップで足ります。ハッシュチェーンが要るのは、記録を管理している自分たちが書き換えていないことを、他人に示す必要があるときです。

逆に、この章の仕組みでは足りない場合もあります。

- 記録そのものを WORM（write once, read many）の媒体に置くことを、規制が求めている場合。S3 のユーザーガイドは、Object Lock が SEC 17a-4 などの規制に対して第三者の評価を受けていると書いています。その場合は、ダイジェストではなく記録そのものを、compliance モードのバケットに置く設計になります。自分の業務がどの規制に当たるかは、ここでは判断できません
- 1 件の記録が台帳に含まれることを、台帳全体を読まずに示したい場合。この章の検証は、ダイジェストまでの記録をすべて読みます
- 自分たちも AWS も信用しない相手に示す場合。複数の組織がそれぞれ写しを持つ仕組みが要ります。AWS の中でその役だった Amazon Managed Blockchain は、先に書いたとおり終了が決まっています
- リレーショナルデータベースの上で、SQL で履歴を引きたい場合。AWS が QLDB の利用者に示した道は Aurora PostgreSQL と監査用のテーブルです。Aurora は 60章で扱います

Cloudflare と Vercel についても、2026-10-13 に公式ドキュメントを確かめました。Cloudflare R2 には bucket locks があり、オブジェクトの削除と上書きを、日数、期日、無期限のいずれかで禁じられます。ルールはダッシュボードや Wrangler から外せます。バケットの持ち主にも外せないモードは、ドキュメントに見当たりませんでした。性質としては governance モードに近く、自分にも消せない証拠の置き場所にはなりません。Vercel Blob の概要のページには、保持期間でオブジェクトを守る機能の記述がありませんでした。ハッシュチェーンのほうは、どのデータベースの上でも同じように書けます。D1 でも Postgres でもかまいません。違いが出るのは、証拠を置く場所です。
