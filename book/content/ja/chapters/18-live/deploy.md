# 18 Live Streaming: デプロイ

このページでは、前のページまでに書いたチャンネルと視聴ページを AWS に置き、実際に配信して、止まったことを確かめます。後半では、配信の状態の変化を受け取る仕組みと、視聴者ごとの遅延の違いを扱います。

## 配信してみる

<!-- section: 18.broadcast -->

ここからは AWS のアカウントが必要で、料金も発生します。

```bash
vp run stream:infra:diff
vp run stream:infra:deploy
```

デプロイすると、チャンネル、ストリームキー、イベントを受ける Lambda とルールができます。この時点ではまだ何も流れていないので、IVS の料金はかかっていません。

### 配信ソフトの設定

OBS Studio を例にします。IVS のドキュメントは 30.2 以降を前提に書かれています。

```bash
vp run stream:key --show
```

1. OBS の Settings > Stream を開いて、Service に「Amazon IVS」を選ぶ
2. Stream Key に、いま表示された `sk_` で始まる値を貼る
3. Settings > Output で Output Mode を Advanced にして、Streaming タブの Keyframe Interval を 2 にする
4. Video Bitrate を、`stream:key` が表示した上限より低くする。720p なら 3,500 kbps 未満。余裕をみて 2,500 くらいから
5. Settings > Video の Output (Scaled) Resolution を 1280x720 にする
6. メイン画面で Start Streaming

Service の一覧に Amazon IVS がなければ、「Custom」を選んで、Server に `stream:key` が表示した `rtmps://...:443/app/` を入れます。

OBS を使わずに、動画ファイルを FFmpeg で送る方法も、IVS のドキュメントに例があります。

### 見る

別の端末で、再生 URL を視聴ページに渡してから開きます。

```bash
vp run stream:config
vp run preview:stream:web
```

`stream:config` は視聴ページをビルドし、スタックの出力から取った再生 URL を `web/dist/config.json` に書きます。`preview:stream:web` は、そのビルド結果を <http://localhost:4183> で配ります。

配信を始めてから見えるようになるまでには、少し時間がかかります。ドキュメントによると、キーフレームの間隔が 2 秒なら 6〜7 秒ほどです。その間、ページは「offline」と表示したまま待ち、自分で再接続します。

このページを人に見せるなら、`web/dist` を [03章](/ja/chapters/03-spa.md)の方法で S3 と CloudFront に置けば済みます。この章の主題はチャンネルなので、その構成はスタックに入れていません。

### 終わったら、止める

OBS の Stop Streaming を押します。押したら、止まったことを次の節で確かめます。

## 止まっていることを確かめる

<!-- section: 18.status -->

この章でいちばん大事な節です。

IVS の入力の料金は、映像が送られている時間に対してかかります。料金ページには「IVS に送られたすべての stream は、視聴されていなくても、入力の料金がかかる」と書かれています。視聴者が帰ったあとも、OBS が動いていれば課金は続きます。

OBS のウィンドウを閉じたつもりで最小化しただけだった、配信用の PC をそのままにして帰った、といったことは十分に起こります。だから、止まっていることをコマンドで確かめます。

```bash
vp run stream:status --expect-offline
```

このコマンドは、いま配信中かどうかを IVS に聞きます。配信中なら何分経ったかを表示して終了コード 1 で終わり、止まっていれば 0 で終わります。

IVS に聞くのに使っているのは `GetStream` という API で、応答の読み方に注意が要ります。

<<< @/examples/18-live/src/stream.ts{status}

配信していないチャンネルに `GetStream` を呼んでも、「オフラインです」という応答は返ってきません。返るのは `ChannelNotBroadcasting` という**エラー**です。API リファレンスにも、`OFFLINE` という state は返らないことがあるので頼らないように、と書いてあります。

ここで避けなければならないのは、エラーをすべて「オフライン」として扱うことです。権限が足りないときも、ネットワークが切れたときも、スロットリングに当たったときもエラーになりますが、どれも配信が止まっている証拠ではありません。「わからない」を「止まっている」と表示してしまえば、このスクリプトを使う意味がなくなります。そのため、`ChannelNotBroadcasting` だけをオフラインと読み、ほかのエラーは例外にしています。テストもこの区別を確かめています。

`viewerCount` にも注意が要ります。IVS が視聴者を数え終わらなかったときは `-1` が返るので、「視聴者 -1 人」と表示しないように `null` に直しています。

### 止まらないとき

OBS を操作できないときは、API で配信を切れます。

```bash
vp run stream:stop
```

ただし、多くの配信ソフトは、切られると自動で再接続します。`StopStream` のドキュメントにも、その注意書きがあります。確実に止めたいなら、先に鍵を消します。

```bash
vp run stream:infra:deploy -c streamKey=off
vp run stream:stop
vp run stream:status --expect-offline
```

鍵を消してから切れば、配信ソフトが再接続しようとしても通りません。

この 3 行が役に立つのは、止め忘れたときだけではありません。心当たりのない視聴者が見続けていて、出力の料金が増えているときにも、同じ 3 行で止められます。映像が入ってこなければ、IVS には配るものがないからです。金額は[費用のページ](/ja/chapters/18-live/wrap.md)の「URL が広まったとき」で計算します。

IVS の側にも、配信が続きすぎないようにする仕組みが 2 つあります。配信ソフトからのデータが 30 秒途絶えると IVS が切断することと、1 本の stream が最長 48 時間であることです。ただし、48 時間で切れても、再接続する設定の配信ソフトは新しい stream を始めるので、当てにはできません。

## 状態の変化を受け取る

<!-- section: 18.events -->

配信が始まったら通知したい、終わったら何かしたい、というときに、`GetStream` を毎秒呼ぶ必要はありません。IVS が EventBridge に送るイベントを受け取ります。

ルールは、`aws.ivs` から来たイベントのうち、このチャンネルのものだけを Lambda に渡します。Lambda に与えている権限は、自分のロググループに書くことだけです。IVS の権限は持たせていないので、この関数はストリームキーを読めません。

届いたイベントは、まず形を確かめます。

`event_name` を enum にせず、ただの文字列にしているのは意図したことです。イベントの種類は、こちらが知らないうちに増えるかもしれません。知らない名前のイベントが来たときは、失敗させずに、記録して先へ進めます。

形が合わないイベントが届いても、関数は失敗させません。

形が合わないイベントは、何度やり直しても合わないので、ログに残して正常に終わります。

### イベントは「だいたい届く」

IVS のドキュメントは、イベントを best effort で送ると書いています。具体的には、次のことが起こりえます。

- 届かないことがある
- 数時間遅れて届くことがある
- 順序が入れ替わることがある。「Stream End が Stream Start より先に届く」こともある

ドキュメントには、めったに起きないとも書いてあります。それでも、起きたときに「配信中」の表示がいつまでも消えないアプリでは困ります。

そこで、届いたイベントから「いま配信中か」を組み立てる関数を、**順序に頼らない**形で書きました。

<<< @/examples/18-live/src/timeline.ts{belief}

`believe` は、stream ごとに、どの名前のイベントを見たかの集合を作ります。終わりのイベントが集合に入っていれば、その stream は終わったと判断します。集合なので、イベントが届いた順番も、同じイベントが 2 回届いたことも、結果に影響しません。

終わりを最終的な状態として扱えるのは、stream の ID が使い回されないからです。チャンネルが配信を始めるたびに、新しい `stream_id` が付きます。終わりのあとに始まりが届いたとしても、それは遅れて届いた古い始まりであり、配信が再開したわけではありません。

テストでは、4 つのイベントを 24 通りすべての順序で流して、結論が変わらないことを確かめています。

それでも、**届かなかったイベント**には対処できません。終わりのイベントが届かなければ、この関数は「配信中」と言い続けます。そこで、イベントから組み立てた結論を `GetStream` の答えと照らし合わせます。

<<< @/examples/18-live/src/timeline.ts{reconcile}

```bash
vp run stream:status --events
```

このコマンドは、`GetStream` の答えと、ログに残ったイベントから組み立てた結論を並べ、食い違っていればどちらを信じるかを表示します。信じるのは `GetStream` です。

この節から持ち帰ってほしい設計の指針は、状態の持ち主に状態を聞くことです。イベントは「何かが変わったらしい」という合図にすぎず、状態を持っているのは IVS なので、いまの状態は IVS に聞きます。イベントだけで状態を組み立てて、それを正しいものとして扱うアプリは、イベントが 1 つ届かなかった日に壊れます。

## 視聴者ごとに「いま」が違う

<!-- section: 18.latency -->

ライブ配信には、分散システムとして見たときの面白い性質があります。**全員が同じ映像を見ているのに、同じ瞬間は見ていません。**

```figure
caption: 知らせはチャットで 2 人に同時に届き、ゴールの映像は視聴者ごとに違う遅れで届く（時刻は説明のための作り物で、測った値ではない）
type: sequence
actor cam: カメラ
actor chat: チャット | 別の経路
actor a: 視聴者 A | デスクトップ
actor b: 視聴者 B | iOS のブラウザ
step cam -> cam: 12:00:00 ゴールが決まる
step chat -> a: 12:00:00 "GOAL!"
step chat -> b: 12:00:00 "GOAL!"
step cam -> a: 12:00:03 ゴールの映像
step cam -> b: 12:00:08 ゴールの映像
```

視聴者 A と視聴者 B で遅延が違うのは、珍しいことではありません。ドキュメントによれば、遅延は配信者と視聴者の場所、回線、途中の部品で変わります。加えて、iOS のブラウザは低遅延の再生に対応していないので、通常の遅延になります。同じ配信を同じ部屋で PC と iPhone で開くと、音がずれて聞こえるはずです。

視聴ページには、その視聴者の遅延を表示しています。表示しているのはプレイヤーの `getLiveLatency()` が返す値で、サーバーからプレイヤーまでの遅延です。カメラからサーバーまでの遅延は含みません。

遅延の違いが問題になるのは、映像とは**別の経路**で届くものを映像と組み合わせたときです。チャット、投票の結果、スコアの表示、「配信が終わりました」の通知がそうです。図のとおり、チャットの「GOAL!」は映像より先に全員へ届き、結果を先に知らせてしまいます。しかも、どれだけ先に届くかは視聴者ごとに違うので、サーバー側で「3 秒待ってから送る」と決めても全員には合いません。

invariant として書くと、こうなります。**別の経路で届くものが、映像のどの場面と同時に見えるかは、保証されない。** 映像と同期している前提で画面を作ってはいけません。

### 映像と一緒に届けたいもの

クイズの問題を映像のその場面で全員に出したい、というように、どうしても映像と合わせたいものには、IVS の **timed metadata** が使えます。

1 KB までの小さなデータを `PutMetadata` で送ると、IVS が映像の中に埋め込みます。視聴者には、映像のその位置を再生したときに届きます。遅延が 3 秒の人には 3 秒後、8 秒の人には 8 秒後で、それぞれにとっての「同じ場面」で届くことになります。

視聴ページは、届いた timed metadata をそのまま表示します。`player.ts` の `TEXT_METADATA_CUE` で受け取っています。配信中に、ドキュメントにある CLI のコマンドで試せます。

```bash
aws ivs put-metadata --channel-arn <ChannelArn> --metadata '{"question":"..."}'
```

ただし、timed metadata には制約があります。ドキュメントにあるとおり、送ってから埋め込まれるまでの時間に保証はなく、送れるのは 1 つのチャンネルに毎秒 5 回まで、それも配信中だけです。チャットの代わりにはならないので、「映像のこの場面で」と言いたいものだけに使います。

このコマンドと、ページでの表示は、実機では確かめていません。
