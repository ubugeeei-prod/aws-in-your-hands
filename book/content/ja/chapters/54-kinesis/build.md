# 54 Kinesis: しくみと実装

[最初のページ](/ja/chapters/54-kinesis.md)で、リビジョンを stream に書き、関数が順に読んで履歴を作る構成を見ました。このページでは、レコードの形、shard と順序、書く側、読む側、event source mapping の設定、スタックの順にコードを読みます。

## レコードの形

<!-- section: 54.record -->

<<< @/examples/54-kinesis/src/revision.ts{revision}

リビジョンは、ノート 1 つの変更 1 回です。`version` は 05章でノートが持っている版で、書き込みが成功するたびに 1 つ増えます。ノートの ID と版の組は、誰が何回送っても同じリビジョンを指します。重複を見分けるのに使うのは、この組です。

Kinesis もレコードに sequence number という番号を付けますが、重複の見分けには使えません。書く側が同じリビジョンを 2 回送れば、stream には別々の sequence number を持つレコードが 2 件できるからです。Kinesis のドキュメントも、厳密さが要るアプリケーションには、レコードの中に自前のキーを入れるよう勧めています。

partition key はノートの ID にしました。同じノートのリビジョンが 1 つの shard に並び、順序が保たれます。

本文も題名も入れていません。レコードは 24 時間 stream に残り、読める人は全員が読めます。運ぶのは、誰のどのノートが何版になったかだけです。

<<< @/examples/54-kinesis/src/revision.ts{codec}

レコードの中身は、Kinesis にとってはただのバイト列です。JSON であることも、リビジョンの形をしていることも、読む側が確かめます。

確かめて通らなかったレコードは、何度読み直しても通りません。こうしたレコードを poison record と呼び、専用のエラーにしてあります。あとで出てくる再試行の設定は、一時的な失敗と poison record を区別できないので、ログで区別できるようにするためです。

3 つ目の検査は、partition key とリビジョンのノートが一致することです。ノート n1 のリビジョンが別のキーで書かれると、そのレコードは n1 のほかのリビジョンとは別の順序で届くかもしれません。順序を信用できないレコードは、受け取りません。

## shard と順序

<!-- section: 54.shards -->

partition key がどの shard に入るかは、ハッシュで決まります。ドキュメントによると、Kinesis は partition key の MD5 を 128 ビットの整数として読み、その値を範囲に含む shard にレコードを入れます。shard はそれぞれ、0 から 2^128 − 1 までのうちの連続した範囲を受け持っています。

<<< @/examples/54-kinesis/src/local-stream.ts{hash}

手元のモデルも同じ計算をします。モデルについては[手元で動かすページ](/ja/chapters/54-kinesis/local.md)で説明します。

順序について、ドキュメントが約束していることは次のとおりです。

- 同じ partition key のレコードは、同じ shard に入る
- GetRecords で受け取るレコードは、sequence number の順に並んでいる
- sequence number は shard の中で増えていく。別の shard の番号とは比べられない

約束していないこともあります。別々の shard にあるレコードのあいだに、順序はありません。ノート a の版 2 とノート b の版 1 のどちらが先に読まれるかは決まっていません。この章の履歴はノートごとなので、それで足ります。

sequence number は 10 進の文字列で、ドキュメントの例では 56 桁あります。JavaScript の number には収まらないので、比べるときは `BigInt` にします。連番でもありません。

### partition key の選び方

partition key は、順序を保ちたい単位と、負荷を散らしたい単位の両方を決めます。

ノートの ID にすると、順序はノートごとに保たれ、ノートがたくさんあれば shard にまんべんなく散ります。利用者の ID にすると、利用者ごとの順序が保たれるかわりに、よく書く利用者 1 人のレコードが 1 つの shard に集まります。固定の文字列にすると、全体の順序が保たれるかわりに、shard を何本にしても 1 本しか使われません。

1 つのキーに書き込みが集中して shard の上限を超えると、そのキーのレコードは `ProvisionedThroughputExceededException` で断られます。ほかの shard が空いていても変わりません。この状態を hot key と呼びます。shard を増やしても、1 つのキーは 1 つの shard にしか入らないので、解決しません。

### shard を分ける、まとめる

shard の数は、あとから変えられます。この操作を resharding と呼び、1 つを 2 つに分ける split と、2 つを 1 つにまとめる merge があります。

分けられた元の shard（親）は閉じられて、新しいレコードを受け付けなくなります。すでに入っているレコードは、保持期間が切れるまで親に残ります。新しいレコードは、子の shard に入ります。

ここに順序の落とし穴があります。あるノートの版 1〜3 が親にあり、split のあとで書かれた版 4 と 5 が子にあるとき、子を先に読むと版 4 が版 1 より先に届きます。Kinesis のガイドは、親を最後まで読み切ってから子を読むよう求めています。親を読み切ったことは、GetRecords が次の位置を返さなくなることで分かります。

Lambda の event source mapping がこの順で読むかどうかは、読んだ Lambda のドキュメントからは確認できませんでした。この章のコンシューマーは、そうでなくても履歴が巻き戻らないように作ってあります。

## 書く側

<!-- section: 54.producer -->

書き込みの API は 2 つあります。PutRecord は 1 件ずつ、PutRecords は 1 回に 500 件まで、合計 10 MiB までをまとめて送ります。

PutRecords は、全体として成功か失敗かを返す API ではありません。1 件ごとに受け付けるか断るかを決め、断った 1 件があっても、その後ろのレコードは処理します。応答には、リクエストと同じ順で、1 件ごとの結果が並びます。

そのため、同じノートのリビジョンを 2 つ、1 回のリクエストに入れると、順序が入れ替わることがあります。

<<< @/examples/54-kinesis/src/producer.ts{put-naively}

この関数は、ドキュメントの例と同じことをしています。1 回送り、断られたものだけをもう一度送ります。版 1 と版 2 を一緒に送って版 1 だけが断られると、stream には版 2、版 1 の順で入ります。一度入ったレコードの順序は、あとから変えられません。API リファレンスも、PutRecords は順序を保証しないと書いています。

<<< @/examples/54-kinesis/src/producer.ts{plan}

この章の書く側は、1 回のリクエストに、同じ partition key のレコードを 2 つ入れません。リビジョンの列を「ラウンド」に分け、同じノートの次のリビジョンは、必ず次のラウンドに回します。別々のノートのリビジョンは、同じラウンドにいくつ入っても構いません。

<<< @/examples/54-kinesis/src/producer.ts{put-in-order}

ラウンドは 1 つずつ送ります。断られたレコードがあれば、そのラウンドの中で送り直し、全部が入るまで次のラウンドには進みません。決めた回数で入り切らなければ、そこで止めて、まだ送っていないレコードを呼び出し元に返します。先へ進めば、後ろの版が前の版を追い越すからです。

引き換えにするのは、リクエストの回数です。1 つのノートのリビジョンを 5 件続けて書くと、リクエストは 5 回になります。たくさんのノートを 1 件ずつ書くなら、500 件が 1 回で済みます。

API リファレンスが順序のために勧めているのは、PutRecord を 1 件ずつ呼び、前のレコードの sequence number を `SequenceNumberForOrdering` に渡す書き方です。この章がそうしなかったのは、ノートがたくさんあるときに 1 件 1 リクエストになるからです。同じノートのレコードを同じリクエストに入れない、という条件だけで、PutRecords でも同じ順序が保てます。

### 送り直しと重複

リクエストを送ったあと、応答が返る前に接続が切れることがあります。書く側には、レコードが入ったのかどうかが分かりません。もう一度送れば、入っていた場合は同じリビジョンが 2 件になります。

これは防げません。防がずに、読む側で 1 回だけ効かせます。リビジョンにノートの ID と版を入れてあるのは、そのためです。

### 2 つの書き手

`putInOrder` が守るのは、1 つの書き手が送る順序です。2 つのプロセスが同じノートのリビジョンを別々に送る場合、どちらが先に stream に入るかは、この関数には決められません。順序の出どころが DynamoDB のテーブルなら、最初のページで書いたとおり、DynamoDB Streams のほうが合っています。

<<< @/examples/54-kinesis/src/kinesis-writer.ts{writer}

SDK を呼ぶ部分は、これだけです。stream は ARN で指定します。応答の配列を、sequence number があれば成功、なければエラーコードとして読み替えます。

## 読む側

<!-- section: 54.consumer -->

<<< @/examples/54-kinesis/src/history.ts{history}

履歴は、ノートごとに 1 つのアイテムです。`version` はこれまでに適用したいちばん高い版で、`revisions` は適用したリビジョンの数です。すべてのリビジョンが順に 1 回ずつ適用されていれば、2 つは同じ値になります。差があれば、届かなかったか、遅れて届いて捨てられたリビジョンがあります。

<<< @/examples/54-kinesis/src/dynamodb-history.ts{apply}

適用は、条件付きの UpdateItem 1 回です。条件は「このノートのアイテムがまだ無いか、保存してある版がこのリビジョンの版より小さい」。通れば、版を進めて `revisions` に 1 を足します。

この条件 1 つが、2 つの役目を果たします。同じリビジョンがもう一度届くと、保存してある版と同じなので通りません。古いリビジョンが遅れて届いても通りません。比べるのと書くのが 1 回のリクエストなので、2 つの配送が同時に来ても、両方が通ることはありません。05章の楽観的ロックと同じ道具です。

条件が通らなかったことは、エラーではなく答えとして返します。

版が 1 つ飛んでいても、通します。版 1 のあとに版 3 が来たら、履歴は版 3 に進み、`revisions` は 2 になります。飛んだ版を待つ作りにしなかったのは、待っても来ないことがあるからです。あとで見るように、event source mapping は処理できない batch を諦めて先へ進みます。諦められた batch に版 2 が入っていたら、版 2 を待つコンシューマーは、そのノートについて永久に止まります。この章は、止まらずに進み、欠けたことを数で残すほうを選びました。

<<< @/examples/54-kinesis/src/consumer.ts{event}

関数が受け取るイベントも、外から来る値です。使う欄だけを Valibot で確かめます。`data` は base64 の文字列で、`approximateArrivalTimestamp` は秒で表した時刻です。

<<< @/examples/54-kinesis/src/consumer.ts{handler}

ハンドラーは、レコードを届いた順に適用します。適用できないレコードに当たったら、そこで止まり、そのレコードの sequence number を返します。この返し方を partial batch response と呼びます。「ここより前は済んだ。ここから先をもう一度」という意味になります。

失敗したレコードを飛ばして続きを処理しないのは、順序のためです。失敗したのがノート a の版 2 で、続きに版 3 があれば、版 3 を先に適用することになります。

## event source mapping の設定

<!-- section: 54.mapping -->

関数がいつ、何件で呼ばれ、失敗したらどうなるかは、event source mapping の設定で決まります。既定値のままでは危ない項目が多いので、1 つずつ見ます。既定値と上限は、2026-10-13 に Lambda のドキュメントで読んだものです。

<<< @/examples/54-kinesis/src/settings.ts{settings}

この値は、スタックがそのままデプロイし、手元のモデルも同じ値でテストします。

`batchSize` は、1 回の呼び出しに入れるレコードの最大数です。既定は 100、上限は 10,000 です。`maximumBatchingWindowSeconds` は、batch が埋まるのを待つ時間で、既定の 0 ではレコードが届きしだい呼び出します。Lambda は shard ごとに 1 秒に 1 回の頻度で読みにいき、溜まっていれば追いつくまで続けて呼び出すと、ドキュメントにあります。

`parallelizationFactor` は、1 つの shard を同時にいくつの batch で処理するかです。既定は 1 で、10 まで上げられます。上げても partition key ごとの順序は保たれる、とドキュメントにあります。shard 全体の順序は保たれなくなります。この章は 1 のままです。

### 失敗したとき

関数がエラーを返すと、Lambda は同じ batch をもう一度渡します。成功するまで、その shard の続きは読みません。

`maximumRetryAttempts` の既定は −1 で、レコードが stream から消えるまで再試行を続けます。poison record が 1 件あると、保持期間のあいだ shard が止まります。ドキュメントは、既定の設定では壊れたレコードが shard を最長 1 週間止めうる、と書いています。この章は 3 回にしました。最初の 1 回と合わせて 4 回試し、だめなら諦めます。

`maximumRecordAgeSeconds` は、古すぎるレコードを諦める設定です。既定の −1 では、古さを理由に諦めることはありません。この章は 6 時間にしました。保持期間の 24 時間より短いので、諦められたレコードは、そのあと 18 時間は stream から読み戻せます。

`bisectBatchOnFunctionError` を有効にすると、失敗した batch を 2 つに割って、それぞれを試します。割ることを繰り返すと、悪いレコードが 1 件だけの batch に追い込まれます。割ることは再試行の回数に数えない、とドキュメントにあります。

`reportBatchItemFailures` は、関数が返した partial batch response を Lambda に読ませる設定です。この設定には罠があります。**有効にしていないと、関数が失敗を返しても、Lambda はその batch を成功として扱います。** この章のハンドラーは例外を投げずに失敗を返すので、設定が抜けると、失敗したレコードとその後ろが黙って読み飛ばされます。スタックのテストは、この設定が入っていることを確かめています。

### 諦めた batch の行き先

再試行が尽きるか、古くなりすぎると、Lambda はその batch を捨てて先へ進みます。`onFailure` に送り先を指定しておくと、捨てたことの記録が残ります。送り先には SQS、SNS、S3 などを選べます。

<<< @/examples/54-kinesis/src/failure-record.ts{failure-record}

SQS に届く記録に、レコードの中身は入っていません。入っているのは、stream の ARN、shard、最初と最後の sequence number、件数、届いた時刻です。中身は、この範囲を stream から読み戻して確かめます。stream がレコードを持っているあいだしか読み戻せないので、記録が届いたら、保持期間が切れる前に見る必要があります。S3 を送り先にすると、呼び出しのイベントそのものも保存されます。この章は、扱う部品を増やさないために SQS にしました。

### 読み始める位置

mapping を作るときに、どこから読むかを決めます。`TRIM_HORIZON` は残っているいちばん古いレコードから、`LATEST` はいまより後に書かれたレコードから、`AT_TIMESTAMP` は指定した時刻からです。

この章は `TRIM_HORIZON` にしました。Lambda のドキュメントによると、mapping が読み始めるまでには数分かかることがあり、`LATEST` ではそのあいだに書かれたレコードを取りこぼすことがあります。

### iterator age

Lambda は、関数に渡したイベントの最後のレコードが stream に届いてからどれだけ経っているかを、`IteratorAge` というメトリクスに出します。コンシューマーが追いついていれば小さく、詰まっていれば、時間が経つのと同じ速さで増えていきます。この値が保持期間に届くと、レコードは読まれないまま消えます。

スタックは、この値が 30 分を超えたら鳴るアラームを持っています。

## 読み手を増やす

<!-- section: 54.readers -->

同じ stream を別の関数にも読ませたければ、event source mapping をもう 1 つ作ります。位置は mapping ごとに覚えているので、互いに影響しません。

ただし、読み取りの帯域は分け合います。ドキュメントによると、ふつうの読み手（shared throughput）は、shard 1 つにつき 1 秒 2 MB を全員で分け、GetRecords を呼べるのは shard あたり 1 秒に 5 回までです。書かれてから読み手に届くまでの遅れは、読み手が 1 つなら平均 200 ミリ秒ほど、5 つなら 1,000 ミリ秒ほどとされています。

enhanced fan-out は、読み手を stream に登録して、shard ごとに専用の 2 MB/秒を持たせるしくみです。Kinesis が HTTP/2 でレコードを送ってくるので、遅れは読み手の数によらず 70 ミリ秒ほど、とドキュメントにあります。料金は、読み手 1 つと shard 1 つの組につき 1 時間 0.0195 ドルで、shard 1 つをもう 1 本持つのと同じ額です。それに加えて、読んだ量 1 GB につき 0.0169 ドルがかかります。登録できるのは、provisioned と on-demand の Standard では stream あたり 20 までです。

読み手が 1 つか 2 つで、数百ミリ秒の遅れが問題にならないなら、enhanced fan-out は要りません。この章のスタックも使っていません。

Lambda を使わずに読むなら、どこまで読んだか（チェックポイント）を自分で保存します。Kinesis Client Library（KCL）は、その保存と、複数のワーカーへの shard の割り振り、resharding への追従を引き受ける Java のライブラリです。ほかの言語からは、MultiLangDaemon という Java のデーモンを介して使います。この本では扱いません。

<<< @/examples/54-kinesis/src/shard-order.ts{shard-order}

この章の 2 つ目の読み手（`kinesis:replay`）は、GetRecords を直接呼びます。チェックポイントは持たず、毎回最初から読みます。shard を親から子の順に並べ、1 本ずつ最後まで読むので、resharding のあとでもノートごとの順序は保たれます。

`ConsumerBehind` は読む側です。`IteratorAge` の最大値が 30 分を超えたら鳴ります。関数が呼ばれていないあいだはデータが無いので、その期間は正常として扱います。

`RecordsGivenUp` は、諦められた batch です。失敗のキューに 1 件でもあれば鳴ります。キューを空にするまで鳴り続けるので、見たあとで消す手順を[デプロイのページ](/ja/chapters/54-kinesis/deploy.md)に書きました。

`WritesRefused` は書く側です。stream が書き込みを断った数（`WriteProvisionedThroughputExceeded`）が、5 分ごとの集計で 3 回続けて 0 より大きいときに鳴ります。一瞬の超過は書く側の再試行で吸収されるので、15 分続いたときだけ知らせます。

このスタックのリソースは 12 種類で、どれも、この本が固定している cdkd 0.296.28 が専用の実装を持っています。Cloud Control API を経由する種類はありません。
