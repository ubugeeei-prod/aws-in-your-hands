# 14 Cache: 手元で動かす

## 手元で動かす

<!-- section: 14.local -->

ここまでに作ったレート制限とキャッシュを、1 つの API として手元で動かします。最初はメモリのストアを使います。`examples/14-kv-cache/.env.example` を、同じ場所に `.env` という名前でコピーしてください。

<<< @/examples/14-kv-cache/.env.example

```bash
vp run dev:kv
```

別のターミナルから、6 回呼びます。

```bash
curl -s -i http://localhost:8794/items
```

1 回目は `x-cache: miss` で、300 ミリ秒ほどかかります。2 回目からは `x-cache: hit` で、すぐに返ります。`ratelimit-remaining` が 4、3、2 と減っていき、6 回目には 429 と `retry-after` が返ります。

この 5 回を誰のぶんとして数えるかは、リクエストの送信元のアドレスで決めています。

<<< @/examples/14-kv-cache/src/caller.ts{address}

AWS では、API Gateway が見た送信元の IP アドレスを使います。このアドレスはイベントの `requestContext` に入っていて、呼ぶ側がヘッダーで書き換えることはできません。手元の開発サーバーでは、ソケットの相手のアドレスを使います。`x-forwarded-for` のようなヘッダーは、呼ぶ側が好きな値を書けるので、読みません。

`Request` には送信元のアドレスが入っていません。そのため、アプリはアドレスを 2 つ目の引数で受け取ります。Lambda のハンドラーはイベントから取り出して渡します。開発サーバーは、04章の `nodeServer` が教えてくれるソケットの相手のアドレスを渡します。

<<< @/examples/14-kv-cache/src/dev.ts{dev}

<<< @/examples/14-kv-cache/src/caller.ts{subject}

IPv6 のアドレスは、先頭の 64 bit でまとめて数えます。1 つのネットワークが、それだけの数のアドレスを 1 人に配るからです。アドレスが取れなかったリクエストは、全員まとめて 1 つの枠で数えます。設定を間違えたときに、制限が緩むのではなく厳しくなるようにするためです。

`x-client-id` のようなヘッダーで名乗ってもらう方式にしなかったのは、防御にならないからです。別の名前を名乗れば上限は別に数えられ、名乗るたびにストアの項目が 1 つ増えます。認証の前に置くレート制限は、呼ぶ側が選べないもので数えます。

IP アドレスで数える方式にも限界があります。会社や学校のように出口が 1 つのネットワークでは、中の全員が 5 回を分け合います。逆に、アドレスをたくさん持っている相手は、アドレスの数だけ枠を持ちます。利用者を見分けたいなら、[06章](/ja/chapters/06-auth.md)の検証済みのトークンから ID を取ってください。IP アドレスで数えるレート制限は、認証の手前に置く、大まかな歯止めです。

アプリの中では、レート制限がキャッシュより先に走ります。`limited` は `/items` のルートを包む関数で、枠が残っているときだけ中のルートを呼びます。

<<< @/examples/14-kv-cache/src/app.ts{limit}

`catch` の中では、数えるストアが落ちたときに、リクエストを通すか断るかを決めています。これは技術ではなく、プロダクトの判断です。一覧の API なら、ストアの障害で API まで止めたくないので、通すほうがよいでしょう。ログインの試行なら、守りが外れた状態で通したくないので、断るほうがよいでしょう。そのため、`catch` の奥に固定せず、`RATE_ON_ERROR` という設定にしてあります。

この章のスタックは `allow` にしていて、それには代償があります。ストアが落ちているあいだはアプリの上限が効かず、同じ相手が何回でも通ります。そのとき残っている歯止めは、API の手前に置いたステージのスロットリング（API 全体で 1 秒に 10 件。設定は[デプロイ](/ja/chapters/14-kv-cache/deploy.md)のページにあります）だけです。それでは足りない API なら、`deny` にしてください。

どのストアを使うかは、起動時に環境変数で決まります。

### Valkey と DynamoDB Local で動かす

本物のサーバーに対して動かすには、コンテナを 2 つ立てます。

```bash
vp run kv:local:start
vp run kv:local:migrate
vp run kv:test:local
```

`kv:local:start` を実行するには、Docker のデーモンが動いている必要があります。devShell に入っても Docker は付いてこないので、Docker Desktop などを別に起動しておいてください。立ち上がるのは `valkey/valkey:9.0.6-alpine`（ポート 6390）と `amazon/dynamodb-local:3.3.1`（ポート 8001）です。

`kv:test:local` は、[章の最初のページ](/ja/chapters/14-kv-cache.md)で紹介したコントラクトテストを、この 2 つに対して流します。どちらかが動いていなければ、スキップではなく失敗にしています。スキップは、一見すると成功に見えるからです。

`.env` の `KV_STORE` を `valkey` か `dynamodb` に変えれば、`vp run dev:kv` もそのストアを使います。

この章を書いたマシンには Docker のデーモンが無く、`kv:local:start` は実行できていません。かわりに、Valkey 9.1.2 と DynamoDB Local 3.3.1 をコンテナではなくプロセスとして立てて、コントラクトテストの 22 件と `dev:kv` を通しました。テストとアプリは本物のサーバーで確かめてあり、コンテナを立てるタスクだけが未確認です。

手元では再現しないものも、挙げておきます。

- IAM と TLS。手元の Valkey には、パスワードも TLS もありません。トークンの署名と TLS 1.3 の接続は、ElastiCache でしか確かめられません
- cluster mode。手元の Valkey は 1 台です。ElastiCache Serverless は cluster mode で動き、クライアントの動きが変わります
- TTL による削除。手元では、期限切れの項目が消えるかどうかに頼っていません
- 実行環境が複数あること。開発サーバーはプロセスが 1 つなので、メモリのレート制限も正しく動いて見えます

このうち、最後の点にはとくに注意してください。`KV_STORE=memory` は、手元では正しく動いて見えますが、Lambda にのせると上限が緩みます。
