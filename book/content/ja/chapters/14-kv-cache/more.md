# 14 Cache: 実装のつづき

## キャッシュに置けるのは、消えても困らないもの

<!-- section: 14.cache -->

[前のページ](/ja/chapters/14-kv-cache/build.md)までで、レート制限の数を DynamoDB と Valkey に置きました。このページでは、もう 1 つの題材である一覧のキャッシュを作ります。

キャッシュの原則は、**正しいのは元データで、キャッシュはその写しである**、ということです。写しはいつ消えてもよく、消えたら元データからもう一度作れます。この関係が成り立たないデータを、キャッシュに置いてはいけません。

元データは、次のインターフェースにしてあります。

<<< @/examples/14-kv-cache/src/catalog.ts{source}

この元データは作りもので、固定の一覧を、わざと 300 ミリ秒遅らせて返しています。本物のシステムなら、[13章](/ja/chapters/13-sql.md)の SQL の集計や、ほかのチームの API にあたる場所です。キャッシュが効くのは、元データが遅いか、呼ぶたびに料金がかかるときなので、その代役を置きました。

読み方は read-through です。まずキャッシュを読み、無ければ元データを読んで、写しをキャッシュに入れます。

<<< @/examples/14-kv-cache/src/read-through.ts{optional}

要点は、キャッシュへの読み書きを `try` で囲んでいることです。キャッシュが落ちていても、遅くても、読めない値が入っていても、リクエストは元データから答えます。遅くはなりますが、間違った値は返しません。キャッシュの障害で API が 500 を返すのは、キャッシュをデータの持ち主のように扱ってしまったときです。

応答には、その一覧がいつ元データから出てきたかを載せています。

<<< @/examples/14-kv-cache/src/contract.ts{list}

`x-cache` ヘッダーは `hit` か `miss` かを、`age` ヘッダーは何秒前の写しかを伝えます。呼ぶ側が「この値はどれくらい古い可能性があるのか」を知る手段を、最初から付けておきます。

### 古い値を読む場面の再現

キャッシュを持つと、元データと食い違う時間が必ず生まれます。これを stale read と呼びます。3 つのテストで、単純な形から順に再現します。

<<< @/examples/14-kv-cache/test/read-through.test.ts{stale}

1 つ目のテストは、元データを `v2` に変えても、TTL が切れるまでは `v1` が返ることを確かめています。これは不具合ではなく、TTL を 30 秒にした時点で受け入れた仕様です。

2 つ目は、書いた側がキャッシュを消せば、次の読み取りで新しい値になることを確かめています。元データを変えたらキャッシュを消す、というのはよく使われる対策です。

3 つ目は、キャッシュを消しても古い値が残る場合があることを示しています。

```figure
caption: 読む側が元データに聞いている最中に、書く側が更新と削除を済ませると、古い値がキャッシュに入り、TTL が切れるまで読む側の全員に返る
type: sequence
actor reader: 読む側
actor cache: キャッシュ
actor source: 元データ
actor writer: 書く側
note cache: (空)
note source: v1
step reader -> cache: t1 ミス
step reader -> source: t1 元データに聞く
step writer -> source: t2 元データを更新する
note source: v2
step writer -> cache: t3 キャッシュを消す
note cache: (空): 消すものが無い
step source --> reader: t4 "v1" を受け取る
step reader -> cache: t4 "v1" を保存する
note cache: v1 (元データは v2)
note cache: t5 TTL まで "v1" を返す
```

読む側が元データに聞いている最中に、書く側が更新と削除を済ませます。そのあとで、読む側が持っていた古い答えがキャッシュに入ります。削除はもう済んでいるので、この古い値を消しに来る人はいません。

この食い違いを防ぎきる方法は、この章のコードにはありません。バージョンを比べてから書くなどの手はありますが、複雑になります。この章では、キャッシュの削除は古い時間を短くするためのもので、古さの上限を決めているのは TTL だ、と考えます。したがって TTL は、「最悪この時間だけ古くてもよい」と言える長さにします。そう言えないデータ（残高、在庫、権限）は、キャッシュせずに元データを読みます。

## 期限切れの瞬間に集中する読み込み

<!-- section: 14.stampede -->

キャッシュがよく効いている API ほど、写しの期限が切れた瞬間が危険になります。

その瞬間に 100 件のリクエストが来ていたら、100 件ともミスし、100 件とも遅い元データへ取りに行きます。キャッシュが守っていたはずの元データに、いちばん大きな負荷がかかるわけです。これをキャッシュスタンピード（cache stampede）と呼びます。

テストでは、10 個の実行環境が同時にミスする場面を作り、元データが 10 回呼ばれることを確かめています（「sends every caller to the source when nothing coordinates them」）。対策を入れる前に、まず何が起きるかを固定するためです。

対策は 3 つ入れました。

### 1 つのプロセスの中での相乗り

同じキーの読み込みが進行中なら、新しく始めずに、その結果を待ちます。single flight と呼ばれるやり方です。

<<< @/examples/14-kv-cache/src/read-through.ts{single-flight}

<<< @/examples/14-kv-cache/test/read-through.test.ts{single-flight-test}

ただし、single flight が効くのは 1 つのプロセスの中だけです。Lambda は、同時に来たリクエストごとに別の実行環境を用意し、1 つの実行環境が同時に処理するリクエストは 1 件です。そのため、**Lambda では single flight の出番がほとんどありません。** コンテナや常駐のサーバー（[12章](/ja/chapters/12-containers.md)）で動かすときに効く対策で、コードを共通にしておくために入れてあります。

### 実行環境をまたぐためのロック

Lambda で効かせるには、どの実行環境からも見えるストアに、「いま詰め直している」という印としてロックを置きます。

<<< @/examples/14-kv-cache/src/read-through.ts{lock}

ロックを取れた 1 件だけが元データを読み、ほかのリクエストは少し待ってからキャッシュを読み直します。

<<< @/examples/14-kv-cache/test/read-through.test.ts{lock-test}

このロックは、**正しさを守るためのものではありません。** ロックには期限があり、持ち主が固まったり落ちたりすれば、ひとりでに外れます。そのとき 2 件が同時に詰め直すかもしれませんが、問題にはなりません。2 件が同じ元データを読んで、同じ写しを書くだけだからです。このロックが減らしているのは負荷であって、間違いではありません。

そのため、待つ回数にも上限があります。ロックの持ち主が戻ってこなくても、決めた回数だけ待ったら、自分で元データを読みに行きます。テストの「does not wait forever for a lock holder that died」と「goes to the source after waiting as long as it was told to」が、この動きを確かめています。

### 期限の分散

もう 1 つ、単純でよく効くのが、TTL に揺らぎ（jitter）を足す方法です。

<<< @/examples/14-kv-cache/src/read-through.ts{jitter}

デプロイの直後や、キャッシュが空になった直後は、たくさんのキーが同じ瞬間に書かれます。TTL がすべて同じなら、30 秒後にすべてが同時に切れます。0〜20% の揺らぎを足すと、切れる瞬間がばらけます。

<<< @/examples/14-kv-cache/test/read-through.test.ts{jitter-test}

乱数は引数で受け取っているので、テストでは決まった値を渡して、「5 つのうち、ちょうど 1 つだけが切れている」と言い切れます。

この章の API はキーが 1 つしかないので、揺らぎが効く場面はありません。利用者ごとの一覧やページごとの一覧のように、キーが増えたときに効いてきます。

## Lambda のメモリをキャッシュに使う

<!-- section: 14.memory -->

04章で、Lambda のメモリに置いたノートは実行環境ごとに別々で、いつ消えるかも選べないことを確かめました。そのときの結論は「データの持ち主にはなれない」でしたが、キャッシュとしては使える、とも書きました。ここでは、その使い方を見ます。

<<< @/examples/14-kv-cache/src/lambda.ts{handler}

`KV_STORE=memory` にすると、数も写しも、この実行環境の中の `Map` に入ります。

<<< @/examples/14-kv-cache/src/memory-store.ts{memory}

通信が無いので、いちばん速く、料金は 0 です。キャッシュとしては十分に使えます。写しが実行環境ごとにばらばらでも、それぞれが元データから作った写しなら、古さの上限は TTL のままで、共有のキャッシュよりミスが多くなるだけです。

レート制限は、そうはいきません。テストに、そのまま書いてあります。

- 実行環境が 2 つあると、上限 3 の利用者が合計 6 回通る
- 片方の実行環境に入れた写しは、もう片方からは見えない

上限が「実行環境の数 × N」になってしまい、実行環境がいくつあるかは、こちらでは決められません。さらに、Lambda は実行環境を数時間ごとに終了させます（ドキュメントによると、呼ばれ続けている関数でも同じです）。そのたびに、数は 0 に戻ります。数える仕事は共有のストアに置き、メモリに置くのは、ずれても誰も困らない写しだけにします。

メモリのキャッシュを、DynamoDB や Valkey の手前に 1 段足す構成もよく使われます。まずメモリを読み、無ければ共有のキャッシュを、それも無ければ元データを読みます。この章のコードには入れていませんが、`CacheStore` を 2 つ重ねれば作れます。その場合、古さの上限が 2 段の TTL の合計になることに注意してください。

## エッジの設定と CloudFront KeyValueStore

<!-- section: 14.edge -->

3 つ目の「KV」である CloudFront KeyValueStore は、この章では実装しません。[10章](/ja/chapters/10-edge.md)で、リダイレクトの表とメンテナンスのスイッチに使いました。ここでは、DynamoDB や Valkey との違いだけを整理します。

- 関数からは読むだけです。書き込みは、関数の外から専用の API でします。そのため、リクエストのたびに数えるレート制限には使えません
- 小さなデータ向けです。値は 1 KB まで、ストア全体で 5 MB までです
- 更新は遅れて届きます。どれくらい遅れるかの数字は、Developer Guide に見つかっていません（10章）
- 読めるのは CloudFront Functions だけです。東京の Lambda から読む用途のものではありません

向いているのは、人やデプロイがたまに書き換え、すべてのリクエストがエッジで読み、数秒古くても困らないデータです。フィーチャーフラグ、リダイレクトの表、メンテナンスのスイッチがこれにあたります。置くデータが違うので、DynamoDB や Valkey とは競合しません。

フィーチャーフラグを東京の Lambda で読みたいなら、DynamoDB に置いて、この章の read-through でメモリに短く写すのが素直です。
