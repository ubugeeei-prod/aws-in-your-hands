# 14 Cache: しくみと実装

[前のページ](/ja/chapters/14-kv-cache.md)で、数える側とキャッシュの側のインターフェースを決めました。このページでは、その 2 つを DynamoDB と Valkey に実装します。

## 読んでから書くと数え間違える

<!-- section: 14.atomic -->

レート制限を素直に書くと、「いまの回数を読み、上限より小さければ、1 足した値を書く」になります。この書き方は、2 件が同時に来ると壊れます。

```figure
caption: 上限が 1 のとき、2 件が同時に「読んでから書く」と、どちらも通り、増やした 1 回ぶんが消える
type: sequence
actor a: リクエスト A
actor store: 保存された回数
actor b: リクエスト B
note store: 0
step a -> store: t1 回数を読む: 0
step b -> store: t2 回数を読む: 0
step a -> store: t3 0 < 1 なので 1 を書く
note store: 1
step b -> store: t4 0 < 1 なので 1 を書く
note store: 1 (1 回ぶんが消えた)
note a: 通る
note b: 通る
```

2 件とも「まだ 0 回」と読むので、2 件とも通ります。しかも、保存された回数は 1 のままです。上限を破ったうえに、破った記録も残りません。

この場面を、決まった順序で再現するテストがあります。わざと「読んでから書く」ストアを作り、2 件が読み終わるまで書き込みを止めています。

<<< @/examples/14-kv-cache/test/rate-limit.test.ts{lost-update}

直すには、読むことと書くことを、ストアの中の 1 ステップにします。DynamoDB では次のように書きます。

<<< @/examples/14-kv-cache/src/dynamodb-store.ts{increment}

`ADD #hits :one` は「いまの値に 1 を足す」という命令です。アプリは値を読まず、足し算は DynamoDB がします。そこに 05章でも使った条件式を付けて、上限未満のときだけ足すようにしています。条件の判定と加算は、DynamoDB の中で 1 つの操作として実行されます。2 件が同時に来ても、片方が先に適用され、もう片方はその結果に対して判定されます。

読まずに足していることは、ユニットテストで固定しています。送るコマンドは `UpdateItem` が 1 つだけで、その前に読み取りはありません。さらに、「50 件が同時に来ても、通るのはちょうど 20 件で、数も 20 になる」というコントラクトテストを、DynamoDB Local に対して流して通しています。

この方式には、知っておくべきことが 2 つあります。

1 つ目は、拒否されたリクエストにも料金がかかることです。条件が成り立たなかった書き込みも、書き込み 1 単位を消費します。上限を超えても呼び続ける相手は、呼んだ回数だけ DynamoDB の料金を発生させます。大量のリクエストを受け止める場所は、アプリのレート制限ではなく、もっと手前に置かなければなりません。この章のスタックは、HTTP API のステージにスロットリングを付け、テーブルが 1 秒に受け付ける書き込みにも上限を置いています。設定は[デプロイ](/ja/chapters/14-kv-cache/deploy.md)のページに、金額は[最後のページ](/ja/chapters/14-kv-cache/wrap.md)の「料金」にあります。

2 つ目は、加算が冪等ではないことです。DynamoDB への書き込みが成功したのに応答が届かなかった場合、SDK は再試行して、もう 1 回足します。1 回のリクエストが 2 回と数えられるわけです。レート制限なら、利用者が 1 回ぶん損をするだけなので、そのままにしています。お金や在庫のように数え間違いが許されないものには、この方式を使わないでください。そういうデータには、05章の「応答が届かなかったら」で扱った、同じ操作に同じ ID を付けるやり方が要ります。

## TTL による削除は遅れる

<!-- section: 14.ttl -->

レート制限の項目は、区間が過ぎれば要らなくなります。キャッシュの写しも、期限が来れば要りません。放っておくとテーブルに溜まり続けるので、DynamoDB の TTL（time to live）を使います。項目に「この時刻を過ぎたら消してよい」を Unix 秒で書いておくと、DynamoDB が消してくれる機能で、削除に書き込みの料金はかかりません。

ただし、項目は期限が来た瞬間には消えません。公式ドキュメントは「期限から数日以内に削除する」と書いています。そして、消えるまでのあいだ、その項目はふつうに読めます。

Valkey や Workers KV の期限に慣れていると、期限を過ぎた値は返ってこないものと考えがちですが、DynamoDB は返します。そのため、読む側で期限を確かめます。

<<< @/examples/14-kv-cache/src/dynamodb-store.ts{cache-get}

`get` に `now` を渡していたのは、このためです。期限が切れているかどうかを決めるのは、DynamoDB ではなく、読んだ側の時計です。TTL には掃除だけを任せます。

読む側の判定は、テストで固定してあります。

<<< @/examples/14-kv-cache/test/dynamodb-store.test.ts{ttl-test}

項目には期限を 2 つ書いています。`expiresAtMs` はミリ秒で、読む側の判定に使います。`expiresAt` は秒で、DynamoDB が掃除に使います。TTL の属性は秒でなければならないので、2 つに分けました。

[次のページ](/ja/chapters/14-kv-cache/more.md)で使うロックにも、同じ事情があります。期限の切れたロックがテーブルに残るので、ロックが無い場合だけでなく、あっても期限が切れている場合も、取ってよい条件に入れています。

<<< @/examples/14-kv-cache/src/dynamodb-store.ts{lock}

レート制限のほうは、TTL の遅れの影響を受けません。キーに区間の開始時刻が入っているので、古い区間の項目が残っていても、新しい区間からは見えないからです。正しさを TTL に頼らない作りにしておけば、「数日」という幅を気にせずに済みます。

なお、実際の DynamoDB で項目が消えるまでの時間は、計っていません。

## Valkey での実装

<!-- section: 14.valkey -->

Valkey は、メモリの上で動く key-value のサーバーです。Redis がライセンスを変える直前のオープンソース版から分かれたプロジェクトで、Redis のコマンドがそのまま通ります。ElastiCache が動かせるエンジンの 1 つで、ほかに Redis OSS と Memcached があります。

Valkey にも 1 を足すコマンド（`INCR`）はありますが、「上限未満のときだけ足す」を 1 つのコマンドではできません。そこで、小さなスクリプトにします。

<<< @/examples/14-kv-cache/src/valkey-store.ts{scripts}

Valkey は、スクリプトを最初から最後まで、ほかのコマンドを挟まずに実行します。DynamoDB が条件と更新を 1 ステップにするのと同じ保証を、別のやり方で得ています。

キャッシュのほうは、もっと単純です。

<<< @/examples/14-kv-cache/src/valkey-store.ts{valkey-cache}

`get` は `now` を使っていません。Valkey は、期限が切れたキーを自分で返さなくなるので（公式ドキュメントによると、期限の誤差は 0〜1 ミリ秒）、読む側で確かめる必要がありません。DynamoDB との違いがいちばんはっきり出るのは、この点です。

そのかわり、期限を判定する時計が Valkey のサーバーのものになり、テストから差し替えられません。メモリと DynamoDB には偽の時計を渡せますが、Valkey には渡せないので、コントラクトテストも Valkey に対しては実際に時間を待っています（`test/local-stores.test.ts`）。

もう 1 つの大きな違いは、Valkey の中身は消えることがある、という点です。ElastiCache Serverless は、データを複数の Availability Zone に非同期で複製します。非同期なので、書き込みに成功の返事をもらった直後に障害が起きると、その書き込みが失われることがあります。また、保存量の上限に達すると、期限つきのキーが追い出されます。レート制限の数が消えると、その利用者はもう一度上限まで呼べるようになります。それを許せるかどうかで、Valkey に数を置くかどうかが決まります。

## ElastiCache で増える決めごと

<!-- section: 14.elasticache -->

手元の Valkey は、コンテナを 1 つ立てれば動きます。AWS で動かすと、決めることが増えます。

### ノードベースと Serverless

ElastiCache には、置き方が 2 つあります。

| | ノードベース | Serverless |
| --- | --- | --- |
| 決めること | ノードの種類、台数、どの AZ に置くか | 名前だけ（上限は設定できる） |
| 料金 | ノードの時間課金。東京の `cache.t4g.micro`（Valkey）1 台で月 USD 14.60 | 保存量（GB 時間）と ECPU。Valkey は最小 100 MB ぶんで月 USD 7.37 |
| ネットワーク | VPC の中だけ | VPC の中、またはパブリックエンドポイント |
| TLS | 有効にするか選ぶ | 常に有効 |
| cluster mode | 選べる | 有効のみ。クライアントが対応している必要がある |

どちらも、呼ばれなくても料金がかかります。DynamoDB や Lambda のように、使わなければ 0 になるわけではありません。Serverless という名前から「使ったぶんだけ」を想像すると、ここで外れます。料金ページには、課金はキャッシュが使えるようになったときに始まり、消すまで続く、と書かれています。

### VPC なしでつなぐパブリックエンドポイント

11章で書いたとおり、ノードベースのクラスターは VPC の中にしか置けません。Lambda からつなぐには関数を VPC に入れることになり、関数はインターネットへの経路を失います。この章のアウトラインも、もともとは「Valkey は VPC を伴う」としていました。

ところが、いまのドキュメントを読み直すと、ElastiCache Serverless には接続の種類が VPC とパブリックの 2 つあります。パブリックエンドポイント（public endpoint）には、VPC なしで、インターネット越しにつなげます。使えるのは、Valkey 9.0 以降の Serverless だけです。

この章のスタックは、Lambda を VPC に入れずに済むので、パブリックエンドポイントを使います。関数はこれまでの章と同じ場所で動き、DynamoDB も同じように呼べます。VPC に入れる構成（接続の種類を `vpc` にして、サブネットとセキュリティグループを渡し、関数を 11章の VPC につなぐ）は、この章のコードにはありません。

インターネットから届くキャッシュと聞けば、警戒するのが当然です。パブリックエンドポイントには、条件が 2 つ付いています。

- すべての接続に IAM 認証が要ります。パスワードで認証するユーザーは使えず、キャッシュに付けるユーザーグループは、全員が IAM 認証のユーザーでなければなりません
- TLS 1.3 が要ります。それより古い TLS では、ハンドシェイクが通りません

つまり、キャッシュを守っているのはネットワークの壁ではなく、IAM です。04章から続けてきた、ロールに何を許すかを決める考え方が、ここでもそのまま使えます。

### パスワードの代わりに送る署名

IAM 認証では、パスワードの代わりに、有効期限 15 分のトークンを送ります。トークンの正体は、SigV4 で署名した URL です。

<<< @/examples/14-kv-cache/src/elasticache-token.ts{token}

この関数は、どこにも通信しません。手元にある認証情報で署名するだけで、署名を検証するのは、受け取った ElastiCache です。Lambda の中では、実行ロールの認証情報で署名することになります。ロールには、`elasticache:Connect` を、キャッシュと ElastiCache のユーザーの両方に対して許しておきます。

AWS のドキュメントが参考実装として載せているのは Java のコードで、Node.js 用の公式の部品は見当たりませんでした（Valkey の公式クライアントである GLIDE は、トークンの生成と更新を自分でします）。上のコードは、その Java の実装を写したものです。テストでは、SigV4 の計算を別に手で書いて、署名が一致することを確かめています。ただし、**このトークンを本物の ElastiCache に渡したことは、まだありません。**

### クライアントに iovalkey を選んだ理由

Node.js の Valkey クライアントは、npm で 2 つ確かめました。

- `@valkey/valkey-glide` 2.5.3 は、Valkey の公式クライアントです。IAM 認証を内蔵しています。中身は Rust で、OS と CPU ごとのネイティブのパッケージを使います
- `iovalkey` 0.4.0 は、ioredis から分かれたクライアントで、JavaScript だけで書かれています

この本は、Lambda のコードを synth のときに esbuild で 1 つのファイルにまとめていて、Docker は使いません。ネイティブのパッケージは、まとめるマシン（たとえば macOS）と動かす場所（Linux の arm64）で別のものが要るので、このやり方にうまく合いません。そこで、JavaScript だけの iovalkey を選びました。認証まわりで書くコードは、GLIDE のほうが少なくなるはずです。コンテナで動かす（[12章](/ja/chapters/12-containers.md)）なら、選び直してかまいません。

<<< @/examples/14-kv-cache/src/valkey-client.ts{elasticache}

iovalkey を選んだ代償が 1 つあります。iovalkey はパスワードを固定の文字列として受け取るので、15 分後に再接続が起きると、古いトークンを送ってしまいます。そこで、接続を 10 分ごとに作り直しています。

<<< @/examples/14-kv-cache/src/valkey-client.ts{rotating}

もう 1 つ、キャッシュが返事をしないときに、リクエストを巻き添えにしないための仕組みを入れています。

<<< @/examples/14-kv-cache/src/valkey-client.ts{deadline}

待つのは 1 秒までで、それを過ぎたら、キャッシュは無かったものとして先へ進みます。この上限が無いと、キャッシュの障害が、Lambda のタイムアウト（10 秒）いっぱいの待ち時間になって利用者に届きます。
