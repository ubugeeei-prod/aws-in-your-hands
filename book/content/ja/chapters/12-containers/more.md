# 12 Containers: 実装のつづき

[前のページ](/ja/chapters/12-containers/build.md)で、サーバーとイメージ、リポジトリ、タスクを置くサブネットが決まりました。このページでは、タスクのロール、サービスと ALB、更新中に起きること、タスクの数の調整を扱います。

## 2 つのロール

<!-- section: 12.roles -->

04章の Lambda には実行ロールが 1 つありました。ECS のタスクにはロールが 2 つあり、名前が似ているので、役割を先に分けておきます。

<<< @/examples/12-containers/infra/lib/containers-stack.ts{roles}

**タスク実行ロール**（task execution role）は、アプリのコードが動き出す**前**に、ECS のエージェントが使います。用途は、ECR からのイメージの取得と、ログストリームへの書き込みだけです。コンテナの中のコードからは使えません。

**タスクロール**（task role）は、コンテナの中のコードが AWS を呼ぶときに使います。Lambda の実行ロールに当たるのは、タスクロールです。

04章と並べると、次のようになります。

| | Lambda（04章） | ECS のタスク |
| --- | --- | --- |
| コードが AWS を呼ぶ権限 | 実行ロール | タスクロール |
| コードの取得とログの送信 | Lambda 自身が行う（ログは実行ロールの権限で書く） | タスク実行ロール |

このアプリは AWS を 1 つも呼ばないので、タスクロールには権限がありません。05章のテーブルにつなぐなら、`table.grantReadWriteData(taskRole)` と書きます。同じ権限をタスク実行ロールに付けても、アプリからは使えません。反対に、タスク実行ロールの権限をタスクロールに付けると、アプリが必要のない権限を持つことになります。

タスク実行ロールの権限は、CDK が組み立てています。`ecs.ContainerImage.fromEcrRepository` がこのリポジトリからの取得を、`ecs.LogDrivers.awsLogs` がこのロググループへの書き込みを足します。

<<< @/examples/12-containers/infra/lib/containers-stack.ts{task}

テストは、ポリシーがタスク実行ロールにだけ付いていることと、許可している操作がちょうど 6 つであることを確かめています。`ecr:GetAuthorizationToken` だけは、対象が `*` になります。この操作はリポジトリを指定できないので、04章から続けてきた「`*` を使わない」方針の例外になります。スタックの中の `*` がこの 1 つだけであることも、テストで固定しました。

`readonlyRootFilesystem` は、コンテナのファイルシステムを読み取り専用にします。このアプリはディスクに何も書かないので、ほかの誰にも書けないようにしてあります。

### ヘルスチェック

ALB は、ターゲットグループに登録されたタスクへ、決まった間隔で `GET /health` を送ります。失敗が続いたタスクには、リクエストを送らなくなります。

間隔は、既定の 30 秒から 10 秒に縮めました。新しく登録されたタスクは、**1 回**成功すれば健全と見なされます（`healthyThresholdCount` の 2 は、不健全になったタスクが復帰するのに必要な回数です）。反対に、2 回続けて失敗するとタスクは振り分け先から外されるので、壊れたタスクにリクエストが届く時間は、長くても 20 秒ほどです。

すべてのタスクが不健全になったときの挙動は、知っておく必要があります。ALB は送り先が無いとは判断せず、すべてのタスクにリクエストを送ります（fail open）。ヘルスチェックが厳しすぎて全部のタスクが外れるよりも、動いているかもしれないタスクに送るほうがよい、という考え方です。

1 つ目の規則が、[前のページ](/ja/chapters/12-containers/build.md)の `Keep-Alive: timeout=65` の理由です。ALB はタスクとの接続を使い回し、60 秒使わなかった接続を閉じます。Node.js のサーバーは、既定では 5 秒で閉じます。サーバーが先に閉じると、ALB はまだ使えると見なしている接続にリクエストを流し、届け先を失ったリクエストが 502 になります。AWS のドキュメントも、アプリ側の時間を ALB より長くするよう勧めているので、65 秒にしました。

## 更新中に起きること

<!-- section: 12.rollout -->

`-c imageTag=v2` を付けてデプロイすると、タスク定義が新しくなり、サービスがタスクを入れ替え始めます。この入れ替えをローリングアップデート（rolling update）と呼びます。次の 2 つの図は、入れ替えがうまく進む場合と、新しいタスクが起動できない場合です。

```figure
caption: desired count 2、minimumHealthyPercent 100、maximumPercent 200 のローリングアップデートでは、新しいタスクがヘルスチェックに通ってから古いタスクが止まる
type: sequence
actor old: 古いタスク (v1)
actor new: 新しいタスク (v2)
actor req: リクエスト | 誰が答えるか
note old: 1: 2 つ running
step req -> old: 1: v1 v1
note new: 2: 最大 2 つ起動中 (pull, boot)
step req -> old: 2: v1 v1
note new: 3: running, 最初のヘルスチェックに合格
step req -> old: 3: v1 v1
step req -> new: 3: v2 v2 (両方の版が答える)
note old: 4: 2 つ draining
note old: v1 は進行中の分を終える
note new: 4: 2 つ running
step req -> new: 4: v2 v2
note old: 5: stopped
note new: 5: 2 つ running
step req -> new: 5: v2 v2
```

```figure
caption: 新しいタスクが 3 を越えられないと、circuit breaker がデプロイを失敗と判定して、最後に COMPLETED になった状態へ戻す
type: sequence
actor old: 古いタスク (v1)
actor new: 新しいタスク (v2)
note old: 3': 2 つ running
step new -x new: 3': 起動かヘルスチェックに 3 回失敗
note old: 4': 2 つ running
note new: 4': circuit breaker: deployment FAILED
step new --> old: 4': 最後の COMPLETED へロールバック
```

`minimumHealthyPercent: 100` は、健全なタスクを 2 つより減らさないという指定です。`maximumPercent: 200` は、入れ替えの間は 4 つまで動かしてよいという指定です。この 2 つによって、古いタスクを止める前に新しいタスクを起動する順序が決まります。50 と 100 にすると、先に 1 つ止めてから 1 つ起動する順序になり、余分なタスクが要らないかわりに、入れ替えの間は処理能力が半分になります。

**deployment circuit breaker** は、2 つ目の図の状況、つまり新しいタスクが 3 の段階を越えられないときのための仕組みです。新しいタスクが起動できない、またはヘルスチェックに通らない状態が続くと、更新を失敗と判定します。失敗と判定するまでの回数はタスクの数の半分（最低 3、最高 200）で、タスクが 2 つなら 3 回です。`rollback: true` にしてあるので、最後に成功した状態へ自動で戻します。

circuit breaker を有効にしていないと、更新は失敗と判定されないまま続きます。

circuit breaker には見つけられない壊れ方があります。見るのは、タスクが起動したかどうかと、ヘルスチェックに通ったかどうかだけです。`/health` には 200 を返すのに `/notes` が 500 になる壊れ方は検出できません。この壊れ方は、あとの「新旧が同時に動く」の節で実際に起こします。

### タスクが止まるとき

ローリングアップデートの図の 4 で、古いタスクが draining になりました。次の図は、その間に起きることを細かく示したものです。

```figure
caption: タスクを止めるとき、ECS は先にロードバランサーから外し、それから SIGTERM を送り、まだ残っていれば SIGKILL を送る
type: sequence
actor ecs: ECS とロードバランサー
actor srv: タスクの中のサーバー
step ecs -> ecs: t0: ECS がタスクを止めると決める
note ecs: task: DEACTIVATING, target: draining
note ecs: 新しいリクエストはこのターゲットに来ない
note srv: 進行中の分にはまだ答える
step ecs -> ecs: t0+?: 接続が無くなるか、30 秒経つ
note ecs: deregistrationDelay = 30
step ecs -> srv: t1: task: STOPPING, SIGTERM
step srv -> srv: "draining" とログ、listen をやめる
step srv -> srv: idle な keep-alive 接続を閉じる
step srv -> srv: 進行中の分を終える
step srv -> srv: "stopped" とログ、exit 0
step srv -> srv: t1+25: deadline、残りを切って exit 1
step ecs -> srv: t1+30: まだ居れば SIGKILL
note ecs: stopTimeout = 30
```

ECS は、先にタスクを ALB から外し、それから SIGTERM を送ります。この順序なので、SIGTERM が届くころには、新しいリクエストはもう来ていないはずです。

**deregistration delay** は、ALB が振り分け先から外すと決めたタスクについて、進行中のリクエストが終わるのを待つ時間です。既定の 300 秒のままだと、タスクを 1 つ止めるたびに最大 5 分待つことになるので、30 秒に縮めました。このアプリのリクエストは長くても 10 秒で終わる、という前提を置いています。ファイルのアップロードやストリーミングのような長いリクエストがあるアプリでは、縮めすぎるとリクエストが途中で切れます。

ALB が先に外してくれるならグレースフルシャットダウンは不要に見えますが、必要です。deregistration delay より長いリクエストは残りますし、[前のページ](/ja/chapters/12-containers/build.md)で見たとおり、keep-alive の接続を閉じないとプロセスが終了できません。ALB を通らない仕事（[08章](/ja/chapters/08-async.md)のキューの処理など）には、ALB から外す段階がそもそもありません。

この順序は、ECS のドキュメントが書いているタスクの状態の並び（DEACTIVATING で登録解除、そのあと STOPPING で SIGTERM）から読み取ったもので、実際に動かしてログの時刻で確かめてはいません。確かめるためのコマンドは用意してあります。

```bash
vp run ecs:watch
```

`ecs:watch` は、`/health` を 1 秒に 1 回呼んで、どの版が答えたかを表示し続けます。別のターミナルで動かしたままデプロイすれば、v1 と v2 が混ざる時間が見えます。エラーは 1 件も出ないはずですが、これも確かめていません。

## 新旧が同時に動く

<!-- section: 12.versions -->

ローリングアップデートの図の 3 の段階では、v1 と v2 が同時に応答していました。この時間は数十秒のこともあれば、タスクが多ければ数分になることもあります。ロールバックが起きれば、v2 が書いたものを v1 が読む時間も生じます。

タスクの外にデータがあれば、両方の版がそのデータを読み書きします。

この章の不変条件を 1 文で書くと、**「同時に動いているどの版も、同時に動いているどの版が書いたレコードでも読める」**です。

例として、v2 でノートに `pinned` という項目を足す場合を考えます。

<<< @/examples/12-containers/src/compat.ts{formats}

`v1` と `v2` は、うまくいく組み合わせです。v1 は知らない項目を何も言わずに捨て、v2 は無い項目を既定値で埋めます。

`v2Required` と `v1Strict` は、どちらも厳密で正しい書き方に見えますが、更新を壊します。

テストでは、タスクの外にあるデータの代わりになるものを用意しました。

<<< @/examples/12-containers/src/compat.ts{store}

保存してあるのは JSON の文字列で、それぞれのタスクは、自分の版のスキーマを通して読み書きします。DynamoDB の項目でも、SQL の行でも、キューのメッセージでも、起きることは同じです。

テストは、実際の HTTP サーバーを 2 つ、同時に起動します。

<<< @/examples/12-containers/test/versions.test.ts{rollout}

```figure
caption: レコードはどのタスクよりも長く残るので、v1 と v2 は互いが書いたレコードを読むことになる
type: sequence
actor v1: v1 のタスク
actor rec: レコード | どのタスクよりも長く残る
actor v2: v2 のタスク
step v1 -> rec: t1 POST /notes
note rec: {id,title,body,createdAt}
step v2 -> rec: t2 POST /notes
note rec: {..., pinned:false}
step rec --> v1: t3 GET /notes: 両方読む
note v1: "pinned" を捨てる
step rec --> v2: t4 GET /notes: 両方読む
note v2: pinned=false で埋める
note v2: t5 ロールバック: v2 が止まる
step rec --> v1: t5 v2 が書いたものもまだ読む
```

壊れる 2 つの書き方では、次のことが起きます。

**新しい版が、古いレコードに無い項目を必須にした（`v2Required`）。** v2 のタスクに届いた `GET /notes` が 500 になります。v1 のタスクに届いたリクエストは成功するので、利用者には 2 回に 1 回失敗するように見えます。その間も `/health` は 200 のままなので、ALB も circuit breaker も気づきません。テストは、ヘルスチェックが通ることと一覧の取得が失敗することを、並べて確かめています。

**古い版が、知らない項目を拒否する（`v1Strict`）。** v2 が 1 件書いた時点から、v1 のタスクはレコードを読めなくなります。急いでロールバックしても直りません。v2 のコードは消えても、v2 が書いたレコードは残るからです。

この 2 つの壊れ方から、変更の順序についての決まりが導けます。

- 項目を**足す**ときは、任意の項目として足し、読む側で既定値を埋める。古い版は、知らない項目を無視できるようにしておく
- 項目を**必須にする**のは、その項目を書かない版がどこにも動いていなくなり、古いレコードも埋め終わってからにする。足すことと必須にすることは、別のデプロイに分ける
- 項目を**消す、または名前を変える**ときは、1 回で済ませない。新しい名前を足す、両方を書く、読む側を切り替える、古いほうを消す、の順に分ける

この決まりは、ECS に限ったものではありません。止めずに入れ替える仕組みには、どれも新旧が同時に動く時間があります。タスクを 2 つ並べて順に入れ替えるようになったことで、その時間が目に見えるようになりました。

このサンプルをデプロイしても、タスクどうしが共有するデータはありません。ノートはまだメモリの中にあります。デプロイした環境で新旧の両方に同時に触れるのは、いまのところ利用者だけで、`ecs:watch` に表示される `x-app-version` の入れ替わりがそれに当たります。テストが使っている `SharedRecords` は、05章や 13章のデータストアにつないだときに起きることを、手元で先に確かめるためのものです。

## タスクを増やす、減らす

<!-- section: 12.scaling -->

<<< @/examples/12-containers/infra/lib/containers-stack.ts{scaling}

使っているのは **target tracking** という方式です。サービス全体の平均 CPU 使用率を 60% に保つ、という目標だけを決めて、タスクの数の増減は任せます。エアコンに設定温度だけを伝えるのに似ています。

指標としてよく使われるものは 2 つあります。

**CPU 使用率。** このサンプルが使っている指標で、計算で忙しくなるアプリに向きます。Node.js は 1 つのスレッドでリクエストを処理するので、0.25 vCPU のタスクは CPU を使い切るとすぐにリクエストが待たされます。早めに増やすために、目標を 60% にしました。

**ターゲットあたりのリクエスト数**（`ALBRequestCountPerTarget`）。ALB が数えた、タスク 1 つあたりのリクエスト数です。データベースや外部の API を待つ時間が長いアプリは、忙しくても CPU 使用率が上がらないので、リクエスト数のほうが実態に合います。このサンプルには入れていません。タスク 1 つが何件処理できるかを測らないと、目標の値を決められないからです。

2 つの指標を両方付けることもできます。その場合、どちらか 1 つでも増やすべきだと判定すればタスクは増え、すべての指標が減らしてよいと判定したときだけ減ります。増やすのは速く、減らすのは慎重に進む作りです。

上限の 4 は、料金の上限でもあります。タスクが 1 つ増えると、パブリックサブネットなら月 USD 12.65 増えます。4 つのまま動き続けると、このスタックの固定費は月 USD 75.62 になります。上限を決めずに auto scaling を付けると、請求にも上限が無くなります。

スケールインでタスクが減るときも、止まり方は更新のときと同じです。ALB から外され、SIGTERM が届き、`stopTimeout` が過ぎれば SIGKILL が届きます。グレースフルシャットダウンは、スケールインでも役に立ちます。なお、デプロイが進んでいる間、スケールインは止まります（スケールアウトは止まりません）。

auto scaling は、負荷をかけて試してはいません。確かめたのは、設定がテンプレートに入ることだけです。
