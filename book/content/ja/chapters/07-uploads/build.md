# 07 File Upload: しくみと実装

[前のページ](/ja/chapters/07-uploads.md)では、API が許可証を出し、ブラウザが画像を S3 に直接送るところまでを見ました。このページでは、送った画像を添付として記録する処理と、途中で止まったときに残るものの片付け、画像の見せ方を扱います。

## 2 つの置き場所、1 つの順序

<!-- section: 07.finish -->

画像は S3 にあり、どのノートにどの画像が付いているかは DynamoDB にあります。この 2 つへの書き込みを 1 つのトランザクションにまとめる方法はありません。

05章の楽観ロックは 1 つのテーブルの中の話で、条件付きの書き込みが、検査と更新を 1 つの手順にしていました。この章では、相手が 2 つのサービスです。どちらかに書いた直後に関数が落ちると、片方だけが書かれた状態が残ります。

片方だけが書かれた状態を防ぐことはできません。できるのは、どちらが欠けた状態なら許すかを選ぶことです。

```text
finish (step 3)                        if the function stops right after this step
  a. HeadObject: is it there?          nothing changed
  b. DeleteObjectTagging (S3)          object without a record   <- allowed; cleaned up later
  c. PutItem ATTACHMENT#... (DynamoDB) done

remove
  a. DeleteItem ATTACHMENT#... (DynamoDB)   object without a record   <- allowed; cleaned up later
  b. DeleteObject (S3)                      done

never, at any step:                    a record whose object is missing or about to expire
```

守る不変条件は、次の 1 文です。

**添付の記録があるなら、そのオブジェクトは存在していて、自動削除の対象から外れている。**

逆の状態、つまり記録のないオブジェクトは許します。記録のないオブジェクトは誰にも見えず、利用者の画面も壊れません。かかるのは保存料金だけで、あとから掃除できます。

一方、オブジェクトのない記録は利用者に見えます。ノートを開くと、壊れた画像が表示されます。そのため、オブジェクトのない記録は作らないと決めます。

こう決めると、書き込みの順序も決まります。足すときはオブジェクトを先に、記録を後に書きます。消すときは記録を先に、オブジェクトを後に消します。こうしておけば、どこで止まっても、記録が指すオブジェクトは必ず存在します。

アップロードされたオブジェクトには、`upload-state=pending` というタグが付いています。バケットには、このタグが付いたまま 1 日たったオブジェクトを消す規則があり、完了の処理がこのタグを外します。タグを外した後で、記録を書きます。

完了の処理は、2 回呼んでも結果が同じです。記録がすでにあれば、その記録を返すだけです。記録の書き込みは条件付きなので、2 つの完了が同時に走っても、記録は 1 つしかできません。ルートを `PUT` にしたのは、このためです。

<<< @/examples/07-uploads/api/src/attachments.ts{timing}

完了を受け付けるのは、オブジェクトがバケットに届いてから 15 分以内です。この期限は、「残ったものを片付ける」で説明する掃除と、完了の処理が、同じオブジェクトを同時に触らないようにするためにあります。

### 途中で止めるテスト

テストは、決まった場所で処理を止めて、2 つの置き場所の両方を確かめます。メモリ上の実装に、次の 1 回だけ失敗する仕掛けを入れて、止まる場所を固定しています。

| 止める場所 | S3 | DynamoDB | その後 |
| --- | --- | --- | --- |
| 送った。完了を呼ばない | オブジェクト（pending） | なし | 1 日後にライフサイクルルールが消す |
| タグを外した。記録の書き込みが失敗 | オブジェクト（タグなし） | なし | もう一度完了を呼ぶと、記録が 1 つできる。呼ばれなければ掃除が消す |
| タグを外すのに失敗 | オブジェクト（pending） | なし | もう一度完了を呼ぶと成功する |
| 完了した。レスポンスが届かない | オブジェクト（タグなし） | 記録 | もう一度呼んでも、同じ記録が返る |
| 削除で記録を消した。オブジェクトの削除が失敗 | オブジェクト（タグなし） | なし | 利用者には成功を返す。掃除が消す |
| ノートを消した。添付の後始末が失敗 | オブジェクト（タグなし） | 記録 | ノートがないので API からは届かない。掃除が両方消す |

どの行でも、記録があるのにオブジェクトがない状態は起きていません。

## 残ったものを片付ける

<!-- section: 07.orphans -->

記録のないまま残ったオブジェクトには、2 種類あります。

1 つ目は、送られたのに完了されなかったオブジェクトです。タブを閉じたり通信が切れたりすると起きるので、いちばんよく起きるのはこの種類だと考えられます。この種類は、S3 自身に消させます。

<<< @/examples/07-uploads/api/src/object-store.ts{tags}

ライフサイクルルール（lifecycle rule）は、条件に合うオブジェクトを、作成から一定の日数がたった後に S3 が自分で消す設定です。この章の規則は、`upload-state=pending` のタグが付いたオブジェクトを 1 日後に消す、というものです。コードを 1 行も動かさずに済みます。

公式ドキュメントによると、タグを条件にした規則は 1 日に 1 回評価され、削除は非同期に実行されます。実行の時点でタグがもう付いていなければ、削除は行われません。期限と実際の削除の間には、遅れがありえます。つまり、きっかり 24 時間後に消えるのではなく、1 日たってからしばらくして消えます。

2 つ目は、タグを外した後に記録を失ったオブジェクトです。「途中で止めるテスト」の表の 2 行目、5 行目、6 行目がこれにあたります。タグがないので、ライフサイクルルールの対象になりません。S3 はテーブルの中身を知らないので、S3 だけで見つけることもできません。バケットとテーブルを突き合わせる処理が要ります。

<<< @/examples/07-uploads/api/src/sweep.ts{sweep}

掃除は、バケットのオブジェクトを順に見て、記録かノートのどちらかがなければ消します。消す順序は利用者による削除と同じで、記録が先、オブジェクトが後です。

1 時間より新しいオブジェクトには触りません。完了の期限は 15 分なので、1 時間たったオブジェクトが完了の途中であることはありません。関数の時計と S3 の時計が少しずれていても、余裕があります。このように時間で区切る方法は、2 つの処理の間にロックを置けないときによく使われます。

知らない形のキーは、報告するだけで消しません。このアプリが書いたものではないからです。

掃除は関数ではなく、あなたの認証情報で動くタスクです。何を消すかを先に確かめられます。

```bash
vp run uploads:sweep
vp run uploads:sweep --delete
```

定期的に自動で動かすなら、スケジューラーが要ります（[08章](/ja/chapters/08-async.md)で足します）。

### この設計に残る穴

この設計には、閉じていない穴が 1 つあります。

署名付きのフォームは、期限までは何度でも使えます。利用者が画像を送って完了し、そのあと 5 分以内に同じフォームをもう一度送ると、S3 はオブジェクトを置き換えて、フォームに書かれたタグをもう一度付けます。記録はあるのに、オブジェクトは pending に戻ります。1 日後にライフサイクルルールがオブジェクトを消し、記録だけが残ります。こうして不変条件が破れます。

壊せるのは自分の添付だけで、他人の添付には届きません。それでも、不変条件が破れることに変わりはありません。この動きを再現するテストを、意図して 1 つ置いてあります。

閉じ方は 2 つ考えられます。1 つは署名付き PUT に替えて、`If-None-Match` で、同じキーへの 2 回目の書き込みを S3 に拒否させる方法です。公式ドキュメントは、このヘッダーを使える操作に `PutObject` を挙げていて、POST Object は挙げていません。この方法をとると、大きさの範囲を S3 に守らせる確かな方法を手放すことになります。もう 1 つは、許可証の期限が切れた後でタグをもう一度外す処理を足す方法です。どちらも、この章では実装していません。

掃除が見つけられないものもあります。オブジェクトのない記録です。誰かがバケットのオブジェクトを手で消すと、この状態になります。見つけるにはテーブルの側から調べる必要があり、この章の掃除はそれをしません。

## 画像を見せる

バケットは公開しないので、`<img>` が画像を読むための URL を、API が別に用意します。

<<< @/examples/07-uploads/api/src/s3-object-store.ts{presign-view}

添付の一覧を返すとき、1 枚ごとに、5 分だけ有効な署名付きの GET の URL を作って付けます。この URL も関数の中で計算するだけで、S3 へのリクエストは発生しません。

一覧のルートは、ノートが呼び出した人のものかどうかを確かめます。しかし、返した URL そのものは、誰が使っても通ります。アクセストークンは要りません。URL をチャットに貼れば、貼られた人も 5 分間は画像を見られます。URL はブラウザの履歴にも、プロキシのログにも残ります。

公式ドキュメントは、署名付き URL をベアラートークンと呼び、それにふさわしい扱いで守るよう勧めています。この章が選んだ守り方は、期限を短くすることだけです。5 分たつと画像が読めなくなるので、画面は、画像の読み込みに失敗したら一覧を取り直します。

アプリの認可をリクエストのたびに働かせたいなら、別の構成になります。CloudFront を前に置いて、署名付きの cookie か URL を使う方法です。章のアウトラインでは、CloudFront と OAC を通す案でした。しかし OAC だけでは、URL を知っている人なら誰でも読めます。利用者ごとに分けるには署名の仕組みが別に要るので、この章では署名付きの GET にしました。

### 期限より先に切れることがある

署名付き URL の期限は指定した時間ですが、それより先に切れる場合があります。

公式ドキュメントによると、一時的な認証情報で作った署名付き URL は、その認証情報が失効すると、指定した期限が後であっても無効になります。

<<< @/examples/07-uploads/api/src/lambda.ts{handler}

Lambda は、実行ロールから得たアクセスキーを、セッショントークンと一緒に環境変数で関数に渡します。セッショントークンが付くのは、一時的な認証情報です。したがって、この章の URL とフォームは、すべてこの規則の対象になります。その認証情報がどれくらいの長さで入れ替わるのかは、公式ドキュメントで確認できませんでした。署名付き URL のページに EC2 や ECS の目安は載っていますが、Lambda の数字はありません。

この章の期限は 5 分なので、影響は小さいはずです。それでも、認証情報が切れる直前に作った URL は、5 分たたないうちに切れます。7 日間有効な共有リンクのようなものを Lambda から作っても、7 日はもちません。長い期限が要るなら、別の仕組みを検討してください。

06章の[無効にしても、しばらく通る](/ja/chapters/06-auth/deploy.md)とは、ちょうど逆向きの現象です。06章では、止めたいのに期限まで通りました。この章では、通したいのに期限の前に止まります。どちらも、検証する側が手元の情報だけで判断することから起きます。
