# 48 SDK: 実装のつづき

[前のページ](/ja/chapters/48-sdk/build.md)では、1 回の呼び出しの中身を読みました。このページでは、呼び出しを重ねる部品と、データの出し入れを扱います。ページネーターとウェイター、ストリーム、署名付き URL、DynamoDB の値の変換、そしてテストの書き方です。

## ページネーターとウェイター

<!-- section: 48.pages-waiters -->

一覧を返す操作は、1 回の応答に収まらないとき、続きを指す値を返します。DynamoDB の Scan と Query なら `LastEvaluatedKey` で、次のリクエストの `ExclusiveStartKey` に渡します。ページネーター（paginator）は、この受け渡しを非同期のイテレーターに包んだ関数です。`paginateScan` や `paginateQuery` のように、操作ごとに用意されています。

ページネーターには上限がありません。サービスが続きの値を返さなくなるまで、尋ね続けます。大きなテーブルに対する Scan を `for await` で回すと、テーブルを端から端まで読み、読んだぶんの料金がかかります。そこで、ページ数に上限を付けて包みます。

<<< @/examples/48-sdk/src/pages.ts{pages}

ループを抜ければ、それ以上のリクエストは出ません。ページネーターは、次のページを求められるまで何も送らないからです。1,000 ページあるテーブルの台本に対して上限を 4 にすると、届いたリクエストは 4 件でした。

`pageSize` は、DynamoDB では `Limit` として送られます。05章のリポジトリは、ページネーターを使わず、`Limit` と自前のカーソルで 1 ページずつ返しています。API が 1 ページずつ返す形なら、そのほうが素直です。ページネーターが合うのは、バッチやスクリプトのように、1 つの処理の中で続きを読み切るときです。

ウェイター（waiter）は、リソースが目的の状態になるまで、間隔をあけて問い合わせ続ける関数です。`waitUntilTableExists` は `DescribeTable` を繰り返し、テーブルが `ACTIVE` になったら返ります。渡すのは、待つ時間の上限（`maxWaitTime`、秒）です。間隔は、`minDelay` から始めて `maxDelay` まで、ジッター付きで伸びます。DynamoDB のこのウェイターの既定は 20 秒と 120 秒でした。

上限を過ぎると `TimeoutError`、`abortSignal` で打ち切ると `AbortError` で終わります。どちらも `name` で見分けます。

知っておきたいのは、このウェイターが、**どんな例外も「まだ」と解釈する**ことです。テーブルがまだ無いときの `ResourceNotFoundException` を待つのは当然ですが、ソースを読むと、それ以外の例外も同じ扱いになっています。権限がなくて `AccessDeniedException` が返り続ける台本で確かめると、ウェイターは 1 回で諦めず、`maxWaitTime` が尽きるまで問い合わせを続け、`TimeoutError` で終わりました。原因は権限なのに、見えるのは時間切れです。SDK は、403 が続くと 60 秒たったところで警告を出すようになっていますが、今回のように 400 で返る権限エラーには効きません。ウェイターが時間切れになったら、まず同じ操作を 1 回だけ直接呼んで、返ってくる例外を見ます。

## ストリーム

<!-- section: 48.streams -->

S3 の `GetObject` の `Body` は、バイト列ではなくストリームです。Node.js では Node.js のストリーム、ブラウザでは Web のストリームで、どちらにも SDK が 3 つのメソッドを足しています。`transformToString()`、`transformToByteArray()`、`transformToWebStream()` です。

このメソッドは 1 度しか呼べません。ストリームは巻き戻せないからです。2 度目の `transformToString()` が例外になることを、テストで確かめました。

もう 1 つ、SDK のドキュメントが注意していることがあります。接続は使い回されるので、`Body` を最後まで読むか、破棄するかしないと、その接続は空きません。ヘッダーだけ見て `Body` を放っておくコードは、接続を 1 本ずつ塞いでいきます。中身が要らないなら、`HeadObject` を使います。

`transformToString()` は、オブジェクトを丸ごとメモリに読みます。添付ファイルの大きさを決めるのはアップロードした人で、読む側ではありません。上限を付けて読む関数を用意します。

Lambda から大きなオブジェクトをそのまま呼び出し元へ流す話は、[17章](/ja/chapters/17-ai.md)のレスポンスストリーミングと同じ形になります。この章では扱いません。

### 大きなアップロード

送る側では、`@aws-sdk/lib-storage` の `Upload` が、大きな本文をパートに分けて並行に送ります。07章で名前だけ出てきたマルチパートアップロードを、SDK が組み立てるものです。

既定値は、パートの大きさが 5 MiB、同時に送るパートが 4 つです。本文が 1 パートに収まるときは、マルチパートにせず `PutObject` を 1 回送ります。手元のエンドポイントで確かめると、ちょうど 5 MiB の本文は `PutObject` 1 件、1 バイト増やすと `CreateMultipartUpload`、`UploadPart` が 2 件、`CompleteMultipartUpload` の 4 件になりました。完了のリクエストには、パートが番号順に並んでいます。

パートが再試行しても通らなかったときは、`Upload` が `AbortMultipartUpload` を送ります。パート 2 だけ 500 を返す台本で、取り消しのリクエストが届き、完了のリクエストは届かないことを確かめました。07章に書いたとおり、完了も中止もされなかったパートには料金がかかり続けるので、この既定（`leavePartsOnError: false`）は変えません。取り消しのリクエスト自体が届かないこともありえるので、07章のスタックにある、未完了のマルチパートアップロードを中止するライフサイクルルールは、`Upload` を使っていても必要です。

07章のアプリは、ブラウザから S3 へ直接送るので、サーバー側で `Upload` を使う場面がありません。使うのは、Lambda や ECS のタスクが自分でファイルを作って S3 に置くときです。

## 署名付き URL

<!-- section: 48.presign -->

[07章](/ja/chapters/07-uploads.md)で、署名付き URL を使いました。SDK の側から見ると、署名付き URL は「送らずに署名だけしたリクエスト」です。`getSignedUrl` は、コマンドをミドルウェアスタックに通して HTTP リクエストを作り、署名を URL のクエリに入れて返します。送信はしません。手元のエンドポイントに向けたクライアントで URL を作っても、リクエストは 1 件も届きませんでした。

何も指定しないときの期限は 900 秒です。

URL には、署名に使ったキーの ID（`X-Amz-Credential`）が入ります。一時的な認証情報で署名したときは、セッショントークン（`X-Amz-Security-Token`）も入ります。URL は、その認証情報の名前で出した委任状です。S3 のドキュメントは、署名付き URL は指定した期限と、署名に使った認証情報の期限の、早いほうで切れると書いています。

そのため、同じ `expiresIn: 3600` でも、署名した場所で寿命が変わります。Lambda の実行ロールの認証情報は一時的なものなので、1 時間の URL を出したつもりが、もっと早く切れることがあります。関数が受け取った認証情報に残りがどれだけあるかは、この章では確かめていません。IAM ユーザーの長期のキーで署名した URL は、指定した期限まで有効です。ただしドキュメントによると、キーを無効にしたり消したりすれば、URL もそこで切れます。

残りの時間は、署名の前に確かめられます。クライアントの `config.credentials()` が返す認証情報に `expiration` があります。長い期限の URL が要るなら、この値を見て、足りなければ短い期限で出し、切れたら取り直せる作りにします。07章は期限を 5 分にして、この影響を小さくしています。

実際の S3 で、認証情報の失効によって URL が切れるところは、この章では確かめていません。ドキュメントの記述です。

`PutObject` の署名付き URL には、もう 1 つ気づいたことがあります。固定している版で作ると、URL に `x-amz-sdk-checksum-algorithm=CRC32` と `x-amz-checksum-crc32=AAAAAA==` が入ります。後者は 0 バイトの本文のチェックサムです。署名の時点では本文がないので、空として計算されています。この URL に実際の本文を PUT したとき S3 がどう答えるかは、確かめていません。07章は、アップロードに `PutObject` の URL ではなく、条件を付けられる POST を使っているので、この点には当たりません。

## DynamoDB の値の変換

<!-- section: 48.marshalling -->

DynamoDB の API は、値を型つきで受け渡しします。文字列は `{ "S": "a" }`、数は `{ "N": "1" }` です。05章から使っている `@aws-sdk/lib-dynamodb` のドキュメントクライアントは、JavaScript の値とこの形を、送るときと受け取るときに変換します。この変換をマーシャリング（marshalling）と呼びます。

ドキュメントクライアントは、元のクライアントを包んだものです。再試行も接続も、元のクライアントのものを使います。

変換の規則は、設定として書いておきます。値はどれも、固定している版で何も指定しないときと同じです。

<<< @/examples/48-sdk/src/document.ts{translate}

何がどう変換されるかは、手元のエンドポイントに届いた本文で確かめました。

| JavaScript の値 | 送られるもの |
| --- | --- |
| 文字列、数、真偽値、`null` | `S`、`N`、`BOOL`、`NULL` |
| 配列、オブジェクト | `L`、`M` |
| 文字列の `Set`、数の `Set` | `SS`、`NS` |
| `Uint8Array` | `B` |
| `bigint` | `N` |
| 空文字列 | `S` の空文字列 |

断られるものもあります。どれも、送る前に例外になります。

| 値 | 結果 |
| --- | --- |
| マップやリストの中の `undefined` | 例外。`removeUndefinedValues` を案内する |
| 空の `Set` | 例外 |
| `Date`、クラスのインスタンス | 例外。`convertClassInstanceToMap` を案内する |
| 2 の 53 乗以上の数 | 例外。`NumberValue` を案内する |
| `NaN`、`Infinity` | 例外 |

案内に従う前に、何が起きるかを知っておきます。`convertClassInstanceToMap` を有効にすると、`Date` は空のマップとして保存されます。日時は消えます。05章が日時を ISO 8601 の文字列で持っているのは、このためです。

黙って落ちるものが 1 つあります。アイテムの直下にある `undefined` の属性は、例外にならず、送られません。ドキュメントには、アイテム自体はマップとは見なさない、とあります。`{ pk: "a", title: undefined }` を Put すると、届くのは `pk` だけでした。Put はアイテムを丸ごと置き換えるので、`title` を持っていたアイテムからは `title` が消えます。意図どおりのこともありますが、Valibot のスキーマで任意のフィールドを持つ型を使うなら、頭に入れておきます。

読む側では、数が問題になります。`N` は桁の文字列として届くので、JavaScript の `number` に収まらない値もありえます。確かめた結果は次のとおりです。

| 保存されている `N` | 受け取る値 |
| --- | --- |
| `1`、`1.5` | `number` |
| `9007199254740993` | `bigint` |
| `1.00000000000000000001` | `number` の `1` |

大きな整数は `bigint` になります。`bigint` は `JSON.stringify` に渡すと例外になるので、そのまま API の応答に入れると 500 です。桁の多い小数は、何も言わずに丸められます。どちらも、この本のノートのアプリでは起きません。件数とバージョンしか数を持たないからです。金額や外部の ID を `N` で持つなら、`wrapNumbers: true` にして、数を桁の文字列を持つ `NumberValue` で受け取ります。書く側も `NumberValue.from("…")` で渡せます。

## バンドルとクライアントの再利用

<!-- section: 48.bundle -->

v3 の SDK がサービスごと、コマンドごとに分かれているのは、使うぶんだけをバンドルに入れるためです。どの書き方でどれだけ変わるか、esbuild の `mainFields` がなぜ効くかは、[29章](/ja/chapters/29-lambda-tuning.md)が実測しています。この章では測っていません。

この章から付け加えるのは、クライアントを 1 つにする理由です。ここまでに 3 つ出てきました。接続はクライアントごとに持つので、作り直すと接続もやり直しになります。再試行の予算もクライアントごとなので、呼び出しのたびに作ると、予算は毎回満額で、障害のときに再試行を抑える働きをしません。認証情報も、クライアントが覚えています。

SDK の README も、Lambda ではサービスとリージョンごとにクライアントを 1 つ、ハンドラーの外で作るよう勧めています。05章の `compose.ts` は、最初からそうなっています。

## テスト

<!-- section: 48.testing -->

SDK を使うコードのテストには、偽物を差し込む場所が 3 つあります。

いちばん外側は、自分で決めたインターフェースです。05章の `NoteRepository` がこれで、アプリのテストはメモリ上の実装に対して走ります。テストが確かめるのはアプリの判断で、SDK のコマンドの形は出てきません。この本がほとんどのテストをこの形で書いているのは、守りたい不変条件が、アプリの言葉で書かれているからです。「ノートは 100 件まで」は、`UpdateCommand` の `ConditionExpression` ではなく、リポジトリの約束として確かめたいことです。

1 つ内側は、クライアントの `send` です。`send` を置き換えて、渡されたコマンドを調べます。`aws-sdk-client-mock` は、この層のためのライブラリです。npm のレジストリで確かめたところ、2026 年 10 月 13 日の時点で最新は 4.1.0、公開は 2024 年 10 月 15 日で、非推奨にはなっていません。sinon に依存しています。2 年のあいだ新しい版が出ていないことになります。固定している版の SDK と組み合わせて動くかは、試していません。この層のテストは、リポジトリの実装が正しい引数でコマンドを作ったかを確かめるのに向いています。ただし、確かめられるのは「そう送った」までで、サービスがそれを受け付けるかはわかりません。05章は、この層を DynamoDB Local に対するテストで確かめています。

いちばん内側は、HTTP です。32章は `requestHandler` を偽物に替え、この章は本物のハンドラーを手元のサーバーにつなぎました。SDK そのものの挙動、つまり再試行、タイムアウト、接続を確かめられるのは、この層だけです。アプリのテストをここで書くことは勧めません。応答をプロトコルの形で手書きすることになり、その形が本物と合っているかを誰も保証しないからです。この章の台本も、SDK が読む最小限のフィールドしか返していません。

この章のテストは、もう 1 つ工夫をしています。SDK は、環境変数と `~/.aws` の設定を読みます。開発者の端末に `max_attempts` や `AWS_PROFILE` があると、既定値を確かめるテストの結果が変わります。そこで、テストの最初に `AWS_` で始まる環境変数を消し、設定ファイルの場所を一時ファイルに向けます。既定値のテストは、さらに別のプロセスで実行します。
