# 28 Multi-Region: デプロイ

このページでは、2 つのスタックを AWS にデプロイする準備をし、デプロイの順序と確認の手順、切り替えの訓練の進め方を書きます。このページの手順は、どれも実行していません。

## AWS にのせる準備

スタックのクラスは 1 つで、リージョンを変えて 2 回使います。

違いは、どちらがテーブルを定義するかと、バケットの複製の向きだけです。

テーブルのレプリカは大阪にもできるのに、定義を東京のスタックにだけ置いたのには理由があります。DynamoDB のドキュメントによると、CloudFormation は、グローバルテーブルのように複数のリージョンにまたがるリソースを、スタックのあいだで調整できません。レプリカをリージョンごとのスタックに分けて定義すると、更新のときにドリフトのエラーになります。1 つのリージョンを基準に選び、すべてのレプリカをそのスタックに書くのが勧められている方法です。大阪のスタックは、同じ名前のテーブルを名前で参照するだけです。

同じドキュメントに、もう 1 つ注意があります。すでにある `AWS::DynamoDB::Table` のリソースの種類を、テンプレートで `AWS::DynamoDB::GlobalTable` に書き換えてはいけません。テーブルが消されることがあります。05章のテーブルをこの章の形に変えるときは、そのまま書き換えずに、ドキュメントの手順（テーブルを残す設定にしてスタックから外し、レプリカを足してから、新しい種類として取り込む）に従います。この章のスタックは、新しいテーブルを作ります。

### 指定したときだけ作るもの

料金がかかるもの、ドメインが要るもの、相手のスタックが先にあることを前提にするものは、コンテキストで名前を指定したときだけ作ります。

<<< @/examples/28-multi-region/infra/bin/app.ts{context}

値はスキーマで確かめているので、`-c rtc=yes` のような書き間違いは、既定の構成をデプロイせずに synth の段階で止まります。

`-c domain=...` を付けると、2 つのスタックそれぞれに、Route 53 と API Gateway のリソースを足します。

<<< @/examples/28-multi-region/infra/lib/region-stack.ts{dns}

足すのは 5 種類です。API Gateway のリージョン別のカスタムドメインは、同じリージョンの証明書を必要とするので、証明書はスタックごとに 1 つ要ります。ヘルスチェックは、共有する名前ではなく、そのリージョンの API の URL を直接呼びます。共有する名前の行き先は、このヘルスチェックの結果で決まるからです。レコードは、同じ名前で 2 つでき、`SetIdentifier` で区別されます。フェイルオーバーのエイリアスレコードでは `EvaluateTargetHealth` を有効にする必要があると CloudFormation のリファレンスにあるので、有効にして、テストで固定しました。

ホストゾーンは、このスタックでは作りません。すでに持っているゾーンの ID と名前を渡します。ドメインを持っていなければ、この部分は使えません。

### cdkd が扱う種類

既定の構成が使う種類は、東京のスタックが 12 種類、大阪のスタックが 11 種類です。違いは `AWS::DynamoDB::GlobalTable` だけで、そのほかは 05章と 22章で使ったものです。どれにも、固定した版の cdkd（0.296.28）が専用の実装を持っています。ドメインを付けたときに増える 5 種類のうち、`AWS::CertificateManager::Certificate` と `AWS::Route53::RecordSet` には専用の実装があり、`AWS::Route53::HealthCheck`、`AWS::ApiGatewayV2::DomainName`、`AWS::ApiGatewayV2::ApiMapping` は Cloud Control API 経由になります。この 3 つは、Cloud Control API が対応している種類の一覧に載っています。

cdkd のグローバルテーブルの実装について、インストールしたパッケージを読んでわかったことが 2 つあります。実装が扱うプロパティの一覧に `Replicas` はありますが、`MultiRegionConsistency` と `GlobalTableWitnesses` はありません。MRSC のテーブルを、この版の cdkd で作れるとは考えにくいです。もう 1 つは、スタックがリージョンを宣言していれば、cdkd はそのスタックをそのリージョンにデプロイすることです。state を置くバケットの名前にはリージョンが入っておらず、bootstrap はアカウントに 1 回と説明されています。大阪のスタックのデプロイに、東京で済ませた bootstrap で足りるかどうかは、確かめていません。

どれも、パッケージの中身とテンプレートを読んだだけで、実物には作っていません。

## デプロイと確認

<!-- section: 28.deploy -->

順序があります。

```bash
vp run mr:infra:synth
vp run mr:standby:infra:deploy
vp run mr:infra:deploy
vp run mr:status
```

大阪が先なのは、東京のバケットの複製の設定が、宛先である大阪のバケットを必要とするからです。テーブルは東京のスタックが作るので、大阪の関数は、東京のデプロイが終わるまでテーブルを読めません。そのあいだ、大阪のヘルスチェックの経路は `503` を返します。

`mr:status` は、2 つのリージョンを順に見て回ります。

<<< @/examples/28-multi-region/scripts/mr.ts{status}

両方のリージョンで、テーブルのレプリカが `ACTIVE` と表示され、ヘルスチェックの経路が `200` を返せば、準備ができています。

次に、この章の中心だった衝突を、実物で起こします。

```bash
vp run mr:conflict
vp run mr:conflict --apply
```

`--apply` を付けないと、何をするかを表示するだけです。付けると、東京でノートを 1 件作り、大阪で読めるようになるのを待ってから、2 つのリージョンに同じ version の編集を同時に送ります。

<<< @/examples/28-multi-region/scripts/mr.ts{conflict}

期待する結果を、1 つに決めることはできません。2 つの `PUT` が複製の遅れより短い間隔で届けば、両方に `200` が返り、5 秒後には両方のリージョンが同じ 1 つのタイトルを持っているはずです。手元から東京と大阪までの遅延の差が複製の遅れより大きければ、後から届いたほうに `409` が返ります。どちらになったかを記録してください。`200` が 2 つ返ったなら、[しくみと実装のページ](/ja/chapters/28-multi-region/build.md)のテストと同じことが、実物で起きたことになります。

### 設定を足すとき

逆向きの複製は、東京のバケットができたあとで足します。

```bash
vp run mr:standby:infra:deploy -c back=on
```

コンテキストは、デプロイのたびに付けます。付け忘れてデプロイすると、付けていたときに作ったものが、差分として消されます。続けて使う設定は、`examples/28-multi-region/cdk.json` の `context` に書いておくほうが安全です。

ドメインを付ける場合は、2 つのスタックに同じ値を渡します。

```bash
vp run mr:standby:infra:deploy -c domain=<名前> -c zoneId=<ゾーンの ID> -c zoneName=<ゾーンの名前>
vp run mr:infra:deploy -c domain=<名前> -c zoneId=<ゾーンの ID> -c zoneName=<ゾーンの名前>
```

2 つのスタックが、同じドメインの証明書をそれぞれのリージョンで要求し、DNS で検証します。検証用のレコードを 2 つのスタックが同時に扱ってもうまくいくかどうかは、確かめていません。

ドリフトの検査（`vp run mr:infra:drift`）は、東京のスタックにだけ用意しました。この本のドリフトのタスクは、1 つのリージョンの 1 つのスタックを前提に作ってあるからです。大阪のスタックには、`diff`、`deploy`、`destroy` の 3 つだけがあります。

## 切り替えの訓練

<!-- section: 28.failover-drill -->

リージョンの障害を、自分で起こすことはできません。起こせるのは、Route 53 に東京が異常だと思わせることです。そのための設定を用意しました。

```bash
vp run mr:infra:deploy -c drill=on -c domain=<名前> -c zoneId=<ゾーンの ID> -c zoneName=<ゾーンの名前>
```

`-c drill=on` を付けると、東京の関数のヘルスチェックの経路だけが `503` を返すようになります。ほかの経路は、今までどおり動きます。これは、[しくみと実装のページ](/ja/chapters/28-multi-region/build.md)で扱った「異常と判定されたが、実際には動いている」状態そのものです。

訓練で測るのは、次の時刻です。

1. デプロイが終わった時刻
2. Route 53 のコンソールで、東京のヘルスチェックが異常に変わった時刻
3. 共有の名前へのリクエストの `x-aih-region` が、初めて `ap-northeast-3` になった時刻
4. 手元のすべてのクライアントで、`ap-northeast-3` だけが返るようになった時刻

1 から 2 が検出の時間、2 から 3 が DNS の時間、3 から 4 がクライアントの時間で、`examples/28-multi-region/src/objectives.ts` の内訳と比べられます。3 と 4 のあいだに `mr:conflict` と同じ編集を送れば、古い行き先を覚えているクライアントが何を起こすかも、実物で見られます。

戻すときは、`-c drill=on` を外してデプロイします。ヘルスチェックが正常に戻ると、Route 53 はまた東京を返します。戻るときにも、切り替わるときと同じ長さの窓があります。大阪で書かれたノートは、テーブルの複製で東京にも届いています。大阪で書かれた画像は、`-c back=on` を付けていなければ、東京にはありません。

この訓練が確かめないことも、書いておきます。東京が実際には動いているので、東京に書かれて大阪に届かなかったデータは生まれません。本物の障害で失うデータの量は、この訓練ではわかりません。複製を止める実験には、AWS Fault Injection Service にグローバルテーブル用のアクションがあると、DynamoDB のドキュメントに書かれています。使い方は調べていません。[概要のページ](/ja/chapters/28-multi-region.md)の一覧にあった、サインイン、シークレット、デプロイの仕組みが、東京なしで動くかどうかも、この訓練の外にあります。
