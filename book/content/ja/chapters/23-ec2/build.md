# 23 VM: しくみと実装

[前のページ](/ja/chapters/23-ec2.md)で、料金と全体の構成を見ました。このページでは、インスタンスへの入り方、権限、AMI、最初の起動で走るスクリプトを順に作ります。

## SSH のポートは開けない

<!-- section: 23.access -->

サーバーに入る手段は、長いあいだ SSH でした。22 番のポートを開け、鍵を配り、踏み台を置きます。この章では、そのどれもしません。開いているポートは攻撃の入口になり、配った鍵は誰かの PC に残り続けるからです。

かわりに Systems Manager の Session Manager を使います。インスタンスの中では SSM Agent というプロセスが動いていて、Systems Manager に向けて HTTPS の接続を張っています。手元で `aws ssm start-session` を呼ぶと、Systems Manager がその接続を通してシェルをつなぎます。接続を始めるのはいつもインスタンスの側なので、インバウンド（inbound）の規則は 1 つも要りません。誰が入れるかは、鍵ではなく IAM が決めます。

必要なものは 3 つあります。

1. **SSM Agent。** AWS が配っている Amazon Linux 2023 の AMI には、最初から入っています
2. **権限。** インスタンスのロールに `AmazonSSMManagedInstanceCore` というマネージドポリシーを付けます（次の節で扱います）
3. **Systems Manager までの経路。** 料金がかかるのは、この経路です

経路の作り方は 3 通りあります。金額は、通信がなくてもかかる 1 か月ぶんです。

| インスタンスの置き場所 | Systems Manager への経路 | 経路の料金 |
| --- | --- | --- |
| プライベートサブネット | インターフェースエンドポイントを 3 つ（`ssm`、`ssmmessages`、`ec2messages`） | 61.32 |
| プライベートサブネット | NAT Gateway | 48.91（11章の `-c egress=nat`） |
| パブリックサブネット | インターネットゲートウェイと、インスタンスのパブリック IPv4 アドレス | 3.65 |

どれを選んでも、インバウンドの規則は空のままです。パブリックサブネットに置いても、外からインスタンスへの接続は始められません。

### 既定はプライベートサブネット

試すだけなら、パブリックサブネットのほうが 5 分の 1 以下の料金で済みます。そのため、どちらを既定にするかは迷いました。

それでもプライベートを既定にした理由は 2 つあります。1 つは、パブリック IPv4 アドレスを持つマシンは、セキュリティグループの規則が 1 行足されるだけで外から届くようになることです。いまはインバウンドが空でも、長く動かすマシンの設定は、いずれ誰かが変更します。もう 1 つは外向きの通信です。パブリックサブネットのインスタンスは、443 番ならインターネットのどこへでも出られますが、プライベートサブネットのインスタンスが届くのは Systems Manager と S3 だけです。中のソフトウェアが乗っ取られたときに、攻撃者にできることが変わります。

長く置くマシンや、24章のように複数台で動かすものは、プライベートサブネットに置くのが普通なので、既定もそれに合わせました。この章を一度通すだけなら、`-c placement=public` で十分です。その場合もインバウンドは空で、テストがそれを固定しています。

### 11章の VPC につなぐ

インターフェースエンドポイントは、11章のスタックの設定を切り替えて足します。

```bash
vp run net:infra:deploy -c interfaceEndpoints=ssm,ssmmessages,ec2messages
```

11章で見たとおり、`-c` はその 1 回のコマンドにしか効きません。あとで `-c` を付けずに 11章をデプロイし直すと、エンドポイントが消えて、この章のインスタンスは Systems Manager から見えなくなります。

エンドポイントが 3 つとも必要かどうかは、言い切れません。Systems Manager のドキュメントは 3 つを並べていますが、同じページに、SSM Agent 3.3.40.0 以降は `ec2messages` のかわりに `ssmmessages` を使うとも書いてあります。`ec2messages` を省ければ月に USD 20.44 減ります。ただ、エンドポイントを省いてよいとは書かれておらず、実機でも試していないので、この章は 3 つとも置いています。

`securityGroupIngress` がないのは書き忘れではなく、インバウンドを許可しないという設定です。テストは、インバウンドの規則が 1 つも無いことと、SSH のキーペアを指定していないことを確かめています。

アウトバウンド（outbound）は 443 番だけにしました。セキュリティグループを作ると、最初は「すべての宛先へ、すべての通信を許可」というアウトバウンドの規則が付き、規則を 1 つ書くとそれに置き換わります。DNS、時刻合わせ、次の節で扱うインスタンスメタデータへの通信は、セキュリティグループが検査しないので、規則を書かなくても通ります。

### 経路がないときに起きること

この章でいちばんつまずきやすいのが、経路の不足です。エンドポイントを足し忘れてもデプロイは成功し、インスタンスは起動して、状態は running になります。ところが Systems Manager にはいつまでも現れず、エラーもどこにも出ません。

そこで、経路があるかどうかを、デプロイの前に手元で確かめられるようにしました。11章の経路のモデルをそのまま使っています。

<<< @/examples/23-ec2/src/access.ts{access}

`vp run ec2:plan` に、11章をデプロイするときの設定を渡してみてください。

```bash
vp run ec2:plan interfaceEndpoints=ssm
```

`ssmmessages` と `ec2messages` が `UNREACHABLE` と表示されて、タスクは失敗で終わります。S3 への経路は、11章が既定で作るゲートウェイエンドポイント（gateway endpoint）です。こちらは無料で、OS のパッケージ、SSM Agent の更新、この章のリリースの取得に使います。

Amazon Linux 2023 のパッケージのリポジトリに、プライベートサブネットから S3 のゲートウェイエンドポイントだけで届くことは、確かめていません。リポジトリが S3 のバケットであることも、ドキュメントの出力例にあるホスト名から読み取っただけです。届かなければ、最初の起動で Node.js が入らず、ユーザーデータのスクリプトが失敗します。そのときの調べ方は、[つまずきやすいところ](/ja/chapters/23-ec2/wrap.md)に書きました。

## インスタンスの権限は、中から取りに行く

<!-- section: 23.role -->

Lambda に実行ロールがあったように、インスタンスにもロールを持たせます。

<<< @/examples/23-ec2/infra/lib/ec2-stack.ts{role}

EC2 はロールを直接は受け取れません。インスタンスプロファイル（instance profile）という入れ物にロールを 1 つ入れて、それをインスタンスに付けます。CDK の高水準のコンストラクトを使えば自動で作られますが、何が作られるのかを見えるようにしたかったので、自分で書きました。

`AmazonSSMManagedInstanceCore` は AWS が管理しているポリシーです。中を読むと、対象はすべて `"Resource": "*"` で、`ssm:GetParameter` も入っています。そのため、このインスタンスの中のプロセスは、アカウントの Parameter Store の値を読もうと思えば読めます。04章から `*` を使わない方針で来ましたが、ここでは AWS のポリシーをそのまま使うので例外です。自分で足した権限は、リリースを置くバケットの `releases/` の下を読む権限 1 つだけです。

### 認証情報の出どころ

インスタンスの中の AWS CLI や SDK は、アクセスキーを設定しなくても動きます。認証情報を IMDS（Instance Metadata Service）から取っているからです。インスタンスの中からだけ届く `169.254.169.254` というアドレスがあり、そこに問い合わせると、ロールの一時的な認証情報が返ってきます。認証情報には期限があり、自動で入れ替わります。ディスクに鍵を置かずに済むのは、この仕組みがあるからです。

便利な反面、インスタンスの中で動くものなら何でもこのアドレスに問い合わせられる、という弱点があります。たとえば、ユーザーが指定した URL の内容を取りに行く機能がアプリにあるとします。URL として `http://169.254.169.254/...` を渡されると、アプリが認証情報を取ってきて、レスポンスとして返してしまうかもしれません。

IMDS には版が 2 つあります。v1 はただの GET に答えるので、いま挙げた攻撃がそのまま通ります。v2 では、先に PUT でトークンを受け取り、それをヘッダーに付けて問い合わせます。URL を 1 つ GET させるだけの穴からは、PUT もヘッダーの追加もできません。さらに、`X-Forwarded-For` ヘッダーの付いた PUT は拒否されるので、プロキシ越しのリクエストも通りません。

<<< @/examples/23-ec2/infra/lib/ec2-stack.ts{instance}

`httpTokens: "required"` で、v2 だけを受け付けるようにしています。`httpPutResponseHopLimit` は、トークンを載せたレスポンスがネットワークを何段まで渡れるかを決める値で、1 ならインスタンス自身にしか届きません。インスタンスの中でコンテナを動かし、コンテナにもロールを使わせたいときは 2 にします。Amazon Linux 2023 の AMI は、何も指定しなくても v2 必須、hop limit 2 で起動するとされていますが、AMI やアカウントの既定値には頼らず、コードに書いて固定しました。

v2 にしても、ロールがインスタンスに 1 つしかなく、中のプロセス全部が共有することは変わりません。権限の低い `notes` というユーザーで動かしているノート API も、トークンを取る手順を踏めば、同じ認証情報を手にできます。インスタンスのロールに付けた権限は、そのマシンで動くすべてのコードに付けた権限だと考えてください。

## AMI を選ぶ

<!-- section: 23.ami -->

AMI（Amazon Machine Image）は、インスタンスの最初のディスクの中身になるひな形です。この章は Amazon Linux 2023 の arm64 版を使います。

AMI には `ami-0123...` のような ID があります。ID はリージョンごとに違い、新しい版が出るたびに変わるので、コードに書くとすぐ古くなります。そこで AWS は、いちばん新しい AMI の ID を、Parameter Store の公開のパラメーターとして配っています。

<<< @/examples/23-ec2/infra/lib/ec2-stack.ts{ami}

このコードからテンプレートを合成（synth）すると、`AWS::SSM::Parameter::Value<AWS::EC2::Image::Id>` という型のパラメーターが 1 つできます。値を引くのはデプロイのときで、合成の段階では AWS に何も問い合わせません。テストは、パラメーターの名前が `/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-arm64` であることと、合成が問い合わせを残さないことを確かめています。

このコードに落ち着くまでに、固定した版（aws-cdk-lib 2.273.0）で 2 回つまずきました。

まず、よく紹介される `MachineImage.latestAmazonLinux2023()` は、`kernel` を渡しても無視して、カーネル 6.1 用のパラメーターを引きます。Amazon Linux のドキュメントによると、`kernel-default` のほうは 2026 年 8 月から 6.18 になっています。次に、かわりに `AmazonLinux2023ImageSsmParameter` を直接使うと、既定では合成のときに AMI を調べに行こうとするので、アカウントを指定していないスタックでは合成が失敗します。これを避けるには `cachedInContext: false` が要ります。

### 「最新」の AMI は置き換えを起こす

最新の ID を引く仕組みは便利ですが、長く動かすマシンには向きません。

AMI の ID が変わると、インスタンスは**置き換え**になります。CloudFormation のドキュメントでは `ImageId` の変更は Replacement で、cdkd のソースでも同じ扱いです。新しい AMI は頻繁に出るので、先月と同じコードをデプロイしただけで、マシンが新しいものに入れ替わることがあります。そのとき、ルートボリュームの中身は古いインスタンスと一緒に消えます。CDK の型定義のコメントにも、このイメージを使うならインスタンスに状態を置くな、と書いてあります。

そこでこの章では、消えて困るデータをルートボリュームに置かないようにしました（[データは別のボリュームに置く](/ja/chapters/23-ec2/more.md)）。あわせて、AMI を固定できるようにもしてあります。

```bash
aws ssm get-parameter --region ap-northeast-1 --name /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-arm64 --query Parameter.Value --output text
vp run ec2:infra:deploy -c amiId=ami-xxxxxxxxxxxxxxxxx
```

1 行目で、いまの ID がわかります（認証情報が要ります）。その ID を `-c amiId=` で渡すと、テンプレートには ID がそのまま入り、自分で変えるまで変わりません。練習なら「最新」のままで構いません。置いたままにするマシンなら AMI を固定して、パッチは自分の予定で当てます（[パッチを当てる](/ja/chapters/23-ec2/deploy.md)）。

どちらの場合も、デプロイの前に `vp run ec2:infra:diff` を見る習慣をつけてください。ただし、パラメーターの先で AMI が変わったことを、cdkd の diff が置き換えとして表示するかどうかは、確かめていません。

## 最初の起動でやること

<!-- section: 23.user-data -->

起動したばかりのインスタンスには、Node.js も、ノート API も、それを動かすユーザーもありません。これらを用意するのがユーザーデータ（user data）です。インスタンスを作るときにシェルスクリプトを渡しておくと、最初の起動のときに root で実行されます。

渡すスクリプトは、TypeScript の関数が組み立てます。

<<< @/examples/23-ec2/src/user-data.ts{user-data}

スクリプトは、Node.js を入れ、権限の低いユーザーを作り、設定ファイルと systemd のユニットと 2 つのスクリプトを置き、サービスを有効にして、最後にデータボリュームを用意します。組み立てた結果を `examples/23-ec2/deploy/user-data.sh` に置いてあるので、TypeScript を読まなくても、実行される内容をそのまま読めます。

この関数は純粋で、入力は設定だけです。時刻も、デプロイのときに決まる値も入らないので、同じ設定からはいつでも同じスクリプトが出ます。そのため、テストで読んだものと、インスタンスで実行されるものが一致します。

### root のシェルに入る値はすべて疑う

ユーザーデータは root で実行されます。そこに設定値を文字列として埋め込むので、値に `; rm -rf /` や `$(...)` が紛れ込むと、そのまま実行されてしまいます。

<<< @/examples/23-ec2/src/machine.ts{spec}

埋め込む値は、すべてこのスキーマを通します。パスに使えるのは英数字と `.` `_` `-` だけで、名前は小文字で始まる短い文字列に限ります。引用符も、空白も、改行も入りません。テストは、どの項目に危険な値を入れても、スクリプトの生成が例外で止まることを確かめています。

秘密の値も入れません。ユーザーデータは、インスタンスの中のどのプロセスからも IMDS 経由で読めますし、`aws ec2 describe-instance-attribute` を呼べる人なら外からも読めます。この章のサンプルに秘密の値はありませんが、あったとしてもユーザーデータに置いてはいけません。テストは、設定ファイルに入る項目が 6 つ（許可するオリジン、ログのレベル、ステージ、ホスト、ポート、ノートのファイルのパス）だけであることも確かめています。

### ユーザーデータの限界

ユーザーデータに頼りすぎると困る点が 3 つあります。

1 つ目は、実行されるのが最初の起動の 1 回だけであることです。あとでスクリプトを直してデプロイしても、動いているインスタンスでは実行し直されません。cdkd のソースを読むかぎり、`UserData` の変更はインスタンスに届きもしません。CloudFormation ならインスタンスを再起動しますが、その場合もスクリプトは実行されません。マシンの構成を変えるには、インスタンスを作り直すか、中に入って手で変えることになります。

2 つ目は、失敗に気づきにくいことです。スクリプトが 5 行目で落ちても、EC2 から見れば OS は立ち上がっているので、インスタンスは running のままです。この章のスクリプトは `set -euo pipefail` を指定して、最初に失敗したところで止まるようにしてあります。半分だけ設定されたマシンより、途中で止まったマシンのほうが見つけやすいからです。結果は `vp run ec2:status` で見られ、出力はインスタンスの `/var/log/cloud-init-output.log` に残ります。

3 つ目は、大きさが 16 KB までに限られることです。いまのスクリプトは 4 KB ほどで、アプリのコードを詰め込む場所ではありません。

この 3 つ目が、設計を決めています。ユーザーデータが用意するのはマシンまでで、アプリは入れません。アプリは何度も入れ替えるものだからです。入れ替えの手順は、[デプロイして、インスタンスに入る](/ja/chapters/23-ec2/deploy.md)で作ります。
