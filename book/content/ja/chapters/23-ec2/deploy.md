# 23 VM: デプロイ

このページでは、スタックをデプロイしてアプリを入れ、そのあと運用で必要になるスナップショットとパッチを扱います。[手元で動かす](/ja/chapters/23-ec2/local.md)のページに書いたとおり、このページのコマンドは実機ではまだ実行していません。

## デプロイして、インスタンスに入る

<!-- section: 23.deploy -->

デプロイには順番があり、先に 11章の VPC、次にこの章のスタックです。ここでは既定の構成で進めます。

```bash
vp run ec2:plan
vp run net:infra:deploy -c interfaceEndpoints=ssm,ssmmessages,ec2messages
vp run ec2:infra:diff
vp run ec2:infra:deploy
```

2 行目から、時間単位の課金が始まります。安いほうの構成で試すなら、2 行目の `-c` を外して、4 行目に `-c placement=public` を付けます。その場合は、以降の `ec2:infra:` のコマンドにも毎回同じ `-c` を付けてください。付け忘れてデプロイすると、インスタンスがプライベートサブネットに作り直されます。

デプロイが終わった時点では、ユーザーデータのスクリプトがまだ実行中です。数分待ってから、状態を確かめます。

```bash
vp run ec2:status
```

Systems Manager から見たインスタンスの状態、cloud-init の結果、サービスの状態、データボリュームのマウントが表示されます。インスタンスの状態が `Online` なら、経路と権限は通っています。この時点では、サービスは有効になっているだけで、動いてはいません。アプリがまだ無いからです。

### アプリを入れる

```bash
vp run ec2:app:release
```

このタスクは、API をビルドして S3 に置き、インスタンスに取りに来るよう伝えます。伝える手段は Run Command です。Session Manager と同じ経路でコマンドを送り、結果を受け取ります。

古い版はインスタンスに残っているので、前の版に戻すにはリンクを付け替えるだけで済みます。

```bash
vp run ec2:app:rollback 20261012T010203Z-0123456789abcdef
```

版の名前には、`ec2:app:release` が表示したものを使います。自動では戻しません。戻すかどうかは、自分で判断します。

### 動いているか確かめる

```bash
vp run ec2:smoke
vp run ec2:logs
```

`ec2:smoke` は、インスタンスの中で `curl` を実行して、ノートを 1 件作り、一覧を取ります。API はインスタンスの外からは呼べないので、中から呼んでいます。

手元の `curl` やブラウザから呼びたいときは、ポートフォワーディングを使います。

```bash
vp run ec2:forward
curl -s http://localhost:8787/health
```

1 行目を動かしている間、手元の 8787 番がインスタンスの 8787 番につながります。セキュリティグループには何も足していません。対話型のシェルが必要なときは `vp run ec2:session` を使います。

`ec2:forward` と `ec2:session` には、AWS CLI とは別に Session Manager プラグインが要ります。devShell には入っていないので、AWS のドキュメントの手順で入れてください。入れなくても、マネジメントコンソールの Session Manager からシェルを開けますし、`ec2:status`、`ec2:smoke`、`ec2:logs`、`ec2:app:release` はプラグインなしで動きます。

誰が入れるかは IAM が決める、と[SSH のポートは開けない](/ja/chapters/23-ec2/build.md)の節に書きました。これは、`ssm:StartSession` や `ssm:SendCommand` を許された人が、このマシンの管理者になるということでもあります。Run Command のコマンドは管理者権限で実行されますし、セッションのユーザー（`ssm-user`）も `sudo` を使えます。この 2 つの権限は、SSH の鍵と同じ重さで扱ってください。

ドリフトの検査は、02章と同じです。

```bash
vp run ec2:infra:drift
```

ここまでのコマンドを実機で初めて実行するときに、気をつけて見たいのは cdkd の動きです。このスタックのリソースの種類のうち、インスタンス、セキュリティグループ、インスタンスプロファイル、ロール、バケットには、cdkd が専用の実装を持っています。ボリュームとボリュームのアタッチメント（volume attachment）には専用の実装がなく、Cloud Control API 経由になります。11章の VPC の出力を `Fn::ImportValue` で読むところも、実行するのは初めてです。最初に確かめたいのは、これらの点です。

## スナップショットとリストア

<!-- section: 23.backup -->

データボリュームは 1 つしかないので、壊れるとノートが全部なくなります。これに備えるのがスナップショットです。スナップショットはある時点のボリュームの写しで、S3 に置かれ、リージョンの中のどの AZ にもボリュームとしてリストアできます。差分で保存されるので、2 回目からは変わったぶんだけが保存されます。

この節の手順も、コマンドのフラグを devShell の AWS CLI の help で確かめただけです。

### スナップショットを取る

```bash
vp run ec2:data:unmount
aws ec2 create-snapshot --region ap-northeast-1 --volume-id vol-xxxxxxxxxxxxxxxxx --description "notes before the upgrade"
vp run ec2:data:mount
```

ボリュームの ID は、スタックの出力の `DataVolumeId` です。

書き込みの途中のボリュームを写すと、中途半端な状態が写ることがあります。そのため、1 行目で先にサービスを止めてアンマウントします。スナップショットに写るのは取り始めた時点の中身なので、完了まで待つ必要はありません。状態が `pending` になったら、3 行目でマウントし直してサービスを起こせます。1 行目から 3 行目までの間、API は止まっています。

`ec2:data:mount` が実行するのは、最初の起動のときと同じスクリプトです。フォーマットしないという判断も同じです。

### スナップショットから戻す

いちばん単純なのは、スナップショットからボリュームを作る作業をスタックに任せる方法です。

```bash
vp run ec2:infra:deploy -c dataSnapshotId=snap-xxxxxxxxxxxxxxxxx
```

スタックを消した後であれば、このコマンドで、インスタンスと、スナップショットの中身を持ったボリュームができます。最初の起動のスクリプトは、ファイルシステムがあるのを見て、フォーマットせずにマウントします。あとは `vp run ec2:app:release` を実行すれば、ノートが戻ります。AZ が使えなくなったときも同じ方法が使えて、11章の VPC が別の AZ にサブネットを持っていれば、そちらにリストアできます。ただし、この章のスタックは 1 つ目の AZ に固定しているので、コードの変更が要ります。

動いているスタックに `dataSnapshotId` を足す場合は、事情が違います。CloudFormation のドキュメントでは、ボリュームの `SnapshotId` は更新できないプロパティです。cdkd のソースではボリュームの置き換えになり、古いボリュームが消える操作なので、`--force-stateful-recreation` を付けないと拒否されます。この経路はソースを読んだだけで、動かしていません。

スナップショットから作ったボリュームは、最初のうち遅いことがあります。中身は、読まれたときに初めて S3 から運ばれてくるからです。

忘れやすいのは、スナップショットがスタックのリソースではないことです。スタックを消しても残り、料金がかかり続けます。残っていないかは、[片付け](/ja/chapters/23-ec2/wrap.md)で確かめます。

## パッチを当てる

<!-- section: 23.patch -->

Lambda では、OS のパッチは AWS の仕事でした。EC2 では、自分の仕事になります。

Amazon Linux 2023 のインスタンスは、AMI が作られた時点のパッケージの版に**固定されています**。`dnf upgrade` を実行しても新しいものは何も来ませんし、セキュリティ更新が自動で当たることもありません。先月と今月で同じコマンドが同じ結果になるように、こういう作りになっています。

したがって、何もしなければ、マシンは起動した日の状態のまま古くなっていきます。パッチの当て方は 2 つあります。

1 つは、動いているインスタンスをその場で上げる方法です。新しい版が出ているかを調べて、版を名指しして上げます。

```bash
vp run ec2:patch:check
vp run ec2:patch:apply 2023.12.20260930
```

2 行目の引数には、1 行目が表示した版を渡します。`latest` は受け付けません。Amazon Linux のドキュメントも、`latest` を指定すると、試していない更新を本番でいきなり試すことになると書いています。カーネルが更新された場合、再起動するまでは古いカーネルで動き続けるので、`aws ec2 reboot-instances` で再起動してください。その間、API は止まります。

もう 1 つは、新しい AMI でインスタンスを置き換える方法です。[AMI を選ぶ](/ja/chapters/23-ec2/build.md)の節の `-c amiId=` に新しい ID を渡してデプロイします。ユーザーデータが最初から実行され、データボリュームが付け直されるので、そのあとリリースをもう一度入れます。手で変更した跡が何も残らないので、こちらのほうが結果を予想しやすくなります。Amazon Linux のドキュメントも、この方法を勧めています。

ただ、置き換えにはわかっていないことがあります。置き換えのときにボリュームのアタッチメントがどう動くのかを、cdkd のソースから読み切れませんでした。古いインスタンスから外して新しいインスタンスに付ける、という順序で cdkd が処理するのか、途中で失敗するのかがわかりません。実機で試すまで、この方法は「できるはず」の段階です。試すときは、先にスナップショットを取ってください。

Systems Manager には、Patch Manager という機能もあります。足りないパッチを調べ、当て、当たっているかを一覧にする機能で、台数が増えたら必要になります。ドキュメントによると、Patch Manager は Amazon Linux 2023 の版の固定を見ずに、いつも最新のリポジトリを使うので、その点には注意が要ります。この章では設定していません。

### 作り直せる状態を保つ

置き換えでパッチを当てる考え方を進めていくと、Auto Scaling group に行き着きます。インスタンスの作り方（起動テンプレート、launch template）と台数を渡しておくと、インスタンスが不健康になったときに、新しいものに置き換えます。台数を 1 にしておけば、常に 1 台がいる状態を保つ仕事を AWS に任せられます。

この章では作っていません。置き換えが自動で起きるなら、置き換えのたびに必要な作業も、すべて自動でなければならないからです。いまの構成では、データボリュームの付け直しとリリースの入れ直しに、人の手が要ります。そこまで自動にする価値があるかどうかは、[1 台は単一障害点](/ja/chapters/23-ec2/wrap.md)の節の条件と合わせて判断します。

### 長く動かすマシンで自分が持つもの

- **OS とランタイムのパッチ。** Node.js も OS のパッケージなので、同じ方法で上がります
- **ディスクの空き。** journald のログと、`/opt/notes/releases` の古い版は、放っておくと増えます。消すのは自分です
- **コードと実物のずれ。** セッションで入って手で直した内容は、どこにも記録されません。次に作り直したマシンには、その修正が入っていません。ドリフトの検査が見るのは AWS のリソースの設定で、OS の中までは見ません
- **バックアップ。** 取っているだけでなく、リストアできることまで確かめます
