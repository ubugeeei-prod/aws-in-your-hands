# 23 VM: 実装のつづき

[前のページ](/ja/chapters/23-ec2/build.md)で、インスタンスとその最初の起動までを作りました。このページでは、その上で動くノート API の側を作ります。プロセスを systemd に任せ、止められたときの終わり方を決め、ノートを別のボリュームのファイルに書きます。

## プロセスを systemd のサービスにする

<!-- section: 23.service -->

`node server.mjs` と打てば API は動きますが、セッションを閉じれば止まります。落ちても誰も起こしませんし、OS を再起動したら、誰かがもう一度打たなければなりません。

この仕事を引き受けるのが systemd です。systemd は Linux で最初に起動して、ほかのプロセスを管理するプログラムです。何を、どのユーザーで、どう動かし、落ちたらどうするかを、ユニット（unit）というファイルで伝えます。

<<< @/examples/23-ec2/deploy/notes.service

上から順に読んでいきます。

`RequiresMountsFor` と `AssertPathIsMountPoint` は、データボリュームがマウントされていなければ起動しない、という指定です。この指定がないと、ボリュームの用意に失敗したまま API が立ち上がり、ノートがルートボリュームの同じパスに書かれます。動いているように見えたまま、インスタンスを作り直した日にノートが全部消えます。

`ConditionPathExists` は、アプリの本体がまだ無ければ、エラーにせずに起動を見送る指定です。最初のリリースの前は、本体が無いのが正常な状態です。

`User=notes` で、root ではなく専用のユーザーとして動かします。`ProtectSystem=strict` は、このプロセスにファイルシステム全体を読み取り専用として見せる指定で、`ReadWritePaths` に書いたデータボリュームだけが例外です。API に穴があっても、書き換えられる場所はデータボリュームしかありません。

`Restart=on-failure` は、異常終了したら 2 秒後に起こし直す指定です。ただ、起動するたびに落ちるプロセスを起こし続けても意味がないので、`StartLimitBurst` で、1 分のうちに 5 回落ちたら起こすのをやめるようにしています。やめたサービスは `failed` という状態で残るので、状態を見ればわかります。

`ExecStart` の `/usr/bin/node-24` は、Amazon Linux 2023 の `nodejs24` というパッケージが入れる、版の名前が付いた実行ファイルです。名前に版の付かない `node` は別の版を指すように切り替えられるので、使っていません。

環境変数はユニットに直接書かず、`EnvironmentFile` で別のファイルから読みます。その中の `HOST=127.0.0.1` によって、API はインスタンスの中でしか待ち受けません。誰かがセキュリティグループを開けてしまっても、外からは届きません。

ここに書いたディレクティブの意味は、systemd 252 の man page で確かめたものです。Amazon Linux 2023 に入っている systemd の版は、インスタンスの上では確かめていません。

### ログの行き先

04章のアプリは、ログを標準出力に JSON で書きます。systemd の下では、そのログが journald に溜まります。Amazon Linux 2023 には、以前からある `/var/log/messages` はありません。

```bash
vp run ec2:logs
```

このタスクは、Run Command で `journalctl --unit notes.service` を実行して、最後の 50 行を取ってきます。

Lambda のときと違って、このログはインスタンスのルートボリュームにあるので、インスタンスが消えればログも消えます。インスタンスが落ちた理由を知りたいときほど、ログが残っていないことになります。これを避けるには、ログをインスタンスの外に出します。CloudWatch エージェントを入れれば journald の内容を CloudWatch Logs に送れますが、プライベートサブネットからは `logs` のインターフェースエンドポイントがもう 1 つ必要で、月に USD 20.44 増えます。ロールにも権限が要ります。練習用のマシンには過剰なのでこの章では入れていませんが、本番のマシンには必須です。

## 止まるときの手順

<!-- section: 23.shutdown -->

サービスは、外から止められることがあります。リリースのたびに再起動しますし、OS の再起動もあります。そのとき systemd は、止まるように求める SIGTERM というシグナルをプロセスに送ります。

何も手当てをしなければ、Node.js はその場で終了します。処理の途中だったリクエストはレスポンスを受け取れないまま切られ、ノートを保存している最中だった場合は、呼んだ側には保存されたかどうかもわかりません。

<<< @/examples/23-ec2/src/shutdown.ts{shutdown}

SIGTERM を受けたら、新しい接続を断り、処理中のリクエストを最後まで終え、書き込みがディスクに届くのを待ってから終了します。これをグレースフルシャットダウンと呼びます。

```figure
caption: SIGTERM を受けたプロセスは、新しい接続を断り、処理中のリクエストと書き込みを終えてから終わる
type: sequence
actor systemd: systemd
actor proc: notes process
actor client: client
step systemd -> proc: t0: systemctl restart, SIGTERM
step proc -> proc: t1: 待ち受けのソケットを閉じる
step client -x proc: 新しい接続は拒否
step proc --> client: t2: t0 より前のリクエストに 201
step proc -> proc: t3: 待っていた書き込みを flush
step proc -> proc: t4: exit 0
step systemd -> proc: t5: 新しいプロセスを起動
note proc: また待ち受ける
step client -> proc: 接続を受け付ける
```

```figure
caption: 待つ限度は 2 つあり、プロセスが自分で終わる 20 秒が、systemd の 30 秒より先に来る
type: sequence
actor systemd: systemd
actor proc: notes process
actor client: client
step systemd -> proc: t0: SIGTERM
note proc: 20 s たっても t2 が来ない
step proc -x client: 残りの接続を閉じる
step proc -> proc: exit 1
note systemd: 30 s たってもプロセスがいる
step systemd -> proc: SIGKILL (TimeoutStopSec)
```

1 つ目の図は処理中のリクエストが時間内に終わる場合、2 つ目の図は終わらない場合です。待つ時間には限度があり、20 秒たっても終わらないリクエストは、プロセスの側から切ります。systemd は 30 秒（ユニットの `TimeoutStopSec`）たつと SIGKILL を送り、プロセスはこれを拒めないので、その前に自分で終了するようにしています。テストはこの 2 つの数字の大小を確かめていて、片方だけを変えると失敗します。

## データは別のボリュームに置く

<!-- section: 23.data -->

04章では、ノートは `Map` の中にあり、実行環境が入れ替わると消えました。この章ではプロセスが 1 つで、動き続けるので、ノートをファイルに書きます。

<<< @/examples/23-ec2/src/file-notes.ts{repository}

このクラスは、04章の `NoteRepository` というインターフェースをそのまま実装しています。

守りたい不変条件は、次の 1 文です。**201 を返したノートは、プロセスが再起動しても、インスタンスが作り直されても、読める。**

この条件を壊すのは、書いている途中の停止です。ファイルを半分だけ書いたところで電源が落ちると、JSON として読めないファイルが残り、次に起動したときにノートが 1 件も読めなくなります。

<<< @/examples/23-ec2/src/file-notes.ts{storage}

そのため、ファイルを直接は上書きしません。隣に新しいファイルを書き、ディスクに届いたことを確かめてから、名前を付け替えます。名前の付け替えは、済んだか済んでいないかのどちらかにしかなりません。読む側に見えるのは古い中身か新しい中身のどちらかで、混ざったものは見えません。

テストは、この手順の 3 か所（書き込み、付け替え、ディレクトリの同期）で順に電源を落とします。どこで落ちても、残ったファイルは丸ごと読めて、メモリの中身と一致します。壊れたファイルを見つけたときは、空の状態で起動せず、起動を拒否します。空で起動すると、次の書き込みで、壊れたファイルを空のファイルで上書きしてしまうからです。

逆は成り立ちません。付け替えのあと、ディレクトリの同期で失敗すると、呼んだ側には 500 が返るのに、ノートは保存されています。失敗と伝えられたのに保存されている、という状態です。呼んだ側が再試行すれば、同じノートが 2 件できます。04章の API には、重複を防ぐ仕組みがありません。また、このクラスが正しく動くのは、プロセスが 1 つのときだけです。同じファイルを 2 つのプロセスが開けば、後から書いたほうが、もう片方の書き込みを消します。プロセスが 1 つであることを保証しているのは、コードではなく systemd です。

### ファイルを置くディスク

インスタンスのディスクは EBS ボリュームです。ネットワーク越しにつながるディスクで、インスタンスとは別のリソースとして存在できます。

インスタンスには、ルートボリュームが 1 つ付いてきます。OS が入っているディスクで、AMI から作られ、インスタンスを消すと一緒に消えます。ここにノートを置くと、[AMI を選ぶ](/ja/chapters/23-ec2/build.md)の節で見たとおり、1 回のデプロイで消えることがあります。

そこで、ボリュームをもう 1 つ作ります。

<<< @/examples/23-ec2/infra/lib/ec2-stack.ts{data-volume}

このボリュームは、インスタンスの設定の中に書かず、独立したリソースにしています。そのため、インスタンスが置き換えられても消えません。EC2 の既定でも、起動のあとに付けたボリュームは、インスタンスを消しても残ります。

このボリュームが消えるのは、スタックを消したときです。消し方を決めるのが `dataOnDestroy` で、既定は `delete` です。練習用なので、スタックと一緒に消えて何も残りません。本番では、消す前にスナップショットを取る `snapshot` か、ボリュームを残す `retain` にします。どちらの場合も、残ったものには料金がかかり続けます。

ボリュームは 1 つの AZ に属していて、同じ AZ のインスタンスにしか付けられません。コードでも、インスタンスと同じ AZ を渡しています。インスタンスを別の AZ に移す場合、ボリュームはそのままでは移せないので、スナップショットを取って、移った先の AZ にリストアします。

### 空のボリュームを一度だけフォーマットする

新しいボリュームには何も入っていないので、ファイルシステムを作ってマウントする必要があります。

<<< @/examples/23-ec2/deploy/notes-data-volume.sh

このスクリプトでいちばん重要なのは、`case` の部分です。`mkfs` はボリュームの中身を消すので、中身のあるボリュームに対して実行すると、ノートが全部なくなります。そして、このスクリプトは新しいインスタンスの最初の起動のときに実行されます。つまり、インスタンスを作り直して、古いボリュームを付け直したときにも実行されます。

そのため、フォーマットするのは、ファイルシステムが無いと確かめられたときだけです。ファイルシステムがあるとわかれば触りません。判断できないときも触らず、失敗して止まります。

テストは、このスクリプトを bash で実際に実行します。ディスクに触るコマンド（`blkid`、`mkfs.xfs`、`mount` など）だけを、呼ばれたことを記録する偽物に差し替えてあります。1 台目のインスタンスでフォーマットし、2 台目のインスタンス（fstab は新しく、ボリュームは同じ）でもう一度実行して、`mkfs` が 1 回しか呼ばれていないことを確かめます。

ほかにも、いくつか手当てをしています。ボリュームがインスタンスに付くのは起動の後なので、デバイスが現れるまで最大 5 分待ちます。`/etc/fstab` には、デバイス名ではなく UUID で書きます。いまのインスタンスでは EBS ボリュームが NVMe のデバイスとして見え、名前が起動のたびに入れ替わることがあるからです。`nofail` は、ボリュームが無くても OS を起動させる指定です。これが無いと、ボリュームを外したインスタンスが起動しなくなり、中に入って直すこともできなくなります。
