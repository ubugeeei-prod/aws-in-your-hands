# 66 Distributed SQL: 分散 DB を EC2 でセルフホストする

[13章](/ja/chapters/13-sql.md)では、分散したデータベースを Aurora DSQL として借りました。この章では同じ種類のデータベースを自分で 3 台の EC2 に載せて動かし、借りていたときの料金が何に支払われていたのかを確かめます。

載せるのは YugabyteDB です。PostgreSQL のクライアントがそのままつながるので、13章のマイグレーションと repository、コミットの競合を再試行するループを、1 行も変えずに使えます。変わるのは、データベースの面倒を見る人です。ノードが止まったら起こし、版を上げる順番を決め、証明書を配り、バックアップを取る仕事が、すべて自分に回ってきます。

この章も、**置いてあるだけで時間で課金されるもの**を作ります。3 台を動かすと、クエリを 1 つも送らなくても 1 日でおよそ USD 6.40、1 か月（730 時間）で USD 194.66 かかります。既定の構成はノードが 0 台で、台数は `-c nodes=3` を付けたときだけ増えます。試した日のうちに、[片付け](/ja/chapters/66-distributed-sql/wrap.md)まで進めてください。

この章の手順は、AWS では一度も動かしていません。その代わり、YugabyteDB のバイナリを手元の Mac に取得し、`127.0.0.1` の上で 3 ノードのクラスターを実際に動かしました。13章のコードをそのまま流し、ノードを 1 台、続けて 2 台止めて、何が起きたかを記録してあります。手元で見たことと、文書を読んだだけのことの内訳は、[章末の検証メモ](/ja/chapters/66-distributed-sql/wrap.md)にまとめました。

前提は [13章](/ja/chapters/13-sql.md)、[11章](/ja/chapters/11-network.md)の VPC、[23章](/ja/chapters/23-ec2.md)の EC2 とボリューム、[24章](/ja/chapters/24-celld.md)の fleet の運用、[22章](/ja/chapters/22-recovery.md)の復旧の考え方です。コードは `examples/66-distributed-sql/` にあります。

## どのデータベースを載せるか

<!-- section: 66.choice -->

候補は CockroachDB、TiDB、YugabyteDB の 3 つです。2026-10-13 に、それぞれのライセンスの本文と公式文書を読んで比べました。

YugabyteDB を選んだ理由は 2 つあります。1 つ目はライセンスです。リポジトリの `LICENSE.md` によれば、データベース本体は Apache License 2.0 で、本番で自分で動かすことに鍵の発行も申請も要りません。商用のライセンスが要るのは、管理ツールの YugabyteDB Anywhere のほうで、この章では使いません。2 つ目は PostgreSQL との互換です。YugabyteDB の SQL の層（YSQL）は PostgreSQL 15 のコードを使っていて、手元のクラスターは `PostgreSQL 15.12-YB-2025.2.7.0-b0` と名乗りました。13章の `pg` と SQL が、そのまま通ります。

CockroachDB も PostgreSQL のワイヤプロトコル（バージョン 3.0）に対応しています。ただし、いまのライセンス（CockroachDB Software License）は、ライセンスキーなしで動かせる範囲を、開発用の非本番環境と、1 ノードだけの構成に限っています。キーのないクラスターは 7 日を過ぎると、同時に開けるトランザクションが 5 つに絞られます。年間の売上が 1,000 万ドル未満の事業者には無料のキー（Enterprise Free）がありますが、テレメトリーの送信が条件です。売上の条件を満たしていて、キーの申請とテレメトリーを受け入れられるなら、CockroachDB も同じ土俵に乗ります。その場合は、公式が 1 ノードに 4 vCPU 以上を強く勧めていることも、見積もりに入れてください。

TiDB は Apache License 2.0 ですが、話すのは MySQL のプロトコルです。13章のコードは使えません。本番の最小構成も、TiDB が 2 つ、PD が 3 つ、TiKV が 3 つと、部品が多くなります。もとのアプリケーションが MySQL で書かれているなら、TiDB が第一の候補になります。

動かす版は、長期サポートの系列（v2025.2）の、読んだ時点での最新（2025.2.7.0、2026-10-05 公開）に固定します。

## 全体像

<!-- section: 66.picture -->

```figure
caption: 3 つのゾーンに 1 台ずつ置く。どのノードも SQL を受け、tablet ごとのリーダーが残りの 2 台へ書き込みを写す
node app: Application | client security group
node a: Node a | zone 1
node b: Node b | zone 2
node c: Node c | zone 3
node s3: S3 bucket | artifacts/, backups/
node ssm: Session Manager
edge app -> a: SQL over TLS, 5433
edge a -> b: Raft, 7100 and 9100
edge a -> c: Raft, 7100 and 9100
edge a --> s3: backups
edge ssm -> a: no inbound port
group vpc: VPC, private subnets = a, b, c
mark a
```

図ではノード a だけに矢印を引いていますが、3 台は対等です。どのノードも SQL の接続を受け、S3 に届き、Session Manager から入れます。リーダーも固定ではありません。テーブルは tablet と呼ぶかけらに分かれていて、tablet ごとに 3 つの写しがあり、そのうちの 1 つがリーダーです。ある tablet のリーダーがノード a にいて、別の tablet のリーダーがノード b にいる、という状態がふつうです。

ノードは 11章のプライベートサブネットに置き、public IP も、外から届くポートも持たせません。アプリケーションは、クライアント用のセキュリティグループに入ったものだけが、SQL のポート（5433）に届きます。ノードどうしの通信（7100 と 9100）は、ノードのセキュリティグループのメンバーからだけ受け付けます。通信はどちらも TLS で、証明書はこのクラスター専用の認証局が署名します。

ロードバランサーは置きません。どのノードも同じ SQL を受けられるので、接続先を 3 つ持って、つながらなければ次へ進む処理を、クライアントの側に短く書きます。Network Load Balancer を前に置く構成もありますが、時間で課金される部品が 1 つ増えます。

## 守りたい不変条件

<!-- section: 66.overview -->

この章で確かめる不変条件（invariant）は 2 つです。

- 確認の応答を返した書き込みは、ノードを 1 台失っても残り、一度見えたあとで消えることがない
- トランザクションの競合は、再試行できるエラー（SQLSTATE `40001`）としてクライアントに届き、13章の再試行ループがそれを処理する

1 つ目を守っているのは YugabyteDB で、この章のコードではありません。この章の CDK とスクリプトが受け持つのは、その前提を壊さないことです。3 つの写しを 3 つのゾーンに分け、2 台を同時に止めず、3 つのディスクを同時に捨てず、時計を合わせておきます。

手元のクラスターでは、どちらも実際に確かめました。ノード b を SIGKILL で落としても、残る 2 台は確認済みの 40 件をすべて返し、続く書き込みも受け付けました。2 台を落とすと、残った 1 台は 20 秒待っても書き込みを確認せず、2 台を戻すと、確認済みの 40 件はすべて残っていました。上限 3 件のところへ 12 件の作成を 3 つのノードから同時に送ると、作成は 3 件で止まり、その間に `40001` による再試行が、実行のたびに 4 回から 29 回起きました。詳しい記録は[手元で動かす](/ja/chapters/66-distributed-sql/local.md)のページにあります。

## 自分で動かさないほうがよい場合

<!-- section: 66.when-not -->

ほとんどの場合、自分では動かさないほうがよいです。

料金から見ても、小さな負荷では割に合いません。毎秒 10 件の書き込みと 90 件の読み取りが 1 か月続くとして計算すると、Aurora DSQL は USD 68.65、この章の 3 台は USD 196.77 です（どちらも仮定つきの計算で、内訳は[費用のページ](/ja/chapters/66-distributed-sql/wrap.md)にあります）。しかもこの金額には、夜中にノードが止まったときに起きる人の時間が入っていません。Aurora DSQL では、版の更新も、ノードの置き換えも、バックアップも、時計合わせも、料金の中に入っていました。

Cloudflare や Vercel を使っているなら、なおさらです。Cloudflare の D1 は、Cloudflare が運用するサーバーレスのデータベースで、料金はクエリと保存量で決まります。Vercel は、データベースを Marketplace 経由で Neon や Supabase などの事業者から用意する形です（どちらも 2026-10-13 に公式文書で確認しました）。借りていて困っていないなら、そのまま借りておくのが正解です。

自分で動かす理由になるのは、次のような事情です。

- 版と更新の時期を自分で決めたい。特定の版に固定したい、あるいは特定の拡張を使いたい
- データを置く場所を、ゾーンやマシンの単位で決める必要がある（規制、契約）
- すでにこのデータベースを運用しているチームがいる
- 負荷が大きく、一定している。マシンを使い切れるなら、従量課金より安くなる点がどこかにあります。ただし、その点がどこにあるかは、実際の負荷で測らないとわかりません

どれにも当てはまらないなら、この章は「借りていたものの中身を見る」ために読んでください。次のページでは、YugabyteDB のしくみを、13章で使ったことばに置き換えながら見ていきます。
