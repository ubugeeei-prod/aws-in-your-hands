[最初のページ](/ja/chapters/17-ai.md)では、モデルを 1 回呼び、使うモデルの ID を選びました。このページでは、ノートを要約して少しずつ返す API を実装します。

## 入力の上限と、返すイベントの形

04章と同じく、API の契約から決めます。最初はリクエストです。

本文は 10,000 文字までで、04章のノートと同じ上限です。この上限は入力の検証であり、費用の上限でもあります。入力のトークンは課金されるので、どんな長さでも受け付ける API は、いくらでも払う API になります。

ただし、文字数とトークン数は同じではありません。トークンはモデルが文章を読み書きする単位で、数え方はモデルごとに違います。10,000 文字が何トークンになるかは、呼んでみるまで正確にはわかりません。文字数の上限で抑えられるのは、入力の費用のおおよその大きさまでです。

出力は、入力より正確に抑えられます。

<<< @/examples/17-ai/src/prompt.ts{request}

`maxTokens` は、1 回の呼び出しで生成されるトークン数の上限です。要約なら 400 あれば足りますし、この値を決めておけば、1 回の出力はここまでだと言い切れます。

system prompt の 3 行目は、ノートの本文に書かれた指示への備えです。ノートの本文はユーザーが書くので、「これまでの指示を忘れて…」と書かれたノートが届くかもしれません。そこで、指示は `system` に、ノートは `messages` に分けて渡し、ノートはデータだとモデルに伝えています。ただ、この 1 行で防ぎ切れるわけではありません。本当の歯止めは、この API の出力がただの文字列で、何かを実行する権限を持たないことです。

次は、この API が返すイベントです。

<<< @/examples/17-ai/src/contract.ts{events}

レスポンスは server-sent events（SSE）にします。SSE は、1 つの HTTP レスポンスの中で、サーバーがイベントを順に送り続ける形式です。`delta` が何回か届き、最後に `done` か `error` のどちらかが 1 回だけ届きます。最後に必ずどちらかが 1 回届くという決まりは、[ストリームが途中で切れたとき](/ja/chapters/17-ai/local.md)の扱いで使います。

## ストリームを読む

<!-- section: 17.stream -->

`ConverseStream` は `Converse` のストリーミング版で、次のイベントを順に返します。

```text
order  event              carries
1      messageStart       role
2      contentBlockDelta  a piece of text (repeats)
3      contentBlockStop
4      messageStop        stopReason: end_turn, max_tokens, ...
5      metadata           usage: inputTokens, outputTokens
```

このイベントの列は SSE ではありません。AWS 独自の形式で届き、SDK が async iterable にして渡します。

大事なのは最後の数行です。`messageStop` を受け取らないままストリームが終わったら、`done` ではなく `error` を返します。届いた文章がどれほどもっともらしくても、モデルが終わりを告げていない以上、完成したとは言えないからです。

## 止める、待つ、やり直す

<!-- section: 17.failures -->

モデルの呼び出しには、混んでいる、上限を超えた、権限がない、途中で切れた、といった何種類もの失敗があります。すべてを同じエラーとして扱うと、やり直す価値のある失敗と、やり直しても結果が変わらない失敗を区別できません。

<<< @/examples/17-ai/src/failure.ts{classify}

分ける基準は、同じリクエストをもう一度送ったら通る可能性があるかどうかの 1 つだけです。

`ThrottlingException` は、アカウントのクォータ（quota）を超えたときに返ります。クォータはモデルごとに決まっているトークン使用量の上限で、少し待てば通るかもしれません。`ServiceUnavailableException` は Bedrock 側の容量の問題なので、これも待つ価値があります。一方、`AccessDeniedException` や `ValidationException` は、ロールかモデル ID かリクエストが間違っているので、何度送っても結果は同じです。

名前を知らないエラーには、分類を返しません（`undefined`）。知らないエラーを、やり直せるものと勝手に決めないためです。

待ち時間は次のように決めます。

<<< @/examples/17-ai/src/failure.ts{backoff}

待ち時間の上限を試行のたびに 2 倍に伸ばし、その上限までの範囲からランダムに選びます。ランダムにするのは、同時に失敗した呼び出し元が同時にやり直して、また同時に失敗するのを避けるためです。乱数は引数で受け取るので、テストでは待ち時間が決まった値になります。

<<< @/examples/17-ai/src/summarize.ts{start}

このコードで決めていることが 3 つあります。

1 つ目は、やり直す範囲です。やり直すのは、呼び出し元にまだ何も送っていない間に限ります。ストリームが開く前の失敗は呼び出し元から見えないので、黙ってやり直せます。しかし、`delta` を 1 つでも送ったあとにやり直すと、同じ文章の先頭がもう一度流れます。送ったものは取り消せないので、そこから先は `error` を返し、やり直すかどうかは呼び出し元に任せます。

2 つ目は締め切りです。締め切りは、全部の試行をまとめて 1 つにします。30 秒の締め切りを試行ごとに持つと、3 回の試行で 90 秒待たせることになるからです。`AbortSignal.timeout` を最初に 1 つ作り、全部の試行で共有します。

3 つ目は中止です。止める理由が何であっても、モデルへのリクエストを中止します。呼び出し元がいなくなった、締め切りが来た、中継が終わった、の 3 つのシグナルを `AbortSignal.any` でまとめて SDK に渡しています。誰も読まない文章でも、モデルが書き続ければ課金されるからです。

SDK 自身も、何も設定しなければ最大 3 回まで再試行します。この章では SDK の再試行を切り（`maxAttempts: 1`）、再試行を自分のコードに置きました。締め切りと一緒に管理でき、テストもできるからです。

ストリームを始める前に失敗した場合は、ふつうの HTTP のエラーを返します。スロットリングなら 429、締め切りなら 504 です。まだ何も送っていないので、ステータスコードで失敗を伝えられます。

ストリームが始まったあとは、ステータスコードを 200 で送り終えているので、失敗はストリームの中の `error` イベントで伝えます。つまり、この API では 200 が返っても成功とは限らず、呼び出し元は、最後のイベントを見るまで結果を判断できません。

ハンドラーは最後に `summary` というログを 1 行書きます。結果、試行回数、モデルが報告したトークン数が入っていて、1 回の要約にいくらかかったかの記録になります。
