# 62 CI Runner: 実装のつづき

[前のページ](/ja/chapters/62-ci-runners/build.md)は、webhook を受けて Fargate のタスクを起動する構成を、自分で組み立てました。このページでは、同じことをする出来合いの方法と、GitLab の場合、そして Fargate の上ではできない Docker のビルドを扱います。このページに書くことは、どれも 2026-10-13 にドキュメントを読んだ内容で、動かして確かめてはいません。

## GitHub が挙げる方法と、CodeBuild

<!-- section: 62.options -->

GitHub のドキュメントは、自動でスケールさせるならエフェメラルなランナーを使うよう勧め、常駐のランナーでの自動スケールは勧めないと書いています。そのうえで挙げている方法は、3 つあります。

**Actions Runner Controller（ARC）。** Kubernetes のオペレーターです。listener と呼ばれる Pod が GitHub に HTTPS の long poll を張り、ジョブが来ると、コントローラーが JIT の設定を作って、ランナーの Pod を 1 つ起動します。GitHub は、Kubernetes の基盤と経験のあるチームに ARC を勧めています。[34章](/ja/chapters/34-eks.md)のクラスターがすでにあるなら、有力な選択肢です。ランナーのためだけにクラスターを持つのは、割に合いません。listener が常に動いているので、ジョブが無いあいだもクラスターと Pod の料金がかかります。

**runner scale set のクライアント。** ARC が使っている API（runner scale set）を、Kubernetes なしで使うための Go のクライアントで、`actions/scaleset` として公開されています。README によれば public preview で、スケールセットの作成、JIT の設定の生成、メッセージの受信を受け持ち、ランナーの起動は利用者に任せています。webhook を受ける口を外に開けずに済むのが利点です。そのかわり、GitHub に long poll を張り続けるプロセスを、どこかで動かしておく必要があります。

**`workflow_job` の webhook。** この章の方法です。ドキュメントは、この webhook のペイロードを使って自前の自動スケールを組めると書いています。常駐するものが無いかわりに、公開の URL を 1 つ持ち、配送の重複や取りこぼしを自分で扱います。

AWS の側にも、出来合いの方法があります。

**CodeBuild のランナー。** CodeBuild のプロジェクトに、`WORKFLOW_JOB_QUEUED` のイベントを受ける webhook を設定します。ワークフローの側は、`runs-on` に `codebuild-<プロジェクト名>-${{ github.run_id }}-${{ github.run_attempt }}` と書きます。CodeBuild は、ジョブごとにビルドを 1 つ始め、その中でエフェメラルなランナーを動かし、ジョブが終わるとビルドも終わらせます。buildspec のコマンドは、既定では無視されます。GitHub との接続には、GitHub App、OAuth アプリ、個人のアクセストークンのどれかを使います。

この章で書いたもののうち、受信、判定、登録、起動、片付けは、CodeBuild が受け持ちます。前のページのコードは 1 行も要りません。違いは次のとおりです。

| | この章の構成 | CodeBuild のランナー |
| --- | --- | --- |
| 自分で書くもの | 受信の Lambda、スタック | プロジェクトの設定 |
| ジョブの環境 | Fargate のタスク | CodeBuild のビルド環境（EC2 か Lambda） |
| Docker のデーモン | 使えない | プロジェクトの `privilegedMode` で使える（EC2 のとき） |
| フォークのジョブを断る判定 | 自分のコードで行う | ドキュメントに見つからなかった。GitHub の設定に頼る |
| ジョブが届く権限 | 空のタスクロール | プロジェクトのサービスロール |
| 1 分の単価（東京、arm64） | およそ USD 0.0020（2 vCPU、8 GB） | USD 0.00425（arm1.small） |

最後の 2 行が、選ぶときの要点です。CodeBuild のビルドは、プロジェクトのサービスロールで動きます。このロールに付けた権限は、ジョブから使えると考えてください。CodeBuild でも、ロールにはログの書き込みなど最低限だけを付け、AWS へは OIDC で入るのがよいはずです。ただし、サービスロールの認証情報がランナーのジョブからどう見えるかは、ドキュメントでは確かめられませんでした。

それでも、多くのチームにとっては CodeBuild のほうが適しています。保守するコードが無く、Docker のビルドができ、単価の差が効くほどの量が無いからです。この章の構成が合うのは、起動の条件を自分のコードで決めたいとき、ジョブの環境を自分のタスク定義とネットワークに置きたいとき、量が多いときです。

なお、CodeBuild の Lambda のコンピュートは、起動が速いかわりに、Docker のビルドと、15 分を超える実行ができません。

## GitLab で同じことをする

<!-- section: 62.gitlab -->

GitLab Runner は、作りが違います。runner manager と呼ばれる常駐のプロセスが、GitLab にジョブが無いかを問い合わせ続け（`POST /api/v4/jobs/request`）、受け取ったジョブを executor に実行させます。GitHub の `workflow_job` に当たる、ジョブごとにランナーを起動するための webhook の使い方は、GitLab のドキュメントには見つかりませんでした。ジョブの状態が変わったことを知らせる webhook はありますが、ランナーの自動スケールと結び付けた説明はありません。したがって、GitLab では、何かが常に動いていることになります。

**登録。** runner manager は、runner authentication token（`glrt-` で始まります）で GitLab に登録します。トークンは、画面か `POST /user/runners` で作り、runner manager の `config.toml` に保存されます。以前の registration token は廃止予定で、GitLab 20.0 で削除されると書かれています。GitHub の JIT と違い、このトークンは 1 回きりではなく、runner manager が動いているあいだ使い続けるものです。期限と自動の更新を設定できます。常駐するホストにこのトークンが置かれるので、守るべき場所は runner manager のホストです。

**1 件のジョブに 1 つの環境。** ジョブを実行するのは executor です。おもな executor は Kubernetes、Docker、Docker Autoscaler、Instance の 4 つで、Shell や Docker Machine は保守だけの扱いか廃止予定です。AWS でジョブごとに新しい環境を作るには、Instance か Docker Autoscaler を、fleeting plugin と組み合わせます。AWS 用の plugin（`fleeting-plugin-aws`）は、EC2 の Auto Scaling グループの台数を、runner manager から直接増減させます。

Instance executor のドキュメントは、`capacity_per_instance` と `max_use_count` をどちらも 1 にすると、ジョブごとに、ほかのジョブの影響を受けない使い捨てのインスタンスが与えられ、ジョブが終わるとすぐ削除されると書いています。これが、この章の不変条件に当たる設定です。`max_use_count` を 1 より大きくすると、インスタンスが複数のジョブに使い回されます。

Auto Scaling グループの側には、plugin の README が条件を挙げています。希望する台数と最小の台数を 0 にし、スケーリングポリシーは付けず、`AZRebalance` のプロセスを止め、スケールインからの保護を有効にします。台数を決めるのは runner manager だけ、という形にするためです。README には、runner manager に必要な IAM のアクションの一覧もあります。

ドキュメントの例は、`idle_count = 5` として、待機のインスタンスを 5 台保っています。ジョブの待ち時間は短くなりますが、何も流れていない時間にも 5 台ぶんの料金がかかります。0 にすれば、ジョブが来てからインスタンスを起動するので、待ち時間が延びます。

**この章の構成に置き換えると。** runner manager を小さな Fargate のサービスか EC2 インスタンスで 1 つ動かし、ジョブは Auto Scaling グループのインスタンスで実行する形になります。ジョブが無い月にも、runner manager のぶんの料金がかかります。[23章](/ja/chapters/23-ec2.md)の t4g.small なら、8 GB のボリュームを含めて月 USD 16.54 です（41章の計算）。ジョブを Fargate で実行する方法として、GitLab は Fargate 用のドライバーの手順を載せていますが、コミュニティによるサポートで、本番向けではないと明記されています。runner manager 用の EC2 インスタンスも、別に要ります。

EC2 インスタンスでジョブを実行する場合、ジョブはインスタンスメタデータから、インスタンスプロファイルの認証情報を取得できます。ジョブ用のインスタンスには、プロファイルを付けないか、何も許さないロールを付けます。

**CodeBuild。** CodeBuild は、GitLab のランナーにも同じ形で対応しています。`.gitlab-ci.yml` のジョブに `tags: codebuild-<プロジェクト名>-$CI_PROJECT_ID-$CI_PIPELINE_IID-$CI_JOB_NAME` と書くと、ジョブごとにビルドが 1 つ始まり、その中でランナーが 1 件のジョブを実行します。この方法では、常駐の runner manager は要りません。ランナーは、ビルドのコンテナの中で、shell executor として動きます。

**フォークと保護。** GitLab では、フォークからのマージリクエストのパイプラインは、既定ではフォークの側のプロジェクトで作られて動きます。親のプロジェクトで動かすと親のランナーが使われ、フォークのコードが親のシークレットを盗もうとしうると、ドキュメントは注意しています。ランナーを保護されたブランチのジョブだけに限る設定（protected runner）もあります。

**AWS への入り方。** GitLab のジョブも、OIDC で AWS のロールを引き受けられます。ジョブに `id_tokens` を書いてトークンを受け取り、`sts assume-role-with-web-identity` に渡します。信頼ポリシーは、`gitlab.com:sub` の値（`project_path:<グループ>/<プロジェクト>:ref_type:branch:ref:main` の形）で絞ります。考え方は 20章と同じで、ランナーのロールではなく、ジョブが引き受けるロールに権限を持たせます。

## 特権なしでイメージをビルドする、キャッシュを置く

<!-- section: 62.docker-builds -->

Fargate のタスクでは、特権つきのコンテナを動かせません。ECS のドキュメントは、その影響として Docker in Docker を挙げています。この章のランナーのイメージには Docker の CLI と buildx が入っていますが、デーモンは動いていません。したがって、ジョブの中の `docker build` は失敗します。GitHub Actions では、`container:` を指定したジョブ、サービスコンテナ、Docker コンテナのアクションも、Linux のランナーに Docker が入っていることを前提にしているので、この章のランナーでは動きません。

イメージのビルドが必要なときの選択肢を、ドキュメントに書かれている範囲で挙げます。

- **ビルドだけを、デーモンのある場所に出す。** いちばん単純です。イメージをビルドするジョブだけ `runs-on` を GitHub のランナーか CodeBuild のランナーにし、残りのジョブを自分のランナーで動かします。CodeBuild は、プロジェクトの `privilegedMode` を有効にすると、ビルドの中で Docker のデーモンを動かせます
- **rootless の BuildKit。** GitLab のドキュメントは、特権モードを使えないときの方法として、`moby/buildkit:rootless` のイメージと `--oci-worker-no-process-sandbox` を使う手順を載せています。BuildKit 自身のドキュメントは、コンテナの中で rootless で動かすには seccomp と AppArmor の制限を外すか、このフラグを使うと書き、このフラグは勧めないとも書いています。Fargate のタスクで動くかどうかは、どちらのドキュメントにも記述がなく、確かめていません
- **Buildah。** GitLab のドキュメントは、デーモンなしで OCI のイメージを作る方法として挙げています。Fargate で動くかどうかは、確かめていません
- **kaniko は使わない。** かつては、この用途の定番でした。Google のリポジトリは 2025-06-03 にアーカイブされ、README に、もう開発も保守もされないと書かれています。GitLab のドキュメントも、kaniko のページを「removed」としています

結局、Fargate の上で確実にできることは、ドキュメントからは言えません。ビルドのジョブを外に出す最初の方法を勧めます。

特権つきのコンテナや Docker のソケットをジョブに渡して解決するのは、避けてください。GitLab のセキュリティのページは、特権モードはコンテナのセキュリティの仕組みをすべて無効にするのと同じだと書いています。使い捨ての仮想マシンの中でなら、その影響はその 1 台に留まります。EC2 のインスタンスを 1 件のジョブで使い捨てる構成が、Docker のビルドに向いているのは、そのためです。

### キャッシュ

使い捨ての環境には、前のジョブが取得した依存パッケージが残っていません。ジョブのたびに取得し直すぶん、時間がかかります。これは不変条件の裏返しで、ローカルのキャッシュを残す設計は、前のジョブが書いたものを次のジョブに見せる設計です。キャッシュは、環境の外に、信頼の範囲を決めて置きます。

GitHub Actions のキャッシュ（`actions/cache`）は、リポジトリごとに既定で 10 GB まで使え、7 日間使われなかったものは消されます。セルフホストランナーから使ったときの保存先や料金については、読んだページに記述がありませんでした。

GitLab Runner は、キャッシュを S3 に置く設定を持っています。`config.toml` の `[runners.cache]` で `Type = "s3"` を選び、`[runners.cache.s3]` にバケットとリージョン、認証の方法（`iam` か `access-key`）を書きます。ドキュメントは、自動スケールではほとんどのジョブが新しいホストで動くのでローカルのキャッシュが効かず、そのために分散キャッシュがあると説明しています。

どちらの場合も、キャッシュは、ジョブが書き、あとのジョブが読むものです。信頼できないブランチのジョブが書いたキャッシュを、本番向けのジョブが読まないようにしてください。GitHub のドキュメントは、`pull_request_target` などの特権のあるワークフローが main ブランチとキャッシュを共有することを、危険の 1 つに挙げています。

コンテナイメージのレイヤーは、[52章](/ja/chapters/52-ecr.md)の ECR に置けます。ランナーのイメージを自分で作って道具を入れておくのも、取得し直す量を減らす方法です。ただし、Fargate はイメージをタスクごとに取得し直すので、イメージを大きくすると、起動がそのぶん遅くなります（41章）。
