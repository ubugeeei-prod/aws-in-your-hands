# 62 CI Runner: しくみと実装

[概要](/ja/chapters/62-ci-runners.md)で決めた構成を、配送が届いてからタスクが起動するまでの順に読みます。最初に、ランナーが GitHub にどう登録されるかを確かめます。受信の側が何を持ち、タスクに何を渡すかは、そこから決まるからです。

## ランナーの登録

<!-- section: 62.registration -->

ランナーは、GitHub から呼ばれるのを待つサーバーではありません。ランナーの側から GitHub へ HTTPS でつなぎ、ジョブを受け取ります。GitHub のドキュメントがランナーのホストに求めているのは、443 番ポートで外へ HTTPS の接続を張れることです。外から入ってくる通信を求める記述はありません。セキュリティグループで入る通信を 1 つも許さずに済むのは、このためです。

つなぐ前に、ランナーを登録します。GitHub のドキュメントにある登録の方法は 2 つです。

1 つは登録トークン（registration token）です。API かリポジトリの設定画面で発行し、ランナーの `config.sh` に渡します。有効期間は 1 時間です。`--ephemeral` を付けて設定したランナーは、ジョブを 1 件実行すると登録が外れます。この方法では、登録トークンをランナーの環境に持ち込み、その中で設定の手順を実行することになります。

もう 1 つが just-in-time の設定です。`POST /repos/{owner}/{repo}/actions/runners/generate-jitconfig` にランナーの名前、ランナーグループの ID、ラベルを渡すと、登録が作られ、`encoded_jit_config` が返ります。ランナーは `./run.sh --jitconfig <値>` で起動するだけで、設定の手順はありません。ジョブを多くても 1 件実行したところで、GitHub が登録を消します。一度も接続しなかった場合も、エフェメラルなランナーの登録は 1 日で自動的に消えます（通常のランナーは 14 日です）。

この章は just-in-time の設定を使います。ランナーの環境に入るのは、そのランナー 1 つぶんの、1 回きりの設定だけになるからです。

### GitHub App として API を呼ぶ

`generate-jitconfig` を呼ぶには、リポジトリの管理者に相当する権限が要ります。個人のアクセストークンを Lambda に持たせるのは避け、GitHub App を作ります。GitHub App には、この章にとって都合のよい点が 3 つあります。webhook を App 自身が持てること、App が使うトークンが 1 時間で切れること、トークンを発行するたびに対象のリポジトリと権限を絞れることです。

認証は 2 段階です。まず App の秘密鍵で JWT に署名します。GitHub は、アルゴリズムを RS256、有効期限を 10 分以内とし、発行時刻は時計のずれを見込んで 60 秒前にすることを勧めています。

<<< @/examples/62-ci-runners/src/github.ts{jwt}

次に、その JWT で installation access token を発行します。配送のペイロードには、App がインストールされた先を表す `installation.id` が入っているので、それを使います。

<<< @/examples/62-ci-runners/src/github.ts{app}

トークンは、配送に書かれたリポジトリ 1 つに対して、`administration: write` と `actions: read` だけを求めます。前者は `generate-jitconfig` とランナーの削除に、後者は workflow run の読み取りに必要な権限です（GitHub App に必要な権限の一覧で確認）。

ここで注意が要ります。`administration: write` は、ランナーの登録だけの権限ではありません。リポジトリの設定を変える権限で、API の説明は、リポジトリの作成、削除、設定、チーム、コラボレーターの管理を対象に挙げています。リポジトリ単位でランナーを登録するかぎり、これより狭い権限はありません。つまり、この App の秘密鍵は、リポジトリの管理者の鍵と同じ重さで扱う必要があります。この章では、秘密鍵を Secrets Manager に置き、読めるのを受信の Lambda のロールだけにしています。組織単位でランナーを登録する API もありますが、この章では扱っておらず、そちらに必要な権限も確かめていません。

## 配送を受け取る

<!-- section: 62.receiver -->

GitHub App の設定で `workflow_job` のイベントを購読すると、ジョブの状態が変わるたびに、webhook の URL へ POST が届きます。状態は `queued`、`in_progress`、`completed`、`waiting` の 4 つで、ランナーを起動するのは `queued` のときだけです。

この URL は、誰でも呼べます。function URL の認証を `NONE` にしているからで、GitHub は IAM の署名を付けられないので、そうするほかありません。本物の配送かどうかは、署名で確かめます。GitHub は、webhook に設定したシークレットを鍵にして、リクエストのボディの HMAC-SHA256 を計算し、`X-Hub-Signature-256` ヘッダーに `sha256=` を付けた 16 進で入れてきます。

<<< @/examples/62-ci-runners/src/signature.ts{verify}

比較に `===` を使っていないのは、GitHub のドキュメントが、一定時間で終わる比較を使うよう求めているからです。先頭から何文字合っていたかが応答の時間に表れると、署名を 1 文字ずつ当てられます。この関数は、GitHub のドキュメントに載っている検算用の値（シークレット、ペイロード、署名の 3 つ組）で、テストしてあります。

署名は、ボディのバイト列そのものに対して計算されています。JSON として読んでから文字列に戻したものでは一致しません。そのため、04章の `readJson` は使わず、上限つきでバイト列を読む関数をこの章に書きました。

<<< @/examples/62-ci-runners/src/receive.ts{body}

読んだバイト列は、署名が合うまで、JSON としても解釈しません。署名が合ってから、Valibot のスキーマに通します。

<<< @/examples/62-ci-runners/src/events.ts{delivery}

スキーマは、GitHub が公開している OpenAPI の定義（`webhook-workflow-job-queued`）のうち、受信の処理が読む項目だけを写したものです。ペイロードにはほかに 100 以上の項目がありますが、読まないものは検証もしません。

受信の処理の全体は、次のとおりです。

<<< @/examples/62-ci-runners/src/receive.ts{receive}

順序に意味があります。大きさの上限、署名、イベントの種類、JSON、スキーマ、判定の順に進み、どこかで外れたら、そこで応答を返します。署名が合わないリクエストには、ボディが JSON かどうかにかかわらず 401 を返します。署名を持たない相手に、ボディのどこが悪いかを教えないためです。

応答の状態コードは、GitHub の側での見え方で決めています。GitHub は、10 秒以内に 2XX が返らなかった配送を失敗として記録します。失敗した配送は自動では再送されず、画面か API から手で再送します。そこで、起動しないと判断した配送には、理由を付けて 200 を返します。受信の側の判断であって、失敗ではないからです。500 を返すのは、起動しようとして失敗したときだけです。失敗の一覧に残るので、再送すればやり直せます。

受信の Lambda のタイムアウトは 9 秒にしてあります。10 秒の手前で打ち切ることで、Lambda がまだ動いているのに GitHub が失敗と記録する、という食い違いを避けています。GitHub の API を 3 回と RunTask を 1 回呼ぶ処理が 9 秒に収まるかどうかは、計っていません。収まらないことが多いようなら、受信は配送をキューに入れるだけにして、起動を [08章](/ja/chapters/08-async.md)のワーカーに回します。

## 起動するかどうかを決める

<!-- section: 62.decision -->

判定は 2 段階です。1 段階目は、配送のペイロードだけで決まります。

<<< @/examples/62-ci-runners/src/decide.ts{screen}

ラベルの検査を最初に置いているのは、ここで外れる配送がいちばん多いからです。App をインストールしたリポジトリでは、GitHub のランナーで動くジョブ（`ubuntu-latest` など）の配送も、同じ URL に届きます。

ラベルの条件は、ジョブが求めるラベルのすべてが、この章のランナーの持つ 1 つのラベルと一致することです。ジョブが `[self-hosted, aih-fargate]` を求めていたら、起動しません。GitHub は、ジョブが求めるラベルをすべて持つランナーにジョブを渡します。JIT で登録したランナーに `self-hosted` などの既定のラベルが付くのかどうかを確かめられなかったので、確実に受け取れるジョブにだけランナーを起動します。受け取れないジョブのために起動したランナーは、来ないジョブを待ち続けます。

リポジトリは、完全一致の一覧と照らします。非公開であることも確かめます。どちらも、ペイロードの `repository` から読める値です。

2 段階目は、フォークからのジョブを見分けます。`workflow_job` のペイロードには、コードがどのリポジトリから来たかを示す項目がありません（OpenAPI の定義で確認）。そこで、ジョブが属する workflow run を API で読みます。

<<< @/examples/62-ci-runners/src/events.ts{run}

<<< @/examples/62-ci-runners/src/decide.ts{admit}

workflow run には、ワークフローが動くリポジトリ（`repository`）と、コードの元のリポジトリ（`head_repository`）の両方が入っています。フォークからのプルリクエストでは、この 2 つが違います。同じでなければ起動しません。フォークのプルリクエストで `head_repository` が実際にフォークを指すことは、ドキュメントの定義から読んだだけで、実物では確かめていません。

断られたジョブは、GitHub の側ではキューに入ったままになります。セルフホストランナーを待つジョブは、24 時間たつと自動でキャンセルされます。フォークからのプルリクエストに CI が必要なら、そのジョブは GitHub のランナーで動かす（`runs-on` を分ける）のが筋です。

この判定は、GitHub の設定の代わりにはなりません。フォークからのプルリクエストでワークフローを動かすかどうか、承認を必要とするかどうかは、リポジトリの設定で決まります。非公開リポジトリでは「Run workflows from fork pull requests」が、公開リポジトリでは外部のコントリビューターに承認を求める設定があります。受信の側の判定は、その設定が緩んだときにも、ランナーが起動しないようにするための 2 枚目の歯止めです。

## 1 件のジョブに 1 つのタスク

<!-- section: 62.launch -->

同じ配送は、2 回届くことがあります。手で再送したときは、同じ `X-GitHub-Delivery` の値でもう一度届きます。2 回届いてタスクが 2 つ起動すると、2 つ目のランナーは、受け取るジョブが無いまま動き続けるか、あとから来た別のジョブを受け取ります。どちらも料金がかかります。

そこで、起動の前に、ジョブの持ち主になる手順を入れます。

<<< @/examples/62-ci-runners/src/claims.ts{interface}

実装は、[05章](/ja/chapters/05-dynamodb.md)の条件つきの書き込みです。

<<< @/examples/62-ci-runners/src/dynamodb-claims.ts{claims}

キーは配送の ID ではなく、リポジトリとジョブの ID です。守りたいのは「1 件のジョブに 1 つのタスク」であって、「1 回の配送に 1 つのタスク」ではないからです。

条件式の後半は、持ち主になったあとで受信の Lambda が止まった場合のためのものです。持ち主の記録だけが残り、タスクは起動していない状態になると、再送しても重複として断られ、ジョブは永久にランナーを得られません。そこで、起動中の記録には期限を付け、期限を過ぎた記録は取り直せるようにしています。[08章](/ja/chapters/08-async.md)の可視性タイムアウトと同じ考え方です。期限の長さは、受信の Lambda が動ける時間より長くなければなりません。短いと、まだ動いている Lambda から持ち主を奪い、2 つ起動してしまいます。この関係は、テストで固定しています。

<<< @/examples/62-ci-runners/src/config.ts{timing}

持ち主になったら、登録を作り、タスクを起動します。

<<< @/examples/62-ci-runners/src/launcher.ts{input}

JIT の設定は、コンテナの引数として渡します。タスク定義の `entryPoint` が `/home/runner/run.sh` なので、`command` に `--jitconfig` と値を渡せば、GitHub のドキュメントにある起動のしかたと同じになります。タスク定義の `secrets` は、RunTask の上書きでは変えられません（`ContainerOverride` に `secrets` はありません）。タスクごとに違う値を渡せるのは、`command`、`environment`、`environmentFiles` です。

この渡し方には、確かめられていない前提が 1 つあります。RunTask の `overrides` は、全体で 8,192 文字までです。`encoded_jit_config` の長さは、ドキュメントに書かれておらず、API を呼んでいないので、わかりません。超えた場合は、ECS に送る前に、理由を付けて失敗するようにしてあります。その場合の代わりの渡し方は、検証メモに書きました。

渡した値は、`ecs:DescribeTasks` を呼べる人には見えます。タスクの上書きとして記録されるからです。この値で登録できるのはランナー 1 つで、そのランナーが接続したあとは、同じ値でもう一度登録できるのかどうかを確かめていません。アカウントの中で `DescribeTasks` を呼べる範囲は、狭くしておいてください。

RunTask は、成功の応答の中に失敗を入れて返すことがあります。

<<< @/examples/62-ci-runners/src/launcher.ts{ecs}

サブネットに空きのアドレスが無いときなどは、HTTP の応答は 200 で、`tasks` が空で、`failures` に理由が入ります。例外を待っているだけでは、起動できなかったことに気づけません。

### 起動に失敗したとき

受信の処理は、失敗した場所によって、後始末が違います。

| 失敗した場所 | そのとき残っているもの | 後始末 |
| --- | --- | --- |
| workflow run の読み取り、登録の作成 | 持ち主の記録 | 記録を消して 500 |
| RunTask | 持ち主の記録と、接続先の無いランナーの登録 | 登録を消し、記録を消して 500 |
| 登録の削除 | 同じ | 記録だけ消して 500。登録は 1 日で GitHub が消す |
| 起動後の記録の更新 | 動いているタスク | 何も戻さず 200。記録は起動中のまま期限が切れる |
| 持ち主になった直後に Lambda が止まる | 期限つきの記録 | 期限のあとの再送でやり直せる |

4 行目は、放置すると重複につながります。タスクは動いているのに記録が起動中のままなので、期限のあとに同じ配送を再送すると、もう 1 つ起動します。自動の再送は無いので、人が再送しなければ起きません。再送する前に、ログの `claim not completed` を確かめてください。

ランナーの名前は、起動を試みるたびに変わります。

<<< @/examples/62-ci-runners/src/decide.ts{name}

同じ名前で登録し直したときに GitHub が何を返すかを、確かめられなかったからです。`generate-jitconfig` の応答には 409 がありますが、ドキュメントはその条件を書いていません。名前を毎回変えておけば、前の試みが残した登録に邪魔されません。

これらの順序は、`test/receive.test.ts` が、代役を使って 1 つずつ再現しています。

### ランナーが受け取るのは、起動のきっかけになったジョブとは限らない

タスクは、あるジョブの配送をきっかけに起動しますが、そのジョブを受け取るとは限りません。GitHub は、ラベルの合うランナーにジョブを渡すだけで、ランナーとジョブを 1 対 1 で結び付けてはいないからです。2 件のジョブがほぼ同時にキューに入ると、ランナーも 2 つ起動し、どちらがどちらを受け取るかは決まっていません。ジョブの数とランナーの数が合っていれば、それで困ることはありません。

困るのは、数が合わなくなったときです。ランナーが起動する前にジョブがキャンセルされると、ランナーは来ないジョブを待ち続けます。Fargate のタスクには、最長の実行時間の設定がありません（単発のタスクのドキュメントと RunTask のリファレンスには見つかりませんでした）。そこで、見回りの Lambda が、古いタスクを止めます。

<<< @/examples/62-ci-runners/src/sweep.ts{expired}

上限は 6 時間にしました。GitHub のランナーでのジョブの上限と同じ値です。ジョブを実行中のタスクも、上限を過ぎれば止めます。暴走したジョブの料金に、上限を付けるためでもあります。

## スタック

タスクのロールは 2 つあり、どちらもほとんど何もできません。

タスクロールの認証情報は、コンテナの中から、決まったアドレスに問い合わせれば取得できます。つまり、タスクロールに付けた権限は、ジョブが書いたどのコマンドからも使えます。だから空にしてあります。AWS に入る必要のあるジョブは、20章のワークフローと同じく、`id-token: write` を付けて OIDC のトークンを求め、信頼ポリシーがブランチや環境を確かめたうえで、ロールを引き受けます。セルフホストランナーのジョブでも OIDC のトークンを求められることは、トークンに `runner_environment` というクレームがあり、その値に `self-hosted` があることから読み取りました。ドキュメントに、そう明記した文はありません。信頼ポリシーをいっそう絞るなら、このクレームを条件に足すこともできます。
