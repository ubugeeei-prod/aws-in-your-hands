# 07 File Upload: presigned URL と S3

06章で、サインインした人が自分のノートだけを読み書きできるようになりました。この章では、ノートに画像を付けられるようにします。

画像は、ブラウザが S3 に直接送ります。API は画像を一度も受け取りません。API がするのは、この人はこの場所に、この種類の、この大きさまでの画像を 1 枚置いてよい、という許可証を出すことだけです。

前提は [06章](/ja/chapters/06-auth.md)です。コードは `examples/07-uploads/` にあります。ノートの保存は 05章、サインインと認可は 06章のコードをそのまま import して使うので、この章で書くのは、添付のために増える部分だけです。

## 全体像

```figure

step api -> api: key = u/<sub>/<note id>/<attachment id>
step api -> api: ロールの認証情報で POST ポリシーに署名
step api --> browser: 201 attachmentId, upload: url, fields
step browser -> s3: 2. POST fields, file (トークンなし)
step s3 --> browser: 204。ポリシーを満たさなければ 4xx
note s3: tag: upload-state=pending
step browser -> api: 3. PUT .../attachments/{attachmentId}

step browser -> s3: 5. img src = presigned GET (トークンなし)
mark s3
```

この章で新しく作るのは、アップロード用のバケット 1 つと、06章のテーブルに増える添付の記録です。

### 画像が API を通らない理由

画像を API に送り、Lambda から S3 に書く方法もありますが、この章では使いません。Lambda を通すと、画像の大きさのぶんだけ関数が動き、メモリを使います。また、Lambda が 1 回の呼び出しで受け取れるのは 6 MB までです。画像を運ぶのは S3 が得意とすることなので、S3 に直接送ります。

そのかわり、解決しなければならないことが 1 つ出てきます。S3 は、06章のアクセストークンを知りません。ブラウザが S3 に直接リクエストを送るとき、この人が誰で、何をしてよいのかを、S3 に伝える手段が要ります。その手段が署名付き URL（presigned URL）です。

### 3 つのリクエストに分かれる

全体像の図の 1、2、3 のとおり、添付は 3 つの別々のリクエストでできています。許可をもらうリクエスト、S3 に送るリクエスト、送ったことを伝えるリクエストです。

1 つの操作に見えるものが 3 つに分かれているので、途中で止まることがあります。2 まで終わって 3 が届かないことも、3 の途中で関数が落ちることもあります。途中で止まったときの扱いは、[しくみと実装](/ja/chapters/07-uploads/build.md)で詳しく見ます。

### 署名付き URL が渡すもの

署名付き URL は、署名を URL に含めた、期限つきの URL です。S3 へのリクエストには、ふつう AWS の認証情報で署名します。署名付き URL は、その署名を先に済ませて URL に埋め込んだものなので、受け取った人は、AWS の認証情報を持っていなくても、その 1 つの操作を実行できます。

公式ドキュメントには、押さえておくべきことが 3 つ書いてあります。

- 署名付き URL が使う権限は、URL を作ったプリンシパル（principal）のものです。そのプリンシパルにできないことは、URL にもできません
- 署名付き URL はベアラートークン（bearer token）です。持っている人なら誰でも使えます
- 期限までは、何度でも使えます

この章で URL を作るのは Lambda 関数です。そのため、関数の実行ロールに許した範囲が、API が配るすべての許可証の外枠になります。ロールの権限を絞る理由が、ここでも 1 つ増えます。

### 大きさと種類を守る場所

ブラウザのコードで大きさを確かめても、守ったことにはなりません。確認を飛ばして S3 に直接送れば済むからです。API も画像を見ないので、守れません。守れるのは、画像を受け取る S3 だけです。

S3 に守らせる方法は 2 つあります。

| | 署名付き PUT | 署名付き POST（この章） |
| --- | --- | --- |
| 形 | 署名付きの URL に `PUT` で送る | 署名付きのポリシーをフォームに入れて `POST` で送る |
| 種類 | `Content-Type` を署名に含めると、同じ値でしか送れない | ポリシーの条件で一致を要求できる |
| 大きさ | 範囲を指定する仕組みはない | `content-length-range` で最小と最大を指定できる |
| 上書きの禁止 | `If-None-Match` が使える操作に `PutObject` がある | その一覧に POST Object はない |

この章では POST を選びました。5 MB までという上限を S3 自身に拒否させる方法が、公式ドキュメントにはっきり書いてあるのは POST のほうだからです。POST ポリシー（POST policy）は、アップロードが満たすべき条件を並べた文書で、`content-length-range` は「アップロードされる内容の、許される最小と最大の大きさ」と説明されています。

PUT でも、API が先に大きさを聞いて `Content-Length` を署名に含めれば、その大きさでしか送れなくなるはずです。ただ、公式ドキュメントにあるのは、送るつもりのヘッダーはすべて署名するとよいという一般的な勧めまでで、`Content-Length` についての記述は確認できませんでした。確かめられていない方法を、守りの中心には置きません。

POST を選んだかわりに、表の最後の行にある上書きの禁止は使えなくなります。その影響は、しくみと実装の[この設計に残る穴](/ja/chapters/07-uploads/build.md)で説明します。

<<< @/examples/07-uploads/api/src/s3-object-store.ts{presign-upload}

`createPresignedPost` は、S3 にリクエストを送りません。関数の中で計算して署名するだけです。S3 がポリシーを確かめるのは、あとでブラウザの POST が届いたときです。

`Fields` に入れた値は、それぞれ、完全に一致することを求める条件になります。入れているのはキー、`Content-Type`、タグで、これに大きさの範囲と期限（5 分）が加わります。ブラウザが選べるものは残していません。`starts-with` のような幅のある条件を 1 つも使っていないことは、テストで確かめています。

この部分は、実物の S3 では確かめられていません。とくに、タグをフォームで送ることがそうです。POST Object のドキュメントには `tagging` という欄がありますが、POST ポリシーの条件の表に `tagging` という名前は載っていません。フォームの欄はすべて条件に書かなければならないという規則があるので、SDK が作る `{"tagging": "..."}` という条件で通るはずだ、と読みました。確かめる手順は、[この章の検証メモ](/ja/chapters/07-uploads/wrap.md)にあります。

### S3 が見ないもの

S3 が確かめるのは、フォームに書かれた `Content-Type` がポリシーと一致することです。ファイルの中身が本当に PNG かどうかは見ないので、`image/png` と名乗る HTML も置けます。

この章でしている対策は 2 つです。1 つは、許す種類を 4 つの画像形式に絞ることです（SVG はスクリプトを含められるので外しました）。もう 1 つは、画像をアプリとは別のオリジン（S3 のドメイン）から配ることです。中身を検査したいなら、アップロードの後で動く処理が要ります（[08章](/ja/chapters/08-async.md)で足します）。

## キーは API が決める

<!-- section: 07.keys -->

オブジェクトキー（object key）は、バケットの中でオブジェクトを指す名前です。`/` を含められますが、フォルダーがあるわけではありません。

<<< @/examples/07-uploads/api/src/keys.ts{keys}

キーは `u/<持ち主>/<ノートの ID>/<添付の ID>` で、3 つの部分はすべてサーバーが決めます。持ち主は検証済みのトークンの `sub` です。ノートの ID は、その持ち主の下で実在を確かめたものです。添付の ID は、時刻と乱数から作ります。

ファイル名はキーに入れません。利用者が入力した文字列をキーに入れると、`../` や `/` で他人の場所を指せないかを、毎回確かめることになります。入れなければ、確かめる対象がありません。

<<< @/examples/07-uploads/api/src/attachments.ts{request-upload}

考え方は 06章と同じです。このノートがこの人のものかを確かめる if 文はなく、ノートを、呼び出した人の `sub` の下で探すだけです。他人のノートは見つからないので、404 が返ります。403 を返さないのも 06章と同じ理由で、ノートの ID が使われているかどうかを教えないためです。

<<< @/examples/07-uploads/api/src/app.ts{routes}

ルートは、06章のアプリにそのまま足しています。サインインを確かめる 06章のミドルウェアが先に登録されているので、足した 4 つのルートも、トークンがなければ 401 を返します。

テストは、次のようにしてこの仕組みを破ろうとします。

- Bob が Alice のノートに許可を求めると、存在しないノートと同じ 404 が返る
- Bob がクエリ、ヘッダー、ボディのすべてに Alice の名前と Alice のキーを書いても、返ってくるキーは `u/bob/` で始まる
- Bob は、Alice の添付の ID を知っていても、完了も、一覧も、削除もできない
- キーの部品に `/`、`..`、空文字が入ると、キーを組み立てる関数が例外を投げる

### 許可証は、1 人 1 日 100 枚まで

`requestUpload` が最後にする検査は、許可証の枚数の上限です。

許可証を出しただけでは、使われるまでバケットに何も置かれません。そのため、いま何枚出ているのかは、バケットを見てもわかりません。数えずにいると、サインインした利用者は許可証を好きなだけ受け取れて、1 枚ごとに最大 5 MB を置けます。完了しなかったものは 1 日後に S3 が消しますが、それまでは保存料金がかかります。

そこで、出した枚数を数えます。

<<< @/examples/07-uploads/api/src/permit-ledger.ts{ledger}

枚数は、ノートと同じテーブルに置きます。データの置き場所は増やしていません。

<<< @/examples/07-uploads/api/src/permit-ledger.ts{dynamodb}

持ち主のパーティションに、日付（UTC）ごとに 1 つのアイテムを置き、数を 1 ずつ足します。数を足すことと、上限より小さいことの確認を、1 回の更新でします。そのため、同時に届いた 2 つのリクエストが、両方とも最後の 1 枚を取ることはありません。05章でノートの件数を数えたのと同じ形です。

上限に達すると、429 `upload_quota_exceeded` を返します。ノートの件数の上限は 409 でしたが、許可証の上限は 429 です。待てば、つまり日付が変われば、また通るからです。

数えているのは出した枚数で、使われた枚数ではありません。使われなかった許可証も 1 枚と数えます。一方で、404 で断ったリクエストと、ノート 1 つに 10 枚という上限で断ったリクエストは数えません。

この上限によって、1 人が 1 日に置ける未完了のオブジェクトは、100 個、500 MB までになります。日付ごとのアイテムは、この章では消していないので、アップロードした日ごとに小さなアイテムが 1 つ残ります。

この上限では防げないことが 1 つあります。上に書いたとおり、許可証は期限（5 分）までは何度でも使えます。同じキーに上書きするので、置かれる量は増えません。しかし、S3 へのリクエストの数は、この上限では絞れません。
