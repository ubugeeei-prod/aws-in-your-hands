# 10 Edge: 手元で動かす

[前のページ](/ja/chapters/10-edge.md)では、エッジの関数 `edge-router.js` を読み、Node.js のテストで動かしました。このページでは、同じ関数を手元のサーバーで動かし、KVS の整合性と、KVS の中身を書き換えるスクリプトを扱います。

## 手元で動かす

<!-- section: 10.local -->

テストに加えて、ブラウザや `curl` からも関数を呼べるようにしてあります。

```bash
vp run dev:edge
```

<http://localhost:8790> で、関数と `site/` の中身をつないだサーバーが立ち上がります。Docker も AWS のアカウントも要りません。

```bash
curl -si http://localhost:8790/plans | head -n 3
curl -s http://localhost:8790/ | grep '<h1>'
curl -si 'http://localhost:8790/sale?ref=mail' | grep -i location
```

`/plans` には、`/pricing/` への 301 が返ります。リダイレクトの表とフラグは `examples/10-edge/edge-data.json` に書いてあります。

<<< @/examples/10-edge/edge-data.json

サーバーを動かしたまま、`maintenance` を `true` に書き換えて保存すると、次のリクエストから 503 になります。`newHome` を `true` にすると、`/` の中身が入れ替わります。サーバー側のターミナルには、リクエストごとに、KVS から読んだキーの名前が出ます。

<<< @/examples/10-edge/src/local/dev.ts{dev}

このサーバーが再現しないものは、次の 4 つです。

- 反映の遅れ。このサーバーでは、ファイルを保存した次のリクエストで値が変わります。本物の KVS はそうなりません。遅れについては、このページの「KVS が約束すること、しないこと」で扱います
- CloudFront のキャッシュ。どのリクエストも、関数とオリジンの代用品を通ります
- ランタイムの制約。構文、サイズ、メモリ、実行時間の上限は再現しません
- S3 の応答の細部。無いファイルには、単純な 404 を返しています

### cdkd のエミュレーターで動かす

cdkd には、synth したディストリビューションを手元で動かす機能があります。関数は cdkd が用意した実行環境で動き、KVS は JSON ファイルで代用できます。

```bash
vp run dev:edge:cdkd
```

こちらのサーバーは <http://localhost:8791> で待ち受けます。先ほどと同じ `curl` を試したところ、同じ応答が返りました。`import cf from "cloudfront"` も、ID なしの `cf.kvs()` も、そのまま動いています。S3 のオリジンと CloudFront Function だけなら、Docker は要りませんでした。

ただし、cdkd のエミュレーターも CloudFront そのものではありません。エミュレーターがランタイム 2.0 の制約をどこまで再現しているかは、調べていません。言えるのは、2 つの別々の代用品で同じ結果になった、というところまでです。Lambda@Edge はこのエミュレーターでは実行されず、警告を出して飛ばされます。

## KVS が約束すること、しないこと

<!-- section: 10.kvs -->

KVS は名前のとおりキーと値を入れる場所ですが、DynamoDB（[05章](/ja/chapters/05-dynamodb.md)）とは性質がかなり違います。違いは 3 つあり、最初は大きさです。

<<< @/examples/10-edge/src/kvs/config.ts{limits}

キーは 512 バイト、値は 1 KB、1 つの KVS 全体で 5 MB までです。1 回の更新リクエストで変更できるのは 50 キー（または 3 MB）までです。値に入れられるのは文字列、バイト列、JSON です。KVS は設定の表を置く場所で、アプリのデータを置く場所ではありません。

2 つ目は、書ける相手です。関数は読むだけなので、訪問回数を数えるような、リクエストのたびに書く使い方はできません。

3 つ目がいちばん重要で、書いた値はすぐには読めません。

```figure
caption: UpdateKeys が成功したあと、値はエッジロケーションごとに別々の時刻に届き、t1 では 2 人の読者が別々の答えを受け取る
type: sequence
actor op: 運用者
actor a: エッジロケーション A
actor b: エッジロケーション B
step op -> op: t0 UpdateKeys が成功
note a: t0 maintenance = off
note b: t0 maintenance = off
step op --> a: t1 届く
note a: t1 maintenance = on
note b: t1 maintenance = off
step op --> b: t2 届く
note a: t2 maintenance = on
note b: t2 maintenance = on
```

更新の API が成功を返した t0 の時点では、どのエッジロケーションも古い値を読んでいるかもしれません。t1 では、東京の読者には 503 が返り、別の場所の読者には通常のページが返る、ということが起こりえます。すべてのエッジロケーションが同じ値を読むようになるのは t2 です。

t0 から t2 までの長さについて、Developer Guide には数字も保証も見つけられませんでした。手がかりは 2 つだけです。1 つは、`meta()` が返す最終更新時刻について「エッジへの伝播時間は含まない」と書かれていることです。もう 1 つは、提供開始時の AWS の公式ブログが「数秒で全エッジロケーションに伝播する」と説明していることです。ブログは仕様書ではないので、この本では「たいていは数秒らしいが、上限は約束されていない」ものとして扱います。実際に計ってもいません。

この性質から、設計では次の 3 つを守ります。

- 書いた直後に全拠点で読めると仮定しません。同期のスクリプトが終わっても、切り替わったとは限りません
- 途中の状態で困らないデータだけを置きます。リダイレクトが数秒のあいだ古くても、誰も困りません。反対に、ある瞬間から全員を確実に締め出す必要があるなら、KVS のスイッチは向いていません
- 書いた順番に依存しません。A を書いてから B を書いても、B が見えるエッジロケーションで必ず A も見えるとは、ドキュメントのどこにも書かれていません

なお、1 回の関数の実行の途中で値が変わることはありません。ドキュメントによれば、更新は実行と実行のあいだに処理されます。

## 表を安全に書き換える

<!-- section: 10.sync -->

KVS の中身を `edge-data.json` に合わせるスクリプトを書きます。全部消して全部入れ直すのがいちばん簡単ですが、消してから入れ直すまでのあいだ、リダイレクトがすべて止まります。そこで、差分だけを送ります。

<<< @/examples/10-edge/src/kvs/plan.ts{plan}

`planSync` は、入れるキー、消すキー、そのままのキーを分けます。純粋な関数なので、AWS なしでテストできます。

消す範囲には制限を付けています。このスクリプトが消すのは、`flag:` と `redirect:` で始まるキーだけです。ほかのキーが KVS にあっても、見つけたことを報告するだけで、触りません。同じ KVS を別の用途と共有していたときに、`edge-data.json` に無いという理由で他人のデータを消さないためです。

### ETag で、見ていない変更の上書きを防ぐ

2 人が同時に表を書き換える場合を考えます。自分が KVS を読んで差分を計算しているあいだに、同僚がコンソールで 1 行直したとします。自分の差分は古い中身をもとにしているので、そのまま書くと、同僚の変更を知らないまま上書きするかもしれません。

KVS の API には、この上書きを防ぐ仕組みがあります。KVS は版を表す ETag を持っていて、書き込みには、自分が読んだ版を示す `If-Match` を必ず添えます。版が進んでいれば、書き込みは拒否されます。05章の条件付き書き込みと同じ考え方で、楽観的な更新と呼ばれます。

<<< @/examples/10-edge/src/kvs/sync.ts{port}

スクリプトから見た KVS の操作は、`read` と `update` の 2 つだけです。AWS SDK を呼ぶ本物と、テスト用の代用品が、同じ型を実装します。

<<< @/examples/10-edge/src/kvs/sync.ts{sync}

`syncStore` は、やり直すたびに KVS を読み直し、計画を立て直します。古い計画をもう一度送ることはありません。この作りによって、失敗の種類ごとに何が起きるかが決まります。

- 誰かが先に書いた場合、書き込みは拒否されるので、読み直します。新しい計画は、相手の変更を見たうえで立てられます
- 書き込みは届いたのに応答が届かなかった場合（タイムアウトや切断）、書けたかどうかはこちらからわかりません。読み直せばわかります。書けていれば差分は空になり、同じ変更を二重には送りません
- 複数のリクエストの途中で止まった場合、KVS は半分だけ新しい状態で残ります。50 キーを超える変更は複数のリクエストに分かれ、1 つのリクエストは全部成功か全部失敗かのどちらかですが、リクエストの列全体はそうではないからです。もう一度実行すれば、残りだけが送られます
- 何度やっても競合する場合、5 回であきらめてエラーにします。いつまでも繰り返すことはありません
- 権限が無い場合や値が不正な場合、やり直しても結果は同じなので、すぐに止まります

守りたいことを 1 文にすると、「sync は、自分が読んでいない変更を上書きしない。そして、どこで失敗しても、もう一度実行すれば `edge-data.json` に収束する」です。`examples/10-edge/test/sync.test.ts` は、ETag を持つ代用品の KVS に対して、上の失敗を 1 つずつ決まった順序で起こし、この文が壊れないことを確かめます。

### AWS を呼ぶところ

<<< @/examples/10-edge/src/kvs/store.ts{adapter}

`read` が読む順番は、先に ETag、後で中身です。逆にすると、新しい ETag と古い中身の組ができることがあります。この組で書き込むと、ETag が合っているので通ってしまい、見ていない変更を上書きします。先に ETag を取っておけば、ずれたときに手元に残るのは必ず古い ETag なので、書き込みは拒否されます。

KVS の API には、ほかのサービスと違う点が 2 つあります。

1 つは、API が 2 つに分かれていることです。KVS そのものを作ったり消したりするのは、通常の CloudFront の API です。中のキーと値を読み書きするのは、CloudFront KeyValueStore という別の API です。どちらにも `DescribeKeyValueStore` があり、返す ETag は別物で、入れ替えて使えません。

もう 1 つは署名です。キーと値の API は、リージョンを持たないグローバルなエンドポイントで、SigV4A という署名方式を使います。AWS SDK for JavaScript は、SigV4A の署名の実装を別パッケージにしています。公式ドキュメントの例は、CRT（ネイティブのバイナリ）を使う `@aws-sdk/signature-v4-crt` を読み込んでいますが、この章では JavaScript だけで動く `@aws-sdk/signature-v4a` を使いました。SDK のソースを読むと、どちらかが読み込まれていれば使われます。手元のテストでは、署名のヘッダーが SigV4A の形式（`AWS4-ECDSA-P256-SHA256`）になることまで確かめています。AWS がこの署名を受け付けることは、まだ確かめていません。

この振り分けには、確かめられていない点があります。API リファレンスには `ConflictException`（409）が載っていますが、古い ETag を送ったときに返るエラーがこれだとは書かれていません。このアダプターは `ConflictException` だけを競合として扱います。実際には別のエラーが返るのであれば、そのあとの動きはステータスで分かれます。5xx 以外なら、同期はやり直さずにエラーで止まります。5xx か、ステータスのないエラーなら、一時的な失敗として読み直し、5 回までやり直します。どちらの場合も上書きはしないので安全な側に倒れますが、直すべき点です。
