# 51 Chime SDK: しくみと実装

[前のページ](/ja/chapters/51-chime-sdk.md)で、サーバーの仕事は席を渡すことだけだと書きました。このページでは、その API を作ります。順番は、部屋とメンバー、席を渡す処理、席を取り上げる処理、テーブルの条件、Chime を呼ぶ部分、スタック、ブラウザーのページです。

## 部屋とメンバー

<!-- section: 51.rooms -->

Chime SDK には「この人は入ってよい」という考え方がありません。`CreateAttendee` を呼べば、誰のぶんでもアテンディーができます。入ってよい人の名簿は、こちらで持ちます。

<<< @/examples/51-chime-sdk/api/src/room-store.ts{room}

部屋（room）は、名簿と、いま使っているミーティングの ID と、誰がどのアテンディーを持っているかの対応を 1 つにまとめたものです。この対応を、この章では席（seat）と呼びます。1 人の利用者が 1 つの部屋に持てる席は 1 つです。

ルートは 7 本で、どれも 06章の API に足します。

<<< @/examples/51-chime-sdk/api/src/app.ts{routes}

06章の `createApp` は、追加のルートを受け取って、サインインの確認の後ろに並べます。トークンのない呼び出しはルートに届く前に 401 になるので、ここに書いた処理はどれも、`context.identity.sub` が本人だとわかっている状態で動きます。誰の席を作るかは、パスにもボディにも書かせません。

メンバーでない人には、部屋が存在しないのと同じ答えを返します。

<<< @/examples/51-chime-sdk/api/src/rooms.ts{membership}

404 と 403 を使い分けているのは、相手がすでに知っていることに合わせるためです。部屋の ID を当てずっぽうで試す人に 403 を返すと、その ID の部屋があることを教えてしまいます。メンバーは部屋があることを知っているので、持ち主にしかできない操作には 403 を返します。

応答の形は 2 つあります。

<<< @/examples/51-chime-sdk/api/src/contract.ts{room}

メンバーに見せるのは、名簿と、誰が席を持っているかまでです。アテンディーの ID も join token も入れません。

<<< @/examples/51-chime-sdk/api/src/contract.ts{seat}

席の形は、Chime の API が返す形のままにしてあります。ブラウザーのライブラリーが、`CreateMeeting` と `CreateAttendee` の応答をそのまま受け取るように作られているからです。必須にしたのは、固定した版のライブラリーが実際に読むフィールドだけです。

`sub` を検査している `subSchema` にも理由があります。Chime の `ExternalUserId` は 2〜64 文字で、使える文字が決まっていて、`aws:` で始められません。Cognito の `sub` は UUID なので収まりますが、収まらない値がメンバーとして登録されると、その人は席を取るたびに Chime に断られます。だから、メンバーに加える時点で断ります。

## 席を渡す

<!-- section: 51.join -->

状態を持っている場所は 2 つあります。テーブルは誰がどの席に座っているかを知っていて、Chime はどの join token が有効かを知っています。この 2 つを 1 つのトランザクションで書き換える方法はありません。そこで、途中で止まっても不変条件が破れない順番を選びます。

```figure
caption: join token は、テーブルに席が記録されてから返る
type: sequence
actor browser: ブラウザー
actor api: API
actor table: DynamoDB
actor chime: Chime SDK
step browser -> api: POST .../join
step api -> table: 1. 部屋を読む
step api -> chime: 2. GetMeeting
step api -> chime: 3. DeleteAttendee
step api -> chime: 4. CreateAttendee
step api -> table: 5. 席を記録
step api --> browser: 6. join token
```

<<< @/examples/51-chime-sdk/api/src/rooms.ts{join}

順番の理由を、手順ごとに書きます。

手順 2 では、テーブルにミーティングの ID があっても、まず `GetMeeting` で確かめます。ミーティングは、誰も接続していない時間が 5 分続くと Chime が終わらせるので、テーブルの記録は古くなります。無ければ作り、ID をテーブルに書きます。この書き込みは「読んだときの ID のままなら」という条件つきです。2 人が同時に最初の参加者になると、2 人とも `CreateMeeting` を呼びますが、テーブルに書けるのは片方だけです。書けなかったほうは、自分の作ったミーティングを消して、最初からやり直します。

`CreateMeeting` に渡している `token` は、API の `ClientRequestToken` です。リファレンスには「別のミーティングには別のトークンを使う」とあり、同じリクエストを再送したときのためのものだと読めますが、同じトークンで 2 回呼んだときに何が返るかは書かれていません。そのため、この章は 1 回の呼び出しごとに新しい値を渡し、二重に作られることへの備えは、テーブルの条件つきの書き込みに任せています。

手順 3 は、同じ人がもう一度参加したときのためです。新しい席を作る前に古い席を消すので、新しい join token が返る時点で、古いほうは使えなくなっています。join token をどこかに写されたと思ったら、参加し直せば無効にできます。

手順 5 が、このページでいちばん大事な行です。アテンディーは手順 4 で Chime の中にできていますが、join token を返すのは、テーブルへの記録が成功したあとです。記録には条件が 4 つ付いています。部屋が閉じられていないこと、この人がいまもメンバーであること、ミーティングが手順 2 のものと同じであること、この人の席が手順 1 で読んだときのままであることです。どれかが崩れていたら、作ったばかりのアテンディーを消して、やり直します。

3 回続けて負けたら、409 を返してあきらめます。この場合も、作ったアテンディーは消してあります。

### 順序をテストで固定する

「途中で別のリクエストが割り込む」ことを、テストでは決まった位置で起こします。テスト用の道具は、あるメソッドが次に呼ばれる直前に別の処理を走らせるか、その呼び出しを失敗させます。

たとえば、Bob のアテンディーが Chime にできてから、テーブルに記録されるまでのあいだに、持ち主の Alice が Bob を部屋から外す場合です。記録は「メンバーであること」の条件で失敗し、Bob には 404 が返ります。Bob に送られたどの応答にも join token は入っておらず、Chime に残るアテンディーは Alice の 1 人ぶんだけです。

同じやり方で、2 人が同時に最初の参加者になる場合、同じ人が 2 つのタブから同時に参加する場合、`GetMeeting` と `CreateAttendee` のあいだでミーティングが終わる場合を再現しています。テストは `api/test/seats.test.ts` にあります。

## 席を取り上げる

<!-- section: 51.revoke -->

退出は、席を渡す処理の逆です。

<<< @/examples/51-chime-sdk/api/src/rooms.ts{leave}

先に Chime のアテンディーを消し、そのあとでテーブルの席を消します。逆にすると、`DeleteAttendee` が失敗したときに、テーブルは席を忘れているのに join token は生きている、という状態が残ります。この順番なら、失敗してもテーブルに席が残るので、もう一度退出すれば消せます。ただし、失敗してからやり直すまでのあいだは、join token が使えたままです。テストでも、その事実をそのまま確かめています。

メンバーを外す処理と、部屋を閉じる処理は、同じ順番に従います。

<<< @/examples/51-chime-sdk/api/src/rooms.ts{revoke}

まず権利を取り上げ、次にその権利で作られたものを終わらせ、最後に記録を消します。メンバーを外すときは、先に名簿から消します。そのあとは、進行中の参加があっても、席の記録が「メンバーであること」の条件で失敗します。部屋を閉じるときは、先に `closed` の印を付けます。そのあとは、新しいミーティングも席も記録できません。

部屋の記録を最後に消すのには、もう 1 つ理由があります。ミーティングの ID は、この記録の中にしかありません。新しい名前空間の API にはミーティングを一覧する呼び出しがないので、ID を先に忘れると、動いているミーティングを止める手段がなくなります。`DeleteMeeting` が失敗したら、部屋は閉じた状態のまま残り、持ち主がもう一度閉じれば続きから進みます。

### ブラウザーが黙って消えたとき

ここまでの退出は、ブラウザーが `POST /rooms/{id}/leave` を呼んでくれる場合の話です。タブを閉じる、端末の電源が落ちる、といったときは、誰も API を呼びません。アテンディーは残り、join token も有効なままです。

この章の API は、これを検知しません。ミーティングは、誰も接続していない時間が 5 分続けば終わり、そのとき全員のアテンディーも消えます。それまでのあいだに、残った join token を知っている人は入り直せます。知っているのは本人のブラウザーだけのはずなので、この章ではここまでにしています。本番で足すものは[費用、注意点、片付けのページ](/ja/chapters/51-chime-sdk/wrap.md)に書きました。

## テーブルの条件

<!-- section: 51.store -->

席を渡す処理が頼っているのは、テーブルの条件つきの書き込みです。インターフェースは、その条件をメソッドの単位にしています。

<<< @/examples/51-chime-sdk/api/src/room-store.ts{store}

どのメソッドも書き込み 1 回で、条件が成り立たなければ `false` を返します。読んでから書く、という 2 段の操作はありません。

部屋は、05章のノートのテーブルに、ノートとは別のキーで入れます。

<<< @/examples/51-chime-sdk/api/src/dynamodb-room-store.ts{keys}

条件は、DynamoDB の条件式として書きます。

<<< @/examples/51-chime-sdk/api/src/dynamodb-room-store.ts{conditions}

席を取るときの条件式は、`meetingId = :meeting`、席が読んだときのままであること、`closed = :open`、`contains(members, :sub)` の 4 つを `AND` でつないだものです。席を手放すときは、後ろの 2 つを付けません。外されたメンバーの席を消せなくなるからです。

この条件式は、DynamoDB に対して実行していません。Nix のシェルには Docker の daemon が無く、DynamoDB Local を起動できないためです。テストが確かめているのは、メモリー上の実装が同じ条件に従うことと、DynamoDB 用の実装がこのページに書いたとおりの式を送ることまでです。式が受け付けられ、書いたとおりに働くかどうかは、デプロイして確かめる必要があります。

## スタック

<!-- section: 51.stack -->

スタックの中身は、06章のものから SPA の配信を除き、Chime を呼ぶ権限とルートを足したものです。ユーザープール、テーブル、関数、HTTP API は 06章と同じ書き方なので、ここでは違うところだけを取り上げます。

Chime SDK のミーティングは、CloudFormation のリソースではありません。テンプレートのリソースの一覧に Chime SDK は無く、固定した版の aws-cdk-lib にも対応するモジュールがありません。宣言できるのは、ミーティングを作る権限だけです。

<<< @/examples/51-chime-sdk/infra/lib/calls-stack.ts{chime-permissions}

`chime:CreateMeeting` のリソースが `*` になっているのは、手抜きではありません。IAM のサービス認可リファレンスで、このアクションにはリソースの種類が定義されていません。まだ無いミーティングを ARN で指すことはできないからです。残りの 4 つはミーティングに対する操作なので、このアカウントの、API を呼ぶリージョンのミーティングに限っています。テストは、`*` が `chime:CreateMeeting` の 1 か所だけであることと、Chime のアクションがこの 5 つだけであることを固定しています。

この権限では、関数は、同じアカウントの別のアプリが作ったミーティングにも触れます。絞る方法はあります。`CreateMeeting` は条件キー `aws:RequestTag` に、残りは `aws:ResourceTag` に対応しているので、ミーティングにタグを付けて、そのタグのものだけを許可できます。この章では試していないので、スタックには入れていません。

ルートは、部屋のものを 5 行足しました。

<<< @/examples/51-chime-sdk/infra/lib/calls-stack.ts{routes}

どのルートにも JWT オーソライザーが付いています。アプリの中のサインインの確認と合わせて二重になりますが、API Gateway の側で断られたリクエストは、関数まで届きません。

スタックにあるものは、すべて使ったぶんだけ課金されるものです。API Gateway の HTTP API、Lambda、オンデマンドの DynamoDB、Cognito のユーザープールで、時間で課金されるものはありません。

## ブラウザーのページ

<!-- section: 51.web -->

ページは、06章のサインインをそのまま使う小さな Vue のアプリです。ビルドは Vize です。06章の画面と違うのは、部屋を作る、人を入れる、参加する、退出する、の 4 つの操作があることです。

設定は、06章の `/config.json` にキーを 1 つ足しました。

<<< @/examples/51-chime-sdk/web/src/config.ts{config}

`media` が `"none"` のとき、ページは席を取るところまで進み、そこで止まります。手元の API が渡す接続先は作り物なので、つなぎにいっても失敗するだけだからです。

`"chime"` のときは、受け取った席をクライアントライブラリーに渡します。

<<< @/examples/51-chime-sdk/web/src/session.ts{start}

`MeetingSessionConfiguration` に渡しているのが、API の応答の 2 つのオブジェクトです。ここから先、ブラウザーは Chime のメディアサービスと直接やり取りします。マイクの許可を求めるのは `startAudioInput` のところで、カメラは利用者がボタンを押すまで使いません。ほかの参加者の声は 1 本に混ざって届くので、`<audio>` 要素は 1 つで足ります。映像は参加者ごとのタイルで届き、タイルに付いている `boundExternalUserId` が、サーバーがアテンディーを作るときに入れた `sub` です。

このモジュールは、参加するときに初めて読み込みます。ビルドすると 1.3 MB（gzip で 295 kB）ほどのチャンクになり、ページを開いただけの人には送りません。

セッションが終わる理由はいくつもあります。理由ごとに何を表示し、何をするかは、ライブラリーを読み込まないふつうの関数にしてあります。

<<< @/examples/51-chime-sdk/web/src/call.ts{signal}

`AudioJoinedFromAnotherDevice` は、同じ join token で別の場所から接続されたときに届きます。自分で別の端末に移ったのなら問題ありません。身に覚えがなければ、join token が漏れています。ページは、参加し直せば向こうの接続が切れることを伝えます。参加し直すと、サーバーは古いアテンディーを消してから新しいものを作るからです。

<<< @/examples/51-chime-sdk/web/src/call.ts{release}

終わったあとに API へ退出を伝えるかどうかも、理由によって変わります。別の端末に席が移っただけのときに退出を伝えると、アテンディーが消え、移った先の通話まで切れてしまいます。

このページのうち、メディアにかかわる部分は、型検査とビルドを通しただけです。マイク、カメラ、音声の再生、映像のタイルは、一度も動かしていません。
