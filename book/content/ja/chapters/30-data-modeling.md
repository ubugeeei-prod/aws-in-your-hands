# 30 Data Modeling: DynamoDB の single-table design、GSI、Streams、transaction

[05章](/ja/chapters/05-dynamodb.md)では、DynamoDB のテーブルを、持ち主とノートの ID で引くキーバリューストアとして使いました。読み方が 2 種類しかなかったので、キーを 1 組決めれば足りました。この章では、読み方が増えたときにテーブルをどう設計するかを扱います。ノートを添付と一緒に 1 回で読み、最近更新した順に並べ、タグで探し、件数を数えます。

DynamoDB では、読み方を先に書き出し、それに合わせてキーを決めます。1 つのテーブルに種類の違うアイテムを並べる single-table design、別の並び順のための global secondary index（GSI）、複数のアイテムをまとめて書くトランザクション、変更を読んで派生データを作る DynamoDB Streams を、ノートのアプリに順に足していきます。足すたびに、何が保証されて、何がいくらかかるのかを確かめます。

前提は 05章です。コードは `examples/30-data-modeling/` にあります。この章は HTTP の層を足しません。作るのは、05章の `NoteRepository` の下に入る保存の層と、ストリームを読む Lambda 関数です。認証（[06章](/ja/chapters/06-auth.md)）と添付のアップロード（[07章](/ja/chapters/07-uploads.md)）は、そのまま上に載ります。

スタックに、置いてあるだけで料金がかかるリソースはありません。外から呼べるエンドポイントもありません。

SQL で書けば数行で済む要求を、この章はかなりの手間をかけて実装します。その手間に見合わない場合については、このページの最後の「リレーショナルデータベースのほうが合うとき」に書きました。

アプリが書き込む先は、図で強調してあるテーブル 1 つです。ノート、添付、タグ、件数のカウンターが、すべてこのテーブルのアイテムです。

インデックスとタグの件数は、テーブルから派生したデータです。インデックスは DynamoDB が、タグの件数はストリームを読む Lambda 関数が、テーブルへの書き込みのあとで更新します。どちらも、テーブルより少し遅れます。この章で繰り返し出てくるのは、この区別です。テーブルに書いた瞬間に正しいものと、あとから追いつくものを、読み方ごとに決めていきます。

## 読み方を先に書き出す

<!-- section: 30.access-patterns -->

アプリがデータをどう読み書きするかを 1 つずつ書いたものを、アクセスパターン（access pattern）と呼びます。この章のノートのアプリには、次の 6 つがあります。

| 読み方 | 読む先 | 整合性 |
| --- | --- | --- |
| ノート 1 件と、その添付すべて | テーブルへの `Query` 1 回 | 強整合 |
| ある持ち主の、最近更新したノートの一覧 | GSI への `Query` | 結果整合だけ |
| あるタグの付いたノートの一覧 | テーブルへの `Query`（タグのアイテム） | 結果整合で読む |
| ある持ち主のノートの件数 | カウンターのアイテムを `GetItem` | 強整合で、正確 |
| タグごとのノートの件数 | ストリームから作ったアイテムを `GetItem` | ストリームの処理のぶん遅れる |
| slug からノートを引く | `GetItem` 2 回 | 強整合 |

slug は、持ち主の中で重複しない、ノートの別名です（`kyoto-2026` のような文字列）。重複を許さないことを、DynamoDB の上でどう守るかを見るために足しました。

書き込みの側にも決まりがあります。

- ノート、そのタグ、slug、件数は、すべて書かれるか、どれも書かれないかのどちらかです
- 添付は、ノートが存在するときにだけ書けます
- 古い `version` に基づく更新は、05章と同じく拒否されます

量の上限も先に決めます。ノートは持ち主 1 人あたり 100 件まで、タグはノート 1 件に 8 個まで、一覧の 1 ページは 20 件までです。タグの上限は、ノートとタグを 1 つのトランザクションで書けるようにするための上限でもあります。

## リレーショナルデータベースのほうが合うとき

<!-- section: 30.fit -->

この章で作るものを SQL で書くと、ノート、添付、タグの 3 つのテーブルと、いくつかのインデックス、`UNIQUE` 制約、`COUNT(*)` になります。並び順を増やすにはインデックスを 1 行足せば済み、題名の写しを書き直す必要も、件数を別に持つ必要もありません。この章の大半は、リレーショナルデータベースなら宣言 1 つで済むことを、アプリのコードで実装する話です。

そのかわりに DynamoDB で得られるものは、05章で挙げたとおりです。接続を管理しなくて済み、VPC が要らず、使っていない間の料金がほぼ 0 で、どの読み方も、データが増えても読む量が変わらないように設計できます。読み方が決まっていて、数が少なく、あとから増えにくいアプリには合います。

次のどれかに当てはまるなら、SQL を選ぶほうが無理がありません。

- 読み方がまだ決まっていない、または頻繁に増える
- 種類の違うデータをまたぐ集計や結合が中心にある
- 一意性や参照の制約がいくつもある
- 件数の上限（1 つのトランザクションに 100 アイテムまで）に収まらない単位で、まとめて書きたい

AWS の中では、[13章](/ja/chapters/13-sql.md)の Aurora DSQL や RDS for PostgreSQL がその選択肢です。

Cloudflare を使っているなら、D1 がそのまま合う場面が多いはずです。2026-10-13 時点の公式ドキュメントによると、D1 は SQLite の SQL で問い合わせるデータベースで、インデックスは `CREATE INDEX` で作り、一意性は `CREATE UNIQUE INDEX` で守れます。`batch()` で送った複数の文は 1 つのトランザクションとして実行されます。料金は読んだ行と書いた行の数で決まり、インデックスのある列への書き込みは、書いた行が 1 つ以上増えます。この章でいう「インデックスの書き込みにも料金がかかる」と同じ形です。制約は大きさと並行性にあります。データベース 1 つは 10 GB までで、この上限は引き上げられません。1 つのデータベースは問い合わせを 1 つずつ順に処理します。Cloudflare は、利用者ごとやテナントごとにデータベースを分ける使い方を想定していると書いています。

Durable Objects の SQLite も近い選択肢です。オブジェクト 1 つが、自分だけの SQLite のデータベース（10 GB まで）を持ち、単一スレッドで動きます。SQL の API は同期で動くので、1 回の処理の中で読んでから書くまでの間に、別のリクエストが割り込みません。この章が条件付き書き込みとトランザクションで作っている保証を、実行のモデルが最初から与えてくれます。持ち主 1 人のノートを 1 つのオブジェクトに入れる設計なら、この章の問題の多くは起きません。そのかわり、オブジェクトをまたぐ問い合わせは自分で組み立てることになります。

Vercel には、この種のデータベースの自社製品はありません。同じ日に確認した公式ドキュメントでは、Vercel 自身のストレージは Blob と Global Config で、リレーショナルや NoSQL のデータベースは、Marketplace を通して他社のサービスを用意する形です。

ノートのアプリがこの章の規模にとどまるなら、D1 や Durable Objects を離れる理由は、データの設計にはありません。DynamoDB の設計を学ぶ意味があるのは、ほかの理由で AWS の上にいて、接続もサーバーも持たない保存先がほしいときです。
