# 02 Toolchain: しくみと実装

環境に入り、依存を入れたところから続けます。このページでは、タスクの仕組み、設定の検証、CDK のコード、synth、cdkd の順に、サンプルの中身を見ていきます。

## コマンドはすべて `vp run`

<!-- section: 02.vp -->

この本のコマンドは、すべて `vp run <タスク名>` で実行します。Make やほかのタスクランナーは使いません。タスクはルートの `vite.config.ts` に定義してあり、ルートで実行します。タスク名を付けずに `vp run` とだけ入力すると、タスクの一覧が表示されます。

タスクの名前を見ても、その裏で何が実行されるのかはわかりません。そこでこの本では、`vp run` を使うコードブロックのすぐ下に、そのタスクが実際に実行するコマンドを載せています。表示は `vite.config.ts` と `tools/` のコードから組み立てているので、定義と食い違うことはありません。同じタスクは、ページの中で最初に出てきたところにだけ載せます。cdkd を呼ぶタスクは、実行するときにも、同じコマンドを `$ (cd ... && AWS_REGION=... cdkd ...)` の形で端末に表示します。

`vp` には `vp dev`、`vp build`、`vp test`、`vp check` といった組み込みのコマンドもあり、こちらは Vite+ の機能です。`vp run build:book` のように `run` が付くものが、この本で定義したタスクです。名前が似ているので、取り違えないようにしてください。

タスクは 2 種類に分けてあります。

<<< @/vite.config.ts{kinds}

`live` は、AWS のように手元の外にあるものを読むか変えるタスクで、必ず `cache: false` にしています。

キャッシュを無効にするのは、`vp run` が、入力ファイルの変わっていないタスクの実行を省いて、前回の出力を再生することがあるからです。ビルドなら時間の節約になりますが、デプロイやドリフトの検出で同じことが起きると、表示された「成功」は前回のもので、いまのアカウントについては何も示していません。キャッシュが使われたときは `cache hit, replaying` と表示されるので、新しく実行した結果とは見分けられます。

`cache: false` にはもう 1 つ効果があり、呼び出し元の環境変数がそのままタスクに渡ります。`AWS_PROFILE` がタスクに届くのはこのためです。

この章のサンプルには `hello` という名前を付けたので、`hello:infra:synth` や `hello:infra:deploy` などのタスクができます。03章は `spa`、04章は `api`、本のサイトは `book` です。

手元だけで完結する検査は、1 つのタスクにまとめてあります。

```bash
vp run check:all
```

`check:all` は、format、lint、型検査、テスト、すべての CDK アプリの synth、本のビルドとリンク検査を実行します。AWS には触らず、ドリフトの検出も含みません。

lint には、Oxlint の組み込みのルールに加えて、[awscdk-lint](https://awscdk-lint.dev/) を入れてあります。筆者の同僚の ren-yamanashi さんが作っている、CDK のコードのための lint です。コンストラクトの ID を変数から組み立てている、`this` を渡すべきところに `scope` を渡している、といった、CDK が黙って受け入れてしまう書き方を指摘してくれます。この本では、公開されている recommended のルールをそのまま、すべての CDK アプリにかけています。設定は `vite.config.ts` の `lint` にあります。

型検査には、`vp check` ではなく `vp run typecheck` を使います。プロジェクトごとに `tsc` を実行するだけのタスクです。このタスクでは、執筆中に原因のわかりにくい失敗がありました。変更していないソースに対して、`aws-cdk-lib` の import を別のモジュールと取り違える型エラーが、同じ入力で 5 回実行して 2 回出たのです。原因は pnpm と TypeScript 7 の組み合わせでした。pnpm は、中身が同じファイルを 1 つの実体へのハードリンクとして配置します。`aws-cdk-lib` には `export * from './lib';` とだけ書かれた `index.d.ts` が 3,501 個あり、そのすべてが同じ inode を指していました。TypeScript 7 はファイルを inode で見分けるので、これらを区別できなくなっていました。`pnpm-workspace.yaml` に `packageImportMethod: clone-or-copy` を指定し、ハードリンクをやめて複製にしたところ、エラーは出なくなりました。ときどき失敗する検査は、もう一度実行すれば通るので放置されがちですが、原因はたいていどこかにあります。

## 型が守るもの、守らないもの

<!-- section: 02.types -->

サンプルが作るのはバケット 1 つだけですが、設定を 2 つ受け取ります。環境の名前（`stage`）と、古い版のオブジェクトを残す日数（`noncurrentVersionDays`）です。

CDK では、こうした設定をコンテキストとして渡せます。`cdk.json` に書くか、コマンドラインで `-c stage=prod` のように指定します。ただし、コンテキストは型のない値として届きます。`-c noncurrentVersionDays=30` と書いたときに届くのは、数値の `30` ではなく文字列の `"30"` です。

TypeScript の型注釈は、この値を検査しません。`as HelloConfig` と書いてもコンパイラが何も言わなくなるだけで、実行時の値は変わりません。そこで、外から来た値は実行時にスキーマと照合します。この照合を runtime validation と呼びます。

<<< @/examples/02-toolchain/lib/config.ts{schema}

型（`HelloConfig`）はスキーマから導いています。型と検査を別々に書いていないので、片方だけ直し忘れることがありません。

<<< @/examples/02-toolchain/lib/config.ts{parse}

不正な値があると、どの項目が悪いかを添えて synth の時点で失敗するので、AWS には届きません。

この先の章でも同じやり方をとります。環境変数、HTTP のリクエストとレスポンス、ブラウザのストレージ、キューのメッセージは、どれも型の外から届く値です。入口で一度検証し、その内側では型を信頼します。

型が守らないものもあります。型検査に通っても、IAM の権限が足りているとは限らず、サービスの上限に収まっているとも、複数の処理が同時に走ったときに正しく動くとも限りません。これらは、テストと実環境での確認で確かめます。

## コンストラクト、スタック、アプリ

<!-- section: 02.cdk -->

AWS CDK は、AWS のリソースを TypeScript の class として書く仕組みです。単位が 3 つあります。

- construct: 1 つ以上のリソースを表す class。`s3.Bucket` はコンストラクトです
- スタック（stack）: まとめて作り、まとめて消すリソースの単位
- アプリ（app）: スタックを集めたプログラム全体

<<< @/examples/02-toolchain/lib/hello-stack.ts{stack}

`s3.Bucket` の 1 行は、バケットのほかに、HTTPS 以外の接続を拒否するバケットポリシーも作ります。コンストラクトは、このような既定の設定をまとめて持っています。

`removalPolicy` は、スタックを消したときにバケットをどうするかを決めます。練習用の環境ではスタックと一緒に消し、`prod` では残します。データを持つリソースでは、消し忘れて料金がかかることと、消してはいけないものを消してしまうことのどちらが困るかを、リソースごとに決める必要があります。サンプルでは、この判断をテストで固定しています。

<<< @/examples/02-toolchain/bin/app.ts{app}

`env` にはリージョンだけを書き、アカウントを書いていません。こうすると、synth は認証情報なしで動き、AWS には何も問い合わせません。どのアカウントに作るかは、デプロイのときに使う認証情報で決まります。そのアカウントを毎回表示して照合するのが、01章で設定した `AIH_AWS_ACCOUNT_ID` です。

## synth: コードをテンプレートにする

<!-- section: 02.synth -->

synth（合成）は、CDK のコードを実行して、CloudFormation のテンプレート（template）と呼ばれる JSON を `cdk.out/` に出力する処理です。AWS は何も変わりません。

```bash
vp run hello:infra:synth
```

`examples/02-toolchain/cdk.out/AihHello.template.json` を開くと、`AWS::S3::Bucket` と `AWS::S3::BucketPolicy` の 2 つが書かれています。CDK のコードは、最終的にこの宣言的な文書になります。

テストは、このテンプレートに対して書きます。

```bash
vp run test:unit
```

`examples/02-toolchain/test/hello-stack.test.ts` は、バケットが非公開であること、`prod` では削除でも置き換えでもバケットが残ること、設定した日数がライフサイクルルールに入ることを確かめています。このテストが確かめるのは、意図したテンプレートが出力されることです。AWS がそのテンプレートを受け入れるか、作られたバケットが期待どおりに振る舞うかは、テストの対象外です。

設定を変えて synth し直すこともできます。`vp run` は、タスク名のあとの引数をそのままコマンドに渡します。

```bash
vp run hello:infra:synth -c stage=prod
```

## cdkd: テンプレートを AWS に反映する

<!-- section: 02.cdkd -->

テンプレートを AWS に反映する経路は 2 つあります。

1 つは AWS CDK CLI（`cdk deploy`）で、テンプレートを CloudFormation に渡します。CloudFormation は AWS のサービスで、テンプレートを受け取ってリソースを作り、何を作ったかを自分で記録し、失敗したら巻き戻します。こちらが標準の経路です。

もう 1 つが cdkd です。同じテンプレートを読みますが、CloudFormation を通さず、AWS の各サービスの API（一部は Cloud Control API）を直接呼んでリソースを作ります。何を作ったかの記録は state と呼び、自分のアカウントの S3 バケットに JSON で保存します。

cdkd は `cdk deploy` を速くした別名ではなく、作る経路も記録の場所も別のツールです。そのため、次の 3 点を押さえておきます。

1. cdkd の公式ドキュメントは、cdkd を開発・テスト用途向けとし、本番には AWS CDK CLI を勧めています（確認日 2026-10-11、固定した版は 0.296.28）。この本は、学習中に変更と確認を短い間隔で繰り返すために cdkd を使います。本番向けの経路は [20章](/ja/chapters/20-shipping.md)で扱います。
2. 同じリソースを 2 つの経路で交互に管理してはいけません。cdkd で作ったスタックを `cdk deploy` で更新したり、その逆をしたりすると、2 つの記録が食い違います。
3. state を失うと、cdkd は自分が何を作ったかわからなくなります。state のバケットはバージョニングが有効で、復旧の手段として `cdkd import` があります。ただし、この本では復旧を実行して確かめてはいません。

準備として、アカウントとリージョンの組ごとに一度だけ bootstrap を実行します。

```bash
vp run infra:bootstrap
```

このタスクは AWS を変更します。固定した版のソースによると、作られるのは次の 3 つです。

| 作られるもの | 名前 | 用途 |
| --- | --- | --- |
| S3 バケット | `cdkd-state-<アカウント ID>` | state の保存。アカウントに 1 つ |
| S3 バケット | `cdkd-assets-<アカウント ID>-<リージョン>` | デプロイ用のファイルの置き場 |
| ECR リポジトリ | `cdkd-container-assets-<アカウント ID>-<リージョン>` | コンテナイメージの置き場 |

cdkd の bootstrap は、名前は似ていますが `cdk bootstrap` とは別のものです。`cdk bootstrap` は CloudFormation のスタック（`CDKToolkit`）を作り、その中にデプロイ用の IAM ロールも含めます。cdkd の bootstrap は IAM ロールを作らず、cdkd はサインインに使った認証情報の権限でそのままリソースを作ります。
