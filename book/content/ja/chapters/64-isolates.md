# 64 Isolates: V8 isolate の実行環境を AWS でセルフホストする

[04章](/ja/chapters/04-http-api.md)のアプリは、`Request` を受けて `Response` を返す関数でした。Cloudflare Workers が動かすのも同じ形の関数で、そのランタイムは workerd という名前で公開されています。この章では、workerd を自分の AWS アカウントで動かし、04章のアプリを 1 行も書き換えずに載せます。そのうえで、Workers というプラットフォームが受け持っていた仕事のうち、どれが自分の仕事になるのかを確かめます。

この章で作るものは、**置いてあるだけで時間単位の料金がかかります**。ロードバランサーと Fargate のタスク 1 つで、リクエストが 1 件も来なくても 1 日およそ USD 1.24、1 か月（730 時間）で USD 37.68 です。既定の構成はイメージのリポジトリだけで、時間課金のリソースは、イメージのタグを指定してデプロイしたときに初めてできます。試した日のうちに、[片付け](/ja/chapters/64-isolates/wrap.md)まで進めてください。

workerd は、この章を書いたマシン（macOS、arm64）で実際に起動しました。04章のアプリを載せて呼び出し、テストもその実物に対して動かしています。一方、コンテナイメージは一度もビルドしておらず、AWS には何もデプロイしていません。Linux の workerd は取得して中身を確かめただけで、実行していません。内訳は[章末の検証メモ](/ja/chapters/64-isolates/wrap.md)にまとめました。

前提は 04章のノート API、[11章](/ja/chapters/11-network.md)の VPC、[12章](/ja/chapters/12-containers.md)のコンテナのスタックです。同時に処理中のリクエストがモジュールスコープを共有する話は、[35章](/ja/chapters/35-lambda-managed-instances.md)の続きにあたります。コードは `examples/64-isolates/` にあります。

## workerd とは

<!-- section: 64.what -->

workerd の README は、自分のことを「Cloudflare Workers を動かしているのと同じコードにもとづく、JavaScript と Wasm のサーバーランタイム」と説明しています。使い道として挙げているのは 3 つで、Workers 向けに書いたアプリケーションをセルフホストするサーバー、手元の開発とテストの道具、プログラムできる HTTP プロキシです。ライセンスは Apache License 2.0 です。

README には、太字の警告が 1 つあります。趣旨を訳すと、次のとおりです。

> workerd は堅牢なサンドボックスではありません。workerd は、それぞれの Worker が設定で許されたリソースにしか触れられないように分離しようとします。しかし workerd だけでは、実装のバグに備えた十分な多層防御を持っていません。悪意があるかもしれないコードを動かすなら、仮想マシンのような、適切で安全なサンドボックスの中で workerd を動かさなければなりません。

この章の例が動かすのは、自分で書いた 04章のアプリだけです。他人のコードを動かす話は、次の節で境界を整理したうえで、やらないことにします。

2026-10-13 の時点で確かめたことを並べます。

- **配布。** ビルド済みのバイナリは npm で配られています。`workerd` パッケージが、プラットフォームごとのパッケージ（darwin-arm64、darwin-64、linux-arm64、linux-64、windows-64）のうち、そのマシンに合うものを連れてきます。Linux arm64 があるので、この本がほかの章で使っている arm64 の Fargate にそのまま載せられます
- **版。** 版の番号は日付です。README によれば、その版が対応するいちばん新しい compatibility date を表します。この章は、2026-10-12 に公開された 1.20261012.1 に固定しました
- **動く条件。** Linux では glibc 2.35 以降が要ると README に書かれています（Ubuntu 22.04 や Debian 12）。macOS は 13.5 以降です
- **設定。** Cap'n Proto のテキスト形式で書いた 1 つのファイルです。worker の一覧（services）、待ち受けるソケット（sockets）、worker に渡す binding を、このファイルに書きます
- **互換性。** worker ごとに compatibility date を指定します。workerd を新しくしても、古い日付を指定した worker の動きは変わらないと、README は約束しています

固定した版は、リポジトリの 1 か所に書いてあります。

<<< @/examples/64-isolates/src/release.ts{release}

`version` は `package.json` の devDependency と同じ値で、テストが 2 つの一致を確かめます。手元のマシン用のバイナリは npm が連れてきますが、イメージに入れる Linux arm64 のバイナリは、開発するマシンの種類に関係なく必要です。そのため、配布物の大きさとダイジェストを別に固定しました。

## isolate が分けるもの、分けないもの

<!-- section: 64.isolate -->

isolate は、V8 が 1 つのプロセスの中に作る実行の単位です。Cloudflare のドキュメントは、isolate ごとにメモリが完全に分かれていること、1 つのランタイムが数百から数千の isolate を動かせること、関数ごとに仮想マシンを作らないので、仮想マシンの方式にあるコールドスタートが無いことを挙げています。起動の速さとメモリについては、「コンテナや仮想マシンの上の Node のプロセスよりおよそ 100 倍速く起動し、起動時のメモリは 1 桁少ない」と書いています。Cloudflare が述べている数字で、この本では測っていません。

これまでの章に出てきた単位と並べると、違いは「隣と何を共有しているか」にあります。プロセスどうしは、OS のカーネルを共有しています。コンテナは、カーネルの機能で見える範囲を狭めたプロセスで、カーネルを共有している点は変わりません。Fargate のタスクについては、AWS のドキュメントが「タスクごとに分離の境界を持ち、カーネル、CPU、メモリ、ネットワークインターフェースをほかのタスクと共有しない」と書いています。isolate は、この中でいちばん多くを共有しています。プロセスも、スレッドも、V8 そのものも隣の isolate と同じで、分けているのは V8 が管理するメモリだけです。microVM を含めた比較は、[67章](/ja/chapters/67-firecracker.md)が扱います。

Cloudflare は、この薄い境界の上で、他人どうしのコードを 1 つのプロセスに同居させています。Cloudflare のセキュリティモデルのページによると、それができるのは、isolate の外側に次のものを重ねているからです。

- プロセス全体を囲むサンドボックス。Linux の namespace と seccomp で、ファイルシステムとネットワークへのアクセスをすべて禁じています。外とのやり取りは、別のプロセスが仲介します
- 信頼の度合いが違う Worker を別々のプロセスに分ける仕組み（cordon）と、一部の Worker を専用のプロセスに移す仕組み
- Spectre への備え。コードの実行中は `Date.now()` の値を止め、ほかのタイマーもスレッドも与えません
- V8 のセキュリティ修正が公開されてから 24 時間以内に、新しいランタイムを本番に出す体制

同じページは、V8 の攻撃面が仮想マシンより広いことも認めています。

workerd のリポジトリにあるのは、このうち isolate とランタイムの部分です。外側の層は入っていません。README の警告は、その差を指しています。手元で動かした workerd でも、差の 1 つが見えました。CPU を 2 秒間使い続ける worker の中で、時計は進んでいました（[しくみと実装](/ja/chapters/64-isolates/build.md)の「workerd が課さない上限」）。

セルフホストする側が足すべきものは、README が書いているとおり、workerd のプロセスを囲む、仮想マシンのような境界です。この章の構成では、Fargate のタスクがその役をします。ただし、Fargate のタスクが分けるのは、タスクとタスクのあいだです。同じ workerd のプロセスに載せた worker どうしを分けているのは、やはり isolate だけです。互いに信頼できないコードを、1 つのプロセスに載せてはいけません。

## プラットフォームを離れて失うもの、残るもの

<!-- section: 64.leave -->

残るものは、コードです。04章のアプリは、`Request`、`Response`、`URLPattern`、`fetch` といった Web 標準の API と、`node:crypto` の `randomUUID` だけに頼っています。workerd はどちらも持っているので、アプリのファイルには手を入れません。[しくみと実装](/ja/chapters/64-isolates/build.md)で書くのは、入口の 3 行と設定のファイルだけです。

失うものは、ランタイムの外側にあったものすべてです。

- **グローバルなネットワーク。** Workers のコードは、Cloudflare の世界中の拠点で動きます。この章の workerd は、東京のリージョンのタスク 1 つで動きます
- **binding の先。** workerd の設定には、KV、R2、Queues の binding の種類があります。ただし、設定のスキーマの説明によれば、これらは操作を HTTP リクエストに変えて、設定で名指ししたサービスへ送るだけです。保存先そのものは workerd に入っていないので、自分で用意します。D1 という種類の binding は、この版のスキーマにはありません
- **Durable Objects の分散。** Durable Objects は workerd の中で動きます。保存先はメモリの中か、実験的と明記されたローカルディスクで、オブジェクトは常に 1 つのランタイムの中にあるとスキーマに書かれています。複数のマシンにまたがって 1 つのオブジェクトを保つ仕組みは、workerd にはありません。[24章](/ja/chapters/24-celld.md)の celld は、その部分を自分で持つ別のランタイムです
- **リクエストごとの上限。** Workers は、CPU 時間の上限を超えたリクエストをエラーにし、メモリの上限を超えた isolate を作り直します。workerd は、どちらの上限も課しません
- **デプロイの道具と観測。** `wrangler deploy` も Workers Logs もありません。代わりに使うのは、コンテナイメージ、ECS のサービスの入れ替え、CloudWatch Logs です
- **セキュリティ修正の速さ。** V8 の修正を取り込むには、自分で workerd の版を上げ、イメージを作り直してデプロイします
- **料金の形。** リクエストごとの料金が、タスクとロードバランサーの時間の料金に変わります

AWS の binding にあたるものは、IAM のロールと SDK です。DynamoDB や S3 を使うアプリを workerd に載せるなら、SDK が workerd の上で動くか、認証情報をどう渡すかを確かめる必要があります。この章は、メモリの中にノートを置く 04章のアプリだけを扱っていて、そこまでは確かめていません。

## AWS での構成

<!-- section: 64.architecture -->

```figure
caption: workerd は Fargate のタスクの中の 1 つのプロセスで、ロードバランサーから来たリクエストを、設定で結び付けた worker に渡す
node client: Client
node alb: ALB | HTTP :80
node workerd: workerd | socket http, *:8080
node notes: notes worker | 04章のアプリ, isolate
node ecr: ECR repository | workerd + config + bundle
node logs: CloudWatch Logs
edge client -> alb: HTTP
edge alb -> workerd: リクエスト, /health
edge workerd -> notes: fetch(request, env)
edge ecr --> workerd: イメージの取得
edge workerd --> logs: 標準出力
group task: Fargate task (arm64) = workerd, notes
mark workerd
```

workerd を載せる場所の候補は、[23章](/ja/chapters/23-ec2.md)の EC2 インスタンスと、12章の Fargate でした。Fargate にした理由は 4 つあります。

1 つ目は、動く条件です。workerd のビルド済みバイナリは glibc 2.35 以降を求めます。23章のインスタンスの OS である Amazon Linux 2023 は、AWS のドキュメントによれば glibc 2.34 です。取得した Linux arm64 のバイナリを調べると、実際に `GLIBC_2.35` の版のシンボルを参照していました。Amazon Linux 2023 の上で起動を試してはいませんが、条件を満たしていない場所を選ぶ理由はありません。コンテナなら、ベースイメージを Debian 12 にするだけで済みます。

2 つ目は、分離です。前の節で見たとおり、workerd のプロセスの外側には境界が要ります。Fargate のタスクは、その境界を AWS が用意してくれる単位です。

3 つ目は、入れ替えです。workerd には、設定の変更を見張って読み直す `--watch` がありますが、ヘルプは「本番では勧めない」と書いています。README が本番向けに紹介しているのは、systemd にソケットを開かせて workerd に引き継ぐ方法です。動いているプロセスに新しいコードを無停止で読み込ませる手順は、どちらにも書かれていません。そこで、新しい版は新しいプロセスとして起動し、古いプロセスと入れ替えます。12章の ECS のサービスとロードバランサーは、その入れ替えをすでに持っています。

4 つ目は、ログです。workerd は、worker が `console.log` に書いた行を標準出力に出します。コンテナの標準出力は、12章と同じ設定で CloudWatch Logs に届きます。

ロードバランサーを CloudFront に替える構成は取っていません。タスクへリクエストを配り、ヘルスチェックで入れ替えを支えるのはロードバランサーの仕事なので、CloudFront を使うとしても、[03章](/ja/chapters/03-spa.md)のディストリビューションを、ロードバランサーの前に足す形になります。

スタックは 12章のものとほぼ同じで、設定も同じ 3 つを CDK のコンテキストで渡します。

<<< @/examples/64-isolates/src/config.ts{config}

## セルフホストに向く場合、向かない場合

<!-- section: 64.when -->

Workers で足りているなら、Workers にいるのがよい選択です。世界中の拠点、binding、リクエストごとの上限、セキュリティの多層防御は、どれも workerd のバイナリには入っていません。料金も、小さな負荷では Workers のほうが安くなります。月 1,500 万リクエストの例では、Workers が USD 8.00、この章の構成が USD 39.02 です（[費用](/ja/chapters/64-isolates/wrap.md)）。

AWS の上で同じアプリを動かしたいだけなら、04章の Lambda が先に来ます。コードは同じで、置いてあるだけの料金がありません。

それでも workerd を自分で動かす理由として考えられるのは、次のような場合です。

- Workers 向けに書いたコードを、VPC の中のデータのそばで動かしたい
- 本番と同じランタイムを、手元と CI で動かしたい。この用途だけなら AWS は要らず、[手元で動かす](/ja/chapters/64-isolates/local.md)のページで足ります
- データを置く国やネットワークを、自分で決める必要がある
- 自分で書いた小さな worker をたくさん、1 つのプロセスにまとめて動かしたい

どの場合でも、他人が書いたコードを受け取って動かす用途には、この章の構成だけでは足りません。そうした実行環境の作り方は、[63章](/ja/chapters/63-agent-sandbox.md)が別の単位で扱います。

公開されている似たランタイムとして、存在と保守の状況を確かめたのは 1 つだけです。Supabase Edge Runtime は Deno にもとづくサーバーで、README は自分をベータ版と呼び、プロキシをする main runtime と、利用者のコードを動かす user runtime に分かれていると説明しています。最新のリリースは 2026-10-01 でした。Workers の API をそのまま動かすものではなく、この章では試していません。24章の celld は、Workers と Durable Objects のアプリケーションを動かす別のランタイムです。
