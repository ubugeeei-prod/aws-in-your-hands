### 1 ファイルに 1 文

D1 のマイグレーションは 1 つのファイルに SQL を何文でも書けますが、この章では 1 ファイルに 1 文だけにしました。

DSQL は 1 つのトランザクションに DDL を 1 文しか入れられないので、何文か書いたファイルは、全部通るか全部戻るかのどちらかにすることができません。最初から 1 文にしておけば、ファイル 1 つがトランザクション 1 つにそのまま対応します。

ランナーの本体は次のとおりです。

<<< @/examples/13-sql/src/migrate.ts{migrate}

ファイルを名前の順に流し、どこまで流したかをテーブル（`public.aih_migrations`）に記録するところは、D1 と同じです。違うのは、ループの中のコメントが説明している部分です。

DDL と DML は同じトランザクションに入れられないので、スキーマの変更と、変更したという記録は、別々のトランザクションになります。そのため、変更が終わってから記録を書くまでの間にプロセスが落ちると、適用済みなのに記録が無い状態が残ります。

その状態で次に実行すると、同じ文がもう一度流れます。そこで、どの文も 2 回流して問題のない形（`IF NOT EXISTS`）で書くことにし、[前のページの lint](/ja/chapters/13-sql.md) でそれを強制しています。マイグレーションの不変条件は、**記録があるなら、その文は適用されている。記録が無い文は、もう一度流しても結果が変わらない**、です。

この不変条件は、記録を書く直前で止めるテストで確かめています。

<<< @/examples/13-sql/test/migrate.test.ts{interrupted}

適用済みのファイルをあとから書き換えると、ランナーはチェックサムの違いに気づいて止まります。直したいときは、新しい番号のファイルを足してください。

手元の PostgreSQL は `ASYNC` という語を受け付けないので、ランナーは手元に送るときだけ、送る直前にこの語を取り除きます。

## トランザクションは丸ごとやり直す

<!-- section: 13.transactions -->

この章で D1 といちばん違うのが、トランザクションの扱いです。

ノートを作るときは、持ち主がまだ 100 件に達していないことを確かめてから書きます。素直に書けば、件数を数え、少なければ `INSERT` する、という処理になります。この処理が同時に 2 つ走った場合を、上限が 2 件で、すでに 1 件ある状態から追います。

```figure
caption: 上限が 2 件で、持ち主がすでに 1 件持っているとき、同時に走った 2 つのトランザクションのうち B はコミットで負け、やり直して上限に当たる
type: sequence
actor a: transaction A | POST /notes
actor db: Aurora DSQL
actor b: transaction B | POST /notes
step a -> db: t1 BEGIN (note_count = 1 を見る)
step b -> db: t2 BEGIN (note_count = 1 を見る)
step a -> db: t3 UPDATE owners SET note_count = 2
step a -> db: t4 INSERT INTO notes ...
step b -> db: t4 UPDATE owners SET note_count = 2
step a -> db: t5 COMMIT: ok
step b -> db: t5 INSERT INTO notes ...
step b -x db: t6 COMMIT: SQLSTATE 40001 (OC000)
note b: B が書いたものは何も適用されない
step b -> db: t7 再び BEGIN (note_count = 2 を見る)
step b -> db: t8 UPDATE ... WHERE note_count < 2
note b: t8 0 行
step b -> db: t9 COMMIT
note b: API は quota_exceeded を返す
```

Aurora DSQL のトランザクションは、始まった時点のデータを最後まで読み続けます（スナップショット分離）。B は t2 の時点の `note_count = 1` を見ているので、A がすでに書いたことを知らず、t4 の `UPDATE` はそのまま通ります。

ふつうの PostgreSQL であれば、B は t4 で、A のロックが外れるのを待ちます。DSQL は待たせません。ロックを取らずに両方を進めさせ、コミットのときに、同じ行を先にコミットしたトランザクションがいないかを調べます。これを楽観的同時実行制御（OCC）と呼びます。B は t6 で負けて SQLSTATE `40001`（serialization failure）を受け取り、B が書いたものは何も残りません。

負けた側は、**トランザクションを最初からやり直します**。

<<< @/examples/13-sql/src/transaction.ts{run}

`COMMIT` だけをもう一度送るのでは足りません。図の t7 で、やり直した B は `note_count = 2` を読み、今度は「もう入らない」と判断しています。1 回目とは答えが違うので、前回の判断を覚えておいて `INSERT` だけを流し直すと、3 件目ができてしまいます。

この章の不変条件は、**トランザクションは、全体がコミットされるか、全体がやり直されるかのどちらか。やり直しで結果が変わるのは、データベースから読み直した値によってだけ**、です。

### 件数を数えずに、行を 1 つ更新する理由

`SELECT count(*) FROM app.notes` で数えてから `INSERT` する書き方では、A も B も「1 件」と読み、それぞれ別の行を `INSERT` します。同じ行には書いていないので、DSQL は競合と見なしません。両方がコミットされて 3 件になります。この現象は write skew と呼ばれます。

`owners` の `note_count` を必ず更新するようにしたのは、2 つのトランザクションをあえて同じ行でぶつけるためです。同じ行に書けば、データベースが片方を止めます。

その代わり、同じ持ち主の作成と削除は、同時には 1 つしか通りません。1 人のノートであればそれで十分ですが、全員が同じ 1 行を更新する設計にすると、やり直しばかりになります。DSQL での設計では、どの行でぶつけるかを決めることが中心になります。

4 回とも負けた場合は、あきらめて 503 を返します。

どの回もロールバックされているので、何も書かれていません。呼んだ側は、同じリクエストをそのまま送り直せます。

読み取りも、同じランナーを通しています。スキーマを変えた直後は、古いスキーマを覚えている接続が `40001`（OC001）を受け取ることがあるからです。その分、1 回の読み取りごとに `BEGIN` と `COMMIT` の往復が増えます。

`version` の確認と、この再試行は、別のものを見つけます。`version` が見つけるのは、画面を開いてから保存するまでの数秒から数分の間に、ほかの誰かが書き換えた場合です。OCC が見つけるのは、ミリ秒の幅で同時にコミットしようとした場合です。どちらも必要です。
