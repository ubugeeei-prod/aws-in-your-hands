# 13 SQL: デプロイ

ここまでのアプリは、手元の PGlite の上で動いていました。このページでは、同じアプリを Lambda 関数として Aurora DSQL のクラスターにつなぎ、デプロイとバックアップの手順まで進みます。

## Lambda からつなぐ

<!-- section: 13.connect -->

### 接続

<<< @/examples/13-sql/src/dsql.ts{dsql}

DSQL に特有なのは、`password` に関数を渡しているところです。node-postgres は新しい接続を張るたびにこの関数を呼び、関数はその場でトークンを署名して返します。

トークンの署名は手元の計算だけで終わり、AWS には問い合わせません。そのため速いのですが、認証情報が間違っていてもトークンは作れてしまい、失敗がわかるのはクラスターにつなぎに行ったときです。

トークンの期限は既定で 15 分です。ただし、期限が確かめられるのは接続するときだけで、つながった接続は、トークンの期限が切れたあとも使えます。接続には別の上限があり、DSQL は 60 分で接続を切ります。そこで `maxLifetimeSeconds` を指定して、50 分たった接続はプールの側から捨てるようにしています。

`max: 1` にしたのは、Lambda の実行環境が一度に 1 つのリクエストしか処理しないからです。接続の数は、同時に動いている実行環境の数とほぼ同じになります。クラスターの上限は既定で 10,000 接続で、新しい接続は毎秒 100 本までです。

TLS は `rejectUnauthorized: true` にして、証明書の連鎖とホスト名を、Node.js が持っている認証局の一覧で確かめます。

<<< @/examples/13-sql/src/lambda.ts{handler}

04章と同じく、ファイルのいちばん外側は実行環境ごとに 1 回だけ動くので、プールもそこで 1 つだけ作ります。2 回目以降の呼び出しは、開いたままの接続を使い回します。

設定は起動時に確かめます。

### クラスターと権限

<<< @/examples/13-sql/infra/lib/sql-stack.ts{cluster}

クラスターの定義には、インスタンスの大きさも、サブネットも、パスワードもありません。固定している版の CDK（aws-cdk-lib 2.273.0）には DSQL 用の高水準のコンストラクトがまだ無いので、CloudFormation の `AWS::DSQL::Cluster` をそのまま表す `CfnCluster` を使っています。

練習用なので、削除保護は切り、スタックと一緒に消えるようにしました。本番では逆にします。

<<< @/examples/13-sql/infra/lib/sql-stack.ts{role}

権限は 2 段になっています。

1 段目は IAM です。`dsql:DbConnect` は、このクラスターに admin 以外のデータベースロールでつないでよい、という許可です。名前の似た `dsql:DbConnectAdmin` は `admin` としてつなぐ許可で、`admin` になるとテーブルを消せてしまうため、関数には渡していません。

2 段目はデータベースの中です。つないだあと、どのテーブルに何ができるかは、データベースロールへの `GRANT` で決まります。

<<< @/examples/13-sql/src/grant.ts{grant}

組み立てる文は 3 種類です。最初の `CREATE ROLE ... WITH LOGIN` が、ログインできるデータベースロールを作ります。`AWS IAM GRANT` は DSQL 独自の文で、この IAM ロールはこのデータベースロールとしてログインしてよい、という対応を登録します。`GRANT` で渡しているのは行の読み書きだけなので、関数はスキーマを変えられません。マイグレーションは、あなたが `admin` として手元から流します。

これらの文は `$1` を受け付けないので、データベースロールの名前と IAM ロールの ARN を SQL の文字列に埋め込むしかありません。[しくみと実装](/ja/chapters/13-sql/build.md)のページで、アプリは値を SQL に埋め込まないと書きましたが、ここだけは例外です。そのため、埋め込む前に 2 つの名前の形を厳しく確かめ、テストも付けました。

<<< @/examples/13-sql/infra/lib/sql-stack.ts{function}

バンドルの形式を CommonJS にしたのは、node-postgres が CommonJS で、Node.js の標準モジュールを `require()` で読むからです。synth でできたバンドルを手元の Node.js 24 で読み込み、データベースに触らないルートが応答するところまでは確かめました。

### 受け付ける量の上限

<<< @/examples/13-sql/infra/lib/sql-stack.ts{throttle}

04章と同じ、ステージのスロットリングです。受け付けるのは API 全体で 1 秒に 10 件、瞬間的なバーストは 20 件までで、超えた分は API Gateway が 429 で断り、関数もデータベースも呼ばれません。この API にも認証が無いので、上限が無ければ、呼ばれた分の DPU がそのまま請求になります。行の数は、[しくみと実装](/ja/chapters/13-sql/build.md)のページで実装した件数の上限が、持ち主 1 人あたり 100 行で止めています。

## デプロイして、マイグレーションを流す

<!-- section: 13.deploy -->

ここからは AWS を変更します。この節の手順は、まだ一度も実際の AWS で通せていません。

```bash
vp run sql:infra:diff
vp run sql:infra:deploy
```

クラスター、関数、API ができますが、まだ動きません。クラスターは空で、関数のロールもデータベースに入れないからです。データベースを作っただけではテーブルが無いのは、D1 でも同じです。

```bash
vp run sql:db:migrate
vp run sql:db:grant
```

`sql:db:migrate` は、手元と同じマイグレーションを、今度は `ASYNC` を付けたまま流します。インデックスの文が返すジョブの ID を使い、`sys.jobs` を見ながら完了を待ちます。`sql:db:grant` は、上の grant の文を流して、関数のロールを `notes_api` に結びつけます。

どちらのタスクも `admin` としてつなぐので、あなた自身の認証情報に `dsql:DbConnectAdmin` が要ります。

順番は、マイグレーションが先です。`GRANT ... ON ALL TABLES` が効くのは、その時点で存在するテーブルだけだからです。あとでテーブルを足すマイグレーションを流したら、`sql:db:grant` ももう一度流してください。

```bash
vp run sql:smoke
```

作成、読み戻し、更新、古い `version` での更新（409 を期待）、削除を順に確かめます。04章のスモークテストと違って、読み戻しは必ず成功するはずです。

シードを入れる場合は `vp run sql:db:seed` を使います。ログは `vp run sql:logs` で見られ、競合でやり直した回数は `transaction retry` の行でわかります。ドリフトの検査は `vp run sql:infra:drift` です。

固定している版の cdkd（0.296.28）は、`AWS::DSQL::Cluster` に専用の実装を持っておらず、Cloud Control API 経由で扱います。作成、エンドポイントの組み立てに使っている identifier の取得、ドリフトの読み戻し、削除が実際に通るかは、未確認です。

### クラウド用の reset を作らなかった理由

`sql:db:reset:local` はありますが、`sql:db:reset` はあえて作っていません。

クラウドでの reset は、テーブルをすべて消すことを意味します。コマンド 1 つで実行できるようにしておくと、いつか本番に向けて実行してしまいます。練習用のクラスターを空に戻したいときは、スタックごと消して作り直してください。

### 動いているデータベースのスキーマを変えるとき

D1 でも同じですが、マイグレーションとコードのデプロイは同時には起きないので、古いコードが新しいスキーマで動く時間が必ずあります。

DSQL では、ここに `ADD COLUMN` の制約が重なります。足せるのは制約も既定値もない列だけなので、列を足す、新しいコードを出す、古い行を埋める（1 回のトランザクションは 3,000 行まで）、という段階に分けることになります。この章では、そこまでは実装していません。

## バックアップとリストア

<!-- section: 13.backup -->

D1 には Time Travel があり、何も設定しなくても、過去 30 日の任意の分に戻せます。Aurora DSQL では、同じことをするのに手間が増えます。

Aurora DSQL のバックアップは、AWS Backup という別のサービスを通して取ります。取れるのはクラスター全体のバックアップで、その場で 1 回取るか、スケジュールと保持期間を決めて自動で取るかを選びます。リストアは元のクラスターを巻き戻すのではなく、常に**新しいクラスター**を作ります。

そのため、リストアのあとには、アプリの接続先を新しいエンドポイントに変える作業が残ります。この章のスタックは、クラスターの identifier からエンドポイントを組み立てているので、そこを差し替えることになります。データベースロールと `AWS IAM GRANT` が新しいクラスターに引き継がれるかは、確かめていません。

DSQL のドキュメントのバックアップのページには、指定した時刻の状態に戻す機能の説明はありませんでした。失ってもよい時間の長さは、バックアップを取る間隔で決まると考えておくのが安全です。

使われていないクラスターは Idle、さらに Inactive という状態に移り、計算資源が 0 になります。バックアップは Active のクラスターでないと取れないので、夜中のスケジュールで、誰も使っていないクラスターのバックアップが失敗することがありえます。

RDS と Aurora は、自動バックアップを持っています。Aurora は連続的に取っていて、保持期間（1〜35 日）の中の任意の時点に戻せます。RDS と Aurora でも、戻すと新しいインスタンスやクラスターができます。

この章では、練習用のデータなので、バックアップを取るリソースは作っていません。手順も試せていません。
