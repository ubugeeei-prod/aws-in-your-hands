# 57 Polly: しくみと実装

[前のページ](/ja/chapters/57-polly.md)で、Polly にできることと、音声を S3 に置く構成を見ました。このページでは実装を順に読みます。キャッシュのキー、同時に届いたリクエストの扱い、長いノートの分割、SSML のエスケープ、ルート、スタック、手元での起動の順です。

## キャッシュのキー

<!-- section: 57.cache -->

キャッシュのキーは、Polly が返す音声を決めるものすべてから作ります。エンジン、声、出力の形式、そして送る SSML です。どれか 1 つでも違えば別の音声なので、別のオブジェクトにします。

<<< @/examples/57-polly/src/cache-key.ts{key}

ハッシュにしておくと、文章の長さに関係なくキーの長さが決まり、ノートの文章がキーに現れません。キーを知っているだけでは何も読めない点も大事です。バケットは公開していないので、音声を読むには関数が署名した URL が要ります。その URL をもらえるのは、文章そのものを `POST /speech` で送った人だけです。つまり、音声を聞ける人は、もとの文章をすでに持っています。同じ文章を 2 人の利用者が別々に持っていれば、2 人は同じオブジェクトを聞きますが、どちらも相手から何も知らされません。

キーにノートの ID や持ち主を入れていないのは、そのためです。入れると、ノートを 1 文字直すたびに全体を合成し直すことになり、同じ文章の重複も省けません。

`VERSION` は、SSML が同じでも音が変わるような変更をしたときに上げます。たとえば、サンプリング周波数を指定するように変えたときです。上げると、すべての文章が新しいキーになり、古い音声はライフサイクルルールが消します。

### 印を置いた関数が止まったとき

印を置いたあと、音声を書く前に関数が止まることがあります。タイムアウトかもしれませんし、Polly がエラーを返したのかもしれません。印だけが残ると、その文章は誰にも合成されなくなります。

対処は 2 つあります。1 つは、合成に失敗したら印を返すことです。印の中身は置いた時刻で、失敗した関数はそれを 0 に書き換えます。上のコードの `catch` がそれです。もう 1 つは、古い印を引き継ぐことです。関数が何も言わずに止まった場合に備えて、置かれてから 90 秒を過ぎた印は、持ち主がいないものとして扱います。

<<< @/examples/57-polly/src/speak.ts{claim}

引き継ぎにも競争があります。古い印を 2 つのリクエストが同時に見つけると、両方が引き継ごうとします。そこで、書き換えには `If-Match` を付け、読んだときの ETag のままであるときだけ書き込みます。先に書き換えたほうが ETag を変えるので、もう一方は 412 で断られます。

<<< @/examples/57-polly/src/s3-audio-cache.ts{replace}

<<< @/examples/57-polly/test/speak.test.ts{takeover}

90 秒は、関数のタイムアウト（60 秒）より長くしてあります。印を持った関数は、印が古いと見なされる前に必ず止まっているので、生きている持ち主から印を奪うことはありません。スタックのテストが、この大小関係を確かめています。

この不変条件には、守れない場合が 1 つあります。合成が終わって Polly への支払いが決まったあと、音声を S3 に書く前に関数が止まると、次のリクエストがもう一度合成します。料金は 2 回ぶんかかります。Polly の合成と S3 への書き込みを 1 つの操作にする方法は無いので、これは受け入れています。保証しているのは「同時に届いても 1 回」と「成功した合成は 2 度と繰り返さない」の 2 つです。

時刻の比較には、関数ごとの時計を使っています。Lambda の実行環境どうしで時計がずれていても、90 秒と 60 秒の差より小さければ結果は変わりません。ずれの大きさについての保証は調べていません。

## 長いノートを分ける

<!-- section: 57.chunk -->

ノートの本文は 10,000 文字まであり、`SynthesizeSpeech` の 1 回ぶんの上限を超えます。そこで、上限に収まる部分に分けて、部分ごとに合成します。

分ける場所は文の終わりです。文の途中で音声を切ると、つなぎ目で抑揚が途切れます。日本語の句点と感嘆符、疑問符、改行のあとで切り、英語のピリオドは、あとに空白が続くときだけ文の終わりと見なします。`3.14` のような小数を 2 つに切らないためです。

<<< @/examples/57-polly/src/chunk.ts{sentences}

文を順に詰めていき、次の文を足すと上限を超えるところで区切ります。1 つの文が上限より長いときは読点や空白のあとで切り、それでも収まらなければ文字の単位で切ります。文字の単位で切るときは、絵文字のようなサロゲートペアを半分にしないよう、コードポイントで数えます。

<<< @/examples/57-polly/src/chunk.ts{pack}

大きさの数え方には注意が要ります。ドキュメントは上限を「3,000 文字」と書いていますが、何を 1 文字と数えるかは書いていません。日本語の 1 文字が 1 なのか、UTF-8 の 3 バイトぶんなのか、`&` を `&amp;` と書いたら 1 なのか 5 なのかが分かりません。そこで、エスケープしたあとの文章を UTF-8 のバイト数で数えることにしました。どの数え方をしても、これより大きくはなりません。

<<< @/examples/57-polly/src/ssml.ts{measure}

この数え方では、日本語は 1 回のリクエストに 1,000 文字までしか入りません。実際の上限が 3,000 文字なら、3 倍に細かく分けていることになります。料金は文字数で決まるので、細かく分けても金額は変わらず、増えるのはリクエストの数と、つなぎ目の数です。Polly を呼んで数え方が分かったら、`billedSize` を直してください。

部分に分けることには、上限に収める以外の利点もあります。部分ごとにキャッシュのキーが決まるので、長いノートの最後の段落だけを直したとき、合成し直すのはその部分だけです。ノートの題は本文とは別の部分にして、あとに 0.7 秒の間を入れています。

<<< @/examples/57-polly/src/chunk.ts{segments}

つなぎ合わせは、ブラウザで順に再生するだけにしました。MP3 のファイルを前後につないで 1 本にできるかどうかを、Polly のドキュメントでは確認できなかったからです。

## 利用者の文章を SSML に入れる

<!-- section: 57.ssml -->

題のあとに間を入れるために、関数は SSML を送ります。すると、利用者の書いた文章が XML の中に入ります。ノートに `<break time="10s"/>` と書いた人がいれば、そのままでは 10 秒の無音が合成されますし、`</speak>` と書けば文書が壊れて、合成がエラーになります。SQL に値を埋め込むときと同じ問題です。

対処も同じで、利用者の文章は、タグとして解釈されない形にしてから入れます。SSML で特別な意味を持つ文字は 5 つあり、ドキュメントに一覧があります。

<<< @/examples/57-polly/src/ssml.ts{escape}

エスケープのほかに、XML に書けない文字を取り除いています。XML 1.0 は、タブと改行を除く制御文字や、片方だけのサロゲートを、エスケープした形でも受け付けません。ノートに 1 文字でも混ざっていると、文書全体が不正になります。Polly がこうした文字をどう扱うかは確かめていませんが、送る前に落としておけば、どう扱われても困りません。

すでにエスケープされた文字列、たとえば `&lt;break/&gt;` も、もう一度エスケープします。利用者が書いたのはその 14 文字であって、タグではないからです。

SSML を組み立てる場所は 1 つだけで、そこに現れるタグは、コードに書いてある `<speak>` と `<break>` だけです。`<break>` の時間は数値から作り、利用者の入力は入りません。

<<< @/examples/57-polly/src/ssml.ts{document}

テストは、タグ、コメント、CDATA、実体の定義、エスケープ済みの文字列などを入れて、関数が書いたタグ以外に `<` や `>` が 1 つも残らないことを確かめています。SSML を使わずに `TextType` を `text` にすれば、この問題は起きません。間を入れる必要が無いなら、そのほうが単純です。

## スタック

<!-- section: 57.stack -->

作るのは、キャッシュのバケット、関数とそのロール、ロググループ、function URL です。

<<< @/examples/57-polly/infra/lib/polly-stack.ts{bucket}

ライフサイクルルールは 2 つです。音声は 30 日で消します。キャッシュなので、消えても次のリクエストで作り直されるだけです。30 日という期間は、保存の料金よりも、ノートの内容を別の形で持ち続ける期間として決めました。ノートを消しても、その音声はすぐには消えません。キーがハッシュなので、どの音声がどのノートのものかを、関数は知らないからです。この点は[次のページ](/ja/chapters/57-polly/wrap.md)でもう一度扱います。

印は 1 日で消します。印が意味を持つのは 90 秒だけですが、ライフサイクルルールの期間は日の単位で書くので、いちばん短い 1 日にしました。残っているあいだも、古い印は引き継がれるので、動作には影響しません。

<<< @/examples/57-polly/infra/lib/polly-stack.ts{role}

ロールに許可しているのは、ログの書き込みを除くと、`polly:SynthesizeSpeech`、2 つのプレフィックスの下への `s3:GetObject` と `s3:PutObject`、バケットへの `s3:ListBucket` です。`s3:GetObject` は、印を読むことのほかに、署名付き URL と `If-Match` の書き込みに要ります。`s3:ListBucket` が無いと、無いキーへの HEAD に S3 が 404 ではなく 403 を返します（07章）。削除の許可はありません。消すのはライフサイクルルールだけです。

`polly:SynthesizeSpeech` の `Resource` は `*` です。このスタックで `*` を使っているのは、ここだけです。Polly にはレキシコン以外のリソースが無く、レキシコンを使わないリクエストがどの ARN で評価されるのかを、ドキュメントから読み取れませんでした。

<<< @/examples/57-polly/infra/lib/polly-stack.ts{function}

function URL は、17章と同じく `AWS_IAM` で守っています。署名の無いリクエストは、関数が動く前に断られます。`NONE` にすると、URL を知った人が誰でも、このアカウントの料金で音声を作れます。ブラウザから直接呼ぶアプリにするなら、function URL の代わりに 06章の API Gateway とオーソライザーの後ろに置きます。

関数の入口は、04章の部品をそのまま使っています。

## 手元で動かす

<!-- section: 57.local -->

手元では Polly を呼びません。代わりに、文章の長さに比例した長さの音（440 Hz）を WAV ファイルにして返す関数を使います。

<<< @/examples/57-polly/src/fake-synthesizer.ts{fake}

声の代わりに音が鳴るだけですが、キャッシュ、分割、URL の並びは、デプロイしたものと同じコードが動きます。バケットの代わりは、メモリの中の `Map` です。

```bash
cp examples/57-polly/.env.example examples/57-polly/.env
vp run dev:polly
```

別の端末から、同じノートを 2 回送ります。

```bash
curl -s -X POST http://localhost:8857/speech \
  -d '{"title":"買い物","body":"牛乳を買う。卵も買う。"}'
```

1 回目のレスポンスは、次の形です。`parts` が 2 つあるのは、題と本文が別の部分だからです。

```text
{"voice":"Kazuha","engine":"neural","parts":[{"url":"http://localhost:8857/local/audio/speech/c94c63d6…?expires-in=3600","source":"synthesized"},{"url":"http://localhost:8857/local/audio/speech/0bc01537…?expires-in=3600","source":"synthesized"}],"billedCharacters":14,"expiresInSeconds":3600}
```

2 回目は、URL が同じで、`source` が `cache`、`billedCharacters` が 0 になります。`billedCharacters` の 14 は、手元の代役がコードポイントで数えた値で、Polly の数え方ではありません。URL をブラウザで開くと、音が鳴ります。

`.env` の `SPEECH_BACKEND` を `polly` にし、`SPEECH_BUCKET` にデプロイしたバケットの名前を書くと、手元のサーバーが本物の Polly と S3 を使います。新しい文章を送るたびに課金されます。この切り替えは試していません。

<<< @/examples/57-polly/src/dev.ts{dev}

テストと型検査は、ほかの章と同じです。

```bash
vp run test:unit
vp run typecheck
```

手元で再現していないものは、Polly の声、合成にかかる時間、文字の数え方、S3 が条件付きの書き込みを実際にどう裁くか、IAM、ライフサイクルルールです。同時に届いたリクエストのテストは、条件付きの書き込みを「無ければ作る」「変わっていなければ置き換える」の 2 つの規則だけで真似たメモリの中のバケットに対して動いています。
