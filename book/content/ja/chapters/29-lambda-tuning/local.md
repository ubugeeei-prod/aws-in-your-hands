# 29 Lambda Tuning: 手元で動かす

## 手元で測る

<!-- section: 29.local -->

[ここまでのページ](/ja/chapters/29-lambda-tuning/more.md)で書いたコードを、AWS を使わずに動かします。手元で測れるのは、バンドルの大きさと、そのバンドルを Node.js が読み込む時間です。認証情報も、課金も要りません。

```bash
vp run tune:bundle
```

このタスクは、同じ関数を 5 通りにバンドルして `examples/29-lambda-tuning/dist/` に書き出し、それぞれを新しい Node.js のプロセスで読み込んで時間を測ります。新しい実行環境が最初にすることを、手元でまねているわけです。

<<< @/examples/29-lambda-tuning/src/bundle/measure.ts{load}

測っているのは `import` にかかった時間だけで、Node.js そのものの起動は入っていません。読み込みは 5 通りを 1 回ずつ順番に繰り返します。マシンがほかの仕事で忙しくなっても、その影響が 5 通りに同じようにかかるようにするためです。

手元の Mac（Apple silicon、Node.js 24.21.0）で、31 回ずつ読み込ませた結果は次のとおりでした。

```text
node v24.21.0, darwin arm64, 31 loads each

variant                    bytes        gzip   load, median    fastest
as-chapter-05         1350.2 KiB   236.5 KiB        80.8 ms    58.9 ms
module-first           921.6 KiB   170.0 KiB        68.8 ms    46.2 ms
minified               350.6 KiB   107.4 KiB        64.5 ms    47.1 ms
aggregated-client      396.2 KiB   119.0 KiB        72.9 ms    51.6 ms
sdk-external            21.9 KiB     7.4 KiB        80.4 ms    56.7 ms
```

バイト数は、何度実行しても同じです。時間はそうではありません。このときは同じマシンでほかの作業が動いていて、続けて 3 回実行すると、中央値は回によって 2〜3 割動きました。3 回とも変わらなかったのは順番で、ミニファイしたバンドルがいちばん速く、05章の設定のままのバンドルと、SDK を外したバンドルがいちばん遅い、という並びでした。マシンが静かなときに 15 回ずつで測り直すと、中央値は 47.8 ミリ秒から 58.5 ミリ秒の範囲に収まり、差はもっと小さくなりました。

この表から読み取れるのは、次の 2 つまでです。

- バンドルを 4 分の 1 にしても、読み込みの時間は 2 割ほどしか縮んでいません。バイト数と時間は比例しません
- SDK を外したバンドルは、いちばん小さいのに速くありません。SDK を `node_modules` の多数のファイルから読むことになるからです

読み取れないことのほうが多くあります。Lambda は、読み込みの前にコードをダウンロードして展開します。バンドルの大きさが効くはずのその部分を、この計測は含んでいません。CPU も違います。256 MB の関数に割り当てられる CPU は vCPU の 7 分の 1 ほどなので、同じ読み込みに手元より長くかかると考えるのが自然ですが、測っていません。SDK を外した場合に Lambda が読むのは、ランタイムに入っている SDK で、手元の `node_modules` とは置き方も版も違います。

**手元の時間は、Lambda の時間ではありません。** この表は、5 通りを 1 台のマシンの上で比べたもので、AWS で何ミリ秒になるかは教えてくれません。それを知るには、[デプロイして測る](/ja/chapters/29-lambda-tuning/deploy.md)しかありません。

表の後には、バンドルごとに、どのパッケージが何 KiB を占めているかが続きます。予算を超えたときに見るのはここです。最後の行は、デプロイするバンドルが予算に収まっているかどうかで、超えていればタスクは失敗します。

残りの 2 つのタスクは、計算と集計です。

```bash
vp run tune:plan
vp run tune:report:sample
```

`tune:plan` は、タイムアウトの並び、メモリの設定ごとの料金、provisioned concurrency の料金を表示します。`--memory 512 --ms 30 --requests 5000000 --provisioned 2` のように、自分の関数の数字を渡せます。単価は `data/pricing/` から読みます。`tune:report:sample` は、[最初のページ](/ja/chapters/29-lambda-tuning.md)で見た集計です。

テストは次のコマンドで動かします。

```bash
vp run test:unit
```

テストが確かめているのは、REPORT 行と `platform.report` の読み取り、課金時間の計算、同時実行数の模型、タイムアウトの並び、応答しないテーブルに対する締め切り、バンドルの予算、そしてスタックのテンプレートです。バンドルのテストは、時間については何も主張しません。回によって動く数字をテストにすると、理由なく落ちるテストになるからです。

手元で再現しないものは次のとおりです。

- 実行環境そのもの。コードのダウンロード、実行環境の起動、凍結と解凍、数時間ごとの入れ替えは再現しません
- メモリの設定と CPU の割り当て。手元のプロセスは、マシンの CPU をそのまま使います
- 同時実行数の上限とスロットリング。模型は規則を写したもので、Lambda の動きを測ったものではありません
- Lambda が書く REPORT 行。手元にあるのは、公式ドキュメントから写した行だけです
- 関数のタイムアウト。締め切りのテストは、シグナルを手で発火させています
