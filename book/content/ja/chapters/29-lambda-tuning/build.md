# 29 Lambda Tuning: しくみと実装

[前のページ](/ja/chapters/29-lambda-tuning.md)で、Init フェーズと Invoke フェーズの境目と、REPORT 行の読み方を見ました。このページでは、費用のかからない順に、バンドル、ハンドラーの外のコード、メモリを扱います。

## バンドルを小さくする

<!-- section: 29.bundle -->

新しい実行環境は、まず関数のコードを取ってきて展開し、それから読み込みます。公式ドキュメントは、初期化の遅さの要因として、パッケージの大きさ、初期化のコードの量、ライブラリ自身の準備の 3 つを挙げています。バンドルを小さくすると、このうち最初の 2 つが減ります。

何が大きいのかは、測ればわかります。`vp run tune:bundle` は、同じ関数を 5 通りにバンドルして、バイト数とパッケージごとの内訳を表示します。

<<< @/examples/29-lambda-tuning/src/bundle/variants.ts{variants}

05章と 19章の設定でバンドルすると 1,350.2 KiB で、そのうち自分たちのコードは、Valibot を合わせても 50 KiB に届きません。残りはほとんど AWS SDK です。小さくする余地は SDK の側にあります。

### main ではなく module を辿らせる

いちばん効いたのは、esbuild の `mainFields` でした。パッケージの `package.json` には、入口のファイルを指す項目がいくつかあります。`main` は Node.js 向けで、中身はたいてい CommonJS です。`module` はバンドラー向けで、中身は ES modules です。

esbuild は、Node.js 向けにバンドルするとき、`main` を先に見ます。esbuild のドキュメントは、この既定では `module` と `main` の両方を持つパッケージに tree shaking がおそらく効かない、と書いています。tree shaking は、どこからも使われていないコードを落とす処理で、ES modules にしか効かないからです。AWS SDK はまさに両方を持つパッケージなので、既定のままだと CommonJS 版が丸ごと入ります。

<<< @/examples/29-lambda-tuning/src/bundle/variants.ts{shared}

`NodejsFunction` は、`mainFields` を指定したときにだけ esbuild に渡します。固定している版の aws-cdk-lib のソースで確かめました。そこで、スタックの側で指定します。

<<< @/examples/29-lambda-tuning/infra/lib/tuning-stack.ts{bundling}

`module` を先にするだけで、バンドルは 1,350.2 KiB から 921.6 KiB になりました。SDK の各パッケージから、このアプリが使わないコードが落ちたぶんです。`@aws-sdk/client-dynamodb` だけで、189.9 KiB が 56.6 KiB になりました。

esbuild が既定を `main` にしているのは、`module` にブラウザ向けのコードを置いているパッケージがあるからです。順番を変えるのは、安全だとわかっている場合に限る、とドキュメントにあります。そこでテストでは、できあがったバンドルを素の Node.js で読み込み、DynamoDB の代役に `GetItem` を 1 回送らせて、SDK が実際に動くことを確かめています。依存を足したときには、この検査が壊れていないことを見てください。

### ミニファイする

次に効いたのはミニファイで、921.6 KiB が 350.6 KiB になりました。gzip で圧縮した大きさでは、170.0 KiB が 107.4 KiB です。デプロイパッケージは zip なので、ダウンロードされる量に近いのは圧縮後の数字です。

代わりに失うものがあります。ミニファイすると、関数や変数の名前が短い文字に変わるので、ログに出るスタックトレースが読みにくくなります。ソースマップを一緒に配って Node.js に読ませれば戻せますが、そのぶんパッケージは大きくなります。この章では付けていません。19章のログにはリクエスト ID と経路が入っているので、まずそこから辿り、どうしても行番号が要るときは、同じコミットをミニファイなしでバンドルして照らし合わせます。

### クライアントの書き方

SDK のクライアントには、2 通りの書き方があります。05章が使っているのは、`DynamoDBClient` を作り、操作ごとのコマンド（`GetCommand` など）を `send` に渡す書き方です。もう 1 つは、`DynamoDB` や `DynamoDBDocument` のように、すべての操作をメソッドとして持つクラスを使う書き方です。

後者は、クラスがすべての操作を抱えているので、使っていない操作をバンドラーが落とせません。比べるために、その書き方の入口を 1 つ用意しました。デプロイはしません。

<<< @/examples/29-lambda-tuning/measure/aggregated.ts

同じ設定でバンドルすると 396.2 KiB で、45.6 KiB 増えます。`@aws-sdk/client-dynamodb` の取り分は、30.0 KiB から 63.6 KiB になりました。DynamoDB だけならこの程度ですが、操作の多いサービスほど差は開きます。

### SDK を入れないという選択

`NodejsFunction` は、`externalModules` を指定しないと、`@aws-sdk/*` をバンドルから外します。Lambda の Node.js ランタイムには SDK が最初から入っているので、それを使わせるためです。こうするとバンドルは 21.9 KiB まで小さくなります。

05章はこれを選ばず、`externalModules: []` で SDK をバンドルに入れました。この章も同じです。理由は 2 つあります。

1 つは版です。公式ドキュメントによると、ランタイムに入っている SDK は、ランタイムの版とリージョンで決まる特定のマイナーバージョンで、最新ではありません。Lambda が定期的に更新します。バンドルに入れておけば、動くのは `pnpm-lock.yaml` に書かれた版です。公式ドキュメントも、依存を完全に管理したいなら、すべてデプロイパッケージに入れるよう勧めています。

もう 1 つは読み込み方です。公式ドキュメントは、依存を `node_modules` のまま配るよりも、バンドルするほうを勧めています。ファイルを読む回数が減るからです。ランタイムの SDK を Lambda の上で読み込むのにどれだけかかるかは、この章では測っていません。手元の計測では、SDK を外したバンドルがいちばん遅く読み込まれましたが、これは `node_modules` から読んだ場合の数字で、Lambda のランタイムとは置き方が違います。[手元で動かす](/ja/chapters/29-lambda-tuning/local.md)に結果を載せました。

### 大きくなったら落ちるテスト

バンドルは、依存を 1 つ足しただけで倍になることがあります。気づくのがコールドスタートが遅くなってからでは遅いので、上限を決めてテストにします。

<<< @/examples/29-lambda-tuning/src/bundle/budget.ts{budget}

<<< @/examples/29-lambda-tuning/src/bundle/budget.ts{check}

いまのバンドルは 358,983 バイト、圧縮して 109,933 バイトなので、1 割ほどの余裕があります。テストが見ているのは、CDK が synth のときに作る、実際にアップロードされるファイルです。`tune:bundle` が「デプロイされるもの」として測っているバンドルと 1 バイトも違わないことも、テストで確かめています。

上限を超えたときにするのは、数字を上げることではなく、何が増えたかを `vp run tune:bundle` の内訳で見ることです。増えた理由に納得できたら、そのとき数字を上げます。

Lambda 自身の上限は、API から直接アップロードする ZIP で 50 MB、展開後で 250 MB です。この関数からは遠いので、上限は Lambda の制約ではなく、自分たちで決めた歯止めです。

## ハンドラーの外に置くもの

<!-- section: 29.init -->

ハンドラーの外に書いたコードは、実行環境ごとに 1 回だけ走り、作ったものは次の呼び出しまで残ります。公式ドキュメントは、SDK のクライアントとデータベースの接続をここで作るよう勧めています。

<<< @/examples/29-lambda-tuning/src/compose.ts{compose}

クライアントを外に置くと、2 件目からの呼び出しが速くなります。SDK は TCP の接続を使い回すので、DynamoDB への接続と TLS の確立は、実行環境の最初の呼び出しのときだけで済みます。SDK のドキュメントは、DynamoDB のような短い操作では、接続の確立のほうが操作そのものより長くかかることがある、と書いています。ハンドラーの中で毎回クライアントを作ると、この接続を毎回捨てることになります。

外に置いてはいけないものもあります。利用者のデータ、イベントの中身、認証情報のような、リクエストに属する値です。実行環境は次の利用者のリクエストにも使われるので、外側の変数に残した値は、次の呼び出しから見えてしまいます。外に置くのは、どのリクエストにも共通のものだけです。

外に置くコードには費用もあります。コールドスタートのたびに走り、その時間は課金されます。provisioned concurrency を使うと、実行環境を用意する時点で走り、リクエストが来なくても課金されます。そこで公式ドキュメントは、一部の経路でしか使わないものは、必要になるまで読み込みを遅らせるよう勧めています。

このアプリには、遅らせる対象がありません。どの経路も、同じ検証と同じテーブルを使うからです。07章の添付や 17章の要約のように、一部の経路だけが別の SDK クライアントを使う関数を 1 つにまとめたときには、そのクライアントを `await import()` で読み込むか、関数を分けるかを考えます。

### ES modules と最初の await

04章から、バンドルの形式は ES modules です。公式ドキュメントは ES modules を勧めていて、その理由は、ファイルの最上位で `await` を書けることです。設定を外から取ってくるような非同期の初期化を、Init フェーズのうちに終わらせられます。終わらせないまま Init を抜けると、残りは最初の呼び出しの途中で走ることになります。

この章の関数には、非同期の初期化がありません。環境変数の検証は同期で終わり、SDK が DynamoDB に接続するのは最初の `send` のときです。そのため、最初の呼び出しの `Duration` には接続の時間が入ります。初期化のうちに 1 回呼んでおけば Init に移せますが、オンデマンドの関数では、同じ時間が Init に移るだけで、利用者が待つ長さは変わりません。

SnapStart は、初期化を終えた実行環境のスナップショットから再開する機能です。対応しているのは Java、Python、.NET で、Node.js のランタイムは対象外です（2026-10-13 時点）。

## メモリを決める

<!-- section: 29.memory -->

メモリは 128 MB から 10,240 MB まで、1 MB 刻みで選べます。この設定は名前より広い意味を持っていて、Lambda は CPU をメモリに比例して割り当てます。1,769 MB で vCPU 1 つぶんです。256 MB の関数が使えるのは、計算上はその 7 分の 1 ほどになります。

料金もメモリに比例します。実行時間の料金は、メモリ（GB）に課金時間（秒）を掛けた GB 秒に単価を掛けたものです。

<<< @/examples/29-lambda-tuning/src/cost-inputs.ts{billed}

メモリを 2 倍にすると、1 ミリ秒あたりの単価も 2 倍になります。同時に CPU も 2 倍になるので、実行時間が半分になれば料金は変わらず、応答だけが速くなります。半分より短くなれば安くなり、そこまで縮まなければ高くなります。

<<< @/examples/29-lambda-tuning/src/cost-inputs.ts{memory}

`vp run tune:plan` は、いまの設定と実行時間を渡すと、ほかの設定での料金と、料金が同じになる実行時間を表示します。メモリの部分は次のとおりです。

```text
Memory, for 1000000 invocations a month (list price, USD, ap-northeast-1, arm64)
  now: 256 MB and 50 ms billed per invocation
      MB   if still that long   costs the same at
     128                 0.28            100.0 ms
     256                 0.37             50.0 ms
     512                 0.53             25.0 ms
    1024                 0.87             12.5 ms
    1769                 1.35              7.2 ms
    3008                 2.16              4.3 ms
  Whether the duration falls with more memory is measured in AWS, not computed here.
```

2 列目は、実行時間が 50 ミリ秒のまま変わらなかった場合の月額です。3 列目は、いまと同じ料金になる実行時間で、たとえば 512 MB にして 25 ミリ秒より短くなるなら得をします。リクエスト料金（100 万回で 0.20）はメモリに関係なくかかるので、2 列目は倍々にはなりません。

実行時間が縮むかどうかは、関数が何に時間を使っているかで決まります。JSON の解析や暗号の計算のように CPU を使っている時間は、CPU が増えれば縮みます。DynamoDB の応答を待っている時間は、CPU を増やしても縮みません。ノートの API の時間の大半は後者のはずなので、メモリを増やしても料金が上がるだけになる可能性があります。「はず」と書いたのは、測っていないからです。

初期化は事情が違います。バンドルを読み込んで評価するのは CPU の仕事なので、メモリを増やすと `Init Duration` が縮むことが期待できます。公式ドキュメントも、ライブラリを読み込む関数はメモリを増やすと速くなることがある、と書いています。これも、この章では測っていません。

測り方は 2 つあります。1 つは、この章のスタックを `-c memorySize=512` のように値を変えてデプロイし直し、同じリクエストを送って REPORT を比べる方法です。手順は[デプロイのページ](/ja/chapters/29-lambda-tuning/deploy.md)にあります。もう 1 つは、公式ドキュメントが紹介している AWS Lambda Power Tuning です。Step Functions のステートマシンが、関数を複数のメモリの設定で実際に呼び出して、設定ごとの料金と速さを出します。あなたのアカウントで関数を本当に呼ぶ道具なので、料金がかかり、書き込みのある関数では副作用も起きます。この章では使っていません。

メモリを決めるときに見る数字は、もう 1 つあります。REPORT の `Max Memory Used` が `Memory Size` に近ければ、足りなくなる手前です。メモリを使い切ると、その呼び出しは失敗します。

アーキテクチャは 04章から arm64 です。東京リージョンの実行時間の単価は、arm64 が 1 GB 秒あたり 0.0000133334、x86 が 0.0000166667 で、arm64 のほうが 2 割安くなっています。
