# 29 Lambda Tuning: 実装のつづき

[前のページ](/ja/chapters/29-lambda-tuning/build.md)では、1 つの実行環境の中で変えられるものを扱いました。このページでは、実行環境がいくつ要るのかを決める同時実行数と、呼び出し元に合わせたタイムアウトを扱い、最後にレイヤーと extension に触れます。

## 同時実行数

<!-- section: 29.concurrency -->

Lambda の同時実行数（concurrency）は、その瞬間に処理中のリクエストの数です。1 つの実行環境は 1 度に 1 件しか処理しないので、同時実行数は、同時に要る実行環境の数でもあります。毎秒のリクエスト数とは別の量で、公式ドキュメントは次の式で見積もるよう書いています。

<<< @/examples/29-lambda-tuning/src/concurrency.ts{formula}

毎秒 100 件を 1 件 0.5 秒で処理するなら、同時実行数は 50 です。同じ毎秒 100 件でも、1 件に 1 秒かかれば 100 になります。リクエストが増えなくても、処理が遅くなるだけで実行環境は増えるわけです。

このスタックの API は、ステージのスロットリングで毎秒 10 件までしか受けません。1 件が 50 ミリ秒なら、同時実行数は平均で 0.5 です。ところが、DynamoDB の応答が止まって、どのリクエストも 9 秒の締め切りまで待つようになると、同じ毎秒 10 件で 90 になります。下流が遅くなったときに実行環境が一気に増えるのは、Lambda の障害でよく見る形です。

この関係を手元で確かめるために、小さな模型を書きました。

<<< @/examples/29-lambda-tuning/src/concurrency.ts{simulate}

模型が従っているのは、公式ドキュメントに書かれた規則だけです。空いている実行環境があればそれを使い、無ければ新しく作り、上限に達していれば断ります。初期化の間も実行環境は塞がっているので、最初のリクエストが 300 ミリ秒の初期化を待っている間に次が来ると、もう 1 つコールドスタートが起きます。テストでは、同じ到着の並びでもハンドラーが遅いと実行環境が増えること、予約済み同時実行数を超えたぶんが断られること、provisioned concurrency を超えたぶんがコールドスタートになることを固定しています。

模型が再現していないことも 2 つあります。使われない実行環境がいつ片付けられるかと、実行環境を増やせる速さの上限です。

### アカウントの上限

同時実行数には、アカウントとリージョンごとの上限があります。既定は 1,000 で、そのリージョンのすべての関数で分け合います。新しいアカウントはこれより低い値から始まり、利用に応じて自動で引き上げられる、と公式ドキュメントにあります。低い値がいくつなのかは書かれていません。自分のアカウントの値は、次のコマンドか Service Quotas で確かめます。

```bash
aws lambda get-account-settings
```

上限はほかに 2 つあります。1 つは毎秒のリクエスト数で、同時実行数の 10 倍までです。1 件が 100 ミリ秒より短い関数では、同時実行数より先にこちらに当たります。もう 1 つは増やせる速さで、関数ごとに、10 秒あたり実行環境 1,000 個までです（どちらも 2026-10-13 に読んだ値です）。

どの上限に当たっても、Lambda はリクエストをスロットリングし、429 で断ります。断られた呼び出しは、`Invocations` にも `Errors` にも数えられず、`Throttles` というメトリクスに出ます。そのとき API Gateway が利用者に返すステータスは、この章では確かめていません。

### 予約済み同時実行数

予約済み同時実行数（reserved concurrency）は、関数に同時実行数を取り分ける設定です。取り分けた数はその関数の上限になり、同時に、ほかの関数に使われない下限にもなります。料金はかかりません。

使いどころは 2 つあります。1 つは歯止めで、下流を守るためと、料金を守るためです。先ほどの例なら、5 を予約しておけば、DynamoDB が止まっても実行環境は 5 つまでしか増えません。もう 1 つは確保で、ほかの関数がアカウントの枠を使い切っても、大事な関数が動けるようにします。0 を指定すると、その関数は 1 件も処理しなくなります。暴走した関数を止めるスイッチとして、公式ドキュメントが挙げている使い方です。

予約できるのは、アカウントの上限から 100 を引いた数までです。予約のない関数のために、Lambda が必ず 100 を残すからです。そのため、上限が 100 以下のアカウントでは、1 つも予約できません。

<<< @/examples/29-lambda-tuning/infra/bin/app.ts{context}

このスタックが予約を既定にせず、`-c reservedConcurrency=5` と渡されたときだけ付けるのは、このためです。17章と 21章も同じ扱いにしています。

### provisioned concurrency

予約済み同時実行数は数を取り分けるだけで、実行環境は用意しません。あらかじめ初期化した実行環境を持っておくのが、provisioned concurrency です。指定した数までは、リクエストは初期化を待ちません。

<<< @/examples/29-lambda-tuning/infra/lib/tuning-stack.ts{provisioned}

provisioned concurrency は `$LATEST` には付けられず、バージョンかエイリアスに付けます。呼び出す側もそのエイリアスを指していなければ、用意した実行環境は使われません。そこで、指定があるときは API の統合先をエイリアスに切り替えています。バージョンとエイリアスそのものは 20章で扱いました。

知っておくことが 4 つあります。

- 指定した数を超えたリクエストは断られず、ふつうのオンデマンドの実行環境に回ります。そこではコールドスタートが起きます。超えた回数は `ProvisionedConcurrencySpilloverInvocations` に出ます
- 予約済み同時実行数と併用するなら、provisioned はそれ以下でなければなりません
- provisioned でもコールドスタートが無くなるとは限りません。Lambda が実行環境をリセットしたときには起こりうる、と公式ドキュメントにあります
- 初期化のコードは、実行環境を用意するときと、Lambda が実行環境を入れ替えるときに走り、リクエストが 1 件も来なくても課金されます

そして、時間で課金されます。**provisioned concurrency は、置いてあるだけで料金がかかります。** 256 MB で 1 つなら、月に 2.83 です。1,024 MB で 2 つなら 22.64 になります。Lambda の無料枠は、provisioned concurrency を有効にした関数には適用されません。

使ったぶんの単価も変わります。provisioned の実行環境で動いた時間は、オンデマンドより安い単価で課金されます。この 2 つを合わせて、どれだけ使えば元が取れるかを計算します。

<<< @/examples/29-lambda-tuning/src/cost-inputs.ts{provisioned}

東京リージョンの arm64 の単価は、オンデマンドが 1 GB 秒あたり 0.0000133334、provisioned の確保が 0.0000043068、provisioned で動いた時間が 0.0000100492 です。確保と実行を足すと 0.0000143560 で、オンデマンドを上回ります。1 か月のあいだ休みなく使い切っても、オンデマンドより 8% ほど高い計算です。元が取れる稼働率は 131% で、そのような月はありません。x86 でも同じ結果でした。

つまり東京リージョンでは、provisioned concurrency を料金の節約のために選ぶ理由が、単価の上ではありません。買っているのは応答の速さだけです。必要な時間帯だけ有効にする方法として Application Auto Scaling が公式ドキュメントに挙がっていますが、この章では扱っていません。

## タイムアウトの並び

<!-- section: 29.timeouts -->

リクエストは、いくつもの場所を順に通り、それぞれの場所に待ち時間の上限があります。外側が先に諦めると、内側は誰も受け取らない仕事を続けることになります。

```figure
caption: 外側ほど長く待つように並べる。内側が先に諦めれば、外側には形の整った返事が届く
node client: クライアント
node api: API Gateway HTTP API | 最長 30 秒、変更不可
node fn: Lambda 関数 | タイムアウト 10 秒
node handler: ハンドラーの締め切り | 9 秒
node sdk: SDK の 1 回の試行 | 接続 1 秒 + 応答 2 秒
node table: DynamoDB
edge client -> api
edge api -> fn
edge fn -> handler
edge handler -> sdk
edge sdk -> table
```

<<< @/examples/29-lambda-tuning/src/timeouts.ts{values}

いちばん外の値は動かせません。HTTP API が統合先を待つのは最長 30 秒で、引き上げられないクォータです。関数のタイムアウトは最長 900 秒まで設定できますが、30 秒以上にしても、API Gateway が先に諦めて利用者にエラーを返します。その後に関数が何をしても、受け取る相手はいません。諦められた関数がいつまで動いて課金されるのかは、この章では確かめていません。どちらにしても関数は 30 秒より短くしておくもので、04章から 10 秒にしてあります。

内側で起きることには、もう少し説明が要ります。関数がタイムアウトに達すると、Lambda は実行環境ごと止めます。アプリは返事を書けず、19章のリクエストの行も出ません。残るのは Lambda 自身が書く行だけで、REPORT 行には `Status: timeout` が付きます。止められた実行環境はリセットされ、次の呼び出しは初期化からやり直しになります。

これを避けるには、関数のタイムアウトより先に、アプリ自身が諦める必要があります。ところが[前のページ](/ja/chapters/29-lambda-tuning/build.md)で見たとおり、SDK のタイムアウトは既定では無効です。応答しないテーブルを前にすると、05章のアプリは 10 秒待って、Lambda に止められます。

そこで 2 つの手当てをしました。1 つは SDK のタイムアウトで、接続に 1 秒、応答に 2 秒、試行は 2 回までです。もう 1 つは、ハンドラー全体の締め切りです。

<<< @/examples/29-lambda-tuning/src/deadline.ts{deadline}

Lambda は、残り時間を `context.getRemainingTimeInMillis()` で教えてくれます。ハンドラーはそこから 1 秒を引いた長さの `AbortSignal` を作り、その中でアプリを呼びます。引いた 1 秒は、エラーのレスポンスとログの行を書くための時間です。

シグナルは、SDK の呼び出しまで届けなければ意味がありません。05章のリポジトリを書き換えずに済むよう、クライアントのほうを包みました。

<<< @/examples/29-lambda-tuning/src/deadline.ts{client}

`AsyncLocalStorage` を使っているのは、リクエストごとに別のシグナルを持たせるためです。Lambda のふつうの関数は 1 度に 1 件しか処理しないので、変数 1 つでも足りますが、手元のサーバーは複数のリクエストを同時に処理します。1 件の締め切りが別の 1 件を止めないことは、テストで確かめています。

締め切りが来ると、SDK の呼び出しは例外で終わります。05章のアプリはそれを捕まえ、いつもの形の 500 を返し、スタックトレースをログに書きます。利用者には request ID の付いた返事が届き、ログからは何が止まったのかがわかります。意味としては 503 のほうが近いのですが、05章の契約にその区別が無いので、契約は変えていません。

並びが崩れていないことは、関数で検査します。

<<< @/examples/29-lambda-tuning/src/timeouts.ts{http}

検査しているのは 4 つです。関数が呼び出し元より先に終わること、返事を書く時間が残してあること、SDK のタイムアウトが無効のままでないこと、SDK の 1 回の試行が締め切りに収まることです。スタックのテストは、テンプレートに出た関数のタイムアウトをこの検査に通します。再試行のあいだの待ち時間は計算に入れていません。全体を止めるのは締め切りの役目です。再試行そのものの設計は [32章](/ja/chapters/32-limits.md)で扱います。

### キューを読む関数

呼び出し元がキューの場合は、比べる相手が変わります。08章のワーカーのように SQS を読む関数では、関数のタイムアウトと、キューの可視性タイムアウトを並べます。

<<< @/examples/29-lambda-tuning/src/timeouts.ts{queue}

公式ドキュメントは、可視性タイムアウトを関数のタイムアウトの 6 倍以上にするよう勧めています。バッチウィンドウを使うなら、その秒数も足します。関数がスロットリングされたときに、Lambda が再試行する時間を残すためです。関数のタイムアウトのほうが長い組み合わせは、イベントソースマッピングを作る時点で断られます。08章は、30 秒の関数に 180 秒の可視性タイムアウトを付けていて、この規則のとおりです。

## レイヤーと extension

<!-- section: 29.layers -->

レイヤー（layer）は、関数に追加で載せる .zip です。中身は実行環境の `/opt` に展開されます。公式ドキュメントが挙げる使いどころは、依存を複数の関数で共有すること、デプロイパッケージを小さく保つこと、ランタイムに入っている SDK の版を固定することです。1 つの関数に付けられるのは 5 つまでで、展開後の 250 MB の上限には、レイヤーのぶんも数えられます。

この章の関数は、レイヤーを使いません。依存はすべて 1 つのファイルにバンドルしてあり、共有する相手もいないからです。バンドルした Node.js の関数にとって、レイヤーは読み込むファイルを増やすだけになります。レイヤーが要るのは、自分でバンドルできないものを載せるときです。19章で任意で付けた OpenTelemetry のレイヤーがその例でした。

extension は、関数と同じ実行環境で動く別のプログラムです。監視やセキュリティの道具が、レイヤーとして配っています。チューニングの観点で知っておくことは 3 つあります。

- extension は、関数と CPU、メモリ、ストレージを分け合います
- すべての extension の初期化が終わるまで、Lambda はハンドラーを呼びません。初期化の遅い extension は、コールドスタートをそのぶん遅くします
- extension が動いた時間も課金されます。ハンドラーが返った後に extension が使った時間は、`PostRuntimeExtensionsDuration` というメトリクスに出ます

レイヤーや extension を足すときは、足す前と後で REPORT を比べてください。公式ドキュメントも、影響を知るには、付けた版と付けない版を並べて動かすよう勧めています。
