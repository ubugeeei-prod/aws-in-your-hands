# 68 Nitro: しくみと実装

[前のページ](/ja/chapters/68-nitro.md)で、Nitro System の部品を見ました。このページでは、その設計がインスタンスを使う側に出てくる 3 か所を順に扱います。ボリュームのデバイス名、インスタンスタイプの名前、Graviton です。Nitro Enclaves は[次のページ](/ja/chapters/68-nitro/more.md)にあります。

## デバイス名は起動のたびに変わりうる

<!-- section: 68.devices -->

23章では、データボリュームを `/dev/sdf` という名前でインスタンスに付けました。ところが、EBS のドキュメントにある `lsblk` の実行例には、`sdf` という名前のディスクは出てきません。出てくるのは `nvme0n1` と `nvme1n1` です。

資料に書いてあることから並べます。Nitro System のインスタンスでは、EBS ボリュームは NVMe のブロックデバイスとして現れます。ホワイトペーパーによれば、ボリュームを付けると、Nitro Card for EBS が NVMe のデバイスを 1 つ用意し、ハイパーバイザーがインスタンスにホットプラグのイベントを送ります。OS の NVMe ドライバーは、デバイスが応答した順に `/dev/nvme0n1`、`/dev/nvme1n1` と名前を付けます。EBS のドキュメントは、この順序が起動のたびに変わりうること、付けるときに指定した名前とは別の名前になることを明記しています。

指定した `/dev/sdf` が捨てられるわけではありません。その名前は NVMe のコントローラーの情報の中に記録されていて、Amazon Linux は、それを読んで `/dev/sdf` から本当のデバイスへのシンボリックリンクを作る udev のルールを持っています。23章のスクリプトが `/dev/sdf` を待つだけで済んでいるのは、このためです。

ここから言えることが 2 つあります。1 つ目は、23章のスクリプトが Amazon Linux に頼っていることです。ドキュメントは、ほかの OS では挙動が違うかもしれない、と書いています。別のディストリビューションの AMI に替えると、`/dev/sdf` は現れず、スクリプトは 5 分待ってから失敗するはずです。2 つ目は、`/dev/nvme1n1` のような名前をスクリプトに書いてはいけないことです。次の起動では、その名前がルートボリュームを指しているかもしれません。

ドキュメントが勧めているのは、変わらない識別子を使うことです。フォーマットした後なら、ファイルシステムの UUID があります。23章が `/etc/fstab` に UUID を書いたのは、そのためでした。フォーマットする前に使えるのは、ボリューム ID です。EBS ボリュームは、NVMe のシリアル番号として自分のボリューム ID を返します。ハイフンだけが抜けています。


テストの入力は、util-linux のソースを読んで手で書いたものです。インスタンスで `lsblk` を実行して取ったものではありません。

ネットワークの側は、読者がすることがありません。Nitro System のインスタンスはネットワークに ENA を使い、Amazon Linux 2023 はそのドライバーを最初から持っている、とドキュメントにあります。11章で作った VPC のネットワークを実装しているのは Nitro Card for VPC だ、とホワイトペーパーは書いています。セキュリティグループの判定がカードのどこで行われるかまでは、書いてありません。

## インスタンスタイプの名前を読む

<!-- section: 68.names -->

`t4g.micro` や `c6g.large` という名前には、決まった並びがあります。EC2 のドキュメントの命名規則のページによれば、先頭がシリーズ、次が世代、その後ろがオプション、ピリオドの後ろがサイズです。

- シリーズ: 何に向けた種類か。`t` はバースト可能、`m` は汎用、`c` はコンピューティング最適化、`r` はメモリ最適化
- 世代: 数字が大きいほど新しい
- オプション: `a` は AMD、`g` は AWS Graviton、`i` は Intel のプロセッサー。`d` はインスタンスストア、`n` はネットワークと EBS の強化、`b` はブロックストレージの強化、`z` は高い CPU 周波数、`flex` は Flex インスタンス
- サイズ: `micro`、`large`、`4xlarge` など。`metal` はベアメタル

この表を、そのままコードにしました。

<<< @/examples/68-nitro/src/instance-type.ts{decode}

```bash
vp run nitro:names
vp run nitro:names r7iz.2xlarge
```

実行すると、名前を部品ごとに表示します。次は、この章の `c6g.large` と、ベアメタルの `c7gn.metal` の部分です。

```text
c6g.large
  series      c: Compute optimized
  generation  6
  processor   g: AWS Graviton processors
  size        large
  arch        arm64

c7gn.metal
  series      c: Compute optimized
  generation  7
  processor   g: AWS Graviton processors
  option      n: Network and EBS optimized
  size        metal (bare metal: no hypervisor)
  arch        arm64
```

命名規則のページに書いていないこともあります。オプションの文字の順序は書いてありません。プロセッサーの文字が先頭に来る、というのは、ドキュメントに出てくる名前を見てこのコードが置いた仮定です。`m5.large` のようにプロセッサーの文字が無い名前が何を意味するかも、書いてありません。`gr6f` の `gr` や `f`、`dl1` の `dl` は、2026-10-13 に読んだ時点で一覧にありませんでした。このコードは、一覧に無い部品を「ページに無い」と表示し、推測しません。

名前からわからないことは、もっとあります。vCPU の数、メモリの大きさ、コアあたりのスレッドの数、Nitro Enclaves に対応しているか、どのリージョンで使えるかは、名前には書かれていません。インスタンスタイプのガイドの仕様の表で調べます。

この本の用途で選ぶなら、見る場所は 3 つです。

シリーズは、メモリと vCPU の比で決まります。仕様の表では、`c6g.large` が 2 vCPU に 4 GiB、`m6g.large` が 2 vCPU に 8 GiB です。Node.js のプロセスが 1 つ動くだけなら、`c` で足ります。`t` は別の種類の選択です。ホワイトペーパーによれば、`t` のインスタンスは CPU とメモリを実際より多く貸し出す前提で作られていて、同じコアをほかのインスタンスと順番に使うことがあります。そのぶん安く、ほとんどの時間は何もしていない 23章のような API に合います。常に CPU を使う仕事には合いません。

世代は、新しいほどプロセッサーが新しく、単価も少し上がります。東京リージョンで `m6g.large` は 1 時間 USD 0.099、`m7g.large` は USD 0.1054 です。同じ仕事がどれだけ速く終わるかは、資料からは出せません。自分の仕事で測るしかありません。

サイズは、仕様の表の vCPU とメモリで選びます。エンクレーブの親にするなら、次の節に書く理由で、Graviton の `large` が下限です。

## Graviton

<!-- section: 68.graviton -->

Graviton は、AWS が設計した Arm のプロセッサーです。ホワイトペーパーによれば、Nitro Card を作っている Annapurna Labs が設計しています。仕様の表では、`t4g`、`m6g`、`c6g` が Graviton2、`m7g` と `c7g` が Graviton3、`m8g` と `c8g` が Graviton4、`m9g` と `c9g` が Graviton5 です（2026-10-13 時点）。Lambda の arm64 は Graviton2 だと Lambda のドキュメントにあります。Fargate の arm64 は Graviton だと書いてあるだけで、世代は書いてありません。

この本は、04章の Lambda、12章の Fargate、23章のインスタンスのすべてで arm64 を既定にしてきました。理由は単価です。

```bash
vp run nitro:prices
```

```text
Unit prices in ap-northeast-1, USD, list price (arm64 / x86)
  EC2 t4g.micro and t3.micro, per hour     0.0108000000 / 0.0136000000  arm64 is 20.6% less
  EC2 c6g.large and c6i.large, per hour    0.0856000000 / 0.1070000000  arm64 is 20.0% less
  Fargate, per vCPU-hour                   0.0404500000 / 0.0505600000  arm64 is 20.0% less
  Fargate, per GB-hour of memory           0.0044200000 / 0.0055300000  arm64 is 20.1% less
  Lambda, per GB-second (first tier)       0.0000133334 / 0.0000166667  arm64 is 20.0% less
```

どの単位でも、arm64 のほうが 2 割ほど安くなっています。AWS の製品ページも、同等の x86 のインスタンスより最大 20% 安い、と書いています。比べている組は、コードに書いてあります。

これは単価の比較で、同じ仕事にかかる料金の比較ではありません。1 単位でこなせる仕事の量がプロセッサーによって違えば、差は 2 割より大きくも小さくもなります。この本は、どちらも測っていません。

単価のほかに、数え方の違いがあります。ホワイトペーパーによれば、x86 のインスタンスは 1 つのコアの 2 つのスレッドを 2 vCPU として渡し、Graviton は 1 つのコアを 1 vCPU として渡します。仕様の表でも、`c6g.large` は 2 vCPU で 2 コア、`c6i.xlarge` は 4 vCPU で 2 コアです。同じ「2 vCPU」でも、中身のコアの数が違います。

この違いが、エンクレーブの親インスタンスの下限を決めています。エンクレーブには、少なくともコア 1 つを丸ごと渡し、親にも 1 つ残します。Nitro Enclaves の FAQ は、コアが 1 つしかないインスタンスでは使えない、と書いています。対応するインスタンスタイプの一覧でも、`large` のある x86 のファミリーはどれも `large` が除かれていて、Graviton は `large` から入っています。その結果、いちばん小さい親は、Graviton なら `c6g.large` の 1 時間 USD 0.0856、同じ世代の x86 なら `c6i.xlarge` の USD 0.214 です。4 割で済みます。

arm64 に移すと、壊れるものがあります。

- **ネイティブのモジュール。** C や Rust で書かれた部分を持つ npm のパッケージは、arm64 用のバイナリが要ります。Lambda のドキュメントは、移す前にすべての依存が arm64 版を出しているか確かめるよう書いています。04章の関数のように JavaScript だけを束ねたものは、何も変えずに動きます
- **コンテナイメージ。** イメージはアーキテクチャごとに別物です。12章で `docker build` に `--platform linux/arm64` を付けたのは、タスク定義が arm64 を指定しているからでした。x86 でビルドしたイメージを arm64 のタスクで動かすことはできません。1 つのタグで両方を配る方法は [52章](/ja/chapters/52-ecr.md)の範囲です
- **Lambda の layer と extension。** これもアーキテクチャごとに用意されている必要がある、と Lambda のドキュメントにあります
- **ビルドする機械。** CI の機械が x86 なら、arm64 のイメージやバイナリを作る設定が別に要ります
- **OS。** Graviton が対応しているのは Linux だけだ、とドキュメントにあります

x86 を選ぶ理由は、たいていこの一覧のどれかです。arm64 版のない依存が 1 つあれば、それで決まります。
