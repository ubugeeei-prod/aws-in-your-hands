# 68 Nitro: 実装のつづき

[前のページ](/ja/chapters/68-nitro/build.md)までは、Nitro System が読者に見せている面の話でした。このページは、読者が自分で使える仕組みである Nitro Enclaves を扱います。エンクレーブが何で、何を証明でき、KMS がそれをどう使うかを順に見て、最後にノートのアプリの設計とスタックに進みます。

## エンクレーブと、その計測値

<!-- section: 68.enclave -->

エンクレーブは、親インスタンスから vCPU とメモリを切り出して作る仮想マシンです。自分のカーネルを持ち、切り出された vCPU とメモリは、親の OS からは見えなくなります。ドキュメントは、インスタンスどうしを分けているのと同じ Nitro Hypervisor の仕組みで、エンクレーブを親から分けている、と書いています。

エンクレーブに無いものを並べます。外へのネットワーク、永続的なストレージ、SSH のような対話的な入口です。あるのは、親とのあいだの vsock だけです。vsock は仮想マシンとホストをつなぐソケットで、アドレスは CID という番号とポートの組です。親の CID は常に 3 で、最初のエンクレーブは既定で 16 になります。

制約もあります。1 台の親に作れるエンクレーブは 4 つまでで、親を止めるとエンクレーブも終わります。ハイバネーションとは併用できません。FAQ によれば、ベアメタル、バースト可能なタイプ（T3 など）、コアが 1 つしかないインスタンスでは使えません。23章の `t4g.micro` を親にできないのは、このためです。

エンクレーブで動かすものは、エンクレーブイメージファイル（`.eif`）にまとめます。Docker のイメージを `nitro-cli build-enclave` に渡すと、OS とアプリを 1 つにしたファイルができます。このファイルは暗号化されていません。ドキュメントは、秘密をイメージに入れてはいけない、と書いています。秘密は、起動した後で外から受け取ります。そこで、受け取る側が本当にそのイメージから起動したエンクレーブなのかを、渡す側が確かめる手段が要ります。

その手段が、計測値です。`build-enclave` は、イメージファイルと一緒に、SHA-384 のハッシュをいくつか出力します。PCR（platform configuration register）と呼ばれます。

| PCR | 何のハッシュか |
| --- | --- |
| PCR0 | イメージファイル全体 |
| PCR1 | Linux のカーネルと起動用のデータ |
| PCR2 | アプリ |
| PCR3 | 親インスタンスの IAM ロールの ARN |
| PCR4 | 親インスタンスの ID |
| PCR8 | イメージファイルに署名した証明書 |

PCR0 から PCR2 はビルドのときに決まり、PCR8 は署名付きでビルドしたときにだけ出ます。PCR3 と PCR4 はイメージとは無関係で、48 バイトの 0 に ARN やインスタンス ID をつなげたものの SHA-384 だ、とドキュメントにあります。

テストは、ドキュメントに載っている例の ARN とインスタンス ID から、ドキュメントに載っている値と同じハッシュが出ることを確かめています。

エンクレーブは、起動した後で、ハイパーバイザーに文書を 1 つ頼めます。アテステーションドキュメント（attestation document）です。中には、そのエンクレーブの PCR と、エンクレーブが渡した公開鍵が入っていて、全体に AWS の署名が付いています。形式は CBOR で、署名は COSE、署名の鍵は AWS Nitro Attestation PKI という公開された認証局につながります。この文書を頼めるのはエンクレーブの中からだけだ、とドキュメントは書いています。

`--debug-mode` で起動したエンクレーブでは、文書の PCR がすべて 0 になります。デバッグモードでは、親からエンクレーブのコンソールを読めます。そういうエンクレーブの文書はアテステーションに使えない、とドキュメントは書いています。

ここで、3 つを分けておきます。資料に書いてあるのは、親の利用者が root であってもエンクレーブの中には触れない、ということです。そこから言えるのは、この隔離が、インスタンスどうしを分けている隔離と同じものだ、ということです。EC2 に仕事を置いている時点で、読者はすでにその隔離を信じています。エンクレーブは、信じる相手を増やしません。外から確かめられないのは、隔離そのものです。一方で、アテステーションドキュメントの署名は、公開されているルート証明書があれば誰でも検証できます。この仕組みのなかで、AWS の外の人が自分で確かめられる数少ない部分です。

## KMS が鍵を渡す相手を決める

<!-- section: 68.policy -->

KMS は、このアテステーションドキュメントを読めます。`Decrypt` や `GenerateDataKey` のリクエストに、`Recipient` というパラメーターで文書を付けると、KMS は 2 つのことをします。

1 つ目は、返事の宛先を変えることです。KMS は平文を返す代わりに、文書に入っていた公開鍵で平文を暗号化して、`CiphertextForRecipient` というフィールドで返します。`Plaintext` は空になります。開けるのは、対応する秘密鍵を持つエンクレーブだけです。

2 つ目は、文書の中身をポリシーの条件に使えるようにすることです。条件キーは 2 種類あります。`kms:RecipientAttestation:ImageSha384` は PCR0 と比べられ、`kms:RecipientAttestation:PCR<番号>` はその番号の PCR と比べられます。ドキュメントは、文書の付いていないリクエストではこの条件が満たされず、権限は拒否される、と書いています。

エンクレーブは、自分の IAM の身元を持ちません。ドキュメントの手順では、親がインスタンスのロールの一時的な認証情報を IMDSv2 から取り、vsock でエンクレーブに渡します。エンクレーブはその認証情報でリクエストに署名します。KMS から見ると、親が送っても、エンクレーブが送っても、呼び出しているのは同じロールです。違いは、文書が付いているかどうかだけです。

だから、権限はすべてキーポリシーに書きます。

<<< @/examples/68-nitro/src/policy.ts{policy}

ステートメントは 2 つです。

1 つ目は、アカウントに鍵の管理を任せます。任せるのは管理だけで、`kms:Decrypt` も `kms:GenerateDataKey` も入れていません。KMS が既定で作るキーポリシーは、アカウントに `kms:*` を与えます。そうすると、アカウントの中の IAM ポリシーで、条件なしの `Decrypt` を誰にでも許せてしまいます。KMS のドキュメントも、この点に注意を促しています。

2 つ目は、親インスタンスのロールに、データキーを取り出す 2 つの操作を許します。条件は、文書の PCR0 が、指定した計測値と一致することです。計測値が渡されていないときは、このステートメント自体を作りません。

ロールの側には、KMS の権限を何も付けません。鍵と呼び出す側が同じアカウントにあれば、キーポリシーだけで権限を決められる、と KMS のドキュメントにあります。付けないのは、条件の無い許可が IAM の側に紛れ込む余地を無くすためです。

```figure
caption: エンクレーブは文書を付けて Decrypt を呼び、KMS は文書の公開鍵に宛てて答える。親が同じロールで呼んでも、文書が無いので拒否される
type: sequence
actor parent: 親インスタンス | ロール
actor enc: エンクレーブ
actor hv: Hypervisor
actor kms: AWS KMS
step parent -> enc: open (包まれた鍵)
step enc -> hv: attest (公開鍵)
step hv --> enc: 署名付きの文書
step enc -> kms: Decrypt + Recipient
note kms: 署名と PCR0 を確かめる
step kms --> enc: CiphertextForRecipient
note enc: 鍵を開き, ノートを復号
step enc --> parent: ノートの本文
step parent -x kms: Decrypt, 文書なし
```

図では、エンクレーブから KMS への矢印を直接引いています。実際には、エンクレーブにネットワークが無いので、通信は親の上の vsock-proxy を通ります。ドキュメントによれば、TLS のセッションは KMS とエンクレーブのあいだで張られ、親は中身を読めないまま転送します。

## ノートを封印する

<!-- section: 68.design -->

ノートのアプリに足す設計は、エンベロープ暗号化です。ノートごとにデータキーを 1 つ作り、ノートはそのデータキーで、データキーは KMS の鍵で暗号化します。保存するのは、暗号文と、包まれたデータキーです。ふつうのエンベロープ暗号化と違うのは、データキーを作る場所と、包みを解く場所がエンクレーブの中だけ、という点です。

持ち主とノートの ID は、暗号化のときに追加の認証データとして渡しています。暗号文には含まれませんが、開くときに同じ値を渡さないと、復号が失敗します。親が、あるノートの暗号文を別の持ち主のノートとして差し出しても、開きません。データキーは、使い終わったら 0 で埋めます。

守りたい不変条件は、次の 1 文です。**親インスタンスは、平文のデータキーを一度も手にしない。**

この条件が何を言っていないかも、書いておきます。ノートの本文は、親を通ります。利用者からのリクエストを受けるのは親で、封印を頼むときも、開封の結果を受け取るときも、本文は親のメモリにあります。この設計が守るのは鍵です。鍵が親に無ければ、親のディスクやスナップショットを持ち出した人、親のロールの認証情報を盗んで別の場所から KMS を呼んだ人は、保存されたノートを 1 件も読めません。親に入り込んで、動いているエンクレーブに 1 件ずつ開封を頼める人は、読めます。そこまで防ぐには、利用者のトークンの検証をエンクレーブの中で行い、利用者とエンクレーブのあいだを暗号化する必要があります。この章は、そこまで作っていません。

もう 1 つ、作っていないものがあります。このコードをエンクレーブのイメージにする部分です。イメージの中では、vsock で待ち受け、ハイパーバイザーから文書を取り、それを付けて KMS を呼ぶ必要があります。ドキュメントの例は Python で vsock を開き、KMS の呼び出しは AWS が配っている `kmstool_enclave_cli` というコマンドに任せています。Node.js 24 の `net` モジュールのドキュメントには、vsock が出てきません。TypeScript のまま動かす道は確かめられなかったので、この章のコードは `KeyService` の手前までにして、その先はモデルで確かめます（[手元で動かす](/ja/chapters/68-nitro/local.md)）。
