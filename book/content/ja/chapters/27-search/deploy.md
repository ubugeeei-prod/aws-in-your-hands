# 27 Search: デプロイ

[手元で動かした](/ja/chapters/27-search/local.md)検索を AWS にのせます。テーブル、インデックス、索引の関数、検索の関数の順に定義を見てから、デプロイの手順に進みます。この章は AWS に一度もデプロイしていないので、手順は用意したもので、実行した記録ではありません。

## スタック

<!-- section: 27.stack -->

このスタックに、時間で課金されるリソースはありません。NAT Gateway もロードバランサーも、常に動いているコンテナやデータベースもなく、料金はすべて使った分です。

### テーブル

<<< @/examples/27-search/infra/lib/search-stack.ts{table}

05章のテーブルに `stream` を足しただけです。`NEW_AND_OLD_IMAGES` は、変更の前と後の両方のアイテムをレコードに入れる設定です。索引の関数は、変更後のアイテムを埋め込み、変更前のアイテムから消すべきパッセージを求めます。

読み込みの上限は、05章の 150 から 400 に上げています。1 回の検索が所有者のノートを全部読むので、最大の 100 件、約 3 MB を読むと 375 ユニットになるからです。

05章のスタックのテーブルは使いません。ストリームを足すには 05章のスタックを変える必要があり、章ごとに独立して作って消せるという、この本の約束が崩れるからです。実際のアプリでは、ノートのテーブルは 1 つで、そこにストリームを足します。

### ベクトルのバケットとインデックス

<<< @/examples/27-search/infra/lib/search-stack.ts{vectors}

S3 Vectors のリソースは 2 段です。ベクトルバケットの中に、インデックスを作ります。ふつうの S3 のバケットとは別の種類のリソースで、名前はアカウントとリージョンの中で一意であればよく、世界中で一意である必要はありません。公開の設定は常に遮断されていて、外せません。

インデックスの `dimension` は、埋め込みのモデルが返す次元と同じでなければなりません。同じ定数（`EMBEDDING_DIMENSIONS`）を、アダプターとスタックの両方が使っています。データ型、次元、距離の種類は、どれも作ったあとで変えられません。CloudFormation のリファレンスでは、変更するとインデックスが置き換えられます。つまり、中身が消えます。

`aws-cdk-lib` 2.273.0 には、S3 Vectors の L2 コンストラクトがないので、L1 の `CfnVectorBucket` と `CfnIndex` を使っています。固定した版の cdkd（0.296.28）は、ベクトルバケットに専用の実装を持ち、バケットの名前を必須にしています。名前を明示しているのはそのためです。インデックスには専用の実装がなく、Cloud Control API 経由で作られます。この経路でインデックスが作れることは、確かめていません。インデックスの ARN を、リソースの属性から読まずに名前から組み立てているのも、未確認の経路に頼る箇所を減らすためです。

スタックを消すと、インデックスとその中のベクトル、バケットが消えます。ベクトルはテーブルから作り直せるので、練習用としては `DESTROY` で構いません。本番でも、インデックスを残す理由はあまりありません。守るべきなのはテーブルです。

### 索引の関数

<<< @/examples/27-search/infra/lib/search-stack.ts{indexer}

実行ロールが許可するのは、ストリームを読むこと、Titan を呼ぶこと、インデックスにベクトルを書いて消すことです。テーブルそのものを読む権限はありません。ノートの中身は、ストリームのレコードに入って届きます。

ストリームを読む権限は `table.grantStreamRead` で付けています。この中の `dynamodb:ListStreams` だけは、対象が `*` になります。`aws-cdk-lib` の `Table` がそう書いているためで、テストは、`*` を持つステートメントがこの 1 つだけであることを確かめています。このアクションの対象をストリーム 1 本に絞れるかどうかは、確かめていません。

イベントソースマッピングは、ストリームと関数をつなぐ設定です。この章にとって意味のある設定は 5 つあります。

- `startingPosition` の `TRIM_HORIZON` は、ストリームに残っている最も古いレコードから読み始めます。デプロイの途中に書かれたノートを取りこぼさないためです
- `reportBatchItemFailures` は、関数が返した「ここで失敗した」という番号を Lambda に使わせます。付けないと、関数が何を返しても、バッチ全体の成功か失敗かしか伝わりません
- `retryAttempts` は 3 です。既定は「レコードが期限切れになるまで再試行」で、失敗し続けるレコードが 1 件あると、同じシャードの後ろのレコードが最長 24 時間止まります
- `onFailure` は、再試行しても失敗したバッチの情報を SQS のキューに送ります。キューに何が届くのか、レコードそのものなのか位置の情報だけなのかは、この章では確かめていません。どちらにしても、キューにメッセージがあれば、インデックスに反映されていない変更があります。直すには、[作り直し](/ja/chapters/27-search/build.md)を実行します
- `filters` は、ソートキーが `NOTE#` で始まるレコードだけを関数に渡します。テーブルには 05章のカウンターのアイテムもあり、ノートを作るたびに書き換わります。絞らないと、関数が何もしない呼び出しに料金を払うことになります

キューを読む関数は作っていません。失敗の原因が、モデルのスロットリングなのか、権限の誤りなのか、読めないレコードなのかによって、やるべきことが違うからです。キューにメッセージがあることを知らせるアラームは、19章の方法で足せます。

### 検索の関数

<<< @/examples/27-search/infra/lib/search-stack.ts{search}

実行ロールは、テーブルの `Query`、Titan の呼び出し、インデックスへの問い合わせ、回答のモデルの呼び出しを許可します。書き込みは 1 つもありません。

`s3vectors:QueryVectors` に加えて `s3vectors:GetVectors` が要るのは、問い合わせにメタデータの条件を付け、メタデータを返させているからです。ドキュメントによると、どちらかをするなら両方の権限が必要で、片方しかなければ 403 になります。

回答のモデルの権限は、17章の `modelArns` をそのまま使っています。inference profile と、行き先のリージョンのモデルです。

function URL は 17章と同じ設定です。認証を `AWS_IAM` にしてあることが、所有者のヘッダーを信じてよい理由でした。`NONE` に変えると、URL を知っている人なら誰でも、好きな所有者を名乗ってノートを検索できます。

## デプロイして確かめる

<!-- section: 27.deploy -->

```bash
vp run search:infra:diff
vp run search:infra:deploy
```

デプロイしただけでは、料金はほぼかかりません。課金が始まるのは、ノートを書いて索引の関数が動いたときです。

```bash
vp run search:seed
```

`search:seed` は、手元と同じ 5 件のノートを、あなたの認証情報でテーブルに書きます。書き込みはストリームに流れ、索引の関数が Titan で埋め込みます。この埋め込みは課金されます。5 件の短いノートなので、量はわずかです。

検索の URL は署名が必要です。17章の署名のコードに、所有者のヘッダーを足しました。ヘッダーは署名の対象に含めています。

<<< @/examples/27-search/scripts/sign.ts{sign}

```bash
vp run search:smoke
```

`search:smoke` も課金されます。埋め込みが 3 回と、短い回答が 1 回です。順に、次のことを確かめます。

- 署名なしのリクエストが 403 で断られること
- `alice` として「支払いのトラブル」を検索し、当たりがあること。このクエリは、どのノートとも語を共有していないので、当たれば意味の検索が働いています。索引が追いつくまで、5 秒おきに最大 1 分待ちます
- `alice` と `bob` の結果に、相手のノートが入っていないこと
- `alice` の質問に対する回答が、出典、文章、引用の順に届くこと

2 つ目が失敗した場合、原因は 2 通り考えられます。索引がまだ終わっていないか、Titan が出した距離がしきい値の 0.7 より遠いかです。しきい値は調整していない値なので、後者は十分ありえます。ログで確かめます。

```bash
vp run search:logs
vp run search:logs -- --indexer
```

検索のログには `search` の行があり、`dropped` が落とした当たりの数です。索引のログには、ノートごとの `indexed` と、埋め込みごとの `embedded`（トークン数つき）があります。

テーブルとインデックスが合っているかは、次で確かめます。

```bash
vp run search:reindex
vp run search:reindex -- --apply
```

`--apply` を付けないと、違いの件数を表示するだけで、何も変えません。`--apply` を付けると、足りないノートを埋め込み直し、余ったベクトルを消します。このタスクはテーブルを `Scan` で全部読みます。`Scan` は読んだアイテムのすべてに課金されるので、利用者のリクエストの中では使わず、こうした保守の作業にだけ使います。

ドリフトの検査は 02章と同じです。

```bash
vp run search:infra:drift
```
