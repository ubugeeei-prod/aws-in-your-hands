# 33 Production Readiness: 本番に出す前の点検

ここまでの章は、どれも最後に「本番にするなら」という短い一覧を置いて、次へ進んできました。テーブルは `RemovalPolicy.DESTROY` のまま、アラームの閾値は練習用の値のまま、アカウントは 1 つのままです。この章では、その一覧をまとめて引き受けます。

扱うのは、04章から育ててきたノートのアプリを、本物の利用者と本物のデータに向けて公開する前に、何が成り立っていなければならないかです。おすすめの設定を並べる章ではありません。項目の 1 つ 1 つに、それが無いと何が起きるか、どう確かめるか、どの章がその作業をしているかを書きます。

動かせる部分も 1 つ作ります。合成したテンプレート（`cdk.out` の `*.template.json`）を読んで、公開されたバケット、`*` の付いたポリシー、保持期間のないロググループ、過去に戻せないテーブル、アラームのない関数、スタックと一緒に消えるデータを見つける検査です。この本のすべてのスタックに当てた結果も載せます。練習用のスタックなので、指摘はたくさん出ます。

先に断っておくと、この章は AWS に何もデプロイしません。検査が読むのはテンプレートだけで、アカウントの実際の状態は見ていません。検査が見えないものについては、[手元で動かすページ](/ja/chapters/33-production-readiness/local.md)の最後に 1 節を取ってあります。

前提は [19章](/ja/chapters/19-observability.md)、[20章](/ja/chapters/20-shipping.md)、[21章](/ja/chapters/21-security.md)、[22章](/ja/chapters/22-recovery.md)です。ほかの章は、項目が指している先として出てきます。コードは `examples/33-production-readiness/` にあります。

## 全体像

<!-- section: 33.overview -->

点検は 8 つの分野に分かれていて、項目は全部で 32 あります。

```text
area        items  what it asks
accounts    3      which account is production, and who can do what in it
identity    3      what running code may do, and how people and CI sign in
data        6      what survives an accident, a stack deletion, and a user's request to delete
failure     5      who finds out, how fast, and what they do next
change      4      how a change gets in, and how it gets out again
cost        4      what a quiet month costs, and what bounds a loud one
abuse       3      what stands in front of every public entry
operations  4      who is on call, what is written down, what was rehearsed
```

項目の一覧は、コードの中にデータとして置いてあります。次のタスクで、チェックリストの形で読めます。

```bash
vp run ready:review
```

確かめ方は、項目によって 3 通りあります。

```figure
caption: 点検の項目は、テンプレートを読む検査、アカウントを読むタスク、人への問いの 3 通りで確かめる
node review: 点検の項目 | 8 分野, 32 項目
node template: ready:check | 合成したテンプレートを読む
node tasks: 各章のタスク | sec:posture, recovery:status, obs:alarms
node person: 人への問い | 当番, 復元の訓練, RTO と RPO
node cdkout: cdk.out | *.template.json, AWS は呼ばない
node account: AWS アカウント | 実際の設定と記録
edge review -> template: 10 項目の一部
edge review -> tasks: 13 項目
edge review -> person: 32 項目すべて
edge template -> cdkout: 読む
edge tasks -> account: 読む, 一部は変える
mark review
```

1 つ目は、テンプレートを読む検査です。この章で作るもので、デプロイの前に手元で動きます。見られるのは、テンプレートに書いてあることだけです。

2 つ目は、アカウントを読むタスクです。root ユーザーに MFA があるか、PITR の戻せる範囲がいつからいつまでか、アラームがいまどの状態かは、テンプレートには書いてありません。これらは前の章が用意したタスクで確かめます。この章では 1 つも実行していません。

3 つ目は、人に聞くしかない問いです。今週の当番は誰か、最後に復元を試したのはいつか、RTO を誰が承認したか。32 項目のすべてが、最後はこの形の問いで終わります。テンプレートの検査がすべて通っても、答えられない問いが残っていれば、準備はできていません。

## 項目の書き方

<!-- section: 33.item -->

1 つの項目は、次の形をしています。

<<< @/examples/33-production-readiness/src/review.ts{item}

`must` が成り立っているべきこと、`without` がそれが無いときに起きることです。`chapters` は作業をしている章、`rules` はテンプレートの検査のルール、`tasks` はアカウントを見るタスク、`ask` は人への問いです。

`without` を必ず書くことにしたのは、理由のわからない項目は守られなくなるからです。「ログの保持期間を設定する」とだけ書かれた項目は、急いでいる日に飛ばされます。「設定しないと、利用者が消してほしいと言ったデータがログに何年も残る」と書いてあれば、飛ばしてよいかどうかを自分で判断できます。

項目をデータにしたので、一覧が実際のコードからずれていないことをテストで確かめられます。検査のルールがどれも、いずれかの項目に置かれていること。項目が挙げるタスクが、`vite.config.ts` に実在すること。この 2 つが崩れると、テストが落ちます。

AWS には、同じ目的の仕組みがすでにあります。Well-Architected Framework は、運用上の優秀性、セキュリティ、信頼性、パフォーマンス効率、コスト最適化、持続可能性の 6 つの柱で設計を見直す枠組みです。その中の OPS07-BP02 は、公開前に運用の準備を確かめる点検を operational readiness review（ORR）と呼び、要件のチェックリストを使った点検として説明しています。AWS のドキュメントによると、ORR は AWS が自社の障害の教訓から作った仕組みで、項目は自分たちの障害の振り返りで育てていくものです。

この章の 32 項目は、その ORR をこの本のアプリについて書いたものにあたります。Well-Architected の項目と同じことを言っている箇所では、[デプロイのページ](/ja/chapters/33-production-readiness/deploy.md)で、柱と項目の番号を挙げます。内容を写すことはしません。Well-Architected のほうがずっと広く、この章が触れていない柱もあります。パフォーマンス効率は [29章](/ja/chapters/29-lambda-tuning.md)がいちばん近く、持続可能性はこの本では扱っていません。

## 全部を一度にやらない

<!-- section: 33.stages -->

32 項目を、最初の利用者が来る前にすべて満たす必要はありません。[21章](/ja/chapters/21-security.md)が守りを 3 段に分けたのと同じで、項目にも、いつから要るかの違いがあります。

自分しか使わない練習用のアカウントで要るのは、root ユーザーの MFA、アクセスキーを作らないこと、予算の通知くらいです。01章で済ませました。この段階では、スタックと一緒にデータが消えるほうがむしろ都合がよく、テンプレートの検査が出す指摘の大半は、直すべきものではありません。

他人のデータを預かった日から、話が変わります。消えたら困るものができたので、データの分野の項目（戻せること、スタックと一緒に消えないこと、公開されていないこと）が先に要ります。次に、止まっていることに気づけること、つまり障害の分野のアラームと通知先です。

料金を受け取る、あるいは止まると誰かの仕事が止まるようになったら、残りが要ります。アカウントを分けること、段階的に切り替えること、当番と訓練です。

この順番は、この本の判断です。事情に合わせて前後させてかまいません。大事なのは 21章と同じで、まだやっていない項目について、忘れているのではなく、選んで後回しにしていると言えることです。テンプレートの検査に「理由つきの例外」を用意したのも、そのためです。

逆に、この点検が要らない場面もあります。数日で捨てる試作や、落ちても誰も困らない社内の道具に、当番と訓練は要りません。その場合でも、データの分野の最初の 3 項目だけは見ておくことを勧めます。試作のバケットに本物のデータが入ることは、よくあるからです。

## Workers や Vercel から来た人へ

<!-- section: 33.platforms -->

この章の項目は、AWS に固有のものと、どこで動かしても変わらないものに分かれます。

テンプレートの検査が見ているのは、ほとんどが前者です。関数ごとのロール、ロググループの保持期間、`DeletionPolicy`、バケットの公開設定は、AWS では利用者が 1 つずつ決める設定で、決め忘れると既定の値になります。既定の値が安全とは限りません。保持期間を書かなかったロググループは、無期限に残ります。

Cloudflare や Vercel では、この種の設定の多くを、プラットフォームが決めています。たとえば Workers Logs の保持は最長 7 日で（2026-10-12 に確認）、利用者が決めるのは「何日にするか」ではなく、「7 日より長く残したいときにどうするか」です。決めることが少ないぶん、決め忘れも少なくなります。そのかわり、プラットフォームの決めた値が自分の要件に合わないときは、外に出す仕組みを足すことになります。

Vercel は、公開前のチェックリストを公式ドキュメントに載せています（2026-10-12 に確認）。分野は operational excellence、security、reliability、performance efficiency、cost optimization の 5 つで、障害対応の計画とロールバックの手順、WAF、レート制限、チームの権限、ログを残すための Log Drains、支出の通知といった項目が並んでいます。この章の分野とよく重なります。監査ログや負荷試験のように、Enterprise プランでだけ使えると書かれた項目もあります。Cloudflare が同じ形の一覧を公開しているかどうかは、確認していません。

どこで動かしても変わらないのは、人への問いのほうです。当番は誰か、復元を試したか、RTO と RPO は何時間か、利用者のデータを消してほしいと言われたらどこを消すか。プラットフォームが設定を引き受けてくれても、これらの答えは引き受けてくれません。

いまのプラットフォームの決めた値で要件が満たせていて、人への問いにも答えられるなら、それで準備はできています。AWS に移ると決めることが増えます。増えるぶんだけ自分の要件に合わせられますが、合わせる必要がなければ、増えた設定は決め忘れの種でしかありません。
