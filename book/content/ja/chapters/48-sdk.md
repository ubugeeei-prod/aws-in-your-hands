# 48 SDK: AWS SDK for JavaScript v3 を端から端まで

01章から、AWS を呼ぶコードはどれも `client.send(command)` の 1 行でした。この 1 行のあいだに、SDK は認証情報を探し、リクエストを組み立てて署名し、送り、だめなら待ってもう一度送り、応答をオブジェクトか例外に変えています。どの段にも既定値があり、その既定値は書かなくても動くように選ばれているので、ふだんは意識しません。意識するのは、関数がタイムアウトしたときや、再試行が思ったより多かったときです。

この章では、その 1 行の中身を、導入済みのパッケージのソースと型、それに公式のガイドで読みます。読んだ内容は、手元に立てた小さな HTTP サーバーに本物のクライアントをつないで確かめます。AWS は呼びません。再試行の回数、待ち時間、タイムアウト、ページの継ぎ方、ウェイターの打ち切り方を、実際に通信させて数え、テストで固定します。SDK を上げて既定値が変われば、テストが落ちて知らせます。

前提は [01章](/ja/chapters/01-account.md)の認証情報、[04章](/ja/chapters/04-http-api.md)、[05章](/ja/chapters/05-dynamodb.md)、[07章](/ja/chapters/07-uploads.md)です。再試行の一般論、つまりバックオフとジッターがなぜ要るか、再試行の予算とは何かは、[32章](/ja/chapters/32-limits.md)が扱っています。ここでは繰り返さず、固定している版の SDK が実際に何をするかだけを確かめます。コードは `examples/48-sdk/` にあります。CDK のスタックはありません。

## 全体像

<!-- section: 48.overview -->

```figure
caption: 1 回の send が通る順。再試行のループより下は、試行のたびにもう一度通る
node app: アプリのコード | client.send(command)
node early: initialize、serialize、build | 入力から HTTP リクエストを作る
node retry: retryMiddleware | 試行を繰り返す
node sign: httpSigningMiddleware | 署名する
node log: attemptLogMiddleware | この章で足す
node deser: deserializerMiddleware | 応答を出力か例外にする
node handler: リクエストハンドラー | node:https、接続の再利用
node endpoint: サービスのエンドポイント
edge app -> early
edge early -> retry
edge retry -> sign
edge sign -> log
edge log -> deser
edge deser -> handler
edge handler -> endpoint: HTTPS
mark retry
```

SDK のクライアントは、ミドルウェアスタック（middleware stack）と呼ぶ関数の並びを持っています。`send` を呼ぶと、入力はこの並びを上から下へ通り、最後にリクエストハンドラーが HTTP で送ります。応答は同じ並びを下から上へ戻ります。図にある `retryMiddleware` などの名前は、導入済みの `DynamoDBClient` に並びを尋ねて返ってきたものです。

図でいちばん大事なのは、再試行をするミドルウェアの位置です。署名も、応答の解釈も、送信も、その下にあります。そのため、署名は試行のたびにやり直されます。リクエストの本文を作る処理と、認証情報を取り出す処理は上にあるので、1 回の `send` につき 1 度しか走りません。認証情報を取り出すミドルウェアはコマンドの側のスタックにあり、図では上から 2 つ目の箱に含めています。

この章で読むパッケージと版は次のとおりです。どれも、この本のほかの章が使っているものと同じ版です。

| パッケージ | 版 | この章で読むところ |
| --- | --- | --- |
| `@aws-sdk/client-dynamodb`、`@aws-sdk/client-s3` | 3.1149.0 | クライアント、コマンド、例外、ページネーター、ウェイター |
| `@smithy/core` | 3.35.2 | ミドルウェアスタック、再試行、エラーの分類 |
| `@smithy/node-http-handler` | 4.12.1 | 接続、タイムアウト |
| `@aws-sdk/credential-provider-node` | 3.972.85 | 認証情報を探す順序 |
| `@aws-sdk/lib-dynamodb`、`@aws-sdk/lib-storage`、`@aws-sdk/s3-request-presigner` | 3.1149.0 | 値の変換、アップロード、署名付き URL |

`@smithy/` で始まるパッケージは、SDK の土台です。クライアントの生成元である Smithy のランタイムで、再試行や HTTP の送信のような、サービスによらない部分はここにあります。

## クライアントとコマンド

<!-- section: 48.client-command -->

v3 の SDK は、サービスごとに 1 つのパッケージに分かれていて、呼び出しは 2 つのオブジェクトで書きます。クライアントは設定と接続を持ち、コマンド（command）は 1 つの API 操作とその入力を表します。次は、この章のスクリプトがノートを 1 件読むところです。

<<< @/examples/48-sdk/scripts/tour.ts{call}

クライアントが持つのは、リージョン、認証情報の取得元、再試行の設定、リクエストハンドラー、そしてミドルウェアスタックです。再試行の予算と、開いたままの接続も、クライアントごとに 1 つずつあります。クライアントを 2 つ作れば、予算も接続も別々になります。この点はテストで確かめました。関数の外で 1 つだけ作って使い回す理由は、ここにあります。

コマンドは、入力を入れただけの軽いオブジェクトです。`send` に渡された時点で、クライアントのスタックと自分のスタックを合わせて、実行する関数を組み立てます。同じパッケージには `DynamoDB` のように全操作をメソッドとして持つクラスもありますが、この本では使いません。理由はバンドルの大きさで、[29章](/ja/chapters/29-lambda-tuning.md)が実測しています。

`send` の 2 つ目の引数には、その呼び出しだけの設定を渡せます。この章で使うのは `abortSignal` です。

## 手元のエンドポイント

<!-- section: 48.local-endpoint -->

SDK の挙動を確かめるには、決まった答えを返す相手が要ります。そこで、ループバックで待ち受ける HTTP サーバーを書き、クライアントの `endpoint` をそこへ向けます。クライアントは本物で、署名も再試行も接続の管理も、AWS に向けたときと同じコードが動きます。違うのは相手だけです。

このサーバーは、この章が書いたものです。DynamoDB でも S3 でもありません。テーブルもバケットも持たず、署名も検査せず、台本に書かれた答えを返すだけです。サービスの側の挙動、たとえば本物の DynamoDB がどんなときにどのエラーを返すかは、このサーバーからは何もわかりません。

サーバーが知っているのは、2 つのプロトコルの外枠だけです。DynamoDB は JSON を POST し、操作の名前を `x-amz-target` ヘッダーに入れます。エラーは、ステータスと、本文の `__type` に入ったコードで表します。S3 は REST で、本文は XML です。

## この章が要らない場合

<!-- section: 48.when-not -->

Cloudflare Workers から D1 や R2 を使うときは、この章の大半が要りません。Cloudflare のドキュメントは、binding を「権限と API が 1 つになったもの」と説明していて、Worker のコードにキーやトークンを置く必要はないとしています（2026 年 10 月 13 日に確認）。認証情報を探す順序も、署名も、エンドポイントも、開発者が考える対象として出てきません。再試行とタイムアウトをどこまでプラットフォームが受け持つかは、この章では確かめていません。

AWS では、権限は実行ロールに、API は SDK に分かれています。そのぶん、呼び出しの 1 つ 1 つについて、何回試すか、どこで諦めるか、どの認証情報を使うかを自分で決められますし、決めなければ既定値が決めます。この章は、その既定値を知るためのものです。

アプリが 05章の形のまま動いていて、困っていないなら、[しくみと実装](/ja/chapters/48-sdk/build.md)の再試行とタイムアウトの節だけを読めば足ります。既定のクライアントにはタイムアウトが 1 つもない、という 1 点は、知らずに本番へ出すと痛い目を見ます。
