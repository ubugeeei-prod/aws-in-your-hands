# 29 Lambda Tuning: cold start、メモリ、同時実行数、bundle

04章から、ノートの API は Lambda の関数で動いてきました。メモリは 256 MB、タイムアウトは 10 秒、バンドルは esbuild の既定のまま、と最初に決めた値をそのまま使っています。

この章では、ハンドラーが呼ばれる前に Lambda の中で何が起きているかを見て、そこで変えられるものを 1 つずつ動かします。扱うのは、バンドルの大きさ、ハンドラーの外に書くコード、メモリ、同時実行数、タイムアウトの 5 つです。レイヤーと extension は、判断に要る範囲だけ触れます。

先に断っておくと、この章には Lambda の上で測った時間が 1 つもありません。手元で確かめたのは、バンドルのバイト数と、Mac の上でそのバンドルを読み込む時間、そして計算とテストまでです。手元の時間は Lambda の時間ではないので、AWS で測る手順は用意してありますが、実行はしていません。

前提は [04章](/ja/chapters/04-http-api.md)と [19章](/ja/chapters/19-observability.md)です。コードは `examples/29-lambda-tuning/` にあります。

## 全体像

<!-- section: 29.overview -->

Lambda は、関数を実行環境（execution environment）の中で動かします。リクエストが来たときに空いている実行環境が無ければ、Lambda は新しく 1 つ作り、初期化してからハンドラーを呼びます。この初期化を待つ呼び出しがコールドスタートです。

```figure
caption: 1 件目は実行環境の用意と初期化を待ち、2 件目は同じ実行環境でハンドラーだけが動く
type: sequence
actor caller: API Gateway
actor lambda: Lambda
actor env: 実行環境
step caller -> lambda: 1 件目
step lambda -> env: 作ってコードを置く
step env -> env: Init: ハンドラーの外のコード
step env -> env: Invoke: ハンドラー
step env --> caller: レスポンス
note env: 凍結されて次を待つ
step caller -> lambda: 2 件目
step lambda -> env: 同じ実行環境を使う
step env -> env: Invoke: ハンドラー
step env --> caller: レスポンス
```

Init フェーズで Lambda がするのは、extension の起動、ランタイムの起動、関数の静的なコードの実行の 3 つです。静的なコードは、ファイルのうちハンドラーの外に書いた部分を指します。Init フェーズには 10 秒の制限があり、終わらなければ、最初の呼び出しのときに関数のタイムアウトの範囲でやり直されます。

`composeTunedApp` は 05章のアプリを組み立てる関数で、環境変数の検証も DynamoDB のクライアントの生成もこの中で済ませます。実行環境ごとに 1 回しか走りません。ハンドラーのほうは呼び出しのたびに走ります。`withDeadline` は、関数のタイムアウトより少し手前に締め切りを置く仕掛けで、[実装のつづき](/ja/chapters/29-lambda-tuning/more.md)で説明します。

呼び出しが終わると、Lambda は実行環境を凍結して、しばらく取っておきます。次のリクエストが来れば解凍して使い回すので、ハンドラーの外で作ったクライアントや接続はそのまま残っています。ただし、いつまで残るかは決まっていません。公式ドキュメントは、絶えず呼ばれている関数でも数時間ごとに実行環境を終了させると書いています。

1 つの実行環境が同時に処理するのは 1 件だけです。処理中に次のリクエストが来ると、Lambda は実行環境をもう 1 つ作ります。このため、コールドスタートは「しばらく呼ばれなかった後」だけでなく、「同時に来る数が増えたとき」にも起きます。

コールドスタートの頻度と長さについて、公式ドキュメントは、典型的には呼び出しの 1% 未満で、100 ミリ秒未満から 1 秒を超えるものまである、と書いています。この数字は AWS の説明で、この章の関数で確かめたものではありません。

変えられる設定と、それが効く場所をまとめると、次のようになります。

```figure
caption: この章で動かす 5 つの設定と、それぞれが効く場所
direction: right
node bundle: バンドル | 大きさ、依存の選び方
node outside: ハンドラーの外のコード | クライアント、設定の検証
node memory: メモリ | CPU と単価
node timeout: タイムアウト | 呼び出し元より短く
node conc: 同時実行数 | 予約、provisioned
node init: Init フェーズ
node invoke: Invoke フェーズ
node envs: 実行環境の数
edge bundle -> init
edge outside -> init
edge memory -> init
edge memory -> invoke
edge timeout -> invoke
edge conc -> envs
```

スタックは 05章、19章と同じ形のテーブルと API を持ち、メモリと同時実行数を `-c` で渡せるようにしてあります。既定のままデプロイすれば、置いてあるだけでかかる料金はありません。時間で課金されるのは provisioned concurrency を指定したときだけで、その場所には本文で印を付けます。

## REPORT 行の読み方

<!-- section: 29.report -->

Lambda は、呼び出しが終わるたびに記録を 1 つログに書きます。何もしなくても出ているので、チューニングはこの行を読むところから始められます。既定のログ形式（プレーンテキスト）では、次のような 1 行です。公式ドキュメントに載っている例をそのまま引きます。

```text
REPORT RequestId: b70435cc-261c-4438-b9b6-efe4c8f04b21 Duration: 3004.92 ms Billed Duration: 3117 ms Memory Size: 128 MB Max Memory Used: 33 MB Init Duration: 111.23 ms
```

`Duration` はハンドラーにかかった時間で、初期化の時間は入っていません。`Init Duration` は初期化にかかった時間で、その呼び出しが実行環境を初期化したとき、つまりコールドスタートのときにだけ現れます。この項目があるかどうかで、コールドスタートを数えられます。

`Billed Duration` は課金される時間です。上の例では 3004.92 と 111.23 を足して 1 ミリ秒単位に切り上げた 3117 になっています。初期化の時間も課金されるということです。マネージドランタイムを使い ZIP で配る関数では、オンデマンドの呼び出しの初期化は以前は課金されていませんでしたが、2025 年 8 月 1 日からはどの種類の関数でも課金されます。

`Memory Size` は設定したメモリ、`Max Memory Used` は実際に使った最大量です。2 つが近ければメモリが足りていない兆候で、大きく離れていれば減らせる可能性があります。

19章のスタックは、メトリクスフィルターのためにログ形式を JSON にしました。この章のスタックも JSON にしています。JSON 形式では、同じ記録が `platform.report` という種類のオブジェクトになり、項目に名前が付きます。


```text

cold starts       4 (80.0%)
initialization    p50 111.2 ms, p95 1236.0 ms, max 1236.0 ms (6)
```

### 19章のログとの違い

19章のログには、リクエストごとに `durationMs` がありました。アプリが自分で測った値で、ルーティングからレスポンスを作るまでの時間です。REPORT の `Duration` はハンドラー全体にかかった時間なので、アプリの `durationMs` に加えて、イベントを `Request` に直す処理と、レスポンスを結果のオブジェクトに直す処理も入ります。どちらにも初期化の時間は入りません。

利用者が待った時間にいちばん近いのは、19章でアラームを付けた API Gateway の `Latency` です。コールドスタートの影響を見るときは、REPORT の `Init Duration` で頻度と長さを調べ、入口の `Latency` の p95 や p99 で利用者への影響を確かめる、と分けて使います。

`Init Duration` が何を含むかには、読み取れなかった点が 1 つあります。公式ドキュメントは Init フェーズの仕事を先ほどの 3 つと書いていますが、その前にあるコードのダウンロードと実行環境の起動が `Init Duration` に入るのかどうかは、書かれていませんでした。

失敗の後には、もう 1 つ見えにくい初期化があります。呼び出しがタイムアウトやクラッシュで終わると、Lambda は実行環境をリセットし、次の呼び出しのときに初期化をやり直します。この初期化は別の行としては報告されず、次の呼び出しの時間に含まれます。タイムアウトの直後のリクエストが遅いときは、これを疑います。

## チューニングが要らない場合

<!-- section: 29.when-not -->

この章の内容は、やらなくて済むなら、やらないのがいちばんです。次のどれかに当てはまるなら、先に進む前に手を止めてください。

入口の `Latency` の p95 と p99 に不満が無いなら、コールドスタートを減らす理由がありません。AWS の説明どおり 1% 未満なら、p95 にも p99 にもほとんど現れず、見えるのは最大値のあたりだけです。

料金が目的なら、まず金額を見ます。月 100 万回、256 MB、1 回 50 ミリ秒という 04章の仮定で、Lambda の料金は定価で **0.37**、無料枠の適用後は 0 です。この規模では、メモリを半分にしても節約できるのは月 0.08 ほどです。料金のためのチューニングに意味が出るのは、呼び出しが月に数千万回を超えるか、1 回が長い関数です。

順番も大事です。この章は、費用のかからないものから並べてあります。バンドルを小さくするのと、ハンドラーの外のコードを見直すのは、何も払わずにできます。メモリは AWS で測ってから変えます。provisioned concurrency は時間で課金されるので最後です。

応答の遅れを常に数十ミリ秒に収めたい、接続を張ったままにしたい、といった要求が先にあるなら、関数を調整するより、[12章](/ja/chapters/12-containers.md)のコンテナのような常時動く構成を比べるほうが早いことがあります。Cloudflare Workers のように実行の単位が違う基盤との比較は、[最後のページ](/ja/chapters/29-lambda-tuning/wrap.md)に書きました。

次の[しくみと実装](/ja/chapters/29-lambda-tuning/build.md)では、バンドル、ハンドラーの外のコード、メモリを順に扱います。
