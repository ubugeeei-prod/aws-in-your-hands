# 章ごとの状態と不変条件

この本のサンプルはどれも小さなものですが、複数の場所にまたがって動きます。ブラウザ、CDN の各拠点、関数の実行環境、データベースは、それぞれ別の時点の状態を持ち、別々に失敗します。

分散システムの話題は、分散データベースの章だけでなく、本のあちこちに出てきます。このページでは、どの章に何が出てくるかをまとめます。

## どの章でも確かめる 8 つの問い

状態を持つサンプルでは、次の問いに答えます。

1. 状態の持ち主は誰か。どこにあるデータが正しいのか
2. 読み書きはどの経路を通るか
3. 整合性の保証は何で、どの範囲で成り立つか。1 回の読み取り、1 つのセッション、1 つのリージョン、全体のどれか
4. 同時に更新されたらどうなるか
5. 同じメッセージが 2 回届いたらどうなるか
6. 応答が返る前に接続が切れたら、処理は済んだのか済んでいないのか
7. 一部だけ成功して止まったら、どう戻すか
8. そのために追加でかかる料金は何か

そのうえで、守りたい性質である不変条件（invariant）を平易な 1 文で書き、その不変条件を壊そうとするテストを付けます。

サービスの名前から保証を推測することはしません。global、serverless、durable、exactly-once といった言葉は、それだけでは何も保証しないからです。

## テストはどれもローカルで実行したもの

上の表のテストは、どれも手元で実行したものです。AWS の上では、どの章の検査もまだ一度も実行していません。05章の条件付き書き込みを DynamoDB に送ったことも、08章のワーカーに本物の S3 のイベントを渡したことも、13章のトランザクションを本物のクラスターで競合させたこともありません。25章から先も同じで、どの章もデプロイしていません。

手元で動かした相手は、ほとんどがメモリ上のモデルか代役です。実物のソフトウェアを手元で動かした章は、25章から先では 4 つあります。

- 30章は、テーブルの規則 16 件とノートブックの規則 19 件を、DynamoDB Local 3.3.1 に対して実行しました。DynamoDB Local はトランザクションの衝突を報告しないので、衝突して再試行する経路は、メモリ上のモデルでしか通していません
- 58章は、ジャーナルの規則と、追記から監査までの 1 件、合わせて 11 件を、DynamoDB Local 3.3.1 に対して実行しました。Object Lock のバケットは、手元では動かしていません
- 64章は、workerd 1.20261012.1 を macOS（arm64）で起動し、テストをその実物に対して動かしました。コンテナイメージは一度もビルドしておらず、Linux の workerd は実行していません
- 66章は、YugabyteDB 2025.2.7.0-b107 の 3 ノードのクラスターを macOS（Apple シリコン）で起動し、ノードを 1 台、2 台と落として確かめました。Linux のバイナリは一度も動かしていません

DynamoDB Local も、手元の workerd も、1 台のマシンの上のクラスターも、AWS の上のサービスやインスタンスではありません。4 つの章が確かめたのは、そのソフトウェアが手元でどう動いたかまでです。

ローカルのテストには、決まった順序で失敗を再現できる利点があります。ただし、確かめているのはこの本のコードの判断であり、AWS のサービスの挙動ではありません。実際の反映の遅れ、実行環境の増え方、IAM の反映、イベントの実際の形、本物の障害のときの動きは、実環境でしか確かめられません。何が残っているかは、[検証記録](/ja/reference/validation.md)に章ごとに書いてあります。

この本は、最初の API から複数リージョンの構成を扱うような進め方をしません。小さなふつうの例から始め、次にその失敗例を見て、必要な場合だけ深いラボに進みます。

実環境で障害を起こす実験は、専用の環境と、明示的に実行するタスクに分けます。ふだんの `vp run check:all` は AWS に触りません。
