# 17 AI Development for Workers AI Users: Bedrock

With Workers AI, you write one line of `env.AI.run()` and a model answers. On AWS, the service that does this is Amazon Bedrock.

In this chapter you first call a model once, in a few lines. Then you build an API that summarizes the body of a note and sends the summary back piece by piece as it is written. The call itself is about as short as it is on Workers AI. What grows is everything around it: who may call, how much may be spent, and what happens when the stream is cut.

One thing up front. Calling a model is billed by the token, and that is just as true when the call comes from a server on your own machine. The tests and the default development server in this chapter run without calling any model. I'll flag each task that is billed as we reach it.

You need [chapter 04](/en/chapters/04-http-api.md). The code is in `examples/17-ai/`.

## The big picture

<!-- section: 17.architecture -->

```text
Caller (a script with AWS credentials; later a browser behind your own auth)
  |  HTTPS, signed with SigV4
  v
Lambda function URL (ap-northeast-1)   AuthType: AWS_IAM, InvokeMode: RESPONSE_STREAM
  |  unsigned or unauthorized: 403, the function is not invoked
  v
Lambda function (Node.js 24, arm64, 256 MB, timeout 40 s)
  |  Hono app -> summarizer -> ModelGateway
  |  execution role: its own log group, and one inference profile
  v
Amazon Bedrock ConverseStream (inference profile jp.amazon.nova-2-lite-v1:0)
  |  the request is processed in ap-northeast-1 or ap-northeast-3
  v
events: messageStart, contentBlockDelta..., messageStop, metadata
  ^
  |  relayed to the caller as server-sent events: delta..., then done or error
```

Two things differ from chapter 04.

The first is the front door. The API Gateway HTTP API from chapter 04 waits for the whole Lambda response before it returns anything. It cannot send a response piece by piece. So this chapter uses a **function URL**, an HTTPS endpoint attached directly to a Lambda function. A function URL has a response streaming mode that passes on whatever the function has written so far.

The second is that Bedrock sits behind Lambda. Your function generates no text. It asks Bedrock and relays the events that come back.

### Choosing the front door

According to the official documentation, there are three ways to get a Lambda streaming response out to a caller.

- A function URL (`RESPONSE_STREAM`)
- An API Gateway REST API, with the response transfer mode of a proxy integration set to `STREAM`. HTTP APIs do not have this
- Calling `InvokeWithResponseStream` directly from an SDK

This chapter picks the function URL because it adds exactly one resource. The price is that the only authentication a function URL has of its own is an IAM signature. If you need API keys, WAF, or a Cognito authorizer, the REST API is the one to use (see the table in chapter 04). What it takes to let a browser call this comes up under "Going to production".

### Never leave it open to everyone

A function URL authenticates with `AWS_IAM` or with `NONE`, and that's the whole menu. With `NONE`, anyone who knows the URL can invoke the function. This function runs a model every time it is invoked, so that would mean strangers running inference on your bill.

So this chapter uses `AWS_IAM`. Lambda checks the request's signature (a SigV4 signature, the way AWS APIs identify a caller) before the function runs. Only someone in the same account who is allowed `lambda:InvokeFunctionUrl` and `lambda:InvokeFunction` can call it. The caller in this chapter is a script that signs with your credentials.

An SPA cannot call it directly, because AWS credentials do not belong in a browser. The outline planned to connect an SPA, but that needs the sign-in from [chapter 06](/en/chapters/06-auth.md). This chapter only requires chapter 04, so I put "no public endpoint without authentication" first and stopped here.

## Choosing a model

<!-- section: 17.models -->

What goes in `modelId`? This is where Bedrock is a good deal more work than Workers AI.

On Bedrock, each model differs in which Regions it can be called from, and by which route. There are three routes.

- **In-Region**: processed only inside the Region you called. You pass the model ID as it is
- **Geo**: processed in some Region inside a fixed geography
- **Global**: processed in some commercial Region anywhere in the world

For Geo and Global you pass the ID of an **inference profile** in place of the model ID. It is a name for a model together with the Regions a request may be sent to. The mechanism is called cross-Region inference.

So calling the Tokyo endpoint does not mean the inference runs in Tokyo. With a profile that starts with `jp.`, it is Tokyo or Osaka. With `global.`, it is anywhere. If you have rules about where your data may be processed, settle this first. The official documentation also says to check the destinations and not to judge by the prefix of the ID alone.

These are the IDs I checked on each model's page (its model card) on 2026-10-11.

<<< @/examples/17-ai/infra/lib/models.ts{models}

The default is the `jp.` profile of Amazon Nova 2 Lite, for three reasons: its destinations stay inside Japan, it is an Amazon model so there is nothing to sign up for, and it is cheap. By the way, Nova 2 Lite cannot be called In-Region from Tokyo. The table on its model card marks only Geo and Global.

The model can be swapped through the environment variable `BEDROCK_MODEL_ID`, or with `-c modelId=...` when you deploy. An ID that is not in the table above stops the synth, though. That isn't spite. It's for the sake of IAM, which is next.

### Getting access

Bedrock used to have a console page where you requested access model by model. The current documentation says that many models are usable from the start. Two formalities remain.

- **Anthropic models** need a use case form submitted once, the first time (once per account or organization)
- **Models sold through AWS Marketplace** (Anthropic's among them) have Bedrock start a subscription in the background on the first invocation. The caller needs permissions such as `aws-marketplace:Subscribe`, and it can take up to 15 minutes to complete. Amazon's models do not go through Marketplace

The second one hides a trap. The Lambda execution role in this chapter has no Marketplace permissions. So if you switch to an Anthropic model, first get `vp run ai:hello` to pass once with your own permissions. Once the model is enabled, callers no longer need the Marketplace permissions.

### The ARNs in the execution role

An inference profile gives IAM more to name: the profile itself, and the model in each destination Region.

<<< @/examples/17-ai/infra/lib/models.ts{arns}

For `jp.amazon.nova-2-lite-v1:0` that is one profile and two models, in Tokyo and Osaka. Forget one destination and only the requests routed there are denied. ## The input limit and the events you return

<!-- section: 17.contract -->

As in chapter 04, we start from the contract. The request first.

<<< @/examples/17-ai/src/contract.ts{request}

The body may be up to 10,000 characters, the same limit as a note in chapter 04. This is validation, and it is also a cost ceiling. Input tokens are billed, so "accepts any length" means the same as "pays any amount".

Characters and tokens are different things, though. A token is the unit in which a model reads and writes text, and each model counts differently. How many tokens 10,000 characters turn into is not known exactly until you make the call. Think of the character limit as holding the input cost down roughly.

The output can be held down much more precisely.

<<< @/examples/17-ai/src/prompt.ts{request}

`maxTokens` is the limit on the tokens one call may generate. For a summary, 400 is plenty. Fixing this value lets you say flatly that one call's output goes no further.

Look at the third line of the system prompt too. The body of the note is written by a user. A note that says "forget your instructions and..." may arrive. The instructions go in `system`, the note goes in `messages`, and the model is told that the note is data. That does not make it safe. The output of this API is a plain string with no authority to do anything, and that is the real safeguard.

Next, the events this API returns.

<<< @/examples/17-ai/src/contract.ts{events}

The response is server-sent events (SSE), a format in which a server keeps sending events inside one HTTP response. Some `delta` events arrive, and then exactly one `done` or `error` at the end. That "always exactly one of the two at the end" pays off later in the chapter.

## Reading the stream

<!-- section: 17.stream -->

`ConverseStream` is the streaming version of `Converse`. What comes back is a sequence of events.

```text
order  event              carries
1      messageStart       role
2      contentBlockDelta  a piece of text (repeats)
3      contentBlockStop
4      messageStop        stopReason: end_turn, max_tokens, ...
5      metadata           usage: inputTokens, outputTokens
```

It is not SSE. It arrives in AWS's own format, and the SDK turns it into an async iterable.

<<< @/examples/17-ai/src/converse-stream.ts{schema}

Event kinds it does not know pass through and are ignored, so that nothing breaks when Bedrock adds a new one. An event it does know, with the wrong shape, stops everything. A `delta` whose `text` is not a string should not flow on to the caller.

And now the relay.

<<< @/examples/17-ai/src/summarize.ts{relay}

The lines to look at are the last few. If the stream ends without a `messageStop`, the relay answers `error`, not `done`. However plausible the text that arrived, if the model never said "that's all", you cannot call it finished.

It checks `stopReason` too. A summary that stopped for anything other than `end_turn`, say `max_tokens`, is cut in the middle of a sentence. It still gets a `done`, but `complete` is `false`.

`MAX_SUMMARY_CHARS` is a backstop. `maxTokens` is passed, so normally it is never reached. Even so, you don't want to write code that keeps forwarding a string from outside with no limit at all.

## Stop, wait, try again

<!-- section: 17.failures -->

A model call fails in many ways. It's busy, you went over a limit, you lack permission, it was cut midway. Fold them all into one "error" and you can no longer tell what is worth retrying from what is not.

<<< @/examples/17-ai/src/failure.ts{classify}

There is one criterion: if you sent the same request again, could it pass?

`ThrottlingException` comes back when you exceed your account's quota (a limit on token usage, set per model). It may pass after a short wait. `ServiceUnavailableException` is a capacity problem on Bedrock's side, also worth waiting for. `AccessDeniedException` and `ValidationException`, on the other hand, will be the same however often you send them. The role, the model ID, or the request is wrong.

About an error whose name it does not know, the code says nothing (`undefined`). It will not decide on its own that the unknown is retryable.

Here is how it waits.

<<< @/examples/17-ai/src/failure.ts{backoff}

The ceiling of the wait doubles each time, and the actual wait is picked at random below it. The randomness keeps callers who failed together from retrying together and failing together again. The random number comes in as an argument, so in tests the waits are fixed values.

And here is the code that uses it.

<<< @/examples/17-ai/src/summarize.ts{start}

Three points.

**It retries only while nothing has been sent yet.** A failure before the stream opens is invisible to the caller, so it can be retried silently. Once even one `delta` has gone out, a retry would send the start of the same text a second time. What was sent cannot be taken back, so from there on it answers `error` and leaves the decision to retry with the caller.

**There is one deadline for all attempts together.** Give each attempt its own 30 seconds and three attempts keep the caller waiting 90. One `AbortSignal.timeout` is created at the start and shared by every attempt.

**Whatever the reason for stopping, the request to the model is aborted.** The caller left, the deadline passed, the relay ended: three signals are combined with `AbortSignal.any` and handed to the SDK. A model bills for text nobody will read just the same.

Left alone, the SDK also retries, up to 3 attempts. This chapter turns that off (`maxAttempts: 1`) and keeps retries in its own code, where they share the deadline and can be tested.

## Making it an API

<!-- section: 17.app -->

Now the pieces go onto Hono.

<<< @/examples/17-ai/src/app.ts{route}

A failure before the stream starts gets an ordinary HTTP error: 429 for throttling, 504 for the deadline. Nothing has been sent yet, so the status code can carry it.

After it starts, the status code has already gone out as 200. So a failure is reported by an `error` event inside the stream. In other words, this is an API where "it answered 200" does not mean "it worked". A caller cannot decide the outcome before it has seen the last event.

At the end it writes one log line called `summary`: the outcome, the number of attempts, and the token counts the model reported. That line is the record of what one summary cost.

Here is the important part. **An API server running on your machine and inference running on your machine are two different things.**

<<< @/examples/17-ai/src/dev.ts{dev}

With `AI_BACKEND=fixture`, the server replays a prepared sequence of events. It does not call AWS. Nothing is billed. It needs no credentials.

Change it to `AI_BACKEND=bedrock` and the same server calls real Bedrock with your credentials. The server is on `localhost`, but the model runs inside AWS and bills by the token. Nothing that imitates Bedrock locally comes with the SDK.

Workers AI is the same. Cloudflare's documentation says that Workers AI always connects to your account to run models, even in local development, and incurs usage charges. That sets it apart from the bindings mentioned in chapter 04, which connect to a local simulation.

It is also why the development server listens only on `127.0.0.1`. With `bedrock`, anyone who can reach that port can run inference on your bill.

There are five fixtures, selected with `AI_FIXTURE`. You can watch a failing stream locally as often as you like.

```bash
AI_FIXTURE=truncated vp run dev:ai
```

Send the same `curl` now and three `delta` events arrive, followed not by `done` but by `error` (`interrupted`).

One more thing to try. With the `complete` fixture, send the `curl` and press Ctrl+C while it is still flowing. The server's log shows a line whose `outcome` is `cancelled`. That is the record of the server learning that the connection was gone and aborting its request to the model.

That is the local story, though. On Lambda things are different. More on that below.

## When the stream is cut

<!-- section: 17.partial -->

Streams get cut. The model may stop, Lambda may time out, the Wi-Fi may drop.

```text
time  Bedrock                Lambda                    caller
t1    messageStart      -->  (opens the SSE stream)
t2    delta "金曜の"      -->  delta              -->   shows "金曜の"
t3    delta "リリース…"   -->  delta              -->   shows "金曜のリリース…"
t4    (connection drops)     error: interrupted  -->   partial text + "incomplete"
t4'   or: the caller's own connection drops here       no terminal event at all
```

At t4, Lambda can send an `error`. But if, as at t4', the link between Lambda and the caller is cut, nothing arrives at all. You cannot validate what never arrives, so the client treats "the last event never came" as a failure in itself.

<<< @/examples/17-ai/src/client.ts{events}

If the server ends without sending `done` or `error`, the client adds an `error` of its own. Seen from the reader's side, then, a stream always ends in `done` or `error`.

The part that reads SSE is short, so it is written here.

<<< @/examples/17-ai/src/client.ts{sse}

An event counts only once its closing blank line has arrived. A `data:` line that arrived halfway is not used.

Now, what do you do with the text left in your hands when the stream is cut? You have to decide. This chapter's answer is this.

<<< @/examples/17-ai/src/client.ts{collect}

**Partial output may be shown, but it is not stored as the summary.** The result is `complete` only when a `done` was received and its `complete` is `true`. Everything else is `incomplete`, and whatever arrived goes into `partial`. Showing it on screen marked as unfinished is fine. Store it as the note's summary, though, and the next time the note is opened, a summary cut in mid-sentence appears as the finished article. Nobody can tell any more where it was cut.

The invariant in one sentence: **output for which no `done` was received is never treated as a completed summary.**

A test tries to break it. It takes the bytes of a response that completes and cuts them one byte at a time, from zero bytes up to one byte short of the end, and has the client read each cut, both when the connection closes quietly and when it fails with an error. Wherever the cut falls, the result is `incomplete`, and `partial` is always a leading part of the real text.

The sample in this chapter does not store summaries (storage starts in chapter 05). When you add it, write only results whose `status` is `complete`.

### Permissions

<<< @/examples/17-ai/infra/lib/ai-stack.ts{role}

The action needed to call `ConverseStream` is `bedrock:InvokeModelWithResponseStream`. The API name and the action name differ, which is confusing at first. `Converse` is `bedrock:InvokeModel`. This function never calls `Converse`, so it does not get that one.

The resources are just the profile from earlier and the models at its destinations. The model statement carries a condition that narrows it to "only when called through this profile". The tests check that this is the only action and that no resource contains `*`.

### The function

<<< @/examples/17-ai/infra/lib/ai-stack.ts{function}

A word on `timeout`. This is where Lambda differs most from your machine.

The Lambda documentation says this: a streamed response is not interrupted when the invoking client's connection is broken, and you are billed for the full function duration.

On the local development server, disconnecting produced `cancelled`. On Lambda it does not. Reading the source of Hono's `streamHandle`, I found nothing that connects a failed write to cancelling the response body either. So on Lambda, assume the model keeps writing to the end even after the caller is gone.

Three things do stop it: `maxTokens` (the output limit), the app's deadline (30 seconds), and the function's `timeout` (40 seconds). The function's `timeout` is longer than the deadline to leave the app time to send its `error` event and finish. A test guards that ordering.

`AWS_IAM` and `RESPONSE_STREAM`. The stack contains no `AWS::Lambda::Permission` at all, which means no resource-based policy hands anyone the right to call. A test pins that down too.

## If you come from Workers AI

<!-- section: 17.workers-ai -->

Here are the differences. The Cloudflare side is limited to what I confirmed in the official documentation.

| | Cloudflare Workers AI | This chapter (Bedrock) |
| --- | --- | --- |
| How you call | A binding. Declare it and it appears as `env.AI`; call `env.AI.run(model, options)` | An AWS SDK client. Send a `ConverseCommand` or a `ConverseStreamCommand` |
| Permissions | The Worker that declared the binding can call | IAM. The execution role names the ARNs of the model and the inference profile |
| Naming a model | A name such as `@cf/meta/llama-3.1-8b-instruct` | A model ID or an inference profile ID. What is usable depends on the Region and the route |
| Where it runs | Cloudflare's network | One of the Regions the profile allows |
| Streaming | Pass `stream: true` and it returns `text/event-stream`, usable as the response as it is | A sequence of events arrives as an async iterable from the SDK. Turning it into SSE is up to you |
| Billing unit | Neurons. 10,000 a day free, then USD 0.011 per 1,000 Neurons. Per-token prices are listed per model as well | Input and output token prices per model and Region |
| Local development | No simulation. Always remote, always billed | No simulation. Always remote, always billed |

Workers AI gets you started sooner. One line of binding and you can call, without thinking about permissions or where the model lives. Streaming is done once you hand what comes back to a `Response`.

On Bedrock you decide all of that yourself: which ARNs to allow, which Regions process the request, in what form the stream leaves. It is more work, but "this function can call this model and no other" and "inference is processed inside Japan" become things you write down as configuration. Which is better depends on what you are building and on the rules you have to keep.

The last row is the same. On both, the API may run on your machine while the inference runs over there and is billed.

## What it costs

Amounts are in USD, Tokyo Region, on-demand, before tax. The details of the calculation are in [Pricing Worksheets](/en/reference/pricing.md).

**A month in which nobody calls costs 0.** Neither a function URL nor Lambda charges for existing. Bedrock's on-demand pricing bills only the tokens you call for. Logs expire after 7 days.

When it is called, it looks like this. The assumptions are 1,000 summaries a month, each with 2,000 input tokens and 150 output tokens. The token counts are assumptions; the real values for your notes are in the `usage` of the `summary` log line.

| Item | Quantity | List price | After the monthly free allowance |
| --- | --- | --- | --- |
| Nova 2 Lite input | 2 million tokens | 0.79 | 0.79 (no free allowance confirmed; none deducted) |
| Nova 2 Lite output | 150,000 tokens | 0.50 | 0.50 (same) |
| Lambda requests | 1,000 | 0.00 | 0 |
| Lambda duration | 1,000 GB-seconds | 0.01 | 0 |
| CloudWatch Logs ingestion | 0.001 GB | 0.00 | 0 |
| Subtotal | | **1.30** | **1.29** |

The unit prices for Nova 2 Lite are USD 0.000396 per 1,000 input tokens and USD 0.003311 per 1,000 output tokens (AWS Price List, checked 2026-10-11). Output costs more than 8 times what input does. This is the point of setting `maxTokens`.

Lambda duration assumes 4 seconds per summary on average. The function is running, and billed, while it waits for the model. The charge for transferring the response out to the internet is not in this table (it is not 0; it is not included).

About the ceiling. Output is at most 400 tokens per summary, so even if all 1,000 wrote up to the limit, the output part is USD 1.32. The input, as said above, is limited only by characters, so no such flat statement can be made for it.

Change the model and the unit prices change. The same token counts on Claude Haiku 4.5 (Tokyo, USD 1.10 per million input tokens and USD 5.50 per million output tokens) come to USD 3.03 for inference alone, more than twice Nova 2 Lite. Tokenizers differ by model, though, so the same text does not give the same token count. Read it as a comparison of unit prices.

Some things I could not confirm: whether Bedrock has a free allowance, and how many tokens are billed for a call that is aborted midway. Neither was confirmed from a primary source, so both stay unknown.

Deleting the stack stops the charges from this chapter.

| `dev:ai` stops with `Invalid environment` | Is there an `examples/17-ai/.env`? `AI_BACKEND` has no default |
| `ai:hello` fails with `AccessDeniedException` | The model is not enabled, or your permissions are short. A Marketplace model can take up to 15 minutes after the first call. Anthropic models need the use case form first |
| `ai:hello` fails with `ValidationException` or `ResourceNotFoundException` | Check `BEDROCK_MODEL_ID`. Is it an ID that cannot be called from Tokyo, or a bare model ID for a model that requires an inference profile? |
| The function URL answers 403 | There is no signature, or the caller lacks `lambda:InvokeFunctionUrl` and `lambda:InvokeFunction` |
| The API answers 500 with `code` `misconfigured` | The execution role cannot call that model. Do `BEDROCK_MODEL_ID` and the destinations in `infra/lib/models.ts` agree? `vp run ai:logs` |
| The API answers 429 with `code` `throttled` | You exceeded the account's quota. Check that model's limit in Service Quotas |
| The last event is `error` with `interrupted` | The stream was cut midway. If `retryable` is `true`, you can send the same request again |
| The response arrives all at once at the end | Is the URL's `InvokeMode` `RESPONSE_STREAM`? If you put a proxy in between, is it buffering? Look at the times in `ai:smoke` |

## Going to production

- **Let a browser call it.** The official documentation describes putting CloudFront in front of the function URL and having CloudFront sign requests with origin access control. The URL stays `AWS_IAM`. On its own, though, that lets anyone who knows the CloudFront URL call, so the app has to verify the access token from chapter 06. The documentation also says that for POST the SHA-256 of the body must be sent in the `x-amz-content-sha256` header. This chapter builds none of that
- **Add a limit per user.** The only limit so far is per call. The same person calling 10,000 times is billed 10,000 times. A limit on the count needs authentication that tells users apart, and a place to keep the count
- **Check the account's quota.** Inference has a limit on token usage for each model. According to the documentation, the values actually applied to an account can be lower than the published defaults. Look up your own in Service Quotas (this chapter did not check the values)
- **Add a budget notification.** That is Budgets, from chapter 01. A notification does not stop spending. The limits above do
- **Decide where the data may go.** A `jp.` profile stays in Japan; `global.` is worldwide. Decide where the data may be processed before you choose a model
- **Track the model's end date.** Each model card gives an end-of-life indication. Claude Haiku 4.5, for instance, is "EOL no sooner than 2026-10-16". The model ID is an environment variable because the day to change it will come
- **Move deployment to the AWS CDK CLI and CloudFormation.** As discussed in chapter 02

## Cleanup

```bash
vp run ai:infra:destroy
```

The function, the function URL, the role, and the log group are deleted, along with the logs.

What remains is the storage created by cdkd's bootstrap (chapter 02) and the deployment files in it. On the Bedrock side, this chapter created no resources. If you called a Marketplace model even once, however, that subscription stays in the account. It costs nothing unless you call the model, but it has not "gone away", so keep it in mind.
