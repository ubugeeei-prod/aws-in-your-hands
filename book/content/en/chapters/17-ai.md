# 17 AI: Bedrock

On Workers AI, one line of `env.AI.run()` gets you an answer from a model. The AWS service that plays this part is Amazon Bedrock.

In this chapter you first call a model once, in a few lines of code. Then you build an API that summarizes the body of a note and returns the summary piece by piece as it is generated. The code that calls the model is about as short as it is on Workers AI. What takes more code is everything around the call, which decides who may call, how much may be spent, and what happens when the stream is cut.

Calling a model is billed by the token, and that holds when the call comes from a server on your own machine. For that reason the tests and the default development server in this chapter run without calling a model. Each task that is billed is marked as billed where it appears.

You need [chapter 04](/en/chapters/04-http-api.md). The code is in `examples/17-ai/`.

Two things differ from chapter 04.

The first is the entry point. The API Gateway HTTP API from chapter 04 waits for the whole Lambda response before it returns anything to the caller, so it cannot return a response piece by piece. This chapter uses a **function URL** instead, an HTTPS endpoint attached directly to a Lambda function. A function URL has a response streaming mode that sends the caller whatever the function has written so far.

The second is that Bedrock sits behind Lambda. Bedrock generates the text, and the function in this chapter only relays the events Bedrock returns to the caller.

### Choosing the entry point

According to the official documentation, there are three ways to get a Lambda streaming response out to a caller.

- A function URL (`RESPONSE_STREAM`)
- An API Gateway REST API, with the response transfer mode of a proxy integration set to `STREAM`. HTTP APIs do not have this feature
- Calling `InvokeWithResponseStream` directly from an SDK

This chapter chose the function URL because it adds only one resource. In exchange, the only authentication a function URL has of its own is an IAM signature. If you need API keys, WAF, or a Cognito authorizer, choose the REST API (see the table in chapter 04). How to let a browser call the API is covered under [Going to production](/en/chapters/17-ai/wrap.md).

### Never leave it open to everyone

A function URL authenticates with either `AWS_IAM` or `NONE`. With `NONE`, anyone who knows the URL can invoke the function. This function runs a model every time it is invoked, so strangers could run inference on your bill.

This chapter therefore uses `AWS_IAM`. With `AWS_IAM`, Lambda checks the request's SigV4 signature before it runs the function. A SigV4 signature is how AWS APIs establish who is calling. Only a caller in the same account who is allowed `lambda:InvokeFunctionUrl` and `lambda:InvokeFunction` can call the URL, and in this chapter that caller is a script that signs with your credentials.

AWS credentials cannot be kept in a browser, so an SPA cannot call the URL directly. The outline written before this chapter planned to connect an SPA, but that needs the sign-in from [chapter 06](/en/chapters/06-auth.md). This chapter requires only chapter 04, so it puts not creating a public endpoint without authentication first and does not connect an SPA.

## Choosing a model

<!-- section: 17.models -->

Deciding what to put in `modelId` takes far more work than on Workers AI, because on Bedrock each model differs in which Regions it can be called from and by which route. There are three routes.

- In-Region processes the request only inside the Region you called. You pass the model ID as it is
- Geo processes it in one of the Regions inside a fixed geography
- Global processes it in one of the commercial Regions anywhere in the world

For Geo and Global you pass the ID of an **inference profile** in place of the model ID. An inference profile is a name for a model together with the Regions a request may be sent to. The mechanism is called cross-Region inference.

So calling the Tokyo endpoint does not mean that inference runs in Tokyo. A profile that starts with `jp.` processes the request in Tokyo or Osaka, and one that starts with `global.` processes it anywhere in the world. If you have rules about where your data may be processed, check the destinations before you choose a model. The official documentation also says to check the destinations and not to judge by the prefix of the ID alone.

### Getting access

Bedrock used to have a console page where you requested access model by model. The current documentation says that many models can be used from the start. Two steps remain.

- Anthropic models need a use case form submitted once, the first time. It is submitted once per account or organization
- For models sold through AWS Marketplace (Anthropic's among them), Bedrock starts a subscription in the background on the first invocation. The caller needs permissions such as `aws-marketplace:Subscribe`, and the subscription can take up to 15 minutes to complete. Amazon's models do not go through Marketplace

The Lambda function in this chapter cannot complete the second step, because its execution role has no Marketplace permissions. If you switch to an Anthropic model, first get `vp run ai:hello` to pass once with your own permissions. Once the model is enabled, callers no longer need the Marketplace permissions.
