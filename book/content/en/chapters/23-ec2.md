# 23 EC2 When You Want Control: SSM, EBS, and Process Management

So far you have not owned a single server. Lambda runs only when it is called, and AWS looks after the operating system. This chapter goes the other way: you own the machine, operating system and all.

You will build one EC2 instance, which is one virtual machine. No SSH port is opened. The notes API from [chapter 04](/en/chapters/04-http-api.md) runs on it as a systemd service, and the notes live on a disk separate from the instance.

Money first. This chapter creates things that are **billed by the hour just for existing**. The default layout costs about USD 2.33 a day and USD 70.74 if you leave it for a month (730 hours). Stop the instance and it still costs USD 62.86. The cheaper layout is USD 0.43 a day and USD 13.07 a month. The breakdown comes right below. Once you have tried it, please go all the way to the cleanup section the same day.

You need the VPC from [chapter 11](/en/chapters/11-network.md). The code is in `examples/23-ec2/`.

## Why EC2, at this point?

<!-- section: 23.why -->

If the Lambda function from chapter 04 is enough, you do not need EC2. It costs nothing while unused and AWS patches it for you. It is hard to find an easier place to put code.

You start wanting a machine of your own in cases like these.

- **A process has to run for a long time.** One Lambda invocation lasts 15 minutes at most. Holding connections for hours, or keeping a large index in memory, is not what it is for
- **You need to touch the operating system or the kernel.** Kernel parameters, file systems, fine network settings. Neither Lambda nor Fargate gives you a kernel you can change
- **You need special hardware.** GPUs, a lot of memory, fast disks attached directly to the instance
- **You want to run software that no managed service offers.** A database or daemon you operate yourself. celld in chapter 24 is exactly that

In exchange, work that AWS has been doing becomes yours.

- Patching the operating system and the runtime
- Restarting the process when it dies, and noticing that it died
- The disk: whether it fills up, and how to get it back when it breaks
- What starts, and in what order, when the machine boots
- And the fact that when this one machine stops, everything stops

This chapter deals with these five, one at a time. The last one cannot be dealt with. The section on a single point of failure states the conditions for accepting it.

## What it costs just to exist

<!-- section: 23.cost -->

Amounts are in USD, for the Tokyo Region, at on-demand list prices, before tax, with a month of 730 hours. The arithmetic is in [Pricing Worksheets](/en/reference/pricing.md).

| Layout | Running, one day | Running, one month | Stopped, one day | Stopped, one month |
| --- | --- | --- | --- | --- |
| Default (private subnet) | 2.33 | 70.74 | 2.07 | 62.86 |
| `-c placement=public` | 0.43 | 13.07 | 0.05 | 1.54 |

Here is what is inside.

- **The instance**: a `t4g.micro` (2 vCPU, 1 GiB) is USD 0.0108 an hour, 7.88 for 730 hours
- **The volumes**: gp3 is USD 0.096 per GB-month. An 8 GiB root volume and an 8 GiB data volume come to 1.54. The AMI decides the size of the root volume, and 8 GiB is an assumption that was not checked on a real instance
- **A public IPv4 address** (only with `placement=public`): USD 0.005 an hour, 3.65 for 730 hours
- **Interface endpoints** (only in the default layout): USD 0.014 an hour each, per zone. Three of them in two zones come to 61.32 for 730 hours

Three things to take from the table.

**Stopping does not stop the volume charges.** When you stop an instance, only the instance charge stops. The disks are still there with their contents, and you keep paying for the space. "Stop it when idle and it costs nothing" is not true.

**Most of the default layout's cost is the endpoints.** And the endpoints belong to the chapter 11 stack, so stopping or deleting this chapter's instance does not stop them. Why they are the default anyway is explained under "No SSH port".

**With public IPv4 addresses, the kind matters.** `placement=public` in this chapter uses an address that is assigned automatically at each start. It is released when the instance stops, and the charge stops with it. The next start brings a different address. If you want a fixed one and use an Elastic IP address, that one is billed while the instance is stopped too. This chapter uses no Elastic IP address.

There is one more trap that the table does not show. T-family instances such as `t4g` normally use little CPU and spend saved-up CPU credits to run flat out for a while. Left alone, they launch in a mode called unlimited: they may keep running flat out after the credits are gone, and the excess is billed at USD 0.04 per vCPU-hour. A runaway process turns straight into a bill. This chapter's stack sets standard mode. When the credits run out the instance gets slow, and the bill does not grow.

How the instance is counted is in code.

## No SSH port

<!-- section: 23.access -->

Getting into a server used to mean SSH. Open port 22, hand out keys, put a bastion in front. This chapter does none of that. An open port is a way in for attackers, and a key stays on somebody's laptop for good.

Session Manager, a part of Systems Manager, takes its place. Here is how it works. A process called SSM Agent runs on the instance and opens an HTTPS connection toward Systems Manager. When you call `aws ssm start-session`, Systems Manager connects a shell through that connection. It is always the instance that starts the connection, which is why not a single inbound rule is needed. Who may get in is decided by IAM, not by a key.

Three things are required.

1. **SSM Agent.** The Amazon Linux 2023 AMIs that AWS publishes come with it installed
2. **Permissions.** The instance's role gets a managed policy called `AmazonSSMManagedInstanceCore` (next section)
3. **A path to Systems Manager.** This is the part that costs money

There are three ways to make that path. The amounts are for one month with no traffic at all.

| Where the instance sits | The way to Systems Manager | Cost of the way |
| --- | --- | --- |
| Private subnet | Three interface endpoints (`ssm`, `ssmmessages`, `ec2messages`) | 61.32 |
| Private subnet | A NAT gateway | 48.91 (`-c egress=nat` in chapter 11) |
| Public subnet | The internet gateway, and a public IPv4 address on the instance | 3.65 |

Whichever you choose, inbound stays empty. Even in a public subnet, nothing outside can start a connection to the instance.

### The default is the private subnet

To be honest, this was a close call. For just trying things out, the public subnet costs less than a fifth.

Two reasons made the private subnet the default anyway. First, a machine with a public IPv4 address is one security group rule away from being reachable from outside. Inbound is empty today, but somebody will touch the settings of a long-lived machine someday. Second, outbound traffic. An instance in a public subnet can reach anywhere on the internet on port 443. In the private subnet it reaches Systems Manager and S3, and that is all. When software on it is taken over, what the attacker can do differs.

A machine that stays for a long time, and anything that runs as several machines like chapter 24, normally goes into private subnets, so the default follows that. For a single pass through this chapter, `-c placement=public` is plenty. Inbound is empty there as well, and a test pins it.

## The instance fetches its permissions from inside

<!-- section: 23.role -->

A Lambda function had an execution role, and an instance gets a role as well.

<<< @/examples/23-ec2/infra/lib/ec2-stack.ts{role}

EC2 cannot take a role directly. You put one role into a container called an instance profile and attach that to the instance. CDK's higher-level constructs do this silently, but writing it out shows what is being created.

`AmazonSSMManagedInstanceCore` is a policy that AWS maintains. Reading it, every statement is for `"Resource": "*"`, and `ssm:GetParameter` is among the actions. A process on this instance can therefore read values from the account's Parameter Store if it tries. The book has avoided `*` since chapter 04; using an AWS policy as it is makes this the exception. Only one permission was added by hand: reading under `releases/` in the bucket that holds releases.

### Where do the credentials come from?

The AWS CLI and the SDKs on the instance work without any access key being configured. Where do they get credentials?

The answer is IMDS, the Instance Metadata Service. There is an address, `169.254.169.254`, that is reachable only from inside the instance, and asking it returns temporary credentials for the role. They expire and are replaced automatically. This is why no key has to sit on the disk.

Convenient, and it has a weak spot: anything running on the instance can ask that address. Suppose the application has a feature that fetches a URL the user supplies. Given `http://169.254.169.254/...`, the application might fetch the credentials and hand them back in its response.

IMDS has two versions. Version 1 answers a plain GET, and the attack above goes straight through. Version 2 has you obtain a token with a PUT first and send it in a header with each request. A hole that only allows "make it GET one URL" can do neither the PUT nor the header. On top of that, a PUT carrying an `X-Forwarded-For` header is rejected, which keeps out requests relayed by a proxy.

<<< @/examples/23-ec2/infra/lib/ec2-stack.ts{instance}

`httpTokens: "required"` allows version 2 only. `httpPutResponseHopLimit` is how many network hops the reply with the token may travel. With 1 it reaches the instance itself and nothing behind it. If you run containers on the instance and want them to use the role, it has to be 2. The Amazon Linux 2023 AMI reportedly launches with version 2 required and a hop limit of 2 even when nothing is specified, but the stack writes the values down instead of relying on defaults of the AMI or the account.

One thing version 2 does not change: there is one role per instance, shared by every process on it. The notes API runs as `notes`, a user with few privileges, and it can still obtain the same credentials by going through the token steps. Think of the permissions on an instance's role as permissions given to all the code that runs on that machine.

## Choosing an AMI

<!-- section: 23.ami -->

An AMI (Amazon Machine Image) is the template for an instance's first disk. This chapter uses the arm64 build of Amazon Linux 2023.

An AMI has an ID such as `ami-0123...`, which differs by Region and changes with every new release. Write the ID into code and it is out of date in no time. So AWS publishes "the ID of the newest AMI" as a public parameter in Parameter Store.

<<< @/examples/23-ec2/infra/lib/ec2-stack.ts{ami}

Synthesizing this puts one parameter of type `AWS::SSM::Parameter::Value<AWS::EC2::Image::Id>` into the template. The value is looked up at deploy time, and synthesis asks AWS nothing. The test checks that the parameter is named `/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-arm64` and that synthesis leaves no lookup behind.

This took two stumbles to get right, with the pinned version (aws-cdk-lib 2.273.0).

First, the commonly shown `MachineImage.latestAmazonLinux2023()` ignores a `kernel` option and asks for the parameter of the 6.1 kernel. According to the Amazon Linux documentation, `kernel-default` has meant 6.18 since August 2026. Second, using `AmazonLinux2023ImageSsmParameter` directly instead makes it try, by default, to look the AMI up during synthesis, and synthesis fails for a stack without an account. It needs `cachedInContext: false`.

### "Latest" is a trigger for replacement

A handy mechanism, and a poor match for a machine that lives long.

When the AMI ID changes, the instance is **replaced**. The CloudFormation documentation lists a change to `ImageId` as Replacement, and the cdkd source treats it the same way. New AMIs come out often. In other words, deploying the same code as last month can swap the machine for a brand-new one. What was on the root volume goes away with the old instance. A comment in the CDK type definitions says as much: with this image, do not keep state on the instance.

That is why this chapter does two things. One is to keep data that must not be lost off the root volume (see "Data goes on a separate volume"). The other is to let you pin the AMI.

```bash
aws ssm get-parameter --region ap-northeast-1 --name /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-arm64 --query Parameter.Value --output text
vp run ec2:infra:deploy -c amiId=ami-xxxxxxxxxxxxxxxxx
```

The first line prints the current ID (it needs credentials). Pass it with `-c amiId=` and the template holds the ID itself, which does not change until you change it. For practice, "latest" is fine. For a machine you leave running, pin it and patch on your own schedule (see "Patching").

Either way, get into the habit of reading `vp run ec2:infra:diff` before a deploy. To be honest, whether cdkd's diff shows a change of the AMI behind the parameter as a replacement was not verified.

## What the first boot does

<!-- section: 23.user-data -->

A freshly started instance has no Node.js, no notes API, and no user to run it as. Providing them is the job of user data. Hand a shell script to the instance at launch and it runs as root on the first boot.

The script is put together by a TypeScript function.

<<< @/examples/23-ec2/src/user-data.ts{user-data}

It does five things: installs Node.js, creates a user with few privileges, writes the settings file, the systemd unit, and two scripts, enables the service, and prepares the data volume. The result is kept in `examples/23-ec2/deploy/user-data.sh`, so you can read exactly what runs without reading TypeScript.

The function is pure. Its only input is the settings: no clock, and no value that is decided at deploy time. The same settings always give the same script. What the tests read is therefore what the instance runs.

### Distrust every value that enters a root shell

User data runs as root. Settings are embedded in it as text, so if `; rm -rf /` or `$(...)` slips into a value, it is executed as written.

<<< @/examples/23-ec2/src/machine.ts{spec}

Every embedded value passes through this schema. Paths are letters, digits, `.`, `_`, and `-` only. Names are short strings that start with a lowercase letter. No quotes, no spaces, no line breaks. The tests confirm that with a dangerous value in any field, generating the script itself stops with an exception.

No secrets go in either. User data can be read through IMDS by any process on the instance, and from outside by anyone who may call `aws ec2 describe-instance-attribute`. This chapter's sample has no secrets, but if it had, this would not be the place for them. A test also checks that the settings file has exactly six entries: the allowed origin, the log level, the stage, the host, the port, and the path of the notes file.

### The limits of user data

Useful, and it hurts if you lean on it too much.

**It runs once.** On the first boot only. Fix the script and deploy later, and it does not run again on the running instance. As far as the cdkd source shows, a change to `UserData` does not even reach the instance. CloudFormation would restart the instance, and the script would still not run. To change how the machine is set up, you replace the instance or go in and change it by hand.

**Failures are hard to notice.** If the script dies on line 5, the instance is still running. As far as EC2 can tell, the operating system is up. This script uses `set -euo pipefail` so that it stops at the first failure: a stopped machine is easier to spot than a half-configured one. `vp run ec2:status` shows the result. The output stays in `/var/log/cloud-init-output.log` on the instance.

**16 KB at most.** The script is about 4 KB today. It is not a place to stuff application code.

That last point shapes the design. User data prepares the machine and does not install the application, because the application is something you replace many times. The way to replace it is built under "Deploying, and getting in".

## Turning a process into a service

<!-- section: 23.service -->

Type `node server.mjs` and the API runs. But it stops when the session closes. Nobody restarts it when it dies. After a reboot, somebody has to type it again.

systemd takes that over. It is the program that starts first on Linux and looks after the other processes, and a file called a unit tells it what to run, as whom, how, and what to do when it dies.

<<< @/examples/23-ec2/deploy/notes.service

Let's read it from the top.

`RequiresMountsFor` and `AssertPathIsMountPoint` say: do not start unless the data volume is mounted. Without them, something scary can happen. If the API comes up after the volume preparation failed, the notes are written to the same path on the root volume. Everything looks fine, and it is all gone the day the instance is replaced.

`ConditionPathExists` says: if the application itself is not there yet, quietly skip the start. Before the first release, that is the normal state.

`User=notes` runs the process as a dedicated user, not as root. `ProtectSystem=strict` shows the whole file system to this process as read-only, and the data volume listed in `ReadWritePaths` is the only exception. If the API has a hole, that is the only place that can be overwritten.

`Restart=on-failure` restarts the process two seconds after an abnormal exit. Restarting a process that dies at every start forever is pointless, though, so `StartLimitBurst` gives up after five deaths within a minute. A service that was given up on stays in the `failed` state, which you can see.

`/usr/bin/node-24` in `ExecStart` is the executable with the version in its name, installed by the `nodejs24` package of Amazon Linux 2023. Plain `node` can be switched to point at another version, so it is not used.

Environment variables are not written into the unit. `EnvironmentFile` reads them from a separate file, and `HOST=127.0.0.1` in there confines the API to the instance. Even if somebody opens the security group, it cannot be reached from outside.

The meaning of these directives was checked in the man pages of systemd 252. The version that Amazon Linux 2023 ships was not looked at on an instance.

### Where do the logs go?

The chapter 04 application writes its logs to standard output as JSON. Under systemd, they collect in a facility called journald. Amazon Linux 2023 has no traditional `/var/log/messages`.

```bash
vp run ec2:logs
```

This task runs `journalctl --unit notes.service` through Run Command and brings back the last 50 lines.

The difference from Lambda is that these logs are on the instance's root volume. When the instance goes, the logs go. Exactly when you want to know why it died, there are no logs. Avoiding that means shipping the logs out. The CloudWatch agent can send journald entries to CloudWatch Logs, but from a private subnet it needs one more interface endpoint, `logs`, which adds USD 20.44 a month, and the role needs permissions for it. This chapter does not set it up. It is the kind of thing that is too much for a practice machine and required for a production one.

## Stopping politely

<!-- section: 23.shutdown -->

A service gets stopped. Every release restarts it, and the operating system reboots now and then. When that happens, systemd sends the process a signal called SIGTERM: a request to stop.

Left alone, Node.js exits on the spot. Requests that were being handled are cut off without a response. If a note was being saved, the caller cannot even tell whether it was saved.

<<< @/examples/23-ec2/src/shutdown.ts{shutdown}

When asked, refuse new connections, finish the requests in flight, wait for the writes to reach the disk, and then exit. That is a graceful shutdown.

```text
time  systemd                    notes process                         client
t0    systemctl restart   --->   SIGTERM received
t1                               listening socket closed               new connection: refused
t2                               request in flight finishes  --->      201 for the request sent before t0
t3                               pending file writes flushed
t4                               exit 0
t5    starts the new process     listening again                       connections accepted

if t2 has not happened 20 s after t0:  remaining connections closed, exit 1
if the process is still there 30 s after t0 (TimeoutStopSec):  systemd sends SIGKILL
```

Waiting has a limit. A request that has not finished after 20 seconds is cut from this side. systemd sends SIGKILL at 30 seconds (the unit's `TimeoutStopSec`), and that cannot be resisted, so the process settles things itself before then. A test watches the order of these two numbers. Change only one and it fails.

Here is where it is put together.

<<< @/examples/23-ec2/src/server.ts{server}

`createApp` is imported from chapter 04 as it is. Not one line of the application changed. What changed is around it: a file instead of a `Map`, a process that stays instead of a function, and a place to receive signals.

The test opens a real socket to check this. It sends a request, holds it halfway through, and calls the shutdown. After seeing a new connection refused, it lets the held request go on. The first request gets its 201, then the writes are awaited, then the process ends with exit code 0. That order is pinned.

Between t1 and t5 in the diagram, nobody is listening. It is a few seconds, but a request that arrives then fails. With one machine, a restart is always an outage. Removing it takes a second process and a load balancer in front of both ([chapter 12](/en/chapters/12-containers.md)).

## Data goes on a separate volume

<!-- section: 23.data -->

In chapter 04 the notes were in a `Map`, and they vanished when the execution environment was replaced. This time there is one process, and it keeps running. So the notes go into a file.

<<< @/examples/23-ec2/src/file-notes.ts{repository}

It implements the `NoteRepository` interface from chapter 04 unchanged.

What it has to guarantee, in one sentence: **a note that was answered with 201 can be read after the process restarts and after the instance is replaced.**

What attacks that is a stop in the middle of a write. If the power goes after half the file was written, what is left does not parse as JSON. At the next start, not a single note can be read.

<<< @/examples/23-ec2/src/file-notes.ts{storage}

So the file is never overwritten directly. A new file is written beside it, confirmed to have reached the disk, and then renamed over the old one. A rename either happened or did not. A reader sees the old content or the new content, never a mixture.

The test cuts the power at each of the three steps in turn: the write, the rename, and the directory sync. Wherever it stops, the file that remains reads in full and agrees with what is in memory. When a damaged file is found, the process refuses to start instead of starting empty. Starting empty would overwrite the damaged file with an empty one at the next write.

Now the honest part. The reverse does not hold. If the directory sync fails after the rename, the caller gets a 500 and the note is saved anyway: "told it failed, and yet it is there". If the caller retries, there are two copies of the note. The chapter 04 API has nothing that prevents duplicates. Also, this class is correct for one process only. If two processes open the same file, whichever writes later erases the other's write. What guarantees that there is one is systemd, not the code.

Against a real disk, it is implemented like this.

<<< @/examples/23-ec2/src/node-files.ts{node-files}

### Which disk is that file on?

An instance's disks are EBS volumes: disks attached over the network, which can exist as resources of their own, apart from the instance.

An instance comes with one root volume. It holds the operating system, is created from the AMI, and is deleted along with the instance. Put the notes there and, as "Choosing an AMI" showed, one deploy can erase them.

So one more volume is created.

<<< @/examples/23-ec2/infra/lib/ec2-stack.ts{data-volume}

The point is that it is a separate resource, not something written inside the instance's settings. When the instance is replaced, this volume is not deleted. By EC2's own default, too, a volume attached after launch stays when the instance is deleted.

Then when is it deleted? When the stack is destroyed. `dataOnDestroy` decides that, and the default is `delete`: this is for practice, so it goes with the stack and nothing is left behind. In production use `snapshot` (take a snapshot before deleting) or `retain` (keep the volume). Either way, what remains keeps costing money.

A volume belongs to one Availability Zone and attaches only to an instance in the same zone. The code passes the instance's zone to it. If you ever want to move the instance to another zone, the volume cannot follow. You take a snapshot and restore it in the new zone.

### Format an empty volume, once

A new volume is blank. It needs a file system, and it needs to be mounted.

<<< @/examples/23-ec2/deploy/notes-data-volume.sh

The most important part of this script is the `case`. `mkfs` erases what is on a volume. Run it against a volume with contents and every note is gone. And this script runs on the first boot of a new instance, which means it also runs when the instance was replaced and the old volume was attached again.

So it formats only when it has confirmed that there is no file system. Told there is one, it leaves the volume alone. When it cannot tell, it also leaves the volume alone, and stops with a failure.

The test really runs this script with bash. Only the commands that touch a disk (`blkid`, `mkfs.xfs`, `mount`, and so on) are replaced with stand-ins that record that they were called. It formats on a first instance, runs again on a second instance (a fresh fstab, the same volume), and confirms that `mkfs` was called exactly once.

There are smaller details too. The volume is attached after the instance starts, so the script waits up to five minutes for the device to appear. `/etc/fstab` gets the UUID, not the device name: on current instances, EBS volumes show up as NVMe devices whose names can swap between boots. `nofail` says that the operating system boots even without the volume. Without it, an instance whose volume was detached would not boot, and you could not even get in to fix it.

## Snapshot and restore

<!-- section: 23.backup -->

There is one data volume. If it breaks, every note is gone. The safeguard is a snapshot: a copy of the volume at a point in time, kept in S3, and restorable as a volume in any zone of the Region. Snapshots are incremental, so from the second one on only what changed is stored.

The procedure in this section, too, was only checked as far as the flags of the commands, against the help of the AWS CLI in the devShell.

### Taking one

```bash
vp run ec2:data:unmount
aws ec2 create-snapshot --region ap-northeast-1 --volume-id vol-xxxxxxxxxxxxxxxxx --description "notes before the upgrade"
vp run ec2:data:mount
```

The volume ID is the stack output `DataVolumeId`.

Copying a volume that is being written to can capture a half-finished state. So the service is stopped and the volume unmounted first. A snapshot captures the contents at the moment it starts, and there is no need to wait for it to complete. Once its state is `pending`, the third line mounts the volume again and starts the service. The API is down in between.

What `ec2:data:mount` runs is the same script as on the first boot, with the same decision not to format.

### Going back

The most straightforward way is to let the stack create the volume from the snapshot.

```bash
vp run ec2:infra:deploy -c dataSnapshotId=snap-xxxxxxxxxxxxxxxxx
```

After the stack was destroyed, this creates the instance and a volume with the snapshot's contents. The first-boot script sees a file system and mounts it without formatting. Then `vp run ec2:app:release`, and the notes are back. The same goes for a zone that has become unusable: if the chapter 11 VPC has a subnet in another zone, you can restore there (this chapter's stack is fixed to the first zone, so that needs a code change).

Adding `dataSnapshotId` to a running stack is a different matter. In the CloudFormation documentation, a volume's `SnapshotId` is a property that cannot be updated. In the cdkd source it replaces the volume, and is refused unless `--force-stateful-recreation` is given, because the operation deletes the old volume. This path was only read, not run.

A volume created from a snapshot can be slow at first. Its contents are brought from S3 only when they are first read.

And last, the thing that is easiest to forget: a snapshot is not a resource of the stack. Destroy the stack and it stays, and keeps costing money. The cleanup section checks for it.

## Patching

<!-- section: 23.patch -->

With Lambda, patching the operating system was AWS's job. Here it is yours.

Amazon Linux 2023 has a property that surprises people who do not know it. An instance is **locked** to the package versions of the moment its AMI was built. Type `dnf upgrade` and nothing new arrives. Security updates are not applied on their own either. The same command gives the same result last month and this month, and that is the purpose.

In other words, if you do nothing, the machine grows old as it was on the day it started. There are two ways to patch.

**Upgrade in place.** Check whether a newer release exists, and upgrade to it by name.

```bash
vp run ec2:patch:check
vp run ec2:patch:apply 2023.12.20260930
```

The argument on the second line is a version that the first line printed. `latest` is not accepted. The Amazon Linux documentation says the same thing: asking for `latest` means trying an untested update in production first. If the kernel was updated, the old kernel keeps running until a reboot. Reboot with `aws ec2 reboot-instances`. The API is down while that happens.

**Replace.** Swap the instance for one from a newer AMI. All it takes is deploying with a new ID in `-c amiId=` from "Choosing an AMI". User data runs from the beginning, the data volume is attached again, and you install the release once more. No trace of manual changes remains, so the result is easier to predict. The Amazon Linux documentation recommends this way too.

There is something unknown here, though. How the volume attachment behaves during a replacement could not be worked out from the cdkd source: whether cdkd detaches it from the old instance and attaches it to the new one in that order, or fails midway. Until it has been tried on real AWS, this path is "should work". When you try it, take a snapshot first.

Systems Manager also has a feature called Patch Manager: find missing patches, apply them, list what is compliant. Once there are many machines, you will want it. One caution: according to the documentation, Patch Manager ignores the Amazon Linux 2023 version lock and always uses the latest repositories. This chapter does not configure it.

### The idea of staying replaceable

Take "replace" to its conclusion and you arrive at an Auto Scaling group. Give it a recipe for the instance (a launch template) and a count, and it replaces an instance that becomes unhealthy with a new one. With a count of one, "there is always one machine" becomes AWS's job.

This chapter does not build one. The reason is that if replacement happens automatically, everything a replacement requires must be automatic too: attaching the data volume again, and installing the release again. In the current layout both need a person. Whether automating that far is worth it is a decision to make together with the next section.

### What is yours on a long-lived machine

- **Patches for the operating system and the runtime.** Node.js is an operating system package too. It is upgraded the same way
- **Free disk space.** The journald logs and the old versions in `/opt/notes/releases` grow if left alone. Deleting them is up to you
- **The gap between the code and the real thing.** What you fixed by hand in a session is recorded nowhere. The next machine you build will not have that fix. The drift check looks at the settings of AWS resources, not inside the operating system
- **Backups.** Not just taking them: being able to restore them

## One machine is a single point of failure

<!-- section: 23.spof -->

In this chapter's layout, state lives in one place: one file, on one volume, in one zone. One process reads and writes it.

What stops when something happens, and what comes back? Side by side:

```text
event                              API stops for        comes back by itself?                      the notes
process crashes                    about 2 s            yes: systemd, Restart=on-failure           kept
release, or a restart              a few seconds        yes: part of the same command              kept
OS hangs, kernel panics            until you act        no: the instance status check fails        kept
host hardware fails                minutes (unmeasured) usually: automatic recovery, same instance kept; memory is lost
instance terminated or replaced    until you redeploy   no: deploy again, then release again       kept: the volume is its own resource
data volume lost or damaged        until you restore    no: restore from a snapshot                back to the last snapshot
zone ap-northeast-1a impaired      as long as it lasts  no: this stack has nothing in another zone unreachable until the zone is back
```

The first two rows are handled by what this chapter built.

The fourth row is handled by EC2. Every minute EC2 runs status checks, and when something is wrong with the infrastructure on AWS's side (power, network, the physical host), automatic recovery moves the instance to other hardware. It is on from the start for instances that support it. The instance ID, the IP addresses, the attached volumes, and the zone all stay the same. Only what was in memory is lost. For the notes API, that is the same as a reboot.

Do not lean on it too much, though. Recovery acts only when the infrastructure check fails. When the operating system itself is stuck, as in the third row, the other check (the instance status check) fails, and nothing is done about it. Fixing it is up to you. And recovery does not act when the hardware to move to has no capacity, or while the AWS Health Dashboard lists a service event. In a large outage, which is exactly when you want the help, you cannot count on it.

From the fifth row on, a person has to act. If it is the middle of the night, things stay down until morning.

### Conditions for accepting one machine

So this is not saying "one machine is wrong". For many uses, one is enough. But if you accept it, put the conditions into words.

1. **The time it may be down is longer than the time it takes a person to notice and fix it.** It will be down for minutes to hours, nights and holidays included
2. **Going back to the last snapshot is acceptable.** Or the data can be rebuilt from somewhere else
3. **Somebody notices that it stopped.** Without a way of noticing, the time in condition 1 is unbounded
4. **The rebuild procedure has been run at least once.** A first restore on the day of the failure is something to avoid

If you can say yes to all four, one machine is the right choice. It is cheap, simple, and you can see everything that is going on.

If you cannot, you need a second machine, in another zone. And here you notice something: this chapter's layout cannot simply become two machines, because the notes are in a file on one of them. To have two, state has to move off the machine (DynamoDB from chapter 05, or the database from chapter 13), with a load balancer in front. Go that far and much of the reason for owning the machine is gone. Fargate in chapter 12 does the same with far less work.

One EC2 instance is for when you want state on the machine and one machine's worth of reliability is enough. celld in chapter 24 is the step after that: several machines, with state still on them.

## Lambda, Fargate, EC2

<!-- section: 23.compare -->

The same API can now live in three places (Fargate is [chapter 12](/en/chapters/12-containers.md)). Side by side:

| | Lambda (chapter 04) | Fargate (chapter 12) | EC2 (this chapter) |
| --- | --- | --- | --- |
| What runs | An execution environment, only when called | A container kept running | A machine kept running |
| Length of one piece of work | 15 minutes at most | No fixed limit | No fixed limit |
| Cost when nobody calls | 0 | Billed | Billed. Volumes are billed even when stopped |
| The kernel | Not yours to touch | Not yours to touch | Yours |
| Local disk | `/tmp`, temporary, per execution environment | Temporary, per task (20 GiB by default) | An EBS volume that can outlive the instance |
| OS patches | AWS | The host is AWS's. What is in the image is yours | All yours |
| When it dies | A new environment at the next call | The service replaces the task | systemd restarts the process. Beyond that, you |

A good way to choose is to go from the top. If Lambda will do, use Lambda. If the work does not fit in 15 minutes or connections have to stay open, Fargate. EC2 is for what is still missing after that: the kernel, the hardware, a disk on the machine.

The further down, the more you can do and the more you have to do. EC2 really is the freest of the three, but that does not mean the most capable. It means the widest range of things you do yourself.

"Billed" in the Fargate column carries no amount because the unit prices were not checked in this chapter. The amounts are under "What it costs" in [chapter 12](/en/chapters/12-containers.md).

## Where people get stuck

| When this happens | Look here |
| --- | --- |
| `ec2:infra:deploy` fails to resolve an import | Is the chapter 11 stack (`AihNetwork`) deployed? |
| `ec2:status` says the instance is not registered with Systems Manager | There is no path. Give `vp run ec2:plan` the settings chapter 11 was deployed with and look for `UNREACHABLE`. In the first few minutes after launch, registration may simply not be finished |
| It is `Online`, but there is no service and no `/opt/notes` | User data failed partway. Look at the cloud-init line of `ec2:status`, then connect with `ec2:session` and read `/var/log/cloud-init-output.log`. If it stopped at `dnf`, the package repositories were not reachable |
| `ec2:app:release` ends with `AccessDenied` | The instance's role may read only under `releases/` in the release bucket |
| After a release, it says `/health` did not answer | `vp run ec2:logs`. `Invalid environment` points at the settings file, `refusing to start over it` at a damaged notes file |
| The service stays `failed` | It died five times in a minute and systemd gave up. Fix the cause, then release again |
| The service refuses to start and the log talks about a mount | The data volume is not mounted. `vp run ec2:data:mount` |
| `ec2:session` says the plugin is missing | The Session Manager plugin is installed separately from the AWS CLI |
| A deploy replaced the instance | The "latest" AMI changed, or you passed a different `-c` than last time. Read the `diff` first. The AMI can be pinned with `-c amiId=` |
| `ec2:infra:destroy` stops while detaching the volume | Run `vp run ec2:data:unmount` first. A mounted volume does not detach cleanly |
| You stopped the instance and are still billed | The volumes, and the interface endpoints of chapter 11, are billed while it is stopped |

The symptoms in this table were put together from the documentation and the source. They were not reproduced.

## If this were production

- **Decide whether one machine is acceptable.** Answer the four conditions above. If any answer is no, this chapter's layout is not the one
- **Do not delete the data with the stack.** `-c dataOnDestroy=snapshot` or `retain`. Take snapshots on a schedule, and run a restore once
- **Pin the AMI and have a patch schedule.** With "latest", AWS's releases decide the day of the replacement
- **Send logs and metrics off the machine and add alarms.** So that the reason does not vanish along with the machine (for how to put an alarm together, see [chapter 19](/en/chapters/19-observability.md))
- **Narrow down who may get in.** Who holds `ssm:StartSession` and `ssm:SendCommand`? Sessions can be recorded as well
- **To publish the API, put a load balancer in front.** Do not open a port on the instance directly ([chapter 12](/en/chapters/12-containers.md))
- **Review the instance's role.** `AmazonSSMManagedInstanceCore` can read widely in Parameter Store. Check what is kept there
- **Turn on termination protection.** An instance has a setting that refuses termination through the API
- **Deploy with the AWS CDK CLI and CloudFormation.** The official cdkd documentation describes cdkd as for development and testing and recommends the AWS CDK CLI for production (chapter 02)
- **Set up a spending alert.** The budget from chapter 01 is the last net for an instance you forgot to delete. It is a notification, not a cap

## Cleaning up

<!-- section: 23.cleanup -->

There is an order.

```bash
vp run ec2:data:unmount
vp run ec2:releases:empty --yes
vp run ec2:infra:destroy
vp run net:infra:destroy
```

The first line puts the data volume into a state in which it can be detached. The second empties the release bucket: the pinned cdkd does not delete a bucket that is not empty (without `--yes` it only lists). The third deletes the instance, the volume, the bucket, and the role. The notes go too. The fourth deletes the VPC and the interface endpoints. To keep the VPC, run `vp run net:infra:deploy` without `-c` and only the endpoints are removed.

Stop after the third line and the endpoint charges (USD 61.32 a month) continue. The most expensive part of this chapter is outside this chapter's stack.

Check with your own eyes that things are gone.

```bash
aws ec2 describe-instances --region ap-northeast-1 --filters Name=instance-state-name,Values=pending,running,stopping,stopped
aws ec2 describe-volumes --region ap-northeast-1
aws ec2 describe-snapshots --region ap-northeast-1 --owner-ids self
aws ec2 describe-vpc-endpoints --region ap-northeast-1
```

If the first and second are empty and the fourth has no endpoint of the Interface type, the hourly charges have stopped. A snapshot in the third is one you took yourself or one that `dataOnDestroy=snapshot` left. If you do not need it, delete it with `aws ec2 delete-snapshot`. With `dataOnDestroy=retain`, a volume remains in the second.

What is left is only the storage that the cdkd bootstrap created (chapter 02).
